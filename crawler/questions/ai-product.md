## 1. 五、在线 AI 产品是怎么做的

> 原题 ID：`q2008` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

五、在线 AI 产品是怎么做的

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

在线AI产品本质是「模型+工程化服务」：把训练好的模型封装成可扩展、低延迟、可计费、可观测的在线API/应用，核心链路是请求接入→预处理→推理→后处理→返回，并围绕成本、延迟、稳定性做工程优化。

### 解析

在线AI产品可以类比成一家餐厅：模型是后厨的厨师，推理服务是厨房流水线，网关是前台点单，缓存/批处理是提前备菜，监控是店长巡店。

1) 整体架构分层：
- 接入层：API网关/负载均衡，负责鉴权、限流、配额、计费、路由。
- 应用层：业务逻辑，如会话管理、Prompt模板、RAG检索、工具调用（Function Calling）、多轮上下文拼接。
- 模型服务层：模型推理服务，通常用Triton、vLLM、TensorRT-LLM、TGI等部署，支持动态批处理、KV Cache、量化。
- 数据与缓存层：向量库、Redis缓存、对象存储、日志。
- 基础设施层：GPU调度、弹性扩缩容、监控告警。

2) 关键工程问题：
- 延迟：首Token延迟（TTFT）和每Token延迟（TPOT）。用流式输出、连续批处理（continuous batching）、PagedAttention、投机解码优化。
- 成本：按Token计费，用批处理提高GPU利用率，用蒸馏/量化/小模型路由降低单次成本。
- 稳定性：限流、降级、重试、熔断、多模型Fallback。
- 可观测：记录请求日志、Token用量、延迟分布、错误率，做A/B测试和效果评估。
- 安全合规：内容审核、Prompt注入防护、数据脱敏、租户隔离。

3) 典型请求流程：用户请求→网关鉴权限流→应用层组装Prompt/检索上下文→推理服务排队批处理→模型生成→流式返回→后处理（审核/格式化）→计费与日志。

4) 适用场景：Chatbot、代码助手、搜索问答、图像生成、语音识别等，凡是需要把模型能力以在线服务形式提供给用户的场景。

**加分点**

能提到vLLM的PagedAttention和continuous batching如何把GPU利用率从30%提升到80%+；能区分TTFT与TPOT的优化手段不同；能讲清RAG与微调在在线产品中的取舍；能提到多租户下的LoRA动态加载、模型路由（小模型先试、大模型兜底）降本；能提到流式输出对用户体验和网关超时设计的影响；能提到用Prometheus+Grafana做Token级监控和成本归因。

**雷区**

常见误解：1) 以为在线AI产品就是调个API，忽略工程化；2) 把训练和推理混为一谈，不知道推理优化重点；3) 认为模型越大越好，忽略延迟和成本；4) 忽略流式输出、限流、降级等生产必备能力；5) 不提安全审核和Prompt注入防护；6) 把RAG和微调当成互斥或万能方案。

## 2. 在 AI 编程的加持下，前后端还是有很大区别的

> 原题 ID：`q2190` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

在 AI 编程的加持下，前后端还是有很大区别的

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

AI 编程能大幅提升编码效率，但前后端的本质差异（运行环境、状态管理、安全边界、调试与交付方式）不会因此消失，AI 只是把差异从“写代码”层面部分转移到了“架构与验证”层面。

### 解析

先给一个通俗类比：前端像“在别人家里（浏览器）摆家具”，后端像“在自己家仓库里管库存和发货”。AI 可以帮你画图纸、写清单，但“谁的地盘、谁负责什么”不会变。

1) 运行环境与信任边界：前端代码运行在用户可控的浏览器/客户端，代码和接口对用户可见，必须假设一切输入不可信；后端运行在受控服务器，掌握数据库、密钥、权限，是真正的信任边界。AI 生成的前端代码再优雅，也不能把鉴权、价格计算、库存扣减放前端。

2) 状态与一致性：前端状态是“会话级、可丢失”的（刷新即没），后端状态是“持久化、需事务”的（订单、账户）。AI 很擅长写 UI 状态管理，但涉及分布式事务、幂等、并发扣库存时，仍需要后端工程师设计。

3) 调试与可观测性：前端问题多在兼容性、渲染、网络；后端问题多在链路、日志、DB 慢查询、并发。AI 能帮读日志、写单测，但线上排障依赖对系统拓扑和业务语义的理解。

4) 交付与演进：前端交付到 CDN/浏览器，可灰度、可回滚；后端涉及数据迁移、接口版本、上下游兼容，变更成本高。AI 让“写”变快，但“改错”和“兼容”的成本结构没变。

5) 适用场景：AI 对前端样板代码、组件、样式、简单 CRUD 后端收益最大；对复杂领域建模、高并发、安全合规、跨系统一致性，AI 只能辅助，不能替代判断。

结论：AI 编程降低了“编码”门槛，但没有消除前后端在信任边界、状态持久化、交付风险上的本质区别，反而让“谁能定义边界、验证正确性”成为更核心的能力。

**加分点**

1) 可提“信任边界”概念：前端是 untrusted client，后端是 trusted zone，OWASP 里大量漏洞源于把后端逻辑放前端。2) 可提“状态机”视角：前端是 ephemeral state，后端是 durable state，对应 CAP、事务隔离级别。3) 可提 AI 生成代码的验证成本：AI 写前端可快速肉眼验证，写后端需集成测试、契约测试、数据迁移演练，验证成本不对称。4) 可提“接口契约”是前后端协作核心，AI 可辅助生成 OpenAPI/类型，但契约的语义和兼容策略仍需人定。5) 可提实际踩坑：AI 生成的后端代码常忽略幂等、事务边界、N+1 查询、密钥硬编码，前端则常忽略 XSS、CSP、可访问性。

**雷区**

1) 误以为“AI 能写全栈，所以前后端没区别了”——忽略运行环境和信任边界。2) 把前后端区别简单等同于“语言不同/框架不同”，没说到状态、安全、交付。3) 认为前端没有架构、后端不需要关注用户体验，都是过时刻板印象。4) 过度依赖 AI 生成后端鉴权/支付逻辑而不做安全审计。5) 把“AI 提升效率”等同于“AI 降低复杂度”，忽略验证和运维成本。

## 3. 👀 AI产品经理视角：如何构建人工智能产品

> 原题 ID：`q2287` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

👀 AI产品经理视角：如何构建人工智能产品

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

构建AI产品需从用户问题出发，以数据为燃料、模型为引擎、体验为界面，通过迭代闭环持续创造价值。

### 解析

AI产品经理构建人工智能产品，核心是解决‘用AI做什么’和‘怎么做’的问题。首先，定义用户痛点与价值主张，判断AI是否是最优解（例如，规则引擎能解决就不必用AI）。其次，将问题转化为机器学习任务（分类、回归、生成等），并评估数据可行性：是否有足够高质量数据？标注成本如何？然后，设计产品原型，包括人机交互方式（如推荐、对话、自动化决策），并考虑AI的不确定性（如置信度展示、人工兜底）。接着，选择技术方案：自研模型、调用API还是开源微调？需权衡成本、效果与迭代速度。之后，建立评估体系：离线指标（准确率、召回率）与在线指标（点击率、留存率），并通过A/B测试验证。最后，持续迭代：收集用户反馈，形成数据闭环，监控模型衰减，定期更新。例如，智能客服产品：先分析常见问题，构建意图分类模型，设计对话流程，上线后根据未识别问题优化模型。整个过程需跨团队协作（算法、工程、设计、运营），并关注伦理与合规。

**加分点**

1. 数据飞轮：设计产品时让用户行为自然产生标注数据，如推荐系统的点击反馈。2. 冷启动策略：用规则、迁移学习或人工模拟。3. 模型可解释性：在金融、医疗等场景，需提供决策依据。4. 成本控制：推理成本与延迟的权衡，如模型蒸馏、量化。5. 伦理风险：偏见、隐私、滥用，需提前设计缓解措施。

**雷区**

1. 唯技术论：盲目追求最新模型，忽略用户需求与商业价值。2. 忽视数据：认为算法决定一切，低估数据质量和标注成本。3. 期望过高：认为AI能100%准确，未设计容错和人工干预。4. 忽略迭代：以为一次上线就完事，没有持续监控和优化。5. 合规盲区：未考虑数据隐私、版权和行业监管。

## 4. 没有装 copilot 能大概说一下 chat gpt吗

> 原题 ID：`q2636` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

没有装 copilot 能大概说一下 chat gpt吗

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

ChatGPT 是 OpenAI 基于 GPT 系列大语言模型、通过对话式微调与 RLHF 对齐后推出的聊天式 AI 助手，本质是“预测下一个 token”的自回归生成模型。

### 解析

可以把它拆成三层来理解。

第一层：底层模型（GPT）。GPT 全称 Generative Pre-trained Transformer，是一个只有解码器（decoder-only）的 Transformer 网络。它做的事非常朴素：给定前面一段文字，预测下一个最可能出现的词（token）。比如输入“今天天气真”，它会算出“好”的概率最高。这个能力叫自回归语言建模。

第二层：预训练。OpenAI 用海量互联网文本、书籍、代码等做“完形填空”式训练，让模型学会语法、常识、推理和世界知识。这一步之后模型其实还不会“聊天”，只会续写。

第三层：对齐（InstructGPT/ChatGPT 的关键）。通过监督微调（SFT，人工写高质量问答示范）+ 奖励模型（RM，人工对多个回答排序训练打分器）+ 强化学习（PPO，让模型生成得分更高的回答），把“续写器”变成“听话的助手”。这就是 RLHF（基于人类反馈的强化学习）。

通俗类比：预训练像让一个人读遍图书馆，知识很杂但不会好好回答问题；SFT 像给他看标准问答范例；RLHF 像请老师不断打分纠正，最终学会礼貌、有用、安全的对话方式。

使用场景：问答、写作、翻译、代码辅助、头脑风暴、总结文档等。它没有联网（除非开了插件/搜索）、没有长期记忆（除非产品层做了记忆功能），本质是“根据上下文概率生成”，所以会一本正经地胡说（幻觉）。

**加分点**

1. 能说出 ChatGPT 与 GPT-3 的区别：GPT-3 是 base model，ChatGPT 是加了 SFT+RM+PPO 的 Instruct 版本，对齐才是产品化的关键。
2. 知道 token 不是字：中文一个汉字可能 1~2 个 token，英文一个词可能拆成多个子词（BPE），这解释了为什么计费和上下文长度按 token 算。
3. 知道温度（temperature）、top-p 等采样参数影响“创造性 vs 稳定性”。
4. 知道幻觉的根因：模型优化的是“下一个 token 的似然”，不是“事实正确性”，没有内置知识库检索。
5. 能提到上下文窗口限制、KV Cache、以及为什么长对话会“忘事”。

**雷区**

1. 把 ChatGPT 说成“搜索引擎”或“数据库”，以为它在查资料——它是在生成，不是检索。
2. 以为它真的“理解”或“有意识”，混淆拟人化表达和技术本质。
3. 以为装了 Copilot 才能用 ChatGPT，其实两者是不同产品：Copilot 是微软把 GPT 能力集成到 Office/GitHub 等场景的助手，ChatGPT 是 OpenAI 的独立对话产品。
4. 忽略 RLHF，只讲 Transformer，答不出“为什么它能好好聊天”。
5. 把 GPT 和 BERT 搞混：GPT 是 decoder-only 自回归生成，BERT 是 encoder-only 双向理解，任务范式不同。

## 5. 这就是为什么流式输出是 AI 产品的第一个关键用户体验——它不是锦上添花，而是决定用户会不会关掉 tab 的分水岭

> 原题 ID：`q3127` ｜ 原分类：工程落地 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

这就是为什么流式输出是 AI 产品的第一个关键用户体验——它不是锦上添花，而是决定用户会不会关掉 tab 的分水岭

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

流式输出把首字节时间从数十秒压到几百毫秒，用感知延迟换总时长，是决定用户留存的关键体验，而非可选优化。

### 解析

原理：LLM 推理是自回归的，token 逐个生成，总时长 T_total ≈ T_prefill + N × T_decode，无法压缩。非流式必须等全部 N 个 token 生成完才返回，用户面对空白屏等待数秒到数十秒；流式则在第一个 token 产出后立即通过 SSE/WebSocket 推送，首字节时间 TTFB 降到几百毫秒，用户立刻看到内容增长，感知等待大幅下降。

工程实现：后端用 SSE（text/event-stream）或 WebSocket，逐 chunk 下发 delta；推理侧需支持 stream=True 的增量解码，注意 UTF-8 多字节字符可能被切在 chunk 边界，必须用增量解码器缓冲，否则出现乱码。前端用 ReadableStream/fetch 逐块解析，做打字机渲染。

权衡：1) 流式下无法在发送前做完整的内容审核/敏感词过滤，只能边流边审或先审后发，带来合规风险；2) 一旦开始推送就无法改 HTTP 状态码，错误只能以事件形式下发，前端要处理中途失败与重试；3) 无法用常规 gzip 压缩整包，需权衡压缩率与延迟；4) 计费/token 统计要在流结束后结算，需处理连接中断的补偿；5) 代理层（Nginx/CDN）默认缓冲会破坏流式，需关闭 proxy_buffering、设置 X-Accel-Buffering: no。

例子：ChatGPT 类产品若改成非流式，用户平均等待 8-15 秒，tab 关闭率显著上升；改为流式后首字 0.5-1 秒，用户愿意等待完整回答。

**加分点**

1) 能指出 TTFB 与总时长的区别，引用 Nielsen 的 0.1s/1s/10s 响应时间阈值说明为何首字必须 <1s；2) 知道 OpenAI/Anthropic 流式协议细节：SSE 的 data: 行、[DONE] 结束标记、delta 增量字段；3) 踩坑：Nginx 默认 proxy_buffering on 导致流式被攒包，需显式关闭；Cloudflare 等 CDN 对 SSE 的缓冲与超时；4) 增量 UTF-8 解码（如 Python codecs.getincrementaldecoder）避免 emoji 被截断；5) 流式下的取消：用户关 tab 要能 abort 上游推理释放 GPU，否则资源泄漏；6) 可结合 speculative decoding/首 token 优化进一步压低 TTFB。

**雷区**

1) 认为流式只是前端打字机动画，忽略后端增量解码与协议改造；2) 以为流式能降低总耗时——它只降低感知延迟，总时长不变甚至略增；3) 忽略流式与内容安全审核的冲突，直接边生成边展示导致违规内容外泄；4) 忘记处理 chunk 边界多字节字符导致乱码；5) 部署时被 Nginx/CDN 缓冲吃掉流式效果却排查不到；6) 连接中断后不做 token 结算与上游取消，造成计费错误和 GPU 资源浪费。

## 6. 挑一个你最满意的 AI 落地场景讲讲难点

> 原题 ID：`q3547` ｜ 原分类：工程落地 ｜ 来源：全平台面经采集(2026-09)·nowcoder

### 题干

挑一个你最满意的 AI 落地场景讲讲难点

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

选一个真实AI落地场景，重点讲清业务约束下的核心难点、方案权衡与量化收益，而非只讲模型效果。

### 解析

我选一个『电商客服工单智能分类+自动回复建议』的落地场景。业务背景：日均约 5 万条用户工单，原来靠 30 人客服团队人工打标签并选择回复模板，平均处理时长 4 分钟，标签体系有 120 个多级类目，且类目每月会新增/调整。

难点一：标签体系动态变化且长尾严重。头部 20 个类目占 70% 流量，尾部 100 个类目样本极少。纯微调分类模型每次类目调整都要重训，迭代周期一周以上，业务无法接受。方案：采用『LLM few-shot + 向量检索相似历史工单』的 RAG 分类，把每个类目的定义、正负例、相似历史工单拼进 prompt，新类目只需运营配置几条样例即可上线，迭代从天级降到小时级。

难点二：准确率与成本的权衡。直接用 GPT-4 全量跑，单条成本约 0.03 元，5 万条/天约 1500 元/天，且延迟 2-3 秒。方案：分层路由——先用轻量微调的小模型（如 BERT/小参数 LLM）做置信度判断，置信度高于阈值直接输出，覆盖约 65% 流量；低置信度再走大模型 RAG。整体成本降到约 500 元/天，P95 延迟从 3s 降到 800ms。

难点三：幻觉与不可控输出。LLM 可能编造不存在的类目或给出错误回复。方案：输出层做 schema 约束（JSON mode + 类目白名单校验），回复建议只允许从审核过的模板库中检索生成，不允许自由发挥；同时加人工抽检和在线反馈闭环，把 badcase 回流到 few-shot 样例池。

难点四：评估与上线。没有现成标注集，先人工标 2000 条作为 golden set，用 macro-F1 而非 accuracy（因为长尾类目），上线后做 A/B，核心指标是自动通过率、人工修正率、平均处理时长。最终自动通过率 78%，人工修正率 12%，平均处理时长从 4 分钟降到 1.5 分钟，客服人力节省约 40%。

关键权衡：一致性 vs 可维护性——类目频繁变，选择 RAG 而非微调牺牲了一点峰值准确率，换来运营可自助迭代；性能 vs 成本——分层路由牺牲少量准确率换成本下降 2/3。

**加分点**

1）提到用 macro-F1 而不是 accuracy，体现对长尾分布的理解；2）分层路由本质是 cascade/early-exit 思想，可类比 Speculative Decoding 或模型级联；3）输出用 JSON schema + 白名单校验，是工程上防幻觉的常见手段；4）把 badcase 回流到 few-shot 池形成数据飞轮；5）能给出具体数字（成本、延迟、通过率）而不是空谈；6）提到类目白名单校验和模板库约束，避免 LLM 自由生成带来的合规风险。

**雷区**

1）只讲模型多强、用了什么大模型，不讲业务约束和工程权衡；2）把准确率当成唯一指标，忽略长尾、成本、延迟、可维护性；3）忽略幻觉和输出格式问题，直接让 LLM 自由生成；4）没有评估方案，拍脑袋说效果很好；5）类目频繁变化却坚持微调，导致迭代周期长；6）不提人工兜底和反馈闭环，认为 AI 可以 100% 替代人工。

## 7. 你是怎么管理 AI 编程时的上下文的

> 原题 ID：`q3548` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·nowcoder

### 题干

你是怎么管理 AI 编程时的上下文的

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

AI 编程的上下文管理，本质是在有限的 token 预算内，动态挑选、压缩、组织最相关的信息（任务目标、代码、约束、历史），让模型每次调用都拿到“刚好够用”的上下文。

### 解析

AI 编程时的上下文管理可以类比为“给一位记忆力有限但能力很强的外包工程师交接工作”。他每次只能看一页纸（上下文窗口），所以你既要保证这页纸信息密度高，又要保证关键信息不丢。

核心分四层：
1. 任务层（长期记忆）：把项目目标、架构约定、编码规范、技术栈、目录结构写成一份精简的“项目说明书”（如 CLAUDE.md / .cursorrules / AGENTS.md），每次对话自动注入。它相当于给模型的“入职文档”，避免重复解释。
2. 会话层（中期记忆）：当前任务的需求、已确认的设计决策、待办清单。用结构化的 TODO/计划文件维护，而不是全靠聊天历史。这样即使上下文被截断，也能从文件恢复。
3. 即时层（短期记忆）：当前正在改的文件、相关函数、报错信息、最近几轮对话。原则是“按需检索”而非“全量塞入”——用 grep/语义检索找到相关代码片段，只贴必要的部分。
4. 工具层：让模型自己通过读文件、搜索、跑测试来按需获取上下文，而不是一次性喂给它。这就是 Agent 化的核心：把“上下文获取”变成模型可调用的动作。

具体策略：
- 分层注入：系统提示放稳定规范，用户消息放当前任务，工具结果放动态信息。
- 压缩与摘要：历史过长时做滚动摘要（把旧对话总结成要点），保留决策和结论，丢弃冗余过程。
- 结构化优于自然语言：用文件树、diff、类型签名代替大段描述，token 效率更高。
- 分而治之：大任务拆成子任务，每个子任务只加载相关上下文，避免“一锅炖”。
- 显式遗忘：主动清理过时信息（已废弃的方案、已修复的 bug），防止误导模型。

适用场景：小脚本可以少管理；大型多文件重构、长周期项目、多人协作时必须系统化管理，否则模型会“失忆”或产生幻觉。

**加分点**

1. 上下文窗口的“中间遗忘”现象（Lost in the Middle，Liu et al. 2023）：模型对开头和结尾的信息召回率明显高于中间，所以关键约束应放在系统提示开头或用户消息结尾，而非埋在中间。
2. 上下文工程（Context Engineering）已从 Prompt Engineering 演进而来：Anthropic 提出的“context engineering”强调在 Agent 循环中动态管理上下文，包括 compaction（压缩）、结构化笔记、子 Agent 隔离上下文。
3. 子 Agent 隔离：把探索性、高噪声的任务（如大范围搜索）交给子 Agent，只把结论返回主 Agent，避免污染主上下文。这是 Claude Code / Cursor 等工具的实际做法。
4. 缓存友好：稳定前缀（系统提示、项目规范）放在前面可命中 prompt caching，降低成本与延迟；动态内容放后面。
5. 可验证性：把上下文写成可执行的文件（测试、类型、lint 规则），让模型能自我校验，比纯文字描述更可靠。

**雷区**

1. 以为“上下文窗口越大越好”，无脑把所有代码和历史都塞进去——导致成本高、延迟大、中间信息被忽略、模型注意力分散。
2. 把上下文管理等同于“写更长的 prompt”，忽略动态检索、压缩和工具调用。
3. 完全依赖聊天历史做记忆，一旦截断或开新会话就丢失关键决策，没有落盘到文件。
4. 混淆“上下文”与“微调/RAG”：上下文是单次推理的输入，RAG 是检索增强，微调是改权重，三者解决不同问题。
5. 忽略上下文污染：把过时的、错误的、互相矛盾的信息留在上下文里，导致模型输出不稳定。
6. 只关注 token 数量，不关注信息结构和位置，关键约束被淹没。

## 8. 你平时是否购买大模型或 AI 编程工具的订阅？使用的是官方订阅还是第三方 API？

> 原题 ID：`q3611` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·xiaohongshu

### 题干

你平时是否购买大模型或 AI 编程工具的订阅？使用的是官方订阅还是第三方 API？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

这题表面问消费习惯，实际考察你是否真正把大模型/Agent 工具用进日常研发闭环，以及能否讲清官方订阅与第三方 API 在成本、能力、合规、稳定性上的取舍。

### 解析

面试官问这个，通常不是查你花没花钱，而是想判断三件事：一，你是否真的高频使用 AI 编程工具，而不是只停留在“听说过”；二，你是否理解不同接入方式的差异，能根据场景做工程选型；三，你是否踩过真实坑，有可迁移的实践经验。

可以分三层回答。

第一层，使用现状：我日常会同时用两类。一类是官方订阅的 AI 编程工具，比如 GitHub Copilot、Cursor、Claude Code 这类，按席位/月付费，优点是开箱即用、IDE 集成好、补全和 Agent 模式体验顺滑，适合个人和团队日常写代码。另一类是官方大模型订阅，比如 ChatGPT Plus、Claude Pro，用于查文档、读论文、写方案、做代码 review。

第二层，官方订阅 vs 第三方 API 的本质区别。官方订阅是“买产品”，你买的是封装好的交互体验、上下文管理、工具调用和持续更新，按人头/月计费，边际成本固定，适合人机交互场景。第三方 API 是“买能力”，你按 token 或调用次数付费，拿到的是裸模型接口，需要自己写 prompt、管上下文、做重试和限流，适合把模型嵌进自己的系统，比如做 RAG、Agent、批量代码生成、CI 里自动 review。

第三层，为什么很多团队两者都用。个人日常用官方订阅，因为体验最好、最省心；生产系统或需要定制、批量、可观测、可审计的场景走 API，因为可控。比如公司内部代码助手，如果直接用官方订阅，无法统一管理密钥、审计日志和成本；走 API 就能接入内部知识库、做权限隔离、按项目核算 token。

一个通俗类比：官方订阅像打车软件，打开就能用，按次/按月付费，体验好但不适合运货；第三方 API 像自己买发动机装车，灵活、可批量、可定制，但你要自己造底盘、加油、修车。

适用场景上：个人学习、日常编码、快速验证想法，优先官方订阅；要做产品、做 Agent、做批处理、要合规审计，优先 API。

**加分点**

1. 能区分“模型订阅”和“编程工具订阅”：前者买的是模型能力，后者买的是 IDE/Agent 工作流，二者计费和限流逻辑不同。2. 知道官方订阅通常有隐性限流，比如按小时/按周的消息数或高级模型配额，重度使用会触发降级；API 则按 token 计费，可预测但可能更贵。3. 能提到成本优化手段：小任务用便宜模型、大任务用强模型；缓存 system prompt；用 batch API 降本；对代码补全用低延迟小模型，对架构设计用强模型。4. 能提到合规与数据边界：官方订阅的个人版通常默认数据可能用于训练，企业版/API 可关闭；公司代码不能随便贴进个人订阅。5. 能提到可观测性：API 可以记录 token 消耗、延迟、失败率，方便做成本归因和效果评估。6. 有真实踩坑：比如第三方 API 中转站不稳定、模型版本被偷偷替换、上下文长度缩水、流式返回中断、密钥泄露风险。

**雷区**

1. 只回答“买过/没买过”，不展开选型逻辑，显得没有工程思考。2. 把官方订阅和 API 混为一谈，认为“都是调模型没区别”，忽略产品封装、限流、合规、可观测性的差异。3. 过度强调“第三方 API 便宜”，却忽略中转站可能违反服务条款、数据安全不可控、模型可能被降级或替换。4. 说“公司代码直接贴到个人 ChatGPT 里”，暴露合规意识薄弱。5. 只谈个人体验，不谈团队/生产场景，显得格局局限。6. 把“订阅”理解成必须付费，忽略免费额度、开源模型本地部署、企业统一采购等替代方案。

## 10. 师兄接着说，你们学生最爱问这个岗位是不是核心？但用人方第一眼只看两件事，那就是你会不会把模型用起来以及你能不能把东西做成

> 原题 ID：`q3706` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

师兄接着说，你们学生最爱问这个岗位是不是核心？但用人方第一眼只看两件事，那就是你会不会把模型用起来以及你能不能把东西做成产品形态

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

面试官真正关心的是你能否把模型落地成可用产品，即‘模型应用能力’与‘产品化能力’，而非岗位是否核心。

### 解析

这句话的核心是：在AI岗位招聘中，用人方不关心‘岗位是否核心’这种学生思维，而是看两个硬指标。第一，会不会把模型用起来——指你能否调用、微调、部署模型，并把它嵌入到实际业务流程中解决问题，比如用LLM做客服摘要、用CV做质检，而不是只停留在跑通demo或调参。第二，能不能把东西做成产品形态——指你能否把模型能力封装成稳定、可交互、可交付的产品，比如提供API、前端界面、错误处理、性能优化、监控告警，让非技术用户也能用。通俗类比：模型是发动机，会用模型是能发动它，做成产品是能造出一辆能上路的车。面试官想听的是你做过什么端到端项目，从数据到模型到服务到用户反馈的完整闭环。

**加分点**

可以提：1）模型应用不只是推理，还包括RAG、Agent、Function Calling等工程模式；2）产品化要关注延迟、成本、幻觉、安全、可观测性，比如用LangSmith或Prometheus监控；3）端到端案例：用FastAPI封装模型、Docker部署、加缓存和限流，再配简单前端，体现全栈意识；4）引用‘Demo到产品’的鸿沟，如数据漂移、用户反馈闭环。

**雷区**

常见错误：1）只强调自己会训练模型、调参、刷榜，却说不清如何上线和产生业务价值；2）把‘核心岗位’等同于技术深度，忽视产品思维；3）认为产品化只是前端或运维的事，与算法无关；4）只谈模型精度，不谈延迟、成本、稳定性等工程指标。
