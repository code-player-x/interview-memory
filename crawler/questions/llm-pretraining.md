## 1. MoE（混合专家模型）的架构原理是什么？路由与负载均衡问题怎么解决？

> 原题 ID：`q1051` ｜ 原分类：架构设计 ｜ 来源：知乎 Agent面经采集(2026-07-16)

### 题干

MoE（混合专家模型）的架构原理是什么？路由与负载均衡问题怎么解决？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

MoE 把 FFN 拆成多个专家，用 Router(门控网络)为每个 token 选 Top-k 个专家计算，实现'参数量大但激活量小'。负载不均用辅助损失(aux loss)或无损均衡(如 DeepSeek 的 bias 调整)让 token 均匀分配。

### 解析

每层含 N 个专家，Router 输出 softmax 权重选 top-k(常 k=2)激活，稀疏计算省算力。核心难题是专家负载倾斜(热门专家过载、冷门专家饿死)，解法：① 负载均衡辅助损失惩罚分布不均；② 专家容量上限+丢弃/补偿；③ DeepSeek-V3 用无辅助损失的动态 bias。

**加分点**

提共享专家(shared expert)、细粒度专家、通信开销(all-to-all)、DeepSeekMoE 改进。

**雷区**

以为 MoE 减少总参数量(实际是增加总参、减少激活参)；忽略负载均衡与通信瓶颈。

### 难度

★★★

### 标签

`MoE` `路由` `负载均衡`

## 2. 多机多卡分布式训练架构一般如何搭建？数据并行/张量并行/流水线并行如何组合？

> 原题 ID：`q1056` ｜ 原分类：架构设计 ｜ 来源：知乎 Agent面经采集(2026-07-16)

### 题干

多机多卡分布式训练架构一般如何搭建？数据并行/张量并行/流水线并行如何组合？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

三种并行组合(3D 并行)：数据并行(DP)复制模型切数据、张量并行(TP)切单层矩阵到多卡、流水线并行(PP)按层切分成阶段。大模型常 TP(机内 NVLink)+PP(机间)+DP(扩批量)，配 ZeRO 切优化器状态。

### 解析

TP 通信频繁(每层 all-reduce)放机内高带宽；PP 把层分段跨机、用 micro-batch 填流水线气泡；DP 用 all-reduce 同步梯度、可叠 ZeRO 省显存。序列并行/专家并行(MoE)按需加。框架用 Megatron-LM/DeepSpeed。

**加分点**

提流水线气泡(bubble)、TP 通信量、ZeRO-3 与 3D 并行叠加、专家并行。

**雷区**

把 TP 放机间导致通信打满；分不清三种并行切的是什么。

## 3. 分布式训练的主要通信瓶颈是什么？AllReduce/NCCL 如何优化？

> 原题 ID：`q1057` ｜ 原分类：架构设计 ｜ 来源：知乎 Agent面经采集(2026-07-16)

### 题干

分布式训练的主要通信瓶颈是什么？AllReduce/NCCL 如何优化？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

瓶颈是梯度同步(DP 的 all-reduce)与层内通信(TP)。优化：用 Ring-AllReduce 降带宽、NCCL 走 NVLink/InfiniBand、通信与计算重叠(反向时异步同步梯度)、梯度累积减少同步频次、混合精度减小传输量。

### 解析

Ring-AllReduce 把通信量摊成 O(N) 与卡数无关；NCCL 提供拓扑感知的高效集合通信(all-reduce/all-gather/reduce-scatter)。ZeRO 用 reduce-scatter+all-gather 替代 all-reduce。计算通信重叠(bucket 分桶)、梯度压缩/量化进一步降开销。

**加分点**

提 reduce-scatter+all-gather=all-reduce、bucket 重叠、梯度压缩、拓扑感知。

**雷区**

只会说'通信慢'给不出方案；混淆 all-reduce 与 all-gather。

### 难度

★★★

### 标签

`分布式训练` `AllReduce` `NCCL`

## 4. 梯度累积（Gradient Accumulation）在分布式训练中的作用是什么？

> 原题 ID：`q1058` ｜ 原分类：架构设计 ｜ 来源：知乎 Agent面经采集(2026-07-16)

### 题干

梯度累积（Gradient Accumulation）在分布式训练中的作用是什么？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

用小 micro-batch 多次前向反向、累加梯度，攒够 N 次再更新一次参数，等效放大 batch size 而不增显存。用于单卡/小显存模拟大 batch，也能减少分布式同步频次。

### 解析

每 micro-step 算梯度但不清零、不更新，累积 accumulation_steps 次后除以步数再 optimizer.step()。等效 batch=micro_batch×steps×卡数。注意 BatchNorm/dropout 与真大 batch 有细微差异，学习率需按等效 batch 调整。

**加分点**

提与 ZeRO 配合、通信频次下降、loss 需按累积步归一化。

**雷区**

忘记除以累积步致梯度偏大；累积期间误清零梯度。

### 难度

★★☆

### 标签

`梯度累积` `显存` `batch`

## 5. batch size 对训练稳定性和效果有什么影响？如何权衡？

> 原题 ID：`q1090` ｜ 原分类：项目深挖 ｜ 来源：知乎 Agent面经采集(2026-07-16)

### 题干

batch size 对训练稳定性和效果有什么影响？如何权衡？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

大 batch 梯度估计更准、训练更稳、吞吐高，但泛化可能变差且需相应放大学习率(线性缩放法则)+warmup；小 batch 噪声大有正则效果但不稳。显存不够可用梯度累积等效放大 batch。

### 解析

batch 增大→梯度方差降、可用更大 lr、GPU 利用率高，但过大易陷尖锐极小值伤泛化，需配 warmup 与 lr 缩放。小 batch 的梯度噪声起隐式正则但收敛慢、易震荡。大模型常用大等效 batch(梯度累积+DP)保稳定，再靠 lr 调度平衡。

**加分点**

提线性缩放法则、warmup、尖锐/平坦极小值、梯度累积等效放大。

**雷区**

改 batch 不改学习率;以为 batch 越大越好忽视泛化。

### 难度

★★☆

### 标签

`batch` `训练` `学习率`

## 6. 词表设计对多语言模型的效果有什么影响？

### 题干

词表设计对多语言模型的效果有什么影响？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

词表若偏英文，对中文等语言 fertility 高(切碎)、上下文利用差、推理成本高、效果弱。多语言模型需平衡各语言覆盖，常做词表扩充或用 BBPE 保证任意字节可编码，兼顾压缩率与公平性。

### 解析

**加分点**

提 BBPE、词表扩充+继续预训练、fertility、语言公平性。

**雷区**

忽略词表对非英语的成本与效果影响;以为直接扩词表即可不需继续训练。

## 7. MoE（混合专家）的核心思想是什么？它和 Dense（稠密）模型在参数量与计算量上有何本质区别，Top-K 路由与稀疏激

> 原题 ID：`q1164` ｜ 原分类：架构设计 ｜ 来源：牛客/知乎/稀土掘金/面试鸭/小红书 等 (WorkBuddy 爬取 2026-07)

### 题干

MoE（混合专家）的核心思想是什么？它和 Dense（稠密）模型在参数量与计算量上有何本质区别，Top-K 路由与稀疏激活如何工作？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

分治法加条件计算；替换FFN为专家加Router

### 解析

MoE 的本质是「分治法」与条件计算：把传统 Transformer 的每个 FFN 层替换为一个门控网络（Router）+ 多个专家（每个专家本身是独立 FFN），但每个 token 只激活其中少数几个专家。这解耦了「参数量」与「计算量」——模型总参数量可以很大（所有专家都需加载），但单个 token 只走 Top-K 个专家，计算量远小于 Dense 模型（如 Mixtral 8×7B 总参约 47B、激活约 13B）。路由流程：Router 对每个 token 算 N 个专家的分数，取 Top-K（常取 1 或 2），softmax 归一化后按权重加权合并选中专家的输出。

**加分点**

参数量计算量解耦；Top-K稀疏激活；加权合并输出；激活参数远小于总参数

### 难度

★★☆

### 标签

`多模态与前沿架构` `分治法加条件计算` `替换FFN为专家加Router` `参数量计算量解耦` `Top-K稀疏激活` `加权合并输出` `激活参数远小于总参数`

## 8. Diffusion Transformer（DiT）为什么用 Transformer 替代 U-Net 作为扩散模型骨干

> 原题 ID：`q1172` ｜ 原分类：架构设计 ｜ 来源：牛客/知乎/稀土掘金/面试鸭/小红书 等 (WorkBuddy 爬取 2026-07)

### 题干

Diffusion Transformer（DiT）为什么用 Transformer 替代 U-Net 作为扩散模型骨干？AdaLN 如何注入时间步/条件？DiT 相比 U-Net 最大的优势（Scaling Law）是什么？MMDiT/SD3 又做了什么改进？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

patch化token；全局注意力

### 解析

传统扩散模型（DDPM/SDXL）以 U-Net 为骨干，靠卷积局部归纳偏置，存在长距离依赖弱、缩放天花板（SDXL 2.6B 后增益骤减）、多模态适配需额外格式转换三痛点。DiT（Peebles & Xie, 2023）把图像/视频切 patch→线性投影成 token，用纯 Transformer 块做全局注意力，直接建模所有 patch 的长距离/时空依赖。条件注入上，DiT 不用 Cross-Attention，而用 AdaLN（自适应层归一化）：把时间步/类别/文本编码后过 MLP，预测 LayerNorm 的缩放 γ 与偏移 β，按去噪阶段动态调整特征分布，计算复杂度从 O(N²) 降到 O(N)，且初期放大噪声、后期细化细节。最大优势是 Scaling Law：DiT 性能随参数量近似线性提升、无饱和（DiT-XL/2 FID 23.0 且可预测扩展），而 U-Net 规模大时 FID 改善饱和。MMDiT（SD3/FLUX）进一步让图像 token 与文本 token 在同一注意力里双向交互（而非仅 Cross-Attention 注入文本）；FLUX 用双流（图像/文本各自 Q/K/V/FFN 权重但共享注意力）。

**加分点**

AdaLN条件注入；Scaling Law线性；U-Net饱和；MMDiT双向注意力；Sora/SD3/FLUX

### 难度

★★☆

### 标签

`多模态与前沿架构` `patch化token` `全局注意力` `AdaLN条件注入` `Scaling Law线性` `U-Net饱和` `MMDiT双向注意力` `Sora/SD3/FLUX`

## 9. MoE 里的 capacity factor（容量因子）和 token dropping（令牌丢弃）是什么？为什么训练 

> 原题 ID：`q1175` ｜ 原分类：架构设计 ｜ 来源：牛客/知乎/稀土掘金/面试鸭/小红书 等 (WorkBuddy 爬取 2026-07)

### 题干

MoE 里的 capacity factor（容量因子）和 token dropping（令牌丢弃）是什么？为什么训练 MoE 要限制每个专家处理的 token 数？容量因子怎么设、被丢弃的 token 去哪了？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

路由倾斜需结构兜底；capacity=γ·(N/E)·TopK

### 解析

路由把每个 token 分给 Top-K 个专家，但每个专家一次能处理的 token 数若不受限，负载会严重倾斜（热门专家爆满、冷门空闲）。capacity factor γ 给每个专家设容量上限 capacity = γ × (tokens_per_batch / num_experts) × TopK。超过容量的 token 被 dropping（残差跳过该专家或走共享专家）。γ=1 为平均容量，γ>1 留余量少丢但增算力，γ<1 更省但更易丢。被丢弃 token 通常经残差原样输出（信息不丢但未被该专家处理），少量丢弃影响小。容量机制是负载均衡的工程配套，与辅助损失互补：辅助损失从梯度引导均衡，容量因子从结构硬性兜底。

**加分点**

γ=1平均,>1少丢多算；丢弃走残差信息不丢；与辅助损失互补

### 难度

★★☆

### 标签

`多模态与前沿架构` `路由倾斜需结构兜底` `capacity=γ·(N/E)·TopK` `γ=1平均,>1少丢多算` `丢弃走残差信息不丢` `与辅助损失互补`

## 12. 什么是 MoE（混合专家）？量化和专家混合如何在不显著降低质量的前提下降低成本？

> 原题 ID：`q1323` ｜ 原分类：概念基础 ｜ 来源：小红书/知乎/稀土掘金 AI Agent 面经 (WorkBuddy 爬取 2026-08)

### 题干

什么是 MoE（混合专家）？量化和专家混合如何在不显著降低质量的前提下降低成本？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

MoE 把前馈层换成多个『专家』+ 一个路由，每 token 只激活少数专家，所以总参数量大但单次计算量小。配合量化，用更少算力达到接近稠密模型的质量。

### 解析

MoE 结构：每个 MoE 层有多个 FFN 专家，router 按 token 选 top-k 专家（如 8 选 2），只有被选中专家参与计算。于是『参数多、激活少』，训练和推理算力远低于同参数稠密模型。
降本：① 激活稀疏→单次 FLOPs 低；② 量化（专家权重 int8/4）→显存与带宽再降；③ 结合 KV Cache/批处理进一步提效。
代价：显存仍大（要存全部专家）、路由不均需负载均衡损失、服务复杂度高。

**加分点**

点出『参数多、激活少』核心。
强调路由负载均衡是训练难点。

**雷区**

以为 MoE 显存也小——它存全部专家，显存仍大。

★★★

## 14. Q：这么厉害？那是不是越涌现就越好？

> 原题 ID：`q1462` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·juejin/nowcoder

### 题干

Q：这么厉害？那是不是越涌现就越好？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

不是，涌现只是能力随规模非线性提升的现象，并不等于模型在所有维度上变好，它可能伴随能力不均衡、不可控、评估失真和成本剧增。

### 解析

先定义：涌现（Emergence）通常指模型规模、数据量、训练计算量增大到某个阈值后，某些能力突然从接近随机水平跃升到显著可用，比如多步推理、上下文学习、指令遵循。它描述的是“能力曲线出现拐点”，不是“模型全面变强”。

为什么不是越涌现越好？
1. 能力不均衡：模型可能在某项基准上涌现，但在事实性、鲁棒性、安全对齐上仍很差。比如能解数学题，却会一本正经编造引用。
2. 不可控性增加：能力越强，模型越可能绕过限制、产生更隐蔽的错误，或出现“能力越大，越会伪装”的对齐问题。
3. 评估失真：很多“涌现”来自指标选择。用精确匹配看是突变，用部分得分看可能是平滑提升；有些任务只是阈值效应，不是真正质变。
4. 成本与收益不匹配：继续堆参数、数据、算力，边际收益可能下降，而推理成本、延迟、能耗线性甚至超线性上升。
5. 适用场景决定价值：客服场景要稳定、可控、低成本，一个 7B 微调模型可能比 100B 通用模型更合适；科研探索才更看重极限能力。

通俗类比：学生从 60 分到 90 分是进步，但“突然会写作文”不代表他同时会做人、会守规矩、不会抄错题。涌现像“突然开窍”，开窍后可能偏科更严重，也可能更难管。

所以正确态度是：关注目标场景下的能力、可靠性、安全、成本四者平衡，而不是盲目追求“越涌现越好”。

**加分点**

1. 可引用 Wei et al. 2022《Emergent Abilities of Large Language Models》与 Schaeffer et al. 2023“Are Emergent Abilities of Large Language Models a Mirage?”的争论：前者认为存在突变，后者指出很多突变是度量不连续导致的假象。
2. 可提“逆缩放”（Inverse Scaling）现象：某些任务上模型越大反而越差，例如迎合用户错误前提、重复 token 等。
3. 可提对齐税与能力涌现的张力：RLHF 提升有用性，但可能损失部分推理能力；安全微调可能让模型更会“拒答”而非更安全。
4. 工程上可用“能力-成本帕累托前沿”选型：先定 SLO（准确率、延迟、成本、安全），再选最小可行模型，而不是默认最大模型。

**雷区**

1. 把涌现等同于全面智能提升，认为规模越大所有指标都单调变好。
2. 只看 benchmark 分数，忽略评测集污染、指标阈值、提示词敏感性。
3. 认为涌现能力可以无条件迁移到业务场景，不做领域验证和微调。
4. 忽略安全与对齐：能力越强，误用和越狱风险越大，不能只谈“厉害”。
5. 把“涌现”和“缩放定律”混为一谈：缩放定律描述平均损失随规模平滑下降，涌现描述特定任务指标的非线性跳变。

## 15. 大模型tokenizer是怎么设计的，不同语言怎么做

> 原题 ID：`q1508` ｜ 原分类：工程落地 ｜ 来源：全平台面经采集(2026-09)·nowcoder/zhihu

### 题干

大模型tokenizer是怎么设计的，不同语言怎么做

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

Tokenizer 本质是把文本映射为子词 ID 序列，主流用 BPE/WordPiece/Unigram 在“词表大小-序列长度-跨语言公平性”之间做权衡，多语言靠共享词表+字节回退+语言采样配比来平衡。

### 解析

1) 目标与约束：tokenizer 要满足 (a) 无损可逆（decode(encode(x))==x），(b) 词表可控（通常 32k~256k），(c) 压缩率高（同样文本 token 数少，直接决定推理成本和有效上下文），(d) 跨语言公平（不能英语 1 token/词、中文 3 token/字）。

2) 主流算法：
- BPE（GPT 系）：从字符/字节开始，反复合并频次最高的相邻对，得到 merge 规则表。编码时按 merge 优先级贪心合并。
- WordPiece（BERT）：类似 BPE，但合并准则用似然增益 score(pair)=freq(ab)/(freq(a)*freq(b))，倾向合并“互信息高”的对。
- Unigram LM（SentencePiece/T5、LLaMA）：先给一个超大候选集，用 EM 迭代估计每个子词概率，再按损失最小化裁剪词表，编码用 Viterbi 找最优切分。
- SentencePiece：把空格也当普通符号（▁），直接在原始文本上训练，天然语言无关，适合中/日/泰等无空格语言。

3) 不同语言怎么做：
- 英文等屈折语：子词能很好覆盖词根词缀，压缩率高。
- 中文：没有空格，若按字切分词表会爆炸且语义粒度粗；实践中常用“字 + 高频词”混合，或直接 byte-level BPE 让常见词成 token。注意中文一个汉字在 UTF-8 下是 3 字节，纯 byte-level 会让中文 token 数约为英文的 2~3 倍。
- 日文/韩文：日文假名+汉字混合，韩文谚文可分解为 Jamo；通常靠 SentencePiece 的 Unigram 自动学到合适粒度。
- 阿拉伯语/印地语等：形态复杂、字符变体多，需要 Unicode 归一化（NFC/NFKC）先处理，否则同一词多种写法会浪费词表。
- 低资源语言/emoji/代码：靠 byte-level 回退（GPT-2 的 256 字节 base）保证任何字符都能编码，永不 OOV。

4) 训练数据配比：多语言词表是零和的——英语语料多，BPE 会把大量 token 分给英文，导致其他语言被“碎片化”。工程上常用温度采样（T=2~5）或按语言上限/下限重采样，让低资源语言也有足够 token 预算。LLaMA 词表 32k 偏英语，mT5/PaLM 用 256k 并显式做语言平衡。

5) 工程权衡：词表越大，embedding 参数越多（V×d），softmax 越贵，但序列越短；词表越小，序列越长，注意力 O(n²) 成本上升。通常 32k~128k 是甜点区。另外 tokenizer 一旦训练完就固定，换 tokenizer 等于要重训模型，所以要在预训练前定好。

**加分点**

1) 能说出 GPT-2 用 byte-level BPE 解决 OOV，代价是中文等非拉丁语言 token 效率下降；GPT-4 的 cl100k/o200k 词表扩大到 100k/200k 并显式优化多语言，中文压缩率明显提升。
2) 知道 HuggingFace tokenizers 库用 Rust 实现，训练时用并行+缓存 pair 频次，比纯 Python 快一个数量级；编码时用 merge rank 的优先队列。
3) 踩坑：训练语料里混入大量 HTML/重复文本会导致 merge 规则被垃圾串占据；归一化不一致（训练用 NFC、推理没做）会造成同一文本不同 token。
4) 能提到 tokenizer 与 embedding 初始化、词表裁剪（pruning）、以及“tokenizer 迁移”问题（换词表需重新对齐 embedding，如用 WECHSEL 之类方法）。
5) 知道评估指标：fertility（每词 token 数）、bytes/token、各语言 token 数方差，用来量化跨语言公平性。

**雷区**

1) 以为 tokenizer 只是“分词”，忽略它直接决定上下文长度、推理成本和跨语言能力。
2) 认为中文必须按词切分，或以为 byte-level 对中文没影响——实际会让中文 token 数暴涨。
3) 混淆 BPE 与 WordPiece 的合并准则，或以为 Unigram 也是贪心合并。
4) 忽略归一化/空格处理，导致 encode-decode 不可逆或训练推理不一致。
5) 以为词表越大越好，忽略 embedding 参数量和 softmax 开销。
6) 多语言只堆语料不做配比，导致低资源语言被英语挤占词表。

### 难度

## 16. 什么是 Scaling Law

> 原题 ID：`q1559` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

什么是 Scaling Law

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

Scaling Law 指模型性能（如损失）随参数量、数据量、计算量按幂律平滑下降的经验规律，可用来预测大模型效果并指导资源分配。

### 解析

Scaling Law（缩放定律）最早由 OpenAI 在 2020 年论文《Scaling Laws for Neural Language Models》中系统提出，核心结论是：在交叉熵损失上，模型性能与模型参数量 N、训练数据量 D、训练计算量 C 之间存在幂律关系，即 L 随这些量增大而按幂函数下降，而不是随机波动。通俗类比：就像往锅里加食材，锅越大、食材越多、火候越足，菜越好吃，但三者要匹配；只加火不加大锅，很快收益就没了。

常见形式可简写为：L(N,D) ≈ L∞ + a·N^(-α) + b·D^(-β)，其中 L∞ 是不可约损失，α、β 为正指数。OpenAI 还给出计算量 C ≈ 6ND 的估算（前向+反向约 6 倍参数量乘 token 数）。DeepMind 的 Chinchilla 进一步指出，在固定计算预算下，模型参数量和训练 token 数应大致同比例增长，最优约为每参数 20 个 token，这纠正了早期“只堆参数”的做法。

适用场景：1）训练前预测大模型最终 loss，判断是否值得继续投入；2）在给定算力预算下选择模型规模与数据量；3）指导数据配比、学习率、batch size 等超参的迁移；4）判断是否进入“数据瓶颈”或“模型瓶颈”。

原理上，它反映的是高维统计学习中的平滑泛化误差下降：随着容量和数据增加，模型对真实分布的逼近误差按幂律减小。但 Scaling Law 不是物理定律，存在失效边界，例如数据重复、分布偏移、任务难度突变、推理能力涌现等，都可能让曲线偏离。

**加分点**

1）能区分 OpenAI 的“参数-数据-计算”三变量幂律与 Chinchilla 的“计算最优”结论，并说出 6ND 估算；2）知道 L∞ 不可约损失，说明性能有下限；3）能提到“涌现能力”与 Scaling Law 的争议：部分能力在特定规模后突然出现，但后续研究认为可能是评测指标不连续导致；4）能结合实践：用 1B 以下小模型拟合曲线外推 100B 模型 loss，误差通常在可接受范围；5）知道数据质量、重复训练、MoE 稀疏化会改变有效参数量与 scaling 系数。

**雷区**

1）把 Scaling Law 说成“模型越大一定越好”，忽略数据量和计算量必须匹配；2）认为它是严格数学定理，可无限外推；3）混淆参数量与有效参数量，比如 MoE 总参数大但激活参数小；4）忽略数据重复、质量差会让曲线提前饱和；5）只背结论，说不出幂律形式、6ND 或 Chinchilla 最优比例。

### 难度

## 17. MoE 混合专家模型是什么？DeepSeek V3、Qwen 为什么用 MoE？

> 原题 ID：`q1593` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

MoE 混合专家模型是什么？DeepSeek V3、Qwen 为什么用 MoE？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

MoE（混合专家）是把一个大 FFN 拆成多个专家子网络，每个 token 只激活其中少数几个，从而在总参数量巨大的同时把每 token 计算量控制在很小，实现“参数多、算得少”。

### 解析

原理：Transformer 每层原本是一个稠密 FFN（如 hidden=7168 时中间维 18432）。MoE 把它替换成 N 个并行专家 FFN + 一个 Router（门控网络）。对每个 token，Router 输出 N 个专家的打分，取 Top-K（常见 K=1~8，DeepSeek V3 是 256 专家选 8 + 1 个共享专家），只把这 K 个专家的输出按门控权重加权求和。

通俗类比：一家公司有 256 位各领域专家（总人力=总参数），但每个客户（token）只按前台分诊找最对口的 8 位咨询（激活参数），所以服务成本只按 8 人算，而不是 256 人。

为什么用 MoE：
1) 解耦参数量与计算量。稠密模型扩大参数，FLOPs 同步线性增长；MoE 总参数可到千亿/万亿级，但每 token 激活参数只有几十亿，训练和推理的算力/显存带宽成本大幅降低。
2) 容量与知识分工。不同专家可特化处理不同语言、领域、语法模式，等价于用更大容量存知识，却不必对每个 token 全量计算。
3) 性价比。DeepSeek V3 总参 671B、每 token 激活约 37B，用远小于稠密 671B 的训练/推理成本达到接近甚至更强的效果；Qwen 的 Qwen2/Qwen3-MoE 同理，用 MoE 在同等推理预算下把模型容量做大。

代价与工程：需要负载均衡（aux loss 或 DeepSeek 的 aux-loss-free 偏置调整）防止专家塌缩；需要 all-to-all 通信把 token 路由到不同设备上的专家，对分布式训练/推理框架要求高；batch 小时专家利用率低。

**加分点**

1) 可提 DeepSeek V3 的细粒度专家 + 共享专家设计：共享专家始终激活负责通用知识，路由专家负责特化，减少冗余；并用 aux-loss-free 的专家偏置动态调平衡，避免辅助损失损害主任务。2) 可提 Switch Transformer 的 Top-1 路由与容量因子（capacity factor）导致 token 被 drop 的踩坑。3) 可提推理时 MoE 是显存/带宽瓶颈而非算力瓶颈，因为要加载全部专家权重但只算少数，所以常用专家并行 + 量化。4) 可提 Mixtral 8x7B 的命名误区：8x7B 不是 56B 激活，而是总参约 47B、激活约 13B。

**雷区**

1) 误以为 MoE 每个 token 会用到所有专家，或以为总参数=激活参数。2) 把“8x7B”理解成 8 个 7B 全激活（56B），实际是稀疏激活。3) 认为 MoE 一定更快：它省的是计算量，但显存占用和通信开销可能更大，小 batch 下未必提速。4) 忽略负载均衡问题，导致专家塌缩（少数专家吃掉所有 token，其余不训练）。5) 把 MoE 当成模型结构创新而非“稀疏化条件计算”这一本质。

## 18. 表1：稠密 Transformer 与混合专家（MoE）架构对比分析

> 原题 ID：`q2283` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

表1：稠密 Transformer 与混合专家（MoE）架构对比分析

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

稠密 Transformer 每 token 激活全部参数，MoE 用稀疏门控只激活少数专家，以显存/通信/负载均衡复杂度换取更大参数量与更低单位算力成本。

### 解析

一、结构对比
稠密 Transformer：每层 FFN 是一个大 MLP，前向时所有参数都参与计算。
MoE Transformer：把 FFN 替换为 N 个专家（每个专家是一个小 FFN）+ 一个 Router/Gate。对每个 token，Router 输出 N 个 logits，取 Top-K（常见 K=1 或 2）专家加权求和。

文字示意图：
稠密层:  x -> [FFN 全部参数] -> y
MoE 层: x -> Router -> TopK -> [Expert_i, Expert_j] -> 加权求和 -> y

二、数据流与计算量
设总参数量 P、激活参数量 P_a、专家数 N、Top-K。
稠密：每 token 计算量 ∝ P。
MoE：每 token 计算量 ∝ P_a ≈ (K/N)·P_ffn + attention。因此总参数可以做到很大，但单 token FLOPs 近似不变。
例如 Switch Transformer：N=2048，K=1，总参数 1.6T，激活仅约 7B 级别。

三、模块划分
1. Router：线性层 + softmax，输出专家概率；训练时常用 noisy top-k、jitter 增加探索。
2. Experts：独立 FFN，参数不共享；可分布到不同设备。
3. 负载均衡：auxiliary loss（如 load balancing loss、router z-loss）防止专家坍缩。
4. 并行策略：专家并行（EP）+ 数据并行 + 张量并行；All-to-All 通信是瓶颈。

四、取舍
优势：
- 同等算力下模型容量更大，质量通常优于同激活量的稠密模型；
- 训练/推理单位 token 成本低，适合大规模扩展。
劣势：
- 显存占用高（要存全部专家）；
- All-to-All 通信开销大，跨节点时延迟明显；
- 负载不均导致部分专家过载/空闲；
- 微调、量化、部署更复杂，batch 小时效率低。

五、扩展性
- 专家数可继续增大，但收益递减，且通信与均衡成本上升；
- 可结合专家剪枝、专家合并、共享专家（DeepSeekMoE 的 shared expert + routed expert）；
- 推理可用 expert offloading、专家缓存、动态路由批处理。

**加分点**

1. 能说出 Switch Transformer 的 K=1 简化与 capacity factor 概念：每个专家有容量上限，超出 token 被 drop 或残差直通，capacity factor 控制丢弃率。
2. 能提到 GShard 的 top-2 gating、aux loss 形式：L_aux = α·N·Σ_i f_i·P_i，其中 f_i 是分派到专家 i 的 token 比例，P_i 是 router 平均概率。
3. 能指出 MoE 的 All-to-All 通信量约为 O(tokens×hidden×K)，在 EP 跨节点时是主要瓶颈，常用分层 All-to-All、计算通信重叠缓解。
4. 能对比 DeepSeekMoE：细粒度专家 + 共享专家隔离，减少冗余知识，提升专家专业化。
5. 能提到训练不稳定问题：router 概率尖锐、专家坍缩，常用 router z-loss、noisy gating、float32 router 计算。

**雷区**

1. 误以为 MoE 推理时也只加载激活专家参数，忽略显存仍需容纳全部专家（除非 offload）。
2. 把 MoE 当成“多个模型 ensemble”，实际是单模型内稀疏激活。
3. 忽略负载均衡损失，认为 router 自然均匀，实际会坍缩到少数专家。
4. 只谈参数量大，不谈通信、显存、batch 效率等代价。
5. 混淆总参数量与激活参数量，导致算力估算错误。

## 19. 此外，我们讨论了如何通过数据、流水线和张量并行等模型并行方法将计算负载分配到多个GPU，从而提高吞吐量并减少延迟

> 原题 ID：`q3059` ｜ 原分类：工程落地 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

此外，我们讨论了如何通过数据、流水线和张量并行等模型并行方法将计算负载分配到多个GPU，从而提高吞吐量并减少延迟

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

模型并行通过数据/流水线/张量三种切分方式把计算与显存负载分摊到多GPU，核心是在吞吐、延迟、通信开销与工程复杂度之间做权衡。

### 解析

模型并行主要分三类：1) 数据并行（DP）：每张卡持有完整模型副本，喂不同 batch，反向做 all-reduce 梯度。实现简单、吞吐高，但显存不省，且 batch 小/模型大时通信占比高；常用 ZeRO/FSDP 把优化器状态、梯度、参数分片来省显存。2) 流水线并行（PP）：按层切分到不同 GPU，micro-batch 流水执行。关键是减少 bubble：GPipe 用 micro-batch 填充，1F1B 交错调度把 bubble 降到约 (p-1)/m。需要处理跨 stage 的 activation 传递与重计算（activation checkpointing）。3) 张量并行（TP）：把单层内的矩阵乘切分，如 Megatron 的列并行/行并行，每层需 all-reduce/all-gather，通信频繁但延迟低，适合 NVLink 高带宽域内；通常 TP 放节点内、PP/DP 放节点间。工程上常组合成 3D 并行（DP×PP×TP），并配合 ZeRO、重计算、混合精度。吞吐提升来自并行度，延迟降低来自单卡计算量减少，但通信与同步会引入新瓶颈，需按拓扑（NVLink/IB）和模型结构选择切分维度。

**加分点**

能说出 Megatron-LM 的列并行+行并行组合使每层只需一次 all-reduce；1F1B 调度 bubble 公式 (p-1)/m；ZeRO 三阶段分别切分优化器状态/梯度/参数；TP 通信量随 hidden size 线性增长，跨节点会因 IB 带宽远低于 NVLink 而严重退化，因此 TP 通常限制在单机 8 卡内；PP 的 stage 划分要均衡计算量，否则最慢 stage 决定整体；activation checkpointing 用计算换显存，重计算比例影响吞吐。

**雷区**

常见错误：1) 认为数据并行能解决显存不足（其实每卡仍存完整模型/优化器状态，除非用 ZeRO/FSDP）；2) 把张量并行跨节点部署而不考虑通信带宽，导致加速比远低于线性；3) 忽略流水线 bubble，以为加卡就线性提速；4) 混淆模型并行与数据并行的适用场景；5) 不考虑 batch size 与 micro-batch 对 bubble 和通信重叠的影响；6) 忽略重计算带来的额外计算开销与显存收益的权衡。

## 20. 比如你要训练一个有几百亿参数的大模型，这时候你得上分布式来训练吧，所以就要了解分布式的通信技术，流水线技术，数据并行技术

> 原题 ID：`q3103` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

比如你要训练一个有几百亿参数的大模型，这时候你得上分布式来训练吧，所以就要了解分布式的通信技术，流水线技术，数据并行技术

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

训练百亿参数大模型需组合数据并行、流水线并行和张量并行，并优化通信与内存，核心是平衡计算与通信、显存与吞吐。

### 解析

训练百亿参数模型时，单卡显存和算力不足，必须采用分布式策略。主要技术包括：
1. 数据并行（DP）：每张卡持有完整模型副本，处理不同数据批次，通过AllReduce同步梯度。优点是实现简单，缺点是显存冗余，通信量大。改进方案如ZeRO（零冗余优化器）将优化器状态、梯度和参数分片到各卡，大幅降低显存。
2. 流水线并行（PP）：将模型按层切分到不同设备，形成流水线。通过微批次（micro-batch）重叠计算与通信，减少气泡（bubble）。例如GPipe和PipeDream。需注意负载均衡和调度策略。
3. 张量并行（TP）：将单个算子（如矩阵乘）切分到多卡，每卡计算部分结果后AllReduce。适合层内并行，通信频繁，通常限于节点内高带宽互联（如NVLink）。Megatron-LM是典型实现。
4. 混合并行：实际训练常结合3D并行（DP+PP+TP）。例如：TP用于节点内，PP跨节点，DP复制。数据流：输入数据分片→各DP组内前向→PP阶段间传递激活→TP组内AllReduce→反向传播→梯度同步。
取舍：TP通信开销大但显存节省明显；PP气泡多但通信少；DP简单但显存冗余。扩展性需考虑通信拓扑（如AllReduce用Ring或Tree）、计算通信重叠、检查点重计算等。
文字示意图：
[数据并行组1] [数据并行组2]
   |                |
[PP阶段1] -> [PP阶段2] -> [PP阶段3]  (每个阶段内TP切分)
   |                |
[AllReduce梯度同步]

**加分点**

1. 源码级：Megatron-LM中张量并行对Transformer层的切分方式，如列并行和行并行线性层，以及前向/反向的通信模式。
2. 论文：GPipe的微批次流水线调度、PipeDream的1F1B策略、ZeRO的三个阶段（优化器状态、梯度、参数分片）。
3. 踩坑：流水线并行中微批次数量与气泡大小的关系（气泡比例≈(p-1)/(m+p-1)），需调整微批次数量；张量并行在跨节点时因通信带宽不足导致性能下降；数据并行中AllReduce的通信量随模型大小线性增长，需用梯度压缩或异步更新。
4. 扩展：使用NVIDIA NCCL、华为HCCL等通信库；考虑混合精度训练、激活重计算、Offload技术。

**雷区**

1. 误以为数据并行可以无限扩展，忽略通信瓶颈和显存冗余。
2. 混淆张量并行与流水线并行的适用场景，例如在低带宽网络使用张量并行。
3. 忽视流水线并行的气泡问题，未使用微批次或调度优化。
4. 认为ZeRO是数据并行的简单替代，实际上ZeRO-3会引入额外通信。
5. 忽略通信与计算的重叠，导致GPU利用率低。

## 21. LLM 有 scaling law，在 VLM 是否也存在 scaling law？

> 原题 ID：`q3190` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

LLM 有 scaling law，在 VLM 是否也存在 scaling law？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

存在，但VLM的scaling law比LLM更复杂：它同时受视觉编码器、连接器、语言模型和数据质量/配比影响，不能简单套用LLM的参数量-数据-算力幂律。

### 解析

LLM的scaling law（Kaplan/Chinchilla）描述的是：在纯文本自回归建模下，测试损失随模型参数量N、数据量D、计算量C呈幂律下降，并给出最优的N与D配比（Chinchilla约20 token/参数）。VLM可以看作“视觉编码器 + 连接器/投影层 + LLM”的多模态系统，因此也存在scaling现象，但形式不同。

通俗类比：LLM像只练一种乐器（文本）的乐手，练习时长、曲目量和乐器质量关系比较稳定；VLM像一支乐队，除了主唱（LLM），还有视觉乐手（ViT）、编曲（连接器）和乐谱（图文数据）。整体水平当然随规模提升，但短板会拖后腿。

具体来说：
1）视觉侧：ViT也有scaling law，图像分辨率、patch大小、视觉参数量、预训练数据量都会影响表征质量。视觉编码器太弱，LLM再大也“看不清”。
2）语言侧：LLM规模仍重要，但VLM常复用预训练LLM，继续放大LLM的边际收益可能低于提升视觉分辨率和数据质量。
3）连接器：MLP、Q-Former、Perceiver等结构决定视觉token如何进入LLM；token数量、压缩率会影响效果和成本。
4）数据：图文对数量、质量、配比（caption、OCR、VQA、交错图文）往往比单纯堆参数更关键。
5）任务：VLM的scaling曲线依赖任务，OCR/图表/细粒度定位更吃分辨率，常识VQA更吃LLM和世界知识。

因此可以说：VLM存在scaling law，但不是单一幂律，而是多变量、分模块、任务相关的scaling。经验上，视觉分辨率、视觉token数、图文数据质量和LLM规模需要协同扩展，否则会出现“木桶效应”。

**加分点**

1）可提Kaplan 2020、Chinchilla 2022，以及ViT的scaling、OpenCLIP/LAION的经验；2）可提Flamingo、BLIP-2、LLaVA、Qwen-VL、InternVL等中视觉编码器规模、分辨率、连接器设计对性能的影响；3）可提“视觉token数”是VLM特有的计算瓶颈，高分辨率会平方级增加token，需动态分辨率、tiling、token压缩；4）可提数据质量与配比常比参数scaling更显著，如Cambrian-1、Idefics等强调数据组合；5）可提评测维度多，scaling law要分任务看，不能只看平均分。

**雷区**

1）直接说“LLM有，VLM没有”；2）把LLM的Chinchilla 20 token/参数直接套到VLM；3）只谈LLM参数量，忽略视觉编码器、分辨率、连接器和数据；4）认为参数量越大VLM一定越好，忽略视觉token爆炸和训练数据质量；5）把scaling law理解成“只要堆算力就线性提升”，忽略幂律收益递减和任务差异。

## 22. 你能不能介绍一下 BERT 和GPT 的训练方式(预训练任务训练细节)的区别

> 原题 ID：`q3196` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

你能不能介绍一下 BERT 和GPT 的训练方式(预训练任务训练细节)的区别

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

BERT 用 Transformer 编码器做双向掩码语言建模（MLM）+ 下一句预测（NSP），GPT 用 Transformer 解码器做单向自回归语言建模（预测下一个 token）。

### 解析

两者都基于 Transformer，但结构、预训练任务和适用场景不同。

1) 结构差异：BERT 使用 Transformer Encoder，自注意力无因果掩码，每个位置能看到左右两侧；GPT 使用 Transformer Decoder，带因果掩码，每个位置只能看到左侧历史。

2) 预训练任务：
- BERT：MLM（Masked Language Modeling）。随机 mask 15% 的 token，其中 80% 替换为 [MASK]，10% 替换为随机词，10% 保持不变，让模型根据上下文预测原词。因为如果总是用 [MASK]，预训练和微调阶段输入分布不一致。BERT 还加了 NSP（Next Sentence Prediction），输入 [CLS] A [SEP] B [SEP]，判断 B 是否是 A 的下一句，用于学习句子级关系。后来 RoBERTa 发现 NSP 作用有限，去掉了 NSP，并采用动态 mask、更大 batch 和更多数据。
- GPT：自回归语言建模（Autoregressive LM），给定前文预测下一个 token，损失是标准的从左到右的交叉熵。GPT-2 用更大规模数据做零样本多任务，GPT-3 用 few-shot/in-context learning，GPT-4 加入 RLHF 等对齐。

3) 通俗类比：BERT 像做完形填空，看到整句话后猜空格；GPT 像接龙，只能看前面已经写出的内容，猜下一个词。

4) 适用场景：BERT 适合理解类任务，如分类、NER、抽取式问答、句子匹配；GPT 适合生成类任务，如文本生成、对话、代码生成，也通过 prompt 做理解任务。

5) 训练细节：BERT 通常用 512 长度、batch 较大、Adam 优化器、学习率 warmup；GPT 系列用自回归目标，训练时每个位置都计算 loss，而 BERT 只对 mask 位置计算 loss。

**加分点**

1) 能指出 BERT 的 MLM 存在预训练-微调不一致问题，以及 80/10/10 策略是为了缓解；2) 知道 RoBERTa 去掉 NSP、动态 mask、更大数据；3) 知道 GPT 的 causal mask 保证自回归，训练时可用 teacher forcing 并行计算所有位置 loss；4) 能提到 BERT 的 [CLS] 用于句子级任务，但 NSP 后来被证明不是必需；5) 能对比 ELECTRA 的 replaced token detection，用生成器替换 token、判别器判断是否替换，训练更高效；6) 能提到 GPT 的 in-context learning 和 RLHF 与 BERT 微调范式的区别。

**雷区**

1) 误以为 BERT 是双向生成模型，其实它不能直接做自回归生成；2) 误以为 GPT 不能做理解任务，其实通过 prompt 可以；3) 把 MLM 说成简单随机 mask，忽略 80/10/10 和只对 mask 位置算 loss；4) 把 NSP 说成 BERT 必备，忽略 RoBERTa 的改进；5) 混淆 Encoder/Decoder 的注意力掩码；6) 误以为 BERT 预训练和微调输入完全一致，忽略 [MASK] 带来的分布差异。

## 23. 分布式训练框架都了解哪些，能不能简单介绍一下

> 原题 ID：`q3206` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

分布式训练框架都了解哪些，能不能简单介绍一下

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

分布式训练框架可按并行维度（数据/张量/流水线/专家）和工程栈（集合通信、调度、容错）划分，主流有 PyTorch DDP/FSDP、DeepSpeed、Megatron-LM、Horovod、Ray Train、Colossal-AI、JAX/Pathways 等，选型核心是模型规模、集群拓扑与迭代效率的取舍。

### 解析

一、先给分类框架，避免罗列名词。

1) 按并行策略：
- 数据并行 DP：每卡完整模型副本，切分 batch，AllReduce 梯度。代表 PyTorch DDP、Horovod。
- 张量并行 TP：切分单层矩阵乘，层内通信频繁，适合 NVLink 高带宽域。代表 Megatron-LM。
- 流水线并行 PP：按层切 stage，micro-batch 流水，存在 bubble。代表 GPipe、PipeDream、Megatron。
- 专家并行 EP：MoE 中不同专家放不同卡，All-to-All 路由。代表 DeepSpeed-MoE、FairScale。
- 序列/上下文并行 SP/CP：切分序列维度，配合 Ring Attention，代表 Megatron-Core、DeepSpeed-Ulysses。
- 3D/4D 混合：TP×PP×DP×EP 组合，如 Megatron-DeepSpeed。

2) 按工程栈：
- 通信原语：NCCL（GPU）、Gloo（CPU）、MPI；集合操作 AllReduce/AllGather/ReduceScatter/All-to-All。
- 显存优化：ZeRO-1/2/3 切分优化器、梯度、参数；FSDP 等价于 ZeRO-3；重计算、混合精度、Offload。
- 调度与容错：Ray、Kubernetes、TorchElastic、Slurm；checkpoint、弹性伸缩、故障恢复。

二、文字示意图（数据流）：

数据并行：
  DataLoader -> 切 batch -> N 个 GPU 副本 -> 各自 forward/backward -> AllReduce 梯度 -> optimizer step

ZeRO/FSDP：
  参数分片存于各卡 -> forward 前 AllGather 当前层 -> 计算 -> 释放 -> backward 再 AllGather -> ReduceScatter 梯度

- 通信量：DP 与参数量成正比；TP 每层通信，需高带宽；PP 通信少但有 bubble；ZeRO 用通信换显存。

- 工程复杂度：DDP < FSDP < DeepSpeed < Megatron 3D。

**加分点**

1) 能指出 DDP 的梯度 bucket 与 overlap：PyTorch DDP 在 backward 中按 bucket 触发 AllReduce，与反向计算重叠，减少通信暴露；bucket_cap_mb 可调。
2) 能解释 ZeRO 三阶段本质：ZeRO-1 切优化器状态，ZeRO-2 加梯度，ZeRO-3 加参数；FSDP 的 FlatParameter 把多个参数展平成一个 flat buffer，一次 AllGather，减少小通信开销。
3) 能提到通信原语实现：Ring AllReduce 分 ReduceScatter + AllGather 两阶段，带宽最优，与参数无关；NCCL 会根据拓扑选 Ring/Tree。

## 24. Q9：MoE（混合专家模型）的架构原理是什么

> 原题 ID：`q3723` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

Q9：MoE（混合专家模型）的架构原理是什么

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

MoE 用多个专家网络加一个稀疏门控路由器，每个 token 只激活 Top-K 个专家，从而在总参数量暴涨的同时把单 token 计算量控制在稠密模型的量级。

### 解析

一、核心结构
MoE 层通常替换 Transformer 中的 FFN 层，由两部分组成：
1) 专家集合 {E_1..E_N}：每个专家就是一个独立的 FFN（如 SwiGLU），结构相同但参数不共享。
2) 路由器/门控 G(x)：一个小的线性层 + softmax，对每个 token 的隐状态 x 打分，选出 Top-K 个专家。

文字示意图：
  token x ──► Router(线性+softmax) ──► 分数 s_1..s_N
                │
                ├─ Top-K 选择 ──► 专家 E_a, E_b
                │
  y = Σ_{i∈TopK} softmax(s_i) · E_i(x)

二、数据流
输入 token → 路由打分 → 选 Top-K 专家 → 各专家独立前向 → 按门控权重加权求和 → 残差连接输出。未被选中的专家不参与计算，因此 FLOPs 只与 K 有关，而参数量与 N 有关。

三、关键设计取舍
1) 稀疏度：N 越大容量越大，但路由更难均衡；K 通常取 1 或 2。
2) 负载均衡：不加约束时路由器会塌缩到少数专家（赢者通吃）。常用辅助损失 aux loss（如 Switch Transformer 的 load balancing loss）或专家容量上限 + token 丢弃。
3) 容量因子 capacity factor：每个专家最多处理多少 token，超出则丢弃或溢出到次优专家，是吞吐与质量的权衡。
4) 并行策略：专家并行（不同专家放不同卡）+ 数据并行 + 张量并行；All-to-All 通信是主要瓶颈。
5) 扩展性：总参数可到万亿级，但激活参数保持小，训练/推理成本近似稠密小模型，是“参数换质量”的典型架构。

四、代表工作
Switch Transformer（K=1，简化路由）、GShard（Top-2）、Mixtral 8x7B（每层 8 专家选 2）、DeepSeek-MoE（细粒度专家 + 共享专家）。

**加分点**

1) 路由塌缩的数学原因：softmax 后若某专家初始得分略高，梯度会正反馈放大，导致其被选概率越来越高，必须靠 aux loss 或噪声注入打破。
2) 共享专家（DeepSeek-MoE）：把通用知识放共享专家、专有知识放路由专家，减少专家间冗余，提升参数效率。
3) 细粒度专家：把大 FFN 切成更多小专家，组合空间指数增长，同等激活参数下表达力更强。
4) 通信优化：All-to-All 可用分层通信、计算通信重叠、专家分组（grouped GEMM）来隐藏延迟；推理时可用专家缓存/预取。
5) 与稠密模型对比：同等激活 FLOPs 下 MoE 通常质量更好，但显存占用大、batch 内负载不均会导致尾延迟。

**雷区**

1) 误以为 MoE 每个 token 会走所有专家——实际只激活 Top-K，否则计算量爆炸。
2) 把“总参数量”当成“计算量”，忽略激活参数与总参数的区别。
3) 忽略负载均衡问题，认为路由器自然会把 token 均分。
4) 认为 MoE 一定比稠密模型好——在数据量不足或小模型规模下，MoE 可能因路由难训而更差。
5) 忽略 All-to-All 通信和专家并行带来的工程复杂度，只谈算法不谈系统。

## 25. 数据并行、模型并行、流水线并行的区别

> 原题 ID：`q3744` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

数据并行、模型并行、流水线并行的区别

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

数据并行复制模型切分数据，模型并行切分模型本身，流水线并行按层切分模型并让不同批次像流水线一样重叠执行。

### 解析

三者都是把大模型训练/推理负载分摊到多卡或多机上的并行策略，核心区别在于“切什么”。

1) 数据并行（Data Parallel, DP）：每张卡持有完整模型副本，把全局 batch 切成若干小 batch 分给各卡；各卡独立前向、反向，得到各自梯度，再通过 AllReduce 等集合通信求平均/求和，最后各卡用相同梯度更新，保证副本一致。类比：同一道题复印给多个学生做，最后把答案汇总取平均。优点是实现简单、吞吐高、适合模型能放进单卡显存的场景；缺点是显存不省（每卡都有完整参数、梯度、优化器状态），通信量与参数量成正比，模型很大时单卡放不下。

2) 模型并行（Model Parallel, MP，常指张量并行 Tensor Parallel）：把单个算子/层的参数矩阵切开，比如把线性层权重按列或按行切到多卡，每卡只保存一部分参数，前向时各卡算一部分再通过 AllReduce/AllGather 拼出结果。类比：一道大题拆成几个小问，每人只做自己那部分，最后拼成完整答案。优点是能突破单卡显存限制，支持超大模型；缺点是切分粒度细、通信频繁，对网络带宽和延迟敏感，通常只在单机内 NVLink 等高带宽场景使用。

3) 流水线并行（Pipeline Parallel, PP）：按模型层（layer）切分，比如前几层放卡0、中间层放卡1、后几层放卡2；数据按 micro-batch 依次流过各卡，形成流水线，让不同 micro-batch 在不同卡上重叠计算，减少空闲气泡（bubble）。类比：工厂流水线，每道工序只做一部分，产品依次经过各工位。优点是显存按层分摊、通信量相对小（只在层边界传激活）；缺点是存在流水线气泡、需要调度 micro-batch，且实现复杂。

实际大模型训练通常是 3D 并行：数据并行 + 张量并行 + 流水线并行组合使用，例如 Megatron-LM、DeepSpeed 等。选择依据：模型能单卡放下就优先 DP；单卡放不下但单机多卡带宽高可用 TP；跨机扩展常用 PP + DP。

**加分点**

1) 能说出 DP 的通信原语：梯度 AllReduce，常用 Ring AllReduce 把通信量降到与参数量同阶且与卡数无关；ZeRO 把优化器状态/梯度/参数分片，本质是“数据并行的显存优化版”。2) 能区分 TP 与 PP 的通信模式：TP 每层都要通信、延迟敏感，适合 NVLink；PP 只在层边界传激活，通信量小，适合跨机。3) 能提到流水线气泡公式：GPipe 中 bubble 比例约为 (p-1)/(m+p-1)，p 为流水线级数、m 为 micro-batch 数，增大 m 可降低气泡；1F1B 调度比 GPipe 更省显存。4) 能提到 Megatron-LM 的列并行/行并行切分方式，以及 sequence parallel、context parallel 等新变体。5) 能指出 DP 在 batch 很小时梯度噪声大、需要梯度累积或增大 global batch。

**雷区**

1) 把“模型并行”和“流水线并行”混为一谈，认为都是切模型所以一样；实际上 TP 切算子内部、PP 切层，通信模式和适用场景不同。2) 以为数据并行能省显存，实际上每卡都有完整模型副本，显存不省。3) 认为流水线并行没有额外开销，忽略气泡和 micro-batch 调度成本。4) 认为张量并行可以随便跨机，忽略其高频通信对带宽的苛刻要求。5) 把 AllReduce 说成只做求和，忽略需要除以卡数取平均（或等价缩放）。6) 认为三种并行互斥，实际大模型训练常组合成 3D 并行。

## 26. AllReduce 通信的原理，在分布式训练里的作用

> 原题 ID：`q3745` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

AllReduce 通信的原理，在分布式训练里的作用

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

AllReduce 是一种集合通信原语，让所有参与进程的相同形状张量在通信后都得到完全相同的归约结果（如求和），在分布式训练中用于同步各 GPU 的梯度，使数据并行等价于大 batch 训练。

### 解析

一、原理
AllReduce 属于集合通信（collective communication）中的归约类操作。给定 N 个进程，每个进程持有一个长度为 M 的张量 x_i，AllReduce 执行逐元素归约（常见 op：sum、prod、max、min），并把结果 y = op(x_0, x_1, ..., x_{N-1}) 写回所有进程。即：

进程0: x0 ─┐
进程1: x1 ─┼─ AllReduce(sum) ─→ 所有进程都得到 y = x0+x1+...+x_{N-1}
进程2: x2 ─┘

关键点：结果对所有进程一致，因此它同时完成了 Reduce（归约）和 Broadcast（广播）两件事。

二、常见实现算法
1. Ring AllReduce（环形）：把每个进程的张量切成 N 份，分两个阶段：
   - Reduce-Scatter：N-1 步，每步每个进程把一块发给右邻居、同时从左邻居收一块并累加，最终每个进程持有某一块的完整归约结果。
   - All-Gather：N-1 步，把各自持有的归约块沿环传播，最终所有进程拼出完整结果。
   通信量：每进程 2*(N-1)/N * M ≈ 2M，与 N 基本无关，带宽最优，适合大张量。
2. Tree AllReduce（树形）：Reduce 阶段沿树向上归约到根，Broadcast 阶段沿树向下分发。延迟为 O(log N)，适合小张量或 N 很大时降低延迟。
3. Recursive Halving/Doubling：N 为 2 的幂时，log N 步完成，每步通信量 M/2、M/4...，总通信量约 M，延迟 O(log N)。
4. 实际库（NCCL、Gloo、MPI）会根据张量大小、拓扑（NVLink/PCIe/IB）、N 自动选择 Ring、Tree、CollNet、NVLS 等算法。

三、在分布式训练中的作用
数据并行（DDP）中，每张 GPU 有完整模型副本、吃不同 mini-batch。反向传播后每个 GPU 得到本地梯度 g_i。若直接各自更新，等价于各训各的；要等价于全局 batch 训练，需要把梯度求平均/求和后同步：

g = (1/N) * Σ g_i

AllReduce 正好完成 Σ g_i，再除以 N（或先 scale loss）即可。之后每个 GPU 用相同 g 更新，参数保持完全一致。

数据流示意：
前向(各卡本地 batch) → 反向得到本地梯度 → AllReduce(sum) → 除以 N → optimizer.step() → 参数一致 → 下一轮

四、取舍与扩展
- 通信量：梯度大小 = 参数量，AllReduce 每步通信量与参数量成正比，是数据并行的主要瓶颈。
- 与计算重叠：DDP 把梯度按 bucket 分桶，反向传播算完一个 bucket 就异步触发 AllReduce，用通信隐藏计算（hook 机制）。
- 扩展性：Ring 带宽最优但延迟随 N 增长；大 N 时常用分层 AllReduce（节点内 NVLink/NVLS + 节点间 IB），或 2D/3D 并行。
- 与其它并行：张量并行/流水并行内部也大量用 AllReduce/AllGather/ReduceScatter；ZeRO 用 ReduceScatter 替代 AllReduce 以省显存。
- 精度：常用 FP16/BF16 通信 + FP32 累加，或梯度压缩（量化、稀疏化）降低带宽。

**加分点**

1. 能说清 Ring AllReduce 两阶段和 2(N-1)/N*M 通信量，并解释为何与 N 无关。2. 知道 DDP 的 bucket + autograd hook 通信重叠机制，以及 gradient accumulation 时 no_sync 的用法。3. 知道 ZeRO/FSDP 用 ReduceScatter + AllGather 替代 AllReduce 来分片优化器状态/梯度，减少显存。4. 能区分 AllReduce、ReduceScatter、AllGather、Broadcast、AlltoAll 的语义和典型用途。5. 了解 NCCL 的 Ring/Tree/CollNet/NVLS 选择策略，以及拓扑感知（NVLink vs PCIe vs IB）对性能的影响。6. 知道通信与计算重叠、梯度压缩、分层通信等优化手段。7. 能指出 AllReduce 要求所有进程参与且张量形状一致，是同步语义，天然是 barrier。

**雷区**

1. 把 AllReduce 说成只是 Reduce（结果只在根节点）或只是 Broadcast，忽略“所有进程都拿到归约结果”。2. 认为 AllReduce 通信量与 GPU 数量 N 成正比，实际 Ring 下约 2M 与 N 无关。3. 混淆数据并行与模型并行：AllReduce 主要用于数据并行的梯度同步，模型并行更多用 AllGather/AlltoAll/点对点。4. 忽略除以 N（或 loss scaling），导致梯度被放大 N 倍、学习率等效变化。5. 以为 AllReduce 是异步的；它本身是同步集合通信，所有 rank 必须参与，否则 hang。6. 只答“用来同步梯度”而不解释为何能保证参数一致、等价于大 batch。7. 忽略通信是瓶颈，不提重叠、分桶、压缩等工程优化。

## 27. 核心问题：MoE 的路由机制（Router）如何训练

> 原题 ID：`q3779` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

核心问题：MoE 的路由机制（Router）如何训练

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

MoE 路由通过一个可学习的门控网络（Gating Network）为每个 token 计算专家权重，用 softmax 得到稀疏 Top-k 选择，并借助负载均衡损失与可微的加权求和端到端训练。

### 解析

MoE（Mixture of Experts）的路由机制本质是一个‘可学习的软硬结合分配器’。通俗类比：一家大医院有多个专科医生（专家），病人（token）先到分诊台（Router），分诊台根据病人症状给每个医生打分，只让得分最高的 1~2 位医生接诊，最后把他们的诊断按置信度加权汇总。

具体流程：
1) 对每个 token 的隐状态 x，Router 用一个小线性层 W_g 计算 logits：s = W_g · x；
2) 对 s 做 softmax 得到每个专家的概率 p_i；
3) 取 Top-k（常见 k=1 或 2）专家集合 E；
4) 输出 y = Σ_{i∈E} p_i · Expert_i(x)，只对选中的专家做前向，因此计算量近似只与 k 有关，而参数量可以很大；
5) 反向传播时，梯度通过 p_i 和 Expert_i 同时回传，Router 的 W_g 也被更新。

关键训练难点与对策：
- 稀疏选择不可微？Top-k 的‘选谁’是离散的，但‘选中后的加权系数 p_i’是可微的，所以梯度能通过权重回传；同时常用 straight-through 或 Gumbel-Softmax 让选择本身也可微。
- 负载不均：Router 容易只偏爱少数专家，导致其他专家‘饿死’。因此加入负载均衡损失（Load Balancing Loss），如 Switch Transformer 的 auxiliary loss：L_aux = α · N · Σ_i f_i · P_i，其中 f_i 是分给专家 i 的 token 比例，P_i 是 Router 给专家 i 的平均概率，鼓励两者都均匀。
- 训练不稳定：常用 Router z-loss 惩罚 logits 过大，稳定 softmax；也有用噪声 Top-k（加高斯噪声）增加探索。
- 容量因子（capacity factor）：每个专家最多处理多少 token，超出则丢弃或走残差，防止单专家过载。

适用场景：需要极大参数量但推理成本受限的大模型（如 Switch Transformer、GShard、Mixtral、DeepSeek-MoE），以及多任务/多模态中不同专家负责不同子分布。

**加分点**

1) 能区分‘稀疏 MoE 训练’与‘稠密模型训练’：MoE 每步只激活部分参数，因此同样 FLOPs 下可堆更大参数量，但显存要放下全部专家。
2) 能提到 Switch Transformer 的简化：k=1 且 Router 用 softmax，配合 auxiliary loss 和 capacity factor，证明万亿参数可行。
3) 能提到专家并行（Expert Parallelism）：专家分布在不同设备，Router 需要 all-to-all 通信把 token 发到对应专家，通信是瓶颈；DeepSpeed-MoE、FairScale 有实现。
4) 能提到 Router 的‘坍缩’问题：若不加均衡损失，Router 会退化成只选一个专家，等价于稠密模型但浪费参数。
5) 能提到 GShard 的随机路由与 Top-2 门控，以及 ST-MoE 的 Router z-loss 对稳定性的作用。

**雷区**

1) 误以为 Router 是规则/硬编码，实际上它是可学习参数，和专家一起端到端训练。
2) 误以为 Top-k 完全不可微所以 Router 无法训练；实际上加权系数可微，且可用重参数化技巧。
3) 忽略负载均衡损失，只讲‘选 Top-k’；这是面试官最想听的训练关键。
4) 把 MoE 说成‘推理时也激活所有专家’，混淆稀疏激活与稠密计算。
5) 认为专家越多越好，忽略通信开销、显存和负载均衡带来的实际瓶颈。

## 28. 核心问题：BPE 的贪心合并策略有什么问题

> 原题 ID：`q3792` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

核心问题：BPE 的贪心合并策略有什么问题

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

BPE 的贪心合并只看当前最高频相邻对，是局部最优，可能产生次优词表、破坏语义边界、对低频词不友好，且合并顺序不可逆。

### 解析

BPE（Byte Pair Encoding）训练时每一步统计语料中所有相邻符号对的频次，选最高频的一对合并成新符号，重复到达到词表大小。问题在于：
1) 贪心局部最优：每步只选当前频次最高的对，不考虑合并后对未来分词/压缩率/下游任务的影响。例如语料里 'e' 和 's' 频繁相邻，但合并 'es' 可能把 'does'、'yes'、'names' 里的跨语素边界也粘在一起，导致 'do'+'es' 这类错误切分。
2) 频次主导，语义/形态边界被忽略：高频但无意义的字符组合（如空格+常见字母、标点组合）会优先合并，而低频但语义完整的词根/词缀（如 'un-', '-tion'）可能被拆碎。
3) 不可逆与路径依赖：合并顺序一旦确定，后续无法撤销；早期一个错误合并会级联影响后续所有合并，词表质量对语料顺序和初始字符集敏感。
4) 对低频词/长尾不友好：低频词往往被切成很多子词，序列变长，增加计算和语义碎片化；而高频词可能被整体保留，造成词表分布不均。
5) 与语言无关但也不懂语言：纯统计，不区分词素、音节、大小写、数字等，可能把 '2023' 切成 '20'+'23' 或 '2'+'023' 这类无意义片段。
通俗类比：像用贪心算法拼乐高，每次只挑当前最多的两块拼一起，不管拼出来是不是一个完整零件，最后可能拼出一堆奇怪组合，而真正需要的标准件反而没拼出来。
适用场景：BPE 适合语料大、追求压缩率和通用性的场景（如 GPT 系列），但若需要形态学感知或低频词友好，可考虑 WordPiece（带似然）、Unigram LM（概率剪枝）、SentencePiece 的 unigram 模式等。

**加分点**

1) 可提 BPE 原始论文 Sennrich 2016 用于 NMT 子词，以及 GPT-2 的 byte-level BPE 把空格也编码进 token，避免 UNK。2) 可对比 WordPiece 的合并准则：不是频次最高，而是选择使语言模型似然提升最大的对，缓解纯频次偏差。3) 可提 Unigram LM 从大词表反向剪枝，用 EM 估计概率，能保留语义完整子词。4) 可提实际踩坑：BPE 对中文/代码等无空格语言，常把常见汉字组合并，但低频专名被切碎；byte-level 下 emoji 可能被切成多字节 token。5) 可提 'merge 顺序不可逆' 导致无法做全局优化，有工作用强化学习或可微分词来学分词器。

**雷区**

1) 误以为 BPE 是全局最优或能保证语义边界；2) 把 BPE 和 WordPiece 混为一谈，说 WordPiece 也是选最高频对；3) 认为 BPE 合并后可以随意拆分/回退；4) 忽略 byte-level BPE 与字符级 BPE 的区别，说 BPE 一定没有 UNK；5) 只答“贪心可能不是最优”而不解释具体表现（边界破坏、长尾碎片化、路径依赖）。

## 29. 核心问题：Tokenizer 的 fertility（生育率）指标是什么

> 原题 ID：`q3793` ｜ 原分类：工程落地 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

核心问题：Tokenizer 的 fertility（生育率）指标是什么

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

Fertility 是衡量 tokenizer 把文本切碎程度的指标，通常定义为「平均每个词被切成多少个 token」，数值越高说明 tokenizer 对某语言/领域越不友好，同样文本消耗的 token 越多、推理越贵、有效上下文越短。

### 解析

Fertility（生育率）在 tokenizer 语境下指：给定一段文本，tokenizer 产出的 token 总数与「词数」的比值。常见定义有两种：
1) tokens / words：平均每个词被切成几个 token，最常用；
2) tokens / 字符 或 tokens / 字节：衡量压缩率，跨语言比较时更公平。

计算示例：句子 "I love tokenization" 若被切成 ["I"," love"," token","ization"]，词数 3，token 数 4，fertility = 4/3 ≈ 1.33。

为什么重要：
- 成本与延迟：token 是计费和算力的基本单位，fertility 高意味着同样内容要付更多钱、跑更慢。
- 有效上下文：模型上下文窗口按 token 计，fertility 高的语言实际能塞进去的字数更少。
- 公平性：英文为中心训练的 tokenizer 对中文、泰语、阿拉伯语等 fertility 往往显著更高，造成「隐性歧视」。
- 训练/推理一致性：分词粒度影响序列长度分布，进而影响位置编码、batch 内 padding 和显存占用。

工程上通常这样评估：准备目标语言/领域的代表性语料，用 tokenizer 编码，统计 tokens/words、tokens/char、以及 OOV/UNK 率；再对比不同 tokenizer（BPE、WordPiece、Unigram、SentencePiece、tiktoken 等）。

典型量级：英文好的 tokenizer fertility 约 1.1~1.3；中文用英文 tokenizer 可能到 1.5~3+（按字算），泰语、缅甸语等可能更高。这也是为什么很多中文/多语言模型要专门扩词表或重训 tokenizer。

**加分点**

1) 区分指标口径：tokens/word 受分词标准影响大，跨语言比较建议用 tokens/byte 或「压缩率」（bytes per token），因为 byte 是语言无关的基准。
2) 与压缩率的关系：fertility 本质是压缩率的倒数视角，BPE 的 merge 次数、词表大小直接决定它；词表越大 fertility 越低，但 embedding 参数量和 softmax 成本上升，是权衡。
3) 实践踩坑：扩词表后必须重新初始化新 token 的 embedding 并做 continued pretraining，否则新 token 是随机向量，效果反而崩；同时要同步更新 tokenizer 的 special tokens、chat template 和 max_length 配置。
4) 论文参考：XLM 系列、ByT5、CANINE 等工作都讨论过 fertility 与多语言公平性；「tokenizer 是模型性能的隐性瓶颈」在多语言场景被反复验证。
5) 线上监控：可以把输入文本的 fertility 作为数据漂移指标，突然升高往往意味着用户输入了训练分布外的语言/领域（如大量代码、emoji、新网络用语）。

**雷区**

1) 把 fertility 和「词表大小」「OOV 率」混为一谈：它们是相关但不同的指标。
2) 只用英文语料评估就下结论说 tokenizer 好，忽略目标语言/领域。
3) 认为 fertility 越低越好：词表过大、粒度过粗会损失细粒度信息，且 embedding/softmax 成本高，还可能让罕见词被拆得不够。
4) 忽略分词口径：用不同分词器统计 words 数导致对比不公平。
5) 扩词表后不做 continued pretraining，直接上线，导致新 token 语义未训练。
6) 忘记 fertility 会随文本类型变化：代码、数字、URL、emoji 的 fertility 与自然语言差异很大，需分场景统计。

## 30. LLaMA 为什么选 32K 词表

> 原题 ID：`q3794` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

LLaMA 为什么选 32K 词表

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

LLaMA 选择 32K 词表是在模型效率、多语言支持与训练数据规模之间权衡的结果，旨在平衡序列长度、计算开销和词汇覆盖率。

### 解析

LLaMA 的 32K 词表（实际为 32000 个 token）是经过大量实验后确定的。词表大小直接影响：1）嵌入层和输出层的参数量（与词表大小成正比）；2）序列长度（相同文本被切分成更少或更多的 token）；3）计算和内存开销。如果词表太小，常见词会被拆成多个子词，导致序列变长，增加计算成本；如果词表太大，嵌入矩阵过大，训练和推理时 softmax 计算量增加，且低频词学习不充分。LLaMA 基于 BPE 算法在大量多语言语料上训练分词器，32K 是在英语和多语言（如中文、代码）之间取得平衡的常见选择。类比：词表就像字典的收录字数，字典太小，很多词要拆成字来解释，句子变长；字典太大，查字典变慢，且很多生僻字用不上。32K 相当于一本中等规模的字典，覆盖常用词，又不会太臃肿。

**加分点**

1）LLaMA 词表基于 SentencePiece 的 BPE 实现，支持字节回退（byte fallback），能处理未登录字符；2）32K 与 GPT-2/3 的 50K 词表对比，LLaMA 更小但通过更多训练数据（1.4T token）弥补覆盖不足；3）词表大小影响模型并行策略，32K 便于在单卡上放置嵌入层；4）后续 LLaMA 2 仍用 32K，而 LLaMA 3 扩大到 128K 以更好支持多语言和代码，说明词表大小随需求演进。

**雷区**

常见误解：1）认为词表越大越好，忽略计算成本；2）认为 32K 是固定最优，实际取决于数据分布和任务；3）混淆词表大小与模型参数量，误以为词表不影响模型大小；4）忽略分词算法（BPE）和训练数据对词表质量的影响。

## 31. 为什么 LLM 不直接用字符级别的 Tokenizer

> 原题 ID：`q3795` ｜ 原分类：工程落地 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

为什么 LLM 不直接用字符级别的 Tokenizer

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

字符级 Tokenizer 序列过长、语义稀疏、计算与显存成本高，且丢失子词/词级统计规律，因此主流 LLM 采用 BPE/WordPiece/Unigram 等子词分词。

### 解析

LLM 不直接用字符级 Tokenizer，核心是工程权衡：

1) 序列长度与注意力成本：Transformer 自注意力计算/显存约 O(L^2)。英文一个词平均 4~5 个字符，若按字符切，序列长度膨胀 4~5 倍，注意力成本膨胀 16~25 倍。长上下文场景（如 32k token）会直接不可用。

2) 语义粒度太细：单个字符（如 'a'、'e'）几乎不携带独立语义，模型需要更多层/更多数据才能把字符组合成词、短语级表示，样本效率低。子词单元（如 'ing'、'token'、'ization'）更接近语素/高频词，能直接承载语义。

3) 词表与 embedding 效率：字符级词表很小（英文约 100~200），看似省 embedding 参数，但序列变长导致每层激活、KV Cache 线性增长，推理吞吐和显存反而更差。子词词表 3w~15w 能在“词表大小”和“序列长度”之间取得平衡。

4) 统计规律与压缩：BPE 本质是字节/字符级贪心合并高频相邻对，等价于一种可逆压缩。它让常见词成为一个 token，罕见词拆成子词，兼顾 OOV 与高频效率。字符级没有这种频率自适应压缩。

5) 多语言/代码/符号：字符级对中文、日文、代码、emoji 等并不友好。中文一个字常是一个语素，按字符切反而可能合理，但英文/代码会严重膨胀；统一用子词 + byte fallback 更稳。

6) 训练目标：语言模型预测下一个 token，token 粒度影响困惑度定义和梯度信号。子词粒度让每个 token 预测更有信息量，训练更稳定。

例子：句子 'unbelievable' 字符级 12 个 token；BPE 可能切成 'un' + 'believ' + 'able' 3 个 token，序列缩短 4 倍，且每个 token 有形态学意义。

工程上还有：字符级对拼写/噪声更鲁棒，但代价是长序列；实际系统常用 SentencePiece/BPE + byte-level fallback，而不是纯字符。

**加分点**

1) 可引用 BPE 论文（Sennrich 2016）、SentencePiece（Kudo 2018）、GPT-2 byte-level BPE、LLaMA 的 SentencePiece。
2) 能算账：L 膨胀 k 倍，注意力 FLOPs 约 k^2，KV Cache 约 k 倍；给出具体数字更有说服力。
3) 提到 byte-level BPE 解决 OOV 和 Unicode 问题，byte fallback 保证任意字符串可编码。
4) 提到 tokenizer 与模型耦合：换 tokenizer 需重训 embedding 和 LM head，工程迁移成本高。
5) 提到压缩率/fertility 指标：英文 BPE 约 1.3 token/word，中文约 1.5~2 token/字，字符级会差很多。
6) 提到长上下文与 tokenizer 的权衡：token 越短，同样上下文窗口能放的信息越少。

**雷区**

1) 只说“字符级效果差”而不给计算/显存/序列长度原因。
2) 误以为字符级词表小就一定省参数，忽略激活和 KV Cache 随序列线性增长。
3) 把 tokenizer 当成纯预处理，忽略它与 embedding、LM head、上下文窗口、推理成本的强耦合。
4) 认为子词一定比字符好：在中文/日文或拼写纠错任务中，字符级/字级可能更合适，需看语言和任务。
5) 混淆 BPE、WordPiece、Unigram 的算法细节，或说 BPE 基于词频而非相邻对频率。
6) 忽略 byte-level fallback，导致遇到未登录字符时无法编码。

## 32. 核心问题：为什么 Next Token Prediction 能让模型学到如此多的知识

> 原题 ID：`q3802` ｜ 原分类：工程落地 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

核心问题：为什么 Next Token Prediction 能让模型学到如此多的知识

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

Next Token Prediction 本质是对海量文本联合分布的极大似然估计，迫使模型把预测下一个词所需的语法、事实、推理与世界知识压缩进参数中，从而涌现出广泛能力。

### 解析

从目标函数看，给定序列 x1..xT，NTP 最大化 sum_t log P(x_t | x_<t)。这等价于最小化真实数据分布与模型分布之间的交叉熵，也就是对语言联合分布做密度估计。要准确预测下一个 token，模型必须隐式建模：1) 局部语法与搭配；2) 长距离指代、篇章结构；3) 事实知识（如“中国的首都是__”）；4) 一定程度的推理与算法模式（如算术、代码补全）。因为互联网文本是人类知识与推理的投影，预测任务把“理解”变成了降低 loss 的手段。工程上，Transformer 的 self-attention 提供可扩展的条件建模能力，参数量、数据量、算力按 scaling law 增长时，loss 下降并伴随下游能力涌现。一个直观例子：训练模型补全“巴黎是法国的__”，要稳定预测“首都”，模型必须把“巴黎-法国-首都”的关系编码进表示；当这种关系在大量上下文中反复出现，就形成可泛化的知识。另一个例子是代码：预测下一个 token 迫使模型学会括号匹配、变量作用域甚至简单算法，因为这些都是高概率续写的必要条件。

**加分点**

1) 信息论视角：NTP 的 loss 是每 token 的 bits，压缩率越高说明模型对数据生成过程建模越好，Ilya Sutskever 常提“压缩即智能”。2) 条件概率分解：P(x)=prod P(x_t|x_<t) 是自回归的精确分解，没有近似，因此理论上可逼近任意文本分布。3) 与对比学习/MLM 对比：MLM 只学双向表示，不能直接生成；NTP 天然适配生成且训练信号密集（每个位置都有监督）。4) 涌现与相变：Wei et al. 的 emergent abilities、Grokking 现象说明某些能力在 loss 降到某阈值后突然出现。5) 工程踩坑：数据质量比数量更关键，重复数据会导致记忆而非泛化；tokenizer 影响知识密度，中文/代码需注意词表；长上下文训练时 attention 复杂度与位置外推是难点。6) 损失与知识的关系：低 perplexity 不等于事实正确，模型可能学到表面共现而非因果，需 RLHF/检索增强。

**雷区**

1) 误以为 NTP 只是“文字接龙”，没有真正理解；实际上预测压力会倒逼内部表征学习。2) 认为模型在训练时“背答案”，但泛化到未见组合说明不是简单查表。3) 混淆 NTP 与 MLM，认为两者等价；MLM 不能直接做自回归生成。4) 忽视数据分布：如果训练语料有偏，NTP 会放大偏见与错误。5) 认为参数量越大一定越好，忽略数据质量、tokenizer、训练策略与 scaling law 的联合作用。6) 把低 loss 直接等同于高事实准确率，忽略幻觉问题。

## 33. 核心问题：数据配比如何影响模型能力

> 原题 ID：`q3804` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

核心问题：数据配比如何影响模型能力

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

数据配比通过决定各能力维度在训练分布中的相对权重，直接塑造模型的能力偏向与泛化边界，是预训练/微调中最关键的超参之一。

### 解析

数据配比指训练语料中不同来源、领域、语言、模态、质量层级的数据所占比例。它影响模型能力的方式有三层：
1) 分布决定能力：模型学的是训练分布，某类数据占比高，模型在该类任务上的表征就更充分、损失更低。例如代码占比从5%提到20%，HumanEval类指标通常上升，但纯文本推理可能略降。
2) 梯度竞争：不同数据产生的梯度方向不同，配比相当于给各任务损失加权。极端不均衡会让模型被高频模式主导，低频能力被‘淹没’。
3) 质量与多样性权衡：高质量数据重复多轮会过拟合，低质数据多则噪声大。常见做法是质量分层+领域配额，如‘高质量网页:代码:数学:多语=6:2:1:1’。

通俗类比：配比像给运动员配餐，蛋白质、碳水、脂肪比例不同，练出的体型和体能不同；只吃一种会偏科。

适用场景：预训练决定基座能力上限；继续预训练用于领域适配（如医疗、法律）；SFT阶段配比决定指令遵循与安全对齐的偏向；多模态中图文配比决定视觉-语言对齐强度。

实践上常用方法：启发式配额、DoReMi/Group DRO等在线调整、根据验证集能力目标做小规模消融再放大。

**加分点**

1) DoReMi（Google, 2023）用极小代理模型+Group DRO自动学域权重，再放大到主模型，比人工配比在多个下游任务上更稳。2) 数据重复（epoch）与配比耦合：Muennighoff等发现重复约4轮内收益接近新数据，之后急剧衰减，所以‘多放高质量数据’不等于无限重复。3) 代码/数学数据能提升推理，但过量会损害长文写作与常识，需按目标能力做帕累托权衡。4) 配比还影响tokenizer与序列长度分布，间接影响训练效率。

**雷区**

1) 认为‘数据越多越好’，忽视配比与重复的边际递减。2) 把配比当成一次性静态超参，不做小规模消融直接上大训练，浪费算力。3) 只看总loss，不看分域验证集，导致某能力悄悄退化。4) 混淆预训练配比与SFT配比的作用：前者塑基座，后者塑行为与格式。5) 忽略数据质量分层，简单按来源等比例混合。

## 34. 为什么重要：DeepSeek-R1 的核心训练方法，让模型自发涌现推理能力

> 原题 ID：`q3809` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

为什么重要：DeepSeek-R1 的核心训练方法，让模型自发涌现推理能力

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

DeepSeek-R1 的核心是用纯强化学习（GRPO）在可验证奖励下训练基座模型，让长链推理、自我反思等能力自发涌现，而非依赖人工标注的推理轨迹。

### 解析

DeepSeek-R1 的核心训练方法可概括为“冷启动 + 纯 RL + 拒绝采样 + 全场景 RL”的多阶段流程，其中最关键的是 R1-Zero 阶段：直接对 DeepSeek-V3 基座模型做大规模强化学习，不先做 SFT 推理数据，只给最终答案正确性和格式奖励。

原理上，它用 GRPO（Group Relative Policy Optimization）替代 PPO：对同一问题采样一组回答，用组内奖励的均值和标准差做基线，省掉价值网络，降低显存和训练成本。奖励主要是规则型可验证奖励：数学题看最终答案是否匹配，代码题看单元测试是否通过，格式奖励要求把推理过程放在  thinking 标签内。

为什么能“涌现”？因为 RL 的目标是最大化最终正确率，模型在探索中会发现：多算几步、回头检查、换思路重试，比直接猜更容易拿高分。于是长链推理、自我验证、反思、多路径尝试等行为被奖励信号逐步强化，自发出现，而不是被人为教出来的。

通俗类比：就像只告诉学生“考试要及格”，不教解题步骤，学生自己摸索出打草稿、验算、换方法，最后形成一套推理习惯。

适用场景：数学、代码、逻辑推理等答案可自动验证的任务；对开放域写作、主观对话等难以规则验证的任务，纯 RL 效果有限，所以 R1 后续又加入冷启动 SFT、拒绝采样生成高质量推理数据、以及通用对话/安全/写作等全场景 RL，兼顾推理与通用能力。

**加分点**

1）GRPO 的组内归一化优势：同一 prompt 采样 G 个输出，奖励减组均值除组标准差，天然做优势估计，无需 critic，显存约为 PPO 的一半。2）R1-Zero 论文中观察到“aha moment”：模型在训练中自发出现“Wait, let me re-evaluate”这类反思语句，说明推理模式是 RL 涌现而非 SFT 注入。3）可验证奖励的局限：规则奖励容易被 reward hacking，例如格式对但答案错、或冗长刷格式分，因此需要格式+正确性联合奖励和长度惩罚。4）R1 蒸馏到小模型时，用 R1 生成的推理数据做 SFT，小模型推理能力显著提升，说明推理轨迹可迁移。5）工程上 GRPO 需要处理变长序列、KL 约束和采样效率，通常配合 vLLM 做 rollout。

**雷区**

1）误以为 R1 主要靠人工标注的 CoT 数据做 SFT，实际上 R1-Zero 完全跳过推理 SFT，核心是纯 RL。2）把 GRPO 和 PPO 混为一谈，忽略 GRPO 去掉 value model、用组内相对奖励的关键差异。3）认为 RL 能凭空产生新知识，实际上 RL 主要激发基座模型已有的潜在能力，基座太弱则涌现有限。4）忽略可验证奖励的适用范围，以为所有任务都能纯 RL 训好。5）把“涌现”理解成突然出现，忽略它是奖励驱动下逐步强化的行为模式。

## 35. 预训练数据中加入代码为什么能提升推理能力

> 原题 ID：`q3811` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

预训练数据中加入代码为什么能提升推理能力

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

代码数据富含严格的结构、长程依赖和可执行验证信号，迫使模型学习逐步、可检验的推理模式，从而迁移到自然语言推理任务。

### 解析

预训练本质是让模型在大量文本上做下一 token 预测，数据分布决定了模型学到什么‘模式’。代码之所以能提升推理，主要有几层原因：

1. 结构化的长程依赖：代码有括号匹配、变量作用域、函数调用链、控制流等硬约束，模型必须记住并利用几十甚至上百 token 前的信息才能正确预测下一个 token。这天然训练了长上下文依赖和状态跟踪能力，而自然语言里这种约束弱得多。

2. 显式的分步执行语义：代码把‘怎么做’写成顺序步骤（赋值、循环、条件、递归），相当于把推理过程外化成 token 序列。模型在预测这些步骤时，实际上在学习‘中间状态如何一步步演化’，这与思维链（CoT）的逐步推理形式高度同构。

3. 可验证/可执行信号：代码可以运行，对错有客观反馈。虽然预训练本身不做执行，但代码文本中大量存在‘输入-输出’、‘断言-结果’、‘错误-修复’的配对，模型能学到因果性和一致性约束，减少纯文本里常见的模糊、矛盾表述。

4. 抽象与组合：函数、类、模块化让模型看到‘把复杂问题拆成子问题再组合’的范式，这种层次化分解正是复杂推理的核心。

5. 数据多样性与密度：代码覆盖算法、数学、逻辑、字符串操作、数据结构等，单位 token 的信息密度和逻辑密度通常高于普通网页文本。

通俗类比：自然语言像日常聊天，可以含糊、跳跃、靠常识补全；代码像数学证明或菜谱，每一步必须前后一致、可执行、可检验。让模型大量读‘证明/菜谱’，它自然更会一步步推导。

适用场景：需要多步推理、数学、逻辑、工具调用、结构化输出的任务受益明显；纯情感、风格化写作收益较小。

**加分点**

1. 论文层面：Codex、CodeT5、StarCoder 等工作观察到代码预训练对推理的迁移；后续有研究（如‘Code as CoT’、‘Program of Thoughts’）把代码作为推理载体，证明代码形式能提升数学与逻辑任务准确率。
2. 数据配比：不是代码越多越好，通常 5%-20% 代码混入效果较好，过多会损害自然语言流畅性和常识。
3. 课程学习：先自然语言后代码、或代码与自然语言交错，可能比纯代码更利于迁移。
4. 机制解释：代码的‘可执行语义’提供了比自然语言更强的监督信号，类似程序合成中的执行反馈，能缓解幻觉。
5. 踩坑：代码数据质量参差（重复、死代码、错误示例）会引入噪声；只加代码不调 tokenizer/词表，可能因代码 token 切分差而收益打折。

**雷区**

1. 误以为‘代码能直接提升所有能力’，忽略数据配比和任务类型，纯代码预训练反而可能降低自然语言理解。
2. 把‘代码可执行’等同于‘预训练时真的执行了代码’，实际预训练只是文本预测，执行反馈是后续 RL/微调阶段的事。
3. 只强调‘代码有逻辑’，却说不清逻辑如何通过下一 token 预测被学到，缺少长程依赖、状态跟踪、分步语义等机制解释。
4. 忽略 tokenizer 影响：代码中大量符号、缩进、命名风格若切分不合理，会削弱学习效果。
5. 把代码和思维链混为一谈：代码是训练数据，CoT 是推理时提示/微调形式，两者相关但不等同。

## 36. 为什么纯 RL 训练能涌现自我反思

> 原题 ID：`q3815` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

为什么纯 RL 训练能涌现自我反思

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

纯RL训练中，模型通过试错获得奖励信号，逐渐学会在输出前/中生成‘检查、纠错、重试’等内部语言，因为这些行为能提高最终奖励，于是自我反思作为策略涌现。

### 解析

自我反思不是被显式编程的，而是强化学习在序列决策框架下的自然产物。把语言生成看作一个马尔可夫决策过程：状态是已生成的 token 序列，动作是下一个 token，奖励来自最终答案是否正确（或过程奖励模型）。当任务足够难、仅靠一次前向推理难以稳定拿高分时，策略会探索各种 token 序列。某些序列恰好包含‘等等，我前面算错了’‘让我重新检查’这类元认知语言，它们改变了后续生成分布，使最终答案更可能正确，从而获得更高奖励。RL（如 PPO、GRPO、RLOO）通过策略梯度提高这些高奖励轨迹的概率，抑制低奖励轨迹。久而久之，模型就学会了在不确定时主动反思。类比：训练小狗做复杂动作，若它偶然做出‘先闻一闻再跳’的动作才拿到零食，这个‘先检查’的行为就会被强化，而不是训练者直接教它‘闻一闻’。关键条件：1) 任务有可验证的最终奖励；2) 模型有足够的生成自由度，能产生反思类 token；3) 训练中探索到过包含反思且最终正确的轨迹；4) 奖励信号能区分‘反思后正确’与‘不反思也正确’，否则反思不会被特别强化。典型例子：DeepSeek-R1 的纯 RL 训练中，模型自发出现‘wait’‘let me re-check’等长链反思，数学和代码任务准确率随之提升。

**加分点**

1) 从信息论角度：反思相当于在推理路径上增加一次‘内部采样+验证’，用额外计算换正确率，RL 会为高不确定性状态分配更多反思 token。2) 与过程奖励模型（PRM）对比：纯 RL 用结果奖励也能涌现反思，但若加入 PRM 或格式奖励，反思会更早、更结构化。3) 源码层面：GRPO 的组内归一化优势让‘反思后正确’的轨迹获得正优势，而‘不反思也正确’的轨迹优势被相对压低，从而放大反思行为。4) 论文：DeepSeek-R1 报告了‘aha moment’，即训练中期反思 token 频率突增，对应验证集准确率跳升。5) 踩坑：若奖励只给最终答案且训练数据太简单，模型无需反思即可满分，反思不会涌现；若惩罚长度，反思会被压制。

**雷区**

1) 误以为自我反思是模型‘有意识’或‘被提示词教出来的’，忽略 RL 的探索-强化机制。2) 认为纯 RL 必须配合人类标注的反思数据，实际上结果奖励即可。3) 把反思等同于 CoT：CoT 是更一般的中间推理，反思是其中一种元认知子行为，纯 RL 可以只涌现反思而不一定涌现完整 CoT。4) 忽略奖励设计：若奖励可被‘假装反思’（如只输出反思词但答案仍错）刷分，会学到无效反思。5) 认为反思一定提升所有任务，对简单任务反而增加计算开销和错误累积。

## 37. 预训练的基座模型虽然拥有丰富的世界知识和语言能力，但它只知道如何做「下一个 token 预测」，不知道如何与用户进行有意

> 原题 ID：`q3826` ｜ 原分类：工程落地 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

预训练的基座模型虽然拥有丰富的世界知识和语言能力，但它只知道如何做「下一个 token 预测」，不知道如何与用户进行有意义的交互

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

预训练基座模型只具备「续写」能力，必须通过指令微调（SFT）、对齐（RLHF/DPO）和推理期约束（prompt/模板/停止符）把它从「文本补全器」改造成「对话助手」。

### 解析

预训练目标决定了模型的行为：给定前缀，最大化下一个 token 的似然。因此基座模型看到「中国的首都是」会续写「北京」，但看到「请帮我写一封请假邮件」时，它可能续写「请帮我写一封辞职邮件」这类同分布文本，而不是执行指令。

工程上通常分三层改造：
1) 数据与格式层：把交互建模成条件生成。用对话模板（如 ChatML、Llama 的 [INST]/[/INST]、system/user/assistant 角色标记）把多轮对话拼成一条序列，只在 assistant 段计算 loss，让模型学会「看到用户轮就生成助手轮」。同时引入 EOS/停止符，避免模型无限续写。
2) 训练层：SFT 用高质量指令-回答对做监督微调，教会模型遵循指令、拒绝、格式输出；再用 RLHF（PPO）或 DPO/ORPO 等偏好优化，让输出更符合人类偏好（有用、无害、诚实）。SFT 解决「会不会做」，对齐解决「做得好不好、安不安全」。
3) 推理层：用 chat template 严格对齐训练格式，设置 stop 序列、max_tokens、temperature/top_p；对工具调用、JSON 输出等用约束解码（grammar/JSON schema）保证结构合法。

一个典型踩坑：训练时用了某模板，推理时手写 prompt 少了 system 标记或空格，模型表现断崖式下降——因为分布不匹配。另一个坑：只在 assistant 段算 loss 时 mask 写错，把用户 token 也计入 loss，模型会学会「复读用户」。

权衡：SFT 数据质量 > 数量，少量高质量数据往往优于海量噪声；对齐会带来「对齐税」，可能损失部分基座能力（如多样性、数学），需要混入预训练数据或做 KL 约束缓解。

**加分点**

1) 能说出 loss mask 的实现细节：labels 中 user/system 段置 -100，PyTorch CrossEntropyLoss 默认 ignore_index=-100。2) 知道 chat template 是「训练-推理一致性」的关键，HuggingFace tokenizer.apply_chat_template 可统一。3) 了解 RLHF 的 PPO 需要 reward model + value model，显存和工程复杂度高，DPO 用偏好对直接优化、更易落地但依赖偏好数据质量。4) 提到「基座能力遗忘」可用 LoRA/QLoRA 降低，或在对齐时加 KL 惩罚、混入通用语料。5) 知道停止符与 EOS 的区别，以及 vLLM/TGI 中 stop 参数的处理。6) 能举例：基座模型做 few-shot 也能「假装」对话，但稳定性差、易被 prompt 注入，生产必须 SFT+对齐。

**雷区**

1) 以为「加个 prompt 模板」就等于会对话，忽略 SFT/对齐的必要性。2) 认为基座模型完全不能对话——few-shot 下可以，只是不可靠。3) 混淆 SFT 与 RLHF 的作用，以为 SFT 就能解决安全/偏好问题。4) 忽略训练与推理模板不一致导致的性能崩塌。5) 把「下一个 token 预测」和「对话」对立，其实对话也是条件 next-token 预测，只是条件分布被改造了。6) 只谈算法不谈工程：显存、数据配比、停止符、约束解码等落地细节缺失。

## 38. 张量并行TP、流水线并行PP、数据并行DP这三者的拓扑结构你应该怎么排布

> 原题 ID：`q3851` ｜ 原分类：手撕算法 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

张量并行TP、流水线并行PP、数据并行DP这三者的拓扑结构你应该怎么排布

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

DP 放最外层跨节点复制，TP 放节点内高带宽 NVLink 域内切分，PP 跨节点按层切分并让相邻 stage 尽量同机/同高速链路，形成 DP×PP×TP 三维网格，通信量大的维度用带宽最高的链路。

### 解析

核心原则：按通信频率与通信量把并行维度映射到带宽/延迟不同的互联层级上。

1) 通信特性对比：
- TP：每层前向/反向都要 all-reduce/all-gather（Megatron 每层 2 次 all-reduce），通信最频繁、量最大，必须放在带宽最高的域内，即单机/单 pod 的 NVLink/NVSwitch（如 H100 NVLink 900GB/s，跨机 IB 仅 400Gb/s≈50GB/s）。TP 组通常 ≤8（单机 GPU 数），最多跨一个 NVLink 域。
- PP：只在 stage 边界传激活/梯度，通信量小但延迟敏感（bubble 与流水节拍），适合跨节点；相邻 stage 最好在同一节点或同一 leaf switch 下，减少 P2P 延迟。PP 度可较大（如 8~16），配合 micro-batch 与 1F1B/interleaved 调度降低 bubble。
- DP：只在反向结束后 all-reduce 梯度，频率最低、可异步/分桶/压缩，放最外层跨节点甚至跨机房；DP 组内用 Ring all-reduce 或 ZeRO 分片。

2) 推荐拓扑（由内到外）：
- 最内层：TP group = 单机 8 卡（NVLink 全互联）。
- 中间层：PP group 跨机，但每个 PP rank 内部包含完整 TP group；相邻 stage 尽量同机架/同 leaf。
- 最外层：DP group 跨节点/跨机架，复制整个 PP×TP 单元。
即 rank 排布：global_rank = dp_rank * (pp_size*tp_size) + pp_rank * tp_size + tp_rank，保证同一 TP 组 rank 连续、落在同机。

3) 例子：64 卡、8 机×8 卡，TP=8、PP=4、DP=2。每台机器一个 TP=8 组；4 台机器组成一个 PP=4 流水线；另 4 台做 DP 副本。TP 走 NVLink，PP 走 IB，DP 走 IB/跨机架。

4) 边界 case：TP 跨机导致 all-reduce 走 IB，吞吐骤降；PP stage 数不能超过层数，且 micro-batch 数需 ≥ PP 度才能填满流水；DP 度=1 时退化为纯 TP+PP；GPU 数不能被 TP*PP 整除时报错；异构链路（NVLink+PCIe）要按最慢链路定 TP 上限。

核心代码（rank 映射与校验，Python）：
```python
def build_parallel_groups(world_size, tp, pp, dp):
    assert world_size == tp*pp*dp, 'world_size must equal TP*PP*DP'
    assert tp <= 8, 'TP should stay within NVLink domain'
    groups = {'tp': [], 'pp': [], 'dp': []}
    for dp_r in range(dp):
        for pp_r in range(pp):
            base = dp_r*pp*tp + pp_r*tp
            groups['tp'].append(list(range(base, base+tp)))
    for dp_r in range(dp):
        for tp_r in range(tp):
            g = [dp_r*pp*tp + pp_r*tp + tp_r for pp_r in range(pp)]
            groups['pp'].append(g)
    for pp_r in range(pp):
        for tp_r in range(tp):
            g = [dp_r*pp*tp + pp_r*tp + tp_r for dp_r in range(dp)]
            groups['dp'].append(g)
    return groups
```
复杂度：建组 O(world_size)，通信复杂度 TP 每层 O(2*B*S*H) all-reduce，PP O(B*S*H) P2P，DP O(P) all-reduce。

**加分点**

1) 引用 Megatron-LM 论文的 TP 每层两次 all-reduce、序列并行减少 LayerNorm/dropout 激活重复；2) 提到 3D 并行 rank 排布与 NCCL 拓扑感知（NCCL_TOPO_AWARE、SHARP、NVLS）；3) PP 调度：GPipe vs 1F1B vs interleaved 1F1B，bubble 比例 (pp-1)/(m+pp-1)；4) DP 用 ZeRO-1/2/3 或 FSDP 分片优化器/梯度/参数，减少 DP 通信；5) 实际踩坑：TP 跨机后 MFU 掉 30%+；PP 相邻 stage 跨 spine 导致 P2P 延迟抖动；DP all-reduce 与 PP P2P 争抢 IB 带宽，需分通道或 QoS。

**雷区**

1) 把 TP 放到跨节点最外层，导致每层 all-reduce 走 IB，性能崩溃；2) 认为 DP 通信最大所以放最内层，实际 DP 频率最低；3) 忽略 PP 的 bubble，PP 度设得比 micro-batch 还大导致空泡；4) 认为三者可任意排列，忽略 NVLink 域大小与 GPU 数整除约束；5) 混淆 TP 与 DP 的 all-reduce 语义（TP 是层内激活切分，DP 是梯度同步）。

## 39. 你要讲你是怎么建立数据清洗管线的

> 原题 ID：`q3854` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

你要讲你是怎么建立数据清洗管线的

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

数据清洗管线是把原始数据经校验、去重、缺失处理、格式统一、异常检测等步骤，变成可信、可复用、可监控的数据资产的一套自动化流程。

### 解析

我会按‘先定义质量、再分层处理、最后监控闭环’来建立。

1) 先定义数据质量契约：明确字段类型、范围、唯一键、空值率、枚举值、时间格式等，写成可执行的规则（如 JSON Schema / Great Expectations / 自定义校验器），并和上游约定 SLA。

2) 分层管线：
- 采集层：从 DB、日志、API、消息队列拉取，保留原始快照（raw），便于回溯。
- 清洗层：
  a. 去重：按主键/业务键，用窗口函数或布隆过滤器/Redis 去重；
  b. 缺失值：按业务决定丢弃、填充（均值/中位数/前向填充）或标记；
  c. 格式统一：时间统一 UTC、手机号/邮箱正则归一、编码统一 UTF-8；
  d. 异常值：3σ、IQR、分位数截断或隔离到死信队列；
  e. 关联补全：维表 join 补全缺失维度。
- 输出层：写入数仓/特征库，并记录血缘和版本。

3) 工程实现：用 Airflow/Dagster/Spark/Flink 编排，任务幂等、可重跑；清洗逻辑写成纯函数便于单测；配置化规则，避免硬编码。

4) 监控与闭环：统计每步的输入/输出行数、空值率、分布漂移、失败率；异常告警并自动隔离脏数据；定期回看规则命中率，迭代规则。

类比：就像净水厂，先定水质标准，再经过沉淀、过滤、消毒，最后检测合格才出厂，不合格的水回流或排掉。

**加分点**

1) 幂等与 exactly-once：用业务主键 + upsert/merge，配合 checkpoint 或事务表，保证重跑不产生重复。
2) 数据质量框架：Great Expectations、Deequ、Soda 的断言式校验，把规则当代码管理。
3) 血缘与版本：记录 raw→clean 的转换版本，出问题可回滚到某个快照。
4) 漂移检测：PSI/KL 散度监控特征分布，防止训练/推理不一致。
5) 死信队列：脏数据不直接丢，进 DLQ 人工复核，形成反馈闭环。

**雷区**

1) 只做去重和填缺失，忽略质量契约和监控，导致脏数据反复出现。
2) 清洗逻辑硬编码在 SQL 里，无法单测和复用。
3) 任务不幂等，重跑产生重复数据。
4) 直接丢弃异常值而不记录，丢失业务信号。
5) 忽略时区和编码，导致时间错位、乱码。
6) 把清洗和特征工程混为一谈，边界不清。

## 40. MoE 中 Router 的训练信号来自哪里？为什么容易出现负载不均衡？⭐

> 原题 ID：`q3886` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

MoE 中 Router 的训练信号来自哪里？为什么容易出现负载不均衡？⭐

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

MoE 的 Router 没有独立标签，它的训练信号来自主任务损失经各专家输出反向传播到门控权重的梯度，再叠加负载均衡辅助损失；负载不均衡是因为路由是“赢者通吃”的离散选择，存在正反馈和自我强化，容易让少数专家吸走大部分 token。

### 解析

1) 训练信号来源：MoE 层输出 y = Σ_i g_i(x) · E_i(x)，其中 g(x)=softmax(TopK(W_g·x))。Router 参数 W_g 的梯度由两部分构成：一是主任务损失 L_task 对 y 的梯度，经 g_i 和 E_i 反传到 W_g，即 ∂L/∂W_g = Σ_i (∂L/∂y)·E_i(x)·∂g_i/∂W_g；二是负载均衡辅助损失 L_bal（如 Switch Transformer 的 importance/load loss、GShard 的 aux loss）直接约束路由分布。所以 Router 不是用“该选哪个专家”的监督标签训练，而是靠任务目标 + 均衡正则联合优化。

2) 为什么容易负载不均衡：TopK 路由是离散、稀疏、赢者通吃的选择。若某专家早期因初始化或数据分布略占优势，它会被更多 token 选中，获得更多梯度、更新更快、变得更强，形成“富者愈富”的正反馈；反之冷门专家得不到足够训练，逐渐退化。加上 batch 内 token 分布本身不均衡、专家容量有限、通信/并行导致的路由抖动，都会加剧马太效应。

3) 通俗类比：像公司里几个客服窗口，客户看到哪个窗口排队短就去哪，但系统又按“当前最闲”动态派单；一旦某个窗口被标记为快，大家都涌过去，它反而变慢，其他窗口闲置。Router 就是那个派单员，若只按当前表现派单，就会把流量集中到少数窗口。

4) 常见缓解：加负载均衡辅助损失（importance loss 让各专家被选概率均匀、load loss 让实际 token 数均匀）、专家容量 capacity factor + token dropping、噪声路由（noisy top-k gating）、Router z-loss 稳定 logits、以及 DeepSeek 等用的无辅助损失偏置项/专家选择路由。

**加分点**

能提到 Switch Transformer 的 aux loss 形式：L_aux = α·N·Σ_i f_i·P_i，其中 f_i 是专家 i 分到的 token 比例，P_i 是路由概率均值，N 为专家数；并指出该损失对 Router 梯度的影响。还能提到 Router z-loss 抑制 logits 过大导致 softmax 饱和、以及 TopK 中 K>1 时梯度会同时流向多个专家。工程上可提 all-to-all 通信与专家并行下，负载不均会直接造成某些 GPU 空转、吞吐下降，因此均衡不仅是精度问题也是系统问题。

**雷区**

常见错误：1) 以为 Router 有独立监督标签或单独预训练，实际上它只靠主任务损失和辅助损失联合训练；2) 把负载不均衡简单归因于“数据不均衡”，忽略路由离散选择带来的正反馈；3) 认为加辅助损失后 Router 梯度只来自辅助损失，其实主任务梯度仍是主要信号；4) 混淆 importance loss 与 load loss，或以为容量因子能完全消除不均衡；5) 忽略推理时 Router 仍可能漂移，训练均衡不等于推理均衡。

## 41. BPE 和 WordPiece 的合并标准有什么不同？分别有什么优劣？⭐

> 原题 ID：`q3889` ｜ 原分类：手撕算法 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

BPE 和 WordPiece 的合并标准有什么不同？分别有什么优劣？⭐

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

BPE 按相邻符号对出现频率最高合并，WordPiece 按能最大提升语料似然的相邻符号对合并（等价于按 PMI/互信息式得分合并）。

### 解析

两者都是自底向上的子词分词算法：初始把词拆成字符（或字节），反复合并相邻符号对，直到词表达到目标大小。

1) BPE（Byte-Pair Encoding）
- 合并标准：统计语料中所有相邻符号对 (a,b) 的频次 count(a,b)，每次选频次最高的对合并成新符号 ab。
- 原理：贪心地压缩高频共现的字符序列，使常见片段成为独立 token。
- 例子：语料 {low:5, lower:2, newest:6, widest:3}，初始字符集后，'e' 与 's' 相邻出现 6+3=9 次，'es' 会被优先合并；之后 'est' 等继续合并。
- 复杂度：朴素实现每轮重扫语料 O(N)，共 V 轮，O(NV)；用优先队列+增量更新可接近 O(N log N)。
- 优点：简单、训练快、可跨语言、对未登录词友好（可回退到字符/字节）。
- 缺点：只看频次，可能合并出语义弱但高频的片段（如 'ing' 与 'ed' 竞争时被高频噪声主导）；对低频词切分可能不理想。

2) WordPiece（BERT 使用）
- 合并标准：对相邻对 (a,b)，计算 score = freq(ab) / (freq(a) * freq(b))，选 score 最大的对合并。
- 原理：该分数等价于点互信息（PMI）的单调变换，衡量 a、b 共同出现的“意外程度”，即合并后对语料似然的提升最大（在语言模型视角下，最大化训练语料的 likelihood）。
- 例子：若 'a' 和 'b' 各自都很高频但很少相邻，score 低，不会合并；若 'q' 和 'u' 几乎总相邻，score 高，优先合并。
- 复杂度：与 BPE 同量级，但每轮需维护 freq(a)、freq(b) 并重算分数，常数更大。
- 优点：更偏向合并“强绑定”的片段，切分更符合语言学直觉，对稀有词/形态变化更稳。
- 缺点：计算稍复杂；对高频但弱关联的常见词可能切得更碎；实现细节（如是否用 \u2581 表示空格、是否限制最大词长）影响大。

边界 case：
- 空串/单字符：直接返回原串或 [UNK]。
- 未登录词：BPE 可回退到字节/字符；WordPiece 常用 [UNK] 或继续按字符切。
- 词表大小：达到目标后停止；若语料太小可能提前无对可合并。
- 大小写/标点：是否归一化、是否把空格当符号，会显著改变结果。
- 多语言/中文：BPE 对中文按字合并，WordPiece 可能因 PMI 把常见双字词合并。

核心代码（Python，简化版，展示两种合并标准）：

from collections import Counter, defaultdict

def get_pairs(word):
    return [(word[i], word[i+1]) for i in range(len(word)-1)]

def train_bpe(corpus, vocab_size):
    # corpus: list of words (str), 已按空格拆好
    vocab = Counter()
    for w in corpus:
        vocab[' '.join(list(w)) + ' </w>'] += 1
    merges = []
    while len(merges) < vocab_size:
        pairs = Counter()
        for word, freq in vocab.items():
            syms = word.split()
            for p in get_pairs(syms):
                pairs[p] += freq
        if not pairs:
            break
        best = max(pairs, key=pairs.get)
        merges.append(best)
        # 合并
        new_vocab = Counter()
        bigram = ' '.join(best)
        for word, freq in vocab.items():
            new_word = word.replace(bigram, ''.join(best))
            new_vocab[new_word] += freq
        vocab = new_vocab
    return merges

def train_wordpiece(corpus, vocab_size):
    vocab = Counter()
    for w in corpus:
        vocab[' '.join(list(w)) + ' </w>'] += 1
    merges = []
    while len(merges) < vocab_size:
        pair_freq = Counter()
        sym_freq = Counter()
        for word, freq in vocab.items():
            syms = word.split()
            for s in syms:
                sym_freq[s] += freq
            for p in get_pairs(syms):
                pair_freq[p] += freq
        if not pair_freq:
            break
        best = max(pair_freq, key=lambda p: pair_freq[p] / (sym_freq[p[0]] * sym_freq[p[1]] + 1e-9))
        merges.append(best)
        new_vocab = Counter()
        bigram = ' '.join(best)
        for word, freq in vocab.items():
            new_word = word.replace(bigram, ''.join(best))
            new_vocab[new_word] += freq
        vocab = new_vocab
    return merges

# 示例
corpus = ['low']*5 + ['lower']*2 + ['newest']*6 + ['widest']*3
print(train_bpe(corpus, 10))
print(train_wordpiece(corpus, 10))

**加分点**

1) 可指出 WordPiece 的 score 是 PMI 的变形：log(freq(ab)/(freq(a)freq(b))) 与 PMI 同序，最大化它等价于在 unigram 语言模型下最大化语料似然（可提论文《Japanese and Korean Voice Search》/BERT 论文）。
2) 可提 BPE 的字节级变体（GPT-2 的 byte-level BPE）解决未登录词，WordPiece 在 BERT 中配合 ## 前缀表示非词首子词。
3) 可提实现优化：BPE 用优先队列+并查集/链表增量更新，避免每轮全量重扫；WordPiece 需维护符号频次表，合并后更新受影响对的分数。
4) 可提与 Unigram LM 分词的区别：Unigram 从大词表开始按损失删除，BPE/WordPiece 从字符开始合并。
5) 踩坑：WordPiece 原始实现中空格用 \u2581 或 ## 表示，若忽略会改变分数；BPE 合并顺序影响最终切分，训练与推理必须一致。

**雷区**

1) 误以为 WordPiece 也是按频次合并，或以为 BPE 用似然。
2) 把 WordPiece 的 score 说成 freq(ab)/freq(a) 或 freq(ab)/freq(b)，漏掉分母乘积。
3) 忽略边界：空串、单字符、未登录词、词表提前耗尽。
4) 认为两者复杂度差异巨大，其实同量级，只是常数和更新方式不同。
5) 把 BPE 的合并标准说成“最长匹配”或“按词频”，混淆训练与推理阶段。
6) 忘记说明推理时如何切分：BPE 按合并顺序贪心应用，WordPiece 用最长匹配/贪心最大分数。

## 42. DeepSeek-R1 的 “aha moment” 是什么？为什么纯 RL 训练能涌现自我反思？⭐

> 原题 ID：`q3899` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

DeepSeek-R1 的 “aha moment” 是什么？为什么纯 RL 训练能涌现自我反思？⭐

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

“aha moment”指 DeepSeek-R1 在纯 RL 训练中自发出现的、模型突然学会停下来重新审视并修正自己推理过程的现象，说明自我反思能力可由奖励驱动涌现，而非必须靠人工标注的反思数据教出来。

### 解析

背景：DeepSeek-R1 先用冷启动数据做 SFT，再做大规模 RL（GRPO），奖励主要来自规则可验证的答案正确性（数学、代码等）和格式奖励，不依赖人类标注的“反思/检查”轨迹。

什么是 aha moment：训练过程中，模型输出里开始频繁出现类似“Wait, let me re-check”“Alternatively”“Hmm, that doesn't seem right”这类自我质疑与回退重算的片段，并且这些片段出现后答案正确率显著提升。论文把它称为“aha moment”，即模型像人一样突然“开窍”，意识到需要检查自己的中间步骤。

为什么纯 RL 能涌现自我反思：
1) 奖励只关心最终答案对不对，但正确率高的轨迹往往包含“检查—发现错误—修正”的模式。RL 是“结果导向”的搜索，策略会朝高期望回报的方向更新，于是这种能提高正确率的元行为被强化。
2) 反思本质是一种可提升期望回报的推理策略：在难题上，直接一条路走到黑容易错，而“生成候选—自检—回退”相当于在 token 空间做搜索/验证，增加了命中正确答案的概率。RL 会自然发现并放大这类策略。
3) 长 CoT 提供了“思考空间”：允许生成很长的推理链，模型才有余地在中间插入检查与重试；如果限制长度，反思行为很难出现。
4) 规则奖励的稀疏但可靠信号 + 大 batch 采样（GRPO 用组内相对优势）让“偶尔出现的反思轨迹”被识别为高优势样本，从而被反复采样和强化，形成正反馈。

通俗类比：就像教小孩做数学题，只告诉他最后答案对不对，不教他“要检查”。小孩为了做对，会自己摸索出“算完再验算一遍”的习惯，因为验算能提高做对概率，于是这个习惯被保留下来。

适用场景：需要多步推理、可自动验证答案的任务（数学、代码、逻辑），纯 RL 更容易涌现反思；而开放式写作等难以自动判对错的任务，效果有限。

**加分点**

1) 论文细节：DeepSeek-R1 用 GRPO（Group Relative Policy Optimization），对同一 prompt 采样一组输出，用组内归一化优势替代 critic，降低 RL 成本；奖励含 accuracy reward（规则判对错）和 format reward（强制 思考 包裹）。
2) 与 R1-Zero 对比：R1-Zero 完全不做 SFT 冷启动，直接 RL，也出现 aha moment，但可读性差、语言混杂；R1 加冷启动后更稳定，说明反思涌现不依赖 SFT 教反思，但 SFT 能规范表达。
3) 机制上可联系“测试时计算/搜索”：反思相当于把推理时的搜索内化进模型权重，类似 STaR、self-consistency、过程奖励模型的动机，但 R1 证明仅用结果奖励也能诱导出过程性行为。
4) 可提“长度与熵”现象：RL 训练中回答长度和推理熵上升，模型学会用更长思考换正确率，反思片段是其中典型模式。

**雷区**

1) 误以为 aha moment 是人工设计/提示词诱导的，或以为需要专门标注反思数据；实际是 RL 自发涌现。
2) 误以为纯 RL 完全不需要任何监督：R1 实际有冷启动 SFT 和多阶段训练，R1-Zero 才是纯 RL，要区分。
3) 把 aha moment 说成模型有了意识或真正“理解”，它只是统计上被奖励强化的推理模式。
4) 认为反思一定提升所有任务表现：在不可验证或开放任务上，反思可能只是啰嗦甚至放大错误。
5) 混淆“结果奖励”和“过程奖励”：R1 主要用结果/规则奖励，过程奖励反而易导致奖励黑客，这点常被答反。

## 43. 张量并行和流水线并行可以同时用吗？3D 并行是什么？⭐

> 原题 ID：`q3904` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

张量并行和流水线并行可以同时用吗？3D 并行是什么？⭐

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

可以同时用，二者正交：张量并行切分单层内部计算，流水线并行切分模型层间阶段，3D 并行就是数据并行+张量并行+流水线并行三者组合。

### 解析

先讲两个概念的本质。

1) 张量并行（Tensor Parallel, TP）：把同一层（比如一个 Linear 或 Attention）的权重矩阵按维度切开，分到多张卡上，每张卡只算一部分，再通过 All-Reduce / All-Gather 把结果拼起来。它切的是“层内”，通信频繁、量大，所以一般限制在单机内（NVLink/NVSwitch 高带宽），典型如 Megatron-LM 的列并行+行并行。

2) 流水线并行（Pipeline Parallel, PP）：把模型按层切成若干 stage，每张卡/每组卡负责一段，数据像工厂流水线一样依次流过各 stage。它切的是“层间”，通信量小（只在 stage 边界传激活），但会引入流水线气泡（bubble），需要 micro-batch、1F1B、interleaved 等调度来降低空转。

两者可以同时用，因为切分维度正交：TP 在 stage 内部继续切单层，PP 在 stage 之间切层。比如 8 卡一组做 TP，再把模型分成 4 个 stage 做 PP，就得到 TP×PP 的二维网格。

3) 3D 并行 = 数据并行（DP）× 张量并行（TP）× 流水线并行（PP）。把 GPU 排成一个三维网格：DP 维复制完整模型、切分数据；PP 维切分层；TP 维切分层内张量。这样能同时突破单卡显存、单机带宽和全局 batch 的限制，是训练 GPT-3/LLaMA 这类大模型的标配（Megatron-LM + DeepSpeed）。

通俗类比：训练大模型像盖一栋大楼。DP 是同时开多个工地盖同样的楼（数据不同）；PP 是把楼分成地基、主体、装修几段，不同施工队接力干；TP 是某一层楼里，一面墙由几个人各砌一半再拼起来。三者可以叠加，互不冲突。

适用场景：模型大到单卡放不下、单机也放不下时，用 PP 跨机切层；单层矩阵太大或想减少单卡计算时用 TP（尽量机内）；想扩大吞吐/数据量时加 DP。

**加分点**

1) 通信特性对比：TP 每层都要 All-Reduce，通信量大且对延迟敏感，所以通常限制在 NVLink 域内（如单机 8 卡）；PP 只在 stage 边界传激活，通信量小，可跨机甚至跨机房。
2) 气泡与调度：朴素 PP 有 (p-1)/(m+p-1) 量级的气泡，用 micro-batch 增大 m、1F1B、interleaved 1F1B（Megatron 的 virtual pipeline）可显著降低；interleaved 还能减少显存峰值。
3) 并行度选择经验：TP 一般 ≤ 单机 GPU 数（如 8），PP 跨机，DP 用剩余维度；总卡数 = TP×PP×DP。
4) 与 ZeRO/FSDP 的关系：ZeRO 属于数据并行范畴的显存优化（切分优化器状态/梯度/参数），常与 3D 并行叠加成“3D+ZeRO”。
5) 源码/论文：Megatron-LM 论文（Shoeybi et al. 2019）给出 TP 的列/行并行实现；GPipe（Huang et al. 2019）和 PipeDream 讲 PP 调度；DeepSpeed 的 3D 并行配置可作参考。

**雷区**

1) 误以为 TP 和 PP 互斥、只能二选一——它们维度正交，可叠加。
2) 把 PP 当成“数据并行的一种”——PP 切的是模型层，不是数据。
3) 忽略 TP 的通信开销，把它跨机部署，导致带宽瓶颈、训练变慢。
4) 忽略 PP 的气泡成本，以为流水线并行没有额外开销。
5) 混淆 3D 并行的三个维度，把 ZeRO 也算成独立第四维（ZeRO 本质是 DP 的显存优化，不是新的切分维度）。
6) 认为并行度越大越好，实际受通信、气泡、batch size 限制，需要权衡。

## 44. 第一阶段：通过超大规模弱监督数据进行对比学习预训练

> 原题 ID：`q3917` ｜ 原分类：概念基础 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

第一阶段：通过超大规模弱监督数据进行对比学习预训练

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

第一阶段通过海量弱监督数据（如图文对）进行对比学习预训练，让模型学会将语义相关的样本在表示空间中拉近、不相关的推远，从而获得通用的多模态表示能力。

### 解析

对比学习预训练的核心思想是：从无标签或弱标签数据中构造正负样本对，通过对比损失（如InfoNCE）训练编码器，使得正样本对的表示相似度高，负样本对的相似度低。在超大规模弱监督数据（如互联网上的图像-文本对）上，这种预训练可以学习到强大的跨模态对齐表示。

通俗类比：就像教一个孩子认识世界，给他看大量图片和对应的文字描述（弱监督），让他自己发现“狗”的图片和“狗”这个词经常一起出现，而“狗”和“汽车”很少一起出现。通过不断对比，他逐渐理解图片和文字之间的语义关联。

原理：给定一个batch的N个图像-文本对，对比学习的目标是让第i个图像与第i个文本的相似度（正样本）最大化，同时与其余N-1个文本的相似度（负样本）最小化。损失函数通常采用InfoNCE：
L = -log( exp(sim(vi, ti)/τ) / Σ_j exp(sim(vi, tj)/τ) )
其中sim为余弦相似度，τ为温度系数。

适用场景：多模态预训练（如CLIP、ALIGN）、自监督视觉表示学习（如SimCLR、MoCo）、跨模态检索、零样本分类等。

**加分点**

1. 可提及CLIP的工程细节：使用对称的InfoNCE损失，即同时计算图像到文本和文本到图像的对比损失；温度系数τ作为可学习参数。
2. 可讨论负样本采样策略：batch内负样本、动量队列（MoCo）、记忆库等，以及如何避免假阴性（如两个不同文本描述同一图像）。
3. 可提及数据规模与质量的影响：CLIP使用4亿图文对，ALIGN使用18亿，数据噪声大但规模效应显著。
4. 可对比生成式预训练（如GPT）与对比式预训练的区别：前者学习生成，后者学习判别式表示。
5. 可提及下游任务迁移：零样本迁移、线性探测、微调等。

**雷区**

1. 误以为对比学习需要人工标注的强监督数据，实际上弱监督（如图文对）即可。
2. 混淆对比学习与生成式学习，认为预训练必须用生成目标。
3. 忽略负样本的重要性，认为只需正样本即可。
4. 认为对比学习只能用于图像，实际上可用于文本、音频、视频等多模态。
5. 错误理解温度系数的作用，认为它只是缩放因子，实际上它控制对困难负样本的关注程度。

## 45. MoE 的负载均衡（路由崩溃/routing collapse）问题是什么？有哪些主流解决方案？

> 原题 ID：`q4013` ｜ 原分类：概念基础 ｜ 来源：Claw题库·Agent开发面试题库 v2.2

### 题干

MoE 的负载均衡（路由崩溃/routing collapse）问题是什么？有哪些主流解决方案？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

路由崩溃自我强化、辅助负载均衡损失、容量因子加溢出残差、共享专家、Expert Choice、改进路由策略

### 解析

门控网络倾向于把大部分 token 持续发给少数「热门」专家，这些专家训练更快、更易被选中，形成自我强化的不平衡（routing collapse），导致热门专家过载、冷门专家得不到训练、极端时退化为只用 1~2 个专家。主流方案：1) 辅助负载均衡损失——鼓励每个专家收到的 token 比例与路由概率趋于均匀（常用变异系数平方作约束）；2) 容量因子（capacity factor）——给每个专家设 token 上限，溢出 token 走残差连接跳过（可能丢失信息）；3) 共享专家（DeepSeekMoE）——设始终激活的通用专家承载公共知识；4) 改进路由如 Expert Choice（专家选 token）、Sinkhorn 双归一化、负载感知分数调整。
