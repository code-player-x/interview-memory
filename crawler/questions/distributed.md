## 2. 多智能体系统如何避免无限循环和通信冗余？

> 原题 ID：`q0018` ｜ 原分类：架构设计 ｜ 来源：javabetter Agent 面试 / CSDN 2026 攻略

### 题干

多智能体系统如何避免无限循环和通信冗余？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

防循环三板斧：最大步数/迭代上限、状态哈希检测重复状态即中断、超时熔断返回当前最优解。通信冗余靠清晰消息协议(带 AgentID/任务ID/消息类型)，指挥官只处理『最终结果』类消息，忽略中间过程。

### 解析

循环根因多为 Agent 互相等待或反复处理无解子任务；防护=硬性步数上限+状态哈希判重+超时。冗余=多 Agent 汇报相似中间结果淹没指挥官；用结构化消息协议与『只收最终结果』策略降噪。

**加分点**

提出 Definition of Done 明确终止条件；Token 控制(对 Agent 间对话摘要)；有意义的重复检测(连续三次同 Action 强制转人工)。

**雷区**

不设上限靠模型『自觉停止』；所有中间消息都发给指挥官导致上下文爆炸。

## 5. 一致性哈希算法原理是什么？在分布式(如向量库/缓存分片)里怎么用？

> 原题 ID：`q0061` ｜ 原分类：架构设计 ｜ 来源：牛客 后端/Agent 面经

### 题干

一致性哈希算法原理是什么？在分布式(如向量库/缓存分片)里怎么用？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

把节点和 key 映射到同一个环(0~2^32)，key 顺时针找到第一个节点归属它。加/删节点只影响相邻区间的少量 key(而非全量 rehash)。用虚拟节点解决数据倾斜，让分布更均匀。

### 解析

普通哈希 mod N 在节点变化时几乎所有 key 重新映射，缓存雪崩。一致性哈希只迁移故障/新增节点邻近的 key，迁移量约 1/N。虚拟节点(每物理节点映射多个环上点)平滑负载。适用缓存分片、向量库分片、负载均衡。

**加分点**

讲清『变更只影响相邻区间』的迁移量优势；虚拟节点解决倾斜；对比 mod N 的雪崩。

**雷区**

说不清为何比 mod N 好；忽略数据倾斜(不提虚拟节点)。

### 难度

★★★

### 标签

`一致性哈希` `分布式` `分片`

## 6. 请详细讲解分布式令牌桶限流的实现

> 原题 ID：`q0083` ｜ 原分类：架构设计 ｜ 来源：小红书 面经汇总

### 题干

请详细讲解分布式令牌桶限流的实现

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

单机令牌桶按时间匀速补令牌、取令牌扣减；分布式用『集中计数（Redis）』或『网关统一限流』：以 user/API 为 key，Lua 脚本原子地『计算当前令牌=min(cap, last+rate*Δt)、判断够扣则放行』，保证原子性与精度。

### 解析

令牌桶=容量 capacity+速率 rate。分布式实现：① 存令牌数与上次时间到 Redis，用 Lua（原子）做『 refill + 扣减 + 返回』，避免竞态；② 或各节点本地桶+中心配额（适合高并发、放宽精度）；③ 也可用 Redis+滑动窗口/漏桶。关键点：时间用服务器单调时钟、Lua 保证原子、限流维度可组合（IP/用户/接口）。

**加分点**

能写 Lua 伪代码、提到时钟漂移、与『网关层限流 vs 应用层限流』的取舍。

**雷区**

用非原子『先读后写』导致超发；忽略分布式时钟。

### 难度

★★★

### 标签

`限流` `令牌桶` `分布式`

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

区分『能力路由』与『负载均衡』两个维度；提到 Agent 卡片与实时负载；给出容错与防循环手段。

**雷区**

## 9. 同一工具因超时被重复调用，怎么避免重复执行高风险操作？大量 Agent 任务并发调大模型怎么做限流？

> 原题 ID：`q161` ｜ 原分类：工程落地 ｜ 来源：（未标注）

### 题干

同一工具因超时被重复调用，怎么避免重复执行高风险操作？大量 Agent 任务并发调大模型怎么做限流？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

防重复：调用前用幂等键/分布式锁占位，超时重试携带同一键，服务端去重或校验状态。限流：对 LLM 调用做令牌桶/信号量，按模型维度配额，加队列与优先级，超出排队或降级。

### 解析

重复执行：客户端对每次工具调用生成幂等键（如 task_id+step+tool），写入分布式锁/去重表；超时重试携带同键，服务端若已执行则直接返回原结果，避免二次副作用（尤其写操作）。并发限流：①对 LLM provider 设全局令牌桶/信号量控制 QPS 与并发数；②按模型（不同费率/限速）分组配额；③任务入队列，超阈排队，关键任务高优先级；④加退避与熔断；⑤必要时批量/异步化降低瞬时压力。

**加分点**

幂等键+去重防重复副作用；令牌桶/信号量按模型配额；队列+优先级。

**雷区**

重试不带幂等键会重复执行 DELETE 类操作；不限流会打爆模型配额触发 429 雪崩。

### 选项

### 答案

项目简介：

基于Go语言开发的一个微服务系统，可以用做微服务下的闹钟服务系统，支持高精准，高负载的定时需求处理，可以向各个业务提供定时任务服务。例如帮助设备自动巡检实现定时巡检任务的注册功能。

个人职责：

1、负责微服务整体设计：主要运用了Kratos框架等Go微服务通用技术。

2、负责存储设计：通过运用MySQL+Redis的二级存储结构，数据分片，数据有序性，数据冷热分区等设计，有效解决了高精准，高负载等问题。

3、负责落地实现： 通过引入模块化+异步化设计思路，让代码实现层次分明，块职责清晰。有效提升了后续的扩展性和可维护性。

难点/亮点：

高精准：通过数据的分治，有序性，二级存储结构设计，为高频扫描提供基础，同时结合Go协程池等技术对任务处理速度的提升，有效的将定时任务的精准度控制在最大误差1秒左右。

高负载：指同一时间大批量任务触发。通过引入RedisZSET对数据进行分片，为任务并发处理提供基础能力，再结合Go协程池等技术，使得高负载情况下任务也能快速处理。

每次添加定时任务时，执行ZAdd动作，以定时任务的执行时间戳作为排序的键Score)进行有序结构的搭建;
ZADD key score member
每次查询定时任务时，执行ZRangeByScore动作，以当前时刻的时间戳加上一个微小偏移量作score的左右边界，
从 Redis 6.2.0 开始，ZRANGEBYSCORE 被标记为弃用，推荐使用 ZRANGE 命令的 BYSCORE 选项来实现相同的功能。
ZRANGE key min max BYSCORE [WITHSCORES] [REV] [LIMIT offset count]
- key：有序集合的键名。
- min：分数范围的最小值（包含）。
- max：分数范围的最大值（包含）。
- 可选参数：

- WITHSCORES：返回成员及其分数。
- LIMIT offset count：从结果集中跳过 offset 个成员，返回最多 count 个成员。

数据冷热分区：有效的协调冷热数据对不同资源的占用是非常关键的。IoTtimer通过定时迁移模块migrator的设计，让动态的热数据一直维护在缓存方便高效存取，把冷数据放在磁盘或延迟冷数据的生成也减少了对关键缓存资源的占用。

### 业务背景描述？

之前的公司，主要是做以视频为核心的各种设备的，然后现在都要求支持设备上云的功能，有很多公司的历史设备公司也要求实现逐步上云，我们物联中台的核心功能就是要支持设备快速上云，所以我们的大多数工作都是和支撑新老设备的快速上云有关的。设备在上云后，是需要跑一定时间的自动化巡检任务的，确保设备的服务调用功能正常，这个自动化巡检就是选择各个节点的凌晨非高峰时间段，定时周期性的触发设备的自动化用例，之前设备少的时候，定时周期任务的触发配置都是写在自动化脚本的配置文件里的，但是后来随着接入历史设备的增多，节点的增多，这些定时任务的配置管理起来就很不方便，所以就有了我们这个定时微服务，来负责多节点设备自动化巡检任务的管理和触发。

### 介绍一下你这个定时微服务？

这个定时微服务功能比较聚焦，可以结合手机上的“闹钟”来理解，只是我们这个是分布式下的闹钟微服务。

这个定时微服务依赖简单，只依赖了mysql+redis这两种最常用的存储技术。整个定时微服务的数据存储设计上运用了分治策略对数据分片和数据冷热分区，落地实现上运用了模块化、异步化等思想。最终的让这个定时微服务具有功能聚焦、高精准、高负载的特性。
模块化的话，就是我们是按功能进行了模块划分，包括任务生成器，调度器，触发器，和执行器

## 11. 如何设计一个分布式ID

> 原题 ID：`q0173` ｜ 原分类：架构设计 ｜ 来源：飞书知识库·系统设计面试题题库

### 题干

如何设计一个分布式ID

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

为了保证全局唯一性可以用时间作为区分点一部分，时间尽可能细化，可以精确到毫秒，甚至是微秒和纳秒。

### 解析

为了保证全局唯一性可以用时间作为区分点一部分，时间尽可能细化，可以精确到毫秒，甚至是微秒和纳秒。如果是分布式系统有多台机器，可以根据机器ID再进行一下区分。如果机器运行的特别快，1毫秒有大量ID生成，可以结合实际限制下实际生成的ID数目。

如果N台机器去ID生成服务器的服务端得到全局ID，很容易保证全局唯一且自增的，但是存在单点失效的问题，不满足高可用。

#### 雪花算法（[简述雪花算法的原理！](https://www.bilibili.com/video/BV1hX4y1k7nw/?spm_id_from=333.337.search-card.all.click&vd_source=071e98898557028cf1e9013c33c721b3)）（1+41+10+12）

生成的结果是一个int64的数据。核心思想是：使用41bit作为毫秒数，10bit作为机器的ID(5个bit是数据中心，5个bit的机器ID)，12bit作为毫秒内的流水号，意味着每个节点在每毫秒可以产生 4096（2^12）个ID。最后还有一个符号位，永远是0。

优点：优点是毫秒数在高位，自增序列在低位，整个ID都是趋势递增的。不依赖数据库等第三方系统，以服务的方式部署，稳定性更高，生成ID的性能也是非常高的。可以根据自身业务特性分配bit位，非常灵活。

缺点：强依赖机器时钟，如果机器上时钟回拨，会导致号重复或者服务会处于不可用状态。

#### Redis生成ID

因为Redis是单线程的，也可以用来生成全局唯一ID。可以用Redis的原子操作INCR和INCRBY来实现。使用Redis集群来获取更高的吞吐量。假如一个集群中有5台Redis，可以初始化每台Redis的值分别是1,2,3,4,5，步长都是5，各Redis生成的ID如下：

- A: 1,6,11,16；
- B: 2,7,12,17；
- C: 3,8,13,18；
- D: 4,9,14,19；
- E: 5,10,15,20。

负载到哪台机器提前定好，未来很难做修改。3\~5台服务器基本能够满足需求，但步长和初始值一定需要事先确定，使用Redis集群也可以解决单点故障问题。

优点：不依赖于数据库，灵活方便，且性能优于数据库；数字ID天然排序，对分页或需要排序的结果很有帮助。

缺点：如果系统中没有Redis，需要引入新的组件，增加系统复杂度；需要编码和配置的工作量较大。

#### UUID

可以利用数据库也可以利用程序生成，一般全球唯一。UUID是由32个的16进制数字组成，所以每个UUID的长度是128位(16^32 = 2^128)。UUID有多个实现版本，影响它的因素包括时间、网卡MAC地址、自定义Namespace等等。

优点：简单，代码方便；生成ID性能非常好，基本不会有性能问题；全球唯一，在遇见数据迁移，系统数据合并，或者数据库变更等情况，可以从容应对。

缺点：没有排序，无法保证趋势递增；UUID往往是使用字符串存储，查询的效率比较低；存储空间比较大，如果是海量数据库，就需要考虑存储量的问题；传输数据量大；不可读。

#### 美团Leaf

Leaf-segment：

直接用数据库自增ID充当分布式ID，减少对数据库的频率操作。过程是从数据库批量的获取自增ID，每次从数据库取出一个号段范围，例如 [1,10000] 代表10000个ID，业务服务将号段在本地生成1\~10000的自增ID并加载到内存，在当前号段消费到某个点时，就异步的把下一个号段加载到内存中。

而不需要等到号段用尽的时候才去更新新号段。这样做很大程度上的降低了系统的风险。Leaf-segment采用双buffer的方式，它的服务内部有两个号段缓存区segment。当前号段已消耗10%时，还没能拿到下一个号段，则会另启一个新的更新线程去更新下一个号段。

Leaf保证了总是会缓存两个号段，即便某一时刻数据库挂了，也会保证发号服务可以正常工作一段时间。通常推荐号段(segment)长度设置为服务高峰期发号QPS的600倍(10分钟)，这样即使DB宕机，Leaf仍能持续发号10-20分钟不受影响。

biz_tag | 针对不同业务需求，用biz_tag字段来隔离，如果以后需要扩容时，只需对biz_tag分库分表即可 |

优点：Leaf服务可以很方便的线性扩展，性能完全能够支撑大多数业务场景；容灾性高：Leaf服务内部有号段缓存，即使DB宕机，短时间内Leaf仍能正常对外提供服务。

缺点：ID号码不够随机，能够泄露发号数量的信息，不太安全；DB宕机会造成整个系统不可用(用到数据库的都有可能)。

Leaf-snowflake：

Leaf-snowflake基本上就是沿用了snowflake的设计，ID组成结构：正数位(占1比特)+ 时间戳(占41比特)+ 机器ID(占5比特)+ 机房ID(占5比特)+ 自增值(占12比特)，总共64比特组成的一个int64类型。不同点主要是在workId的生成上，Leaf-snowflake依靠Zookeeper生成workId。Leaf中workId是基于ZooKeeper的顺序ID来生成的，每个应用在使用Leaf-snowflake时启动时都会都在Zookeeper中生成一个顺序ID，相当于一台机器对应一个顺序节点。

启动服务的过程大致如下：启动Leaf-snowflake服务，连接Zookeeper，在leaf_forever父节点下检查自己是否已经注册过；如果有注册过直接取回自己的workerID(zk顺序节点生成的int类型ID号)，启动服务；如果没有注册过，就在该父节点下面创建一个持久顺序节点，创建成功后取回顺序号当做自己的workerID号，启动服务。Leaf-snowflake对Zookeeper是一种弱依赖关系，除了每次会去ZK拿数据以外，也会在本机文件系统上缓存一个workerID文件。一旦Zookeeper出现问题，恰好机器出现故障需重启时，依然能够保证服务正常启动。

优点：ID号码是趋势递增的8byte的64位数字，满足上述数据库存储的主键要求。

缺点：依赖ZooKeeper，存在服务不可用风险。

## 14. Redis 如何解决集群情况下分布式锁的可靠性

> 原题 ID：`q0441` ｜ 原分类：后端八股 ｜ 来源：飞书知识库·Redis面试题整理

### 题干

Redis 如何解决集群情况下分布式锁的可靠性

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

为了保证集群环境下分布式锁的可靠性，Redis 官方已经设计了一个分布式锁算法 Redlock（红锁）。

### 解析

为了保证集群环境下分布式锁的可靠性，Redis 官方已经设计了一个分布式锁算法 Redlock（红锁）。

它是基于多个 Redis 节点的分布式锁，即使有节点发生了故障，锁变量仍然是存在的，客户端还是可以完成锁操作。官方推荐是至少部署 5 个 Redis 节点，而且都是主节点，它们之间没有任何关系，都是一个个孤立的节点。

Redlock 算法的基本思路，是让客户端和多个独立的 Redis 节点依次请求申请加锁，如果客户端能够和半数以上的节点成功地完成加锁操作，那么我们就认为，客户端成功地获得分布式锁，否则加锁失败。

这样一来，即使有某个 Redis 节点发生故障，因为锁的数据在其他节点上也有保存，所以客户端仍然可以正常地进行锁操作，锁的数据也不会丢失。

Redlock 算法加锁三个过程：

1. 第一步是，客户端获取当前时间（t1）。
2. 第二步是，客户端按顺序依次向 N 个 Redis 节点执行加锁操作：

- 加锁操作使用 SET 命令，带上 NX，EX/PX 选项，以及带上客户端的唯一标识。
- 如果某个 Redis 节点发生故障了，为了保证在这种情况下，Redlock 算法能够继续运行，我们需要给「加锁操作」设置一个超时时间（不是对「锁」设置超时时间，而是对「加锁操作」设置超时时间），加锁操作的超时时间需要远远地小于锁的过期时间，一般也就是设置为几十毫秒。
3. 第三步是，一旦客户端从超过半数（大于等于 N/2+1）的 Redis 节点上成功获取到了锁，就再次获取当前时间（t2），然后计算计算整个加锁过程的总耗时（t2-t1）。如果 t2-t1 < 锁的过期时间，此时，认为客户端加锁成功，否则认为加锁失败。

可以看到，加锁成功需同时满足两个条件（简述：如果有超过半数的 Redis 节点成功的获取到了锁，并且总耗时没有超过锁的有效时间，那么就是加锁成功）：

- 条件一：客户端从超过半数（大于等于 N/2+1）的 Redis 节点上成功获取到了锁；
- 条件二：客户端从大多数节点获取锁的总耗时（t2-t1）小于锁设置的过期时间。

加锁成功后，客户端需要重新计算这把锁的有效时间。计算的结果是「锁最初设置的过期时间」减去「客户端从大多数节点获取锁的总耗时（t2-t1）」。如果计算的结果已经来不及完成共享数据的操作了，我们可以释放锁，以免出现还没完成数据操作，锁就过期了的情况。

加锁失败后，客户端向所有 Redis 节点发起释放锁的操作，释放锁的操作和在单节点上释放锁的操作一样，只要执行释放锁的 Lua 脚本就可以了。

【同源补充】来自同源题「如何用 Redis 实现分布式锁？需要注意什么？」
SET NX PX、原子加锁、唯一 value、Lua 释放、超时防死锁
用 SET key value NX PX 30000 原子加锁（避免 setnx+expire 两步的非原子问题）。需唯一 value 以便仅释放自己锁；用 Lua 脚本保证『判断+删除』原子；设置合理超时防死锁；Redlock 用于多实例更高可用。避免误删他人锁。

### 答案

1. 锁超时失效：业务未执行完，锁已过期，其他客户端可获取锁，导致数据冲突。

### 解析

1. 锁超时失效：业务未执行完，锁已过期，其他客户端可获取锁，导致数据冲突。

- 客户端A获取锁成功，但业务执行时间 超过锁的过期时间（如锁10秒过期，但业务耗时15秒）。锁自动释放后，客户端B获取到锁并操作共享资源。客户端A完成后 误删锁（删除的是B的锁），导致数据不一致。

解决方案：

- 锁的 value 使用唯一标识（如UUID），删除时校验是否为自己的锁（Lua脚本保证原子性）。
- 合理设置锁超时时间（或使用 看门狗机制 自动续期，如Redisson）。

1. 误删锁：非原子操作删除锁时，可能误删其他客户端的锁（如A删了B的锁）。 解决方案：使用 Lua脚本 保证校验和删除的原子性：

- 客户端A获取锁后，执行 GET + DEL 删除锁，但两步操作 非原子性，可能误删其他客户端的锁。
2. 主从切换丢锁：主节点宕机时，锁未同步到从节点，新主节点可能重复分配锁。  解决方案：

- 客户端A在主节点获取锁成功，但主节点 宕机后未同步到从节点。从节点升为主后，客户端B也能获取锁，导致 锁互斥失效。

- 使用 RedLock算法（需多个独立Redis实例，多数成功才算获取锁）。
- 权衡后接受风险（如业务允许短暂不一致）。
3. 不可重入：同一线程多次获取同一把锁时，会被阻塞（SETNX 不支持可重入）。 解决方案：

- 使用 Redisson 等客户端，实现可重入锁（内部用Hash记录线程ID和重入次数）。
4. 竞争性能差：高并发下大量重试抢锁，增加Redis负载。  解决方案：

- 高并发下大量客户端 重试抢锁，导致Redis CPU飙升或网络开销增大。

- 增加随机退避时间（如指数退避）。
- 改用 Zookeeper/etcd 等有序节点实现的锁（公平性更好）。

一句话总结：SETNX简单但不完美，生产环境建议用成熟方案（如Redisson/Zookeeper）。

## 17. Nginx有哪些负载均衡算法

> 原题 ID：`q0784` ｜ 原分类：后端八股 ｜ 来源：飞书知识库·计算机网络面试题整理

### 题干

Nginx有哪些负载均衡算法

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

我了解到的主要有普通轮询、加权轮询、IP哈希、URL哈希、最短响应时间、最短连接这些负载均衡算法。

### 解析

我了解到的主要有普通轮询、加权轮询、IP哈希、URL哈希、最短响应时间、最短连接这些负载均衡算法。（两轮询、两哈希、两最短）

大体上可以分为下面几类：

- 任务平分类：负载均衡系统将收到的任务平均分配给服务器进行处理，这里的“平均”可以是绝对数量的平均，也可以是比例或者权重上的平均，比如轮询和加权轮询算法。
- 负载均衡类：负载均衡系统根据服务器的负载来进行分配，可以用CPU负载来衡量，也可以用连接数、I/O使用率、网卡吞吐量等来衡量系统的压力，比如最短连接数算法。
- 性能最优类：负载均衡系统根据服务器的响应时间来进行任务分配，优先将新任务分配给响应最快的服务器，比如最短响应时间算法。

## 18. **客户端负载均衡**和**服务端负载均衡有啥区别？**

### 题干

**客户端负载均衡**和**服务端负载均衡有啥区别？**

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

负载均衡（Load Balancing）是分布式系统中的关键技术，用于将请求均匀分配到多个服务器上，以提高系统的可用性、性能和扩展性。

### 解析

负载均衡（Load Balancing）是分布式系统中的关键技术，用于将请求均匀分配到多个服务器上，以提高系统的可用性、性能和扩展性。负载均衡可以分为客户端负载均衡和服务端负载均衡两种主要方式。

1. 服务端负载均衡：服务端负载均衡通常由专门的负载均衡器（如硬件设备或软件）实现，位于客户端和后端服务器之间。客户端请求首先到达负载均衡器，负载均衡器根据策略将请求转发到合适的服务器。

常见实现方式：

- 硬件负载均衡器：如F5 BIG-IP、Citrix ADC等，性能高但成本较高。
- 软件负载均衡器：如Nginx、HAProxy、Apache等，灵活且成本较低。

优点：对客户端透明，客户端无需知道后端服务器的细节。集中管理，便于维护和扩展。

缺点：负载均衡器可能成为单点故障，需通过集群或高可用方案解决。增加网络延迟，因为请求需经过负载均衡器。

2. 客户端负载均衡：客户端负载均衡将负载均衡逻辑放在客户端，客户端直接决定将请求发送到哪个服务器，通常结合服务发现机制（如Consul、Eureka、Zookeeper）动态获取可用服务器列表。

常见实现方式：

- Ribbon：Spring Cloud中的客户端负载均衡库，支持多种算法。
- gRPC：内置客户端负载均衡功能。
- 自定义实现：根据需求自行实现负载均衡逻辑。

优点：减少中间节点，降低延迟。避免负载均衡器成为单点故障。

缺点：客户端实现复杂，需处理服务发现和负载均衡逻辑。每个客户端需维护服务器列表，增加客户端负担。

3. 实际应用中的选择

- 微服务架构：通常采用客户端负载均衡，结合服务发现机制，减少中间层依赖。
- 传统Web应用：常用服务端负载均衡，通过Nginx、HAProxy等工具集中管理流量。

4. 动态负载均衡

现代系统常结合动态负载均衡，根据服务器负载、响应时间等实时调整流量分配，进一步提升系统性能。

总结

- 服务端负载均衡：通过中间件集中管理流量，适合传统架构。
- 客户端负载均衡：由客户端直接分配请求，适合微服务架构，减少中间层依赖。

### 解析

[IP限流怎么做](https://www.nowcoder.com/feed/main/detail/87992a533f834f3291b08831bb7309ef?sourceSSR=search)

IP限流是一种用于控制来自特定IP地址的请求频率的技术，通常应用于防止滥用、拒绝服务攻击（DoS）或者确保公平使用资源。简要来说，实现IP限流可以通过以下几种方式：

1. 基于令牌桶算法或漏桶算法：这两种算法是流量整形和速率限制的经典方法。令牌桶算法允许突发流量，在一段时间内积累“令牌”，每个到达的请求消耗一个令牌。如果桶中没有足够的令牌，请求就会被丢弃或延迟处理。漏桶算法则是以恒定的速率处理请求，超出速率的请求会被排队等待或者直接拒绝。
2. 滑动窗口计数器：这种方法通过记录每个IP在特定时间窗口内的请求数量来实现限流。可以使用固定窗口或滑动窗口机制。滑动窗口更精确，因为它考虑了时间的连续性，避免了固定窗口可能产生的临界峰值问题。
3. Nginx限流模块：如果你使用Nginx作为反向代理或负载均衡器，可以利用它的limit_req模块进行IP限流。你可以配置每秒允许的最大请求数，并且可以设置一个共享内存区域来存储状态，以及定义如何处理超过限制的请求（如延迟处理或返回错误）。
4. Redis结合Lua脚本：对于分布式的系统，可以使用Redis结合Lua脚本来实现IP限流。Redis可以用来存储每个IP的请求计数和时间戳，而Lua脚本则可以在不锁定的情况下原子地更新这些值并检查是否超过了限制。
5. API网关：许多API网关产品（如Kong、Apigee等）提供内置的限流功能，可以根据IP地址、用户凭证或其他条件来限制访问速率。它们通常提供了灵活的策略配置界面，便于管理和调整限流规则。

在实际应用中，选择哪种方法取决于具体的需求、现有基础设施以及性能要求。例如，在高并发场景下，你可能需要选择那些能够高效处理大量连接并且对系统资源消耗较小的方法。同时，为了提高用户体验，还可以设计合理的响应机制，比如当达到限流阈值时，返回友好的提示信息给客户端。

关于四层负载均衡（通常指Service，在某些上下文中可能特指如Kubernetes中的Service概念）与七层负载均衡（Ingress）的问题，可以这样简要回答它们的异同点：

相同点

- 目的：两者的主要目的都是为了分散到服务器的流量，提高应用程序的可用性和扩展性。
- 功能：都可以实现请求的转发，将客户端的请求分配给不同的后端服务实例。

不同点

- 工作层次：

- 四层负载均衡（Service）工作于传输层，主要根据IP地址和端口号进行流量分发，不考虑应用层的信息。由于仅基于网络层的信息进行决策，因此其逻辑相对简单。

- 使用场景：

- 四层负载均衡适用于对性能要求高，且不需要理解应用层协议的情况。
- 七层负载均衡更适合需要根据应用层信息进行智能路由的应用场景，比如微服务架构下的API网关角色。
- 安全性：

- 七层负载均衡可以通过解析应用层数据提供额外的安全检查，如SSL终止、WAF(Web应用防火墙)集成等。
- 四层负载均衡通常不具备这些高级安全特性。

通过这样的对比，可以看出四层和七层负载均衡各有优势，选择哪一种取决于具体的应用需求、性能考量以及安全要求。

## 22. 什么是BASE理论

> 原题 ID：`q0953` ｜ 原分类：架构设计 ｜ 来源：飞书知识库·分布式面试题整理

### 题干

什么是BASE理论

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

BASE理论是对CAP理论的延伸，特别适用于大规模分布式系统。

### 解析

BASE理论是对CAP理论的延伸，特别适用于大规模分布式系统。它强调通过牺牲强一致性来获得高可用性和性能。BASE是以下三个特性的缩写：

1. Basically Available（基本可用）：系统在出现部分故障时，仍然能够提供服务，尽管可能是降级的服务。

- 例子：在一个电商网站中，如果商品详情服务不可用，系统可以返回缓存中的旧数据或简化的商品信息，而不是完全不可用。
2. Soft state（软状态）：系统的状态可能会随着时间的推移而变化，即使没有外部输入。这意味着系统不保证数据的即时一致性。

- 例子：在一个分布式缓存系统中，缓存数据可能会在一定时间后过期或被更新，即使没有新的写操作。
3. Eventually consistent（最终一致性）：系统保证在没有新的更新操作的情况下，经过一段时间后，所有节点上的数据会达到一致状态。

- 例子：在一个分布式数据库中，写操作可能会先在一个节点上完成，然后通过异步复制的方式传播到其他节点，最终所有节点上的数据会一致。

实际应用场景

1. 社交网络：用户发布的内容可能需要一些时间才能在所有节点上同步。

- 原因：高可用性和性能比即时一致性更重要。
2. 电商网站：商品库存信息可能会在不同节点上有短暂的不一致，但最终会一致。

- 原因：系统需要处理高并发请求，保证高可用性。
3. 内容分发网络（CDN）：内容更新可能会延迟传播到所有边缘节点。

- 原因：高可用性和低延迟比即时一致性更重要。

BASE理论通过牺牲强一致性来获得高可用性和性能，特别适用于大规模分布式系统。它强调系统的基本可用性、软状态和最终一致性，使得系统在面对故障和高并发时仍然能够提供服务。

【同源补充】来自同源题「BASE 理论是什么？」

BASE 是对 CAP 中 AP 的延伸：Basically Available（基本可用，允许降级）、Soft state（软状态，允许中间不一致）、Eventually consistent（最终一致）。适合高可用互联网系统，牺牲强一致换可用性与性能。

### 题干

负载均衡有哪些算法

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

1. 轮询（Round Robin）：依次将请求分配到每个服务器，循环往复。

### 解析

1. 轮询（Round Robin）：依次将请求分配到每个服务器，循环往复。

- 适用场景：适合服务器性能相近的场景，如静态资源分发。

2. 加权轮询（Weighted Round Robin）：根据服务器权重分配请求，性能强的服务器处理更多请求。

- 适用场景：适合服务器性能差异较大的场景，如混合新旧硬件。

3. 最少连接（Least Connections）：将请求分配到当前连接数最少的服务器。

- 适用场景：适合长连接或请求处理时间不均衡的场景，如文件下载、视频流。

4. 加权最少连接（Weighted Least Connections）：结合服务器权重和连接数分配请求。

- 适用场景：适合服务器性能差异大且请求处理时间不均衡的场景。

5. IP哈希（IP Hash）：根据客户端IP地址哈希值分配请求，确保同一客户端始终访问同一服务器。

- 适用场景：适合需要会话保持的场景，如购物车、用户登录状态。

6.URL哈希：是一种基于URL路径的负载均衡算法，适合需要缓存优化和静态资源分发的场景。它能够将相同URL的请求固定到同一台服务器，提升缓存命中率和性能。

- 适用场景：适合缓存优化和静态资源分发（如图片、CSS、JS文件），相同URL的请求落到同一台服务器，可以利用本地缓存，减少重复计算和网络传输。
- CDN节点缓存静态内容。通过URL哈希将相同内容固定到同一节点，提高缓存命中率。

7. 随机（Random）：随机选择服务器分配请求。

- 适用场景：适合简单负载均衡场景，无需复杂调度。

8. 最短响应时间（Least Response Time）：将请求分配到响应时间最短的服务器。

- 适用场景：适合对响应速度要求高的场景，如实时数据处理。

根据实际需求选择合适的算法，以优化系统性能和资源利用。

限流的作用

限流的主要作用是控制系统的请求流量，防止系统因突发流量或恶意请求而过载。它可以：

1. 保护系统稳定性，避免资源耗尽或崩溃。
2. 保证服务质量，确保合法用户能够正常访问。
3. 防止资源滥用，限制恶意用户或爬虫的请求频率。

1. 防止系统过载：系统的处理能力有限，限流可以确保请求量在系统承载范围内。

5. 满足业务需求：在 API 开放平台或高并发场景中，限流是必要的控制手段。

总结

限流是后端开发中保障系统稳定性和可用性的重要机制，能够有效应对高并发、恶意请求和资源滥用等问题，确保系统在高负载下仍能稳定运行。

## 27. 限流有哪些算法？每个限流算法有什么优缺点

> 原题 ID：`q0958` ｜ 原分类：架构设计 ｜ 来源：飞书知识库·分布式面试题整理

### 题干

限流有哪些算法？每个限流算法有什么优缺点

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

常见的限流算法及其优缺点

1. 计数器算法（固定窗口）：统计单位时间内的请求数量，超过阈值则拒绝请求。

### 解析

常见的限流算法及其优缺点

1. 计数器算法（固定窗口）：统计单位时间内的请求数量，超过阈值则拒绝请求。

- 优点：实现简单，易于理解。适用于简单的限流场景。
- 缺点：存在窗口边界问题，可能导致流量突增。无法平滑处理请求。
2. 滑动窗口算法：将时间窗口划分为多个小窗口，动态统计请求数量。

- 优点：比固定窗口更精确，能够平滑处理请求。解决了固定窗口的边界问题。
- 缺点：实现复杂度较高。需要维护更多的状态信息。
3. 漏桶算法（Leaky Bucket）：请求以固定速率被处理，超过桶容量的请求会被丢弃或排队。

- 优点：能够平滑处理请求，避免突发流量。实现相对简单。
- 缺点：无法应对突发流量的需求。请求处理速率固定，灵活性较差。
4. 令牌桶算法（Token Bucket）：系统以固定速率生成令牌，请求需要获取令牌才能被处理，没有令牌则拒绝请求。

- 优点：能够应对突发流量，允许短时间内处理更多请求。灵活性高，适用于多种场景。
- 缺点：实现复杂度较高。需要维护令牌生成和消耗的状态。
5. 分布式限流：在分布式系统中，使用 Redis 或其他分布式缓存来统一管理限流状态。

- 优点：适用于分布式环境，能够全局控制请求流量。支持高并发场景。
- 缺点：依赖外部存储，增加了系统复杂性。可能存在性能瓶颈。

总结

- 计数器算法：简单但不够精确，适合简单场景。
- 滑动窗口算法：更精确，适合需要平滑处理的场景。
- 漏桶算法：平滑处理请求，但灵活性较差。
- 令牌桶算法：灵活且支持突发流量，适合复杂场景。
- 分布式限流：适用于分布式系统，但实现复杂。

在实际开发中，可以根据具体需求选择合适的限流算法，或者结合多种算法来实现更精细的流量控制。

### 选项

### 答案

熔断（Circuit Breaker）是一种保护系统的设计模式，用于防止分布式系统中的故障扩散。

### 解析

熔断（Circuit Breaker）是一种保护系统的设计模式，用于防止分布式系统中的故障扩散。当某个服务或资源出现故障（如响应超时或异常）时，熔断机制会暂时停止对该服务的请求，直接返回错误或降级处理，避免系统资源被耗尽或雪崩效应。

熔断的核心思想是快速失败，即在检测到故障时立即停止请求，而不是持续重试，从而保护系统的稳定性。

服务熔断的解决方案

1. Resilience4j：

- 特点：轻量级，基于函数式编程。提供了熔断、限流、重试、降级等功能。
- 优点：模块化设计，易于扩展。支持 Java 8 及以上版本。
- 缺点：需要手动配置，学习曲线较高。
2. Sentinel（阿里巴巴开源）：

- 特点：专注于流量控制、熔断、降级和系统保护。支持实时监控和动态规则配置。
- 优点：功能强大，适用于高并发场景。与 Spring Cloud 和 Dubbo 集成良好。
- 缺点：配置和部署相对复杂。
3. Istio（服务网格）：

- 特点：在服务网格层实现熔断、重试、超时控制等功能。无需修改业务代码。
- 优点：对业务透明，适合微服务架构。支持多种语言和框架。
- 缺点：部署和维护成本较高。
4. 自定义熔断器：

- 特点：根据业务需求自行实现熔断逻辑。
- 优点：灵活，完全适配业务场景。
- 缺点：开发成本高，需要处理各种边界情况。

总结

熔断是分布式系统中保护服务稳定性的重要机制，常见的解决方案包括：

- Resilience4j：轻量级，适合现代 Java 应用。
- Sentinel：功能强大，适合高并发场景。
- Istio：服务网格层实现，对业务透明。
- 自定义熔断器：灵活但开发成本高。

## 29. 什么是分布式事务

分布式事务是指在分布式系统中，跨多个服务或数据库节点完成的一个事务操作。

### 解析

分布式事务是指在分布式系统中，跨多个服务或数据库节点完成的一个事务操作。它需要保证这些操作要么全部成功，要么全部失败，满足事务的 ACID 特性：

1. 原子性（Atomicity）：事务中的所有操作要么全部成功，要么全部回滚。
2. 一致性（Consistency）：事务执行前后，系统状态保持一致。
3. 隔离性（Isolation）：事务的执行不受其他事务干扰。
4. 持久性（Durability）：事务提交后，结果永久保存。

为什么需要分布式事务？

在分布式系统中，数据和服务可能分散在不同的节点上，传统的单机事务无法满足需求。例如：

1. 跨服务调用：订单服务调用库存服务扣减库存，需要保证两个操作的一致性。
2. 跨数据库操作：数据分库分表后，一个事务可能涉及多个数据库。
3. 微服务架构：每个服务有自己的数据库，需要协调多个服务的事务。

### 分布式事务的解决方案

1. 两阶段提交（2PC）：

- 通过协调者（Coordinator）和参与者（Participant）实现。
- 分为准备阶段和提交阶段，保证一致性，但性能较低。
2. 三阶段提交（3PC）：

- 在 2PC 的基础上增加预提交阶段，减少阻塞问题。
3. TCC（Try-Confirm-Cancel）：

- 通过业务逻辑实现，分为 Try（尝试）、Confirm（确认）、Cancel（取消）三个阶段。
- 适合对一致性要求高的场景。
4. 本地消息表：

- 通过消息队列和本地消息表保证最终一致性。
- 适合异步场景。
5. Saga：

- 将一个长事务拆分为多个本地事务，通过补偿机制保证最终一致性。
- 适合长事务场景。
6. Seata：

- 开源的分布式事务解决方案，支持 AT、TCC、Saga 等模式。

总结

分布式事务用于在分布式系统中保证跨服务或跨数据库操作的一致性。常见的解决方案包括 2PC、TCC、本地消息表、Saga 和 Seata 等，根据业务需求选择合适的方案。

### 解析

Raft是一种用于管理分布式系统中日志复制的共识算法，旨在简化理解和实现。以下是Raft算法的主要流程：

1. 角色划分：Raft将节点分为三种角色：

- Leader：负责处理客户端请求、管理和同步日志、定期发送心跳。
- Candidate：在选举新Leader时，Follower可以转变为Candidate并发起选举
- Follower：被动响应Leader日志同步请求和Candidate的邀票请求。

2. 任期（Term）：任期是一个整数，用于标识raft集群的一个时间段。每个任期从选举开始，可能有Leader，也可能没有。每个任期都有一个唯一的编号，用于识别过期的信息。

3. Leader选举

- 超时机制：Follower在超时时间内未收到Leader的心跳，会转变为Candidate并发起选举。
- 投票请求：Candidate向其他节点发送投票请求，若获得多数票，则成为Leader。
- 选举成功：新Leader开始发送心跳，阻止其他节点发起选举。

4. 日志复制

- 客户端请求：Leader接收客户端请求，将其作为新日志条目追加到本地日志。
- 日志广播：Leader将新日志条目发送给所有Follower。
- 日志提交：当多数节点复制了日志条目后，Leader将其提交并应用到状态机，然后通知Follower提交。

5. 安全性

- 选举限制：只有包含所有已提交日志的节点才能成为Leader。
- 日志一致性：Leader确保Follower的日志与自己的日志一致，强制覆盖不一致的日志。

6. 故障处理

- Leader故障：Follower超时后发起选举，选出新Leader。
- 网络分区：分区中的多数派节点可以继续选举和日志复制，少数派节点无法选举新Leader或提交日志。

7. 日志压缩

为防止日志无限增长，Raft使用快照机制压缩日志，删除已提交的旧日志。

8. 随机超时

Raft算法中的随机超时有以下两种情况：

1. Follower等待Leader心跳信息的超时间隔是随机的

这里的随机化的超时机制可以防止多个Follower同时转换为Candidate，减少选举冲突。

1. Candidate等待选举结果的超时间隔是随机的

当一个节点转换为Candidate并发起选举后，会等待其他节点的投票结果，这个等待时间是随机的。如果在这个等待的时间段内，没有获得大多数选票，将再次随机设置一个等待时间，发起新一轮投票。这里的随机化的超时机制降低了多个Candidate同时发起选举的可能性。

总的来说，在Raft算法中，随机超时机制是一个关键设计，保证在大多数情况下只有一个节点发起选举，避免多个Candidate选举带来的性能问题。

Raft通过Leader选举、日志复制和安全性机制，确保分布式系统中的数据一致性和高可用性。其设计简化了理解和实现，适用于多种分布式系统场景。

### 选项

### 答案

2PC（Two-Phase Commit，两阶段提交）是一种分布式事务协议，用于确保在分布式系统中，多个参与节点能够就事务的提交或回滚达成一致。

### 解析

2PC（Two-Phase Commit，两阶段提交）是一种分布式事务协议，用于确保在分布式系统中，多个参与节点能够就事务的提交或回滚达成一致。它通常用于数据库或分布式系统中，保证事务的原子性。

两阶段提交的过程

1. 第一阶段：准备阶段（Prepare Phase）

- 事务协调者（Coordinator）向所有参与者（Participants）发送“准备提交”请求。
- 每个参与者执行事务操作，并将结果（成功或失败）记录到本地日志中，但不会真正提交事务。
- 参与者向协调者返回“同意”或“中止”的响应。
2. 第二阶段：提交阶段（Commit Phase）

- 如果所有参与者都返回“同意”，协调者向所有参与者发送“提交”请求，参与者正式提交事务。
- 如果有任何一个参与者返回“中止”，或者协调者在等待响应时超时，协调者会向所有参与者发送“回滚”请求，参与者撤销事务。

优点

- 原子性保证：确保所有参与者要么全部提交，要么全部回滚。
- 简单易实现：协议逻辑清晰，适合对一致性要求较高的场景。

缺点

- 同步阻塞：在第二阶段，所有参与者必须等待协调者的指令，可能导致性能瓶颈。
- 单点故障：协调者一旦故障，整个系统可能无法继续运行。
- 数据不一致风险：如果协调者在发送“提交”请求后崩溃，部分参与者可能提交成功，而其他参与者未收到指令，导致数据不一致。

适用场景

2PC适合对一致性要求极高、但并发量不高的场景，例如金融系统、分布式数据库等。

改进方案

为了解决2PC的缺点，业界提出了许多改进方案，例如：

- 3PC（三阶段提交）：通过引入超时机制减少阻塞问题。
- 分布式事务框架：如Seata、TCC（Try-Confirm-Cancel）等，提供更灵活的事务管理。

## 36. TCC了解过吗

> 原题 ID：`q0968` ｜ 原分类：架构设计 ｜ 来源：飞书知识库·分布式面试题整理

### 题干

TCC了解过吗

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

TCC（Try-Confirm-Cancel）是一种分布式事务解决方案，用于保证跨服务或跨数据库的事务一致性。

### 解析

TCC（Try-Confirm-Cancel）是一种分布式事务解决方案，用于保证跨服务或跨数据库的事务一致性。它通过业务逻辑层面的补偿机制来实现事务的最终一致性，适用于高并发和复杂业务场景。以下是 TCC 的简要介绍：

### 1. TCC 的核心思想

TCC 将分布式事务分为三个阶段：

1. Try（尝试）：

- 预留资源，完成业务检查。
- 例如，冻结用户账户中的部分金额，而不是直接扣款。
2. Confirm（确认）：

- 提交事务，确认执行真正的业务操作。
- 例如，扣减冻结的金额，完成支付。
3. Cancel（取消）：

- 回滚事务，释放预留的资源。
- 例如，解冻用户账户中的金额。

### 2. TCC 的工作流程

- Try 阶段：所有参与者尝试执行操作，预留资源并返回执行结果。
- Confirm 阶段：如果所有参与者的 Try 阶段都成功，则进入 Confirm 阶段，提交事务。
- Cancel 阶段：如果任何一个参与者的 Try 阶段失败，则进入 Cancel 阶段，回滚事务。

### 3. TCC 的优点

- 高性能：Try 阶段只预留资源，不锁定资源，减少了锁冲突，适合高并发场景。
- 最终一致性：通过 Confirm 和 Cancel 机制，保证事务的最终一致性。
- 灵活性：业务逻辑由开发者控制，可以根据业务需求定制补偿机制。

### 4. TCC 的缺点

- 开发复杂度高：需要为每个服务实现 Try、Confirm、Cancel 三个接口，增加了开发工作量。
- 业务侵入性强：需要在业务逻辑中显式处理事务的提交和回滚。
- 补偿机制的设计难度：Cancel 操作需要正确处理资源回滚，避免脏数据。

### 5. TCC 的适用场景

- 高并发场景：如电商系统中的订单支付、库存扣减。
- 跨服务调用：如微服务架构下的分布式事务。
- 需要最终一致性的业务：如资金转账、积分兑换。

### 6. TCC 的实现框架

## 42. 美团leaf算法是怎么解决雪花算法的时钟漂移问题的

> 原题 ID：`q0974` ｜ 原分类：架构设计 ｜ 来源：飞书知识库·分布式面试题整理

### 题干

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

美团的雪花算法通过以下方式解决时钟回拨问题：
1. 时钟回拨检测：在生成ID前，系统会检查当前时间戳是否小于上一次生成ID的时间戳。如果检测到回拨，系统会暂停生成ID，直到时钟恢复正常。
2. 等待时钟恢复：当检测到时钟回拨时，系统会等待时

### 解析

美团Leaf在实现雪花算法时，针对原生雪花算法的时钟回拨问题\*\*进行了优化。时钟回拨是指系统时间由于NTP同步或人为调整，导致当前时间比上一次生成ID的时间还要早，这会导致生成的ID可能重复。Leaf通过以下几种方式解决时钟回拨问题：

1. 时钟回拨问题的原因

雪花算法的ID生成依赖于系统时间戳（41位），如果系统时间发生回拨，可能会导致生成的时间戳比之前的小，从而生成重复的ID。

2. Leaf的解决方案

2.1 时间戳缓存

Leaf在内存中缓存了最近一段时间（例如10秒）的时间戳。当检测到时钟回拨时，Leaf会使用缓存的时间戳继续生成ID，而不是直接使用回拨后的系统时间。

具体实现：

- 每次生成ID时，Leaf会记录当前时间戳，并将其缓存。
- 如果检测到时钟回拨，Leaf会从缓存中取出最近的时间戳，并在此基础上继续生成ID。
- 如果缓存的时间戳也用完了，Leaf会等待时钟追上，或者抛出异常。

优点：

- 避免了因时钟回拨导致的ID重复问题。
- 对性能影响较小，缓存的时间戳可以直接使用。

缺点：

- 缓存的时间戳有限，如果时钟回拨时间过长，仍然可能无法完全解决问题。

2.2 时钟回拨检测与等待

Leaf在生成ID时，会检测当前系统时间是否小于上一次生成ID的时间戳。如果检测到时钟回拨，Leaf会根据回拨的时间长度采取不同的策略：

- 小范围回拨：如果回拨时间在可接受范围内（例如几毫秒），Leaf会等待时钟追上，然后继续生成ID。
- 大范围回拨：如果回拨时间过长（例如几秒或几分钟），Leaf会抛出异常，通知开发者手动处理。

优点：

- 对小范围回拨有较好的容错性。
- 对大范围回拨提供了明确的异常处理机制。

缺点：

- 等待时钟追上可能会影响ID生成的性能。
- 需要开发者处理大范围回拨的异常情况。

2.3 动态调整序列号

在雪花算法中，序列号（12位）用于区分同一毫秒内生成的多个ID。Leaf在时钟回拨时，会动态调整序列号，确保生成的ID不会重复。

具体实现：

- 如果检测到时钟回拨，Leaf会在当前时间戳的基础上，增加一个偏移量（例如1毫秒），并重置序列号。

具体策略：先放宽 top-k 或降低相似度阈值重试一次；仍无果则尝试 BM25/关键词兜底召回；若都失败，可选『无检索直答』（需标注不确定）或『诚实拒答』。
工程上要记录兜底触发率作为召回质量告警；对高敏感场景（医疗/金融）优先『拒答+转人工』而非硬编。
关键是把『置信度』显式建模，而非把低质片段硬塞给模型。

**加分点**

把兜底率作为监控指标反向推动召回优化。
区分『可接受直答』与『必须拒答』场景。

**雷区**

不要让模型在零证据时『强行编』——这正是幻觉来源。

## 53. 重试、降级、fallback、错误向上传递分别怎么处理

> 原题 ID：`q1510` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·nowcoder/zhihu

### 题干

重试、降级、fallback、错误向上传递分别怎么处理

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

重试解决瞬时故障、降级保核心可用、fallback给兜底结果、错误向上传递保留上下文并明确责任边界，四者需按故障类型分层组合并防止重试风暴。

### 解析

一、概念与定位
1. 重试：针对瞬时性故障（网络抖动、限流、短暂超时），在调用方或框架层自动重发。关键参数：最大次数、退避策略（指数退避+抖动）、超时、幂等性、重试预算。
2. 降级：当依赖不可用或超时时，主动关闭非核心功能或切换到简化逻辑，保证核心链路可用。例如推荐服务挂了返回热门榜单，支付风控超时走人工审核。
3. fallback：为某次调用提供兜底返回值或备用实现，是降级的局部实现手段。例如缓存未命中查DB失败返回默认值/旧缓存。
4. 错误向上传递：当无法本地恢复时，把错误连同上下文（错误码、traceId、依赖名、已重试次数）抛给上层，由上层决定继续降级、重试还是终止。

二、分层处理模型（文字示意图）
请求入口
  -> 业务编排层：决定核心/非核心，设置降级开关与fallback
    -> 服务调用层：超时、重试、熔断、隔离
      -> 基础设施层：连接池、负载均衡、重试预算
错误向上传递路径：底层异常 -> 包装为领域异常 -> 编排层捕获 -> 按策略降级/fallback/继续上抛 -> 全局异常处理器转用户提示

三、处理原则
1. 重试只对幂等且瞬时故障使用；非幂等写操作需业务唯一键去重。
2. 重试要带退避和抖动，并设置全局重试预算，避免雪崩。
3. 降级要有开关、预案和监控，能自动触发也能人工干预。
4. fallback 要区分“可接受默认值”和“必须失败”，不能掩盖资损/一致性问题。
5. 错误向上传递要保留 cause 链和上下文，禁止吞异常；上层根据错误类型决策。

四、典型组合
- 读接口：重试2次 -> 仍失败读缓存 -> 缓存无则fallback默认值 -> 记录降级指标。
- 写接口：不自动重试或仅按唯一键重试 -> 失败则落本地消息/事务表 -> 异步补偿 -> 仍失败上抛并告警。
- 核心支付：依赖超时 -> 熔断 -> 降级为排队/异步确认 -> 错误上抛给业务做最终一致性处理。

**加分点**

1. 源码级：Resilience4j 的 Retry 与 CircuitBreaker 组合顺序会影响语义，通常 Retry 在外、CircuitBreaker 在内，否则熔断打开后重试会直接失败；Spring Retry 的 @Backoff 支持 jitter。
2. 论文/模式：AWS  Exponential Backoff and Jitter 指出无抖动重试会同步放大流量；Google SRE 的“重试预算”和“级联失败”章节强调重试必须限流。
3. 踩坑：重试未设超时导致线程池耗尽；重试放大写请求造成重复扣款；降级返回空集合被上层当成“无数据”导致业务误判；错误上抛时丢失 cause 导致排查困难；fallback 缓存旧数据未设过期导致脏读。
4. 可观测：为每次重试、降级、fallback 打点，区分业务失败与系统失败，设置降级率、重试率、熔断状态告警。

**雷区**

1. 所有异常都重试，包括参数错误、权限错误、非幂等写。
2. 重试次数过多且无退避，造成重试风暴和雪崩。
3. 把降级和 fallback 混为一谈：降级是策略，fallback 是具体兜底实现。
4. 无脑吞异常或全部上抛：吞掉导致故障被掩盖，全部上抛导致用户看到底层错误且无法降级。
5. 降级没有开关和监控，故障恢复后无法自动恢复。
6. 忽略幂等和一致性，fallback 返回默认值造成资损或数据不一致。

### 难度

## 54. 热题精讲：字节/阿里面试真题-如何设计AI Agent的负载均衡

> 原题 ID：`q1735` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

热题精讲：字节/阿里面试真题-如何设计AI Agent的负载均衡

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

AI Agent 负载均衡不是简单的请求分发，而是围绕有状态会话、长时任务、异构算力与成本约束做路由与调度，核心是会话亲和 + 能力/负载感知 + 弹性扩缩 + 故障转移。

### 解析

一、先明确 AI Agent 与普通微服务的差异
1) 请求长且流式：一次 Agent 调用可能几十秒到几分钟，含多轮 LLM 调用、工具调用、RAG 检索，连接是 SSE/WebSocket 长连接。
2) 有状态：会话历史、中间推理状态、工具执行上下文、沙箱文件系统，不能随意漂移。
3) 异构资源：CPU 工具节点、GPU 推理节点、外部 API（搜索/代码执行）、向量库，瓶颈各不相同。
4) 成本与配额：token 成本、GPU 显存、第三方 API 限流，需要按成本/配额路由。
5) 任务可中断可恢复：需要 checkpoint 与重放。

二、整体架构（文字示意图）
Client -> API Gateway(鉴权/限流/协议转换) -> Agent Router(负载均衡核心) -> Agent Worker Pool(无状态编排层) -> 下游：LLM 推理集群 / 工具执行沙箱 / RAG 检索 / 记忆存储
                                                        |-> Session Store(Redis/DB)：会话与 checkpoint
                                                        |-> Scheduler/Controller：扩缩容、健康检查、指标

三、模块划分
1) 接入层：鉴权、租户配额、请求排队、协议适配（HTTP/SSE/WS/gRPC）。
2) 路由层（LB 核心）：
   - 两级路由：先按 session_id 做一致性哈希定位到 Agent Worker（会话亲和），再在 Worker 内部按能力/负载选择 LLM 实例或工具节点。
   - 路由策略：加权轮询、最少连接、最少未完成 token、P2C（Power of Two Choices）、一致性哈希 + 虚拟节点、按模型/工具能力的标签路由。
   - 长任务用「粘性 + 迁移」：优先粘住，Worker 故障时从 Session Store 恢复 checkpoint 到新 Worker。
3) 执行层：Agent Worker 无状态化编排，状态外置到 Session Store；工具调用走独立沙箱池，避免拖垮主进程。
4) 资源层：LLM 推理集群（vLLM/TGI，按 GPU 显存与 KV Cache 做调度）、工具沙箱、向量库。
5) 控制面：指标采集（QPS、P99、队列深度、GPU 利用率、token/s）、HPA/KEDA 扩缩、熔断降级、灰度。

四、数据流
请求进入 -> 鉴权/配额 -> 解析 session_id 与所需能力标签 -> 路由层选 Worker（一致性哈希 + 负载修正）-> Worker 从 Session Store 加载上下文 -> 循环：LLM 推理 -> 工具调用 -> 更新 checkpoint -> 流式返回 -> 结束落库。

五、关键取舍
1) 会话亲和 vs 负载均衡：强亲和简单但易热点；解法是一致性哈希 + 虚拟节点 + 过载时允许迁移（带 checkpoint）。
2) 长连接 vs 无状态：长连接省重连成本但占资源；可用「连接与执行分离」，网关维持连接，Worker 可迁移。
3) 延迟 vs 成本：优先本地/小模型，复杂任务升级到大模型；按 token 预算路由。
4) 一致性 vs 可用性：会话状态用最终一致 + 幂等重放，避免强一致拖慢。
5) 集中调度 vs 去中心：集中式易做全局最优但有单点；去中心 P2C 更健壮。

六、扩展性
- 水平扩展 Worker，会话哈希环扩容时用虚拟节点减少迁移。
- 多租户隔离：按租户分池 + 配额，防止 noisy neighbor。
- 多地域：就近接入 + 会话地域亲和，跨域仅做故障转移。
- 可观测：trace 贯穿 LLM/工具调用，便于定位慢环节。

**加分点**

1) 提到 vLLM 的 PagedAttention/Continuous Batching 对 KV Cache 的管理，LB 需感知显存与 KV 占用而非只看 QPS。2) 用 P2C（Power of Two Choices）在去中心场景近似最优，避免全局调度单点。3) 会话迁移用 checkpoint + 幂等重放，工具调用需幂等键防重复执行副作用。4) 一致性哈希虚拟节点解决扩容雪崩，配合「有界负载」策略（如 Google 的 Maglev/有界一致性哈希）。5) 区分「路由」与「调度」：路由选节点，调度决定排队与抢占，长任务需优先级队列与公平调度。6) 成本路由：按 token 单价与租户预算做加权，结合缓存（Prompt Cache/语义缓存）降低重复推理。

**雷区**

1) 只答 Nginx 轮询/最少连接，忽略 Agent 有状态与长连接特性。2) 认为 Worker 必须无状态就完全不做会话亲和，导致每步都重载上下文、成本爆炸。3) 忽略工具调用的副作用与幂等，故障重试导致重复下单/重复发邮件。4) 把 LLM 推理节点当普通服务，忽略 GPU 显存、KV Cache、批处理对负载的影响。5) 只谈扩缩容不谈故障转移与 checkpoint 恢复。6) 忽略多租户 noisy neighbor 与配额，导致大租户拖垮全局。

## 55. 模型工程化实践：多模型路由、优先级调度、首包探测、熔断降级，解决的是模型不稳定怎么办这个生产环境的真实问题

> 原题 ID：`q2205` ｜ 原分类：后端八股（Go） ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

模型工程化实践：多模型路由、优先级调度、首包探测、熔断降级，解决的是模型不稳定怎么办这个生产环境的真实问题

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

核心是把模型调用当成不可靠的远程依赖，用路由+优先级队列+首包探测+熔断降级四层机制，在延迟、成本、稳定性之间做动态权衡。

### 解析

生产环境调用大模型（LLM）API 或自建推理服务时，常见问题：某模型超时/限流/返回质量下降、不同请求对延迟和成本敏感度不同、单点故障导致整条链路雪崩。工程上通常分四层解决：

1) 多模型路由：维护模型注册表（模型名、endpoint、权重、成本、能力标签、健康状态），按请求特征（任务类型、token 长度、SLA、租户等级）选择模型。策略包括加权轮询、最少连接、基于延迟的 P2C（Power of Two Choices）、以及按成本/质量打分的路由。Go 里可用 sync.Map 或 atomic.Value 存路由表，配合 RWMutex 做热更新，避免每次请求加锁。

2) 优先级调度：用带优先级的队列（container/heap 实现最小堆）区分 P0/P1/P2 请求，P0 走独立并发池，防止低优请求占满连接导致高优饿死。关键点是并发信号量按优先级分配，例如 P0 保留 30% 配额，并配合抢占/超时丢弃。

3) 首包探测（TTFT 探测）：流式接口下，先并发向多个候选模型发请求，谁先返回首个 token 就用谁，其余取消（context.WithCancel）。这能显著降低 P99 首包延迟，但要注意取消后仍可能产生计费，需设置探测预算和最大并发探测数。

4) 熔断降级：用滑动窗口统计错误率/超时率，达到阈值打开熔断（如 5s 内错误率>50% 且请求数>20），半开状态放少量探针恢复。降级策略：切备用模型、降级到小模型、返回缓存/模板答案、或直接快速失败。Go 可用 sony/gobreaker 或自研，注意熔断粒度要按模型+租户维度，避免全局熔断误伤。

代码示例（简化熔断+路由）：
```go
type Breaker struct {
    mu       sync.Mutex
    state    int32 // 0 closed,1 open,2 half-open
    failures int
    total    int
    openUntil time.Time
}
func (b *Breaker) Allow() bool {
    b.mu.Lock(); defer b.mu.Unlock()
    if b.state == 1 && time.Now().Before(b.openUntil) { return false }
    if b.state == 1 { b.state = 2 }
    return true
}
func (b *Breaker) Report(err error) {
    b.mu.Lock(); defer b.mu.Unlock()
    b.total++
    if err != nil { b.failures++ }
    if b.total >= 20 && float64(b.failures)/float64(b.total) > 0.5 {
        b.state = 1; b.openUntil = time.Now().Add(5*time.Second)
        b.failures, b.total = 0, 0
    }
}
```
路由选择用 atomic.Value 存 []Model，读多写少无锁；首包探测用 errgroup + context 控制并发。

**加分点**

1) 首包探测要区分“探测请求”和“正式请求”，探测请求应带 max_tokens=1 或专用轻量 prompt，否则成本爆炸；同时用 context 取消后要 drain response body，避免连接泄漏。
2) 熔断阈值不能只看错误率，要结合 P99 延迟和 token 吞吐，因为 LLM 常见“慢但成功”，纯错误率会漏判。可参考 Netflix Hystrix 的滑动窗口和 Google SRE 的 adaptive throttling。
3) 路由表热更新用 atomic.Value 存不可变快照，写时复制，读路径零锁，这是 Go 高并发服务的经典模式（类似 go-kit/etcd 的做法）。
4) 优先级调度要防饥饿，可用 aging：等待越久优先级越高，或给低优请求设置最大排队时间后直接降级。
5) 降级要有兜底语义：返回缓存答案时要标记 stale，避免用户误以为是最新结果；同时记录降级指标用于容量规划。

**雷区**

1) 把熔断做成全局单例，一个模型挂了导致所有模型调用被熔断，正确做法是按模型/租户/接口维度隔离。
2) 首包探测无脑并发所有模型，忽略成本和限流，导致探测本身把配额打满，反而加剧不稳定。
3) 用 time.Sleep 或固定重试代替熔断，重试风暴会放大故障（retry storm），必须配合退避+抖动+熔断。
4) 认为路由只是负载均衡，忽略模型能力差异（长上下文、函数调用、多模态），导致路由到不支持该能力的模型。
5) 降级只做“返回错误”，没有缓存/小模型/模板兜底，用户体验直接崩。
6) 忽略 context 取消的传播，goroutine 泄漏，P99 延迟被拖垮。

### 难度

★★☆

`后端八股（Go）` `juejin`

> 原题 ID：`q2521` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

AI可以给你微服务的概念，但无法帮你权衡CAP理论、设计出符合你业务需求的分布式事务方案

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

微服务架构中CAP与分布式事务没有通用最优解，必须结合业务一致性、可用性与扩展性做显式取舍，AI只能给概念不能替你做业务权衡。

### 解析

微服务拆分本质是把单体事务拆成跨进程/跨库操作，于是CAP与分布式事务成为架构核心矛盾。

一、模块划分
1) 业务域服务：订单、库存、支付、账户，各自独立库，禁止跨库JOIN。
2) 事务协调层：Saga/TCC/本地消息表/事务消息，负责补偿、重试、幂等。
3) 基础设施层：注册中心、配置中心、网关、消息队列、分布式锁、幂等表、对账系统。
4) 可观测层：链路追踪、事务状态机看板、补偿告警。

文字示意图：
Client -> Gateway -> OrderService --(本地事务+Outbox)--> MQ --> InventoryService
                              |                              |
                              v                              v
                         OrderDB                     InventoryDB
                              \________ Saga协调器/对账 ________/

二、数据流与方案取舍
1) 强一致优先：2PC/Seata AT，适合金融核心账务，但阻塞、性能差、协调者单点。
2) 可用性优先：Saga/TCC，最终一致，适合电商下单，需补偿与幂等。
3) 消息最终一致：本地消息表/事务消息/RocketMQ事务消息，适合异步解耦，需处理重复消费与消息丢失。
4) 业务妥协：允许少卖不允许超卖，用预扣库存+超时释放；或允许短暂不一致，用T+1对账兜底。

三、CAP权衡
分布式系统P必须保，C与A二选一。支付扣款选CP，商品浏览选AP。同一系统内不同链路可不同：下单核心链路CP，推荐/评论AP。

四、扩展性
事务方案要可插拔：接口化TransactionCoordinator，按业务注解选择Saga/TCC/消息；补偿动作幂等、可重试、可人工介入；状态机持久化，支持断点续跑。

**加分点**

1) 能说出Seata AT基于全局锁+undo_log，TCC需空回滚/悬挂/幂等三问题；2) 提到Outbox模式与CDC(Debezium)保证本地事务与消息原子性；3) 知道RocketMQ事务消息半消息+回查机制；4) 用状态机+对账系统做最终兜底，而非只依赖MQ；5) 能画Saga正向/补偿时序并说明补偿失败转人工；6) 引用CAP/PACELC或论文如Saga(1987)、TCC、本地消息表。

**雷区**

1) 认为微服务必须强一致，直接上2PC导致性能雪崩；2) 把CAP理解成三选二，忽略P必选；3) 以为MQ能保证不丢不重，忽略幂等与本地消息表；4) 只谈技术方案不谈业务一致性等级与对账兜底；5) 忽略补偿失败、悬挂、空回滚等边界；6) 认为AI给的方案可直接落地，不做业务权衡。

## 57. 你们这个预览是用微服务的方式吗？微前端？

> 原题 ID：`q2787` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·juejin

### 题干

你们这个预览是用微服务的方式吗？微前端？

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

预览功能通常不是微服务，而是前端侧的微前端/组件化方案；后端只提供渲染或数据接口，核心取舍在于隔离性、性能与部署复杂度。

### 解析

先澄清概念：微服务是后端按业务能力拆分的独立部署单元（如用户服务、订单服务），微前端是前端按业务域拆分的独立开发/部署单元（如 qiankun、Module Federation）。预览功能一般属于前端展示层，所以问‘预览是微服务吗’本身是概念错位。

典型架构（文字示意图）：
[浏览器] -> [主应用/壳] -> 加载 [预览微前端子应用]
                              |
                              v
                    [预览渲染服务/接口] -> [文件存储/对象存储]

如果预览是纯前端渲染（如 PDF.js、Office Online、图片/视频标签），则不需要微服务，只需一个静态资源或 CDN。若预览需要服务端转换（如 docx->pdf、视频转码、缩略图生成），则后端会拆出一个独立的‘预览/转换服务’，这可以算微服务，但它只负责计算，不负责前端模块划分。

微前端方案选择：
1) iframe：隔离最好，但通信、路由、弹窗、性能差；
2) qiankun/single-spa：JS 沙箱 + 样式隔离，适合多团队；
3) Module Federation：运行时共享依赖，构建耦合低，适合同技术栈；
4) Web Components：标准隔离，但生态和路由支持弱。

取舍：预览若只是只读展示，优先用 iframe 或独立路由，避免引入微前端复杂度；若预览需要嵌入主应用、共享登录态、动态换肤，则用 qiankun/Module Federation。后端预览服务要无状态、可水平扩展，转换任务用队列（如 RabbitMQ/Kafka）削峰，结果缓存到对象存储，避免重复转换。

**加分点**

1) 能指出‘微服务’和‘微前端’是不同维度的拆分，面试官问法本身有陷阱；2) 提到预览服务用无状态 + 队列 + 缓存，转换结果按文件 hash 去重；3) 提到 qiankun 的 JS 沙箱在 Proxy 不可用时降级 snapshot 沙箱，以及样式隔离的坑；4) 提到 Module Federation 的 shared 依赖版本冲突和运行时加载失败降级；5) 提到 iframe 的 postMessage 通信和同源策略限制；6) 提到预览大文件用分片/流式加载，避免一次性拉取。

**雷区**

1) 把微服务和微前端混为一谈，直接回答‘是微服务’；2) 认为预览必须上微前端，忽略 iframe/独立路由等更轻方案；3) 忽略预览服务的无状态和缓存，导致重复转换、资源浪费；4) 只谈技术栈不谈取舍，比如 qiankun 的沙箱性能损耗、Module Federation 的版本管理成本；5) 忽略安全，如预览用户上传文件时的 XSS、SSRF、恶意文件解析漏洞。

## 58. 分布式锁的落地经验是怎么实现的

> 原题 ID：`q3543` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·nowcoder

### 题干

分布式锁的落地经验是怎么实现的

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

分布式锁落地核心是选型（Redis/etcd/ZooKeeper）+ 正确加解锁（原子性、唯一值、超时续期）+ 业务幂等兜底，并明确锁的粒度、等待策略与降级方案。

### 解析

一、整体架构与数据流
客户端 -> 锁服务(Redis/etcd/ZK) -> 业务执行 -> 释放锁。文字示意：
[业务请求] -> [LockManager: tryLock(key, ttl, token)] -> [Redis SET key token NX PX ttl] -> 成功则执行临界区 -> [Lua: if get(key)==token then del(key)] -> 失败则按策略重试/快速失败。

二、模块划分
1) 锁客户端 SDK：封装加锁、解锁、续期、重试、超时、可重入、锁标识(token)。
2) 锁存储层：Redis（性能高、AP）、etcd/ZooKeeper（强一致、CP，基于租约/临时顺序节点）。
3) 业务层：临界区尽量短，必须做幂等，锁只是降低并发不是唯一正确性保障。
4) 监控告警：锁等待时长、获取失败率、持有时长、续期失败、死锁检测。

三、Redis 实现要点
加锁：SET lock_key unique_token NX PX 30000，必须原子，不能用 setnx+expire 两步。
解锁：Lua 脚本比较 token 再删除，防止误删他人锁。
续期：后台 watchdog 定时（如 TTL/3）续期，业务结束停止；进程崩溃则 TTL 自动释放。
重试：自旋+退避，或 pub/sub 通知减少空轮询。
可重入：Hash 存 token->count，Lua 增减。

四、etcd/ZooKeeper 实现要点
etcd：Lease + Revision，事务 compare revision 创建，Watch 前一个 key 实现公平排队，天然避免惊群。
ZK：临时顺序节点，最小序号获锁，前序节点 Watch，会话断开自动释放。

五、取舍与扩展性
性能 vs 一致性：Redis 快但主从切换可能丢锁，RedLock 有争议；etcd/ZK 一致但吞吐低、延迟高。
锁粒度：粗锁简单但并发低，细锁并发高但复杂度高，按业务 key 分片。
等待策略：快速失败适合用户请求，排队适合后台任务。
降级：锁服务不可用时，可降级为本地锁+幂等，或直接拒绝非核心流量。
扩展：锁 key 分片到多 Redis 实例；用 Redisson 等成熟库减少自研坑。

六、落地经验
1) 锁必须带唯一 token，解锁校验 token。
2) TTL 要大于业务 P99，配合续期，避免业务未完成锁过期。
3) 临界区尽量短，避免网络调用。
4) 业务侧幂等/唯一索引兜底，防止锁失效导致重复。
5) 监控锁等待和持有时间，设置告警。
6) 避免锁嵌套和死锁，统一加锁顺序。

**加分点**

1) 源码级：Redisson 的 watchdog 默认 lockWatchdogTimeout=30s，每 10s 续期；解锁用 Lua 保证原子。2) 论文/理论：Martin Kleppmann 对 RedLock 的质疑与 antirez 的回应，说明 Redis 锁在时钟漂移、GC 停顿下可能失效，不能作为强一致正确性保证。3) etcd 用 Revision 和 Watch 实现公平锁，避免惊群；ZK 临时顺序节点会话断开自动释放。4) 踩坑：主从异步复制下主宕机锁丢失；业务 GC 停顿超过 TTL 导致锁过期；解锁误删他人锁；锁续期线程与业务线程生命周期不一致。5) 可观测：用 P99 持有时长反推 TTL，用失败率决定重试策略。

**雷区**

1) 用 setnx+expire 两步，非原子，可能死锁。2) 解锁直接 del，不校验 token，误删他人锁。3) 认为有了分布式锁就万事大吉，不做幂等，锁失效时数据错乱。4) TTL 设置过短且不续期，业务未完成锁就释放。5) 盲目使用 RedLock 并认为绝对安全。6) 锁粒度过粗导致性能瓶颈，或锁嵌套导致死锁。7) 忽略锁服务不可用时的降级方案。

## 59. 限流、熔断、降级分别解决什么问题

> 原题 ID：`q3571` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·xiaohongshu

### 题干

限流、熔断、降级分别解决什么问题

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

限流控入口流量、熔断防级联故障、降级保核心可用，三者是稳定性治理的不同层次手段。

### 解析

三者都属于服务稳定性治理，但解决的问题和触发时机不同。

1. 限流（Rate Limiting）：解决“流量超过系统处理能力”的问题。核心是保护系统不被突发流量打垮，在入口或调用方做流量整形。常见算法：计数器、滑动窗口、漏桶、令牌桶。例如网关对某 API 限制 1000 QPS，超过直接返回 429。

2. 熔断（Circuit Breaking）：解决“下游依赖故障导致调用方被拖死”的问题。当对某个下游的失败率/慢调用比例超过阈值，熔断器从 Closed 变 Open，后续请求快速失败，不再真正调用下游；经过冷却时间进入 Half-Open 试探，成功则恢复 Closed。典型如 Hystrix、Sentinel、Resilience4j。

3. 降级（Fallback/Degradation）：解决“依赖不可用时如何保住核心业务”的问题。当熔断、限流或超时发生后，返回兜底数据、默认值、缓存旧数据，或关闭非核心功能。例如推荐服务挂了返回热门榜单，支付失败返回“稍后重试”。

文字示意图：
请求 -> [限流] -> 业务逻辑 -> [熔断器] -> 下游服务
                         | 失败/超时
                         v
                      [降级兜底]

取舍：限流偏预防，熔断偏止损，降级偏兜底；限流阈值太严会误杀正常流量，熔断阈值太敏感会频繁抖动，降级策略要区分核心与非核心。扩展性上，三者通常做成可配置规则 + 动态下发，如 Sentinel 的规则中心和集群限流。

【同源补充】来自同源题「熔断、降级、限流的区别？」
限流控入口、熔断防雪崩、降级保核心、稳定性、配合
限流：控制入口流量防压垮；熔断：依赖故障率超阈值时快速失败（开路），避免雪崩，半开探测恢复；降级：系统压力大时关闭非核心功能（返回默认/缓存）保核心。三者配合保护系统稳定性。

**加分点**

1. 熔断器状态机：Closed/Open/Half-Open，滑动窗口统计失败率、慢调用比例、最小请求数。2. 限流算法对比：令牌桶允许突发，漏桶恒定速率，滑动窗口比固定窗口更平滑。3. 降级要区分“读降级”和“写降级”，写降级更危险，可能丢数据。4. 可结合 Sentinel 的 Slot 责任链、Hystrix 的线程池隔离/信号量隔离讲源码。5. 集群限流 vs 单机限流，单机限流在扩容后总阈值会漂移。

**雷区**

1. 把三者混为一谈，认为限流就是降级。2. 只讲概念不讲触发条件和恢复机制，比如熔断没有 Half-Open。3. 忽略降级的数据一致性风险，写操作降级可能造成脏数据。4. 认为熔断后请求一定成功，实际是快速失败。5. 限流只讲单机，忽略分布式场景下需要 Redis/集群限流。6. 把熔断和超时混同，超时是熔断的触发条件之一，不是熔断本身。

## 60. 分布式 CAP 定理，三者为什么不可兼得

> 原题 ID：`q3748` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·zhihu

### 题干

分布式 CAP 定理，三者为什么不可兼得

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

CAP 指一致性、可用性、分区容错性，在分布式系统中网络分区不可避免，因此只能在 C 与 A 之间取舍，无法三者同时满足。

### 解析

CAP 定理由 Eric Brewer 提出，Gillbert 与 Lynch 后来形式化证明。C（Consistency）指线性一致性：所有节点在同一时刻看到同一份数据，读总能读到最近一次成功写；A（Availability）指每个非故障节点在有限时间内对每个请求都返回非错误响应；P（Partition tolerance）指系统在网络分区（节点间消息丢失/延迟）时仍能继续运行。

关键点：分布式系统跨网络部署，网络分区是客观事实，所以 P 通常必须保留。当分区发生时，若两个副本无法通信，客户端同时向两侧写入：
- 选 C：为保证读到的数据一致，必须拒绝部分请求或阻塞等待，牺牲 A；
- 选 A：两侧都接受写入并返回，则可能出现数据分叉，牺牲 C。

文字示意图：
       分区前：Client -> N1 <-> N2
       分区后：ClientA -> N1   |X|   N2 <- ClientB
       CP 选择：N1 拒绝写/读，保证不会返回旧值
       AP 选择：N1、N2 都返回，后续需冲突解决

常见系统取舍：
- CP：ZooKeeper、etcd、HBase、MongoDB（多数派写）、Redis Cluster（部分场景）
- AP：Cassandra、DynamoDB、Eureka、Riak
- CA：单机数据库或理想无分区网络，分布式下不现实

扩展：BASE（Basically Available, Soft state, Eventually consistent）是 AP 的工程化延伸；PACELC 进一步指出：即使没有分区（E），也要在延迟（L）和一致性（C）之间取舍。

**加分点**

1. 能区分 CAP 中的 C 是线性一致性，而非 ACID 的 C（事务一致性）或最终一致性。2. 能指出 P 不是可选项：只要跨网络，分区迟早发生，所以实际是 CP/AP 二选一。3. 能提到 Gilbert-Lynch 证明模型：异步网络、节点可能失效、消息可丢失。4. 能结合 PACELC：分区时选 A/C，正常时选 L/C，例如 DynamoDB 默认最终一致换低延迟，强一致读需额外成本。5. 能说明多数派 quorum：R+W>N 可保证强一致，但分区时少数派不可用，体现 C/A 取舍。6. 能举真实踩坑：Eureka AP 导致读到旧注册信息；ZooKeeper 分区时少数派不可写，影响可用性。

**雷区**

1. 把 CAP 的 C 当成 ACID 的 C，或与最终一致性混为一谈。2. 认为可以同时满足 CAP 三者，或认为 P 可以放弃。3. 把 CA 当成分布式系统可选项，忽略网络分区必然性。4. 认为选 AP 就完全不要一致性，实际是最终一致/冲突解决。5. 只背结论，不能解释分区时读写冲突导致 C 与 A 互斥的机制。6. 把 CAP 套用到单机系统或所有分布式场景，忽略 PACELC 的补充。

★★☆

## 61. 如果同时有大量 Agent 任务调用大模型，如何做并发控制和限流

> 原题 ID：`q3953` ｜ 原分类：架构设计 ｜ 来源：全平台面经采集(2026-09)·weixin

### 题干

如果同时有大量 Agent 任务调用大模型，如何做并发控制和限流

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

用分层限流（网关/服务/模型供应商/租户）+ 令牌桶与并发信号量控制瞬时并发，配合优先级队列、背压、重试退避和熔断，保证系统稳定与公平。

### 解析

整体架构分四层：接入层、调度层、执行层、模型接入层。

文字示意图：
Client/Agent -> API网关(鉴权/租户配额/全局限流) -> 任务队列(Kafka/Redis Stream, 按优先级/租户分区) -> 调度器(并发信号量+令牌桶, 动态调整) -> Worker池(异步调用LLM) -> 模型接入层(供应商级限流/熔断/降级) -> LLM API

1) 限流维度：全局QPS/TPM、租户级、任务类型级、模型/供应商级。QPS用令牌桶或滑动窗口（Redis+Lua保证原子），TPM按token预估或实际用量计费。
2) 并发控制：用信号量（如asyncio.Semaphore、Redis分布式信号量）限制同时在飞的请求数，避免连接池/线程池打满；每个供应商单独设并发上限。
3) 队列与背压：请求先入队，队列长度超阈值直接拒绝或降级（返回缓存/小模型），Worker按容量拉取，天然背压。
4) 优先级与公平：多级队列（高/中/低），加权轮询或DRR保证租户公平，防止大租户饿死小租户。
5) 失败处理：指数退避+抖动重试，区分可重试（429/5xx）与不可重试（400）；熔断器在供应商错误率高时快速失败并切备用模型。
6) 动态扩缩：根据队列深度和延迟自动扩Worker；令牌桶速率可热更新。
7) 可观测：埋点QPS、并发数、排队时长、P99延迟、429率，用于调参。

取舍：严格限流保稳定但可能拒绝请求；宽松限流体验好但易雪崩。通常核心业务保底配额+弹性借用。

**加分点**

1) 令牌桶用Redis+Lua实现原子性，避免竞态；滑动窗口用ZSET或Redis Cell。2) 分布式信号量可用Redis的INCR+过期或Redlock，注意锁续期。3) 参考OpenAI的rate limit header（x-ratelimit-remaining）做自适应退避；Google SRE的Handling Overload（客户端重试预算、抖动）。4) 用Little's Law：并发=QPS×平均延迟，据此估算信号量大小。5) 队列用Kafka分区保证同租户顺序，或Redis Stream消费者组。6) 熔断用Resilience4j/Sentinel，半开状态探测。7) 对LLM可做请求合并（batch）和流式输出降低并发占用。

**雷区**

1) 只做单机限流，忽略分布式下多实例总量超限。2) 只限QPS不限并发，长请求仍会打满连接池。3) 重试不加退避和抖动，造成重试风暴。4) 队列无上限导致内存溢出，或直接同步调用无背压。5) 忽略租户公平，大租户占满配额。6) 把限流和熔断混为一谈，熔断是故障隔离，限流是流量控制。7) 未区分token限流，LLM按token计费，仅QPS不够。

## 71. 基于 Redis 实现分布式锁有什么优缺点

> 原题 ID：`q0440` ｜ 原分类：后端八股 ｜ 来源：飞书知识库·Redis面试题整理

### 题干

基于 Redis 实现分布式锁有什么优缺点

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

基于 Redis 实现分布式锁的优点：

- 性能高效（这是选择缓存实现分布式锁最核心的出发点）。

### 解析

基于 Redis 实现分布式锁的优点：

- 性能高效（这是选择缓存实现分布式锁最核心的出发点）。
- 实现方便。很多研发工程师选择使用 Redis 来实现分布式锁，很大成分上是因为 Redis 提供了 setnx 方法，实现分布式锁很方便。
- 避免单点故障（因为 Redis 是跨集群部署的，自然就避免了单点故障）。

基于 Redis 实现分布式锁的缺点：

- 超时时间不好设置：如果锁的超时时间设置过长，会影响性能，如果设置的超时时间过短会保护不到共享资源。比如在有些场景中，一个线程 A 获取到了锁之后，由于业务代码执行时间可能比较长，导致超过了锁的超时时间，自动失效，注意 A 线程没执行完，后续线程 B 又意外的持有了锁，意味着可以操作共享资源，那么两个线程之间的共享资源就没办法进行保护了。

- 那么如何合理设置超时时间呢？我们可以基于续约的方式设置超时时间：先给锁设置一个超时时间，然后启动一个守护线程，让守护线程在一段时间后，重新设置这个锁的超时时间。实现方式就是：写一个守护线程，然后去判断锁的情况，当锁快失效的时候，再次进行续约加锁，当主线程执行完成后，销毁续约锁即可，不过这种方式实现起来相对复杂。
- Redis 主从复制模式中的数据是异步复制的，这样导致分布式锁的不可靠性：如果在 Redis 主节点获取到锁后，在没有同步到其他节点时，Redis 主节点宕机了，此时新的 Redis 主节点依然可以获取锁，所以多个应用服务就可以同时获取到锁。

**雷区**

- 避免单点故障（因为 Redis 是跨集群部署的，自然就避免了单点故障）。

## 72. 什么是降级？降级和熔断的区别是什么

> 原题 ID：`q0960` ｜ 原分类：架构设计 ｜ 来源：飞书知识库·分布式面试题整理

### 题干

什么是降级？降级和熔断的区别是什么

### 选项

（本题为问答题，原始题库无选项字段）

### 答案

什么是降级？

降级（Degradation）是一种系统保护机制，当系统资源不足或某些服务不可用时，通过暂时关闭或简化非核心功能，确保核心功能能够正常运行。

### 解析

什么是降级？

降级（Degradation）是一种系统保护机制，当系统资源不足或某些服务不可用时，通过暂时关闭或简化非核心功能，确保核心功能能够正常运行。降级的目的是在系统压力过大或故障时，优先保证关键业务的可用性，而不是让整个系统崩溃。

降级的常见方式包括：

1. 返回默认值：例如，商品详情页的推荐服务不可用时，返回空列表或默认推荐。
2. 简化逻辑：例如，跳过复杂的计算或查询，直接返回简化结果。
3. 关闭非核心功能：例如，在系统高负载时关闭评论功能。

降级和熔断的区别

| 特性 | 降级 | 熔断 |
|-|-|-|
| 目的 | 保证核心功能可用，牺牲非核心功能。 | 防止故障扩散，快速失败，保护系统稳定性。 |
| 触发条件 | 系统资源不足、高负载或部分服务不可用。 | 某个服务连续失败或超时。 |
| 实现方式 | 返回默认值、简化逻辑或关闭非核心功能。 | 直接拒绝请求，不再调用故障服务。 |
| 作用范围 | 通常是业务层面的功能降级。 | 通常是服务调用层面的保护机制。 |
| 恢复方式 | 系统负载降低或服务恢复后，自动或手动恢复。 | 熔断器检测到服务恢复后，逐步尝试恢复调用。 |

总结

- 降级：通过牺牲非核心功能，确保核心功能可用，适用于高负载或部分服务不可用的场景。
- 熔断：通过快速失败，防止故障扩散，适用于某个服务连续失败或超时的场景。

两者都是保护系统稳定性的重要手段，通常结合使用，以应对复杂的分布式系统环境。

**加分点**

- 降级：通过牺牲非核心功能，确保核心功能可用，适用于高负载或部分服务不可用的场景。
- 熔断：通过快速失败，防止故障扩散，适用于某个服务连续失败或超时的场景。
