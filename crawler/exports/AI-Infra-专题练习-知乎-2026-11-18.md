## 系统与网络基础

### 异步 I/O 与高速网络

#### A25 · DMA 和 RDMA 分别省去了哪一段 CPU 搬运？

DMA 允许设备与本地内存交换数据，CPU 无需逐字节复制。RDMA 则由网卡在授权的本地与远端内存间传输数据，一侧的读写可少经过对端 CPU 的数据路径。注册内存、提交工作请求和处理完成事件仍有成本，缓冲区也不能在完成前被重用。

#### A26 · TCP 与 RDMA 的数据路径有什么区别？什么情况下能看到延迟优势？

TCP 提供可靠字节流，常规 socket 收发经过内核协议栈。RDMA 可将已注册内存上的通信工作交给网卡，降低协议处理、复制与 CPU 调度开销。应在相同拓扑下分别测短消息、带宽与 CPU 使用量，同时考虑建连、注册和拥塞成本。有内核旁路或卸载的 TCP 实现也会改变对照结果。

#### A27 · PCIe 5.0 ×16 的理论带宽是多少？“双向”怎么算？

每 lane 每方向 32 GT/s，按 128b/130b 编码折合约 3.94 GB/s。×16 单向约 63.0 GB/s，全双工两个方向同时满载合计约 126 GB/s，尚未扣除事务协议开销。一笔单向 GPU 拷贝应对照单向数字，并核实链路协商的实际代际、宽度和 NUMA 拓扑。

#### A28 · 什么叫零拷贝？它能否免掉主机与 GPU 之间的所有数据搬运？

先指出省去的是哪一份中间缓冲。例如设备映射已有主机内存可以省显式的复制步骤，数据访问仍可能走互连。检查页固定、所有权、同步以及谁负责释放。若内核多次读取相同数据，先复制到显存再复用有时比多次跨总线直读更快。


## GPU 硬件与算子

### CUDA 执行与调度

#### W1 · GPU 怎样用 warp 调度隐藏访存或指令依赖的延迟？

一个 warp 等待读取结果时，调度器可以发射另一个就绪 warp 的指令。原始等待仍在发生，但执行单元在此期间完成了其他工作。同一 warp 中的独立指令也能提供并行性；两类独立工作都缺乏时才更可能看到发射空隙。

#### W2 · 为什么调度到另一个驻留 warp 通常不需要软件上下文切换？

驻留线程块已经分配好寄存器与共享内存，各 warp 的执行状态保存在硬件上。调度器改选另一个 warp 时无需经操作系统保存和恢复整套上下文；原 warp 即使等待仍占用资源，能否发射还取决于指令依赖和目标流水线。

#### W3 · resident、eligible 和 issued warp 有何区别？warp slot 表示什么？

Resident 表示 warp 已驻留且尚未结束，eligible 表示下一条指令当前可发射，issued 表示调度器实际选中并发射了该指令。存在就绪但本周期未被选择的 warp。Warp slot 是跟踪驻留 warp 的硬件容量，不能用它推算每周期实际完成多少运算。

#### W4 · warp 为什么会 stalled？遇到大量 stall 就一定要优化吗？

常见原因有访存结果未返回、前序指令尚未完成、目标流水线繁忙、取指受阻或等待块内同步。先看就绪 warp 是否不足、发射槽是否经常空闲，再把主要等待定位到具体指令。若其他 warp 已充分覆盖这些等待，减少某一个 stall 类别未必缩短 kernel 耗时。

#### W5 · warp occupancy 如何计算？为什么实测值可能低于理论值？

用每 SM 驻留的 warp 数除以该架构每 SM 最大驻留 warp 数。假设设备上限为 64，配置只允许 32 个，则理论值为 50%。实测是执行期间平均值，工作块太少、各块耗时不均、最后几波无法铺满设备都可能使它降低。

#### W6 · 给定寄存器、共享内存和 block size，怎样算最多能同时驻留多少 warp？

分别算每 SM 的寄存器、共享内存、线程数、warp 数以及 block 上限各能容纳多少完整线程块，取最小值，再乘每块向上取整的 warp 数。例如 256 线程、每线程 64 个寄存器时每块约需 16,384 个寄存器。实际计算还要考虑分配粒度及硬件分区，用目标设备工具复核。

#### W7 · 想提高 occupancy，怎样判断应先改寄存器用量、tile、block size 还是 grid？

寄存器受限时可缩短临时值存活时间，共享内存受限可减少缓冲或流水级数。过小的线程块可能先触到每 SM 最大块数，此时适度增大块可能有用。Grid 过小则缺的是独立工作块，调寄存器不会解决。每次同时看 spill、数据复用、驻留量和耗时。

#### W8 · 为什么较低 occupancy 的 kernel 反而可能更快？

较大的 tile 能复用输入，较多寄存器可减少临时存取，较深的流水线可能覆盖搬运。若为了容纳更多 warp 而引入 spill 或反复从全局内存加载，执行时间会增加。判断标准应是给定输入的实际吞吐和时延，并检查原来是否已经有足够指令可发射。

### 性能测量

#### W9 · 使用 Nsight Compute 时，怎样从调度指标决定下一步查哪里？

Active 少先查每块资源、grid 大小和尾部效应。Active 多而 eligible 少且发射空闲，再定位是内存依赖、计算依赖还是同步等待。若经常有指令可发射，转查对应执行单元、缓存与 DRAM 吞吐。用单变量实验验证推断，并保留端到端运行作对照。

#### A16 · 多卡时间线出现快慢卡，怎样识别主机提交或不同 CUDA Graph 执行路径造成的差异？

对齐同一迭代每个 rank 的主机线程、kernel 与集合通信。在慢 rank 上，CPU 迟发或某批回退可能表现为 kernel 之间出现空隙、整段执行晚启动，其他 rank 则在通信处等待。对照不同图档位、同步点及开关前后的设备执行时长；不能只看到通信长就认定网络慢。


## 深度学习框架与编译器

### 图捕获与特化

#### A21 · CUDA Graph 主要优化哪一种开销，怎样证明加速来自它？

将稳定的设备工作及依赖提前构图，多次执行时一次提交就能重放整段序列。短 kernel 较多、CPU 提交形成空隙时尤为有价值。固定输入与 kernel 实际工作量，对照主机提交、GPU 时间线及整体延迟，同时报告热身、捕获与额外显存成本。 [vLLM 的 CUDA Graph 设计](https://docs.vllm.ai/en/latest/design/cuda_graphs/)

#### A22 · Decode 的并发数不在已捕获的图档位里时，引擎会怎么办？

核对引擎版本、模式与实际执行形状。若有兼容的更大档位，可用缓冲区、真实长度和掩码补齐后重放；没有合适图则可能改走分段图或普通执行。按生产并发分布比较补齐浪费和回退增加的延迟，再决定需要捕获哪些常见档位。

#### A23 · 为什么有些操作捕获不了？捕获失败会如何影响服务？

捕获区间内的主机同步、依赖设备数据的主机控制流、不支持捕获的调用或跨 stream 依赖都可能构成障碍。即使捕获成功，新形状也未必可重放。预热并固定常用缓冲区、逐档验证，准备回退路径；依赖图优化的负载在回退后应重测尾延迟。

#### A24 · 从 NVIDIA CUDA Graph 迁到昇腾 ACL Graph 时，哪些条件要重新核实？

两者均可重用设备执行序列，但运行时 API、可捕获算子、内存池、通信后端和同步约束不同。先验证静态单卡，再依次加入动态批量、多流和跨卡通信，记录哪些路径能全图重放，哪些需要分段或回退。迁移后的正确性与性能都要在目标硬件上复测。 [vLLM Ascend 图模式](https://docs.vllm.ai/projects/ascend/en/main/user_guide/feature_guide/graph_mode.html)


## 模型推理与在线服务

### 自回归生成与接口

#### A9 · 从 API 收到请求到生成最后一个 token，各层做了什么？

网关校验租户、预算与模型，解析并分词；调度器排队、匹配前缀并分配 KV 块。执行端先 Prefill，再逐步 Decode 和采样，流式返回增量。遇到停止条件、取消或超时时要释放缓存引用和计算资源，最后提交用量并闭合链路追踪。

### 批处理、KV 缓存与调度

#### A7 · SGLang 的基数树前缀缓存有什么好处，维护成本在哪里？

公共前缀共享路径，新请求沿 token 序列寻找最长可复用部分。压缩单分支路径可减少索引节点数，多轮请求和相同系统提示易受益。索引查找、分裂、在用引用维护与淘汰都要付成本，在几乎没有共享前缀的流量中应实测是否值得。

#### A8 · vLLM 什么时候会抢占正在运行的请求，对它有什么影响？

可用 KV 块等关键资源无法满足后续调度时，调度器可能暂停部分请求并回收资源。根据版本与配置，之后可能需要重算前缀或恢复已换出的状态。抢占能让系统继续接单，但常抬高尾延迟；要联合观察显存水位、活跃序列、每轮 token 预算及抢占率。

#### A13 · 估算推理峰值显存时，除了模型权重还要算哪些项？

列出量化元数据、KV 或递归状态、激活与临时工作区、通信缓冲、图常驻缓冲和分配器保留空间。KV 容量用本 rank 的实际层数、KV 头、每序列长度和精度估算。按时间线确定哪些项同时存活，避免把互斥阶段理论最大值直接相加。

#### A29 · KVFlow 用什么信息决定多 Agent 工作流的前缀 KV 应该保留或预取？

对照同名论文，系统用 Agent Step Graph 表示流程，估计各 Agent 距离下次执行还有几步。缓存淘汰时优先保留较快需要的前缀，并提前从 CPU 调入接下来要用的 KV。比较 LRU 时要同时看重算、搬运与等待；对动态分支还需测预测误差的影响。 [KVFlow 原论文](https://arxiv.org/abs/2507.07400)

### 分布式推理与服务拓扑

#### A4 · 少数 MoE 专家过热时，怎样让各设备的工作量更均匀？

按层、专家和 rank 记录 token 量、排队及通信时间。部署侧可重排专家位置、复制常见热点专家或调整组批，训练侧可调负载均衡机制。区分仅改变物理位置与改变模型的选路决定，后者须额外验证质量。用偏斜真实的流量看热点和 P99 是否都改善。

#### A10 · 为什么要分离 Prefill 与 Decode，两类节点怎样分配？

两个阶段的计算形状、并发程度和延迟目标不同，分离能让两类池独立优化，也引入排队与 KV 传输成本。调度时估计未命中的提示工作量、传输时间、Decode 端显存和 token 容量。用真实输入输出长度与到达间隔回放，核对首字和逐 token 延迟。

#### A11 · Mooncake 怎样用 KV Cache 组织分离式服务？

Mooncake 将分布式 KV 缓存、Prefill 与 Decode 实例纳入协同调度。服务可利用不同存储层已有的前缀，在传输和重新计算之间比较成本，并把新算出的状态交给 Decode 端。命中率、可用带宽、传输重叠和过载准入都会改变收益。 [Mooncake 原论文](https://arxiv.org/abs/2407.00079)

#### A17 · 同样八卡，W8A8 MoE 用 DP2、TP4 加 EP，和 DP1、TP8 加 EP，怎样比较？

原题以 DeepSeek-V4-Flash-w8a8 为例。先明确所用引擎中专家组横跨哪些卡、每个副本能否装下。较小 TP 组可提高独立批次并发，但可能多复制状态；较大 TP 可减轻单卡容量压力，却增加某些规约成本。固定路由分布、输入输出长度、量化内核和 SLO，对照达标吞吐与尾延迟。

#### A18 · DeepSeek 类模型用 DP8 Attention 加 EP，与纯 TP8 有何取舍？

DP Attention 对不同请求独立计算，可能减少某些 TP 划分中的 KV 复制；专家层需要按路由分发与收集。纯 TP8 将同批计算切到多卡，局部矩阵规模及逐层规约成本不同。先确认具体框架的纯 TP 是否也切专家权重，再比较低并发、高并发和长上下文三类负载。

#### A19 · 如果两种方案都保留 EP，DP8 加 EP 和 TP8 加 EP 的差别还在哪里？

固定专家映射后，主要对照 Attention、共享专家和稠密层的切分；每个 rank 获得的序列、KV 布局、本地矩阵尺寸及进入专家层前的重排会不同。单独测 Attention、TP 集合通信和 EP All-to-All，以免把共有的专家阶段开销归因于 DP 或 TP。

### 在线运行与压测

#### A6 · 比较 vLLM 与 SGLang，怎样解释两套引擎的差别？

指定版本、模型和负载，分别追踪入队、组批、前缀索引、KV 分配和执行后端。两套引擎功能有重叠，可用实际的分块哈希索引或基数树路径举例。用相同质量和服务目标测试冷缓存、共享前缀、突发负载，再解释差距来自哪一段。 [vLLM 前缀缓存设计](https://docs.vllm.ai/en/v0.15.0/design/prefix_caching/)

#### A12 · vLLM 哪些部署参数最影响服务性能，怎样安排压测？

先固定模型、硬件与精度，再扫 TP/PP、KV 显存预算、最大上下文、每轮 token 数和活跃序列数。前缀缓存、分块 Prefill 与图档位也要结合业务形态。逐组记录首字延迟、token 间隔、达标吞吐、峰值显存和抢占率，分别报告冷启动与稳态。


## 可观测性、可靠性与成本治理

### 性能实验与故障定位

#### A14 · 如何找出推理集群端到端的主要瓶颈？

拆分入口、排队、Prefill、KV 搬运、Decode 和客户端输出，按输入长度、批量及租户分别比较尾延迟。选增幅最大的一段下钻到 CPU 时间线、kernel、互连或等待队列；用同一请求回放验证修复，并检查是否把瓶颈转移到新的位置。

#### A15 · 同批设备表现出快卡与慢卡，可能有哪些负载或硬件原因？

检查热降频、功耗限制、PCIe/NVLink 链路、NUMA 放置、进程争用及到达的数据量。MoE 专家偏斜和长短序列差异会让硬件完全正常的卡表现得较慢。按每 rank 的计算时长、进入通信的时刻、token 数和硬件计数器比较。

#### A20 · 确认某个 rank 是第一个落后的节点后，怎样区分设备、通信和数据问题？

固定输入和映射复现，分别做单卡计算与点对点通信基准，并交换 rank 与设备的绑定。若慢随设备移动，回查频率、错误和链路；若随某批数据或专家移动，回查分片与路由。逐阶段对齐首个偏离处，一次只改一个变量并保留对照。


## 编程、系统与模型基础

### 模型基础

#### A1 · MoE 为什么可能改善推理效率，哪些开销会抵消优势？

每个 token 只激活少数专家，使总参数容量与当步实际计算量部分解耦。全部权重仍需容纳，批量小时各专家的矩阵运算难以跑满，高并发下专家热点与跨卡通信也可能占主导。用相近质量的稠密模型作基线，测每 token 成本、吞吐和服务延迟。

#### A2 · MoE 把路由专家分组，是为了什么？

一些模型先在组级挑候选，再从候选组选择 Top-K 专家，可限制单 token 涉及的专家或节点范围。逻辑组若与物理拓扑协调，通信目的地可能减少。逻辑分组与 EP 的物理进程组并非天然相同，还要验证热点和限定候选对质量的影响。

#### A3 · 为什么有的 MoE 除了路由专家还保留共享专家？

共享专家为所有 token 提供稳定的稠密计算路径，可以学习通用模式；路由专家再处理差异化内容，两条路径按模型定义组合。共享分支也会带来固定计算与内存访问，部署时要说明它如何复制或切分，以及能否和其他工作重叠。

#### A5 · Gated DeltaNet 的递归状态，对推理和前缀缓存意味着什么？

GDN 使用随 token 递推的状态，用门控和增量更新保留或修正历史信息。在该层解码时不必为所有历史 token 逐个保留 KV；前缀复用要保存边界处的递归状态，若有卷积分支还需保留卷积历史。混合模型里的全注意力层仍有 KV。原题写作“qwen3.8”，原帖未给模型链接，此处只解释能核实的 GDN 机制。 [Qwen3.5 实现文档](https://github.com/huggingface/transformers/blob/main/docs/source/en/model_doc/qwen3_5.md)
