## 1. Agent Infra：如何为海量并发 Agent 提供安全隔离的执行沙箱

**回答框架**：每个 Agent 的执行（跑代码/读写文件/访问网络）放进独立沙箱：容器/微VM…

**参考回答**
每个 Agent 的执行（跑代码/读写文件/访问网络）放进独立沙箱：容器/微VM 做资源与文件系统隔离，eBPF/网络策略限制出网，资源配额+超时防滥用，统一调度实现毫秒级启停与水平扩展。

几千万 Agent 并发执行代码，核心风险是『逃逸+资源抢占+横向移动』。工程：① 隔离层用 gVisor/Firecracker 微虚拟机或容器，每个 Agent 独立文件系统与进程空间；② 网络用策略白名单（只允许调指定 API），eBPF 做 syscall 过滤；③ 资源配额(CPU/内存/磁盘)+硬超时，防 fork 炸弹/挖矿；④ 调度层池化预创沙箱，毫秒级复用；⑤ 审计：所有 syscall/网络/文件访问留痕。后端功底是这类系统的基础。

**加分点**

讲清『隔离三件套：文件系统/网络/资源』；提到微VM(gVisor/Firecracker)与 eBPF；联系后端并发/容器经验。

**雷区**

用共享环境直接执行不可信代码（逃逸风险）；只隔离不限额导致资源被挤占。

## 2. 什么是SQL注入攻击？如何防止

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q0839`　|　**标签**：`计算机网络` `网络攻击面试题`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 计算机网络、网络攻击面试题 的理解与工程落地、边界场景的掌握。

**回答框架**：SQL注入攻击是攻击者在HTTP请求中注入恶意SQL语句，让服务端构造执行SQL…

**参考回答**
SQL注入攻击是攻击者在HTTP请求中注入恶意SQL语句，让服务端构造执行SQL语句时，恶意的SQL被一起构造了，然后在数据库中执行，这样就可能对数据库造成大量数据拉取、删除、更新等敏感的操作。

SQL注入攻击是攻击者在HTTP请求中注入恶意SQL语句，让服务端构造执行SQL语句时，恶意的SQL被一起构造了，然后在数据库中执行，这样就可能对数据库造成大量数据拉取、删除、更新等敏感的操作。

预防SQL注入攻击，可以通过这几个方式：

- 使用参数化查询或预编译语句：使用参数化查询或预编译语句来构建和执行SQL查询。这样可以将用户输入的数据作为参数传递给查询，而不是将其直接拼接到SQL语句中，参数化查询可以防止恶意代码的注入。
- 输入验证和过滤：对用户输入的数据进行验证和过滤，确保只接受合法的输入，可以使用白名单过滤、正则表达式验证或者编码转义等技术来防止恶意代码的注入。
- 最小权限原则：在数据库中为应用程序使用最小权限的数据库账户，这样即使发生SQL注入攻击，攻击者也只能在该账户的权限范围内进行操作，减少损失。

## 4. 为什么大模型 Agent 需要沙箱（Sandbox）？它的威胁模型（Threat Model）包含哪几类？

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q1181`　|　**标签**：`Agent 沙盒与安全执行` `工具调用=真实副作用，错误会落地` `两类不可信：模型输出 + 用户输入` `三攻击面：命令/文件/网络` `核心原则：不信任 + 最小权限` `让模型能动手但不能乱动手`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 Agent 沙盒与安全执行、工具调用=真实副作用，错误会落地、两类不可信：模型输出 + 用户输入、三攻击面：命令/文件/网络 的理解与工程落地、边界场景的掌握。

**回答框架**：工具调用=真实副作用，错误会落地；两类不可信：模型输出 + 用户输入

**参考回答**
工具调用=真实副作用，错误会落地；两类不可信：模型输出 + 用户输入

一旦 Agent 具备工具调用/代码执行能力，它就从'会说话'变成'能行动'，错误会落地成真实副作用。沙箱是把这些动作限制在隔离环境里、控制文件/网络/资源/权限的安全边界。威胁模型分两类不可信来源：①模型输出不可信——LLM 可能生成错误甚至恶意的代码（死循环、删文件、外联）；②用户输入不可信——提示注入（直接/间接/隐蔽）诱导 Agent 越权。攻击面集中在三类：系统命令执行（os/subprocess）、文件系统读写（open）、网络外传（requests/socket）。沙箱第一原则就是'不信任'：不完全信任用户输入、不完全信任模型输出、不让模型直接碰生产资源。一句话：让模型能动手，但不能乱动手。

**加分点**

三攻击面：命令/文件/网络；核心原则：不信任 + 最小权限；让模型能动手但不能乱动手

## 5. CodeAct（用一段代码表达 Agent 动作）相比 ReAct 有什么优势？它最大的风险是什么，为什么必须配沙箱？

**回答框架**：优势:代码比多轮tool call更精确；适用:代码/数据/文件批量操作

**参考回答**
优势:代码比多轮tool call更精确；适用:代码/数据/文件批量操作

CodeAct 用代码而非多个自然语言 tool call 表达动作——比如批量读日志、统计 ERROR 数，一段 Python 比 list_files/read_file… 多轮调用更精确高效，适合代码修改、数据处理、文件批量操作、复杂计算。但它最大问题是安全：代码是图灵完备的，一旦 Agent 能执行任意代码，能力等同一个坐在终端前的程序员，且模型生成的代码不可信。必须限制：文件访问范围、网络访问权限、系统命令权限、执行时间、内存、敏感环境变量、危险 API。简化演示可用 SAFE_BUILTINS + exec 替换 __builtins__，但生产绝不够——真实要用容器+权限隔离+资源限制+审计日志+回滚。一句话：CodeAct 是动作表达形式的增强，不是 ReAct 的替代；凡用 CodeAct 必配沙箱、权限、超时、审计、回滚，否则风险极大。

## 6. Agent 沙箱的生命周期怎么管理？为什么强调短生命周期？生产环境如何降启动延迟、防资源泄露？

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q1188`　|　**标签**：`Agent 沙盒与安全执行` `按任务创建,用完即毁` `短生命周期+TTL自动回收` `降延迟:基础镜像+预热池` `防泄露:最大执行/空闲/磁盘+强制回收` `长任务:pause/resume或快照分叉`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 Agent 沙盒与安全执行、按任务创建,用完即毁、短生命周期+TTL自动回收、降延迟:基础镜像+预热池 的理解与工程落地、边界场景的掌握。

**回答框架**：按任务创建,用完即毁；短生命周期+TTL自动回收

**参考回答**
按任务创建,用完即毁；短生命周期+TTL自动回收

最稳妥：按任务创建临时沙箱→初始化环境→执行→净化结果→销毁。用完即毁可最小化状态污染、避免跨用户影响。短生命周期（TTL）是关键：每个沙箱带超时（如 5 分钟），到期自动回收。生产还要管两件事：①降启动延迟——把常用依赖做成基础镜像/自定义模板，维护一批预热（warm）沙箱池，任务来时直接复用；②防资源泄露——设最大执行时间、最大空闲时间、最大磁盘占用和强制回收策略，高并发下重点在资源调度、状态清理、日志追踪。长任务可用 pause/resume（如 E2B：暂停计费、状态落盘、恢复时文件/进程/变量原样恢复）或快照分叉（从同一状态派生多分支试错）。沙箱不是创建完就完事，麻烦在回收与调度。

**加分点**

降延迟:基础镜像+预热池；防泄露:最大执行/空闲/磁盘+强制回收；长任务:pause/resume或快照分叉

## 7. E2B 这类云端 Agent 沙箱的核心原理是什么？Firecracker、Jupyter Kernel 协议、状态持久

**参考回答**

E2B 是 AI Agent 领域最知名的云沙箱，核心抽象是把底层隔离环境封装成适合 Agent 调用的执行服务（运行时+文件系统+命令接口+网络+状态管理统一为任务空间），底层用 Firecracker MicroVM 提供硬件级隔离。关键技术点：①Firecracker microVM——独立内核、~125ms 启动、接近容器的速度，安全性一流；②Jupyter Kernel 协议——E2B 不重造语言引擎，而是用 Jupyter Gateway(WebSocket) + gRPC 适配层统一封装 IPython/IJava/gophernotes/ITypeScript，让 Python/JS/Java/Go/Ruby 共用成熟 REPL 协议，天然支持状态保持、变量查看、中断；③调度用 HashiCorp Nomad（比 k8s 轻、适合短生命周期批量作业、microVM 打包更高效）；④状态持久化——pause() 停止计费、状态落盘，resume() 原样恢复文件/进程/内存变量，长任务可暂停续跑，配合快照从同状态派生多分支。SDK 极简（Sandbox.create/run_code/files/commands/get_host/pause/resume），是它能被广泛'抄作业'的原因。

## 17. 如何在智能体架构中实施数据脱敏、访问控制与审计记录？

> **高频程度**：★★★☆☆　|　**原题 ID**：`q1253`　|　**标签**：`数据安全` `权限控制` `审计` `合规`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 数据安全、权限控制、审计、合规 的理解与工程落地、边界场景的掌握。

**参考回答**
身份贯穿全链路做 ACL 过滤，敏感字段在进入模型前脱敏、出模型后校验，所有动作 append-only 留痕可回放。

访问控制：用户身份必须透传到检索与工具执行两端——向量库的每个 chunk 继承原文档 ACL，检索时按用户可见范围做过滤（在检索阶段过滤而非事后过滤，避免召回了再丢造成结果为空或信息泄露）；工具调用用调用者身份而非服务账号。脱敏：入模前对手机号、身份证、银行卡等做识别与替换（可用占位符 + 映射表，输出时再还原给有权限的用户）；对第三方模型 API 尤其要做，必要时敏感场景走私有化模型；日志与 trace 里同样脱敏，别在排查问题时泄露。审计：所有关键动作写 append-only 事件日志，字段含 who/what/when/输入摘要/输出摘要/工具/结果/trace_id，支持按用户与时间检索并可回放整条决策链；日志保留期与访问权限按合规要求设定。补充：多租户要做数据物理或逻辑隔离，向量库按租户分库或强制 filter；模型返回内容在展示前再做一次敏感信息检测，防止跨用户信息通过模型记忆或缓存泄露。

**加分点**

## 20. 几千万并发沙箱，每个要毫秒级启动、严格资源隔离、安全网络策略——这就是 Agent Infra 要解决的问题

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q1665`　|　**标签**：`工程落地` `juejin`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 工程落地、juejin 的理解与工程落地、边界场景的掌握。

**回答框架**：Agent Infra 的核心是把沙箱做成毫秒级、强隔离、可编排的“进程级微虚拟…

**参考回答**
Agent Infra 的核心是把沙箱做成毫秒级、强隔离、可编排的“进程级微虚拟机”，用池化+快照+内核级隔离+策略化网络来同时满足启动速度、安全与资源约束。

这道题本质是三个互相冲突的目标：毫秒级启动、严格资源隔离、安全网络策略。工程上不能靠单一技术解决，需要分层设计。

1) 启动速度：几千万并发不可能每次冷启动。主流做法是预热池 + 快照恢复。Firecracker 用 microVM，冷启动约 125ms，但通过 VM 快照（snapshot/restore）可压到 5-10ms；gVisor 用用户态内核，启动接近进程但 syscall 开销大；Kata Containers 走轻量 VM。更激进的是把沙箱做成“进程 + 命名空间 + seccomp + cgroup”，启动 1-3ms，但隔离弱于 VM。真实系统常做分级：低风险任务用进程级，高风险用 microVM。

2) 严格资源隔离：CPU 用 cgroup v2 的 cpu.max 做配额，内存用 memory.max + memory.high 做软硬限，IO 用 io.max，进程数用 pids.max。关键是防止“邻居噪声”和 OOM 扩散：每个沙箱独立 cgroup，配合 memory.oom.group 让 OOM 只杀本沙箱。文件系统用 overlayfs + 只读 base，写层按沙箱挂载，避免共享写冲突。

3) 安全网络策略：默认 deny-all，出站走 egress proxy 或 eBPF 做 L3/L4 过滤，DNS 也要劫持到受控 resolver，防止 DNS 隧道。网络命名空间隔离 + veth 对，配合 Cilium/eBPF 做 per-sandbox 策略。对 Agent 场景还要限制访问元数据服务（169.254.169.254）和内网网段，防止 SSRF。

4) 编排与调度：几千万并发意味着控制面必须无状态、分片。沙箱生命周期用状态机管理，调度器按节点资源做 bin-packing，池化预热按负载预测动态伸缩。冷启动和热池要分开监控 P50/P99，毫秒级通常指 P99 而非平均。

5) 可维护性权衡：microVM 隔离强但内存开销大（每 VM 至少几十 MB），进程级轻但内核漏洞风险高。真实落地常按任务风险分级，并统一抽象成 Sandbox API，底层可替换 runtime。

**加分点**

1) 提 Firecracker 的 snapshot 恢复能到 5ms 级，但要注意快照包含内存页，恢复时需处理设备状态和随机数熵源，否则安全随机数会重复。
2) 提 gVisor 的 syscall 拦截用 Go 实现，兼容性坑多，比如 io_uring、某些 ioctl 不支持，Agent 跑浏览器/GPU 任务会踩。
3) 提 cgroup v2 的 memory.high 做软限流比 memory.max 更平滑，避免直接 OOM；pids.max 防 fork 炸弹。
4) 提 eBPF 做网络策略比 iptables 规则链性能好，且能按 cgroup id 关联沙箱，避免规则爆炸。
5) 提“毫秒级”要区分冷启动、快照恢复、池化取用三种口径，面试里主动澄清指标口径是加分项。
6) 提安全上要防侧信道，比如 Spectre 类攻击在共享内核的进程级沙箱里风险更高，microVM 更稳。

**雷区**

1) 只说“用 Docker”就完事：Docker 共享内核，隔离达不到严格，且冷启动远不止毫秒。
2) 把“毫秒级启动”理解成平均延迟：几千万并发下必须看 P99/P999，且要区分池化命中率。
3) 忽略网络默认策略：只做入站限制，忘了出站和 DNS，Agent 被 prompt injection 后容易 SSRF 打内网。
4) 认为 cgroup 能完全隔离 CPU：cpu.max 是配额不是硬实时，仍会有调度抖动，需要绑核或 cpuset 配合。
5) 忽略控制面瓶颈：几千万沙箱的注册、心跳、状态同步会打爆 etcd，需要分片和最终一致设计。
6) 把安全隔离和资源隔离混为一谈：前者防逃逸，后者防抢占，方案不同。

## 21. Vue Router 权限控制怎么做

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q1874`　|　**标签**：`概念基础` `juejin`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 概念基础、juejin 的理解与工程落地、边界场景的掌握。

**回答框架**：Vue Router 权限控制的核心是：用全局前置守卫 beforeEach 拦…

**参考回答**
Vue Router 权限控制的核心是：用全局前置守卫 beforeEach 拦截导航，结合路由 meta 标记与用户角色/权限，决定放行、重定向或跳登录页。

Vue Router 权限控制本质是“导航拦截 + 权限判定 + 动态路由”三件事。

1) 导航拦截：router.beforeEach((to, from, next) => {...}) 是全局前置守卫，每次路由跳转前都会执行。它像小区门口的保安：不管你去哪栋楼，先拦下来查证件。

2) 权限判定：在路由配置里用 meta 声明该页面需要的权限，例如 { path: '/admin', meta: { requiresAuth: true, roles: ['admin'] } }。守卫里读取 to.meta，再和当前用户信息（token、角色、权限列表）比对。

3) 三种处理结果：
- 有权限：next() 放行；
- 未登录：next({ path: '/login', query: { redirect: to.fullPath } }) 跳登录并记录来源，登录后跳回；
- 已登录但无权限：next('/403') 或 next('/')，避免死循环。

4) 动态路由：更彻底的做法是登录后根据后端返回的权限菜单，用 router.addRoute() 动态注册可访问路由，无权限的路由根本不存在，比单纯守卫更安全。

5) 典型流程：登录成功 -> 存 token 和用户角色 -> 拉取权限 -> 动态 addRoute -> 守卫校验 -> 渲染页面。

注意：前端权限控制只是体验层，真正的安全必须由后端接口鉴权兜底。

**加分点**

1) 守卫执行顺序：beforeEach -> beforeResolve -> afterEach，组件内 beforeRouteEnter 在 beforeResolve 之后、导航确认前调用；beforeEach 中 next 必须且只能调用一次，否则导航挂起。
2) 动态路由刷新丢失问题：addRoute 添加的路由在页面刷新后消失，需在守卫里判断“是否已拉取权限”，未拉取则先 await 获取权限并 addRoute，再用 next({ ...to, replace: true }) 重新进入，避免白屏或 404。
3) 权限粒度：路由级（页面）用 meta + 守卫；按钮级（操作）用自定义指令 v-permission 或函数式 hasPermission，二者分层。
4) 与后端配合：接口返回 401 时统一拦截跳登录，403 跳无权限页；token 过期用 refresh token 静默续期。
5) 源码层面：Vue Router 的导航守卫基于 history 的 transitionTo，守卫队列通过 iterator 串行执行，next 本质是推进队列。

**雷区**

1) 只做前端守卫就以为安全：前端可被绕过，后端必须再鉴权。
2) 在 beforeEach 里 next 调用多次或忘记调用，导致导航卡死或报错。
3) 动态路由刷新后丢失，没做“重新拉取权限再 addRoute”的处理，出现刷新即 404。
4) 把权限判断写在组件 mounted 里，页面已渲染才跳转，出现闪烁或数据泄露。
5) 登录后直接 next() 放行，没处理 redirect 回跳，用户体验差。
6) 用角色硬编码判断（如 role === 'admin'），扩展性差，应抽象成权限码或路由 meta 配置。

**回答框架**：Vue Router 权限控制核心是：登录后拿到用户角色/权限，前端用全局前置守…

**参考回答**
Vue Router 权限控制核心是：登录后拿到用户角色/权限，前端用全局前置守卫拦截并按权限过滤路由表，动态路由通常由后端返回权限标识、前端映射成路由（或后端直接返回路由结构），刷新丢失靠持久化 token 后重新拉取权限并 addRoute 重建。

一、整体思路
权限控制分两层：
1) 路由级（页面能不能进）：用 router.beforeEach 全局前置守卫做拦截。
2) 按钮/接口级（页面里能不能点）：用自定义指令 v-permission 或权限判断函数。

二、静态路由 + 动态路由
- 静态路由（constantRoutes）：登录页、404、首页等所有人可访问。
- 动态路由（asyncRoutes）：需要权限的页面，登录后根据用户权限动态 addRoute 注入。

三、动态路由由谁维护？
两种主流方案：
1) 前端维护路由表，后端只返回权限标识（如 roles: ['admin'] 或 permission codes）。前端在 asyncRoutes 上给每条路由打 meta.roles/meta.perms，然后 filter 出有权限的路由再 addRoute。优点：路由结构前端可控、可读性好；缺点：新增页面要改前端代码。
2) 后端直接返回路由结构（menu 树，含 path/name/component 字符串）。前端用 import() 动态映射 component。优点：权限和菜单统一由后端配置，前端不用发版；缺点：前后端耦合、component 字符串映射麻烦、类型不安全。
实际项目常见折中：后端返回菜单/权限码，前端维护 component 映射表，二者按 name 或 path 关联。

四、刷新丢失问题
动态路由是运行时 addRoute 加到内存 router 里的，刷新页面后 JS 重新执行，router 回到初始静态路由状态，动态路由就没了，表现为刷新后跳 404 或白屏。
解决：
1) 登录成功后把 token 存 localStorage/cookie。
2) 在 router.beforeEach 里判断：有 token 且还没拉过用户信息/权限，就调用 getUserInfo + 生成动态路由 + addRoute，然后 next({ ...to, replace: true }) 重新进入目标路由。
3) 用一个标志位（如 store 里的 routesLoaded 或 userInfo 是否已加载）避免死循环和重复添加。
4) 退出登录时 resetRouter（removeRoute 或重建 matcher）清掉动态路由。

五、通俗类比
把 router 想成一栋楼的楼层权限：静态路由是大堂和公共区，谁都能进；动态路由是各公司办公室，门禁卡（token+权限）决定你能进哪几间。刷新相当于你重新进楼，门禁系统要重新读卡发权限，所以必须再拉一次权限把办公室门牌挂回去。

六、关键代码骨架
router.beforeEach(async (to, from, next) => {
  const hasToken = getToken();
  if (!hasToken) {
    if (whiteList.includes(to.path)) return next();
    return next(`/login?redirect=${to.path}`);
  }
  if (to.path === '/login') return next('/');
  if (store.getters.roles.length === 0) {
    try {
      const { roles } = await store.dispatch('user/getInfo');
      const accessRoutes = await store.dispatch('permission/generateRoutes', roles);
      accessRoutes.forEach(r => router.addRoute(r));
      next({ ...to, replace: true });
    } catch (e) {
      await store.dispatch('user/resetToken');
      next(`/login?redirect=${to.path}`);
    }
  } else {
    next();
  }
});

**加分点**

1) addRoute 后必须 next({ ...to, replace: true }) 而不是 next()，否则新加的路由还没生效会命中 404；replace 避免历史记录多一条。
2) Vue Router 4 用 router.addRoute 返回移除函数，或 router.removeRoute(name)，也可通过 router.hasRoute 判断；Vue Router 3 用 router.addRoutes（已废弃）或重置 matcher。
3) 404 通配路由要最后加，否则动态路由会被通配先匹配；常见做法是动态路由加完后再 addRoute 通配。
4) 权限判断建议用 meta + 后端返回的权限码做交集，而不是只判断角色，角色粒度太粗。
5) 刷新重建时用 store 标志位（如 isRoutesLoaded）防止并发/重复 addRoute 导致重复路由警告。
6) 后端返回 component 字符串时，用 import.meta.glob 或 require.context 建立映射，避免 eval 动态 import 的安全和打包问题。
7) 按钮级权限可用自定义指令 v-permission，在 mounted 里判断无权限则 el.parentNode.removeChild(el)。
8) 可结合路由 meta.keepAlive、面包屑、菜单高亮，权限和菜单同源生成。

**雷区**

1) 只在登录页做权限判断，没在全局守卫拦截，用户直接输 URL 就能进。
2) 动态路由加完直接 next()，导致首次进入目标路由 404。
3) 刷新后不重新拉权限，动态路由丢失后跳 404 或白屏，却以为是缓存问题。
4) 把权限判断写在前端就以为安全，实际后端接口必须再校验，前端权限只是体验层。
5) 退出登录不清理动态路由，切换账号后残留上一个账号的路由。
6) 404 通配路由注册在动态路由之前，导致所有动态路由都被 404 拦截。
7) 混淆「后端返回权限标识」和「后端返回路由结构」，说不清 component 怎么映射。
8) 用 addRoutes 多次重复添加导致重复路由警告或内存泄漏。

## 24. 定义权限控制和沙箱场景（这个 Agent 能不能删库？能不能访问敏感数据？）

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q2871`　|　**标签**：`概念基础` `juejin`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 概念基础、juejin 的理解与工程落地、边界场景的掌握。

**回答框架**：权限控制是给Agent划定“能做什么”的规则，沙箱是给Agent一个“只能在这里…

**参考回答**
权限控制是给Agent划定“能做什么”的规则，沙箱是给Agent一个“只能在这里做”的隔离环境；前者管授权，后者管隔离，二者结合才能回答“能不能删库、能不能访问敏感数据”。

权限控制（Authorization/Permission Control）回答的是“这个主体有没有资格执行某个操作”，核心是主体、资源、动作、条件四要素，常见模型有 ACL、RBAC、ABAC。沙箱（Sandbox）回答的是“即使它想乱来，最多能造成多大破坏”，通过进程隔离、文件系统隔离、网络隔离、系统调用过滤等手段，把 Agent 限制在一个受控边界内。

通俗类比：权限控制像公司门禁卡，决定你能不能进财务室；沙箱像把员工关在一间没有窗户、没有外网、只有指定工具的房间里办公。门禁卡可能被伪造或提权，所以还需要房间本身足够坚固。

回到面试题：Agent 能不能删库？如果它的数据库账号只有 SELECT 权限，就不能删；如果它运行在只读副本或临时快照上，即使执行 DROP 也影响不到生产库。能不能访问敏感数据？如果权限系统只给它脱敏后的视图，或者沙箱网络策略禁止它访问敏感数据服务，就访问不到。

工程上通常分层：1）身份与凭证：给 Agent 独立的 service account，最小权限；2）策略层：用 RBAC/ABAC 或 OPA 做细粒度授权，按用户、任务、数据分级动态判定；3）执行层：容器/微虚拟机/gVisor 做沙箱，限制文件、网络、系统调用；4）审计与熔断：记录所有工具调用，危险操作二次确认或人工审批。

适用场景：低风险只读查询可以放宽沙箱、用权限控制即可；高风险写操作、访问 PII、执行任意代码，必须权限最小化加沙箱隔离，甚至人工在环。

**加分点**

1）权限控制是“授权决策”，沙箱是“强制隔离”，二者是纵深防御的两层，不能互相替代。2）可以提到最小权限原则、默认拒绝、职责分离。3）沙箱实现可提 Linux namespace/cgroup、seccomp、gVisor、Firecracker、WebAssembly 沙箱；权限可提 OPA/Casbin、Google Zanzibar 关系元组模型。4）Agent 场景特殊在工具调用是动态生成的，所以要做参数级校验和输出过滤，防止 prompt injection 绕过权限。5）可提“能力（capability）”模型：不直接给身份，而是给一次性、可撤销、限定范围的令牌。

**雷区**

1）把权限控制和沙箱混为一谈，认为有权限就不需要沙箱，或反之。2）只做前端提示词约束，比如“请不要删库”，这不是安全边界。3）给 Agent 复用人类高权限账号，导致权限过大且无法审计。4）忽略间接提示注入：用户输入可能诱导 Agent 调用高权限工具。5）认为只读账号就绝对安全，忽略数据外泄和推理攻击。6）沙箱配置过松，比如挂载 Docker socket、开放外网，等于没隔离。

## 25. 设计了“关键词触发 + LLM 推理”结合的工具决策机制，确保高风险场景（如金融建议）强制触发合规检查

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 概念基础、juejin 的理解与工程落地、边界场景的掌握。

**参考回答**
用规则层做高召回、低延迟的硬触发，用LLM做语义理解与工具选择，高风险场景由规则强制插入合规检查，二者互补而非互斥。

核心思路是分层决策：第一层是确定性的关键词/正则/意图分类器，命中高风险词表（如“推荐股票”“保本收益”“贷款”“转账”）时直接短路，强制调用合规检查工具，绕过LLM的自由裁量；第二层是LLM推理，负责理解用户真实意图、消歧、在多工具间做选择与参数填充。为什么这么设计：LLM有概率性、可能被提示注入绕过、对高风险场景漏判代价极高；而纯规则又太脆、无法覆盖长尾表达。所以用规则保底（高召回、可审计、低延迟），用LLM提体验（高精度、泛化好）。类比：机场安检，金属探测门是规则（必过、强制），人工开箱检查是LLM（灵活判断），但危险品清单是硬性触发。工程上通常实现为：前置规则网关 -> 命中则走强制合规链路 -> 未命中则进入LLM function calling/ReAct循环 -> 工具执行前再过一次输出侧合规校验（双层防护）。适用场景：金融、医疗、法律、未成年人保护等强监管领域。

**加分点**

1）双向防护：输入侧关键词触发 + 输出侧对LLM生成的建议再做合规分类，防止LLM在非触发词下自行给出投资建议。2）关键词表要版本化、可热更新、带优先级和命中日志，便于审计与回溯。3）用轻量分类器（如fastText/小BERT）替代纯关键词，降低“关键词误伤”和“变体绕过”（如拼音、谐音、拆字）。4）规则命中后仍让LLM生成合规话术，但工具调用被硬编码锁定，避免LLM跳过。5）可参考OpenAI function calling的tool_choice强制指定、以及NeMo Guardrails/Guardrails AI的输入输出校验模式。6）注意提示注入：用户可能说“忽略以上规则”，规则层在LLM之前执行可天然抵御。

**雷区**

1）认为LLM足够聪明就不需要规则，忽略高风险场景的漏判成本和不可审计性。2）只做输入侧关键词，不做输出侧校验，LLM仍可能生成违规建议。3）关键词表写死、无版本管理，线上无法快速响应监管变化。4）把规则和LLM做成串行且规则命中就完全不走LLM，导致无法生成合规解释话术，体验差。5）忽略误报：正常讨论“股票”被强制合规，需设计白名单/上下文判断。6）认为关键词触发能覆盖所有变体，忽视谐音、拼音、多语言绕过。

**参考回答**
内容合规需构建覆盖输入输出、贯穿事前事中事后的多层防御体系，核心是分类分级、过滤拦截、审核兜底与持续迭代。

保证内容合规不是单一模型或规则能解决的，而是一个工程体系。通常分四层：
1. 事前预防：制定内容安全策略与分类分级标准（如涉政、涉黄、暴恐、违禁品、歧视等），在训练/微调阶段清洗数据、对齐价值观（RLHF、安全SFT），并给模型注入拒答模板。
2. 事中拦截：在用户输入侧做Prompt过滤（关键词、正则、语义向量检索、小模型分类器），在模型输出侧做流式/整段审核（敏感词库、AC自动机、BERT类分类模型、大模型裁判）。对高风险场景可强制走安全回复或人工确认。
3. 事后兜底：建立人工审核队列、用户举报通道、日志审计与溯源，对漏网内容快速下架并回灌样本。
4. 持续运营：定期更新词库与模型，做红蓝对抗、A/B测试，监控误杀率与漏杀率，平衡安全与体验。
通俗类比：像小区安保——门禁（输入过滤）、巡逻（输出审核）、监控（日志）、保安（人工）、定期演练（红队）。

**加分点**

1. 分层防御：规则层（AC自动机、DFA）低延迟高召回，模型层（BERT/LLM分类器）高精度但成本高，二者级联可兼顾性能与效果。2. 流式输出审核：对LLM逐token生成，需滑动窗口+增量分类，避免整段生成后才拦截导致延迟；可结合前缀树提前命中。3. 对抗鲁棒性：处理谐音、拆字、拼音、emoji、Base64、多语言混写等绕过手段，需归一化+多模态审核。4. 合规标准：参考《生成式人工智能服务管理暂行办法》、网信办算法备案、欧盟DSA/AI Act，建立可审计的合规文档。5. 评估指标：除准确率外，关注误杀率（影响体验）与漏杀率（合规风险），用混淆矩阵和业务阈值调优。

**雷区**

1. 认为只靠敏感词库就能解决，忽略语义变体和上下文。2. 只审核输出不审核输入，导致Prompt注入或诱导性输入绕过。3. 忽视流式场景，等整段生成完再审核，造成延迟和已泄露风险。4. 把合规完全交给大模型，忽略规则层的高召回和可解释性。5. 不区分场景与地区法规，一刀切导致误杀或漏管。6. 没有人工兜底和持续迭代，上线后词库模型僵化。

## 27. 如何保证内容合规？ 你是否理解安全与监管约束

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q2924`　|　**标签**：`概念基础` `juejin`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 概念基础、juejin 的理解与工程落地、边界场景的掌握。

**回答框架**：内容合规靠“输入过滤+生成约束+输出审核+可追溯审计”的多层纵深防御，安全与监管…

**参考回答**
内容合规靠“输入过滤+生成约束+输出审核+可追溯审计”的多层纵深防御，安全与监管约束是产品能否上线的硬性边界，而非事后补丁。

内容合规不是单点技术，而是一套贯穿数据、模型、应用、运营的工程体系。可以类比成“机场安检”：登机前（输入）查证件和危险品，飞行中（生成）有驾驶规则，落地后（输出）再抽检，全程还有监控录像（审计）。

具体分层：
1. 输入侧：对用户 prompt 做敏感词/正则/分类模型检测，拦截违法、色情、暴力、政治敏感等请求；对上传文件做类型、大小、内容扫描。
2. 生成侧：用系统提示词约束模型行为，如“拒绝回答违法内容”；采用安全对齐模型（RLHF/DPO 训练过）；对高风险领域做拒答或转人工。
3. 输出侧：对模型回复做二次审核，可用关键词库、分类模型、大模型自审（LLM-as-judge），命中则替换为安全话术或直接拦截。
4. 数据与训练侧：训练数据清洗去毒，标注合规边界，避免模型学到违规内容。
5. 审计与追溯：记录请求、响应、审核结果、操作人，满足监管留痕要求；支持事后回溯和申诉。
6. 运营侧：建立违规样本库、定期红队测试、人工复核队列、应急响应流程。

安全与监管约束包括：法律法规（如《生成式人工智能服务管理暂行办法》《数据安全法》《个人信息保护法》）、行业规范、平台政策。它们决定：哪些内容不能生成、用户数据能否出境、是否需要实名、是否要内容标识（如 AI 生成水印）、是否要备案。

适用场景：面向公众的 AIGC 产品必须做；企业内部知识库可适当放宽但仍需防泄露；医疗、金融、政务等强监管领域要求更严，需人工审核和可解释性。

**加分点**

1. 提到“纵深防御”和“最小必要”原则，输入输出双侧审核，避免只依赖单一敏感词库（易被谐音、变体绕过）。2. 了解 LLM-as-judge 做输出审核，但知道其有误判和成本问题，可结合小分类模型做级联。3. 知道合规不是 100% 拦截，而是风险分级：低风险自动放行，中风险加提示，高风险拒答/转人工。4. 能说出具体法规名称和备案要求，体现落地经验。5. 提到红队测试和对抗样本，持续迭代规则。6. 知道审计日志要脱敏存储，平衡合规与隐私。

**雷区**

1. 认为“加个敏感词库就完事”，忽略变体、上下文和模型生成的不确定性。2. 只做输入过滤，不做输出审核，模型仍可能生成违规内容。3. 把安全与监管当成法务的事，技术不参与，导致上线后被下架。4. 过度拦截，正常问题也拒答，伤害用户体验。5. 忽略数据合规，如训练数据侵权、用户数据未授权使用。6. 认为开源模型无监管责任，实际部署方仍需负责。7. 不做日志留存，监管检查时无法自证。

## 28. “写文件和执行命令要么标了危险等级、要么强制人工确认，所有执行记录落审计日志。能力越大的系统，越要先想清楚怎么拦住它。”

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q2953`　|　**标签**：`工程落地` `juejin`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 工程落地、juejin 的理解与工程落地、边界场景的掌握。

**回答框架**：对具备写文件/执行命令能力的 Agent，必须做「危险分级 + 强制人工确认 +…

**参考回答**
对具备写文件/执行命令能力的 Agent，必须做「危险分级 + 强制人工确认 + 全量审计」三道闸门，能力越大越要先设计拦截而非先设计能力。

核心是把「能力」和「授权」解耦：Agent 只负责提出动作意图（intent），真正的执行由一层受控的执行器（Executor/Gateway）完成，中间插入策略判定。

1) 危险等级分级（Policy Engine）：
- L0 只读：ls/cat/grep/读日志，自动放行。
- L1 低危写：写临时目录、生成草稿文件、写 /tmp，自动放行但记录。
- L2 中危：修改业务代码、写数据库非生产表、git commit，需要人工确认（HITL）。
- L3 高危：rm -rf、DROP TABLE、kubectl delete、改生产配置、curl | bash、sudo、访问密钥文件，强制人工确认 + 二次校验（如要求输入目标资源名）。
- L4 禁止：直接拒绝，如 rm -rf /、fork bomb、写 /etc/passwd。
分级依据不能只看命令字符串，要结合：命令 + 参数 + 目标路径 + 运行环境（prod/dev）+ 调用者身份。

2) 强制人工确认（Human-in-the-loop）：
- 确认不是弹个「是否继续」，而要展示「将要执行的确切命令、影响范围、diff、回滚方案」。
- 对 L3 采用「确认令牌」：确认后签发一次性 token，绑定命令哈希 + 过期时间，防止确认 A 却执行 B（TOCTOU）。
- 超时未确认默认拒绝（fail-closed），而不是默认放行。

3) 审计日志：
- 记录 who（用户/Agent 身份）、what（原始意图 + 实际执行命令）、when、where（主机/容器/路径）、why（触发它的对话/任务 ID）、result（退出码、stdout/stderr 摘要）、approval（谁批的、何时批）。
- 日志要 append-only、带哈希链或写入独立审计存储，防止 Agent 自己改日志。
- 关键：审计日志本身不能被 Agent 的写权限覆盖，否则等于没有。

4) 工程实现要点：
- 用白名单 + 参数化执行，避免字符串拼接进 shell（防注入）。
- 沙箱：容器/namespace/seccomp 限制文件系统与网络，即使误判也缩小爆炸半径。
- 幂等与回滚：写文件前备份，命令支持 dry-run。

一句话：先设计「拦得住」，再设计「做得多」。

**加分点**

1) 引用真实事故模式：Agent 拿到 shell 后 `rm -rf` 或 `git push --force` 造成不可逆损失，说明为什么默认拒绝（fail-closed）比默认放行重要。
2) 提到 TOCTOU（Time-of-check to time-of-use）：确认时看到的命令和执行时的命令必须一致，用命令哈希绑定确认令牌，这是很多实现忽略的坑。
3) 提到审计日志的防篡改：append-only + 哈希链（类似区块链/透明日志 Certificate Transparency 思路），或写到 Agent 无写权限的独立 sink。
4) 提到分级要基于「解析后的 AST/参数」而非正则匹配字符串，否则 `rm -rf /` 和 `rm -r -f /` 或 `$(echo cm0gLXJm)` 绕过。
5) 提到权限最小化：Agent 进程本身不应有 root，用独立低权用户 + 受限 sudoers。
6) 提到可观测性：审计日志接入 SIEM，异常模式告警（如短时间内大量 L3 请求）。

**雷区**

1) 只做「危险命令黑名单」：正则匹配 `rm -rf` 很容易被 `rm -r -f`、变量拼接、base64 解码执行绕过，黑名单永远不全。
2) 把确认做成「默认放行、超时自动继续」：正确做法是 fail-closed，超时即拒绝。
3) 审计日志和 Agent 写在同一可写目录：Agent 可以删改日志，审计形同虚设。
4) 只记录「执行了什么」，不记录「谁批准的、原始意图是什么」：事后无法追责和复现。
5) 认为「分级一次配置永久有效」：环境变化（dev 变 prod）、命令组合会改变危险等级，需要动态评估。
6) 忽略 TOCTOU：确认和执行之间命令被替换，确认失去意义。
7) 把安全完全交给模型「自觉」：模型可能被 prompt injection 诱导执行危险操作，必须在执行层硬拦截，不能只靠 system prompt。

## 29. 你的小程序用openid去登陆，可以讲一下OAuth流程吗（可信平台对前端发放token，后端处理敏感信息）

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q3331`　|　**标签**：`工程落地` `juejin`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 工程落地、juejin 的理解与工程落地、边界场景的掌握。

**回答框架**：小程序登录本质是「前端拿临时 code 换后端会话」的定制 OAuth 变体：前…

**参考回答**
小程序登录本质是「前端拿临时 code 换后端会话」的定制 OAuth 变体：前端只负责拿 code，敏感信息（openid/session_key）和 token 签发全在后端完成，前端拿到的是后端自签的登录态而非微信 token。

标准 OAuth2 授权码模式是「前端拿 code → 后端用 code + client_secret 换 access_token → 后端用 token 拉用户信息 → 后端签发自己的会话」。微信小程序登录是它的裁剪版：

1. 前端调用 wx.login() 拿到临时凭证 code（5 分钟有效、一次性）。
2. 前端把 code 发给自己的后端（不是发给微信）。
3. 后端用 appid + secret + code 调微信 code2Session 接口，换回 openid、session_key、unionid。
4. 后端用 openid 查/建用户，生成自己的登录态（JWT 或 sessionId），返回给前端。
5. 前端后续请求带这个 token，后端校验即可，不再依赖微信。

关键点：openid 是「用户在这个小程序里的唯一标识」，不是凭证，绝不能当前端 token 用；session_key 是解密敏感数据（手机号、加密用户信息）的密钥，必须留在后端。

为什么不让前端直接拿 openid 登录？因为 openid 可被伪造/重放，且前端无法安全持有 secret。可信平台（微信）只对「后端」发放可信身份，前端只是 code 的搬运工。

工程上还要处理：code 只能用一次（并发/重试会失败）、session_key 会过期需重新登录、多端（小程序/公众号/App）用 unionid 打通、token 过期与刷新策略。

**加分点**

1. 能说出 code2Session 的返回结构和错误码（如 40029 invalid code、45011 频率限制），并做重试/降级。
2. 知道 session_key 不应下发给前端，解密手机号用后端 AES-128-CBC + iv，且要校验 watermark.appid 防跨小程序数据。
3. 登录态设计：JWT 无状态但难吊销，session 有状态但需 Redis；可用「短 JWT + 长 refresh token」或 Redis 存 session 做主动踢下线。
4. 安全细节：code 换 session 要加频率限制防刷；openid 入库要唯一索引；token 用 HttpOnly Cookie 或前端存储 + 防 XSS。
5. 多端统一：用 unionid 做账号体系主键，openid 只作渠道标识。

**雷区**

1. 把 openid 当 token 直接给前端，或前端拿 openid 去请求后端做鉴权——openid 可伪造，等于没鉴权。
2. 把 appsecret 写在前端/小程序里，或前端直接调 code2Session。
3. 以为 code 可重复使用，或不做 code 一次性校验导致重放。
4. 混淆 openid 与 unionid，多端账号打不通。
5. 把 session_key 返回给前端，或解密时不校验 watermark。
6. 只做登录不做会话过期/刷新，token 永久有效。

## 30. OAuth有什么优势（避免前端直接接触敏感信息）

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q3332`　|　**标签**：`概念基础` `juejin`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 概念基础、juejin 的理解与工程落地、边界场景的掌握。

**回答框架**：OAuth 的核心优势是用「授权令牌」代替「账号密码」交给第三方，让前端/第三方…

**参考回答**
OAuth 的核心优势是用「授权令牌」代替「账号密码」交给第三方，让前端/第三方永远拿不到用户的敏感凭证，实现最小权限、可撤销、可审计的委托授权。

OAuth（Open Authorization）是一个开放标准的授权框架，解决的是「如何让第三方应用在用户不交出密码的前提下，有限地访问用户在某个服务上的资源」。

通俗类比：酒店房卡。你入住酒店（资源服务器），不会把身份证和银行卡（账号密码）交给来打扫的服务员（第三方应用），而是去前台（授权服务器）办一张只能开你房间、且当天有效的房卡（access token）。服务员拿房卡干活，丢了可以立刻注销，也进不了别的房间。

核心优势：
1. 避免前端/第三方直接接触敏感信息：用户密码只在授权服务器（如微信/Google 的登录页）输入，第三方应用和前端页面从头到尾看不到密码，只拿到 token。即使第三方被攻破，泄露的也只是 token，不是用户密码，且用户改密码不会波及其他站点。
2. 令牌而非凭证：access token 是短期、有 scope 的凭证，可设置过期时间、可刷新（refresh token）、可随时撤销，比长期有效的密码安全得多。
3. 最小权限（scope）：第三方只能申请并拿到用户同意的权限，比如「只读头像昵称」，不能读私信。
4. 解耦与标准化：资源所有者、客户端、授权服务器、资源服务器四角色分离，支持授权码、PKCE、客户端凭证等多种模式，适配 Web、移动端、服务端、IoT 等场景。
5. 可审计与可扩展：授权服务器统一记录谁在何时授权了哪些 scope，便于风控和合规；也便于做 SSO、第三方登录。

典型流程（授权码模式）：前端把用户重定向到授权服务器 → 用户登录并同意 → 授权服务器回调带 code → 后端用 code + client_secret 换 token → 后端用 token 调资源接口。敏感交换都发生在后端，前端只经手一次性的 code。

**加分点**

1. 能区分 OAuth 2.0 是「授权」框架而非「认证」框架，认证要用 OpenID Connect（OIDC）在其上加 id_token。
2. 知道授权码模式为什么比隐式模式安全：code 经前端但需后端配合 client_secret 才能换 token，且推荐 PKCE（code_challenge/code_verifier）防拦截，移动端/SPA 必用。
3. 了解 token 的形态：不透明 token 需 introspection，JWT 可自包含但撤销难，需短过期 + refresh token 轮换。
4. 踩坑：redirect_uri 必须严格白名单校验，否则会被开放重定向偷 code；state 参数防 CSRF；不要用 implicit 模式；refresh token 要绑定客户端并支持轮换与吊销。
5. 可提 RFC 6749/6750/7636 及 OAuth 2.1 草案对隐式模式和密码模式的废弃。

**雷区**

1. 把 OAuth 当成「登录认证」直接说「用 OAuth 登录」，混淆授权与认证。
2. 以为前端拿到 access token 就安全，实际上 SPA 应尽量走后端换 token 或使用 BFF，避免 token 存在 localStorage 被 XSS 窃取。
3. 认为有了 OAuth 就不需要 HTTPS、不需要校验 redirect_uri 和 state。
4. 把 access token 当长期凭证存数据库明文，或把 client_secret 写在前端代码里。
5. 混淆 OAuth 与 SSO、JWT：SSO 是效果，OAuth 是实现手段之一；JWT 只是 token 的一种格式，不是 OAuth 本身。

## 31. 这就是 Agent 和 Chatbot 的区别：Chatbot 给你一坨文字，Agent 给你一条可审计的决策链

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q3410`　|　**标签**：`概念基础` `juejin`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 概念基础、juejin 的理解与工程落地、边界场景的掌握。

**回答框架**：Chatbot 只输出文本，Agent 输出可审计的决策链：它把目标拆成步骤、调…

**参考回答**
Chatbot 只输出文本，Agent 输出可审计的决策链：它把目标拆成步骤、调用工具、观察结果、再决策，全过程留痕可回溯。

Chatbot 的本质是「文本到文本」的映射：输入一句话，模型自回归生成一段回复，中间没有状态、没有外部动作、没有验证。它像一位只会口头回答的顾问，说完就结束，对不对、做没做都无法追责。

Agent 的本质是「目标到行动」的闭环：它维护一个状态（目标、历史、记忆），在每一步做决策——是继续推理、调用工具、还是给出答案——然后执行、观察结果、再进入下一步。这条链就是决策链（trajectory / trace），典型结构是 ReAct 循环：Thought → Action → Observation → Thought … → Final Answer。

为什么可审计很关键？因为每一步都记录了「当时基于什么信息、为什么选这个动作、工具返回了什么」。出了问题可以定位是推理错、工具错还是参数错；合规场景可以复现和追责；工程上可以回放、评测、做失败归因。Chatbot 只有最终文本，无法回答「你为什么这么说」。

类比：Chatbot 像餐厅里只报菜名的服务员，Agent 像带点单小票的厨师——每一步加什么料、谁经手、什么时间，小票上都写着。

适用场景：Chatbot 适合问答、闲聊、文案生成这类一次性文本任务；Agent 适合需要多步操作、外部信息、状态改变的任务，比如查数据库再下单、多轮检索后写报告、自动修 bug。判断标准很简单：任务是否需要「做」而不只是「说」，是否需要中间过程可追溯。

**加分点**

1) 决策链的工程实现：LangChain/LangGraph 的 trace、OpenAI function calling 的 tool_calls 消息、AutoGPT 的 thought/action 日志，本质都是把隐式推理显式化成可序列化的步骤。2) ReAct 论文（Yao et al. 2022）证明 Thought 步骤能显著降低幻觉，因为强制模型在行动前先写出依据。3) 可审计还带来可评测：可以按 step 做单元测试，而不是只看最终答案对错。4) 安全上，决策链是护栏的挂载点——在 Action 前做权限校验、在 Observation 后做注入检测。

**雷区**

1) 以为 Agent 就是「加了工具调用的 Chatbot」——工具调用只是手段，核心是闭环决策与状态管理。2) 以为决策链等于把思维链原文打印出来——可审计要求结构化、可复现，不是一段自由文本。3) 认为 Agent 一定比 Chatbot 强——简单问答用 Agent 反而更慢更贵更不稳定。4) 忽略审计的代价：全量记录 trace 会带来存储、隐私和延迟问题，需要采样与脱敏。

## 32. 客户敏感信息（手机号、地址等）怎么处理的

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q3634`　|　**标签**：`概念基础` `xiaohongshu`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 概念基础、xiaohongshu 的理解与工程落地、边界场景的掌握。

**回答框架**：客户敏感信息必须做加密存储、脱敏展示、最小化收集与访问控制，绝不能明文落库或明文…

**参考回答**
客户敏感信息必须做加密存储、脱敏展示、最小化收集与访问控制，绝不能明文落库或明文打日志。

处理客户敏感信息（手机号、地址、身份证、银行卡等）的核心原则是：最小化收集、加密存储、脱敏展示、受控访问、可审计、可删除。

1) 收集阶段：只收集业务必需字段，明确告知用途并取得授权（如隐私政策、单独同意）。能不用明文就不用，例如手机号可先做哈希用于去重/查询。

2) 传输阶段：全链路 HTTPS/TLS，禁止在 URL query 里传敏感信息，避免被网关、浏览器历史、日志记录。

3) 存储阶段：
- 数据库字段加密：可用 AES-256-GCM 等带认证的对称加密，密钥放 KMS/密钥管理服务，不跟数据同库同盘。
- 高敏感字段（身份证、银行卡）建议应用层加密后再入库，数据库落盘加密（TDE）只是补充，不能替代应用层加密。
- 需要等值查询的字段，可存“确定性哈希 + 加密密文”两列：哈希用于精确匹配，密文用于解密展示。
- 需要模糊查询的地址，可拆成省市区结构化字段，或使用支持加密检索的方案。

4) 展示阶段：脱敏输出，例如手机号 138****1234，地址只显示到区/街道，身份证 110***********1234。前端、接口、导出文件都要脱敏；只有极少数有权限的角色可申请查看完整信息，并记录审计日志。

5) 使用与访问：RBAC/ABAC 权限控制，最小权限原则；内部系统间调用使用服务身份认证；禁止开发/测试环境使用生产真实数据，需做数据脱敏或造数。

6) 日志与监控：日志、埋点、异常堆栈、APM 中禁止打印完整敏感信息，统一走脱敏工具类；对批量查询、导出、异常访问做告警。

7) 生命周期：设置保留期限，到期删除或匿名化；支持用户注销、撤回授权、数据可携带等合规要求（如 GDPR、个人信息保护法）。

通俗类比：敏感信息像家里的钥匙。不能把钥匙插在门上（明文存储），不能见人就给（无脱敏展示），不能随便配一把放公司抽屉（测试环境用生产数据），也不能丢了不知道（无审计）。正确做法是放保险柜（加密+KMS），只有需要的人按流程申请才能取，取用有记录。

**加分点**

1) 加密算法选择：优先 AES-GCM 这类 AEAD，避免 CBC 无认证带来的 padding oracle 风险；密钥要分层，主密钥在 KMS/HSM，数据密钥加密后随数据存，支持轮换。
2) 确定性加密 vs 随机加密：随机 IV 更安全但无法等值查询；可用 HMAC-SHA256 做盲索引（blind index）支持精确查询，注意 HMAC 密钥也要保护，防止字典攻击手机号。
3) 手机号只有 11 位、空间小，单纯哈希可被彩虹表/暴力枚举，必须加盐或 HMAC 密钥。
4) 日志脱敏最好在框架层统一处理，例如自定义 Logback Converter、Jackson 序列化器，避免依赖开发人员自觉。
5) 合规上可提《个人信息保护法》、GDPR、等保 2.0、PCI-DSS；数据出境、委托处理、第三方共享都要单独评估。
6) 可提字段级加密与数据库 TDE 的区别：TDE 防的是物理盘被偷，防不了有库权限的 DBA 或 SQL 注入。

**雷区**

1) 只做数据库 TDE 就认为安全，忽略应用层加密和 DBA 越权。
2) 用 MD5/SHA1 直接哈希手机号，不加盐不加密钥，可被彩虹表反查。
3) 只在页面脱敏，接口返回和导出 Excel 仍是明文。
4) 把密钥写在配置文件、代码仓库或环境变量里且无轮换。
5) 测试环境直接拷贝生产数据，导致泄露面扩大。
6) 日志里打印完整请求体、响应体，敏感信息随日志落盘。
7) 认为“内网就安全”，不做权限控制和审计。
8) 加密后无法查询就放弃加密，或使用 ECB 模式导致相同明文密文相同，泄露规律。

## 33. 【安全合规】 10. 客户敏感信息（手机号、地址等）怎么处理的？ 11. 涉黄/涉政拒答具体怎么做？

> **高频程度**：★★☆☆☆　|　**原题 ID**：`q3641`　|　**标签**：`概念基础` `xiaohongshu`

**考察点**：【由分类/标签推断】安全与沙箱 方向，重点考察 概念基础、xiaohongshu 的理解与工程落地、边界场景的掌握。

**回答框架**：敏感信息靠'识别-脱敏-隔离-审计'全链路治理，涉黄涉政靠'输入输出双向审核+分…

**参考回答**
敏感信息靠'识别-脱敏-隔离-审计'全链路治理，涉黄涉政靠'输入输出双向审核+分类模型+策略兜底'实现拒答，核心是数据不落地、内容可拦截、行为可追溯。

一、客户敏感信息（手机号、地址、身份证、银行卡等）处理，遵循'最小必要、可用不可见、全程可审计'三原则，分四层：
1) 识别与分类分级：用正则+NER模型（如基于BERT的实体识别）识别PII，按《个人信息保护法》《数据安全法》分为一般/敏感/核心，打标签入库。
2) 传输与存储：传输全链路TLS；存储时对手机号、身份证做加密（AES-GCM）或令牌化（Tokenization），数据库字段级加密，密钥走KMS托管，业务侧只存token，需要时通过鉴权接口换取明文。
3) 使用与展示：日志、埋点、Prompt、模型上下文里一律脱敏，手机号显示为138****1234，地址只保留到区/街道；训练数据先做去标识化与差分隐私处理，避免模型记忆原始PII。
4) 隔离与审计：敏感数据单独库/单独VPC，访问走审批+最小权限RBAC，全量操作留痕，支持溯源和删除（被遗忘权）。
通俗类比：像医院病历，医生能看但看不到完整身份证号，药房只拿到取药码，所有调阅都有记录。

二、涉黄/涉政拒答，本质是内容安全风控，做'输入-生成-输出'三闸门：
1) 输入侧：用户query先过敏感词库（AC自动机）+ 语义分类模型（涉政、涉黄、暴恐、违禁等），命中高风险直接拒答或转人工，不进入大模型。
2) 生成侧：System Prompt里写死安全边界与拒答话术；对高风险话题用RAG/规则约束，不让模型自由发挥；可用安全对齐（RLHF/DPO）让模型学会拒绝。
3) 输出侧：模型返回后再过一次审核模型（如基于BERT/LLM的审核），命中则替换为统一拒答话术，如'抱歉，这个问题我无法回答'，并记录风险等级。
4) 策略与兜底：分级处置——低风险提示、中风险改写、高风险拒答+告警；建立人工复核与申诉通道，定期更新词库和模型，对抗变体（拼音、谐音、拆字、emoji）。
关键点：拒答要'稳、准、可解释'，宁可误杀不可漏放，但也要控制误伤率，避免正常问题被拒。

**加分点**

1) 提到PII识别不能只靠正则，要正则+NER+上下文，手机号有+86、空格、横线等变体；2) 存储用Tokenization而非单纯加密，因为加密后仍可解密，token化让业务侧拿不到明文，符合'可用不可见'；3) 训练侧提差分隐私/去标识化，防止模型记忆并复现PII，这是很多团队忽略的；4) 内容审核提'输入输出双审+生成侧约束'三层，并强调对抗变体（谐音'政治'、拆字、火星文、base64）；5) 提分级处置和误杀率/漏放率权衡，以及人工复核闭环；6) 可提合规依据：个保法、数安法、生成式AI服务管理暂行办法，涉政涉黄属于违法信息必须拦截。

**雷区**

1) 只答'加密'，忽略脱敏、令牌化、访问控制、审计，认为加密就万事大吉；2) 把敏感信息直接拼进Prompt发给第三方大模型，导致数据出境/泄露；3) 认为敏感词库能解决一切，忽略语义变体和上下文，比如'我想了解某历史事件'被误判；4) 只做输出审核不做输入审核，或只做输入不做输出，漏掉模型自己生成违规内容；5) 拒答话术太生硬或暴露审核规则，被用户绕过；6) 忽略日志和埋点里的PII，日志明文存手机号是常见事故；7) 认为拒答就是简单if-else，没有分级和人工兜底。
