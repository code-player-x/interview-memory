## 1. Agent Infra：如何为海量并发 Agent 提供安全隔离的执行沙箱？

> 原题 ID：`q0116`

**高频程度**：★★★★★

**考察点**：考察海量并发下 Agent 代码执行的隔离与调度设计能力，能否同时讲清『安全隔离防逃逸』和『资源隔离防抢占』两件不同的事，并给出大规模并发的工程取舍。

**回答框架**：

点问题：几千万 Agent 并发跑不可信代码，核心风险是逃逸、资源抢占、横向移动。
隔离层：容器/微 VM（gVisor、Firecracker）做文件系统与进程空间隔离，网络走策略白名单，eBPF 做 syscall 过滤。
资源层：CPU/内存/磁盘配额 + 硬超时，防 fork 炸弹与挖矿。
调度层：沙箱池化预热、毫秒级启停、水平扩展。
审计层：syscall/网络/文件访问全量留痕，可回放取证。
收尾：安全隔离与资源隔离方案不同，不能混为一谈。

**参考回答**：

每个 Agent 的执行（跑代码/读写文件/访问网络）放进独立沙箱：容器/微VM 做资源与文件系统隔离，eBPF/网络策略限制出网，资源配额+超时防滥用，统一调度实现毫秒级启停与水平扩展。

几千万 Agent 并发执行代码，核心风险是『逃逸+资源抢占+横向移动』。工程：① 隔离层用 gVisor/Firecracker 微虚拟机或容器，每个 Agent 独立文件系统与进程空间；② 网络用策略白名单（只允许调指定 API），eBPF 做 syscall 过滤；③ 资源配额(CPU/内存/磁盘)+硬超时，防 fork 炸弹/挖矿；④ 调度层池化预创沙箱，毫秒级复用；⑤ 审计：所有 syscall/网络/文件访问留痕。后端功底是这类系统的基础。

## 2. 什么是SQL注入攻击？如何防止？

> 原题 ID：`q0839`

**高频程度**：★★★★

**考察点**：对 SQL 注入原理与防御体系的系统理解，是否知道参数化查询是根本手段、最小权限是兜底。

**回答框架**：

定义：用户输入被拼进 SQL，被数据库当成代码执行。
危害：拖库、篡改、删除，甚至提权。
第一优先：参数化查询/预编译，让数据永远是数据。
辅助手段：输入校验与白名单、用 ORM 避免手拼、错误信息不外泄。
兜底：数据库最小权限账号、WAF、审计。

**参考回答**：

SQL注入攻击是攻击者在HTTP请求中注入恶意SQL语句，让服务端构造执行SQL语句时，恶意的SQL被一起构造了，然后在数据库中执行，这样就可能对数据库造成大量数据拉取、删除、更新等敏感的操作。

预防SQL注入攻击，可以通过这几个方式：

- 使用参数化查询或预编译语句：使用参数化查询或预编译语句来构建和执行SQL查询。这样可以将用户输入的数据作为参数传递给查询，而不是将其直接拼接到SQL语句中，参数化查询可以防止恶意代码的注入。
- 输入验证和过滤：对用户输入的数据进行验证和过滤，确保只接受合法的输入，可以使用白名单过滤、正则表达式验证或者编码转义等技术来防止恶意代码的注入。
- 最小权限原则：在数据库中为应用程序使用最小权限的数据库账户，这样即使发生SQL注入攻击，攻击者也只能在该账户的权限范围内进行操作，减少损失。

- [实战1：如何用 PREPARE 防止 SQL 注入_SQL 入门教程-慕课网](https://m.imooc.com/wiki/sqlbase-sqlpractice1)

## 3. 为什么大模型 Agent 需要沙箱（Sandbox）？它的威胁模型（Threat Model）包含哪几类？

> 原题 ID：`q1181`

**高频程度**：★★★★★

**考察点**：是否理解 Agent 从『会说』到『能做』后引入的真实副作用，能否讲清沙箱的必要性与两类不可信来源。

**回答框架**：

前提：工具调用=真实副作用，错误会落地成真实后果。
威胁模型两类不可信：模型输出不可信（生成错误甚至恶意代码）、用户输入不可信（直接/间接/隐蔽提示注入）。
三处攻击面：系统命令执行、文件系统读写、网络外传。
第一原则：不信任 + 最小权限，不让模型直接碰生产资源。
结论：让模型能动手，但不能乱动手。

**参考回答**：

工具调用=真实副作用，错误会落地；两类不可信：模型输出 + 用户输入

一旦 Agent 具备工具调用/代码执行能力，它就从'会说话'变成'能行动'，错误会落地成真实副作用。沙箱是把这些动作限制在隔离环境里、控制文件/网络/资源/权限的安全边界。威胁模型分两类不可信来源：①模型输出不可信——LLM 可能生成错误甚至恶意的代码（死循环、删文件、外联）；②用户输入不可信——提示注入（直接/间接/隐蔽）诱导 Agent 越权。攻击面集中在三类：系统命令执行（os/subprocess）、文件系统读写（open）、网络外传（requests/socket）。沙箱第一原则就是'不信任'：不完全信任用户输入、不完全信任模型输出、不让模型直接碰生产资源。一句话：让模型能动手，但不能乱动手。

**常见追问**：间接提示注入（网页/文档里藏指令）你怎么防？沙箱能不能替代权限控制？

## 4. CodeAct（用一段代码表达 Agent 动作）相比 ReAct 有什么优势？它最大的风险是什么，为什么必须配沙箱？

> 原题 ID：`q1187`

**高频程度**：★★★★

**考察点**：对 CodeAct『用代码表达动作』范式的理解，能否讲清优势适用场景与图灵完备代码带来的安全边界问题。

**回答框架**：

讲优势：一段代码比多轮 tool call 更精确高效，适合代码修改、数据处理、文件批量操作、复杂计算。
做定位：CodeAct 是动作表达形式的增强，不是 ReAct 的替代。
最大风险：代码图灵完备，且由不可信的模型生成，能力等同一个坐在终端前的程序员。
必须限制的维度：文件范围、网络权限、系统命令、执行时间、内存、敏感环境变量、危险 API。
生产做法：容器隔离 + 权限 + 超时 + 审计 + 回滚；演示级 exec + SAFE_BUILTINS 远远不够。

**参考回答**：

优势:代码比多轮tool call更精确；适用:代码/数据/文件批量操作

CodeAct 用代码而非多个自然语言 tool call 表达动作——比如批量读日志、统计 ERROR 数，一段 Python 比 list_files/read_file… 多轮调用更精确高效，适合代码修改、数据处理、文件批量操作、复杂计算。但它最大问题是安全：代码是图灵完备的，一旦 Agent 能执行任意代码，能力等同一个坐在终端前的程序员，且模型生成的代码不可信。必须限制：文件访问范围、网络访问权限、系统命令权限、执行时间、内存、敏感环境变量、危险 API。简化演示可用 SAFE_BUILTINS + exec 替换 __builtins__，但生产绝不够——真实要用容器+权限隔离+资源限制+审计日志+回滚。一句话：CodeAct 是动作表达形式的增强，不是 ReAct 的替代；凡用 CodeAct 必配沙箱、权限、超时、审计、回滚，否则风险极大。

**常见追问**：SAFE_BUILTINS 这种 Python 层白名单为什么能被绕过？CodeAct 下怎么做断点续跑与结果回传？

## 5. Agent 沙箱的生命周期怎么管理？为什么强调短生命周期？生产环境如何降启动延迟、防资源泄露？

> 原题 ID：`q1188`

**高频程度**：★★★★

**考察点**：沙箱生命周期与资源治理的工程能力，重点看短生命周期、降启动延迟、防资源泄露三件事。

**回答框架**：

标准流程：按任务创建 → 初始化环境 → 执行 → 净化结果 → 销毁。
为什么短生命周期：最小化状态污染，避免跨用户互相影响。
降启动延迟：常用依赖做成基础镜像/模板，维护一批预热（warm）沙箱池直接复用。
防资源泄露：最大执行时间、最大空闲时间、最大磁盘占用 + 强制回收策略。
长任务：pause/resume 或快照分叉（从同一状态派生多分支试错）。
结论：沙箱难点不在创建，在回收与调度。

**参考回答**：

按任务创建,用完即毁；短生命周期+TTL自动回收

最稳妥：按任务创建临时沙箱→初始化环境→执行→净化结果→销毁。用完即毁可最小化状态污染、避免跨用户影响。短生命周期（TTL）是关键：每个沙箱带超时（如 5 分钟），到期自动回收。生产还要管两件事：①降启动延迟——把常用依赖做成基础镜像/自定义模板，维护一批预热（warm）沙箱池，任务来时直接复用；②防资源泄露——设最大执行时间、最大空闲时间、最大磁盘占用和强制回收策略，高并发下重点在资源调度、状态清理、日志追踪。长任务可用 pause/resume（如 E2B：暂停计费、状态落盘、恢复时文件/进程/变量原样恢复）或快照分叉（从同一状态派生多分支试错）。沙箱不是创建完就完事，麻烦在回收与调度。

**常见追问**：预热池里的沙箱复用给下一个用户前，你如何保证状态被清干净？pause/resume 恢复时哪些状态最容易丢？

## 6. 以 E2B 为例，云端 Agent 沙箱如何实现隔离、执行和暂停恢复？

> 原题 ID：`q1191`

**高频程度**：★★★

**考察点**：区分隔离底座、执行接口、调度和持久化，并明确产品实现的版本边界。

**回答框架**：

1) microVM 隔离
2) 命令与代码执行接口
3) 调度和资源控制
4) 快照恢复的边界

**参考回答**：

云端 Agent 沙箱把文件、进程、命令与网络包装成有生命周期的远程执行环境。E2B 的公开架构采用 Firecracker microVM：通过虚拟化提供独立 guest 内核与内存隔离，同时由宿主控制网络、资源配额和镜像。

沙箱内的执行代理负责命令和文件接口；有状态的代码解释器还可接入相应语言运行时。具体是否使用 Jupyter、哪些语言可用，属于某个镜像或代码执行产品的实现，不能推断所有沙箱共享一套固定内核协议。

暂停恢复可保存受支持的内存和文件系统状态，但外部连接、远程凭证与第三方状态未必仍有效，恢复后需重连和校验。启动时延、保留时长与计费取决于版本、资源和服务条款，不使用固定数字代表普遍保证。

## 7. 密钥/凭证为什么不能暴露给沙箱？正确做法是什么？

> 原题 ID：`q1192`

**高频程度**：★★★★★

**考察点**：密钥管理意识，能否说清『密钥不入沙箱』与『服务端代理调用』的具体落地方式。

**回答框架**：

先讲危险：不可信代码可读环境变量/文件（如 $AWS_SECRET_ACCESS_KEY、/etc/passwd）并外传，这是 Code Interpreter 类事故的根源。
原则一：真实密钥绝不进沙箱，只给短期、低权限、范围受限的凭证，用完即废。
原则二：高权限操作由服务端代理，沙箱只发『意图』，代理用真实密钥调下游再把结果回传。
配套：代理层记录来源/参数/额度，做调用审计与配额控制。
兜底：默认断网或网络白名单，即使凭证泄露也传不出去。
一句话：沙箱里能看到的凭据，应是『刚好够这次任务、过期即失效、且能被审计』的最小集。

**参考回答**：

绝不暴露真实密钥进沙箱；沙箱只拿短时效低权限凭证

绝不能把真实密钥以环境变量或文件形式暴露给沙箱——否则模型生成的不可信代码可能读取 $AWS_SECRET_ACCESS_KEY、/etc/passwd 并外传，这是 Code Interpreter 类事故的根源。正确做法：①密钥不进沙箱——沙箱只拿到短期、低权限、范围受限的凭证（short-lived token），用完即废；②服务端代理调用——高权限操作由服务端代理完成，沙箱只发'意图'，代理用真实密钥调下游，结果回传沙箱；③调用审计——代理层记录每次调用的来源、参数、额度；④额度控制——限制 token/调用次数/金额，防滥用；⑤网络默认断网或白名单，即使凭证泄露也外传不出去。一句话：沙箱里能看到的凭据，应该是'刚好够这次任务、过期即失效、且能被审计'的最小集，而不是生产环境的万能钥匙。

**常见追问**：短期 token 的获取动作本身怎么鉴权，会不会变成新的信任问题？代理层怎么防重放和越权？

## 10. 如何防止 Agent 工具调用陷入死循环、或产生破坏性操作（删库/外发/写生产）？

> 原题 ID：`q1198`

**高频程度**：★★★★

**考察点**：对 Agent 失控两类表现（死循环、破坏性操作）的工程防护，能否与工具白名单形成互补视角。

**回答框架**：

防死循环：最大步数/最大工具调用次数上限、重复动作 hash 去重、调用图环检测、超时。
防破坏：危险工具标 high-risk 强制确认或 dry-run、沙箱默认无写权限与无外网、操作前 diff 预览。
讲清关系：白名单管『能调什么』，这一层管『调多了、调危险了怎么办』。
收尾：闸门要放在执行层，不能靠 prompt 让模型自觉。

## 18. 定义权限控制和沙箱场景（这个 Agent 能不能删库？能不能访问敏感数据？）？

> 原题 ID：`q2871`

**高频程度**：★★★★

**考察点**：能否清晰区分『权限控制（授权决策）』与『沙箱（强制隔离）』两个安全层次，并落到 Agent 场景的具体判断。

**回答框架**：

定义区分：权限控制回答『有没有资格做』，沙箱回答『即使乱来最多造成多大破坏』。
权限模型：ACL/RBAC/ABAC，最小权限、默认拒绝、职责分离。
沙箱手段：namespace/cgroup/seccomp、gVisor、Firecracker、WASM。
回到题目：能不能删库 = 账号权限 + 是否只读副本/临时快照；能不能访问敏感数据 = 数据视图 + 网络策略。
分层落地：身份与凭证 → 策略层（RBAC/ABAC/OPA）→ 执行沙箱 → 审计与熔断。

**参考回答**：

权限控制是给Agent划定“能做什么”的规则，沙箱是给Agent一个“只能在这里做”的隔离环境；前者管授权，后者管隔离，二者结合才能回答“能不能删库、能不能访问敏感数据”。

权限控制（Authorization/Permission Control）回答的是“这个主体有没有资格执行某个操作”，核心是主体、资源、动作、条件四要素，常见模型有 ACL、RBAC、ABAC。沙箱（Sandbox）回答的是“即使它想乱来，最多能造成多大破坏”，通过进程隔离、文件系统隔离、网络隔离、系统调用过滤等手段，把 Agent 限制在一个受控边界内。

通俗类比：权限控制像公司门禁卡，决定你能不能进财务室；沙箱像把员工关在一间没有窗户、没有外网、只有指定工具的房间里办公。门禁卡可能被伪造或提权，所以还需要房间本身足够坚固。

回到面试题：Agent 能不能删库？如果它的数据库账号只有 SELECT 权限，就不能删；如果它运行在只读副本或临时快照上，即使执行 DROP 也影响不到生产库。能不能访问敏感数据？如果权限系统只给它脱敏后的视图，或者沙箱网络策略禁止它访问敏感数据服务，就访问不到。

工程上通常分层：1）身份与凭证：给 Agent 独立的 service account，最小权限；2）策略层：用 RBAC/ABAC 或 OPA 做细粒度授权，按用户、任务、数据分级动态判定；3）执行层：容器/微虚拟机/gVisor 做沙箱，限制文件、网络、系统调用；4）审计与熔断：记录所有工具调用，危险操作二次确认或人工审批。

适用场景：低风险只读查询可以放宽沙箱、用权限控制即可；高风险写操作、访问 PII、执行任意代码，必须权限最小化加沙箱隔离，甚至人工在环。

**常见追问**：能力（capability）模型相比 RBAC 在 Agent 场景的优势是什么？只读账号是不是就绝对安全？

核心思路是分层决策：第一层是确定性的关键词/正则/意图分类器，命中高风险词表（如“推荐股票”“保本收益”“贷款”“转账”）时直接短路，强制调用合规检查工具，绕过LLM的自由裁量；第二层是LLM推理，负责理解用户真实意图、消歧、在多工具间做选择与参数填充。为什么这么设计：LLM有概率性、可能被提示注入绕过、对高风险场景漏判代价极高；而纯规则又太脆、无法覆盖长尾表达。所以用规则保底（高召回、可审计、低延迟），用LLM提体验（高精度、泛化好）。类比：机场安检，金属探测门是规则（必过、强制），人工开箱检查是LLM（灵活判断），但危险品清单是硬性触发。工程上通常实现为：前置规则网关 -> 命中则走强制合规链路 -> 未命中则进入LLM function calling/ReAct循环 -> 工具执行前再过一次输出侧合规校验（双层防护）。适用场景：金融、医疗、法律、未成年人保护等强监管领域。

**常见追问**：纯关键词会被谐音/拼音/拆字绕过，你怎么补？正常讨论『股票』的用户被误伤怎么处理？

## 21. OAuth 2.0 授权码流程如何工作？PKCE 和客户端类型分别影响什么？

> 原题 ID：`q3331`

**高频程度**：★★★

**考察点**：授权与身份认证的区别、后通道换 token、PKCE 和秘密的保存边界。

**回答框架**：

1) 授权请求与回调 code
2) token endpoint 换取 token
3) 机密与公共客户端
4) PKCE、回调校验和 CSRF 防护

**参考回答**：

客户端把用户引导到授权服务器，携带 client_id、redirect_uri、scope 等参数；使用 PKCE 时发送 code_challenge。用户完成授权后，服务器向已登记的回调地址返回短期授权码。客户端再到 token endpoint 提交 code、相应 redirect_uri 和 code_verifier，验证通过后获得 token。授权码一次性使用，并绑定客户端与回调。

机密客户端可以在后端安全保存 client_secret 或使用其他客户端认证方式；SPA、原生应用等公共客户端不能把内置 secret 当成可信秘密。PKCE 将兑换动作绑定到发起请求的一方，公共客户端必须采用，机密客户端也推荐采用。还要使用 TLS、严格校验回调 URI，并通过正确的 state/PKCE 等机制防止 CSRF。

授权码流程避免在授权响应里直接返回 access token，但不意味着所有 token 必须永远留在后端；公共客户端也可能持有 token。若要让浏览器只持有站点会话，可采用后端代管 token 的 BFF 架构。

OAuth 解决授权，不直接定义用户登录身份；身份认证通常使用 OIDC。微信小程序 code2Session 有自己的协议，不能直接充当标准 OAuth 授权码流程的完整说明。

**常见追问**：PKCE 为什么不能代替机密客户端的身份认证，也不能消除 XSS 风险？

**核验资料**：[OAuth 2.0 RFC 6749](https://www.rfc-editor.org/rfc/rfc6749.html)；[OAuth Security BCP RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)

## 22. OAuth 相比直接传递凭证有哪些安全优势？

> 原题 ID：`q3332`

**高频程度**：★★★★

**考察点**：对 OAuth 核心价值（用令牌代替凭证、最小权限、可撤销可审计）的理解，能否区分授权与认证。

**回答框架**：

定义：让第三方应用在用户不交出密码的前提下，有限地访问用户在某个服务上的资源。
类比房卡：只开你房间、当天有效、丢了能立刻注销。
优势一：前端/第三方从头到尾看不到密码，被攻破泄露的也只是 token，用户改密码不波及其他站点。
优势二：令牌是短期、有 scope 的凭证，可过期、可刷新、可随时撤销。
优势三：最小权限 + 四角色解耦 + 标准化，适配 Web/移动端/服务端/IoT，便于做 SSO。
优势四：授权服务器统一记录授权行为，可审计可风控。
补充：OAuth 是授权框架，认证要用 OIDC 在其上加 id_token；授权码 + PKCE 优于隐式模式。

**参考回答**：

OAuth 的关键优势是第三方应用不必直接收集和保存用户密码；用户在授权服务器完成认证后，客户端获得受范围、有效期和撤销机制约束的 access token，必要时使用 refresh token。它并不意味着“没人看到凭证”：token 本身通常是高价值 bearer credential。

实现要保护 redirect URI、state/PKCE、scope、token 的安全存储、传输和轮换，并处理过期与撤销。Web 客户端还需结合 XSS/CSRF 威胁模型选择存放方式，不能把 OAuth 当作自动解决全部身份安全问题的协议。

**常见追问**：为什么 access token 泄露后，即使用户密码未泄露，仍可能造成严重风险？

## 23. 如何对手机号、地址等低熵 PII 建立可查询且可轮换的安全索引？

> 原题 ID：`q3634`

**高频程度**：★★★★★

**考察点**：客户敏感信息的全生命周期治理能力，覆盖收集、传输、存储、展示、使用、日志与生命周期管理。

**回答框架**：

总原则：最小化收集、加密存储、脱敏展示、受控访问、可审计、可删除。
收集：只收业务必需字段，明确告知用途并取得授权，能用哈希就不存明文。
传输：全链路 HTTPS/TLS，敏感信息不进 URL query。
存储：字段级加密（优先 AES-256-GCM 等 AEAD），密钥放 KMS 不跟数据同库；需等值查询用『确定性哈希/blind index + 密文』两列。
展示：手机号 138****1234、地址只到区/街道，前端、接口、导出文件都要脱敏。
使用与访问：RBAC/ABAC 最小权限，服务间调用用服务身份，测试环境禁止用生产真实数据。
日志与监控：禁止打印完整敏感信息，框架层统一脱敏，对批量导出与异常访问告警。
生命周期：设保留期限，到期删除或匿名化，支持注销、撤回授权、数据可携带。

**参考回答**：

手机号、身份证号、地址等低熵 PII 不适合直接用裸确定性 hash 做查询索引，因为攻击者可以枚举候选值并反查 hash。需要等值查询时，可在受保护密钥下计算 HMAC 或 pepper 参与的 blind index，并把密钥版本与索引记录在案。

密文或原始 PII 应与索引分离存放，访问受最小权限、审计和脱敏控制；密钥轮换时支持新旧索引并存和渐进回填。模糊查询、去重与统计还需要单独评估泄露面，不能靠一个 hash 解决所有隐私需求。

**常见追问**：为什么对低熵手机号做 SHA-256 后仍容易被离线枚举？

## 25. 大模型沙箱和普通的 Docker 容器是一回事吗？沙箱到底是一个技术点还是一整条链路？

> 原题 ID：`q1182`

**高频程度**：★★★

**考察点**：考察把沙箱理解为六层安全执行链路而非单一容器技术。

**回答框架**：

①结论：不是一回事，Docker 只是隔离执行层的一种实现。②六层链路：入口层、模型决策层、策略护栏层、沙箱管理层、隔离执行层、结果层。③额外职责：工具白名单、参数校验、网络策略、密钥代理、输出脱敏、全链路审计。④表述：面试要答「链路」而不是「我用了容器」，并讲清失败回收与降级。

**参考回答**：

不是一回事。Docker 容器只是「隔离执行层」的一种实现方式，大模型沙箱远不止于此，它是一整条安全执行链路。完整链路至少包含六层：第一，入口层，做鉴权、限流和输入清洗；第二，模型决策层，理解任务并生成工具调用意图；第三，策略护栏层，判断这次调用是否安全、是否命中白名单和权限；第四，沙箱管理层，负责创建隔离环境、分配资源、挂载必要的文件；第五，隔离执行层，真正运行代码或工具，这才是 Docker、namespace 等技术发挥作用的层；第六，结果层，做输出过滤、日志审计和 Trace 回放。所以容器只解决了「隔离执行」这一个点，而大模型沙箱还要额外管工具白名单、参数校验、网络策略、密钥代理、输出脱敏和全链路审计。面试时抓住一句话总结：沙箱不是「我用了容器」，而是能讲清楚模型怎么发起调用、应用层怎么校验、沙箱怎么创建、权限怎么限制、结果怎么过滤、日志怎么审计、失败怎么回收。答成一条链路而不是一个技术点，才是这道题的关键，同时要主动补充失败回收与降级策略。

**常见追问**：密钥代理为什么要单独做一层？沙箱执行失败时怎么回收资源和补偿副作用？

## 26. 生产级沙箱如何做'四层隔离'（文件 / 网络 / 命令 / 权限）？每一层对应的底层技术是什么？

> 原题 ID：`q1184`

**高频程度**：★★★

**考察点**：考察 Linux namespace、seccomp、capability drop 等底层隔离技术。

**回答框架**：

①文件隔离：OverlayFS 临时可写层加 Mount Namespace，只读根文件系统加 tmpfs。②网络隔离：Network Namespace 或 eBPF 出站白名单，默认断网并阻断云元数据地址。③命令隔离：Seccomp-BPF 限制 syscall 白名单，AppArmor/SELinux 定义行为轮廓。④权限隔离：User Namespace 做 UID 映射，非 root 运行加 NoNewPrivs 防提权。

**参考回答**：

四层隔离是面试高频框架。第一，文件隔离：让 Agent 只能看到虚拟出来的临时工作空间。技术是 OverlayFS 提供临时可写层配合 Mount Namespace 阻断文件系统视线，把根文件系统设为只读（--read-only），只在 /tmp 挂 tmpfs 作为临时可写区，挂载业务文件时只用只读方式挂必要文件，防止容器里读到 .env、SSH 密钥或数据库凭证。第二，网络隔离：默认断网（Air-Gapped），只在白名单内的域名和端口放行。技术是 Network Namespace 或 eBPF 做出口白名单，禁用原始套接字，并显式阻断内网地址和云元数据服务地址（169.254.169.254），防止 Agent 通过 curl 外传数据或窃取云凭证。第三，命令与系统调用隔离：禁止 mount、ptrace、reboot 等敏感调用。技术是 Seccomp-BPF 配置 syscall 白名单，配合 AppArmor 或 SELinux 定义进程行为轮廓。第四，权限隔离：进程永远以非 root 的随机 UID 运行、没有 sudo。技术是 User Namespace 做 UID 映射（容器内 root 映射到宿主机的普通用户），加上 NoNewPrivs 标志防止通过 setuid 提权。整体本质是 Linux namespace 加 cgroup 加 seccomp 加 capability drop 的组合拳，cgroup 负责资源限制、namespace 负责视图隔离、seccomp 负责系统调用收敛、capability 负责特权收敛。

**常见追问**：为什么必须阻断 169.254.169.254？User Namespace 的 UID 映射怎么防提权？

## 27. 用 Docker 跑 Agent 代码沙箱，生产级该配哪些参数？每个参数分别防什么？

> 原题 ID：`q1185`

**高频程度**：★★★

**考察点**：考察 Docker 运行沙箱的关键安全参数及其防护目标。

**回答框架**：

①典型组合：--rm --read-only --tmpfs --memory --cpus --network none --pids-limit --cap-drop ALL，只读挂载脚本。②文件：--read-only 防环境被破坏，--tmpfs 保可用。③网络：--network none 物理隔离，防数据外泄。④资源与权限：--cap-drop ALL 去特权，--memory 与 --cpus 防资源爆炸，--pids-limit 防 fork 炸弹。

**参考回答**：

典型严格受限的启动命令是：docker run --rm --read-only --tmpfs /tmp:rw,size=100M --memory=512m --cpus=0.5 --network none --pids-limit 32 --cap-drop ALL，把脚本以只读形式挂载进去执行。各参数对应防的东西是：--read-only 让根文件系统只读，防止容器内的代码污染或永久破坏运行环境，配合 --tmpfs 只开放 /tmp 可写，在安全与可用之间取平衡；--network none 做物理层面的网络隔离，是防数据外泄最关键的一刀，即使 Agent 执行了 curl evil.com 也连不上；--cap-drop ALL 丢弃所有 Linux 特权能力，防止提权操作；--memory 和 --cpus 限制 CPU 与内存，防止代码吃满资源把宿主机拖垮或触发 OOM；--pids-limit 限制进程数，防止 fork 炸弹把宿主机进程表打满；--rm 保证执行完自动清理，避免残留；挂载使用只读（:ro）且只挂必要文件，防止脚本读到 .env、SSH 私钥或数据库配置。这套参数背后对应的是 Linux 内核的安全机制（namespace、cgroup、capability、seccomp），面试常追问「如何防外连」和「如何防 fork 恶意子进程」，标准答法就是 --network none 和 --pids-limit，再叠加 seccomp 限制系统调用会更严格。

**常见追问**：只做这些 Docker 参数够安全吗，还需要补什么？挂载目录为什么必须用只读？

## 28. 大模型流式返回组件/工具协议（如自定义 JSON/DSL）可能未闭合或非法，前端如何做沙盒隔离，防止整个页面白屏崩溃？

> 原题 ID：`q1194`

**高频程度**：★★★

**考察点**：考察前端流式协议容错解析与隔离渲染方案。

**回答框架**：

**参考回答**：

流式协议的半段 JSON/DSL 不能靠“补一个括号再直接解析”来修复并执行。前端应把流按 framing 协议或增量 parser 缓冲，只有在确认一个完整 payload、长度和类型都通过 Schema 校验后，才进入渲染或工具调用路径；不完整内容只做安全文本展示或等待后续片段。

渲染层应使用组件白名单、受限属性、错误边界和资源限额，未知/非法消息进入可观测的错误或降级状态，不能让任意模型输出执行脚本或导致整页崩溃。对工具动作还应在服务端再次做权限和语义校验。

## 31. 多个 Agent 执行者之间如何做资源与权限隔离？

> 原题 ID：`q2979`

**高频程度**：★★★

**考察点**：考察对「老王点点头：“执行者之间的隔离怎么做的」的掌握，重点看能否讲清：‘执行者’可以理解为真正干活的单元：进程、线程、协程、容器、沙箱、Worker、Actor 等

**回答框架**：

‘执行者’可以理解为真正干活的单元：进程、线程、协程、容器、沙箱、Worker、Actor 等；隔离要回答的是：A 执行者崩了/被攻击/占满资源时，B 执行者能不能不受影响；原理上分几层：；1) 地址空间隔离：进程有独立虚拟地址空间（页表），一个进程不能直接读写另一个进程内存；线程共享地址空间，所以线程隔离弱，需要靠 TLS、锁、不可变数据来约束；2) 资源隔离：CPU（cgroup cpu quota、nice）、内存（cgroup memory limit、RSS 限制）、IO（io.max）、文件描述符、网络端口、磁盘配额

**参考回答**：

执行者隔离的核心是让每个执行者拥有独立的资源边界（进程/线程/容器/沙箱）与独立的上下文（内存、文件描述符、权限、状态），通过操作系统或运行时提供的机制实现互不干扰。

‘执行者’可以理解为真正干活的单元：进程、线程、协程、容器、沙箱、Worker、Actor 等。隔离要回答的是：A 执行者崩了/被攻击/占满资源时，B 执行者能不能不受影响。 原理上分几层： 1) 地址空间隔离：进程有独立虚拟地址空间（页表），一个进程不能直接读写另一个进程内存；线程共享地址空间，所以线程隔离弱，需要靠 TLS、锁、不可变数据来约束。 2) 资源隔离：CPU（cgroup cpu quota、nice）、内存（cgroup memory limit、RSS 限制）、IO（io.max）、文件描述符、网络端口、磁盘配额。 3) 权限隔离：Linux 的 uid/gid、capabilities、seccomp 过滤系统调用、SELinux/AppArmor 强制访问控制。 4) 命名空间隔离：namespace 提供 PID、NET、MNT、UTS、IPC、USER 等视图隔离，容器就是 namespace + cgroup + rootfs 的组合。 5) 故障隔离：独立进程/容器，崩溃只影响自身；配合 supervisor 重启、熔断、舱壁模式（bulkhead）。 6) 状态隔离：每个执行者有自己的上下文（请求上下文、事务、会话），避免共享可变全局状态。 通俗类比：一栋大楼里，进程隔离像每人一间独立办公室（墙+门锁），线程隔离像同一间大办公室里的工位（共享空间，靠规矩）；容器像带独立水电表的公寓；沙箱像给小孩玩的围栏，限制能碰的东西。 适用场景：多租户 SaaS 用容器/沙箱隔离租户；浏览器用多进程隔离不同 tab；AI Agent 里每个工具执行器用独立进程/容器，防止一个工具把主进程搞挂；FaaS 用 microVM（Firecracker）做强隔离。

**常见追问**：如何避免「1) 把‘隔离’等同于‘加锁’：锁解决并发正确性，不解决故障和资源隔离」？ 「2) 认为线程之间天然隔离：线程共享堆和文件描述符，一个线程崩溃可能带走整个进程」在真实项目中应如何规避？

## 35. 正则判断为低风险，大模型判断为高风险，最后使用哪个结果？

> 原题 ID：`q3984`

**高频程度**：★★★

**考察点**：正则判断为低风险，大模型判断为高风险，最后使用哪个结。

**回答框架**：

1) 这类“规则/正则 vs 大模型”冲突时，不能简单二选一，应按业务风险策略做仲裁：安全场景通常采用“就高不就低”的保守合并，即大模型高风险优先，再结合置信度、证据和人工复核
2) 正则和 LLM 不是同一层面的判断器
3) 正则基于确定性的模式匹配，优点是精确、可解释、低延迟，缺点是只能覆盖已知模式，遇到变体、谐音、上下文语义、跨句意图就容易漏判
4) 大模型基于语义和上下文理解，优点是泛化强，能发现正则没写到的风险，缺点是可能幻觉、误报、不稳定、成本高
5) 因此当“正则低风险、大模型高风险”冲突时，核心不是问谁更准，而是问业务对漏判和误报的容忍度

**参考回答**：

这类“规则/正则 vs 大模型”冲突时，不能简单二选一，应按业务风险策略做仲裁：安全场景通常采用“就高不就低”的保守合并，即大模型高风险优先，再结合置信度、证据和人工复核。

正则和 LLM 不是同一层面的判断器。正则基于确定性的模式匹配，优点是精确、可解释、低延迟，缺点是只能覆盖已知模式，遇到变体、谐音、上下文语义、跨句意图就容易漏判；大模型基于语义和上下文理解，优点是泛化强，能发现正则没写到的风险，缺点是可能幻觉、误报、不稳定、成本高。

因此当“正则低风险、大模型高风险”冲突时，核心不是问谁更准，而是问业务对漏判和误报的容忍度。用通俗类比：正则像门口保安拿着黑名单核对身份证，大模型像经验丰富的侦探看行为举止。保安说“名单里没有他”，侦探说“他行为很可疑”。如果这是银行金库门口，你显然不能因为保安说没在名单里就放行，而应先把人拦下复核。

工程上常见策略：
1. 安全/风控/内容审核等高风险场景：采用保守合并，任一高风险即高风险，即 final = regex_high OR llm_high，冲突时以高风险为准，并进入人工复核或二次模型复核。
2. 普通场景：可做加权投票或分级：正则命中高危规则直接拦截；正则低风险但 LLM 高风险时，标记为“疑似高风险”，走人工/二次确认，而不是直接放行。
3. 若 LLM 高风险但置信度低、且正则规则强匹配低风险，可降级为“中风险”并抽样复核，但要有监控和回滚。
4. 最终结果最好不是二值，而是风险分/风险等级 + 证据 + 处置动作：放行、打标、限流、人工审核、拦截。

所以标准答案：默认以高风险结果为准，尤其是安全场景；但生产系统应做仲裁层，而不是让两个判断器直接覆盖。

## 39. Web 应用如何实现 OAuth 登录并处理回调、状态校验与令牌安全？

> 原题 ID：`q3351`

**考察点**：考察对「你的微信OAuth登陆怎么做的 √」的掌握，重点看能否讲清：整体分四步

**回答框架**：

整体分四步；1）引导授权：前端拼接 https://open.weixin.qq.com/connect/oauth2/authorize?appid=APPID&redirect_uri=回调地址&response_type=code&scope=snsapi_base或snsapi_userinfo&state=随机串#wechat_redirect，跳转后用户在微信内确认授权；scope 决定能否拿到用户信息：snsapi_base 静默授权只给 openid，snsapi_userinfo 会弹确认框，可再拉昵称头像；2）回调拿 code：微信重定向回 redirect_uri 并带上 code 和 state；后端必须校验 state 与本次会话绑定，防 CSRF；code 只能用一次、5 分钟过期

**参考回答**：

微信 OAuth 登录本质是标准 OAuth2 授权码模式：前端引导用户到微信授权页拿 code，后端用 code + AppSecret 换 access_token 和 openid，再签发自己的登录态。

## 40. 什么是数据主权？它与数据本地化、数据驻留和隐私保护有何区别？

> 原题 ID：`q3119`

**高频程度**：★★★

**考察点**：考察跨区域数据治理中数据主权、数据驻留、本地化、隐私和访问控制的边界。

**回答框架**：

区域化部署：按司法辖区划分独立Region/租户，数据平面本地化，控制平面可集中但只传元数据。；数据分类分级：识别主权敏感数据（个人信息、重要数据、国家秘密），做流转地图。；加密与密钥主权：密钥由本地KMS/HSM管理，云厂商不可见，避免“数据在境内但密钥在境外”。；合同与法律：SCC、数据出境安全评估、标准合同备案。；技术审计：数据血缘、跨境访问日志、最小权限。

**参考回答**：

数据主权讨论的是：数据的存放、访问、处理和跨境传输会受到相关司法辖区法律、合同和监管要求的约束。它不是单一技术属性，具体义务必须结合数据类型、主体、地区和当前法规由合规/法务确认。

它与几个相近概念不同：数据驻留（data residency）强调数据实际存放在哪个区域；数据本地化（data localization）是某些场景下要求在特定区域存储或处理的规则；隐私保护关注个人信息的合法、透明、最小化处理与主体权利。它们可能重叠，但不能互相替代。

工程上应维护数据分类和流转图，按区域与租户隔离数据平面，实施最小权限、加密与密钥管理、跨境访问审计、保留/删除策略和供应商评估。面对跨境、重要数据或敏感个人信息的实际场景，应先确定适用地区和业务事实，再走正式合规评审，而不是从一条通用面试答案推导法律结论。

**常见追问**：为什么“数据存放在某区域”不自动等于满足该区域所有的数据访问与跨境合规要求？
