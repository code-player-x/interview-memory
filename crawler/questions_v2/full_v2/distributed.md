## 1. 一致性哈希算法原理是什么？在分布式(如向量库/缓存分片)里怎么用？

> 原题 ID：`q0061`

**高频程度**：★★★★★

**考察点**：考察环映射、少量迁移与虚拟节点解决数据倾斜的原理。

**回答框架**：

①原理：节点和 key 都映射到 0 到 2^32 的环上，key 顺时针找到第一个节点归属。②优势：增删节点只影响相邻区间的少量 key，迁移量约 1/N，而非全量 rehash。③问题：节点少时分布不均产生数据倾斜。④解法：虚拟节点，每个物理节点在环上映射多个点，平滑负载并支持加权。

**参考回答**：

一致性哈希把节点和 key 都映射到同一个哈希环上（范围 0 到 2^32），key 沿环顺时针找到的第一个节点就归属于它。它的核心价值在于解决传统「hash 取模 N」的扩容雪崩问题：普通取模在节点数量变化时，几乎所有 key 都要重新映射，缓存场景下会造成大面积失效和回源雪崩；一致性哈希在增加或删除节点时，只影响环上相邻区间的少量 key，迁移量大约是 1/N。原始版本的问题是节点较少时在环上分布不均，导致大量 key 集中到某几个节点形成热点，解决办法是引入虚拟节点，让每个物理节点在环上映射成几十到几百个虚拟点，key 命中虚拟点后再归属到对应物理节点，从而让负载更均匀；虚拟节点还便于按机器性能做加权。典型应用是缓存分片（Redis Cluster 的思路是 16384 个槽位而非纯环）、向量库分片、以及负载均衡和分库分表的路由。

**常见追问**：为什么虚拟节点能解决倾斜？扩容时如何避免瞬时大量 cache miss？

## 2. 请详细讲解分布式令牌桶限流的实现？

> 原题 ID：`q0083`

**高频程度**：★★★★

**考察点**：考察令牌桶在分布式环境下的原子实现与时钟问题。

**回答框架**：

①单机模型：桶容量 capacity 加补充速率 rate，按时间匀速补令牌，请求取令牌。②分布式方案：Redis 存令牌数与上次时间，用 Lua 脚本原子完成 refill、判断、扣减、返回。③替代：各节点本地桶加中心配额（放宽精度换吞吐）。④关键点：服务器单调时钟、Lua 保原子、限流维度可组合（IP/用户/接口）。

**参考回答**：

令牌桶模型是容量 capacity 加补充速率 rate：桶按固定速率匀速补充令牌，最多补到 capacity；每个请求到达时先尝试取一个令牌，取到就放行，取不到就拒绝或排队。单机实现很简单，关键在分布式。分布式主流做法是把令牌数和上次刷新时间存在 Redis 里，用一个 Lua 脚本原子地完成四步：读取上次时间和当前令牌数，按经过的时间计算本次应补充的令牌数（不超过容量），判断是否够扣，够则扣减并返回剩余令牌和放行信号，整个过程在 Redis 单线程内原子执行，避免「先读后写」的竞态导致超发。另一种方案是各节点维护本地桶加中心化配额分配，精度略低但吞吐更高，适合超高并发场景；也可以用 Redis 加滑动窗口或漏桶实现。要点有三个：时间基准要用服务器单调时钟，避免客户端时钟漂移；必须用 Lua 保证原子性；限流维度可以组合，按 IP、用户、接口、租户等维度分别建 key。取舍上，网关层限流统一但可能成为瓶颈，应用层限流灵活但要处理分布式一致性。

**常见追问**：Lua 脚本里怎么算 refill？为什么不能直接 setnx 加 expire 两步做限流？

## 3. 同一工具因超时被重复调用，怎么避免重复执行高风险操作？大量 Agent 任务并发调大模型怎么做限流？

> 原题 ID：`q161`

**高频程度**：★★★★

**考察点**：考察幂等键防重复副作用与多维度并发限流的组合。

**回答框架**：

①防重复：每次工具调用生成幂等键（task_id+step+tool），写入分布式锁或去重表占位。②重试语义：超时重试携带同一幂等键，服务端已执行则返回原结果。③并发限流：对 LLM 供应商设全局令牌桶或信号量控制 QPS 与并发数。④配额与优先级：按模型分组配额、任务入队排队、关键任务高优先级并加退避熔断。

**参考回答**：

防重复执行的关键是幂等键。客户端对每一次工具调用生成一个幂等键（如 task_id 加 step 加 tool 的哈希），调用前先写入分布式锁或去重表占位；如果超时重试，必须携带同一个幂等键，服务端先查该键是否已有执行记录，已执行则直接返回原结果而不重复执行业务逻辑，尤其对转账、删除、发消息这类写操作必须有这层保护，否则重试会带来真实的副作用。并发限流对 LLM 要分维度做：一是对 LLM 供应商设全局令牌桶或信号量，同时控制 QPS 和「在飞并发数」（加信号量而不只是 QPS，因为长请求会打满连接池）；二是按模型分组配额，不同模型费率与限速不同；三是任务先入队列，超过阈值就排队，关键任务走高优先级队列避免被批处理饿死；四是配合指数退避加抖动的重试与熔断，避免上游 429 时疯狂重试形成重试风暴把配额打满。

## 4. 如何设计一个分布式ID？

> 原题 ID：`q0173`

**高频程度**：★★★★★

**考察点**：考察分布式 ID 各方案的取舍、雪花算法结构与时钟回拨应对。

**回答框架**：

①要求：全局唯一、趋势递增、高性能、高可用。②方案：UUID、数据库自增、Redis INCR、雪花算法、号段模式。③雪花结构：1 位符号加 41 位毫秒加 10 位机器加 12 位序列，每毫秒每节点 4096 个。④问题：强依赖时钟，回拨会重复或不可用，需等待、备用位或 Leaf-snowflake 方案。

**参考回答**：

分布式 ID 的基本要求是全局唯一、趋势递增、高性能、高可用。常见方案对比：UUID 简单且全球唯一，但无序、字符串存储查询效率低、占空间大，不适合做主键；数据库自增 ID 简单但存在单点和性能瓶颈；Redis 用 INCR 和 INCRBY 生成，单线程保证原子，集群可以初始化不同起始值加固定步长（如 5 台分别从 1 到 5 开始、步长 5）来并行发号，但引入新组件且步长和初始值事先固定难以修改；雪花算法生成 int64，结构是 1 位符号位固定为 0、41 位毫秒时间戳、10 位机器 ID（5 位数据中心加 5 位机器）、12 位毫秒内序列号，即每毫秒每节点可产生 4096 个 ID，优点是时间戳在高位、序列在低位，整体趋势递增，不依赖第三方系统、性能高、bit 位可灵活分配，缺点是强依赖机器时钟，时钟回拨会导致 ID 重复或服务不可用；美团 Leaf 有两个实现，Leaf-segment 用数据库批量取号段（如一次取 1 到 10000）在本地内存发号，并采用双 buffer 机制，当前号段消耗到 10% 就异步预取下一段，保证始终有两个号段缓存，即使 DB 宕机也能持续发号 10 到 20 分钟，缺点是不够随机、会泄露发号量，Leaf-snowflake 沿用雪花结构但用 ZooKeeper 顺序节点分配 workerId，并在本机缓存 workerId 文件，对 ZK 是弱依赖。互联网上主流选择是雪花算法加号段模式。

**常见追问**：雪花算法时钟回拨具体怎么处理？Leaf 的双 buffer 为什么要在 10% 时预取？

## 5. 什么是分布式锁？

> 原题 ID：`q0436`

**高频程度**：★★★★★

**考察点**：考察分布式锁的定义与实现方案选型。

**回答框架**：

①定义：控制分布式系统之间同步访问共享资源的一种方式。②对比单机：单机用 synchronized 或 ReentrantLock 保证同一时刻只有一个线程执行。③实现方案：Redis SET NX、ZooKeeper 临时顺序节点、数据库唯一约束、Redlock、续期。④选型：强一致用 ZK，高并发简单场景用 Redis。

**参考回答**：

分布式锁是控制分布式系统之间同步访问共享资源的一种方式。在单机或单进程环境下，多线程并发时用锁保证一个代码块同一时刻只被一个线程执行，比如 Java 的 synchronized 和 ReentrantLock；但服务部署到多台机器后，这些进程内的锁失效，需要一把跨进程、跨机器的锁来保证互斥。常见实现有三种：Redis 用 SET NX 加过期时间（简单快，但要注意锁过期、误删和续期问题，多实例可靠性可用 Redlock）；ZooKeeper 用临时顺序节点（可靠、可重入、客户端断开后自动释放，适合强一致场景，但性能不如 Redis）；数据库用唯一约束或 select for update（实现简单但性能差、易成为瓶颈）。选型原则是：要求强一致、可重入、自动释放用 ZooKeeper；追求高并发、实现简单用 Redis；数据库方案只适合并发很低或临时救急。

**常见追问**：Redlock 真的能保证安全吗，业界的争议点在哪？ZK 临时节点为什么能自动释放锁？

## 6. 分布式锁实现要点是什么（其实就是怎么加锁、怎么解锁、怎么用）？

> 原题 ID：`q0437`

**高频程度**：★★★★

**考察点**：考察 SET NX PX 加唯一 value 加 Lua 释放的标准实现要点。

**回答框架**：

①加锁：用 SET key value NX PX，key 是锁名，value 是持有者唯一 ID，带过期时间。②为什么带 value：遵循谁申请谁释放原则，解锁时校验。③为什么带过期：兜底防止异常情况下锁被永久占用。④解锁：先判断是否自己的锁再删除，两步必须用 Lua 脚本保证原子性。

**参考回答**：

分加锁和解锁两点讲。加锁用 SET 命令带上 NX 和 PX 参数：key 是锁的名字，value 是持有者的唯一标识（如 UUID 或线程标识加请求 ID），再加一个过期时间。带 value 是为了遵循「谁申请、谁释放」的原则，解锁时可以校验锁是不是自己的，防止误删他人的锁；带过期时间是为了兜底，防止客户端崩溃或网络异常导致锁被永久占用形成死锁。解锁分两步：先 GET 判断锁的 value 是不是自己，是则删除；这两步必须用 Lua 脚本执行以保证原子性，否则在判断完成、删除之前锁刚好过期并被别人获取，就会误删他人的锁。使用时还要注意：锁的过期时间要大于业务最大执行时间，否则业务没跑完锁就过期了也会出问题；如果无法预估执行时长，可以用看门狗机制自动续期（如 Redisson）；锁的粒度要尽量小，避免把不相关的操作串行化。

**常见追问**：业务执行时间不确定时怎么续期？为什么不能把 GET 和 DEL 分两条命令执行？

## 7. Redis 分布式锁何时不足以保护强一致副作用？fencing token 与共识系统如何取舍？

> 原题 ID：`q0441`

**高频程度**：★★★

**考察点**：考察 Redlock 的多节点多数派加锁算法与总耗时校验。

**回答框架**：

①问题：单实例或主从架构下主节点宕机且锁未同步会导致锁失效。②方案：Redlock 红锁，基于多个相互独立的 Redis 主节点（官方推荐至少 5 个）。③加锁流程：记录 t1，向 N 个节点依次 SET NX PX 加唯一标识，加锁操作本身设几十毫秒超时。④成功条件：超过半数节点加锁成功且总耗时小于锁过期时间，失败则向所有节点释放。

**参考回答**：

为了保证集群环境下分布式锁的可靠性，Redis 官方设计了 Redlock 算法。它基于多个相互独立的 Redis 节点（官方推荐至少 5 个，且都是主节点，彼此之间没有主从关系），即使某些节点故障锁变量仍然存在，客户端仍可完成锁操作，解决主从切换时锁未同步导致的互斥失效问题。加锁流程是：第一步记录当前时间 t1；第二步依次向 N 个节点执行加锁，用 SET 命令带 NX 和 EX/PX 选项以及客户端唯一标识，同时对「加锁操作」本身设置一个远小于锁过期时间的超时（一般几十毫秒），这样某个节点故障时不会拖住整体；第三步如果从超过半数（大于等于 N/2+1）的节点上成功获取锁，就再记录时间 t2，计算总耗时 t2 减 t1，只有总耗时小于锁的过期时间才算加锁成功。加锁成功后还要重新计算锁的有效时间，等于最初设置的过期时间减去加锁总耗时，如果剩余时间已经不够完成业务操作，应主动释放锁，避免业务没做完锁就过期。加锁失败则向所有节点发起释放锁操作，用释放锁的 Lua 脚本即可。

**常见追问**：Redlock 在时钟漂移和 GC 停顿下会有什么问题？为什么业界对它争议很大？

## 8. set nx实现的分布式锁，极端场景下，会有什么问题吗？

> 原题 ID：`q0461`

**高频程度**：★★★★

**考察点**：考察 SETNX 锁在超时误删、主从丢锁、不可重入与抢锁性能上的缺陷。

**回答框架**：

①锁超时失效：业务执行超时导致锁过期，他人获锁后被原持有者误删。②误删锁：GET 加 DEL 非原子导致删了别人的锁。③主从切换丢锁：主节点宕机锁未同步，新主可重复发放。④其他：不可重入、高并发重试抢锁压力大。

**参考回答**：

SETNX 锁在极端场景下有五类问题。第一，锁超时失效：客户端 A 拿到锁但业务执行时间超过锁的过期时间，锁自动释放后客户端 B 拿到锁，而 A 执行完又去删锁，删掉的是 B 的锁，导致数据不一致；解决是 value 用唯一标识并在删除时校验，同时合理设置超时或用看门狗自动续期（如 Redisson）。第二，误删锁：如果解锁用 GET 加 DEL 两步，在两步之间锁可能已易主，会误删他人锁；解决是用 Lua 脚本保证校验和删除原子执行。第三，主从切换丢锁：客户端 A 在主节点加锁成功但主节点宕机且锁未同步到从节点，从节点升主后 B 也能加锁，互斥失效；解决是用 Redlock 多节点多数派，或者业务上接受短暂不一致并做好幂等。第四，不可重入：同一线程多次获取同一把锁会被阻塞，因为 SETNX 不支持重入；解决是用 Redisson 这类客户端，内部用 Hash 记录线程标识和重入次数。第五，竞争性能差：高并发下大量客户端重试抢锁会推高 Redis 负载；解决是加随机退避（指数退避），或改用 ZooKeeper、etcd 这类基于有序节点的公平锁。一句话总结：SETNX 简单但不完美，生产环境建议用成熟方案并叠加幂等兜底。

**常见追问**：看门狗续期会不会带来新的问题？什么业务场景可以接受主从丢锁的风险？

## 9. URL 长度、HTTP 方法与安全性之间有哪些真实边界？

> 原题 ID：`q0739`

**高频程度**：★★★★

**考察点**：考察 HTTP 语义中安全性与幂等的准确理解。

**回答框架**：

①语义：GET 获取资源，POST 提交数据。②幂等安全：GET 按规范是安全且幂等的，POST 会改变资源、多次提交会创建多个资源，不幂等。③实现差异：GET 参数在 URL 有长度限制且明文，POST 参数在请求体无长度限制。④追问：规范和实际实现可能背离，若开发者用 GET 做新增操作就不再安全幂等。

**参考回答**：

GET 和 POST 的区别主要在语义和实现上。语义上，GET 从服务器获取资源，是只读操作，按 HTTP 规范是安全且幂等的（多次请求结果一致且不改变服务器状态）；POST 向服务器提交数据，会修改服务器上的资源，多次 POST 会创建多个资源，所以既不安全也不幂等。实现上，GET 把请求参数放在 URL 的查询字符串中，浏览器和服务器对 URL 长度有限制，参数明文可见且会被记录到日志和浏览器历史；POST 把参数放在请求体中，长度基本不受限，相对隐蔽。追问「GET 请求一定是安全且幂等的吗」要答不一定：这取决于服务端的实际实现。如果开发者遵循规范，用 GET 做资源获取，那它就是安全且幂等的；但如果开发者用 GET 处理新增或修改数据的逻辑，那它就不再安全也不是幂等的，比如一些不规范的系统里点击链接就完成删除或下单。这也提醒接口设计要严格遵守语义，否则会被浏览器预取、爬虫抓取或中间代理重试意外触发副作用。

**常见追问**：为什么说两者本质都是 TCP 请求？用 GET 做写操作会带来哪些真实风险？

## 10. Nginx 开源版支持哪些 upstream 负载均衡策略？哪些属于商业或第三方扩展？

> 原题 ID：`q0784`

**高频程度**：★★★

**考察点**：考察 Nginx 常用负载均衡算法及其分类。

**回答框架**：

①列举：普通轮询、加权轮询、IP 哈希、URL 哈希、最短响应时间、最短连接（两轮询、两哈希、两最短）。②分类一：任务平分类，包括轮询与加权轮询。③分类二：负载均衡类，如最短连接数。④分类三：性能最优类，如最短响应时间；分类四：Hash 类，如 IP 哈希和 URL 哈希。

**参考回答**：

Nginx 常见负载均衡算法可以概括为「两轮询、两哈希、两最短」。第一类是任务平分类，把请求平均分配给后端，平均可以是绝对数量平均，也可以是权重或比例平均，包括普通轮询（默认，按顺序依次分发）和加权轮询（按机器性能设置 weight，性能好的多分）。第二类是负载均衡类，根据服务器当前负载分配，可以用连接数、CPU、I/O 使用率、网卡吞吐量等衡量，典型是最短连接数（least_conn），优先给当前连接数最少的节点。第三类是性能最优类，根据响应时间分配，优先把新请求给响应最快的节点，即最短响应时间。第四类是 Hash 类，对请求中的关键信息做哈希，保证相同哈希值的请求落到同一台机器，包括 IP 哈希（保证同一客户端会话粘性）和 URL 哈希（把相同 URL 的请求打到同节点，利于缓存命中）。实际生产中通常用加权轮询加健康检查，需要会话保持时叠加 IP 哈希。

**常见追问**：IP 哈希在客户端走 NAT 或代理时会有什么问题？一致性哈希和 IP 哈希的区别是什么？

## 11. **客户端负载均衡**和**服务端负载均衡有啥区别？**？

> 原题 ID：`q0785`

**高频程度**：★★★★

**考察点**：考察负载均衡决策位置不同带来的架构取舍。

**回答框架**：

①服务端负载均衡：由独立负载均衡器（F5、Nginx、HAProxy）在客户端与后端之间集中转发。②优点：对客户端透明、集中管理便于维护。③缺点：可能单点故障、多一跳网络延迟。④客户端负载均衡：逻辑在客户端，结合服务发现（Consul、Eureka、Nacos）拿到实例列表自行选择，代表 Ribbon、gRPC。

**参考回答**：

核心区别是负载均衡的决策位置不同。服务端负载均衡由专门的负载均衡器实现，位于客户端和后端服务器之间，客户端请求先到均衡器，再由它按策略转发。硬件方案如 F5 BIG-IP、Citrix 性能高但成本高，软件方案如 Nginx、HAProxy、LVS 灵活且成本低。优点是客户端不需要知道后端细节、对客户端透明、集中管理便于维护和统一配置；缺点是负载均衡器本身可能成为单点故障（需要集群或 Keepalived 高可用），并且多经过一跳会增加网络延迟。客户端负载均衡把选择逻辑放在客户端（或服务框架里），结合服务发现机制（Consul、Eureka、Nacos、ZooKeeper）动态获取可用实例列表，由客户端按策略直接发起请求，代表实现有 Spring Cloud 的 Ribbon、gRPC 内置的客户端负载均衡、Dubbo 的服务直连。优点是减少中间节点、降低延迟，且没有中心负载均衡器的单点问题；缺点是客户端实现复杂、每个客户端要维护实例列表、语言绑定强、治理策略升级需要所有客户端配合。选择上，微服务架构通常用客户端负载均衡加服务发现减少中间层依赖，传统 Web 应用常用服务端负载均衡集中管理流量；现代系统也常两者结合做多级负载均衡。

**常见追问**：客户端负载均衡怎么感知实例列表变化？为什么说它对多语言支持不友好？

## 12. IP限流怎么做？

> 原题 ID：`q0833`

**高频程度**：★★★

**考察点**：考察以 IP 为维度的限流实现手段与算法选择。

**回答框架**：

①目的：控制特定 IP 的请求频率，防滥用、防 DoS、保证公平。②算法：令牌桶（允许突发）与漏桶（恒定速率），或固定/滑动窗口计数。③实现：Nginx 的 limit_req 模块、Redis 加 Lua 脚本（分布式）、API 网关内置限流。④细节：滑动窗口避免固定窗口的临界峰值，超限后返回友好提示。

**参考回答**：

IP 限流是控制来自特定 IP 的请求频率，用于防滥用、防 DoS 攻击、保证资源公平使用。实现方式有几种：第一，令牌桶或漏桶算法，这是流量整形和速率限制的经典做法，令牌桶按速率补充令牌、请求消费令牌，桶内有积累所以允许突发流量；漏桶以恒定速率处理请求，超出部分排队或直接拒绝。第二，滑动窗口计数器，记录每个 IP 在时间窗口内的请求数，相比固定窗口它考虑了时间连续性，避免固定窗口在窗口边界产生两倍流量的临界峰值问题。第三，Nginx 的 limit_req 模块，用共享内存区域存储状态，配置每秒最大请求数以及超出后的处理方式（延迟处理或返回 503），还有 limit_conn 限制并发连接数。第四，分布式系统用 Redis 加 Lua 脚本，把每个 IP 的请求计数和时间戳存 Redis，用 Lua 原子地更新和判断是否超限，保证多实例下总量一致。第五，直接用 API 网关（Kong、Apigee 等）内置的限流能力，按 IP、用户凭证等条件配置策略。选型要看并发规模和现有基础设施，同时超限时要返回友好的提示而不是直接暴露技术错误。

**常见追问**：IP 限流在大量用户共享出口 IP（如校园网、NAT）时有什么问题？怎么防止攻击者换 IP 绕过？

## 13. 四层负载均衡（Service）与七层负载均衡（Ingress）有哪些异同点？

> 原题 ID：`q0913`

**高频程度**：★★★

**考察点**：考察传输层与应用层负载均衡的工作层次差异与安全能力。

**回答框架**：

①相同点：都是分散流量、提高可用性与扩展性、转发客户端请求到后端实例。②工作层次：四层基于 IP 和端口转发、逻辑简单；七层基于 HTTP/HTTPS 内容（URL、Header）做路由。③场景：四层适合高性能、不需理解应用协议；七层适合需要内容路由的 API 网关角色。④安全：七层可做 SSL 终止、WAF 集成等高级安全能力。

**参考回答**：

两者相同点是目的相同：都是为了分散到服务器的流量、提高应用可用性和扩展性，并且都能把客户端请求转发给不同的后端实例。不同点主要有三方面：第一，工作层次不同。四层负载均衡（如 Kubernetes 的 Service）工作在传输层，主要根据 IP 地址和端口号分发流量，不解析应用层内容，因此逻辑简单、性能高、开销小；七层负载均衡（如 Ingress）工作在应用层，能解析 HTTP/HTTPS 内容，根据 URL 路径、Host、Header、Cookie 等做路由，支持灰度、A/B、会话保持等复杂策略，但需要解析更多数据，会带来额外延迟和更高资源消耗。第二，使用场景不同。四层适合对性能要求高、不需要理解应用层协议的场景；七层更适合需要根据应用层信息做智能路由的场景，比如微服务架构下的 API 网关。第三，安全能力不同。七层可以解析应用层数据，所以能做 SSL 终止、WAF 集成、请求校验等高级安全功能；四层通常不具备这些特性，只做纯粹的流量转发。实践中常两者配合：外层用四层做高性能入口，内层用七层做内容路由和治理。

**常见追问**：为什么七层转发会带来额外延迟？Kubernetes 里 Service 和 Ingress 是怎么配合的？

## 14. 什么是BASE理论？

> 原题 ID：`q0953`

**高频程度**：★★★★

**考察点**：考察 BASE 三要素及其作为 AP 落地指导的意义。

**回答框架**：

①来源：对 CAP 中 AP 的延伸，Basically Available、Soft state、Eventually consistent。②基本可用：允许损失部分可用性，如降级、限流、延迟响应。③软状态：允许中间状态存在，不要求时刻一致。④最终一致：经过一段时间后数据最终达到一致，是 BASE 的核心。

**参考回答**：

BASE 理论是对 CAP 中 AP 方案的延伸和落地指导，包含三个要素。第一，Basically Available 基本可用：系统在出现故障时允许损失部分可用性，比如响应时间变长、功能降级、部分服务不可用，但核心功能仍然可用，典型手段是限流、降级、熔断和异步处理。第二，Soft state 软状态：允许系统中的数据存在中间状态，即不同节点之间数据副本的同步允许有延迟，不要求任意时刻都强一致，比如订单处于「支付中」这种中间态。第三，Eventually consistent 最终一致：经过一段时间的数据同步后，所有副本最终会达到一致状态，这是 BASE 的核心，也是与强一致最大的区别。BASE 的意义在于：强一致（ACID）往往以牺牲可用性和性能为代价，而大部分互联网业务（社交、电商、内容）并不需要时刻强一致，用最终一致加对账兜底能在可用性、性能、成本之间取得更好的平衡。典型落地是本地消息表、事务消息、Saga、TCC 等最终一致方案。

**常见追问**：最终一致的时间窗口怎么界定？哪些业务绝不能只靠 BASE？

## 15. 什么是最终一致性？和强一致性有什么区别？

> 原题 ID：`q0954`

**高频程度**：★★★★

**考察点**：考察一致性模型差异及其对读可见性的影响。

**回答框架**：

①强一致：任何时刻任何节点读到的都是最新写入的值，等价线性一致。②最终一致：允许中间状态和延迟，经过一段时间后副本最终收敛到一致。③区别：读新鲜度、可用性与延迟、实现复杂度。④落地：弱化到最终一致要用版本号、幂等、对账和对用户可见的中间态设计。

**参考回答**：

强一致性（线性一致性）指任何时刻、任何节点读到的都是最近一次写入的值，所有客户端看到的数据顺序与写入顺序一致，实现上通常需要共识协议（Raft、Paxos）或分布式事务，代价是延迟高、可用性低，网络分区时少数派必须拒绝服务。最终一致性指系统允许副本之间存在同步延迟，写入后短时间内其他节点可能读到旧值，但经过一段时间后所有副本会收敛到同一状态。两者的区别可以从三方面看：一是读新鲜度，强一致保证读到最新，最终一致可能短暂读到旧值；二是可用性与延迟，最终一致可用性更高、延迟更低，因为不需要等待多数派确认；三是实现复杂度，强一致靠共识协议和锁，最终一致靠消息重试、幂等、去重和对账。工程上选择最终一致时要做四件事：用版本号或时间戳解决冲突，保证操作幂等，用对账任务兜底数据差异，并在产品上显式设计中间态（如「支付中」「同步中」）避免用户误解。典型例子是 MySQL 主从延迟导致的读旧数据、跨机房双写、以及基于 MQ 的异步链路。

**常见追问**：最终一致下怎么实现「读己之写」？对账系统一般怎么设计？

## 16. 负载均衡解决什么场景问题？

> 原题 ID：`q0955`

**高频程度**：★★★

**考察点**：考察负载均衡在可用性、性能与扩展性上的价值。

**回答框架**：

①分散流量：把请求均匀分发到多台服务器，避免单机过载。②提高可用性：单点故障时自动摘除故障节点、流量转移。③提升性能：横向扩展处理能力，支撑高并发。④弹性与运维：支持灰度发布、无损上下线、按容量扩缩容。

**参考回答**：

负载均衡主要解决四类问题。第一，流量分散：单台服务器有性能上限，把请求均匀分发到多台机器上，避免某台过载而其他空闲，从而提升整体吞吐。第二，提高可用性：通过健康检查自动摘除故障节点，把流量转移到健康实例，用户对单机故障无感知，实现高可用，这是负载均衡最有价值的地方。第三，提升性能与扩展性：支持水平扩展，需要更高并发时加机器即可线性提升处理能力，同时可以按机器性能做加权分配。第四，支撑运维与变更：灰度发布（按比例把流量切到新版本）、蓝绿部署、无损上下线和平滑重启都依赖负载均衡的流量控制能力；配合多机房部署还能做就近接入和容灾切换。此外负载均衡还能提供会话保持、SSL 终止、限流等附加能力。没有负载均衡，系统既无法横向扩展，也无法在单机故障时保持服务，所以它是分布式系统的入口基础设施。

## 17. 负载均衡有哪些算法？

> 原题 ID：`q0956`

**高频程度**：★★★

**考察点**：考察常见负载均衡算法分类与适用场景。

**回答框架**：

①静态类：轮询、加权轮询、随机、加权随机、源地址哈希。②动态类：最少连接、最快响应时间、最小负载。③高级类：一致性哈希、P2C（两次随机选优）。④选择：无状态均匀算力用轮询，会话相关用哈希，机器性能不均用加权，负载波动大用动态算法。

**参考回答**：

负载均衡算法分几类。静态类不考虑实时状态：轮询依次分发，适合各节点性能相近；加权轮询按权重分发，适合机器配置不同；随机和加权随机按概率选；源地址哈希对客户端 IP 取模，保证同一客户端总落到同一节点，用于会话保持。动态类根据实时指标决策：最少连接优先给当前连接数最少的节点；最快响应时间优先给响应最快的节点；最小负载综合 CPU、内存、连接数等衡量。高级算法有两个值得提：一是一致性哈希，把节点和请求映射到环上，节点变化时只迁移少量数据，适合缓存分片和需要稳定路由的场景；二是 P2C（Power of Two Choices），随机选两个节点取较优的，用极低成本近似全局最优，在去中心化场景（如 Finagle、Linkerd）很常用，避免集中调度的单点。选择上，无状态且算力均匀用轮询，需要会话粘性用哈希，机器性能差异大用加权，负载波动剧烈用动态算法或 P2C，并结合健康检查自动摘除异常节点。

**常见追问**：最少连接算法在请求耗时不均时有什么问题？P2C 为什么能近似最优？

## 18. 限流的作用是什么？为什么要限流？

> 原题 ID：`q0957`

**高频程度**：★★★★

**考察点**：考察限流在保护系统、控制成本与保障公平上的作用。

**回答框架**：

①保护系统：防止突发流量超过承载能力导致雪崩。②控制成本：限制下游调用量，避免第三方配额打满和费用失控。③保障公平：按用户或租户分配配额，防止大客户或恶意请求挤占资源。④配合：限流要与排队、降级、熔断、扩容配合使用，是流量治理的第一道闸门。

**参考回答**：

限流的核心作用是保护系统不被超过自身承载能力的流量打垮。具体有三层价值：第一，保护系统稳定性，系统容量是有限的，当流量突增（热点事件、恶意攻击、上游异常重试）超过容量时，如果不限流会导致响应变慢、线程池和连接池耗尽、数据库被打挂，最终整条链路雪崩，限流让超出部分快速失败，保住核心服务的可用性。第二，控制成本，很多下游依赖是收费的或有限额的，比如第三方 API、大模型 token、短信网关，不限流会打满配额触发 429 甚至产生巨额费用。第三，保障公平，多租户场景下按用户或租户维度设配额，防止某个大客户或恶意请求占满资源，把其他用户饿死。工程上限流要和排队、降级、熔断、弹性扩容配合使用：限流是第一道闸门，排队吸收可等待的流量，降级保证核心链路，熔断隔离故障依赖，扩容提升承载上限。同时限流策略要可动态调整和可观测，否则大促前无法评估容量。

**常见追问**：限流阈值怎么定，靠压测还是靠经验？限流和熔断的本质区别是什么？

## 19. 常见限流算法有哪些？Nginx limit_req 使用的是什么整形模型？

> 原题 ID：`q0958`

**高频程度**：★★★★★

**考察点**：考察固定窗口、滑动窗口、漏桶、令牌桶四类算法的取舍。

**回答框架**：

①固定窗口计数：简单，但窗口边界存在临界峰值问题。②滑动窗口：把窗口细分或记录请求时间戳，精度高但存储和计算成本大。③漏桶：以恒定速率流出，流量绝对平滑，但无法应对突发且可能增加延迟。④令牌桶：按速率补充令牌、允许突发流量，是综合最常用的方案。

**参考回答**：

常见限流算法有四种。第一，固定窗口计数：按固定时间窗口（如每秒）计数，超过阈值就拒绝，实现最简单，但存在临界峰值问题，比如限制每秒 100 个请求，在 1 秒末尾打满 100 个、下一秒开头再打 100 个，就出现两倍流量。第二，滑动窗口：把时间窗口细分成多个小格子并滚动统计，或者记录每个请求的时间戳来计算真正的最近 N 秒请求数，精度高、能消除临界峰值，代价是存储和计算成本更高，Redis ZSet 计数是典型实现。第三，漏桶：请求先入桶再以恒定速率流出，超出桶容量的请求被丢弃或排队，流量整形效果最好、绝对平滑，适合保护下游；缺点是无论系统是否空闲都按固定速率放行，无法利用空闲容量处理突发，且排队会增加延迟。第四，令牌桶：按固定速率往桶里放令牌，桶有容量上限，请求取令牌才能通过，取不到则拒绝或等待；它既能限制平均速率又允许一定程度的突发（消耗积累的令牌），是实践中最常用的方案，Nginx limit_req、Guava RateLimiter、Sentinel 都用它。选型上，简单场景用固定窗口，精度要求高用滑动窗口，需要严格平滑下游用漏桶，兼顾突发与平均速率用令牌桶。

**常见追问**：固定窗口的临界峰值具体怎么发生？令牌桶的突发能力怎么量化？

## 20. 什么是熔断？服务熔断解决方案有哪些？

> 原题 ID：`q0959`

**高频程度**：★★★★★

**考察点**：考察熔断三态模型与主流实现方案。

**回答框架**：

①定义：当下游依赖错误率或超时率达到阈值时快速失败，不再持续调用，防止级联失败。②三态：关闭、打开、半开，半开放少量探针探测恢复。③阈值：滑动窗口统计错误率，常结合慢调用比例而不只看错误率。④实现：Hystrix、Resilience4j、Sentinel、gobreaker，粒度按依赖实例或接口维度。

**参考回答**：

熔断是模仿电路保险丝的机制：当下游依赖（某个服务、工具或模型）在统计窗口内错误率或超时率达到阈值时，熔断器从关闭状态切换到打开状态，后续请求不再真正调用下游而是直接快速失败，从而避免持续打请求把下游压垮、也避免调用方线程被长时间占用导致级联失败。熔断器有三个状态：关闭（正常放行并统计）、打开（直接拒绝，持续一段时间）、半开（经过冷却后放少量探针请求探测下游是否恢复，成功则回到关闭，失败则继续打开）。统计通常用滑动窗口，阈值判断不能只看错误率，还要看慢调用比例和最小请求数，因为 LLM 场景常见「慢但成功」，纯错误率会漏判。主流实现有 Netflix Hystrix（已停止维护）、Resilience4j（轻量、函数式）、阿里 Sentinel（流量治理综合方案，含限流熔断）、Go 的 sony/gobreaker。关键实践是熔断粒度要按依赖实例加接口加租户维度隔离开，避免全局单例导致一个模型挂掉把其他模型调用也一起熔断；同时熔断必须配合降级，打开期间走缓存、小模型或兜底响应，而不是把错误直接抛给用户。

**常见追问**：为什么说只统计错误率会漏判？熔断和限流、降级的边界分别在哪？

## 21. 说下raft算法的主要流程？

> 原题 ID：`q0962`

**高频程度**：★★★★★

**考察点**：考察 Raft 的选举、日志复制、提交与安全性约束。

**回答框架**：

①角色：Leader、Follower、Candidate 三态与任期 term。②选举：选举超时随机化触发，候选人拉票，获多数派当选。③日志复制：Leader 接收写请求追加日志并并行复制，多数派确认后提交并应用到状态机。④安全性：日志匹配特性、只允许日志最新的候选人当选、Commit 必须多数派。

**参考回答**：

Raft 是一种为了可理解性而设计的共识算法，主要流程分三部分。第一，角色与任期：节点有三种角色 Leader、Follower、Candidate，时间被划分为任期 term，每个任期最多一个 Leader。第二，Leader 选举：Follower 在选举超时时间内没收到 Leader 心跳就转为 Candidate，任期加一并向所有节点拉票，获得多数派（N/2+1）投票的候选人成为 Leader 并立即发送心跳确立权威；选举超时时间随机化（如 150 到 300 毫秒）是避免平票反复选举的关键。第三，日志复制：客户端写请求只发给 Leader，Leader 把命令作为日志条目追加到本地，然后并行复制给所有 Follower；Follower 校验日志连续性后追加并返回成功；当某条日志被多数派节点复制后，Leader 就把它标记为已提交并把结果应用到状态机，再返回客户端，同时通过下一次心跳或 AppendEntries 通知 Follower 提交。安全性上 Raft 有两条关键约束：一是日志匹配特性，如果两个日志在相同索引和任期的条目相同，则之前的所有条目也相同；二是选举限制，只允许日志至少和多数派一样新的候选人当选，保证已经提交的日志不会丢失。此外还有日志压缩（快照）和成员变更机制。

**常见追问**：为什么选举超时要随机化？已提交的日志为什么不会被新 Leader 覆盖？

## 22. raft如何处理平票问题？

> 原题 ID：`q0963`

**高频程度**：★★★

**考察点**：考察随机化选举超时是 Raft 解决平票的核心手段。

**回答框架**：

①平票原因：多个 Follower 同时超时转为 Candidate 并各自拉票，票数被分散无人过半。②解法：选举超时时间随机化，让节点在不同时刻发起选举，先起的更容易拿到多数票。③补充：随机化区间（如 150 到 300 毫秒）足够大以降低冲突概率，又足够小以保证选举及时。④结果：即使偶发平票，下一轮随机超时也会很快打破僵局。

**参考回答**：

平票发生在多个 Follower 几乎同时选举超时、同时转为 Candidate 并各自拉票的情况下，票数被分散，没有任何一个候选人拿到多数派。Raft 的处理方式是把选举超时时间随机化：每个节点的选举超时从固定值改成在某个区间内随机取值（典型是 150 到 300 毫秒之间随机），这样节点发起选举的时刻是错开的，最先超时的节点会先拉票并大概率在其他节点超时之前拿到多数派，成为 Leader 后立即发心跳重置其他节点的计时器，避免它们再发起选举。随机区间的选择是个权衡：区间太小则冲突概率高、容易反复平票；区间太大则选举恢复时间长，故障切换慢。如果偶发真的出现平票，本轮选举无人当选，各候选人会在下一轮新的随机超时后重新发起选举，因为随机性存在，很快就能打破僵局，不会无限僵持。这也是 Raft 相比 Paxos 更易理解和实现的一个体现。

**常见追问**：心跳间隔和选举超时的比例通常怎么设？如果随机区间设成固定值会怎样？

## 23. Raft 的基础选主和提交保证是什么？CheckQuorum/lease 属于什么扩展？

> 原题 ID：`q0964`

**高频程度**：★★★★

**考察点**：考察多数派原则如何在网络分区下避免双主。

**回答框架**：

①脑裂定义：网络分区导致集群出现两个以上「主」。②防双主：多数派原则，候选人必须获得超过半数节点投票才能当选。③分区结果：少数派分区无法选出 Leader，旧 Leader 因收不到多数派心跳也会退位。④配合：日志只有多数派复制后才算提交，少数派即使有旧 Leader 也无法提交新日志。

**参考回答**：

脑裂指网络分区导致集群中同时出现多个自认为的 Leader。Raft 用多数派原则解决：候选人必须获得超过半数（N/2+1）节点的投票才能当选 Leader，而一个集群在同一任期内不可能有两个节点同时拿到多数派的票，因为多数派之间必然有交集。发生网络分区时，比如 5 个节点分成 3 和 2 两部分，包含 3 个节点的分区能选出 Leader 并继续提供服务，只有 2 个节点的分区因为凑不齐多数派而无法选出新 Leader，处于不可用状态；如果旧 Leader 被分到少数派一侧，它会因为无法与多数派建立联系、心跳得不到多数派响应，在「Leader 无法与多数派通信时主动退位」的约束下自动退回 Follower，不会持续以 Leader 身份接受写请求。另外，Raft 规定日志条目只有被多数派复制后才算提交并应用状态机，所以少数派分区里即使存在旧 Leader，它提交的任何日志都无法获得多数派确认，一旦分区恢复，这些未提交的日志会被新 Leader 覆盖掉。这套机制保证了 CAP 中的 CP 特性：分区时牺牲少数派可用性，保证不出现双主和数据不一致。

**常见追问**：少数派分区的旧 Leader 收到客户端写请求会怎么处理？分区恢复后未提交日志为什么会被覆盖？

## 24. 介绍一下2PC？

> 原题 ID：`q0965`

**高频程度**：★★★★

**考察点**：考察两阶段提交的流程、优缺点与阻塞问题。

**回答框架**：

①角色：协调者与多个参与者。②阶段一准备：协调者询问各参与者能否提交，参与者执行事务但不提交，返回同意或中止；阶段二提交：全部同意则提交，任一不同意则回滚。③优点：实现相对简单，能保证强一致。④缺点：同步阻塞、协调者单点、参与者宕机导致长时间锁资源、提交阶段部分失败产生不一致。

**参考回答**：

2PC 即两阶段提交，角色包括一个协调者和多个参与者（资源管理器）。第一阶段是准备阶段（投票阶段）：协调者向所有参与者发送 prepare 请求，询问是否可以提交事务；参与者执行事务操作并把 undo 和 redo 写入日志，但不真正提交，然后向协调者返回同意或者中止。第二阶段是提交阶段：如果所有参与者都返回同意，协调者向所有参与者发送 commit，参与者正式提交并释放资源、回复 ack，协调者收到所有 ack 后事务完成；如果任一参与者返回中止或者超时，协调者向所有参与者发送 rollback，参与者用 undo 日志回滚。优点是原理简单、能保证强一致性，数据库的 XA 就是 2PC 的实现。缺点比较明显：一是同步阻塞，参与者在准备阶段执行完业务后要一直持有锁等待第二阶段，期间其他事务访问相同资源会被阻塞，性能差；二是协调者是单点，协调者宕机后参与者会一直处于等待状态、资源被锁住；三是提交阶段可能出现部分参与者收到 commit 而部分没有，导致数据不一致，需要人工介入或额外的补偿机制，这也是 3PC 和 TCC 要解决的问题。

**常见追问**：2PC 在提交阶段协调者宕机会怎样？为什么参与者不能自己决定提交或回滚？

## 25. 介绍一下3PC？

> 原题 ID：`q0966`

**高频程度**：★★★

**考察点**：考察 3PC 在 2PC 上增加询问阶段与超时机制以缓解阻塞。

**回答框架**：

①三阶段：CanCommit 询问、PreCommit 准备、DoCommit 提交。②改进一：增加询问阶段，在真正执行事务前先确认参与方可参与，避免无效的准备开销。③改进二：引入超时机制，参与者和协调者都有超时，减少永久阻塞。④局限：仍无法完全解决一致性问题，网络分区下仍可能数据不一致。

**参考回答**：

3PC 即三阶段提交，在 2PC 的基础上增加了询问阶段并引入超时机制，把流程拆成 CanCommit、PreCommit、DoCommit 三步。第一，CanCommit 询问阶段：协调者先询问各参与者是否可以执行事务，参与者只做轻量的可行性检查（如资源、状态）并返回是或否，不执行实际的业务操作和加锁，这样可以在真正付出代价前快速排除不可行的参与者。第二，PreCommit 准备阶段：如果所有参与者都回答可以，协调者发送 preCommit，参与者执行事务操作并写日志但不提交，返回确认；这一步等价于 2PC 的准备阶段。第三，DoCommit 提交阶段：协调者根据准备结果发送 doCommit 或 doRollback，参与者完成提交或回滚。相比 2PC 的两大改进：一是多了 CanCommit 阶段，避免了对必然失败的参与者做无用功；二是引入超时机制，参与者如果在 PreCommit 之后长时间收不到协调者的决定，到达超时后会默认提交（因为此时所有参与者都已通过预检查，提交概率很大），从而减少资源被永久占用的阻塞问题。局限是 3PC 仍然无法完全解决网络分区下的数据不一致问题，比如分区导致部分节点提交、部分回滚，只是发生概率和影响比 2PC 低。

**常见追问**：3PC 里参与者超时后为什么默认提交而不是回滚？3PC 能完全解决一致性吗？

## 26. 2PC和3PC的区别是什么？

> 原题 ID：`q0967`

**高频程度**：★★★

**考察点**：考察 3PC 相对 2PC 的阶段与超时改进及其局限。

**回答框架**：

①阶段数：2PC 是准备加提交两阶段；3PC 是 CanCommit、PreCommit、DoCommit 三阶段。②是否执行事务：2PC 准备阶段就执行事务并加锁；3PC 先做轻量的 CanCommit 可行性检查。③超时机制：2PC 参与者无超时，会永久阻塞；3PC 参与者有超时，超时后默认提交。④一致性：3PC 降低阻塞与单点影响，但仍不能完全保证一致。

**参考回答**：

两者主要区别有四点。第一，阶段数不同：2PC 只有准备和提交两个阶段，3PC 拆成 CanCommit（询问）、PreCommit（准备）、DoCommit（提交）三个阶段。第二，是否真正执行事务的时机不同：2PC 在准备阶段就执行事务并加锁，一旦后续决定回滚就要靠 undo 日志撤销；3PC 先做 CanCommit 只进行轻量的可行性检查、不加锁不执行业务，确认可行后才在 PreCommit 阶段真正执行事务，这样可以减少因参与者本就无法参与而造成的资源浪费和无效加锁。第三，超时机制不同：2PC 中参与者没有超时，协调者宕机时参与者会一直持锁等待，造成长时间阻塞；3PC 给参与者也引入了超时，PreCommit 之后超时会默认提交，从而降低永久阻塞的概率。第四，容错与一致性：3PC 通过超时和阶段细化降低了阻塞风险和单点影响，但在网络分区下仍可能出现部分节点提交、部分节点回滚的不一致情况，所以它并没有从根本上解决分布式一致性问题，只是缓解了 2PC 的阻塞和单点问题，实际生产中更常用的是 TCC、Saga 和消息最终一致方案。

**常见追问**：为什么说 3PC 仍然不能保证一致性？生产环境为什么很少直接用 3PC？

## 27. TCC了解过吗？

> 原题 ID：`q0968`

**高频程度**：★★★★★

**考察点**：考察 TCC 三阶段模型与空回滚、悬挂、幂等三大问题。

**回答框架**：

①模型：Try 预留资源、Confirm 确认执行、Cancel 取消释放，补偿逻辑写在业务层。②优点：不长时间持锁、性能优于 2PC、可自定义业务粒度。③三大问题：空回滚（未 Try 先 Cancel）、悬挂（Cancel 先于 Try 到达）、幂等（Confirm 与 Cancel 可能重复调用）。④解法：事务控制表记录状态、Cancel 前校验 Try 记录、重复调用直接返回成功。

**参考回答**：

TCC 是 Try-Confirm-Cancel 三段式补偿型分布式事务，把每个参与方的操作按业务拆成三步。Try 阶段做业务检查并预留资源，比如冻结库存、预扣额度；Confirm 阶段确认执行，真正扣减并清除预留；Cancel 阶段取消释放，把预留的资源还回去。与 2PC 的区别在于：TCC 的资源锁定是业务层的、由业务自定义粒度，不像 2PC 那样由数据库在准备阶段长时间持有行锁，所以并发性能更好，也不依赖数据库的 XA 支持。代价是侵入性强，每个服务都要实现三个方法并保证幂等。TCC 落地必须解决三个经典问题：第一，空回滚，即 Cancel 比 Try 先执行（Try 因网络超时未到达），此时 Cancel 要能识别到「没有对应的 Try 记录」并直接返回成功，而不是报错；第二，悬挂，即 Cancel 已执行完后 Try 的请求才到达，导致资源被预留却永远不会被释放，解决办法是在 Try 时先检查事务控制表中该全局事务是否已有 Cancel 记录，有则拒绝 Try；第三，幂等，Confirm 和 Cancel 都可能因为重试被多次调用，必须保证重复执行结果一致，通常用事务控制表的唯一键加状态机来实现。

**常见追问**：TCC 的空回滚和悬挂分别怎么用事务控制表解决？和 Saga 的区别在哪？

## 28. 分布式ID有哪些方案？

> 原题 ID：`q0970`

**高频程度**：★★★★

**考察点**：考察五类分布式 ID 方案的对比与选型。

**回答框架**：

①UUID：无序、字符串长、索引不友好但简单。②数据库自增：单点瓶颈，可用多实例加步长缓解。③雪花算法：时间戳加机器加序列，趋势递增、性能高、注意时钟回拨。④号段模式（Leaf-segment）：批量取段、双 buffer、容灾好。⑤Redis INCR：原子自增，集群可分起始值与步长。

**参考回答**：

主流方案有五种，各自取舍不同。第一，UUID：由 32 位十六进制组成共 128 位，生成简单、性能好、全球唯一，适合数据迁移和合并场景；但无序导致索引插入随机、B+ 树页分裂，字符串存储占空间、查询效率低、不可读。第二，数据库自增：利用数据库的 auto_increment，简单可靠且严格递增，但存在单点瓶颈和性能限制，可用多台实例设不同起始值加固定步长缓解，但扩容时步长和起始值难以调整。第三，雪花算法：生成 64 位整数，1 位符号加 41 位毫秒时间戳加 10 位机器 ID 加 12 位序列号，每毫秒每节点可产生 4096 个 ID；本地生成不依赖外部系统、性能极高、趋势递增且 bit 位可自定义，缺点是强依赖机器时钟，回拨会导致重复或不可用。第四，美团 Leaf-segment：用数据库批量取号段（如一次取 1 到 10000）在本地内存发号，用双 buffer 机制在号段消耗到 10% 时异步预取下一段，保证始终有两个号段缓存，DB 宕机也能继续发号 10 到 20 分钟；可以用 biz_tag 隔离不同业务，扩容方便；缺点是不够随机、会泄露发号量，且整体仍依赖数据库。第五，Redis 生成：利用单线程和 INCR、INCRBY 原子自增，集群可让各实例设置不同起始值（如 1 到 5）和相同步长（如 5）来并行发号，性能优于数据库，但引入新组件、步长和起始值需要提前确定不易修改。互联网主流是雪花算法和号段模式。

## 29. 雪花算法了解吗？

> 原题 ID：`q0971`

**高频程度**：★★★★★

**考察点**：考察雪花算法的 64 位结构与优缺点。

**回答框架**：

①结构：1 位符号位（恒为 0）加 41 位毫秒时间戳加 10 位机器 ID（5 位数据中心加 5 位机器）加 12 位序列号。②容量：每毫秒每节点 4096 个，41 位时间戳可用约 69 年。③优点：趋势递增、本地生成不依赖第三方、性能高、bit 位可灵活分配。④缺点：强依赖机器时钟，回拨会导致重复或不可用。

**参考回答**：

雪花算法生成的是一个 64 位 int64 整数，结构分四部分：最高 1 位符号位固定为 0 保证正数；41 位毫秒级时间戳，可以支撑约 69 年；10 位机器 ID，由 5 位数据中心 ID 加 5 位工作机器 ID 组成，最多支持 1024 个节点；12 位毫秒内序列号，意味着每个节点每毫秒可以产生 4096（2 的 12 次方）个 ID，理论单机 QPS 可达 400 万以上。生成逻辑是：取当前毫秒时间戳，与上次生成的时间比较，如果相同则序列号加一（超过 4096 则等待下一毫秒），如果时间前进则序列号归零，最后把各部分按位左移拼接。优点是：时间戳在高位、序列号在低位，整个 ID 趋势递增，对数据库索引友好；不依赖数据库等第三方系统，以服务或本地库方式部署，稳定性高、性能极高；bit 位可以根据业务特性灵活调整。缺点是强依赖机器时钟，一旦发生时钟回拨（NTP 校时、人工改时间、虚拟机迁移），可能出现 ID 重复，严重的会直接导致服务不可用，生产上必须搭配时钟回拨检测与处理策略。

## 30. 雪花算法有什么缺点知道吗？

> 原题 ID：`q0972`

**高频程度**：★★★★

**考察点**：考察雪花算法的时钟回拨、机器 ID 分配与位宽限制等缺陷。

**回答框架**：

①时钟回拨：最核心缺陷，回拨期间可能生成重复 ID 或直接拒绝服务。②机器 ID 分配：10 位仅支持 1024 节点，人工配置易冲突，需依赖 ZK 或配置中心分配。③趋势递增非严格递增：跨毫秒不保证单调，且暴露时间信息。④应对：等待回拨时间、备用位、Leaf-snowflake 用 ZK 分配 workerId 并本地缓存、或用号段模式兜底。

**参考回答**：

雪花算法主要有四个缺点。第一，强依赖机器时钟，这是最致命的问题：当发生时钟回拨（NTP 校时、跨机房迁移、虚拟机暂停恢复）时，可能生成与之前重复的 ID；常见的处理策略有：回拨幅度小就自旋等待时钟追平，幅度大就抛异常拒绝服务并提出告警，或预留若干 bit 作为备用序列在回拨时使用。第二，机器 ID 分配困难：10 位最多支持 1024 个节点，需要保证每个节点拿到的 workerId 唯一，人工配置容易冲突，通常借助 ZooKeeper 顺序节点或配置中心自动分配；美团 Leaf-snowflake 就是用 ZK 生成 workerId 并在本机文件缓存一份，即使 ZK 短时故障也能启动。第三，趋势递增不是严格递增：同一毫秒内不同节点的 ID 大小关系与生成顺序无关，跨毫秒才单调，所以依赖严格单调的场景要额外处理。第四，信息暴露与位宽限制：时间戳在最高位会暴露生成时间，可推算出业务量；41 位时间戳和 10 位机器位在超大规模或需要更长生命周期时会不够用，需重新划分位宽。

## 31. 美团leaf了解吗？

> 原题 ID：`q0973`

**考察点**：考察 Leaf 的号段模式与 snowflake 模式两套实现。

**回答框架**：

①Leaf-segment：数据库批量取号段、本地内存发号、双 buffer 预取、DB 宕机仍可支撑 10 到 20 分钟。②号段长度：推荐为高峰 QPS 的 600 倍（约 10 分钟用量）。③Leaf-snowflake：沿用雪花结构，用 ZooKeeper 顺序节点分配 workerId，并对 ZK 弱依赖、本地缓存 workerId 文件。④选型：号段模式容灾好但依赖 DB，snowflake 趋势递增但依赖 ZK。

**参考回答**：

美团 Leaf 提供了两套分布式 ID 方案。第一套是 Leaf-segment 号段模式：不直接用数据库自增 ID，而是从数据库批量取一个号段范围（如 1 到 10000），业务服务在本地内存里自增发号，减少数据库访问频率；采用双 buffer 机制，内部维护两个号段缓存区，当前号段消耗到 10% 时就异步启动新线程去取下一个号段，而不等用尽才取，这样即使数据库短暂抖动也不影响发号；通常推荐号段长度设为高峰 QPS 的 600 倍（约 10 分钟用量），保证 DB 宕机后仍能持续发号 10 到 20 分钟；用 biz_tag 字段按业务隔离，未来扩容只需对 biz_tag 分库分表。优点是线性扩展方便、容灾性好；缺点是不够随机会泄露发号数量、且仍依赖数据库。第二套是 Leaf-snowflake：基本沿用雪花算法的结构（1 位符号加 41 位时间戳加 5 位机器 ID 加 5 位机房 ID 加 12 位序列号），区别主要在 workerId 的分配：启动时连接 ZooKeeper，在 leaf_forever 父节点下检查自己是否已注册，已注册则取回原有的顺序 ID 作为 workerId，未注册则创建持久顺序节点并取顺序号；对 ZK 是弱依赖，除启动时取号外还会在本机文件系统缓存 workerId 文件，即使 ZK 出问题且机器重启也能正常启动。优点是趋势递增的 64 位数字满足主键要求，缺点是依赖 ZooKeeper 存在服务不可用风险。

## 32. 美团leaf算法是怎么解决雪花算法的时钟漂移问题的？

> 原题 ID：`q0974`

**高频程度**：★★★

**考察点**：考察 Leaf-snowflake 的启动校验与时钟回拨处理策略。

**回答框架**：

①问题：雪花算法强依赖机器时钟，回拨会生成重复 ID 或服务不可用。②启动校验：服务启动时校验本机时间与 ZK 上记录的时间是否一致，不一致则启动失败。③运行期处理：回拨幅度小时等待时钟追平，幅度大时报警并拒绝发号。④依赖管理：workerId 由 ZK 顺序节点分配并本地缓存，降低对 ZK 的实时依赖。

**参考回答**：

Leaf-snowflake 沿用了雪花算法的 ID 结构，但在 workerId 分配和时钟处理上做了增强来应对时钟漂移。第一，启动期校验：服务启动时会校验本机当前时间与上次发号时间（记录在 ZooKeeper 上）是否一致，只有本机时间大于等于上次记录的时间才允许启动，否则直接启动失败并告警，避免用被回拨的时间开始发号导致重复。第二，运行期回拨处理：如果运行过程中检测到时钟回拨，且回拨幅度很小（比如几毫秒到几十毫秒），就自旋等待直到时钟追上上次的发号时间再继续发号；如果回拨幅度较大，则直接抛异常拒绝发号并告警，宁可短暂不可用也不生成可能重复的 ID，把问题暴露给运维而不是静默产生脏数据。第三，workerId 管理：workerId 由 ZooKeeper 顺序节点分配并在本机文件缓存，每次启动优先读取本地缓存，对 ZK 是弱依赖，即使 ZK 短期不可用也能保证服务正常启动，减少单点风险。这套思路和业界通用的处理方式一致：小回拨等待、大回拨失败告警、预留位兜底，核心原则是宁可不可用也不能重复。

**常见追问**：如果回拨持续存在（比如虚拟机长期时间不准）怎么办？为什么说宁可拒绝服务也不能重复发号？

## 33. 限流、熔断、降级分别解决什么问题？

> 原题 ID：`q3571`

**高频程度**：★★★★★

**考察点**：考察三者定位区分与协同关系。

**回答框架**：

①限流：控制入口流量速率，保护系统不被超过承载能力的流量打垮，属于主动防御。②熔断：下游依赖故障时快速失败，切断故障传播避免级联雪崩，属于故障隔离。③降级：资源不足或依赖不可用时牺牲非核心功能，保证核心链路可用。④协同：限流在入口、熔断在调用链、降级在业务层，三者组合构成稳定性防线。

**参考回答**：

三者解决的问题不同，属于稳定性保障的不同环节。限流解决「流量超过承载能力」的问题：在流量入口按速率或并发数限制通过量，超出的请求快速失败或排队，防止系统被突发流量或恶意请求打垮，是主动防御，常见算法有计数器、滑动窗口、漏桶和令牌桶。熔断解决「下游依赖故障导致级联失败」的问题：当被调用方（服务、工具、模型）的错误率或超时率达到阈值时，熔断器打开，后续请求不再真正调用下游而直接快速失败，避免调用方的线程和连接被长时间占用，从而切断故障传播，经过冷却后半开探测恢复；它是故障隔离机制，解决的是「别人挂了不要把我拖死」。降级解决「资源不足时必须保什么」的问题：当依赖不可用或系统压力过大时，主动关闭或简化非核心功能，把资源让给核心链路，比如推荐服务挂了返回热门榜单、风控超时转人工审核、非核心报表停止刷新；它通常在业务层实现，是有损服务策略。三者协同的方式是：限流在最前面控制进量，熔断在调用链中间隔离故障，降级在业务层兜底体验，再配合超时、重试退避、弹性扩容一起，构成完整的稳定性防线。

**常见追问**：限流和熔断在触发条件上有什么本质区别？降级为什么必须配合开关和监控？

## 34. 分布式 CAP 定理，三者为什么不可兼得？

> 原题 ID：`q3748`

**高频程度**：★★★★★

**考察点**：考察 CAP 不可兼得的原因与 P 必须保留的本质。

**回答框架**：

①三要素定义：一致性、可用性、分区容错性。②不可兼得的原因：网络分区时，要保证一致性就必须让部分节点拒绝服务，要保证可用性就必须接受数据不一致，二者不可同时满足。③P 必须保：网络分区是客观存在的，分布式系统无法回避。④实际取舍：CP（ZooKeeper、etcd）与 AP（Cassandra、Eureka），可用 BASE 指导 AP 落地。

**参考回答**：

CAP 指一致性（所有节点在同一时间看到相同的数据）、可用性（每个请求都能在有限时间内得到响应）、分区容错性（网络分区时系统仍能继续运行）。三者不可兼得的原因在于网络分区的必然性：分布式系统节点之间通过网络通信，一旦发生分区（消息丢失、延迟、网络断开），如果系统坚持保证一致性，那么为了让副本不出现分歧，就必须让无法与多数派通信的节点拒绝服务，从而牺牲可用性；反过来如果坚持保证可用性，让每个节点都能响应请求，那么在分区期间不同节点可能各自接受写入，就可能返回不一致的数据，从而牺牲一致性。所以在分区发生时，C 和 A 必然二选一，不可能同时满足。这引出一个关键结论：在真实分布式系统中网络分区客观存在，P 是必须保留的前提，所谓「三选二」实际是在 C 与 A 之间做取舍，而真正的 CA 系统只在单机或网络分区风险可忽略的小规模集群中存在。工程上是 CP 系统如 ZooKeeper、etcd、HBase，分区时少数派拒绝服务保证一致；AP 系统如 Cassandra、Eureka、Dynamo，分区时仍可读写、接受最终一致。实际选型按业务定：金融交易偏 CP，社交 Feed 和商品浏览偏 AP，并用 BASE 理论（基本可用、软状态、最终一致）指导 AP 的落地。

**常见追问**：为什么说 CA 在分布式下基本不存在？PACELC 对 CAP 做了什么补充？

## 35. 为什么要分库分表？常见策略？

> 原题 ID：`q4055`

**高频程度**：★★★★

**考察点**：考察分库分表的动机、拆分方式与分片键选择。

**回答框架**：

①动机：单表数据量过大导致 B+ 树索引变深、查询变慢、写入锁竞争；单库受连接数与存储上限限制。②分表：水平拆分（按用户 ID 取模、按时间、按地理）与垂直拆分（冷热字段分离）。③分库：突破单机连接数与存储上限，提升整体吞吐。④难点：分片键选择、跨分片查询与事务、扩容再平衡（一致性哈希或预分片）。

**参考回答**：

分库分表主要解决单表或单库数据量过大带来的性能瓶颈。动机有两方面：一是单表数据量过大时，B+ 树索引层级变深、查询 IO 增加、写入时锁竞争加剧，DDL 和备份也越来越慢；二是单库受单机连接数、IOPS 和存储容量上限限制，无法继续横向扩展。拆分方式上，分表分水平拆分和垂直拆分：水平拆分是把同一张表的数据按规则分散到多张结构相同的表，常见分片键有用户 ID 取模、时间范围、地理区域；垂直拆分是把不同字段拆到不同表，通常按冷热字段分离，把大字段和不常访问的字段独立出去，或者按业务把不同表拆到不同库。分库主要是为了突破单机资源上限，把表分散到多个数据库实例，每个实例独立承载连接和 IO。难点有三个：第一，分片键的选择，直接决定数据分布是否均匀和查询是否要跨片，选错了会造成热点（比如按时间戳分片会让最新数据全压在一个分片上），常用做法是按用户 ID 哈希；第二，跨分片查询和事务，聚合查询、排序分页、跨片事务都变得复杂，通常通过冗余字段、异构索引表或中间件解决；第三，扩容再平衡，取模方案扩容时几乎全量迁移，因此更推荐一致性哈希加虚拟节点或预分片（如一次分 1024 个逻辑片）来降低迁移成本。

**常见追问**：分片键选错了会造成什么后果？分库分表后怎么做分页排序？

## 36. 分布式事务有哪些方案？

> 原题 ID：`q4108`

**高频程度**：★★★★★

**考察点**：考察强一致与最终一致两大类方案的对比与选型。

**回答框架**：

①强一致：2PC、3PC、XA、Seata AT，能保证强一致但阻塞、性能差、有协调者单点。②最终一致：TCC（业务补偿，需处理空回滚、悬挂、幂等）、Saga（长事务加补偿）、本地消息表、事务消息。③选型：金融核心账务用强一致，电商下单等用最终一致加对账。④兜底：幂等、重试、对账、人工补偿。

**参考回答**：

方案分强一致和最终一致两大类。强一致类有：2PC（准备和提交两阶段，参与者在准备阶段执行业务并持锁等待，阻塞严重、协调者单点）、3PC（在 2PC 上增加 CanCommit 询问和超时机制，缓解阻塞但仍不能完全保证一致）、XA（数据库层支持的两阶段提交规范）、以及 Seata 的 AT 模式（通过全局锁加 undo_log 实现自动回滚，对业务侵入小）。这类方案能保证强一致，但同步阻塞、性能差、扩展性受限，适合金融核心账务这种绝不能出现不一致的场景。最终一致类有：TCC（Try 预留、Confirm 确认、Cancel 取消，补偿逻辑由业务实现，性能好但侵入强，必须处理空回滚、悬挂和幂等三个问题）、Saga（把长事务拆成多个本地事务，每个配一个补偿动作，正向失败则反向补偿，适合业务流程长的场景）、本地消息表（本地业务与消息记录写在同一事务，再由定时任务或 CDC 投递 MQ）、事务消息（如 RocketMQ 的半消息加回查机制）。这类方案不阻塞、可用性高，但需要幂等、重试和补偿失败处理。选型上：金融转账、支付扣款用强一致；电商下单、积分发放、通知类用最终一致；并且最终一致一定要配幂等键和对账系统做兜底，补偿失败要能告警转人工。

**常见追问**：Seata AT 模式的全局锁是怎么工作的？TCC 的空回滚和悬挂怎么防？

## 37. 如何保证接口的幂等性？

> 原题 ID：`q4109`

**高频程度**：★★★★★

**考察点**：考察唯一键、状态机、Token 与去重等幂等实现手段。

**回答框架**：

①定义：同一请求执行多次与执行一次的效果相同。②场景：支付回调、MQ 重复消费、用户重复点击、重试。③手段：数据库唯一索引、唯一业务号加去重表、Redis SETNX 加过期、状态机加 CAS 更新、乐观锁版本号、Token 机制。④注意：幂等键要能唯一标识一次业务操作，并考虑并发窗口与过期时间。

**参考回答**：

幂等指同一个请求执行一次和执行多次对系统状态的影响相同，是分布式和重试场景的基本要求，常见于支付回调、消息重复消费、用户重复点击和网络重试。实现手段主要有几种：第一，数据库唯一索引，最可靠也最简单，比如订单表用订单号做唯一键，重复插入直接报冲突，是最后一道防线。第二，唯一业务号加去重表，为每次请求生成唯一的业务流水号，处理前先插入去重表，插入成功才执行业务，插入失败说明已处理过，直接返回原结果。第三，Redis 的 SETNX 加过期时间做前置快速去重，配合数据库唯一索引兜底，注意要权衡过期时间和并发窗口，防止键过期后重复请求进来。第四，状态机加 CAS 更新，把业务对象设计成有明确状态流转的，更新时用「update 表 set status 等于新状态 where status 等于期望值」的条件更新，只有状态符合才允许流转，天然防止重复处理。第五，乐观锁版本号，用 version 字段做 CAS，避免并发覆盖。第六，Token 机制，服务端先下发一次性 token，提交时校验并删除，防止重复提交。实际落地通常是组合使用：Redis 做快速拦截、数据库唯一索引做最终兜底、状态机保证业务语义正确，同时把幂等判定的结果记入日志便于排查。

**常见追问**：幂等键的过期时间怎么权衡？为什么状态机的条件更新比单纯加锁更可靠？

## 38. 服务注册与发现怎么工作？

> 原题 ID：`q4112`

**高频程度**：★★★★

**考察点**：考察注册中心的注册、拉取、健康检查与推送机制。

**回答框架**：

①角色：服务提供者、服务消费者、注册中心。②注册：提供者启动时把地址与元数据写入注册中心，并定期续约心跳。③发现：消费者从注册中心拉取或订阅实例列表，缓存在本地并感知变更。④健康检查与摘除：心跳超时或探活失败则摘除实例，配合客户端负载均衡。

**参考回答**：

服务注册与发现解决的是「服务实例的地址动态变化时，调用方怎么找到可用实例」的问题。三个角色是服务提供者、服务消费者和注册中心。工作流程：第一，注册，服务提供者启动时把自己的 IP、端口、元数据和健康状态写入注册中心（如 Nacos、Eureka、Consul、ZooKeeper），并周期性发送心跳续约表明自己还活着。第二，发现，服务消费者从注册中心拉取或订阅所需服务的实例列表，通常在本地缓存一份，并通过长连接推送或定时轮询感知变更，这样调用时不需要每次都问注册中心，降低延迟和压力。第三，健康检查与摘除，注册中心根据心跳超时或主动探活判断实例是否可用，不可用则从列表中摘除并通知消费者，消费者结合客户端负载均衡在健康实例中选择。第四，容错设计，注册中心本身要集群部署保证高可用，消费者本地缓存要能在注册中心短暂不可用时继续工作（如 Eureka 的自我保护模式），避免注册中心故障引发整个服务调用链不可用。相比硬编码地址或静态配置，注册与发现让扩缩容、故障转移和灰度发布都能自动生效。

**常见追问**：Eureka 的自我保护模式解决什么问题？注册中心挂了消费者还能不能正常调用？

## 39. 什么是脑裂？如何避免？

> 原题 ID：`q4114`

**高频程度**：★★★★

**考察点**：考察脑裂成因与多数派、仲裁、隔离等防范手段。

**回答框架**：

①定义：网络分区导致集群同时出现多个「主」，各自接受写导致数据冲突。②危害：双写不一致、数据覆盖、恢复后难以合并。③避免手段：多数派选举（Raft/ZK）、法定人数（quorum）、仲裁节点、心跳与租约、fencing（隔离旧主）。④运维：避免跨机架随意分区、监控选举与任期变化。

**参考回答**：

脑裂指网络分区导致集群中同时出现多个自认为的主节点，各自接受写请求，造成数据冲突或不一致。产生原因是主从节点之间的心跳无法到达（网络抖动、分区、GC 停顿、机器假死），从节点认为主已挂而选举出新的主，而旧主可能仍在对外提供服务。危害是双写导致数据被覆盖或冲突，恢复后难以合并，甚至丢失数据。避免手段有几种：第一，多数派选举，只有获得超过半数节点投票的候选者才能当选主，多数派之间必然有交集，因此同一任期不可能出现两个主（Raft、ZooKeeper 都是这个思路）。第二，法定人数（quorum），配置集群节点数为奇数，读写要求多数派确认，少数派分区即使有旧主也无法完成提交。第三，仲裁节点（如 MongoDB 的 Arbiter、Redis Sentinel 的仲裁），用轻量节点参与投票凑够多数派。第四，心跳与租约机制，主节点必须持续获得多数派对租约的续期，一旦续约失败就主动降级为从，不再接受写请求。第五，fencing 隔离，切主后强制隔离旧主，比如通过 STONITH 断电或网络隔离，防止旧主继续写入。运维上要避免不合理的跨机房部署和设置过短的心跳超时，并对选举、任期变化做监控告警，及时发现异常切换。

**常见追问**：Redis Sentinel 会不会脑裂，怎么缓解？为什么集群节点数建议用奇数？

## 40. 如何设计一个限流防刷系统（如防短信轰炸）？

> 原题 ID：`q4124`

**高频程度**：★★★★★

**考察点**：考察多维度限流、人机校验与风控的组合防刷设计。

**回答框架**：

①多维度限流：按手机号、IP、设备指纹、用户 ID 分别计数，滑动窗口加令牌桶。②图形验证码或人机校验前置，拉长攻击成本。③行为风控：频次异常、号码段异常、时间分布异常评分。④兜底：黑名单、告警、以及与运营商和业务侧的联动。

**参考回答**：

防短信轰炸要从多个维度限制并提高攻击成本。第一，多维度限流：不能只按 IP 限，因为攻击者会换 IP，要对手机号、IP、设备指纹、用户 ID、接口维度分别计数，用滑动窗口或令牌桶实现，并做组合限制，比如同一手机号每分钟最多 1 条、每天最多 10 条，同一 IP 每分钟最多 20 次，全局设置总配额防止被刷爆短信费用；计数用 Redis 加 Lua 保证原子性。第二，人机校验前置：在发送前增加图形验证码、滑块或行为验证，把人机识别的成本加到攻击者身上，这是防刷最有效的第一道闸门；验证通过后下发一次性 token，发送接口必须校验该 token 且只能用一次。第三，行为风控：对请求的频次分布、号码段、时间段、设备特征做评分，识别异常模式（比如某个 IP 段在凌晨集中请求完全不同的号码），命中规则则拦截或要求二次验证。第四，兜底与联动：维护手机号与 IP 黑名单，超限时返回统一的友好提示避免泄露判定规则，同时配置告警，当短信发送量异常升高时及时通知运维并支持一键关闭通道；对涉及资损或骚扰的严重情况与运营商和法务联动处理。整体思路是前端拉高攻击成本、服务端多维度限流、后台风控兜底，三层叠加。

**常见追问**：只按 IP 限流为什么不够？验证码被破解或打码平台绕过怎么办？

## 41. 基于 Redis 实现分布式锁有什么优缺点？

> 原题 ID：`q0440`

**高频程度**：★★★★

**考察点**：考察 Redis 分布式锁的性能优势与可靠性短板。

**回答框架**：

①优点：性能高、实现简单、SET NX PX 原子加锁、Lua 释放、有成熟客户端（Redisson）。②缺点：主从异步复制导致切换丢锁、依赖过期时间与续期、不可重入需自行实现、Redlock 有争议。③适用：高并发、能接受极小概率失效且业务有幂等兜底的场景。④对比：强一致场景改用 ZooKeeper 临时顺序节点。

**参考回答**：

Redis 实现分布式锁的优点很明显：性能高、延迟低，单机就能支撑十万级 QPS，远高于基于数据库或 ZooKeeper 的方案；实现简单，用 SET key value NX PX 一条命令就能原子加锁，用 Lua 脚本原子释放；生态成熟，Redisson 等客户端已经封装了自动续期（看门狗）、可重入、公平锁等能力，接入成本低。缺点也比较突出：第一，可靠性依赖 Redis 的可用性，主从架构下异步复制意味着主节点加锁成功但未同步到从节点时主节点宕机，从节点升主后新的客户端还能拿到同一把锁，互斥被破坏；官方用 Redlock 多节点多数派缓解，但 Redlock 本身在时钟漂移和 GC 停顿下仍有争议。第二，强依赖过期时间，超时太短业务没跑完锁就释放，超时太长又影响故障恢复，需要看门狗续期，而续期线程自身也可能出问题。第三，原生 SETNX 不支持可重入，需要用 Hash 结构记录持有者和重入次数自行实现。因此选型建议是：高并发、允许极小概率失效、且业务侧有幂等或唯一索引兜底的场景用 Redis 锁；对强一致和可靠性要求高的场景改用 ZooKeeper 临时顺序节点。

**常见追问**：Redisson 的看门狗实现原理是什么？什么业务绝不能用 Redis 锁？

## 42. 什么是降级？降级和熔断的区别是什么？

> 原题 ID：`q0960`

**高频程度**：★★★★★

**考察点**：考察降级定义及与熔断的定位差异。

**回答框架**：

①降级定义：系统资源不足或依赖不可用时，主动牺牲非核心功能或返回次优结果，保证核心链路可用。②降级方式：功能开关、返回兜底数据、走简化逻辑、转人工。③熔断定义：下游故障时快速失败切断调用，避免级联雪崩。④区别：熔断是故障隔离手段（自动、基于错误率），降级是业务有损策略（可手动或自动），熔断通常触发降级，但降级不一定要熔断。

**参考回答**：

降级指当系统资源不足或依赖服务不可用时，主动牺牲一部分非核心功能或返回次优结果，把资源集中保证核心链路的可用性。典型做法有三种：功能层面用开关关闭非核心功能（如关闭推荐、关闭评论、暂停报表刷新）、数据层面返回兜底内容（如推荐服务挂了返回热门榜单、商品详情降级只返回基础字段、缓存拿不到就返回默认值或旧数据）、流程层面走简化逻辑或转人工（如风控超时改人工审核、智能客服失败转人工）。降级的核心是「有损但可用」，需要配合降级开关、预案和监控，并且故障恢复后能自动或手动恢复。熔断与降级的区别在于：熔断是一种故障隔离机制，当下游的错误率或超时率达到阈值时自动打开，让请求快速失败而不是继续调用故障依赖，目的是防止级联失败把调用方也拖垮，它关注的是「不要被坏依赖拖死」；降级是一种业务有损策略，关注的是「保住什么、牺牲什么」，可以由熔断触发，也可以由运维手动触发，比如大促前主动关掉非核心功能。所以两者关系是：熔断往往是降级的触发条件之一，打开后通常会走降级逻辑返回兜底结果，但降级不一定需要熔断，熔断也不一定意味着降级（也可以直接快速失败）。

**常见追问**：降级开关怎么做成动态生效的？关掉非核心功能时如何保证数据一致性？
