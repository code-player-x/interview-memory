## 1. 一个每秒 10w QPS 的高并发系统，要求实时输出“最近 1 小时”内访问频率最高的10个IP，你会如何设计？

> 原题 ID：`q0084`

**高频程度**：★★★★

**考察点**：考察高并发下的实时 TopN 统计与滑动窗口设计，以及精确与近似的取舍。

**回答框架**：

①本地分片计数：各节点用分段锁或时间分桶的 HashMap<IP,count> 统计。②滚动窗口：按分钟分桶/环形数组，淘汰 1 小时外数据。③全局合并：聚合层秒级拉取各节点局部 TopK 做堆合并，或 Redis ZSet/Count-Min Sketch。④取舍：精确成本高，近似 TopK 可接受误差时省内存。

**参考回答**：

**回答：**分治：① 各节点本地用『时间分片计数』（如每分钟一个 HashMap<IP,count>）统计；② 用滚动时间窗（环形数组/滑动窗口）淘汰 1 小时外数据；③ 中心层定期拉取各节点分片做『堆排序合并』得全局 Top10；或用 Redis 计数+ZSet/Count-Min Sketch 近似。

**详细展开：**10w QPS 单机扛不住全局精确。方案：本地增量计数（无锁/分段锁）+ 按分钟分桶；实时性要求高就用『流处理（Flink）』做窗口聚合；或 Count-Min Sketch 近似 TopK（省内存、可接受误差）。全局 Top10 由聚合服务周期性（秒级）合并各分片局部 TopK。注意 1 小时窗口的过期淘汰与热点 IP 的内存放大。

**加分项：**提到分片+合并、滑动窗口淘汰、Count-Min Sketch 近似算法、以及『精确 vs 近似』的取舍。

## 4. 什么是CAP理论？

> 原题 ID：`q0950`

**高频程度**：★★★★★

**考察点**：考察分布式理论基本功，重点是 P 不可舍弃、CA 在分布式下不存在这一常见误区。

**回答框架**：

①三个要素定义：一致性 C、可用性 A、分区容错性 P。②三选二的真实含义：网络分区客观存在，P 必须保，实际是在 C 与 A 之间取舍。③典型系统：CP 如 ZooKeeper/etcd，AP 如 Eureka/Cassandra。④延伸：BASE 理论、一致性与延迟的关系。

**参考回答**：

CAP理论是分布式系统中的核心概念，主要包含三个要素：

1. **一致性（Consistency）**：所有节点在同一时间看到的数据是相同的。
2. **可用性（Availability）**：每个请求都能收到响应，无论成功或失败。
3. **分区容错性（Partition Tolerance）**：系统在网络分区的情况下仍能继续运行。

根据CAP理论，分布式系统最多只能同时满足其中两个要素，无法三者兼顾。具体表现为：

- **CA系统**：保证一致性和可用性，但无法容忍网络分区，通常用于单点或小规模集群。
- **CP系统**：保证一致性和分区容错性，但在网络分区时可能牺牲可用性，适合对一致性要求高的场景，如金融系统。
- **AP系统**：保证可用性和分区容错性，但可能牺牲一致性，适合对高可用性要求高的场景，如社交网络。

在实际应用中，系统设计需根据具体需求权衡这三个要素。

**常见追问**：P 在什么情况下可以放弃？最终一致性怎么保证「读己之写」？

## 6. 秒杀一千万个商品，20wQPS：怎么设计？只考虑库存扣减环节，请简要回答设计要点？

> 原题 ID：`q0984`

**考察点**：考察极高 QPS 下单点库存扣减的横向扩展与热点处理。

**回答框架**：

①Redis 集群分片：库存按商品维度打散到 redis 集群，用 DECR 原子扣减。②本地缓存：热点商品在应用层加本地缓存或请求合并，减轻缓存层压力。③分片与负载均衡：服务多实例横向扩展，避免单点过载。④数据库兜底：乐观锁或版本号防超卖，MQ 异步落库。

**参考回答**：

针对秒杀场景下库存扣减环节，要达到20万QPS的设计要点可以简要概括如下：

1. **使用缓存技术库存扣减**：采用高性能缓存系统如**Redis集群**来存储商品库存信息，利用其原子操作（例如`DECR`命令）实现高效且一致的库存扣减。对于热点商品，还可以考虑在应用层使用本地缓存进一步减轻缓存系统的压力。

3. **乐观锁或版本控制**：在数据库层面采用乐观锁机制或者版本号控制，防止超卖问题的发生。虽然主要依赖于缓存进行扣减操作，但最终需要同步到数据库时，这一步骤非常重要。
4. **限流、降级与排队机制**：实施限流措施限制进入系统的请求数量，保护后端服务不被瞬间大流量冲击。对超出即时处理能力的请求，可采用排队机制延迟处理，保证系统稳定运行。
5. **异步处理**：结合消息队列等异步处理方式，将部分非实时性要求的操作（如订单生成、支付确认后的库存更新等）异步化，降低库存扣减环节的直接压力。

这些要点共同作用，旨在构建一个既能够承受高并发访问又能够保证数据准确性的秒杀系统库存扣减解决方案。

**回答**

短链的好处：

第一：对于某些限制内容长度的平台，使用短链可以输入更多的内容

第二：在将链接转换为二维码时，短链生成的二维码更容易识别

第三：有些平台无法识别特殊的长链参数，转为短链就没这个问题

第四：节省成本，需要发短信时，短信是按照长度计费的，短网址可以节省成本

**1. 系统需求分析**

**2. 系统设计**

**（1）短链生成算法**

- **哈希算法**：使用哈希函数（如MD5、SHA256）对长URL进行哈希，取前N位作为短链。

  - 优点：简单易实现。缺点：可能存在哈希冲突，难以设计出一个没有冲突的Hash算法。
- **分布式ID生成**：使用分布式ID生成算法（如雪花算法）生成唯一ID，将ID转换为62进制（a-zA-Z0-9）作为短链。优点：无冲突，可扩展。**（6位可以表示62^6=570亿条短链）**

- **转换规则**：

  - 将十进制数（如雪花算法生成的ID）不断除以62，取余数作为索引，从字符集中获取对应字符，直到商为0。
  - 最终将字符逆序排列，得到62进制字符串。
- 冲突解决

  - **增加校验位**：在短链中加入校验位，确保即使余数相同，短链也不同。
  - **使用更长的短链**：增加短链的长度，减少冲突的概率。
  - **唯一性检查**：在生成短链后，进行唯一性检查，如果冲突则重新生成。
**校验位的生成方法**
校验位的生成通常基于某种算法，常见的算法包括：
- **模运算**：对原始短链的字符值进行某种模运算，生成一个校验位。
- **哈希函数**：对原始短链进行哈希运算，取哈希值的某一位作为校验位。
- **CRC（循环冗余校验）**：使用CRC算法生成校验位。
短链生成算法主要用于将长URL转换为短链，常见的算法包括：
1. **哈希算法**

- **Base62/Base64编码**：将哈希值转换为更短的字符串。
冲突处理：
- 使用唯一ID或时间戳作为哈希输入。
- 检测冲突后，重新生成或附加随机字符。
2. **自增ID**
- 使用数据库自增ID，转换为Base62/Base64编码。
- **优点**：简单且无冲突。
- **缺点**：可能暴露业务量，需确保ID生成器高可用。
3. **随机字符串**

2. **增加随机性**：在哈希值或随机字符串中加入时间戳或随机数。
3. **分布式锁**：在高并发环境下使用分布式锁，确保短链生成的唯一性。
4. **预生成短链池**：提前生成短链，使用时从池中取出，避免实时生成冲突。

## 10. 单点登录系统设计：设计一个单点登录系统？

> 原题 ID：`q0988`

**高频程度**：★★★★

**考察点**：考察 IdP/SP 模型、令牌机制与跨域会话共享。

**回答框架**：

①角色：身份提供者 IdP 统一认证，服务提供者 SP 依赖 IdP 鉴权。②流程：重定向到 IdP 登录、签发安全令牌、SP 校验令牌、建立本地会话。③令牌：JWT 或 SAML 断言，签名与加密防篡改。④安全与扩展：HTTPS、会话超时与单点注销、支持 OAuth/OIDC 与多因素认证。

**参考回答**：

设计一个单点登录（Single Sign-On, SSO）系统，主要是为了在多个应用服务间共享用户的身份验证状态，使得用户只需一次登录就可以访问所有信任该SSO系统的应用。以下是简要的设计思路：

**1. 核心概念**

- **身份提供者(IdP)**：负责处理用户的认证过程，并向服务提供商(SP)发出身份验证声明。
- **服务提供商(SP)**：依赖IdP进行用户身份验证的服务或应用。

**2. 实现步骤**

a. 用户首次登录请求

当用户尝试访问任一SP时，如果尚未登录，则重定向到IdP的登录页面。

b. 用户认证

在IdP上完成用户名和密码等信息的验证。一旦验证成功，IdP会生成一个包含用户身份信息的安全令牌（如JWT、SAML断言等），并将其返回给客户端浏览器。

c. 安全令牌交换

客户端携带这个安全令牌再次访问最初请求的SP。SP收到令牌后，首先需要验证其有效性（通常通过与IdP直接通信或者使用公钥加密技术），然后建立自己的会话。

d. 创建本地会话

一旦SP确认了令牌的有效性，它将在本地为用户创建一个会话，允许用户无需再次登录即可访问该服务。

**3. 安全考虑**

- **传输层安全性**：确保所有的认证流程都通过HTTPS协议进行，以保护数据不被窃听。
- **令牌安全性**：采用合适的签名和加密机制来保护令牌，防止篡改和伪造。
- **会话管理**：正确管理用户会话，包括超时设置、注销流程等，以增强安全性。

## 17. 我有一千万个URL，10MB内存，怎么排序？

> 原题 ID：`q0998`

**高频程度**：★★★★

**考察点**：考察外部排序流程与容量估算，重点是分块加多路归并。

**回答框架**：

①容量估算：按 URL 平均长度估算单块条数，据此决定分块数量。②分块排序：块内内存排序后写磁盘。③多路归并：小顶堆选最小输出，块读完换下一块。④优化：压缩公共前缀、二进制存储减少 IO、分块阶段并行。

**参考回答**：

在内存有限（10MB）的情况下，对一千万个 URL 进行排序，可以采用外部排序（External Sorting）技术。以下是具体步骤：

1. **分块排序**

- 将一千万个 URL 分成多个小块，每个小块的大小适合在内存中排序。
- 假设每个 URL 平均长度为 100 字节，10MB 内存可以容纳约 10MB / 100B = 100,000 个 URL。
- 将数据分成 10,000,000 / 100,000 = 100 个小块。
- 对每个小块在内存中进行排序（如使用快速排序、归并排序等），并将排序后的小块写入磁盘。

2. **归并排序**

- 将所有排序后的小块进行归并排序。
- 由于内存有限，可以使用多路归并（K-way Merge）：

  1. 每次从 K 个小块中读取一部分数据到内存中（K 的值取决于内存大小）。
  2. 使用最小堆（Min-Heap）选择最小的 URL 输出到最终结果文件。
  3. 当一个块的数据用完后，从磁盘读取下一个数据块。
- 重复上述过程，直到所有小块的数据归并完成。

3. **优化**

- **压缩 URL**：如果 URL 有共同前缀（如 `http://`），可以压缩存储以减少内存占用。
- **外部存储**：使用高效的存储格式（如二进制文件）来存储排序后的小块，减少磁盘 I/O。
- **多线程**：在分块排序阶段，可以使用多线程并行处理多个小块，加快排序速度。

总结

通过分块排序和多路归并，可以在有限内存下对大规模数据进行排序。这种方法的核心思想是\*\*分而治之\*\*，将大问题分解为小问题，逐步解决。

## 20. MongoDB中的数据复制是如何工作的？

> 原题 ID：`q1039`

**高频程度**：★★★

**考察点**：考察 oplog 机制驱动的异步复制原理与选举触发。

**回答框架**：

①写入路径：所有写先到 Primary。②oplog：Primary 把写操作记录到 oplog 这个特殊集合。③同步：Secondary 长连接拉取 oplog 并回放，实现异步复制。④延迟与选举：复制存在延迟，Primary 故障时按优先级和最新数据触发选举。

**参考回答**：

MongoDB中的数据复制是通过复制集（Replica Set）来实现的。复制集是一组维护相同数据集的MongoDB服务器的集群，其中包括一个主节点（Primary）和一个或多个从节点（Secondary）。

数据复制的工作原理如下：

1. **主节点写入**：所有的写操作都首先在主节点上执行。
2. **Oplog（操作日志）**：主节点会将所有的写操作记录在一个特殊的集合中，这个集合叫做Oplog（操作日志）。Oplog保存了一份主节点上的所有写操作的记录。
3. **从节点同步**：从节点通过长时间保持与主节点的TCP连接，实时复制主节点上的Oplog。从节点不仅复制写操作，还复制删除和更新操作，以确保数据的一致性。
4. **数据复制延迟**：从节点复制Oplog的过程可能存在一定的延迟，导致从节点上的数据稍微滞后于主节点。这个延迟通常是可配置的。
5. **选举新的主节点**：如果主节点发生故障，复制集会在从节点中选择一个新的主节点。这个过程通常是自动的，复制集中的成员会根据配置中的优先级、可用性等条件选择新的主节点。

通过这种方式，MongoDB的复制集提供了数据冗余、高可用性和故障恢复的功能。当主节点发生故障时，系统可以迅速切换到一个可用的从节点，确保服务的持续可用。

**常见追问**：oplog 太小会有什么后果？复制延迟很大时读从节点会出现什么问题，怎么监控？

## 22. 如果从0开始做一个项目，如何设计架构（按业务怎么分）？

> 原题 ID：`q3545`

**高频程度**：★★★★★

**考察点**：考察从零做架构时按业务能力划分领域、确定数据流与演进路径的能力。

**回答框架**：

①明确业务目标与非功能需求，架构是取舍。②按业务能力而非技术分层划分领域（DDD 限界上下文）。③确定数据流与依赖方向：同步走 API/RPC，跨域状态变更走领域事件。④领域内分层、存储选型（每个领域独享数据库）、扩展性与横切关注点。⑤取舍：核心交易强一致、非核心最终一致，优先模块化单体按需拆分。

**参考回答**：

从零设计架构的核心是：先按业务能力而非技术划分领域边界，再确定数据流与依赖方向，最后为扩展性预留接口和异步事件机制，避免过度设计。步骤是：第一，明确业务目标与非功能需求，先问清核心用户是谁、核心用例是什么、QPS 与数据量、一致性与延迟要求、团队规模和交付节奏，架构是取舍，没有需求就没有架构。第二，按业务能力划分领域，用 DDD 限界上下文，不要按 controller/service/dao 这种技术分层做一级划分，而是按业务能力切，例如电商分为用户、商品、库存、订单、支付、营销、履约，每个领域高内聚低耦合、拥有自己的数据和对外接口。第三，确定数据流与依赖方向，同步调用走 API 或 RPC，跨领域的状态变更走领域事件（如 OrderCreated、PaymentSucceeded）通过 MQ 解耦，依赖方向单向、避免循环依赖。第四，领域内部再分层，接口层、应用层、领域层、基础设施层，让业务逻辑不依赖具体技术，领域层定义 Repository 接口由基础设施实现。第五，存储选型按访问模式来，交易数据用关系型，热点读用 Redis，搜索用 ES，日志事件用 Kafka，报表用 OLAP，每个领域独享数据库避免共享表导致耦合。第六，扩展性上初期用模块化单体按领域分包、接口清晰，当某领域压力大或团队拆分时再抽成独立服务，预留插件、事件订阅、配置化等扩展点。第七，横切关注点如日志、链路追踪、监控告警、配置中心、鉴权、幂等、限流熔断统一作为基础设施不侵入业务。取舍原则是核心交易强一致、非核心最终一致，强依赖同步、通知统计异步，团队小业务未稳时优先单体，非核心不重复造轮子。

**常见追问**：库存扣减到底是订单流程的一部分还是独立领域，怎么判断？Outbox 模式解决了什么问题？

## 23. 大文件上传如何优化（断点续传）？

> 原题 ID：`q4123`

**高频程度**：★★★★★

**考察点**：考察分片上传、哈希校验、秒传与断点续传的完整方案设计。

**回答框架**：

①分片：前端按固定大小（如 5MB）切片，避免单次失败重传全部。②校验：每片计算 hash，服务端记录已传分片，支持秒传与断点续传。③合并：全部片到齐后用 append 合并，校验整体 hash 保证完整性。④优化：并发上传加进度反馈，失败只重传失败分片，分片元数据用 Redis 或数据库记录。

**参考回答**：

核心是分片上传、hash 校验、秒传、合并、断点续传五步。第一，前端分片：把大文件按固定大小（如 5MB）切成多个分片，避免单次请求失败就重传整个文件。第二，计算哈希：对每个分片计算 hash（如 md5），再对整个文件计算一次整体 hash 作为文件唯一标识。第三，校验与秒传：上传前先用文件整体 hash 询问服务端是否已存在，存在则直接秒传返回，不需要真正上传；上传分片时服务端按分片 hash 校验该分片是否已传过，已传则跳过。第四，断点续传：服务端记录每个文件已上传的分片列表（可用 Redis 或数据库存 uploadId 与已传分片序号），用户重新进入上传时先拉取已传分片，只传缺失的部分。第五，合并与校验：所有分片到齐后按顺序用 append 合并成完整文件，再校验整体 hash 与声明一致，防止传输损坏。优化上可以并发上传多个分片提升速度、进度条基于已传分片数计算、失败只重传失败的分片、分片大小要在并发度与请求开销之间权衡（太小请求多、太大重传代价高），另外要考虑分片元数据的过期清理和并发上传同一文件的去重。

**常见追问**：分片大小怎么选？如果上传到一半用户换了网络或刷新页面，怎么保证续传能对上？

## 24. 如何设计一个排行榜？

> 原题 ID：`q4120`

**高频程度**：★★★★★

**考察点**：排行榜设计：ZSet 实时排序、ZINCRBY 更新分数、ZREVRANGE 取 TopN、持久化与分片扩展。

**回答框架**：

1）核心结构：Redis ZSet，member 是用户/对象，score 是分数；2）更新：ZINCRBY 原子加分，或 ZADD 直接设置；3）查询：ZREVRANGE 取 TopN，ZREVRANK 查排名，ZSCORE 查分数；4）持久化：定时落库或通过消息队列异步写 DB，保证可恢复；5）扩展：数据量极大时按维度分片（比如按榜单 ID 或时间段），或分片 ZSet 加归并；6）注意大 key 与热 key 问题；7）时间维度榜单可用 key 加日期后缀。

**参考回答**：

排行榜最适合用 Redis 的 ZSet 实现，因为它天然按 score 排序且支持排名查询。具体设计：第一，数据结构，ZSet 的 member 存用户 ID 或对象 ID，score 存分数（比如积分、票数、热度值）。第二，更新，用户分数变化用 ZINCRBY 原子加分，或者用 ZADD 直接设置新分数，这两个操作都是 O(logN) 且原子，无需加锁。第三，查询，取前 N 名用 ZREVRANGE key 0 N-1 带 WITHSCORES，查某用户排名用 ZREVRANK，查分数用 ZSCORE，取某个分数区间用 ZRANGEBYSCORE；这些操作分别是 O(logN + M) 和 O(logN)，性能很好。第四，持久化，Redis 是内存存储，榜单数据需要落库，可以定时全量落库，或者用消息队列把分数变更异步写回 MySQL/数仓，重启或故障时从库里重建 ZSet；注意如果分数是实时算出来的，也可以选择不落库，靠源数据重算。第五，扩展与治理。数据量极大时（比如千万级用户的全站排行），单个 ZSet 会变成大 key 且占用大量内存，可以考虑：按维度拆分（比如按地区、按榜单 ID 分成多个 ZSet），或者按用户 ID 分片成多个 ZSet，取 TopN 时对每个分片取前 N 再归并；时间维度的榜单（日榜、周榜）用 key 加日期后缀，并对旧 key 设置过期或归档。第六，要关注热 key 问题：如果是全站超热榜单，可以加本地缓存、多副本打散。总结起来就是"ZSet 做实时排序、异步落库保证可恢复、分片解决大 key、本地缓存解决热 key"。

**常见追问**：1）分数相同时排名怎么处理？2）分片 ZSet 怎么归并出全局 TopN？

## 25. 如何设计一个『附近的人』功能？

> 原题 ID：`q4121`

**高频程度**：★★★★

**考察点**：附近的人功能设计：地理索引（GeoHash/Redis GEO）、半径查询与距离排序、精度与性能优化、城市维度预筛。

**回答框架**：

1）核心：把用户经纬度存入地理索引（Redis GEO 基于 ZSet + GeoHash，或 MySQL 空间函数）；2）写入：GEOADD 添加位置；3）查询：GEOSEARCH/GEORADIUS 按半径搜索并返回距离、排序；4）原理：GeoHash 把二维经纬度编码成一维字符串，前缀相同的点地理上邻近，可转成 ZSet 的 score 做范围查询；5）优化：按城市或网格预筛减少候选、控制返回数量、位置更新用异步；6）权衡：精度 vs 性能、隐私与权限。

**参考回答**：

附近的人核心是要支持"给定一个坐标和半径，找出范围内的点并按距离排序"。实现上主要有两种选择。第一种是用 Redis 的 GEO 能力，这是最常用的：GEOADD 把用户的经纬度加进去，GEOSEARCH（新命令，替代 GEORADIUS）可以按半径或矩形范围查询，并支持返回距离、按距离排序、限制返回数量。它的底层原理是 GeoHash——把二维的经纬度编码成一维字符串，地理上邻近的点前缀相同，Redis 再把它转成 ZSet 的 score，就能用 ZSet 的范围查询（ZRANGEBYSCORE）快速筛出候选，然后再精确计算距离排序。第二种是数据库方案，MySQL 有 ST_Distance_Sphere 等空间函数，PostGIS 这类专业地理库能力更强，适合需要复杂空间查询和事务的场景，但性能不如 Redis。工程上要注意几点：第一，精度和性能的权衡，GeoHash 编码位数越长精度越高、但匹配越严格，Redis 用的是 52 位精度，误差在米级以内，一般够用；第二，数据量大时要减少候选集，常见做法是先按城市维度或网格预筛，只在同一城市/网格内做半径查询，避免全国范围全量扫描；第三，用户位置更新频繁（比如骑手、司机），写入量很大，可以考虑异步更新、降低更新频率、或者用专门的时空数据库；第四，返回结果要限制数量并做分页，避免一次返回过多；第五，隐私与权限要考虑，比如只对已授权用户展示位置、做位置模糊化。整体思路是"地理索引做快速筛选 + 精确距离计算做排序 + 城市/网格预筛控规模"。

**常见追问**：1）Redis GEO 和 PostGIS 该怎么选？2）位置更新特别频繁怎么优化？

## 27. 本项目需要同时存储结构化数据（简历、面试记录）和向量数据（文档 Embedding）。方案对比？

> 原题 ID：`q1972`

**高频程度**：★★★

**考察点**：考察结构化数据与向量数据的存储选型。

**回答框架**：

1) 两类数据的本质差异；2) 三种方案对比；3) 选型依据；4) 一致性处理。

**参考回答**：

结构化数据比如简历、面试记录，字段固定、强事务、需要 JOIN、按主键和条件精确查询，典型诉求是 ACID 和一致性；向量数据是文档 Embedding，高维浮点数组，核心操作是 ANN 近似最近邻检索，需要 HNSW、IVF、DiskANN 这类向量索引，对召回率、延迟、内存敏感，常伴随元数据过滤。方案有三种：一是单一关系库加向量扩展，比如 PostgreSQL 加 pgvector，优点是存储统一、事务一致、SQL 直接 JOIN 做元数据过滤、运维简单，适合中小规模（百万级向量以内），缺点是向量索引性能和规模不如专用库，超大规模或高并发会成瓶颈；二是关系库加专用向量库，比如 MySQL 加 Milvus 或 Qdrant，优点是各司其职，向量库为 ANN 深度优化、可水平扩展支持十亿级，关系库保证业务事务，缺点是双写一致性、跨库 JOIN 要在应用层拼装、运维复杂度上升；三是支持向量类型的一体化数据库。我的默认选择是方案二，通过业务主键关联，避免用同一存储硬扛两类负载。

## 30. 模块之间如何交互？

> 原题 ID：`q1481`

**高频程度**：★★★★

**考察点**：考察对「模块之间如何交互」的掌握，重点看能否讲清：模块交互指系统中不同功能单元（模块）之间如何通信与协作

**回答框架**：

同步调用（函数调用/RPC/HTTP）：调用方阻塞等待结果，简单直观，适合强一致、实时性要求高的场景；缺点是耦合调用方与被调方可用性，容易级联故障。；异步消息（MQ）：通过队列/主题解耦，生产者只负责发，消费者按能力消费，适合削峰、解耦、最终一致；代价是复杂度上升（重复消费、顺序、事务消息）。；事件驱动：模块发布领域事件，其他模块订阅，实现‘谁关心谁处理’，进一步降低耦合；但事件链难追踪，需可观测性。；共享数据/共享内存：性能高但耦合最强，容易产生隐式依赖，一般只用于同进程内高性能场景。；依赖倒置：高层模块依赖抽象接口，不依赖具体实现。；接口隔离：接口尽量小、职责单一，避免‘胖接口’导致无关模块被迫一起变。

**参考回答**：

模块交互的核心是定义清晰、稳定、低耦合的接口契约，通过同步调用、异步消息或事件驱动等方式传递数据与控制，让模块可独立开发、测试与演进。

模块交互指系统中不同功能单元（模块）之间如何通信与协作。关键不是‘怎么调’，而是‘约定什么’。 1) 交互的本质：接口契约。契约包含：输入/输出数据结构、调用语义（同步/异步、幂等性）、错误码、超时与重试策略、版本兼容规则。就像两个人合作，先约定‘我说什么、你回什么、出错怎么办’，而不是直接闯进对方房间翻东西。 2) 常见交互方式： - 同步调用（函数调用/RPC/HTTP）：调用方阻塞等待结果，简单直观，适合强一致、实时性要求高的场景；缺点是耦合调用方与被调方可用性，容易级联故障。 - 异步消息（MQ）：通过队列/主题解耦，生产者只负责发，消费者按能力消费，适合削峰、解耦、最终一致；代价是复杂度上升（重复消费、顺序、事务消息）。 - 事件驱动：模块发布领域事件，其他模块订阅，实现‘谁关心谁处理’，进一步降低耦合；但事件链难追踪，需可观测性。 - 共享数据/共享内存：性能高但耦合最强，容易产生隐式依赖，一般只用于同进程内高性能场景。 3) 设计原则： - 依赖倒置：高层模块依赖抽象接口，不依赖具体实现。 - 接口隔离：接口尽量小、职责单一，避免‘胖接口’导致无关模块被迫一起变。 - 迪米特法则：只与直接朋友通信，减少跨层调用。 - 契约版本化：接口变更要向后兼容，如加字段而非改字段，用版本号或兼容层过渡。 4) 通俗类比：模块像公司部门。同步调用像打电话，必须对方接听才能继续；异步消息像发邮件/工单，发完就走，对方有空处理；事件驱动像公司广播，谁关心谁响应。接口契约就是公司规定的公文格式和流程，格式稳定，部门才能各自独立运转。 5) 适用场景：强一致、低延迟选同步；高并发、可容忍最终一致选异步；跨团队、跨系统解耦选事件驱动；同进程高性能选共享内存但需谨慎。

**常见追问**：如何避免「1) 只答‘通过接口调用’，不区分同步/异步/事件，缺乏场景判断」？ 「2) 认为异步一定比同步好，忽略复杂度、一致性和运维成本」在真实项目中应如何规避？

## 31. 控制器，调度器，kubelet中的监听，是监听etcd吗？

> 原题 ID：`q0922`

**高频程度**：★★

**考察点**：考察 K8s 组件是否直接监听 etcd，以及 apiserver 作为唯一入口的架构原因。

**回答框架**：

1.结论：控制器、调度器、kubelet 都不直接监听 etcd；2.机制：统一通过 apiserver 的 Watch API 监听资源变化；3.原因一：安全，apiserver 提供认证、鉴权、审计；4.原因二：抽象，屏蔽底层存储，etcd 可替换；5.原因三：一致性，apiserver 负责缓存、冲突检测与准入控制。

**参考回答**：

在 K8s 中，控制器（Controller）、调度器（Scheduler）和 kubelet 并不直接监听 etcd，而是通过 **`apiserver`**的 **`WatchAPI`** 监听资源变化。这是 Kubernetes 架构的核心设计之一，具体流程如下：

**1. 所有监听均通过`apiserver`**

- **etcd 是唯一的状态存储**，但组件不直接访问它，而是通过 API Server 的**`Watch`接口** 订阅资源变更。
- **原因**：  **安全性**：API Server 提供认证、鉴权、审计等能力。  **抽象性**：组件无需关心底层存储（etcd 可替换为其他存储）。  **一致性**：API Server 处理缓存、冲突检测等逻辑。

**2. 各组件监听流程**

**(1) 控制器（Controller）**

- **监听对象**：Deployment、ReplicaSet、Pod 等资源的事件（如创建、更新、删除）。
- **行为示例**：

  > - `Deployment Controller` 监听 `Deployment` 和 `ReplicaSet` 的变化。
  > - `ReplicaSet Controller` 监听 `ReplicaSet` 和 `Pod` 的变化。
- **触发逻辑**：当资源变更时，控制器对比 **期望状态（Spec）** 和 实际状态（Status），执行调和（Reconcile）。

**(2) 调度器（kube-scheduler）**

- **监听对象**：未调度（`Pending` 状态且 `nodeName` 为空）的 `Pod`。
- **行为示例**：发现新创建的 `Pod` 后，根据调度策略选择节点，向 API Server 发送绑定请求（更新 Pod 的 `nodeName`）。

**(3) kubelet**

- **监听对象**：调度到当前节点（`nodeName=kubelet所在节点`）的 `Pod`。
- **行为示例**：  发现新调度的 `Pod` 后，调用容器运行时（如 Containerd）启动容器。  持续上报 `Pod` 状态（如 `Running`、`Failed`）给 API Server。

**3. 关键设计思想**

- **事件驱动**：所有组件通过 Watch 机制实时响应变更，而非轮询。
- **水平扩展**：多个控制器实例可同时运行，依赖 APIServer 的乐观锁保证一致性。
- **声明式 API**：组件只需声明“期望状态”，由控制器负责调和实际状态。

**常见误解澄清**

- **etcd 的角色**：仅作为持久化存储，不参与事件推送。
- **API Server 的缓存**：提供高效的 Watch 接口，减轻 etcd 压力。
- **List-Watch 模式**：组件首次启动时会先 List 全量数据，再通过 Watch 增量更新。

**面试回答技巧**

- **简明版**：“K8s 组件通过 API Server 的 Watch 接口监听资源变化，而非直接访问 etcd。这种设计保证了安全性和扩展性。”
- **深入版**：“以 `Deployment` 创建为例：API Server 将配置写入 etcd 后，`Deployment Controller` 通过 Watch 感知到新对象，创建 `ReplicaSet`；`ReplicaSet Controller` 再创建 `Pod`；调度器和 kubelet 也通过 Watch 分别完成节点绑定和容器启动。”

这一设计是 Kubernetes 高可扩展性的核心，值得深入理解！

**常见追问**：如果 apiserver 挂了，现有 Pod 会怎样？为什么说 K8s 是声明式加控制器调和的架构？

## 33. 怎么在多台服务器同步session数据（数据库或者分布式系统）？

> 原题 ID：`q3347`

**高频程度**：★★★★

**考察点**：多机 Session 同步方案（粘性会话、集中式存储、Session 复制、JWT）、一致性与可用性权衡。

**回答框架**：

1）问题本质：Session 从进程内状态变成共享状态或让服务无状态；2）粘性会话：零改造但宕机丢会话、扩缩容重分布；3）集中式存储：Client→LB→无状态 App→Redis/DB，最常用；4）Session 复制：广播同步，节点多时网络开销大；5）JWT：签名自包含无状态，但无法主动失效、体积大。

**参考回答**：

单机 Session 存在本机内存，多台服务器时用户请求被负载均衡打到不同机器就出现登录态丢失，解决思路是把 Session 从"进程内状态"变成"进程外共享状态"，或者让服务本身无状态。常见四种方案。第一，粘性会话：LB 按 cookie 或 IP 哈希把同一用户固定到同一台机器，优点是零改造、无网络开销，缺点是机器宕机即丢会话、扩缩容导致重新分布，不满足高可用。第二，集中式 Session 存储，这是最常用的：架构是 Client→LB→无状态 App Server→Redis/DB，Redis 内存 KV 读写微秒级、支持 TTL 自动过期、可做主从/哨兵/Cluster 高可用；数据库持久化强但每请求读写 DB，QPS 高时成瓶颈，一般只做兜底或低频场景。第三，Session 复制：Tomcat 等容器支持在集群间广播同步 Session 副本，节点少时简单，但节点一多网络开销和内存冗余是 O(N²)，不推荐大集群。第四，JWT/客户端令牌：把状态签名后放在客户端，服务端完全无状态、天然适合多机和横向扩展，缺点是签发后无法主动失效，需要短过期加 refresh token 或黑名单来弥补，且 token 体积大、每次请求都携带。工程上一般选 Redis 集中式存储打底，配合合理的 Session TTL 与降级策略，对高并发无状态服务可以用 JWT。

**3.1.1 算法原理**

固定窗口限流是最简单直观的一种限流算法，其基本原理是将时间划分为固定大小的窗口，并在每个窗口内限制请求数量或速率。具体来说，就是将请求按照时间顺序放入时间窗口中，并计算该时间窗口内的请求数量，如果请求数量超出了限制，则拒绝该请求。

**算法步骤：**

1. 将时间划分为固定大小的窗口，例如每秒一个
2. 在每个时间窗口内，记录请求的数量
3. 当新的请求到达时，增加计数器的值加1
4. 如果计数器的值超过了预设的阈值（例如3个请求），则拒绝该请求
5. 当时间窗口结束时，重置计数器

**3.1.4 缺点**

1. 请求分布不均匀：在固定窗口算法中，请求在窗口内的分布可能会不均衡，导致某些窗口内的请求量超出阈值，而其他窗口内的请求较少。
2. 应对突发流量能力有限：由于固定窗口算法的窗口大小是固定的，无法灵活调整，因此难以应对突发的流量高峰。
3. 存在明显的临界问题：在窗口结束时重置请求计数可能会导致处理请求的不公平。例如，窗口结束前的最后一秒内请求数已达上限，而窗口开始时的第一秒内请求计数为零。

比如：限流阈值为每秒5个请求，单位时间窗口为1秒。如果在前0.5秒到1秒的时间内并发5个请求，接着在1秒到1.5秒的时间内又并发5个请求。虽然这两个时间段各自都没有超过限流阈值，但如果计算0.5秒到1.5秒的总请求数，则总共是10个请求，已经远远超过了1秒内不超过5个请求的限流标准。

**3.1.5 适用场景**

固定窗口算法适合在请求速率有明确要求且流量相对稳定的场景中使用。然而，对于应对突发流量和请求分布不均匀的情况，该算法可能表现不足，此时需要考虑使用其他更灵活的限流算法。

**3.2.1 算法原理**

滑动窗口其实也是一种通过将时间窗口划分为一个一个小的时间段来限流的方法，每个小的时间段又称之为小周期。相比于固定窗口限流，它可以根据时间滑动删除过期的小周期，以解决固定窗口临界值的问题。

比如要限制1s内的请求数量，让时间窗口为1s，在前面固定窗口分析中，会出现临界峰值问题，比如在0.5s和1.5s之间，这个1s时间段内的请求数就会出现大于阈值情况，那么滑动窗口就可以将1s窗口划分成两个小周期，每个0.5s。每隔0.5s，就往右滑动一个小周期，这样统计的整个窗口大小仍然是1s，只是过期的左边的那个小周期会随着时间删除，这样整个1s的统计周期就是随时间滑动的。

这样的话，在固定窗口中会出现的临界问题，比如0.5s和1.5s之假设来了10个请求，由于滑动窗口会统计到这个时间段，所以多余请求就会被拒绝。

```Go
    windowSize  time.Duration //窗口小周期大小
    maxRequests int           //最大请求数
    reqTimeList []time.Time   //窗口小周期内的请求时间
    reqMutex    sync.Mutex
}

func NewSlidingLimiter(widowSize time.Duration, maxReq int) *SlidingLimiter {
    return &SlidingLimiter{windowSize: widowSize, maxRequests: maxReq, reqTimeList: make([]time.Time, 0)}
}

func (limiter *SlidingLimiter) AllowReq() bool {
    limiter.reqMutex.Lock()
    defer limiter.reqMutex.Unlock()

    //移除过期请求
    curTime := time.Now()
    for len(limiter.reqTimeList) > 0 && curTime.Sub(limiter.reqTimeList[0]) > limiter.windowSize {
       // 最左边的小窗口要删除
       limiter.reqTimeList = limiter.reqTimeList[1:]
    }

    if len(limiter.reqTimeList) >= limiter.maxRequests {
       return false
    }
    limiter.reqTimeList = append(limiter.reqTimeList, curTime)
    return true

}
```

**3.3.1 算法原理**

漏斗限流算法的核心思想是将请求存储在一个漏斗中，**漏斗以固定的速率漏出请求**。如果漏斗被填满，新到达的请求将被丢弃。请求可以以不定的速率流入漏桶，而漏桶以固定的速率流出，所以漏斗算法可以将突发流量均匀地分配，确保系统在稳定的负载下运行。

算法步骤：

1. **设置桶的容量**：定义服务器在瞬间能够接受的最大请求数。
2. **确定处理速率**：设定每秒能够处理的请求数。
3. **请求处理计算**：

   - **计算处理完成的请求数**：

     - `已处理请求数 = （当前请求时间 - 上次请求时间）× 处理速率`
   - **更新当前请求数**：

     - `最新的当前请求数 = 当前请求数 - 已处理请求数`
4. **比较和处理请求**：

   - 如果当前请求数超过桶的容量，则拒绝本次请求。
   - 否则，允许请求通过，并将当前请求数增加1

**3.3.2 算法实现**

```go
package main

import (
        "fmt"
        "sync"
        "time"
)

type LeakyBucketLimiter struct {
        Rate           int    // 漏桶速率，每秒处理的请求数
        Capacity       int    // 漏桶容量，最多可存储请求数
        CurrentReqNum  int    // 当前漏斗中待处理的请求数，表示当前漏桶中的请求数
        LastTime       time.Time // 上次请求时间
        Lock           sync.Mutex // 请求锁
}

func (l *LeakyBucketLimiter) GetCurrentReqNum() int {
        return l.CurrentReqNum
}

func (l *LeakyBucketLimiter) GetRate() int {
        return l.Rate
}

func (l *LeakyBucketLimiter) GetCapacity() int {
        return l.Capacity
}

// NewLeakyBucketLimiter 初始化
func NewLeakyBucketLimiter(rate, capacity int) *LeakyBucketLimiter {
        return &LeakyBucketLimiter{
                Rate:        rate,
                Capacity:    capacity,
                LastTime:    time.Now(),
        }
}

func (l *LeakyBucketLimiter) Allow() bool {
        l.Lock.Lock()
        defer l.Lock.Unlock()

        // 计算两次请求间隔内应该要处理的请求数
        leakyReqCount := int(time.Since(l.LastTime).Seconds() * float64(l.Rate))

        if leakyReqCount > 0 {
                l.CurrentReqNum -= leakyReqCount
                l.LastTime = time.Now()
        }

        if l.CurrentReqNum < 0 {
                l.CurrentReqNum = 0
        }

        // 如果当前请求数在容量范围内，则请求通过且当前请求数+1(剩余待处理请求数+1)
        if l.CurrentReqNum < l.Capacity {
                l.CurrentReqNum++
                return true
        }
        return false
}

func MockRequest(n int, d time.Duration, l *LeakyBucketLimiter) {
        for i := 0; i < n; i++ {
                time.Sleep(d * time.Millisecond)
                if l.Allow() {
                        fmt.Printf("第%d个请求通过\n", i+1)
                } else {
                        fmt.Printf("第%d个请求被限流\n", i+1)
                }
        }
}

        fmt.Println("==================漏桶算法==================")
        // 创建一个漏桶，速率为每秒处理4个请求，容量为5个请求
        limiter := NewLeakyBucketLimiter(4, 5)
        // 发送10个请求，每50ms发送一个
        MockRequest(10, 50, limiter)
        fmt.Println("--------------------------------------------")
}
```

**3.3.3 优点**

1. **平滑处理请求速度**：漏斗限流能够有效地平滑限制请求的处理速度，防止瞬间请求过多导致系统崩溃或出现雪崩效应。
2. **适应流量变化**：可以通过控制请求的处理速度，使系统能够适应不同的流量需求，避免系统过载或资源过度闲置。
3. **灵活适应场景**：通过调整桶的容量和漏出的速率，漏斗限流可以满足不同的限流需求，灵活适应各种使用场景。

**3.3.4 缺点**

1. **无法动态调整流量**：漏斗的漏出速率是固定的，不够灵活，无法根据实际流量情况进行动态调整。
2. **突发流量处理有限**：在突发流量过大的情况下，漏斗可能很快被填满，大量请求将被拒绝，可能会导致服务质量下降。

**3.3.5 适用场景**

虽然漏斗可以以平滑的速度处理请求，但是仍然不能较好的应对突发流量，所以也是适用于流量相对稳定的场景。

**3.4.1 算法原理**

令牌桶算法限流是维护一个固定容量的存放令牌的桶，令牌以固定的速率产生，并放入桶中。每个令牌代表一个请求的许可。当请求到达时，需要从令牌桶中获取一个令牌才能通过。如果令牌桶中没有足够的令牌，则请求被限制或丢弃。

算法步骤：

1. **桶的容量**：定义桶的容量，即服务器在一瞬间最多可以接受的请求数。
2. **令牌生成速率**：定义令牌的生成速率，例如每秒生成的令牌数。
3. **计算当前令牌数**：

   - 每次请求时，计算桶中剩余的令牌数，也就是当前令牌数。

     - `(本次请求时间 - 上次请求时间) × 令牌生成速率 = 两次请求间隔内生成的令牌数`。
     - `当前令牌数（本次请求前剩余令牌数） + 请求间隔内生成的令牌数 = 最新的当前令牌数（本次请求后剩余令牌数）`。
4. **处理请求**：

   - 比较当前令牌数是否还有剩余，如果有则令牌数减一，请求得到正常处理。
   - 如果令牌耗尽，请求被拒绝。

**3.4.2 算法实现**

```go
type TokenBucket struct {
    capacity int       // 桶的最大容量
    tokens   float64   // 当前令牌数量
    rate     float64   // 每秒生成的令牌数
    lastTime time.Time // 上次更新时间
    mu       sync.Mutex
}

func NewTokenBucket(capacity int, rate float64) *TokenBucket {
    return &TokenBucket{
       capacity: capacity,
       tokens:   float64(capacity), // 初始时桶是满的
       rate:     rate,
       lastTime: time.Now(),
    }
}

func (tb *TokenBucket) Allow() bool {
    tb.mu.Lock()
    defer tb.mu.Unlock()

    now := time.Now()
    elapsed := now.Sub(tb.lastTime).Seconds() // 计算时间间隔
    tb.tokens += elapsed * tb.rate            // 增加令牌数量
    fmt.Printf("elapsed * tb.rate = %.5f , tb.tokens =%.5f  ", elapsed*tb.rate, tb.tokens)
    // 确保令牌数量不超过桶的容量
    if tb.tokens > float64(tb.capacity) {
       tb.tokens = float64(tb.capacity)
    }
    tb.lastTime = now

    // 如果有令牌，则允许请求
    if tb.tokens >= 1 {
       tb.tokens--
       return true
    }
    return false
}

func main() {
    tb := NewTokenBucket(5, 2.0) // 桶容量为 5，每秒生成 1 个令牌

    for i := 0; i < 10; i++ {
       if tb.Allow() {
          fmt.Println("Request allowed:", i)
       } else {
          fmt.Println("Request denied:", i)
       }
       time.Sleep(200 * time.Millisecond) // 模拟请求频率
    }
}
```

令牌桶的生成速度为每秒4个，即每250ms生成一个令牌，每50ms发起一次请求，到第5次、10次请求才会各生成一个令牌，其余请求均被拒绝，符合预期。

**3.4.3 优点**

1. **平滑流量**：令牌桶算法可以将突发流量平滑地分散在一定时间内，从而避免了流量高峰对系统的冲击。这有助于保持系统的稳定性和响应时间的一致性。
2. **灵活性高**：通过调整令牌的生成速率和桶的容量，可以灵活地控制流量。这样可以根据不同的需求和场景，优化系统的性能和资源使用率。
3. **允许突发流量**：由于令牌可以在桶中积累，当流量突然增大时，如果桶中有足够的令牌，系统可以快速响应这种突发流量，避免请求被立即拒绝。这使得令牌桶算法特别适合处理具有突发性流量的应用场景。

**3.4.4 缺点**

实现复杂：相对于固定窗口算法等其他限流算法，令牌桶算法的实现较为复杂。

**3.4.5 适用场景**

从令牌桶限流的优缺点就可以看出，令牌桶面对大量请求时具有柔性，且请求处理速度可以随请求速度而变。所以在适用场景上要更加宽泛一些，比如一些需要动态调整限流速率以及一些需要平滑处理突发流量的场景都合适。

**3.5 四种限流算法的对比**

前面介绍的集中算法实现一般只适用于单机版的限流，单机限流是指在单台服务器上，通过限制其在单位时间内处理的请求数量来防止过载。然而，随着微服务架构的广泛应用，系统服务通常分布在多台服务器上，但节点的应用流量往往不能准确的反应整个系统的流量压力，这时需要分布式限流来确保整个系统的稳定性。接下来，本文将介绍几种常见的分布式限流技术方案。

**4.1.1 实现原理**

所谓中心化的限流其实就是将原本设计实现在本地服务的眼流操作抽离出来，做成一个中心化的限流器，所有服务共享，这里其实选用一个中心化的组件去实现即可，一般选用redis来实现就很方便。

实现步骤：

1. 选用一个中心化组件，比如Redis
2. 设定限流规则，比如每秒允许的最大请求数（QPS），并将该值存储在Redis中
3. 每当有请求到达时，服务器首先向Redis请求令牌
4. 如果获得令牌，请求可以继续处理；如果未获得令牌，则表示请求被限流，此时可以返回错误信息或提示稍后重试

**4.1.2代码实现**

```go
        "fmt"
        "time"
```

1. **单点故障**：所有请求都必须经过Redis处理，所以Redis可能成为整个系统的性能瓶颈。但节点的redis场景下，当出现redis故障的时候，将会导致整个系统崩溃。所以可以使用使用Redis的主从复制或哨兵模式以实现高可用性。

**4.2 基于负载均衡的分布式限流方案**

前面分析了单机版的限流和基于中心化的限流都存在一定的问题，单机版主要是各个节点的流量分布可能不均匀，这将影响到限流阈值的设定，对限流精度造成干扰。而基于中心化的限流方案又会出现单点故障、网络带宽限制等问题。而这里的基于负载均衡的分布式限流其实就是针对单机版限流的一种改进，就是本地限流的基础上加上负载均衡器来均衡流量。

实现方案：

1. **请求分发：**通过负载均衡器或分布式服务发现，将请求均匀地分发到多个机器上。这样，每台机器处理的请求数量大致相同。
2. **本地限流状态维护：**在每台机器上维护一个本地的限流状态，独立地进行限流控制。可以使用令牌桶限流算法来实现这一逻辑。
3. **动态调整限流参数：**根据每台机器的负载情况（例如CPU和内存使用率），动态调整限流参数：

- 如果负载过高，降低限流阈值，减少请求处理量
- 如果负载较低，提高限流阈值，增加请求处理量

**4.2.1 存在的问题**

**Redis做缓存**

Redis由于性能高效，通常可以做数据库存储的缓存，比如给MySQL当缓存就是常见的玩法。具体而言，就是将MySQL的热点数据存储在Redis中，通常业务都满足二八原则，80%的流量在20%的热点数据之上，所以缓存是可以很大程度提升系统的吞吐量。

**怎么做**

一般而言，缓存分为服务器端缓存，和客户端缓存。服务器端缓存即服务端将数据存入Redis，可以在访问DB之后，将从DB得到的数据的缓存起来。

客户端缓存就是对服务端远程调用之后，将结果存储在客户端，这样下次请求相同数据时就能直接拿到结果，不会再远程调用，提高性能节省网络带宽。

用服务端还是客户端呢？

其实是需要分析具体瓶颈在哪里，当然，如果按通常的经验，从服务角度来看，在目前的微服务架构下，每个服务其实都应该缓存一些热点数据，以减轻热点数据频繁请求给自己带来的压力，毕竟微服务也要有一定的互不信任原则。

至于客户端缓存，这个就更看场景了，频繁请求的数据，就有必要做缓存。

下面我们以服务端缓存的视角，来进行缓存分析。

**缓存的几种模式**

缓存一般有如下几种模式：

- **Cache Aside Pattern**：旁路缓存模式
- **Read Through Cache Pattern**：读穿透模式
- **Write Through Cache Pattern**：写穿透模式
- **Write Behind Pattern**：又叫Write Back，异步缓存写入模式

下面我们来详细介绍这四个模式

##### Cache Aside

Cache Aside，即旁路缓存模式，是最常见的模式，应用服务把缓存当作数据库的旁路，直接和缓存进行交互。

读操作的流程如下：

应用服务收到查询请求后，先查询数据是否在缓存上，如果在，就用缓存数据直接打包返回；如果不存在，就去访问数据库，从数据库查询，并放到缓存中。除了查库后加载这种模式，如果业务有需要，还可以预加载数据到缓存。

说完读操作，我们再看看写操作的流程：

在更新操作的时候，Cache Aside模式是一般是先更新数据库，然后直接删除缓存，为什么不直接更新呢？因为更新相比删除会更容易造成时序性问题，这里有同学问时序性问题是什么？举个例子：thread1更新mysql为5 -> thread2更新mysql为3 -> thread2更新缓存为3 -> thread1更新缓存为5，最终正确的数据因为时序性被覆盖了。

Cache Aside适用于读多写少的场景，比如用户信息、新闻报道等，一旦写入缓存，几乎不会进行修改，该模式的缺点是可能会出现缓存和数据库不一致的情况。

##### Read Through

Read Through，读穿透模式，和Cache Aside模式的区别在于应用服务不再和缓存直接交互，而是直接访问数据库服务，这个数据库服务可以理解为一个代理，即单挂起这么一个服务，由它来访问数据库和缓存，作为使用者来看，不知道里面到底有没有缓存，数据库服务会自己来根据情况查询缓存或者数据库。

查询的时候，和Cache Aside一样，也是缓存中有，就用从缓存中获得的数据，没有就查DB，只不过这些由数据库服务托管保存，而对应用服务是透明的。

相比Cache Aside，Read Through的优势是缓存对业务透明，业务代码更简洁。缺点是缓存命中时性能不如Cache Aside，相比直接访问缓存，还会多一次服务间调用。

##### Write Through

在Cache Aside中，应用程序需要维护两个数据存储：一个缓存，一个数据库。这对于应用程序来说，更新操作比较麻烦，还要先更新数据库，再去删除缓存。

Write Through模式相当于做了一层封装：

由这个存储服务先写入MySQL，再同步写入Redis，这样及时加载或更新了缓存数据。

可以理解为，应用程序只有一个单独的访问源，而存储服务自己维护访问逻辑。

当使用Write Through时，一般都配合使用Read Through来使用。Write Through的潜在使用场景是银行系统。

Write Through适用情况有：

- 对缓存及时性要求更高（写入就加载了缓存，当然这种模式可能会有时序性问题）
- 不能忍受数据丢失（相对Write-Behind而言）和数据不一致（当然Cache Aside也是如此）

在使用Write Through时要特别注意的是缓存的有效性管理，否则会导致大量的缓存占用内存资源，因为这种模式下只要写入数据就加载了缓存。

**Write-Behind**

Write-Behind和Write-Through相同点都是写入时候会更新数据库、也会更新缓存。

不同点在于Write-Through会把数据立即写入数据库中，然后写缓存，安全性很高。

而Write-Behind是先写缓存，然后异步把数据一起写入数据库，这个异步写操作是Write-Behind的最大特点。

数据库写操作可以用不同的方式完成

一种是时间上的灵活性，其中一个方式就是收集写操作并在某一时间点（比如数据库负载低的时候）慢慢写入。

另一种方式就是合并几个写操作成为一个批量操作，一起批量写入。

两者是可以根据业务情况结合的。

异步写操作极大地降低了请求延迟并减轻了数据库的负担，但是代价是安全性不够，比如先写入了Redis，更新操作先放在存储服务内存中，但是还没异步写入MySQL之前，存储服务崩溃了，那么数据也就丢失了。

**4种模式怎么选择**

各有优势，但是Cache-Aside Pattern，旁路缓存模式是最常见，最易用的，在业务开发中，其他模式很少会用到。

**总结**

本节我们讲解了缓存的四种使用范式，其中旁路缓存模式是在生产环境应用最广的，后续我们的一些分析，也会围绕着旁路缓存模式来进行。

**开篇-聚合写是什么**

聚合写是什么？顾名思义，就是把很多次写操作，聚合起来，一次性写入，这就是聚合写。

用一个简单的例子，平常家庭生活中，都会产生很多垃圾，如果每产生一次垃圾，就下楼去扔一次，那么一天要下去几十次，这时候我们就把垃圾先放在垃圾桶里，等散步的时候一次处理掉。

看到这里，相信聚合写的价值，已经呼之欲出了。

**开篇-聚合写有什么价值**

为什么需要聚合写？简单来说，聚合写是将多次写操作聚合成一次写操作以提升效率的手段。最常见的例子，就是写数据库，原来写数据是直接入库，而数据库写入性能通常都不怎么高，比如MySQL，常见设备的QPS都在5000以内，而如果是一些热点数据更新，则会更慢。针对这种情况，我们很容易想到是否能在先在内存中进行聚合，再每隔一段时间入一次库，节约几倍的性能是没问题的，这就是聚合写的魅力所在。

当然软件设计领域没有银弹，这样做会不会导致流程更复杂？会不会数据更容易丢失？进而数据插入失败率更高？所以这里其实是个取舍问题，这里我们先不展开，等扩展部分会详细讨论。

**场景-聚合写在计数场景的应用**

大家如果经常看视频或文章，应该知道一般都有点赞功能，即你喜欢这个内容就对内容点击一次赞，那么点赞计数就会+1，如果你点1000次，或者有1000个人点赞，那么操作都执行完成之后总数量就增加了1000。

我们把一次点赞操作抽象为一个请求，那么此时1000个请求就是分别+1，最终写入数据库也写了1000次，为了提升效率，我们其实可以在内存里先计算，最后再一次性向数据库+1000。

如上图所示，左边呢，是每条请求都直接写入DB，右边是在计数服务内存里，聚合之后，一次写入DB。具体的策略可以说：

计数服务收到请求在内存中原子性增加，然后定时写入DB，比如1s一次，如果每秒1000个请求，那么1s对DB的压力只有只有1次，也就是说在数据库视角，1000/s的压力变成了1/s，我们可以称之为写收敛。

原始的1000次更新语句

聚合写这种方案有个缺点，就是数据丢失问题，比如某个计数服务节点宕机了，那么在内存中保存的数据就会丢失。

```SQL
1.update t_seckill_stock set stock = stock - 1 where stock >= 1 and product_id = xxx;
```

```SQL
Insert t_seckill_record(order_id, user_id, goods_id, status) values(......),
```

## 50. 微信支付优惠券秒杀实战：异步化发券、库存批量消费是怎么做的？

> 原题 ID：`q5054`

**高频程度**：★★★★

**考察点**：

**回答框架**：



**参考回答**：

**业务背景及挑战**

这个案例为微信支付有优惠产品的内部方案分享。牛哥脱敏之后进行展示。

先介绍下微信支付有优惠：

可能看到这张图很多同学就知道是什么产品了，不清楚的同学可以看看这篇文章[小程序“微信支付有优惠” 搞定了免费微信提现](https://post.smzdm.com/p/am8dm5e4/)

下面说回秒杀：

支付有优惠 准备进行一次秒杀活动，秒杀的“商品”是微信支付商家优惠券和提现免费券，秒杀的时候不需要进行支付。

相对于一般的秒杀活动，活动有以下特点：

- 发放的都是线上的券，要求尽量快速发券成功，并引导至商家小程序消费，以保证转换率。
- 活动频率较低，且准备时间短。预计这样规模的秒杀活动一年两三次。
- 产品希望系统的容量能达到 1w/s，实际发券为 2w/s：用户每次秒杀成功时会发两张券：商家券和提现免费券。

**挑战**

对于秒杀系统的后台服务，已经有了一些有效的解决思路：缓存，异步化，限流，降级，拆分单点（特别是 IO 单点），压测等。

但具体到这个业务本身，会有一些具体的问题需要解决：

异步化：对于整个业务流程，需要将什么部分进行异步化？

限流：限流系统需要处理秒杀的所有流量，能否解决或避免单点可用性问题？是否需要考虑限流系统的实现、配置的不同会对限流的效果造成的影响？

活动频率低，开发人力少：这种规模的活动当时预计一年两三次，所以活动前后需要扩缩容，否则资源长期闲置会造成极大的浪费。而存储的缩容是一件成本很高的事情，能否通过技术手段降低扩缩容的成本？

压测：业务要求尽快把券发完，所以需要对全流程进行压测确认发券链路性能是否满足要求。这涉及到外部的券系统、商户系统的配合。但工期比较紧张，能否在压测阶段先对内部系统压测以便更早暴露问题？

**同步发券可行么**

也就是同步秒杀可以吗，毕竟QPS要求是2w，如果能同步做，是最好的，对微信已有的商家券、提现券来说，也是可以支持的。并且异步化也会增加一些开发成本，那是否能直接进行同步发券？

发券流程包括：写入用户的兑换记录、调用商家券和提现免费券系统进行发券、商家券系统通知商家等。这个发券的流程是比较重的耗时比较长，在同步请求中完成的话对机器数量的要求较高。

而更重要的是，发券的流程需要依赖商家的系统，我们对商家系统性能的控制力是比较有限的，也不想因此对商家设置过高的门槛。所以也要求对发券的过程进行异步化，以降低商家系统的容量要求。

另外需要注意的是，由于秒杀的奖品是具有一定的引流目的线上商家券，而转换率最高的模式是用户秒杀完获得商家券之后，直接跳转到商家处进行核销。所以发券的速度也不能太慢。

（与此相对照的是代金券：代金券的核销是在微信支付系统中完成的，不需要商家感知。但由于用户在未拉起支付前无法强提示有券，所以核销率会比商家券低不少。）

**异步化**

对哪些流程进行异步化？

异步化是解决秒杀问题的一个重要的思路，但不同的业务场景下，异步化的范围也有所不同。

全流程异步化？最彻底的异步化就是，在对请求做完参数检查、频率限制之后，把后续的一整个流程进行异步化处理。

但这样会产生一个大家可能都经历过的用户体验问题：秒杀后菊花转了很久，最后弹了个框提示：奖品已抢光。产品不太可接受这样的用户体验，所以如果有其他的办法，尽量选择别的。

发券流程异步化

但如果确认用户能抢到券了，且在绝大部分情况下都能发券成功时，再让用户等待一会是可以接受的（甚至多等一会有种参与秒杀的感觉）。

所以在实时流程中，需要确认用户是否能成功发券，大概涉及以下业务逻辑：

**实时流程中的业务逻辑**

所以在实时流程中，需要确认用户是否能成功发券，大概涉及以下业务逻辑：

1. 校验发奖请求，避免刷子通过修改请求包的方法获取不对自己定向投放的高价值奖品，或重复秒杀
2. 确认并扣减库存
3. 在存储中记录发放请求（这里应该是写入NoSQL类数据库）
4. 将发放请求加入异步队列

经过优化，这些实时流程能达到性能要求，所以最终采用这个方案。

**异步队列选型**

当前环境下，常用的可用来异步化的组件有可靠事件中心和 Svrkit MQ。使用可靠事件中心会有以下的问题：

- 会造成队列积压，而可靠事件中心现在用的是公用的资源，会影响到别的业务。

需要承受秒杀的流量，作为一个服务，相比于 Svrkit MQ，在可用性及请求耗时方面不占优势。

所以最终选择使用 Svrkit MQ，其支持错误重试，全局出队限流，开发成本也很低。

但有两个问题需要注意：

- 在极端的情况下如果机器在秒杀的那几分钟挂掉，会导致 MQ 里的请求丢失。最低成本的处理方法是对请求进行上报，后期还能补救。如果排期允许，可以加入扫表补漏的脚本。
- MQ 不支持二阶段事务。不过实际发券成功但给用户返回失败是可以接受的，所以可以在 MQ 入队成功之后再给用户返回成功。

PS：这里的可靠事件中心，Svrkit MQ都是微信的组件，这里保留下来主要给大家展示一下选型的思考。

**发奖结果单机缓存**

在用户抢券成功，进入异步发券流程后，前端需要感知发券的结果。一种方案是使用websocket，服务端主动推送结果，但当前的技术栈对此支持并不完善，长链接对资源的消耗也比较大，贸然使用的风险较高。

所以决定由前端轮询发券的结果，而这个查询请求的量级和秒杀活动相当。理论上这个量级对 kv 来说不成问题，但活动的奖品总数量很多，而且如果发券耗时又比较久（需要匹配商家系统的性能）的情况下，会造成用户多次重试查询，可能引起雪崩。

除了在前端进行查询频率的控制外，为了将存储的 qps 容量留给其他领域以及进一步降低风险，这里加上了发奖结果的“缓存”。

1. 首先把 参与秒杀 ，及 查询结果 的请求按用户 uin 进行路由，使得同一个用户的请求落在相同的机器上。
2. 秒杀和发奖都把数据记录在单机 memcache 中
3. 查询时，先查询 memcache

**库存批量消费（这个优化挺好的，在资源有限的情况节约一点）**

秒杀系统的一个挑战就是库存限制，难点在于库存的计数器可能无法承担请求量。根据隔壁团队项目的压测，quotakv（腾讯内部的一个kv存储，可以理解为Redis）的单 key 写并发能支持到 2.3w/s，看起来是能满足需求的。但容量也未冗余太多，更重要的是业务并未独立部署 quotakv，运维不允许我们这么大的请求量。

为顺次这么低的活动特意申请集群也不是很有必要，而且业界解决这个问题的方法也比较成熟了，思路一般有两种：

- 计数器拆分：把商品的库存计数器拆成多个，然后根据路由决定用户访问哪个计数器（根据实现可以选择进行跳key）。不过这个方案需要先确定好计数器的数量，修改这个数量略为麻烦；而且仍然会把所有请求都穿透到计数器的存储
- 批量结算：每次向中央计数器请求消耗多个库存，然后在本地（共享内存或 进程内存）进行管理。根据能否超发少发，可以选择先消费后结算，或先结算后消费。

由于无独立集群的限制，有优惠选择的是批量结算的模式。另外对于库存管理的要求是不可接受超发，但能接受一定的漏发，所以选择的是先结算后消费的模式。

**库存消费流程**

每次请求消耗库存的流程如下：

1. 检查本地是否有库存，如有则直接消费
2. 如果本地没有库存了，检查本地是否有 quotakv 已无库存的标记，如有则返回无库存，这一步是为了避免真正没库存的时候，所有的请求都穿透到了 quotakv。另外，考虑到产品可能有补库存的需求，这个标记设置了一个有效期。
3. 如果无标记，则尝试往 quotakv 批量消耗库存。如果消费成功，则更新本地的库存数量并消费；如果 quotakv 无库存或 key 不存在，则更新无库存标记。

由于服务采用的是单进程多线程的模式（数据共享更方便，且引入 MQ 时框架必须要求为多线程模式），所以“本地”的库存维护在每台机的进程内存中，使用原子变量即可。

缓存会被击穿吗？

这种缓存击穿的措施需要考虑一下是否会击穿至后端。这个流程下，可能发生击穿的场景是刚开始秒杀的时候，所有机器都没有库存信息，需要请求 quotakv。这种情况并发度最大是机器数量\*奖品数量，本次活动中是百级别或者刚过千级别，问题不大。如果机器数或者奖品数增加，也可以通过秒杀前预加载的方式避免这个问题。

同样的，本地里 quotakv 无库存的标记的过期也是类似的情况。不过可以通过过期时间随机化避免。

**为什么通用文件系统不适合大量小文件？**

在深入设计之前，先理解为什么常见方案（如直接存硬盘）会失效：

1. **元数据开销过大**：

   - 在传统文件系统（如 ext4、NTFS）中，每个文件都有对应的 inode 存储元数据（权限、时间戳、指针等）。
   - 若文件平均 50KB，而文件系统块大小是 4KB，即使文件很小，也至少要占用一个块。元数据空间和磁盘寻道的开销远大于数据本身。
2. **磁盘I/O效率低**：

   - 访问一个小文件通常需要多次 I/O：读取目录、读取 inode、读取数据块。
   - 若文件分散在不同位置，机械硬盘会产生大量的随机读写，而 SSD 也会因大量小请求导致 I/O 队列饱和。
3. **缓存利用率低**：

   - 内存页缓存通常以 4KB 为单位。如果文件是 10KB，即使只读一次，也会占用 3 个页缓存，而实际有效数据只有 10KB，造成内存浪费。
4. **文件数量限制**：

   - 目录中文件过多时，线性查找速度会极慢（即使使用 B-tree 等索引，海量小文件依然会影响路径查找性能）。

---

**针对海量小文件的存储引擎设计思路**

核心思路可以概括为：**合并写入、分离处理元数据和数据、追加写避免覆盖**。

**1. 核心设计模式：日志结构合并（LSM树思想）与对象存储思路**

借鉴 LSM-Tree 和对象存储（如 AWS S3）的理念，不将每个小文件单独存为操作系统文件，而是：

- **数据层面**：将多个小文件合并成一个大文件（Segment/Extent），顺序追加写入磁盘，避免随机写。
- **元数据层面**：建立高效的索引（如 Key-Value 结构），记录每个小文件在哪个大文件中的偏移量和长度。

**2. 具体架构组件**

假设我们设计一个名为 **TinyFS** 的小文件存储引擎，其内部结构如下：

**① 数据文件（Data File）**

- **格式**：一系列固定大小或动态增长的大文件（如每个 512MB 或 1GB），称为 Chunk 或 Segment。
- **写入方式**：**仅允许追加写（Append-only）**。
- **内部结构**：一个大文件内部顺序存放多个小文件的数据块，每个数据块前通常有一个简单的头部记录其大小或 CRC 校验码。

```Plain Text
[Data File: 000001.tfs]
-------------------------------------------------------------
| 头部 | 小文件A数据(30KB) | 头部 | 小文件B(10KB) | 头部 | 小文件C(60KB) | ...
-------------------------------------------------------------
```

**② 索引文件（Index File）**

由于数据是追加的，需要一个地方快速找到某个 Key 对应的数据。这是一个典型的 **Key-Value 存储**需求。

- **Key**：文件的唯一标识（如文件 ID 或路径 Hash）。
- **Value**：文件元数据 + 物理定位。例如：`{file_id: xxx, chunk_id: 000001, offset: 1024, size: 30720, timestamp: xxx, crc: xxxx}`。
- **数据结构选择**：

  - **哈希表**：内存中维护一个大的哈希表，查找 O(1)，但内存占用大，重启需要重建。
  - **B-Tree / B+Tree**：可以存储在磁盘上，支持范围查询，但写放大比 LSM 大。
  - **LSM-Tree**：更适合这种写多读多的场景。先写内存中的 MemTable（有序结构，如跳表），达到阈值后冻结为 Immutable MemTable，然后刷盘成 SSTable（Sorted String Table）文件。查找时依次查 MemTable、Immutable MemTable 和 SSTable。

**③ 预写日志（WAL，Write-Ahead Log）**

- 为了数据一致性，任何写操作（追加文件）必须先记录 WAL。系统崩溃后，可以通过重放 WAL 恢复 MemTable 中未刷盘的数据。

**3. 垃圾回收与合并（Compaction）**

由于采用追加写，更新或删除文件会产生垃圾空间（旧版本的数据仍然在数据文件中，只是索引指向了新版本或标记删除）。

- **标记删除/更新**：写入一条新的数据记录，索引指向新地址。旧的索引和数据成为垃圾。
- **合并过程**：后台线程定期对数据文件和索引文件进行合并。

  1. 读取旧的 Chunk 文件。
  2. 遍历其中的数据，只保留最新的有效数据。
  3. 将有效数据写入新的 Chunk 文件。
  4. 生成新的索引文件或更新索引指向新位置。
  5. 删除旧的 Chunk 文件。

  - 这个过程类似于 LSM-Tree 的 Compaction，可以有效清理碎片，回收磁盘空间。

---

**架构对比：几种技术选型**

如果你需要实现这个系统，可以参考以下几种主流技术的设计思路：

| 方案类型 | 代表技术 | 原理 | 优点 | 缺点 |
|-|-|-|-|-|
| **通用 KV 存储** | **RocksDB**、**LevelDB** | 基于 LSM-Tree，Key 存文件名，Value 存文件内容。 | 写入性能高，延迟低，适合小对象。 | 大 Value（几百 KB 以上）可能导致写放大严重，Compaction 时 I/O 开销大。 |
| **专门的小文件系统** | **Facebook Haystack** | 将多个图片合并存储，通过逻辑卷（Physical Volume）和索引定位。 | 专为小文件（照片）设计，元数据极轻量，减少磁盘寻道。 | 系统相对复杂，社区方案较少。 |
| **对象存储网关** | **MinIO**、**Ceph** | 将小文件聚合为对象存储中的对象。 | 高可用，扩展性好，支持 S3 兼容 API。 | 元数据服务（RADOS Gateway）可能成为瓶颈，延迟相对较高。 |
| **嵌入式数据库** | **SQLite**、**BerkeleyDB** | 将小文件作为 BLOB 存入数据库表。 | 事务支持好，管理简单。 | 数据库文件过大时备份恢复困难，并发性能可能受限。 |

**推荐方案**

对于平均几十 KB 的小文件：

1. **首选 RocksDB/LevelDB 作为存储引擎**：可以利用其高效的写入缓存和 LSM 结构。需要注意的是配置 `blobdb`（大值分离）特性，将较大的值（几十 KB 已算大）存储在单独的文件中，避免值在 LSM 树的多层间频繁拷贝导致写放大。
2. **如果追求极致性能且愿意投入研发**：可以借鉴 Haystack 的设计思路，自定义文件格式，采用“文件名 -> (文件ID, 偏移量, 大小)”的定长内存索引，配合合并写入。
3. **如果希望简单且文件数量在百万级别**：可以直接使用 SQLite，利用其页面缓存和 B-tree 结构。

总的来说，这个问题的核心挑战在于**元数据膨胀**和**磁盘寻道**。通过 **合并写入** 和 **KV 索引分离** 的设计，就能很好地应对几十 KB 小文件的存储场景。

**跨节点关联查询JOIN问题**

（解决方案：1.全局表 2.冗余字段 3.建立1：1的ER实体关系分片）

在 MySQL 中，跨节点关联查询（JOIN）是一个复杂的问题，尤其是在分布式数据库或分库分表场景下。以下是解决这一问题的几种常见方法：

1. **应用层实现 JOIN**

- **方法**：在应用层分别查询两个节点的数据，然后在内存中进行关联操作。
- **优点**：避免数据库跨节点查询的性能开销。灵活性高，可以根据业务需求优化关联逻辑。
- **缺点**：需要编写额外的代码，增加了开发复杂度。如果数据量较大，内存消耗和计算开销会比较高。

2. **数据冗余**

- **方法**：将需要关联的数据冗余存储到同一个节点或表中。
- **优点**：避免了跨节点 JOIN 的问题。查询性能高，直接在同一节点完成 JOIN。
- **缺点**：数据冗余会占用更多存储空间。数据一致性维护成本高，需要额外的同步机制。

3. **使用全局表（广播表）**

- **方法**：将小表（如字典表、配置表）复制到所有节点，确保 JOIN 操作可以在本地完成。
- **优点**：避免跨节点查询，性能较好。适合小表与大表的 JOIN 场景。
- **缺点**：只适用于小表，大表不适合全局复制。数据更新时需要同步到所有节点。

4. **分片键设计优化**

- **方法**：在分库分表时，将需要关联的表使用相同的分片键（Sharding Key），确保关联数据分布在同一个节点。
- **优点**：避免跨节点 JOIN，查询性能高。
- **缺点**：分片键设计需要提前规划，灵活性较低。不适合多维度关联的场景。

5. **使用分布式数据库中间件**

- **方法**：通过中间件（如 MyCat、ShardingSphere）实现跨节点 JOIN。
- **优点**：中间件可以自动处理跨节点查询和聚合。对应用透明，开发复杂度低。
- **缺点**：中间件可能会成为性能瓶颈。需要额外的运维成本。

6. **ETL 预处理**

- **方法**：通过 ETL（Extract, Transform, Load）工具将分散的数据聚合到一个统一的存储（如数据仓库）中，然后在该存储中执行 JOIN。
- **优点**：适合离线分析场景。避免实时查询的性能问题。
- **缺点**：数据延迟较高，不适合实时查询。需要额外的 ETL 工具和存储资源。

7. **使用 NoSQL 或 NewSQL 数据库**

- **方法**：如果业务场景允许，可以考虑使用支持分布式 JOIN 的 NewSQL 数据库（如 TiDB）或 NoSQL 数据库。
- **优点**：原生支持分布式查询，性能较好。
- **缺点**：需要迁移数据，成本较高。可能不完全兼容 MySQL 的语法和特性。

总结

在分布式场景下，解决 MySQL 跨节点 JOIN 问题需要根据具体业务需求选择合适的方法：

- 如果数据量较小，可以考虑 **应用层 JOIN** 或 **全局表**。
- 如果数据量较大，可以通过 **分片键设计优化** 或 **数据冗余** 来避免跨节点查询。
- 对于复杂场景，可以使用 **分布式数据库中间件** 或 ETL 预处理。
- 如果业务允许，也可以考虑迁移到支持分布式 JOIN 的数据库（如 TiDB）。
