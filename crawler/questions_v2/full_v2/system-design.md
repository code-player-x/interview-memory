## 4. 什么是CAP理论？

> 原题 ID：`q0950`

**高频程度**：★★★★★

**考察点**：考察分布式理论基本功，重点是 P 不可舍弃、CA 在分布式下不存在这一常见误区。

**回答框架**：

①三个要素定义：一致性 C、可用性 A、分区容错性 P。②三选二的真实含义：网络分区客观存在，P 必须保，实际是在 C 与 A 之间取舍。③典型系统：CP 如 ZooKeeper/etcd，AP 如 Eureka/Cassandra。④延伸：BASE 理论、一致性与延迟的关系。

**参考回答**：

CAP理论是分布式系统中的核心概念，主要包含三个要素：

1. **一致性（Consistency）**：所有节点在同一时间看到的数据是相同的。
2. **可用性（Availability）**：每个请求都能收到响应，无论成功或失败。
3. **分区容错性（Partition Tolerance）**：系统在网络分区的情况下仍能继续运行。

根据CAP理论，分布式系统最多只能同时满足其中两个要素，无法三者兼顾。具体表现为：

- **CA系统**：保证一致性和可用性，但无法容忍网络分区，通常用于单点或小规模集群。
- **CP系统**：保证一致性和分区容错性，但在网络分区时可能牺牲可用性，适合对一致性要求高的场景，如金融系统。
- **AP系统**：保证可用性和分区容错性，但可能牺牲一致性，适合对高可用性要求高的场景，如社交网络。

在实际应用中，系统设计需根据具体需求权衡这三个要素。

**常见追问**：P 在什么情况下可以放弃？最终一致性怎么保证「读己之写」？

1. **系统架构设计**

3.3 数据库一致性

- 使用数据库事务确保订单和库存的一致性。
- 通过分布式锁（如Redis分布式锁）防止多个请求同时修改库存。

## 6. 秒杀一千万个商品，20wQPS：怎么设计？只考虑库存扣减环节，请简要回答设计要点？

> 原题 ID：`q0984`

**高频程度**：★★★★

**考察点**：考察极高 QPS 下单点库存扣减的横向扩展与热点处理。

**回答框架**：

①Redis 集群分片：库存按商品维度打散到 redis 集群，用 DECR 原子扣减。②本地缓存：热点商品在应用层加本地缓存或请求合并，减轻缓存层压力。③分片与负载均衡：服务多实例横向扩展，避免单点过载。④数据库兜底：乐观锁或版本号防超卖，MQ 异步落库。

**参考回答**：

针对秒杀场景下库存扣减环节，要达到20万QPS的设计要点可以简要概括如下：

1. **使用缓存技术库存扣减**：采用高性能缓存系统如**Redis集群**来存储商品库存信息，利用其原子操作（例如`DECR`命令）实现高效且一致的库存扣减。对于热点商品，还可以考虑在应用层使用本地缓存进一步减轻缓存系统的压力。
2. **分布式架构设计**：部署多个服务实例以支持横向扩展，确保能够处理高并发请求。同时，通过合理的负载均衡策略分散流量，避免单点过载。
3. **乐观锁或版本控制**：在数据库层面采用乐观锁机制或者版本号控制，防止超卖问题的发生。虽然主要依赖于缓存进行扣减操作，但最终需要同步到数据库时，这一步骤非常重要。
4. **限流、降级与排队机制**：实施限流措施限制进入系统的请求数量，保护后端服务不被瞬间大流量冲击。对超出即时处理能力的请求，可采用排队机制延迟处理，保证系统稳定运行。
5. **异步处理**：结合消息队列等异步处理方式，将部分非实时性要求的操作（如订单生成、支付确认后的库存更新等）异步化，降低库存扣减环节的直接压力。

这些要点共同作用，旨在构建一个既能够承受高并发访问又能够保证数据准确性的秒杀系统库存扣减解决方案。

- **哈希算法**：使用哈希函数（如MD5、SHA256）对长URL进行哈希，取前N位作为短链。

  - 优点：简单易实现。缺点：可能存在哈希冲突，难以设计出一个没有冲突的Hash算法。

  - **唯一性检查**：在生成短链后，进行唯一性检查，如果冲突则重新生成。

## 10. 单点登录系统设计：设计一个单点登录系统？

> 原题 ID：`q0988`

**高频程度**：★★★★

**考察点**：考察 IdP/SP 模型、令牌机制与跨域会话共享。

**回答框架**：

①角色：身份提供者 IdP 统一认证，服务提供者 SP 依赖 IdP 鉴权。②流程：重定向到 IdP 登录、签发安全令牌、SP 校验令牌、建立本地会话。③令牌：JWT 或 SAML 断言，签名与加密防篡改。④安全与扩展：HTTPS、会话超时与单点注销、支持 OAuth/OIDC 与多因素认证。

**参考回答**：

设计一个单点登录（Single Sign-On, SSO）系统，主要是为了在多个应用服务间共享用户的身份验证状态，使得用户只需一次登录就可以访问所有信任该SSO系统的应用。以下是简要的设计思路：

**1. 核心概念**

- **身份提供者(IdP)**：负责处理用户的认证过程，并向服务提供商(SP)发出身份验证声明。
- **服务提供商(SP)**：依赖IdP进行用户身份验证的服务或应用。

**2. 实现步骤**

a. 用户首次登录请求

当用户尝试访问任一SP时，如果尚未登录，则重定向到IdP的登录页面。

b. 用户认证

在IdP上完成用户名和密码等信息的验证。一旦验证成功，IdP会生成一个包含用户身份信息的安全令牌（如JWT、SAML断言等），并将其返回给客户端浏览器。

c. 安全令牌交换

客户端携带这个安全令牌再次访问最初请求的SP。SP收到令牌后，首先需要验证其有效性（通常通过与IdP直接通信或者使用公钥加密技术），然后建立自己的会话。

d. 创建本地会话

一旦SP确认了令牌的有效性，它将在本地为用户创建一个会话，允许用户无需再次登录即可访问该服务。

**3. 安全考虑**

- **传输层安全性**：确保所有的认证流程都通过HTTPS协议进行，以保护数据不被窃听。
- **令牌安全性**：采用合适的签名和加密机制来保护令牌，防止篡改和伪造。
- **会话管理**：正确管理用户会话，包括超时设置、注销流程等，以增强安全性。

**4. 扩展与维护**

- 支持多种认证方式（如双因素认证）以提高安全性。
- 提供接口以便于集成更多的服务提供商。
- 对接OAuth等开放标准，以便更容易地与其他系统集成。

**总结**

设计一个单点登录系统涉及多个方面，包括但不限于用户认证、安全令牌的生成与验证、以及会话管理等。关键在于确保整个过程的安全性和可靠性，同时提供良好的用户体验。通过合理的架构设计和安全措施，可以有效地实现跨多个应用的无缝用户认证体验。

**高频程度**：★★★★

**考察点**：以订单聚合和状态机为核心，覆盖下单幂等、库存、支付、超时、事件与对账。

**回答框架**：

1) 先定义订单边界、状态机、不变量和一致性要求
2) 订单主表、明细、金额快照、操作记录与幂等记录分工
3) 下单、库存、支付和履约通过明确状态与持久化事件衔接
4) 用超时关单、重试、补偿和对账处理分布式故障
5) 按查询模式规划分片、索引、归档与可观测性

**参考回答**：

订单系统的核心不是一张订单表，而是一个受约束的订单状态机。先确认订单类型、用户与商家视角、拆单/合单规则、库存与价格锁定时点、支付和退款边界，再定义合法状态，例如 `待支付 → 已支付 → 履约中 → 已完成`，以及 `待支付 → 已取消`。每次迁移都应校验当前状态或版本，禁止跳转、重复扣款和已完成订单被取消。

数据通常包括订单主表、订单明细、收货与金额快照、支付/退款关联、状态操作记录和幂等记录。商品名称、价格、优惠、地址等要保存下单时快照，不能展示时再依赖可能变化的商品资料。订单号既要全局唯一，也要考虑索引局部性和分片路由，不能只追求随机性。

下单接口使用客户端请求号或业务幂等键去重。创建订单、锁定或预扣库存、发起支付跨越多个服务时，不应假设一个本地事务覆盖全部系统：本地写订单与 Outbox 事件放在同一事务，消息消费者幂等处理；关键状态通过重试、补偿和对账收敛。支付回调必须验签、核对商户订单号和金额，并把重复、乱序回调当作正常输入处理。

超时关单可由延迟消息或时间轮触发，但执行时必须再次条件更新状态；它与支付回调并发时，只有一个合法迁移成功。库存确认或释放跟随最终状态，以幂等事件执行。人工改价、关闭、退款等敏感操作需要权限和完整审计。

扩展方面按主要查询模式设计索引和分片：用户订单列表常按用户维度路由，客服按订单号查询可用路由表或编码；冷热数据分层归档，列表页避免跨全库排序。监控应覆盖创建成功率、状态停留时长、支付差异、消息积压、重复请求和对账异常，并预留按业务类型降级和隔离故障的能力。

## 12. 如果从0开始做一个项目，如何设计架构（按业务怎么分）？

> 原题 ID：`q3545`

**高频程度**：★★★★★

**考察点**：考察从零做架构时按业务能力划分领域、确定数据流与演进路径的能力。

**回答框架**：

①明确业务目标与非功能需求，架构是取舍。②按业务能力而非技术分层划分领域（DDD 限界上下文）。③确定数据流与依赖方向：同步走 API/RPC，跨域状态变更走领域事件。④领域内分层、存储选型（每个领域独享数据库）、扩展性与横切关注点。⑤取舍：核心交易强一致、非核心最终一致，优先模块化单体按需拆分。

**参考回答**：

从零设计架构的核心是：先按业务能力而非技术划分领域边界，再确定数据流与依赖方向，最后为扩展性预留接口和异步事件机制，避免过度设计。步骤是：

- 第一，明确业务目标与非功能需求，先问清核心用户是谁、核心用例是什么、QPS 与数据量、一致性与延迟要求、团队规模和交付节奏，架构是取舍，没有需求就没有架构。
- 第二，按业务能力划分领域，用 DDD 限界上下文，不要按 controller/service/dao 这种技术分层做一级划分，而是按业务能力切，例如电商分为用户、商品、库存、订单、支付、营销、履约，每个领域高内聚低耦合、拥有自己的数据和对外接口。
- 第三，确定数据流与依赖方向，同步调用走 API 或 RPC，跨领域的状态变更走领域事件（如 OrderCreated、PaymentSucceeded）通过 MQ 解耦，依赖方向单向、避免循环依赖。
- 第四，领域内部再分层，接口层、应用层、领域层、基础设施层，让业务逻辑不依赖具体技术，领域层定义 Repository 接口由基础设施实现。
- 第五，存储选型按访问模式来，交易数据用关系型，热点读用 Redis，搜索用 ES，日志事件用 Kafka，报表用 OLAP，每个领域独享数据库避免共享表导致耦合。
- 第六，扩展性上初期用模块化单体按领域分包、接口清晰，当某领域压力大或团队拆分时再抽成独立服务，预留插件、事件订阅、配置化等扩展点。
- 第七，横切关注点如日志、链路追踪、监控告警、配置中心、鉴权、幂等、限流熔断统一作为基础设施不侵入业务。取舍原则是核心交易强一致、非核心最终一致，强依赖同步、通知统计异步，团队小业务未稳时优先单体，非核心不重复造轮子。

**常见追问**：库存扣减到底是订单流程的一部分还是独立领域，怎么判断？Outbox 模式解决了什么问题？

## 13. 大文件上传如何优化（断点续传）？

> 原题 ID：`q4123`

**高频程度**：★★★★★

**考察点**：考察分片上传、哈希校验、秒传与断点续传的完整方案设计。

**回答框架**：

①分片：前端按固定大小（如 5MB）切片，避免单次失败重传全部。②校验：每片计算 hash，服务端记录已传分片，支持秒传与断点续传。③合并：全部片到齐后用 append 合并，校验整体 hash 保证完整性。④优化：并发上传加进度反馈，失败只重传失败分片，分片元数据用 Redis 或数据库记录。

**参考回答**：

核心是分片上传、hash 校验、秒传、合并、断点续传五步。

- 第一，前端分片：把大文件按固定大小（如 5MB）切成多个分片，避免单次请求失败就重传整个文件。
- 第二，计算哈希：对每个分片计算 hash（如 md5），再对整个文件计算一次整体 hash 作为文件唯一标识。
- 第三，校验与秒传：上传前先用文件整体 hash 询问服务端是否已存在，存在则直接秒传返回，不需要真正上传；上传分片时服务端按分片 hash 校验该分片是否已传过，已传则跳过。
- 第四，断点续传：服务端记录每个文件已上传的分片列表（可用 Redis 或数据库存 uploadId 与已传分片序号），用户重新进入上传时先拉取已传分片，只传缺失的部分。
- 第五，合并与校验：所有分片到齐后按顺序用 append 合并成完整文件，再校验整体 hash 与声明一致，防止传输损坏。优化上可以并发上传多个分片提升速度、进度条基于已传分片数计算、失败只重传失败的分片、分片大小要在并发度与请求开销之间权衡（太小请求多、太大重传代价高），另外要考虑分片元数据的过期清理和并发上传同一文件的去重。

**常见追问**：分片大小怎么选？如果上传到一半用户换了网络或刷新页面，怎么保证续传能对上？

## 14. 如何设计一个排行榜？

> 原题 ID：`q4120`

**高频程度**：★★★★★

**考察点**：排行榜设计：ZSet 实时排序、ZINCRBY 更新分数、ZREVRANGE 取 TopN、持久化与分片扩展。

**回答框架**：

1）核心结构：Redis ZSet，member 是用户/对象，score 是分数；2）更新：ZINCRBY 原子加分，或 ZADD 直接设置；3）查询：ZREVRANGE 取 TopN，ZREVRANK 查排名，ZSCORE 查分数；4）持久化：定时落库或通过消息队列异步写 DB，保证可恢复；5）扩展：数据量极大时按维度分片（比如按榜单 ID 或时间段），或分片 ZSet 加归并；6）注意大 key 与热 key 问题；7）时间维度榜单可用 key 加日期后缀。

**参考回答**：

排行榜最适合用 Redis 的 ZSet 实现，因为它天然按 score 排序且支持排名查询。具体设计：

- 第一，数据结构，ZSet 的 member 存用户 ID 或对象 ID，score 存分数（比如积分、票数、热度值）。
- 第二，更新，用户分数变化用 ZINCRBY 原子加分，或者用 ZADD 直接设置新分数，这两个操作都是 O(logN) 且原子，无需加锁。
- 第三，查询，取前 N 名用 ZREVRANGE key 0 N-1 带 WITHSCORES，查某用户排名用 ZREVRANK，查分数用 ZSCORE，取某个分数区间用 ZRANGEBYSCORE；这些操作分别是 O(logN + M) 和 O(logN)，性能很好。
- 第四，持久化，Redis 是内存存储，榜单数据需要落库，可以定时全量落库，或者用消息队列把分数变更异步写回 MySQL/数仓，重启或故障时从库里重建 ZSet；注意如果分数是实时算出来的，也可以选择不落库，靠源数据重算。
- 第五，扩展与治理。数据量极大时（比如千万级用户的全站排行），单个 ZSet 会变成大 key 且占用大量内存，可以考虑：按维度拆分（比如按地区、按榜单 ID 分成多个 ZSet），或者按用户 ID 分片成多个 ZSet，取 TopN 时对每个分片取前 N 再归并；时间维度的榜单（日榜、周榜）用 key 加日期后缀，并对旧 key 设置过期或归档。
- 第六，要关注热 key 问题：如果是全站超热榜单，可以加本地缓存、多副本打散。

总结起来就是"ZSet 做实时排序、异步落库保证可恢复、分片解决大 key、本地缓存解决热 key"。

**常见追问**：1）分数相同时排名怎么处理？2）分片 ZSet 怎么归并出全局 TopN？

## 15. 如何设计一个『附近的人』功能？

> 原题 ID：`q4121`

**高频程度**：★★★★

**考察点**：附近的人功能设计：地理索引（GeoHash/Redis GEO）、半径查询与距离排序、精度与性能优化、城市维度预筛。

**回答框架**：

1）核心：把用户经纬度存入地理索引（Redis GEO 基于 ZSet + GeoHash，或 MySQL 空间函数）；2）写入：GEOADD 添加位置；3）查询：GEOSEARCH/GEORADIUS 按半径搜索并返回距离、排序；4）原理：GeoHash 把二维经纬度编码成一维字符串，前缀相同的点地理上邻近，可转成 ZSet 的 score 做范围查询；5）优化：按城市或网格预筛减少候选、控制返回数量、位置更新用异步；6）权衡：精度 vs 性能、隐私与权限。

**参考回答**：

附近的人核心是要支持"给定一个坐标和半径，找出范围内的点并按距离排序"。实现上主要有两种选择。第一种是用 Redis 的 GEO 能力，这是最常用的：GEOADD 把用户的经纬度加进去，GEOSEARCH（新命令，替代 GEORADIUS）可以按半径或矩形范围查询，并支持返回距离、按距离排序、限制返回数量。

它的底层原理是 GeoHash——把二维的经纬度编码成一维字符串，地理上邻近的点前缀相同，Redis 再把它转成 ZSet 的 score，就能用 ZSet 的范围查询（ZRANGEBYSCORE）快速筛出候选，然后再精确计算距离排序。第二种是数据库方案，MySQL 有 ST_Distance_Sphere 等空间函数，PostGIS 这类专业地理库能力更强，适合需要复杂空间查询和事务的场景，但性能不如 Redis。

工程上要注意几点：

- 第一，精度和性能的权衡，GeoHash 编码位数越长精度越高、但匹配越严格，Redis 用的是 52 位精度，误差在米级以内，一般够用；
- 第二，数据量大时要减少候选集，常见做法是先按城市维度或网格预筛，只在同一城市/网格内做半径查询，避免全国范围全量扫描；
- 第三，用户位置更新频繁（比如骑手、司机），写入量很大，可以考虑异步更新、降低更新频率、或者用专门的时空数据库；
- 第四，返回结果要限制数量并做分页，避免一次返回过多；
- 第五，隐私与权限要考虑，比如只对已授权用户展示位置、做位置模糊化。整体思路是"地理索引做快速筛选 + 精确距离计算做排序 + 城市/网格预筛控规模"。

**常见追问**：1）Redis GEO 和 PostGIS 该怎么选？2）位置更新特别频繁怎么优化？

## 17. 本项目需要同时存储结构化数据（简历、面试记录）和向量数据（文档 Embedding）。方案对比？

> 原题 ID：`q1972`

**高频程度**：★★★

**考察点**：考察结构化数据与向量数据的存储选型。

**回答框架**：

1) 两类数据的本质差异；2) 三种方案对比；3) 选型依据；4) 一致性处理。

**参考回答**：

结构化数据比如简历、面试记录，字段固定、强事务、需要 JOIN、按主键和条件精确查询，典型诉求是 ACID 和一致性；向量数据是文档 Embedding，高维浮点数组，核心操作是 ANN 近似最近邻检索，需要 HNSW、IVF、DiskANN 这类向量索引，对召回率、延迟、内存敏感，常伴随元数据过滤。

方案有三种：

- 一是单一关系库加向量扩展，比如 PostgreSQL 加 pgvector，优点是存储统一、事务一致、SQL 直接 JOIN 做元数据过滤、运维简单，适合中小规模（百万级向量以内），缺点是向量索引性能和规模不如专用库，超大规模或高并发会成瓶颈；
- 二是关系库加专用向量库，比如 MySQL 加 Milvus 或 Qdrant，优点是各司其职，向量库为 ANN 深度优化、可水平扩展支持十亿级，关系库保证业务事务，缺点是双写一致性、跨库 JOIN 要在应用层拼装、运维复杂度上升；
- 三是支持向量类型的一体化数据库。我的默认选择是方案二，通过业务主键关联，避免用同一存储硬扛两类负载。

## 18. 常用组件哪些是AP，哪些是CP？

**回答框架**：

**参考回答**：

在分布式系统中，CAP理论指出，系统最多只能同时满足一致性（Consistency）、可用性（Availability）和分区容错性（Partition Tolerance）中的两个。以下是各个系统在CAP理论中的实现：

1. **ZooKeeper**：CP（一致性和分区容错性）

   - **解释**：ZooKeeper 优先保证一致性和分区容错性。在发生网络分区时，ZooKeeper 会牺牲可用性，确保数据的一致性。
2. **Redis 集群**：AP（**可用性和分区容错性**）

   - **解释**：Redis 集群优先保证可用性和分区容错性。在发生网络分区时，Redis 集群会继续提供服务，但可能会牺牲一致性。
3. **Consul**：CP（一致性和分区容错性）**Consul可以根据配置偏向于AP或CP**

   - **解释**：Consul 优先保证一致性和分区容错性。在发生网络分区时，Consul 会牺牲可用性，确保数据的一致性。
4. **etcd**：CP（一致性和分区容错性）

   - **解释**：etcd 优先保证一致性和分区容错性。在发生网络分区时，etcd 会牺牲可用性，确保数据的一致性。
5. **Eureka**：AP（可用性和分区容错性）

   - **解释**：Eureka 优先保证可用性和分区容错性。在发生网络分区时，Eureka 会继续提供服务，但可能会牺牲一致性。

总结：

- **ZooKeeper**、Consul 和 **etcd** 实现了 CP。
- **Redis 集群** 和 **Eureka** 实现了 AP。

## 19. 系统模块之间有哪些交互方式？如何降低耦合并保证可靠性？

> 原题 ID：`q1481`

**高频程度**：★★★★

**考察点**：考察对「模块之间如何交互」的掌握，重点看能否讲清：模块交互指系统中不同功能单元（模块）之间如何通信与协作

**回答框架**：

同步调用（函数调用/RPC/HTTP）：调用方阻塞等待结果，简单直观，适合强一致、实时性要求高的场景；缺点是耦合调用方与被调方可用性，容易级联故障。；异步消息（MQ）：通过队列/主题解耦，生产者只负责发，消费者按能力消费，适合削峰、解耦、最终一致；代价是复杂度上升（重复消费、顺序、事务消息）。；事件驱动：模块发布领域事件，其他模块订阅，实现‘谁关心谁处理’，进一步降低耦合；但事件链难追踪，需可观测性。；共享数据/共享内存：性能高但耦合最强，容易产生隐式依赖，一般只用于同进程内高性能场景。；依赖倒置：高层模块依赖抽象接口，不依赖具体实现。；接口隔离：接口尽量小、职责单一，避免‘胖接口’导致无关模块被迫一起变。

**参考回答**：

模块交互的核心是定义清晰、稳定、低耦合的接口契约，通过同步调用、异步消息或事件驱动等方式传递数据与控制，让模块可独立开发、测试与演进。

模块交互指系统中不同功能单元（模块）之间如何通信与协作。关键不是‘怎么调’，而是‘约定什么’。

1) 交互的本质：接口契约。契约包含：输入/输出数据结构、调用语义（同步/异步、幂等性）、错误码、超时与重试策略、版本兼容规则。就像两个人合作，先约定‘我说什么、你回什么、出错怎么办’，而不是直接闯进对方房间翻东西。
2) 常见交互方式：

- 同步调用（函数调用/RPC/HTTP）：调用方阻塞等待结果，简单直观，适合强一致、实时性要求高的场景；缺点是耦合调用方与被调方可用性，容易级联故障。
- 异步消息（MQ）：通过队列/主题解耦，生产者只负责发，消费者按能力消费，适合削峰、解耦、最终一致；代价是复杂度上升（重复消费、顺序、事务消息）。
- 事件驱动：模块发布领域事件，其他模块订阅，实现‘谁关心谁处理’，进一步降低耦合；但事件链难追踪，需可观测性。
- 共享数据/共享内存：性能高但耦合最强，容易产生隐式依赖，一般只用于同进程内高性能场景。 3) 设计原则：
- 依赖倒置：高层模块依赖抽象接口，不依赖具体实现。
- 接口隔离：接口尽量小、职责单一，避免‘胖接口’导致无关模块被迫一起变。
- 迪米特法则：只与直接朋友通信，减少跨层调用。
- 契约版本化：接口变更要向后兼容，如加字段而非改字段，用版本号或兼容层过渡。 4) 通俗类比：模块像公司部门。同步调用像打电话，必须对方接听才能继续；异步消息像发邮件/工单，发完就走，对方有空处理；事件驱动像公司广播，谁关心谁响应。接口契约就是公司规定的公文格式和流程，格式稳定，部门才能各自独立运转。 5) 适用场景：强一致、低延迟选同步；高并发、可容忍最终一致选异步；跨团队、跨系统解耦选事件驱动；同进程高性能选共享内存但需谨慎。

**常见追问**：如何避免「1) 只答‘通过接口调用’，不区分同步/异步/事件，缺乏场景判断」？ 「2) 认为异步一定比同步好，忽略复杂度、一致性和运维成本」在真实项目中应如何规避？

## 20. 控制器，调度器，kubelet中的监听，是监听etcd吗？

> 原题 ID：`q0922`

**高频程度**：★★

**考察点**：考察 K8s 组件是否直接监听 etcd，以及 apiserver 作为唯一入口的架构原因。

**回答框架**：

1.结论：控制器、调度器、kubelet 都不直接监听 etcd；2.机制：统一通过 apiserver 的 Watch API 监听资源变化；3.原因一：安全，apiserver 提供认证、鉴权、审计；4.原因二：抽象，屏蔽底层存储，etcd 可替换；5.原因三：一致性，apiserver 负责缓存、冲突检测与准入控制。

**参考回答**：

在 K8s 中，控制器（Controller）、调度器（Scheduler）和 kubelet 并不直接监听 etcd，而是通过 **`apiserver`**的 **`WatchAPI`** 监听资源变化。这是 Kubernetes 架构的核心设计之一，具体流程如下：

**1. 所有监听均通过`apiserver`**

- **etcd 是唯一的状态存储**，但组件不直接访问它，而是通过 API Server 的**`Watch`接口** 订阅资源变更。
- **原因**：  **安全性**：API Server 提供认证、鉴权、审计等能力。  **抽象性**：组件无需关心底层存储（etcd 可替换为其他存储）。  **一致性**：API Server 处理缓存、冲突检测等逻辑。

**2. 各组件监听流程**

**(1) 控制器（Controller）**

- **监听对象**：Deployment、ReplicaSet、Pod 等资源的事件（如创建、更新、删除）。
- **行为示例**：

  > - `Deployment Controller` 监听 `Deployment` 和 `ReplicaSet` 的变化。
  > - `ReplicaSet Controller` 监听 `ReplicaSet` 和 `Pod` 的变化。
- **触发逻辑**：当资源变更时，控制器对比 **期望状态（Spec）** 和 实际状态（Status），执行调和（Reconcile）。

**(2) 调度器（kube-scheduler）**

- **监听对象**：未调度（`Pending` 状态且 `nodeName` 为空）的 `Pod`。
- **行为示例**：发现新创建的 `Pod` 后，根据调度策略选择节点，向 API Server 发送绑定请求（更新 Pod 的 `nodeName`）。

**(3) kubelet**

- **监听对象**：调度到当前节点（`nodeName=kubelet所在节点`）的 `Pod`。
- **行为示例**：  发现新调度的 `Pod` 后，调用容器运行时（如 Containerd）启动容器。  持续上报 `Pod` 状态（如 `Running`、`Failed`）给 API Server。

**3. 关键设计思想**

- **事件驱动**：所有组件通过 Watch 机制实时响应变更，而非轮询。
- **水平扩展**：多个控制器实例可同时运行，依赖 APIServer 的乐观锁保证一致性。
- **声明式 API**：组件只需声明“期望状态”，由控制器负责调和实际状态。

**常见误解澄清**

- **etcd 的角色**：仅作为持久化存储，不参与事件推送。
- **API Server 的缓存**：提供高效的 Watch 接口，减轻 etcd 压力。
- **List-Watch 模式**：组件首次启动时会先 List 全量数据，再通过 Watch 增量更新。

**面试回答技巧**

- **简明版**：“K8s 组件通过 API Server 的 Watch 接口监听资源变化，而非直接访问 etcd。这种设计保证了安全性和扩展性。”
- **深入版**：“以 `Deployment` 创建为例：API Server 将配置写入 etcd 后，`Deployment Controller` 通过 Watch 感知到新对象，创建 `ReplicaSet`；`ReplicaSet Controller` 再创建 `Pod`；调度器和 kubelet 也通过 Watch 分别完成节点绑定和容器启动。”

这一设计是 Kubernetes 高可扩展性的核心，值得深入理解！

**常见追问**：如果 apiserver 挂了，现有 Pod 会怎样？为什么说 K8s 是声明式加控制器调和的架构？

## 21. 中文检索系统为何常用 Elasticsearch？分词与倒排索引如何发挥作用？

> 原题 ID：`q3339`

**高频程度**：★★★★

**考察点**：ES 倒排索引原理、中文分词 analyzer 与 IK、BM25 相关性打分、分片水平扩展。

**回答框架**：

1）倒排索引：词→文档列表，按词定位 posting list 求交并，远快于 LIKE '%%'；2）中文分词：analyzer = char_filter + tokenizer + token_filter，IK 的 smart/max_word 与写入粗写策略；3）相关性：BM25 含词频饱和与长度归一化，支持 boost/function_score；4）分片并行：协调节点分发并行查询再归并；5）定位：搜索分析用 ES，事务用 MySQL，不拿 ES 当数据库。

**参考回答**：

ES 的核心价值是倒排索引带来的近实时全文检索能力，配合中文分词器解决切词问题，并通过分片实现水平扩展。

- 第一，倒排索引：正排是"文档→词"，倒排是"词→文档列表"，包含词频和位置。查询时直接按词定位 posting list 再做交并，复杂度与命中词相关而非全表扫描，所以比 LIKE '%%' 快几个数量级，类比书末的索引页，按关键词直接翻页码而不是逐页翻书。
- 第二，中文分词：英文按空格天然分词，中文没有空格必须用分词器，ES 通过 analyzer = char_filter + tokenizer + token_filter 组成分析链，中文常用 IK（ik_smart 粗粒度、ik_max_word 细粒度），工程上一般写入用细粒度建索引、查询用粗粒度提召回，也可以用 jieba、HanLP 或内置 CJK bigram，分词质量直接决定召回率。
- 第三，相关性排序：基于 Lucene 的 BM25，是 TF-IDF 的改进，含词频饱和与文档长度归一化，支持 boost、function_score、多字段 best_fields/most_fields 等策略。
- 第四，分片：天生分布式，协调节点把查询分发到各分片并行执行再归并，支持水平扩展和副本容灾。

最后要强调定位：ES 适合海量文本的模糊和相关性搜索，不适合当强事务数据库，正确架构是 MySQL 存权威数据、ES 做检索索引、用 MQ 或 binlog 同步。

**常见追问**：1）ES 和 MySQL 数据怎么保持同步？2）ik_max_word 写入、ik_smart 查询为什么这样配？

## 22. 怎么在多台服务器同步session数据（数据库或者分布式系统）？

> 原题 ID：`q3347`

**高频程度**：★★★★

**考察点**：多机 Session 同步方案（粘性会话、集中式存储、Session 复制、JWT）、一致性与可用性权衡。

**回答框架**：

1）问题本质：Session 从进程内状态变成共享状态或让服务无状态；2）粘性会话：零改造但宕机丢会话、扩缩容重分布；3）集中式存储：Client→LB→无状态 App→Redis/DB，最常用；4）Session 复制：广播同步，节点多时网络开销大；5）JWT：签名自包含无状态，但无法主动失效、体积大。

**参考回答**：

单机 Session 存在本机内存，多台服务器时用户请求被负载均衡打到不同机器就出现登录态丢失，解决思路是把 Session 从"进程内状态"变成"进程外共享状态"，或者让服务本身无状态。常见四种方案。

- 第一，粘性会话：LB 按 cookie 或 IP 哈希把同一用户固定到同一台机器，优点是零改造、无网络开销，缺点是机器宕机即丢会话、扩缩容导致重新分布，不满足高可用。
- 第二，集中式 Session 存储，这是最常用的：架构是 Client→LB→无状态 App Server→Redis/DB，Redis 内存 KV 读写微秒级、支持 TTL 自动过期、可做主从/哨兵/Cluster 高可用；数据库持久化强但每请求读写 DB，QPS 高时成瓶颈，一般只做兜底或低频场景。
- 第三，Session 复制：Tomcat 等容器支持在集群间广播同步 Session 副本，节点少时简单，但节点一多网络开销和内存冗余是 O(N²)，不推荐大集群。
- 第四，JWT/客户端令牌：把状态签名后放在客户端，服务端完全无状态、天然适合多机和横向扩展，缺点是签发后无法主动失效，需要短过期加 refresh token 或黑名单来弥补，且 token 体积大、每次请求都携带。

工程上一般选 Redis 集中式存储打底，配合合理的 Session TTL 与降级策略，对高并发无状态服务可以用 JWT。

**常见追问**：1）Redis 存 Session 挂了怎么办？2）JWT 怎么做主动登出？

## 23. 上传文件的数量上限由哪些因素决定？

> 原题 ID：`q1831`

**高频程度**：★★★

**考察点**：考察对「上传文件的数量上限多少？」的掌握，重点看能否讲清：这个问题不能只回答一个数字，要分层看： 1) 前端/浏览器：HTML input 的 multiple 本身不限制数量；但浏览器对单次表单提交的字段数

**回答框架**：

这个问题不能只回答一个数字，要分层看：；1) 前端/浏览器：HTML input 的 multiple 本身不限制数量；但浏览器对单次表单提交的字段数、请求体大小、内存有隐性限制；用 JS 分片/并发上传时，并发数通常控制在 3~6 个，避免占满连接和带宽；2) 后端框架：不同语言/框架对 multipart 表单字段数有默认上限；例如 PHP 有 max_file_uploads 默认 20

**参考回答**：

上传文件数量上限没有统一标准，取决于前端框架、后端服务器、网关、存储和业务设计，通常由请求体大小、multipart 解析、文件句柄/内存、超时和产品需求共同决定。

这个问题不能只回答一个数字，要分层看：

1) 前端/浏览器：HTML input 的 multiple 本身不限制数量；但浏览器对单次表单提交的字段数、请求体大小、内存有隐性限制。用 JS 分片/并发上传时，并发数通常控制在 3~6 个，避免占满连接和带宽。
2) 后端框架：不同语言/框架对 multipart 表单字段数有默认上限。例如 PHP 有 max_file_uploads 默认 20；Nginx 有 client_max_body_size 默认 1M，且 multipart 解析受 body 大小限制；Java Spring 的 multipart max-file-size / max-request-size 默认 1MB/10MB；Go 的 net/http 默认没有硬性文件数限制，但 ParseMultipartForm 的 maxMemory 默认 32MB，超出会落盘。
3) 网关/代理：Nginx、API Gateway、负载均衡通常限制请求体大小、请求头大小、超时时间，文件多时容易触发 413、504。
4) 存储/业务：对象存储单次批量上传一般有数量限制，比如 AWS S3 单次 DeleteObjects 最多 1000 个，但上传本身是单对象；业务上通常建议单次不超过 10~100 个，大文件走分片/断点续传。

通俗类比：上传文件就像搬家。前端是打包，后端是收货，网关是小区门禁，存储是仓库。门禁一次只让一辆车进，仓库一次只收一定数量的箱子，所以“最多几个”取决于整条链路最窄的那一环。

实际回答建议：先说明没有固定值，再给出常见默认值，最后说设计原则：小文件批量可设几十到几百，大文件建议分片、并发控制、异步任务，并做前端校验和后端限流。

**常见追问**：如何避免「常见错误：直接说“没有限制”或“最多 100 个”」？ 「把前端 multiple 当成后端限制」在真实项目中应如何规避？

## 24. 系统为什么难以从小规模平滑演进到大规模？

> 原题 ID：`q3088`

**高频程度**：★★★

**考察点**：考察对「此外，如何从小规模开始并随时间逐步扩展系统并不容易理解」的掌握，重点看能否讲清：这句话通常出现在系统设计或 AI Agent 架构讨论中，核心是：很多人以为‘可扩展’就是一开始就上微服务、消息队列、向量数据库、多 Agent 编排

**回答框架**：

需求不确定：早期不知道用户量、数据量、调用模式，过早抽象会押错方向。；架构有惯性：单体、单库、单 Agent 一旦写死，后期拆分要改接口、迁数据、补监控。；扩展不是线性：流量从 100 到 1 万 QPS，瓶颈会从 CPU 变到数据库连接、锁、网络、模型推理排队。；团队与运维复杂度：微服务、多 Agent 会带来部署、观测、调试、权限、成本问题。；成本约束：小规模时用大集群、复杂中间件，ROI 很低。；先做‘可演进的简单系统’：清晰模块边界、接口稳定、数据可迁移。

**参考回答**：

从小规模起步并逐步扩展之所以难，是因为它要求架构在业务、流量、团队和成本都持续变化时，仍能低成本地演进，而不是一开始就设计成终态。

这句话通常出现在系统设计或 AI Agent 架构讨论中，核心是：很多人以为‘可扩展’就是一开始就上微服务、消息队列、向量数据库、多 Agent 编排，但真正难的是‘演进路径’。

通俗类比：盖房子。小规模时像搭帐篷，快、便宜、能住；业务长大后要变成楼房。难点不是帐篷或楼房本身，而是：帐篷里住着人时，怎么一边住一边换地基、加楼层，还不能塌。 为什么难：

1. 需求不确定：早期不知道用户量、数据量、调用模式，过早抽象会押错方向。
2. 架构有惯性：单体、单库、单 Agent 一旦写死，后期拆分要改接口、迁数据、补监控。
3. 扩展不是线性：流量从 100 到 1 万 QPS，瓶颈会从 CPU 变到数据库连接、锁、网络、模型推理排队。
4. 团队与运维复杂度：微服务、多 Agent 会带来部署、观测、调试、权限、成本问题。
5. 成本约束：小规模时用大集群、复杂中间件，ROI 很低。

适用场景：创业公司 MVP、AI Agent 从单 Agent 到多 Agent、从单机到分布式、从规则到模型。 正确做法：

- 先做‘可演进的简单系统’：清晰模块边界、接口稳定、数据可迁移。
- 用指标驱动扩展：QPS、延迟、错误率、token 成本、人工接管率。
- 按阶段引入复杂度：先单库单服务，再读写分离、缓存、队列、分片、多 Agent。
- 保留逃生通道：功能开关、灰度、双写、回滚、可观测性。 例子：AI Agent 早期一个 prompt + 工具调用就能跑；用户多了再拆出检索、规划、执行、记忆模块；再后来才上多 Agent 和向量库。每一步都解决当前瓶颈，而不是提前造终态。

## 27. 审批节点有人工审批、条件分支、抄送、结束节点，你会怎么设计类型？

> 原题 ID：`q1871`

**高频程度**：★★★

**考察点**：考察对「审批节点有人工审批、条件分支、抄送、结束节点，你会怎么设计类型」的掌握，重点看能否讲清：核心思路是把「流程结构」和「节点行为」解耦

**回答框架**：

人工审批节点：执行时创建待办任务(Task)，把流程实例置为 WAITING/挂起状态，等审批人回调（同意/拒绝/加签/转办）后再唤醒引擎继续流转。它是「异步阻塞型」节点。；条件分支节点：同步执行，读取流程变量(context 里的表单/业务数据)，按配置的表达式(如 SpEL/规则引擎)求值，选出命中的一条或多条出边。它是「路由型」节点，本身不产生待办。；抄送节点：同步执行，只做通知（站内信/邮件/IM），不阻塞、不影响流转，执行完直接走默认出边。它是「旁路通知型」节点。；结束节点：终止流程实例，把实例状态置为 COMPLETED，触发结束事件/回调。它是「终止型」节点。

**参考回答**：

用「节点类型枚举 + 统一节点基类 + 策略/工厂分发」设计：人工审批、条件分支、抄送、结束各自是不同 NodeType，共享统一接口，由执行引擎按类型路由到对应处理器。

核心思路是把「流程结构」和「节点行为」解耦。

1) 定义节点类型枚举：APPROVAL(人工审批)、CONDITION(条件分支)、CC(抄送)、END(结束)。
2) 抽象统一节点基类/接口 Node：包含 nodeId、nodeType、name、nextNodes(出边)、配置 config。所有节点实现 `execute(context)` 返回执行结果（如流转到哪些后继节点、是否挂起等待）。
3) 各类型语义不同，用策略模式分别实现：

- 人工审批节点：执行时创建待办任务(Task)，把流程实例置为 WAITING/挂起状态，等审批人回调（同意/拒绝/加签/转办）后再唤醒引擎继续流转。它是「异步阻塞型」节点。
- 条件分支节点：同步执行，读取流程变量(context 里的表单/业务数据)，按配置的表达式(如 SpEL/规则引擎)求值，选出命中的一条或多条出边。它是「路由型」节点，本身不产生待办。
- 抄送节点：同步执行，只做通知（站内信/邮件/IM），不阻塞、不影响流转，执行完直接走默认出边。它是「旁路通知型」节点。
- 结束节点：终止流程实例，把实例状态置为 COMPLETED，触发结束事件/回调。它是「终止型」节点。 4) 引擎主循环：从开始节点出发，取当前节点 -> 按 nodeType 从工厂拿对应 Handler -> 执行 -> 若返回「继续」则把后继节点入队继续跑；若返回「挂起」则持久化实例状态并退出循环，等待外部事件唤醒。 通俗类比：流程像一条流水线，节点是工位。审批工位要「停下来等人签字」，条件工位是「岔路口按规则选路」，抄送工位是「贴个通知单继续走」，结束工位是「下班关灯」。引擎就是传送带，遇到要等人的工位就暂停，等人回来再启动。 关键设计点：统一接口让引擎不关心具体类型；用工厂/注册表按 type 分发，新增节点类型只需加枚举+Handler，符合开闭原则；节点配置(审批人规则、条件表达式、抄送对象)与节点行为分离，便于可视化配置。

**常见追问**：如何避免「1) 把四类节点写成四个 if-else 硬编码在引擎里，新增类型要改引擎，违反开闭原则」？ 「2) 混淆「条件分支」和「审批节点的同意/拒绝分支」：前者是流程结构上的网关，后者是审批结果驱动的出边选择，二者抽象层级不同」在真实项目中应如何规避？

## 28. 分布式限流有哪些实现方案？中心化限流与负载均衡方案各有什么问题？

> 原题 ID：`q5037`

**高频程度**：★★★★

**考察点**：单机与分布式限流算法、全局配额一致性，以及中心化带来的性能和可用性权衡。

**回答框架**：

1) 明确限流维度与时间窗口；2) 比较固定窗、滑动窗、令牌桶和漏桶；3) 本地限流低延迟但非全局精确；4) 中心化计数更统一但成为依赖；5) 设计预分配、降级和观测。

**参考回答**：

**4.1.1 实现原理**

所谓中心化的限流其实就是将原本设计实现在本地服务的眼流操作抽离出来，做成一个中心化的限流器，所有服务共享，这里其实选用一个中心化的组件去实现即可，一般选用redis来实现就很方便。

实现步骤：

1. 选用一个中心化组件，比如Redis
2. 设定限流规则，比如每秒允许的最大请求数（QPS），并将该值存储在Redis中
3. 每当有请求到达时，服务器首先向Redis请求令牌
4. 如果获得令牌，请求可以继续处理；如果未获得令牌，则表示请求被限流，此时可以返回错误信息或提示稍后重试

**4.1.2代码实现**

```go
package main

import (
        "context"
        "fmt"
        "time"

        "github.com/go-redis/redis/v8"
)

const luaScript = `
local key = KEYS[1] -- hmap的key
local rate = tonumber(ARGV[1]) -- 令牌生成速率
local capacity = tonumber(ARGV[2]) -- 桶的容量
local now = tonumber(ARGV[3]) -- 当前时间（毫秒）
local requested = tonumber(ARGV[4]) -- 请求的令牌数

-- 获取上次更新时间和当前令牌数
local last_time, current_tokens = redis.call('HGET', key, 'last_time')
if not last_time then
        last_time = now
        current_tokens = capacity
else
        last_time = tonumber(last_time)
        current_tokens = tonumber(current_tokens)
end

-- 计算时间差
local time_diff = now - last_time -- 单位毫秒
-- 计算新的令牌数
local new_tokens = math.min(capacity, current_tokens + (time_diff * rate / 1000))

local allowed = new_tokens >= requested

if allowed then
        new_tokens = new_tokens - requested
end

redis.call('HSET', key, 'last_time', now)
redis.call('HSET', key, 'tokens', new_tokens)

return allowed
`

var ctx = context.Background()

// Redis客户端
var rdb *redis.Client

// 初始化Redis客户端
func initRedis() {
        rdb = redis.NewClient(&redis.Options{
                Addr: "localhost:6379",
        })
}

// TokenBucketLimiter 令牌桶限流器
type TokenBucketLimiter struct {
        key        string
        rate       float64
        capacity   int
        luaScript  string
}

// NewTokenBucketLimiter 创建新的令牌桶限流器
func NewTokenBucketLimiter(key string, rate float64, capacity int) *TokenBucketLimiter {
        return &TokenBucketLimiter{
                key:        key,
                rate:       rate,
                capacity:   capacity,
                luaScript:  luaScript,
        }
}

// Allow 允许请求
func (limiter *TokenBucketLimiter) Allow(requested int) (bool, error) {
        now := time.Now().UnixNano() / 1e6
        _, err := rdb.Eval(ctx, limiter.luaScript, []string{limiter.key}, limiter.rate, limiter.capacity, now, requested)
        if err != nil {
                if err.Error() != "redis: nil" {
                        return false, err
                }
                return false, nil
        }
        return true, nil
}

func main() {
        initRedis()

        limiter := NewTokenBucketLimiter("my_limiter:token_bucket", 5, 5)

        for i := 0; i < 20; i++ {
                allowed, err := limiter.Allow(1) // 一个请求，只需要一个令牌，所以这里传1
                if err != nil {
                        fmt.Println("Error:", err)
                        continue
                }
                if allowed {
                        fmt.Printf("第%d个请求通过\n", i+1)
                } else {
                        fmt.Printf("第%d个请求被限流\n", i+1)
                }
                time.Sleep(100 * time.Millisecond)
        }
}
```

**4.1.3 存在的问题**

1. **单点故障**：所有请求都必须经过Redis处理，所以Redis可能成为整个系统的性能瓶颈。但节点的redis场景下，当出现redis故障的时候，将会导致整个系统崩溃。所以可以使用使用Redis的主从复制或哨兵模式以实现高可用性。
2. **网络问题**：由于所有的请求都多走了一层redis，所以对网络带宽的依赖会有所增加。如果网络带宽有限，可能会导致请求传输速度变慢，从而影响Redis的整体性能。

**4.2 基于负载均衡的分布式限流方案**

前面分析了单机版的限流和基于中心化的限流都存在一定的问题，单机版主要是各个节点的流量分布可能不均匀，这将影响到限流阈值的设定，对限流精度造成干扰。而基于中心化的限流方案又会出现单点故障、网络带宽限制等问题。而这里的基于负载均衡的分布式限流其实就是针对单机版限流的一种改进，就是本地限流的基础上加上负载均衡器来均衡流量。

实现方案：

1. **请求分发：**通过负载均衡器或分布式服务发现，将请求均匀地分发到多个机器上。这样，每台机器处理的请求数量大致相同。
2. **本地限流状态维护：**在每台机器上维护一个本地的限流状态，独立地进行限流控制。可以使用令牌桶限流算法来实现这一逻辑。
3. **动态调整限流参数：**根据每台机器的负载情况（例如CPU和内存使用率），动态调整限流参数：

- 如果负载过高，降低限流阈值，减少请求处理量
- 如果负载较低，提高限流阈值，增加请求处理量

**4.2.1 存在的问题**

这种方法虽然加了负载均衡器保证了可以在本地实现限流，解决了分布式场景下的单机限流问题，但是由于引入了负载均衡也是系统的复杂性进一步提高，动态扩缩容的适应性也会变差，当系统需要扩容时，要进行额外的配置调整，确保新加入节点流量的均衡，从而达到限流目的。

限流是保障系统稳定和高效运行的重要手段，但是任何解决方案都没有银弹，限流方案同样如此，最优的限流方案因具体需求而异。选择适当的限流策略需要考虑系统需求、现有技术栈、系统负载以及底层性能。只有充分理解每种方案的特性，才能在实际应用中做出最佳选择。

## 29. 常见的缓存使用模式有哪些？旁路缓存、读穿透、写穿透、写回分别适合什么场景？

> 原题 ID：`q5038`

**考察点**：Cache-Aside、Read/Write-Through 与 Write-Back 的数据流、一致性和故障边界。

**回答框架**：

**参考回答**：

**Redis做缓存**

Redis由于性能高效，通常可以做数据库存储的缓存，比如给MySQL当缓存就是常见的玩法。具体而言，就是将MySQL的热点数据存储在Redis中，通常业务都满足二八原则，80%的流量在20%的热点数据之上，所以缓存是可以很大程度提升系统的吞吐量。

**怎么做**

一般而言，缓存分为服务器端缓存，和客户端缓存。服务器端缓存即服务端将数据存入Redis，可以在访问DB之后，将从DB得到的数据的缓存起来。

客户端缓存就是对服务端远程调用之后，将结果存储在客户端，这样下次请求相同数据时就能直接拿到结果，不会再远程调用，提高性能节省网络带宽。

用服务端还是客户端呢？

其实是需要分析具体瓶颈在哪里，当然，如果按通常的经验，从服务角度来看，在目前的微服务架构下，每个服务其实都应该缓存一些热点数据，以减轻热点数据频繁请求给自己带来的压力，毕竟微服务也要有一定的互不信任原则。

至于客户端缓存，这个就更看场景了，频繁请求的数据，就有必要做缓存。

下面我们以服务端缓存的视角，来进行缓存分析。

**缓存的几种模式**

缓存一般有如下几种模式：

- **Cache Aside Pattern**：旁路缓存模式
- **Read Through Cache Pattern**：读穿透模式
- **Write Through Cache Pattern**：写穿透模式
- **Write Behind Pattern**：又叫Write Back，异步缓存写入模式

下面我们来详细介绍这四个模式

**Cache Aside**

Cache Aside，即旁路缓存模式，是最常见的模式，应用服务把缓存当作数据库的旁路，直接和缓存进行交互。

读操作的流程如下：

应用服务收到查询请求后，先查询数据是否在缓存上，如果在，就用缓存数据直接打包返回；如果不存在，就去访问数据库，从数据库查询，并放到缓存中。除了查库后加载这种模式，如果业务有需要，还可以预加载数据到缓存。

说完读操作，我们再看看写操作的流程：

在更新操作的时候，Cache Aside模式是一般是先更新数据库，然后直接删除缓存，为什么不直接更新呢？因为更新相比删除会更容易造成时序性问题，这里有同学问时序性问题是什么？举个例子：thread1更新mysql为5 -> thread2更新mysql为3 -> thread2更新缓存为3 -> thread1更新缓存为5，最终正确的数据因为时序性被覆盖了。

Cache Aside适用于读多写少的场景，比如用户信息、新闻报道等，一旦写入缓存，几乎不会进行修改，该模式的缺点是可能会出现缓存和数据库不一致的情况。

**Read Through**

Read Through，读穿透模式，和Cache Aside模式的区别在于应用服务不再和缓存直接交互，而是直接访问数据库服务，这个数据库服务可以理解为一个代理，即单挂起这么一个服务，由它来访问数据库和缓存，作为使用者来看，不知道里面到底有没有缓存，数据库服务会自己来根据情况查询缓存或者数据库。

查询的时候，和Cache Aside一样，也是缓存中有，就用从缓存中获得的数据，没有就查DB，只不过这些由数据库服务托管保存，而对应用服务是透明的。

相比Cache Aside，Read Through的优势是缓存对业务透明，业务代码更简洁。缺点是缓存命中时性能不如Cache Aside，相比直接访问缓存，还会多一次服务间调用。

**Write Through**

在Cache Aside中，应用程序需要维护两个数据存储：一个缓存，一个数据库。这对于应用程序来说，更新操作比较麻烦，还要先更新数据库，再去删除缓存。

Write Through模式相当于做了一层封装：

由这个存储服务先写入MySQL，再同步写入Redis，这样及时加载或更新了缓存数据。

可以理解为，应用程序只有一个单独的访问源，而存储服务自己维护访问逻辑。

当使用Write Through时，一般都配合使用Read Through来使用。Write Through的潜在使用场景是银行系统。

Write Through适用情况有：

- 对缓存及时性要求更高（写入就加载了缓存，当然这种模式可能会有时序性问题）
- 不能忍受数据丢失（相对Write-Behind而言）和数据不一致（当然Cache Aside也是如此）

在使用Write Through时要特别注意的是缓存的有效性管理，否则会导致大量的缓存占用内存资源，因为这种模式下只要写入数据就加载了缓存。

**Write-Behind**

Write-Behind和Write-Through相同点都是写入时候会更新数据库、也会更新缓存。

不同点在于Write-Through会把数据立即写入数据库中，然后写缓存，安全性很高。

而Write-Behind是先写缓存，然后异步把数据一起写入数据库，这个异步写操作是Write-Behind的最大特点。

数据库写操作可以用不同的方式完成

一种是时间上的灵活性，其中一个方式就是收集写操作并在某一时间点（比如数据库负载低的时候）慢慢写入。

另一种方式就是合并几个写操作成为一个批量操作，一起批量写入。

两者是可以根据业务情况结合的。

异步写操作极大地降低了请求延迟并减轻了数据库的负担，但是代价是安全性不够，比如先写入了Redis，更新操作先放在存储服务内存中，但是还没异步写入MySQL之前，存储服务崩溃了，那么数据也就丢失了。

**4种模式怎么选择**

各有优势，但是Cache-Aside Pattern，旁路缓存模式是最常见，最易用的，在业务开发中，其他模式很少会用到。

**总结**

本节我们讲解了缓存的四种使用范式，其中旁路缓存模式是在生产环境应用最广的，后续我们的一些分析，也会围绕着旁路缓存模式来进行。

## 30. 什么是聚合写？它如何减少下游写放大？

> 原题 ID：`q5039`

**高频程度**：★★★★

**考察点**：批量合并的收益条件、吞吐与时延权衡，避免承诺固定倍数。

**回答框架**：

1) 把多个独立写入批处理，或按同一 key 合并增量
2) 收益来自减少网络往返、事务提交和索引维护次数
3) 效果取决于负载、批大小、热点、存储引擎和持久化策略
4) 同时评估延迟、丢失窗口、幂等、顺序与背压

**参考回答**：

聚合写是在内存、日志或队列中暂存多个写请求，再批量提交，或者把同一对象的多次可交换更新合并为一次。

例如把一秒内对同一计数器的多个 `+1` 合成一个 `+N`，或用数据库批量插入代替逐行提交。

它可能减少网络往返、事务提交、日志刷盘和索引维护，因此提高吞吐；但不存在通用的“提升数十倍”。

实际收益取决于数据库、单批大小、并发、热点程度、是否需要 fsync、数据行与索引大小等，必须压测。若写入不能交换或合并，例如余额转账、严格有序状态迁移，就不能只看最终数值随意聚合。

实现时要设置按数量/时间触发的 flush、最大内存、背压和失败重试；批次必须有稳定标识以支持幂等，部分成功要能定位，进程崩溃前未落盘的数据需要 WAL、消息队列或业务可接受的丢失窗口来处理。

**常见追问**：聚合写发生部分成功或进程崩溃时，如何保证重试不会重复计数？

## 31. 聚合写会带来哪些可靠性和一致性问题？应如何取舍？

> 原题 ID：`q5040`

**高频程度**：★★★

**考察点**：丢失窗口、读己之写、批次原子性、重复与乱序，以及持久化设计。

**回答框架**：

1) 内存缓冲在宕机时可能丢失尚未提交的写入
2) 异步落库导致数据库读到旧值，破坏读己之写
3) 批量失败、重试和多节点聚合会带来重复或乱序
4) 按业务正确性要求选择 WAL、队列、同步写或最终一致

**参考回答**：

聚合写把同步写转换成延迟批处理后，主要风险包括：

- 缓冲数据随进程故障丢失；
- 数据库在 flush 前读到旧值；
- 一个批次部分成功后难以判断哪些需要重试；
- 多节点同时聚合同一 key 时发生重复、乱序或覆盖；
- 积压还会放大恢复时的突发流量。

若业务允许近似值或短暂陈旧，例如非计费的展示计数，可以接受小的丢失窗口并定期校准。若写入涉及余额、库存或不可重复副作用，应使用持久化日志或消息队列、幂等键/序列号、原子条件更新和对账，必要时保留同步提交路径。查询要求读己之写时，可返回写入确认令牌、读取包含未刷新增量的聚合层，或等待明确的 durable acknowledgement；简单 sleep 并不能提供正确性保证。

选型要先写清 RPO、可见延迟、顺序、幂等和恢复时间，再决定批大小与 flush 周期。吞吐收益不应以牺牲未被业务接受的正确性为代价。

**常见追问**：如果消息队列已确认消费但数据库批量写失败，怎样设计可重放而不重复？

## 34. 秒杀系统如何防止超卖和少卖？黄牛又该怎么打击？

> 原题 ID：`q5051`

**高频程度**：★★★★

**考察点**：以库存不变量、幂等交易闭环和多维风控分别解决超卖、库存滞留与不公平竞争。

**回答框架**：

1) 超卖：库存扣减必须是带条件的原子操作，且成功凭证唯一
2) 少卖：区分库存保留与最终售出，用超时释放、重试和对账回收
3) 一致性：订单、库存和支付都用幂等键、状态机与持久化事件衔接
4) 反作弊：账号、设备、行为和关系特征联合风控，IP 限制只作辅助

**参考回答**：

防超卖的核心是不变量：对一个活动商品，已确认占用的数量不能超过可售库存。库存扣减必须经过唯一的权威写入路径，并使用原子条件更新，例如数据库执行 `UPDATE ... SET stock = stock - 1 WHERE stock > 0`，或在 Redis 中用 Lua/事务一次完成资格检查、去重和扣减。

请求要携带稳定的幂等键，重试不能重复占用；如果 Redis 只是前置名额层，数据库仍要有最终约束，不能把可能丢失的缓存写直接当作不可撤销的交易事实。

所谓“少卖”通常是库存已经保留，但订单创建失败、用户未支付或释放失败，导致可售库存被长期占住。

- 应明确区分可售、已保留和已售出：预扣成功后通过本地事务 Outbox 或可靠消息驱动建单；
- 订单在支付时限内未完成则以幂等操作释放保留量；
- 重试队列、死信处理和周期性对账负责修复遗漏。

活动结束时出现未售完也可能是需求不足或风控策略的正常结果，不能为了清空库存而破坏资格与限购规则。

订单状态迁移要带条件或版本号，确保支付成功与超时关单并发时只有合法迁移生效；随后根据最终状态决定确认或释放库存。所有消费者都应支持重复消息，监控库存不变量、保留超时量、订单创建失败和对账差异。

打击黄牛不能只封 IP，因为 NAT 会误伤正常用户，代理也容易绕过。应组合实名认证或账号资格、预约、单账号/设备/支付工具限购、设备指纹、行为频率与轨迹、关系图谱和风险评分；高风险请求再增加验证码或人工校验。风控结果应可解释、可申诉，并为正常用户保留公平的排队或抽签机制。

**常见追问**：支付回调与超时关单同时到达时，如何保证订单和库存最终落在同一业务结果？

1. keyUserGoodsSecNum， 即 SK:UserGoodsSecNum:`goodsID`:`userID`，对应Value为`secNum`，secNum是秒杀单号，秒杀单号在发起秒杀请求的返回包里可以得到，所以这个SK:UserGoodsSecNum:`goodsID`:`userID`的意义是某个用户在某个商品，秒杀单号是多少，如果不是为空，则表示在秒杀流程中，禁止用户重复发起秒杀流程
2. keyStock，即SK:Stock:`goodsID`，对应Value为名额数量，比如SK:Stock:1表示1号产品目前的名额，Value如果是10，就是还剩余10件
3. keyLimit是 SK:Limit:`goodsID`，对应value为全局限额，即单个用户对该商品能秒杀多少件

扣减时候流程要点分析会详细讲解，现在理解个大概思路：

1. 查看是否还有库存，也就是查看SK:Stock:`goodsID` 存放的数字，也就是名额还剩多少
2. 扣减库存，可以用DECR SK:Stock:`goodsID`命令来做
3. 以secNum为Key记录本次秒杀信息，secNum提前用uuid生成即可

注意这里有个并发问题，如果很多请求同时到来，都发现库存>0，比如库存等于1，此时同时去扣减，这时候就给库存整成负数了。

所以这里需要引入LUA来保证原子性，具体代码后面章节会给出。

## 36. 秒杀系统的订单生成、库存回补与超时处理如何设计？

> 原题 ID：`q5053`

**高频程度**：★★★★

**考察点**：预扣库存后的可靠建单、未支付超时释放和并发状态迁移。

**回答框架**：

1) 预扣成功产生持久化事件；2) 消费端幂等创建订单；3) 延迟任务触发超时关单；4) 支付与关单通过条件状态更新竞争；5) 库存回补幂等并由对账兜底。

**参考回答**：

**生成订单、扣减库存**

MySQL这里涉及两部分数据。

1. 库存，字段有：商品id、库存总数、库存数量stock
2. 操作记录数据，字段有 唯一id（用户id+商品id），订单状态（等待支付、订单关闭、支付成功），用户id，商品id，抢购数量

消费消息队列的数据：

1. 扣减数据库存储
2. 产生真正的订单（一般会有专门的订单系统），订单有状态
3. 在数据库t_seckill_record表里产生一条订单记录数据，记录有状态，可以用来支持幂等
4. 通知预扣系统的Redis状态变了，更新下状态，如果发现有数据异常，此时也做修复，前端发现Redis状态变了可以跳转到付费页面
5. 付费之后状态会改变，如果超时未付费，额度退回

这里MySQL不会超卖的大致原理如下：

```SQL
1.update t_seckill_stock set stock = stock - 1 where stock >= 1 and product_id = xxx;

```

如果SQL语句1影响行数未0，说明库存已经扣完，不会再执行第二条语句，而是通知Redis已抢完。

**插入秒杀记录表**

```SQL
Insert t_seckill_record(order_id, user_id, goods_id, status) values(......),
```

 status等于待付款，状态枚举可以查看整体设计中的表结构设计。

**名额加载回Redis**

这里需要判断MySQL库存还存在，并且Redis名额已经为0，此时可能就是少卖了。

为了避免还有请求在处理中，可以增加一个逻辑：上述状态维持超过x分钟（比如5分钟），分钟级的时间足够消息处理了。

确定少卖之后，这时候就把MySQL的库存加载到Redis。

**超时库存返回MySQL**

定时任务扫，如果订单超时未支付，额度加载回MySQL，通过乐观锁+事务实现幂等，此时由于已经支付超时，过去了很长时间，大概率Redis名额早没有了，可以主动触发一次上面的名额加载的逻辑。

也可以简单一点，更新MySQL额度之后，直接加载Redis，失败了还有名额加载逻辑兜底。

退还给MySQL额度具体操作：

通过这个记录的状态来做幂等，退款时状态会变，通过where status条件乐观锁保护；

update t_seckill_record set status = 超时关闭 where order_id = xxx and status = 待支付

Where如果影响行数不为0，就可以继续执行下面操作退还库存。

 update t_seckill_stock set stock = stock + 2 where product_id = xxx;

注意这里是以一次性买2个为例，如果是10就是stock+10

## 37. 微信支付优惠券秒杀实战：异步化发券、库存批量消费是怎么做的？

> 原题 ID：`q5054`

**高频程度**：★★★★

**考察点**：优惠券秒杀中的异步发放、库存批处理与可靠性边界，避免把案例参数当通用结论。

**参考回答**：

**业务背景及挑战**

这个案例为微信支付有优惠产品的内部方案分享。牛哥脱敏之后进行展示。

先介绍下微信支付有优惠：

可能看到这张图很多同学就知道是什么产品了，不清楚的同学可以看看这篇文章[小程序“微信支付有优惠” 搞定了免费微信提现](https://post.smzdm.com/p/am8dm5e4/)

下面说回秒杀：

支付有优惠 准备进行一次秒杀活动，秒杀的“商品”是微信支付商家优惠券和提现免费券，秒杀的时候不需要进行支付。

相对于一般的秒杀活动，活动有以下特点：

- 发放的都是线上的券，要求尽量快速发券成功，并引导至商家小程序消费，以保证转换率。
- 活动频率较低，且准备时间短。预计这样规模的秒杀活动一年两三次。
- 产品希望系统的容量能达到 1w/s，实际发券为 2w/s：用户每次秒杀成功时会发两张券：商家券和提现免费券。

**挑战**

对于秒杀系统的后台服务，已经有了一些有效的解决思路：缓存，异步化，限流，降级，拆分单点（特别是 IO 单点），压测等。

但具体到这个业务本身，会有一些具体的问题需要解决：

异步化：对于整个业务流程，需要将什么部分进行异步化？

限流：限流系统需要处理秒杀的所有流量，能否解决或避免单点可用性问题？是否需要考虑限流系统的实现、配置的不同会对限流的效果造成的影响？

活动频率低，开发人力少：这种规模的活动当时预计一年两三次，所以活动前后需要扩缩容，否则资源长期闲置会造成极大的浪费。而存储的缩容是一件成本很高的事情，能否通过技术手段降低扩缩容的成本？

压测：业务要求尽快把券发完，所以需要对全流程进行压测确认发券链路性能是否满足要求。这涉及到外部的券系统、商户系统的配合。但工期比较紧张，能否在压测阶段先对内部系统压测以便更早暴露问题？

**同步发券可行么**

也就是同步秒杀可以吗，毕竟QPS要求是2w，如果能同步做，是最好的，对微信已有的商家券、提现券来说，也是可以支持的。并且异步化也会增加一些开发成本，那是否能直接进行同步发券？

发券流程包括：写入用户的兑换记录、调用商家券和提现免费券系统进行发券、商家券系统通知商家等。这个发券的流程是比较重的耗时比较长，在同步请求中完成的话对机器数量的要求较高。

而更重要的是，发券的流程需要依赖商家的系统，我们对商家系统性能的控制力是比较有限的，也不想因此对商家设置过高的门槛。

所以也要求对发券的过程进行异步化，以降低商家系统的容量要求。

另外需要注意的是，由于秒杀的奖品是具有一定的引流目的线上商家券，而转换率最高的模式是用户秒杀完获得商家券之后，直接跳转到商家处进行核销。

所以发券的速度也不能太慢。

（与此相对照的是代金券：代金券的核销是在微信支付系统中完成的，不需要商家感知。但由于用户在未拉起支付前无法强提示有券，所以核销率会比商家券低不少。）

**异步化**

对哪些流程进行异步化？

异步化是解决秒杀问题的一个重要的思路，但不同的业务场景下，异步化的范围也有所不同。

全流程异步化？最彻底的异步化就是，在对请求做完参数检查、频率限制之后，把后续的一整个流程进行异步化处理。

但这样会产生一个大家可能都经历过的用户体验问题：秒杀后菊花转了很久，最后弹了个框提示：奖品已抢光。产品不太可接受这样的用户体验，所以如果有其他的办法，尽量选择别的。

发券流程异步化

但如果确认用户能抢到券了，且在绝大部分情况下都能发券成功时，再让用户等待一会是可以接受的（甚至多等一会有种参与秒杀的感觉）。

所以在实时流程中，需要确认用户是否能成功发券，大概涉及以下业务逻辑：

**实时流程中的业务逻辑**

所以在实时流程中，需要确认用户是否能成功发券，大概涉及以下业务逻辑：

1. 校验发奖请求，避免刷子通过修改请求包的方法获取不对自己定向投放的高价值奖品，或重复秒杀
2. 确认并扣减库存
3. 在存储中记录发放请求（这里应该是写入NoSQL类数据库）
4. 将发放请求加入异步队列

经过优化，这些实时流程能达到性能要求，所以最终采用这个方案。

**异步队列选型**

当前环境下，常用的可用来异步化的组件有可靠事件中心和 Svrkit MQ。使用可靠事件中心会有以下的问题：

- 会造成队列积压，而可靠事件中心现在用的是公用的资源，会影响到别的业务。

需要承受秒杀的流量，作为一个服务，相比于 Svrkit MQ，在可用性及请求耗时方面不占优势。

所以最终选择使用 Svrkit MQ，其支持错误重试，全局出队限流，开发成本也很低。

但有两个问题需要注意：

- 在极端的情况下如果机器在秒杀的那几分钟挂掉，会导致 MQ 里的请求丢失。最低成本的处理方法是对请求进行上报，后期还能补救。如果排期允许，可以加入扫表补漏的脚本。
- MQ 不支持二阶段事务。不过实际发券成功但给用户返回失败是可以接受的，所以可以在 MQ 入队成功之后再给用户返回成功。

PS：这里的可靠事件中心，Svrkit MQ都是微信的组件，这里保留下来主要给大家展示一下选型的思考。

**发奖结果单机缓存**

在用户抢券成功，进入异步发券流程后，前端需要感知发券的结果。一种方案是使用websocket，服务端主动推送结果，但当前的技术栈对此支持并不完善，长链接对资源的消耗也比较大，贸然使用的风险较高。

所以决定由前端轮询发券的结果，而这个查询请求的量级和秒杀活动相当。理论上这个量级对 kv 来说不成问题，但活动的奖品总数量很多，而且如果发券耗时又比较久（需要匹配商家系统的性能）的情况下，会造成用户多次重试查询，可能引起雪崩。

除了在前端进行查询频率的控制外，为了将存储的 qps 容量留给其他领域以及进一步降低风险，这里加上了发奖结果的“缓存”。

1. 首先把 参与秒杀 ，及 查询结果 的请求按用户 uin 进行路由，使得同一个用户的请求落在相同的机器上。
2. 秒杀和发奖都把数据记录在单机 memcache 中
3. 查询时，先查询 memcache

**库存批量消费（这个优化挺好的，在资源有限的情况节约一点）**

秒杀系统的一个挑战就是库存限制，难点在于库存的计数器可能无法承担请求量。根据隔壁团队项目的压测，quotakv（腾讯内部的一个kv存储，可以理解为Redis）的单 key 写并发能支持到 2.3w/s，看起来是能满足需求的。但容量也未冗余太多，更重要的是业务并未独立部署 quotakv，运维不允许我们这么大的请求量。

为顺次这么低的活动特意申请集群也不是很有必要，而且业界解决这个问题的方法也比较成熟了，思路一般有两种：

- 计数器拆分：把商品的库存计数器拆成多个，然后根据路由决定用户访问哪个计数器（根据实现可以选择进行跳key）。不过这个方案需要先确定好计数器的数量，修改这个数量略为麻烦；而且仍然会把所有请求都穿透到计数器的存储
- 批量结算：每次向中央计数器请求消耗多个库存，然后在本地（共享内存或 进程内存）进行管理。根据能否超发少发，可以选择先消费后结算，或先结算后消费。

由于无独立集群的限制，有优惠选择的是批量结算的模式。另外对于库存管理的要求是不可接受超发，但能接受一定的漏发，所以选择的是先结算后消费的模式。

**库存消费流程**

每次请求消耗库存的流程如下：

1. 检查本地是否有库存，如有则直接消费
2. 如果本地没有库存了，检查本地是否有 quotakv 已无库存的标记，如有则返回无库存，这一步是为了避免真正没库存的时候，所有的请求都穿透到了 quotakv。另外，考虑到产品可能有补库存的需求，这个标记设置了一个有效期。
3. 如果无标记，则尝试往 quotakv 批量消耗库存。如果消费成功，则更新本地的库存数量并消费；如果 quotakv 无库存或 key 不存在，则更新无库存标记。

由于服务采用的是单进程多线程的模式（数据共享更方便，且引入 MQ 时框架必须要求为多线程模式），所以“本地”的库存维护在每台机的进程内存中，使用原子变量即可。

缓存会被击穿吗？

这种缓存击穿的措施需要考虑一下是否会击穿至后端。这个流程下，可能发生击穿的场景是刚开始秒杀的时候，所有机器都没有库存信息，需要请求 quotakv。这种情况并发度最大是机器数量\*奖品数量，本次活动中是百级别或者刚过千级别，问题不大。如果机器数或者奖品数增加，也可以通过秒杀前预加载的方式避免这个问题。

同样的，本地里 quotakv 无库存的标记的过期也是类似的情况。不过可以通过过期时间随机化避免。

## 38. 为什么通用文件系统不适合海量小文件？应该怎么设计小文件存储系统？

> 原题 ID：`q5055`

**高频程度**：★★★★

**考察点**：海量小文件导致的元数据、随机 I/O 和存储空间放大，以及合并存储与索引设计。

**回答框架**：

1) 分析 inode/元数据与随机访问瓶颈；2) 将小对象聚合进较大容器；3) 独立索引记录偏移和长度；4) 处理删除、压缩和冷热分层；5) 评估对象存储、KV 与专用服务。

**参考回答**：

**为什么通用文件系统不适合大量小文件？**

在深入设计之前，先理解为什么常见方案（如直接存硬盘）会失效：

1. **元数据开销过大**：

   - 在传统文件系统（如 ext4、NTFS）中，每个文件都有对应的 inode 存储元数据（权限、时间戳、指针等）。
   - 若文件平均 50KB，而文件系统块大小是 4KB，即使文件很小，也至少要占用一个块。元数据空间和磁盘寻道的开销远大于数据本身。
2. **磁盘I/O效率低**：

   - 访问一个小文件通常需要多次 I/O：读取目录、读取 inode、读取数据块。
   - 若文件分散在不同位置，机械硬盘会产生大量的随机读写，而 SSD 也会因大量小请求导致 I/O 队列饱和。
3. **缓存利用率低**：

   - 内存页缓存通常以 4KB 为单位。如果文件是 10KB，即使只读一次，也会占用 3 个页缓存，而实际有效数据只有 10KB，造成内存浪费。
4. **文件数量限制**：

   - 目录中文件过多时，线性查找速度会极慢（即使使用 B-tree 等索引，海量小文件依然会影响路径查找性能）。

---

**针对海量小文件的存储引擎设计思路**

核心思路可以概括为：**合并写入、分离处理元数据和数据、追加写避免覆盖**。

**1. 核心设计模式：日志结构合并（LSM树思想）与对象存储思路**

借鉴 LSM-Tree 和对象存储（如 AWS S3）的理念，不将每个小文件单独存为操作系统文件，而是：

- **数据层面**：将多个小文件合并成一个大文件（Segment/Extent），顺序追加写入磁盘，避免随机写。
- **元数据层面**：建立高效的索引（如 Key-Value 结构），记录每个小文件在哪个大文件中的偏移量和长度。

**2. 具体架构组件**

假设我们设计一个名为 **TinyFS** 的小文件存储引擎，其内部结构如下：

**① 数据文件（Data File）**

- **格式**：一系列固定大小或动态增长的大文件（如每个 512MB 或 1GB），称为 Chunk 或 Segment。
- **写入方式**：**仅允许追加写（Append-only）**。
- **内部结构**：一个大文件内部顺序存放多个小文件的数据块，每个数据块前通常有一个简单的头部记录其大小或 CRC 校验码。

```Plain Text
[Data File: 000001.tfs]
-------------------------------------------------------------
| 头部 | 小文件A数据(30KB) | 头部 | 小文件B(10KB) | 头部 | 小文件C(60KB) | ...
-------------------------------------------------------------
```

**② 索引文件（Index File）**

由于数据是追加的，需要一个地方快速找到某个 Key 对应的数据。这是一个典型的 **Key-Value 存储**需求。

- **Key**：文件的唯一标识（如文件 ID 或路径 Hash）。
- **Value**：文件元数据 + 物理定位。例如：`{file_id: xxx, chunk_id: 000001, offset: 1024, size: 30720, timestamp: xxx, crc: xxxx}`。
- **数据结构选择**：

  - **哈希表**：内存中维护一个大的哈希表，查找 O(1)，但内存占用大，重启需要重建。
  - **B-Tree / B+Tree**：可以存储在磁盘上，支持范围查询，但写放大比 LSM 大。
  - **LSM-Tree**：更适合这种写多读多的场景。先写内存中的 MemTable（有序结构，如跳表），达到阈值后冻结为 Immutable MemTable，然后刷盘成 SSTable（Sorted String Table）文件。查找时依次查 MemTable、Immutable MemTable 和 SSTable。

**③ 预写日志（WAL，Write-Ahead Log）**

- 为了数据一致性，任何写操作（追加文件）必须先记录 WAL。系统崩溃后，可以通过重放 WAL 恢复 MemTable 中未刷盘的数据。

**3. 垃圾回收与合并（Compaction）**

由于采用追加写，更新或删除文件会产生垃圾空间（旧版本的数据仍然在数据文件中，只是索引指向了新版本或标记删除）。

- **标记删除/更新**：写入一条新的数据记录，索引指向新地址。旧的索引和数据成为垃圾。
- **合并过程**：后台线程定期对数据文件和索引文件进行合并。

  1. 读取旧的 Chunk 文件。
  2. 遍历其中的数据，只保留最新的有效数据。
  3. 将有效数据写入新的 Chunk 文件。
  4. 生成新的索引文件或更新索引指向新位置。
  5. 删除旧的 Chunk 文件。

  - 这个过程类似于 LSM-Tree 的 Compaction，可以有效清理碎片，回收磁盘空间。

---

**架构对比：几种技术选型**

如果你需要实现这个系统，可以参考以下几种主流技术的设计思路：

| 方案类型 | 代表技术 | 原理 | 优点 | 缺点 |
|-|-|-|-|-|
| **通用 KV 存储** | **RocksDB**、**LevelDB** | 基于 LSM-Tree，Key 存文件名，Value 存文件内容。 | 写入性能高，延迟低，适合小对象。 | 大 Value（几百 KB 以上）可能导致写放大严重，Compaction 时 I/O 开销大。 |
| **专门的小文件系统** | **Facebook Haystack** | 将多个图片合并存储，通过逻辑卷（Physical Volume）和索引定位。 | 专为小文件（照片）设计，元数据极轻量，减少磁盘寻道。 | 系统相对复杂，社区方案较少。 |
| **对象存储网关** | **MinIO**、**Ceph** | 将小文件聚合为对象存储中的对象。 | 高可用，扩展性好，支持 S3 兼容 API。 | 元数据服务（RADOS Gateway）可能成为瓶颈，延迟相对较高。 |
| **嵌入式数据库** | **SQLite**、**BerkeleyDB** | 将小文件作为 BLOB 存入数据库表。 | 事务支持好，管理简单。 | 数据库文件过大时备份恢复困难，并发性能可能受限。 |

**推荐方案**

对于平均几十 KB 的小文件：

1. **首选 RocksDB/LevelDB 作为存储引擎**：可以利用其高效的写入缓存和 LSM 结构。需要注意的是配置 `blobdb`（大值分离）特性，将较大的值（几十 KB 已算大）存储在单独的文件中，避免值在 LSM 树的多层间频繁拷贝导致写放大。
2. **如果追求极致性能且愿意投入研发**：可以借鉴 Haystack 的设计思路，自定义文件格式，采用“文件名 -> (文件ID, 偏移量, 大小)”的定长内存索引，配合合并写入。
3. **如果希望简单且文件数量在百万级别**：可以直接使用 SQLite，利用其页面缓存和 B-tree 结构。

总的来说，这个问题的核心挑战在于**元数据膨胀**和**磁盘寻道**。通过 **合并写入** 和 **KV 索引分离** 的设计，就能很好地应对几十 KB 小文件的存储场景。

## 39. 分库分表会遇到哪些问题？应该怎么解决？

**回答框架**：

1) 按访问模式选择分片键；2) 保留全局 ID 与路由能力；3) 限制跨分片事务和聚合；4) 设计双写迁移、校验与回滚；5) 用中间件或应用层治理分页、唯一性和故障。

**参考回答**：

**跨节点关联查询JOIN问题**

（解决方案：1.全局表 2.冗余字段 3.建立1：1的ER实体关系分片）

在 MySQL 中，跨节点关联查询（JOIN）是一个复杂的问题，尤其是在分布式数据库或分库分表场景下。以下是解决这一问题的几种常见方法：

1. **应用层实现 JOIN**

- **方法**：在应用层分别查询两个节点的数据，然后在内存中进行关联操作。
- **优点**：避免数据库跨节点查询的性能开销。灵活性高，可以根据业务需求优化关联逻辑。
- **缺点**：需要编写额外的代码，增加了开发复杂度。如果数据量较大，内存消耗和计算开销会比较高。

2. **数据冗余**

- **方法**：将需要关联的数据冗余存储到同一个节点或表中。
- **优点**：避免了跨节点 JOIN 的问题。查询性能高，直接在同一节点完成 JOIN。
- **缺点**：数据冗余会占用更多存储空间。数据一致性维护成本高，需要额外的同步机制。

3. **使用全局表（广播表）**

- **方法**：将小表（如字典表、配置表）复制到所有节点，确保 JOIN 操作可以在本地完成。
- **优点**：避免跨节点查询，性能较好。适合小表与大表的 JOIN 场景。
- **缺点**：只适用于小表，大表不适合全局复制。数据更新时需要同步到所有节点。

4. **分片键设计优化**

- **方法**：在分库分表时，将需要关联的表使用相同的分片键（Sharding Key），确保关联数据分布在同一个节点。
- **优点**：避免跨节点 JOIN，查询性能高。
- **缺点**：分片键设计需要提前规划，灵活性较低。不适合多维度关联的场景。

5. **使用分布式数据库中间件**

- **方法**：通过中间件（如 MyCat、ShardingSphere）实现跨节点 JOIN。
- **优点**：中间件可以自动处理跨节点查询和聚合。对应用透明，开发复杂度低。
- **缺点**：中间件可能会成为性能瓶颈。需要额外的运维成本。

6. **ETL 预处理**

- **方法**：通过 ETL（Extract, Transform, Load）工具将分散的数据聚合到一个统一的存储（如数据仓库）中，然后在该存储中执行 JOIN。
- **优点**：适合离线分析场景。避免实时查询的性能问题。
- **缺点**：数据延迟较高，不适合实时查询。需要额外的 ETL 工具和存储资源。

7. **使用 NoSQL 或 NewSQL 数据库**

- **方法**：如果业务场景允许，可以考虑使用支持分布式 JOIN 的 NewSQL 数据库（如 TiDB）或 NoSQL 数据库。
- **优点**：原生支持分布式查询，性能较好。
- **缺点**：需要迁移数据，成本较高。可能不完全兼容 MySQL 的语法和特性。

总结

在分布式场景下，解决 MySQL 跨节点 JOIN 问题需要根据具体业务需求选择合适的方法：

- 如果数据量较小，可以考虑 **应用层 JOIN** 或 **全局表**。
- 如果数据量较大，可以通过 **分片键设计优化** 或 **数据冗余** 来避免跨节点查询。
- 对于复杂场景，可以使用 **分布式数据库中间件** 或 ETL 预处理。
- 如果业务允许，也可以考虑迁移到支持分布式 JOIN 的数据库（如 TiDB）。

## 40. 技术选型时，如何设计一张真正可用于决策的方案对比表？

> 原题 ID：`q1792`

**高频程度**：★★★

**考察点**：考察对「方案对比速查表」的掌握，重点看能否讲清：方案对比速查表不是简单罗列优缺点，而是先明确决策目标和约束，再选维度、量化打分、给出推荐

**回答框架**：

方案对比速查表不是简单罗列优缺点，而是先明确决策目标和约束，再选维度、量化打分、给出推荐；做法：1）定义场景与硬约束（如预算、SLA、团队规模）；2）选 5-8 个关键维度，避免维度爆炸；3）每个方案在每个维度上给出事实或估算值，而非形容词；4）加权求和或做帕累托分析，标出不可接受项；5）输出结论和适用边界

**参考回答**：

方案对比速查表是把多个候选方案按统一维度（成本、延迟、吞吐、一致性、复杂度、可维护性等）横向拉平对比的决策工具，核心是让取舍显性化。

方案对比速查表不是简单罗列优缺点，而是先明确决策目标和约束，再选维度、量化打分、给出推荐。做法：

- 1）定义场景与硬约束（如预算、SLA、团队规模）；
- 2）选 5-8 个关键维度，避免维度爆炸；
- 3）每个方案在每个维度上给出事实或估算值，而非形容词；
- 4）加权求和或做帕累托分析，标出不可接受项；
- 5）输出结论和适用边界。

通俗类比：选数据库像选交通工具。自行车便宜灵活但慢，高铁快但贵且不灵活，货车能拉货但慢。速查表就是一张表：价格、速度、载重、维护难度，按你的需求（送外卖还是搬家）选。 以缓存方案为例：本地缓存 vs Redis vs 多级缓存。维度：延迟（ns vs ms vs 混合）、一致性（弱 vs 强/可调 vs 复杂）、容量（受 JVM 限制 vs 可扩展 vs 大）、成本（低 vs 中 vs 高）、运维复杂度（低 vs 中 vs 高）。

- 结论：读多写少且容忍短暂不一致选本地；
- 需要共享和持久化选 Redis；
- 极致性能且能接受复杂度选多级。

再如 RAG 检索方案：关键词 BM25 vs 向量检索 vs 混合。

- BM25 精确匹配强、可解释、无需训练；
- 向量语义召回强但可能漏关键词；
- 混合用 RRF 融合，效果通常最好但延迟和复杂度上升。

速查表帮助快速定位。

## 41. 多个第三方系统使用不同回调路径时，如何设计统一接入层？

> 原题 ID：`q3539`

**高频程度**：★★★★

**考察点**：考察统一入口与路由分发设计能力：解耦、可扩展、可观测，以及验签、幂等与异步化处理。

**回答框架**：

1）统一入口：路径变量或请求头作为路由 key；
2）路由分发：策略模式加 Handler 注册，新增项目不改入口；
3）鉴权验签：抽象 SignVerifier，防重放（timestamp 加 nonce）；
4）报文解析：先读原始 body 再按项目解析，兼容 JSON、XML、form；
5）幂等与异步：唯一键去重，入口只做验签落库投递 MQ，快速返回 200。

**参考回答**：

背景：公司同时对接了支付、物流、IM、地图等多个第三方，每家回调路径、鉴权方式和报文格式都不同。如果每家写一个 Controller，路径会散落各处、鉴权逻辑重复，新增对接还要改路由配置，维护成本很高。目标是：对外只暴露一个或一类接口，内部按来源路由到对应处理器。方案设计我讲六点。

- 第一，统一入口。用 @RequestMapping("/callback/{project}/**") 或通配路径接收，把路径变量 project 作为路由 key，也可以用请求头 X-Project 或 query 参数。之所以用路径变量而不是多个接口，是因为路径是天然的路由维度，而且对第三方透明——他们只关心自己的 URL。
- 第二，路由分发。定义 CallbackHandler 接口，包含 supports 和 handle 两个方法，用策略模式加 Spring 的 Map 注入自动路由，或者自定义 Router 查表。新增项目只需要加一个 Handler 实现，不改入口代码，符合开闭原则。
- 第三，鉴权与验签。不同第三方的签名算法不同，有 MD5、RSA、HMAC，我抽象出 SignVerifier 按 project 选择实现；验签失败直接返回 401，并且要做防重放，用 timestamp 加 nonce 校验，同时比对来源 IP 白名单。
- 第四，报文解析。这里有个坑：不能直接用 @RequestBody 让框架提前反序列化，因为各家 Content-Type 不同，有 JSON、XML 和 form，而且验签需要原始报文。所以我会先把 body 读成字符串或字节，再按项目用对应的 DTO 解析。
- 第五，幂等与异步。回调可能重复推送，用第三方流水号做唯一键做去重，Redis 做前置拦截、数据库唯一索引做兜底。入口只做验签、落库和投递 MQ，业务异步处理，然后快速返回 200。之所以入口要薄，是因为第三方回调对响应时间很敏感，比如微信和支付宝都要求 5 秒内返回，重业务逻辑会拖垮接口并触发他们的重试风暴。
- 第六，可观测。统一日志记录 project、traceId、原始报文和处理结果，便于排查。复盘有两点：上线后新增对接从半天缩短到半小时；踩过的坑是不同第三方的 Content-Type 不同，统一入口必须兼容，不能写死。

**常见追问**：如果 Redis 挂了，你的幂等还能保证吗？

## 42. 文档预览服务何时应拆为微服务？它与微前端如何配合？

> 原题 ID：`q2787`

**高频程度**：★★

**考察点**：考察区分微服务与微前端两个不同维度的拆分并给出轻量方案。

**回答框架**：

①澄清：微服务是后端按业务能力拆分，微前端是前端按业务域拆分，问法本身概念错位。②判断：预览若纯前端渲染只需静态资源或 CDN，不需要微服务。③后端：若需服务端转换（docx 转 pdf、转码、缩略图）则可拆独立预览服务，无状态加队列削峰加结果缓存。④微前端选型：iframe、qiankun、Module Federation、Web Components 各有隔离与性能取舍。

**参考回答**：

先澄清概念：微服务是后端按业务能力拆分的独立部署单元（如用户服务、订单服务），微前端是前端按业务域拆分的独立开发部署单元（如 qiankun、Module Federation），两者是不同维度的拆分，所以问「预览是不是微服务」本身是概念错位。要分情况回答：如果预览是纯前端渲染（PDF.js、图片/视频标签、Office Online），那不需要微服务，只需要一个静态资源或 CDN；如果预览需要服务端转换（docx 转 pdf、视频转码、生成缩略图），那后端会拆出一个独立的「预览/转换服务」，这可以算微服务，但它只负责计算，不涉及前端模块划分。

这个服务要无状态、可水平扩展，转换任务用队列削峰，结果按文件 hash 缓存到对象存储避免重复转换。

- 如果确实要做微前端，方案取舍是：iframe 隔离最好但通信、路由、弹窗和性能差；
- qiankun 或 single-spa 提供 JS 沙箱和样式隔离，适合多团队；
- Module Federation 运行时共享依赖、构建耦合低，适合同技术栈；
- Web Components 标准隔离但生态弱。

选择原则是预览若只是只读展示优先用 iframe 或独立路由，避免引入微前端复杂度；若需要嵌入主应用、共享登录态和动态换肤，才用 qiankun 或 Module Federation。同时要注意安全，预览用户上传文件时存在 XSS、SSRF 和恶意文件解析漏洞。

**常见追问**：qiankun 的 JS 沙箱在什么情况下会降级？预览转换服务如何避免重复转换？
