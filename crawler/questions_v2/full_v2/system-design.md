## 1. 一个每秒 10w QPS 的高并发系统，要求实时输出“最近 1 小时”内访问频率最高的10个IP，你会如何设计？

> 原题 ID：`q0084`

**高频程度**：★★★★

**考察点**：考察高并发下的实时 TopN 统计与滑动窗口设计，以及精确与近似的取舍。

**回答框架**：

①本地分片计数：各节点用分段锁或时间分桶的 HashMap<IP,count> 统计。②滚动窗口：按分钟分桶/环形数组，淘汰 1 小时外数据。③全局合并：聚合层秒级拉取各节点局部 TopK 做堆合并，或 Redis ZSet/Count-Min Sketch。④取舍：精确成本高，近似 TopK 可接受误差时省内存。

**参考回答**：

单机扛不住全局精确统计，要分治。第一步在各接入节点本地做增量计数：用 HashMap 统计 IP 频次，为避免锁竞争可以用分段锁或每线程本地 Map 再合并，同时按分钟分桶（每分钟一个 Map）。第二步用滚动时间窗管理「最近 1 小时」：维护 60 个分钟桶的环形数组，每分钟新建一个桶并淘汰最旧的桶，这样窗口过期和内存回收都很自然。第三步在中心层做全局聚合：各节点周期性（秒级）上报本地的局部 TopK，聚合服务用小顶堆合并出全局 Top10，实时性要求更高就直接走 Flink 做窗口聚合，或写 Redis ZSet 用 ZINCRBY 加 ZREVRANGE。若可接受误差，用 Count-Min Sketch 加堆做近似 TopK，内存省几个数量级。注意热点 IP 的内存放大和 1 小时窗口的淘汰成本。

**常见追问**：如果要求精确 Top10 且不能有误差怎么办？分钟桶边界处的瞬时峰值会不会导致统计偏差？

## 3. 如何从总体上设计一个微信步数的系统？

**回答框架**：

①功能拆解：步数获取、好友排行、点赞。②量级分档：小数据 MySQL order by 足够；千万到亿级必须用 Redis ZSet。③Key 设计：按天加用户维度隔离，如 steps:ranking:{uid}:{date}。④数据特性：只关心当天或近几天，可设置过期不持久化。

**参考回答**：

微信步数系统的核心功能是展示自己的步数、好友排名和点赞数，步数本身可以调微信的运动 API 获取，真正的技术点在于排名实现。量级决定方案：用户量小直接用 MySQL，按步数字段 order by 查询即可；到了千万乃至亿级，MySQL 排序会变慢，单机内存也放不下全量排序，必须用 Redis 的有序集合 ZSet 做排行榜。Key 设计要考虑两个维度：一是时间，步数每天更新，所以 key 中要带以天为单位的时间戳；二是社交关系，每个人看到的是自己朋友圈的排行，所以 key 还要带当前用户标识，例如 steps:ranking:jack:20230506。ZSet 的 member 用微信号（用户标识），score 用对应步数，查询用 ZREVRANGE 取 TopN，查自己排名用 ZREVRANK。因为用户只关心当天或最近几天数据，不必持久化到 MySQL，给 key 设置几天过期即可，靠 Redis 主动淘汰控制内存。

**常见追问**：好友关系变化时排行榜怎么更新？步数上报非常频繁，怎么设计写入路径避免每次都更新 ZSet？

## 4. 什么是CAP理论？

> 原题 ID：`q0950`

**高频程度**：★★★★★

**考察点**：考察分布式理论基本功，重点是 P 不可舍弃、CA 在分布式下不存在这一常见误区。

**回答框架**：

①三个要素定义：一致性 C、可用性 A、分区容错性 P。②三选二的真实含义：网络分区客观存在，P 必须保，实际是在 C 与 A 之间取舍。③典型系统：CP 如 ZooKeeper/etcd，AP 如 Eureka/Cassandra。④延伸：BASE 理论、一致性与延迟的关系。

**参考回答**：

CAP 是分布式系统的核心理论，指三个要素：一致性（Consistency），所有节点在同一时间看到相同的数据；可用性（Availability），每个请求都能在有限时间内收到响应，无论成功或失败；分区容错性（Partition Tolerance），系统在网络分区（节点间消息丢失或延迟）时仍能继续运行。理论结论是三者最多同时满足两个。但要讲清楚：在真实分布式系统中网络分区是客观存在的，所以 P 必须保留，架构上真正做的是在网络分区发生时于 C 和 A 之间取舍——CP 系统如 ZooKeeper、etcd、HBase 选择牺牲可用性保证一致，分区时少数派节点拒绝服务；AP 系统如 Eureka、Cassandra、Dynamo 选择牺牲强一致保证可用，接受最终一致。跨机房单机场景的 CA 系统在分布式下并不存在。实际设计要按业务取舍：金融交易偏 CP，社交 Feed、商品详情偏 AP，并可用 BASE（基本可用、软状态、最终一致）作为 AP 的落地指导。

**常见追问**：P 在什么情况下可以放弃？最终一致性怎么保证「读己之写」？

## 5. 秒杀系统设计：你会怎么考虑？有哪些设计要点？

> 原题 ID：`q0983`

**高频程度**：★★★★★

**考察点**：考察分层削峰、库存防超卖、异步下单与限流降级的完整秒杀方案。

**回答框架**：

①分层架构：CDN 静态化、网关鉴权限流、独立秒杀服务、缓存与数据库分层。②限流：前端按钮置灰、Nginx/网关限流、用户级频率限制。③库存：Redis 预扣加 Lua 原子脚本，DB 唯一约束或乐观锁兜底。④异步与容错：MQ 削峰下单、幂等防重、排队提示、降级与监控。

**参考回答**：

秒杀的核心矛盾是瞬时超高并发加库存强一致，要点分四块。第一是分层削峰：静态资源全部走 CDN，页面静态化减少动态请求；网关做鉴权、限流、防刷；秒杀业务拆成独立服务与独立集群，避免影响主站。前端层面做按钮置灰防重复点击、答题或验证码拉长请求间隔、URL 动态化（服务端下发一次性随机数）防止脚本提前抢跑。第二是限流：Nginx 或网关用令牌桶/漏桶限流，单用户维度限制每秒请求次数，超量直接快速失败或进排队。第三是库存扣减，这是最关键环节：秒杀开始前把库存预热加载到 Redis，用户请求进来用 Lua 脚本原子地「判断库存大于 0、DECR 扣减、记录已抢用户 ID」三步，扣减成功才允许下单，避免超卖和一人多单；数据库层再用唯一索引或乐观锁（update ... where stock > 0）兜底，保证最终一致。第四是异步与容错：下单、支付、发货等耗时操作放 MQ 异步处理，实现削峰填谷；消费端用订单号或用户 ID 做幂等；库存不足时前端给出「秒杀已结束」的友好提示，用户请求可以进队列给出排队进度；系统要有降级方案（返回兜底页、关闭非核心功能）、Prometheus 加 Grafana 监控 QPS/延迟/错误率并设告警。

**常见追问**：Redis 扣减成功但 MQ 消息丢了导致少卖，怎么补偿？如何防止同一个用户在多个设备上重复秒杀？

## 6. 秒杀一千万个商品，20wQPS：怎么设计？只考虑库存扣减环节，请简要回答设计要点？

> 原题 ID：`q0984`

**高频程度**：★★★★

**考察点**：考察极高 QPS 下单点库存扣减的横向扩展与热点处理。

**回答框架**：

①Redis 集群分片：库存按商品维度打散到 redis 集群，用 DECR 原子扣减。②本地缓存：热点商品在应用层加本地缓存或请求合并，减轻缓存层压力。③分片与负载均衡：服务多实例横向扩展，避免单点过载。④数据库兜底：乐观锁或版本号防超卖，MQ 异步落库。

**参考回答**：

20w QPS 的库存扣减要拆成几个要点。一是用 Redis 集群存储库存，靠 DECR 这类原子操作实现高效一致扣减，难点在于一千万商品意味着热点分散、key 数量巨大，要按商品 ID 做分片打散到不同 Redis 节点，避免单节点成为瓶颈；对超级热点商品（如某个爆款），可以在应用层加本地缓存做请求预筛或合并，只在本地判断有货后才落到 Redis。二是服务侧无状态多实例部署，配合负载均衡按商品维度做一致性路由（同一商品的扣减打到同一分片），避免跨节点竞争。三是数据库层用乐观锁或版本号控制在异步落库时防超卖，Redis 扣减是主路径，DB 是最终账本，二者用 MQ 解耦。四是限流降级与排队：对超出即时处理能力的请求做限流或排队延迟处理，保证系统不被打穿。五是异步化：订单生成、支付确认后的库存同步等非实时操作用 MQ 异步做，降低扣减环节的直接压力。核心目标是既要扛住高并发，又要保证不超卖。

**常见追问**：一千万商品如果分片，热点商品的倾斜怎么处理？Redis 扣减与 DB 落库不一致时如何对账修复？

**考察点**：考察读多写少场景下的计数一致性、去重与缓存异步化设计。

**回答框架**：

①数据模型：帖子/评论的 like_count 冗余字段加点赞记录表，联合唯一索引防重复。②接口：点赞/取消点赞，返回最新点赞数。③性能：Redis Set 存点赞关系、字符串存计数，MQ 异步落库。④一致性与安全：分布式锁或唯一索引保原子、登录校验与频率限制。

**参考回答**：

点赞是典型的读多写少、计数热点场景。数据模型上，帖子表和评论表各冗余一个 like_count 字段用于快速展示，另有点赞记录表存 user_id 加目标 ID（帖子和评论二选一）加时间，并在 (user_id, post_id) 和 (user_id, comment_id) 上建联合唯一索引，天然防止重复点赞。接口提供点赞和取消点赞两个动作，行为是先查是否已点赞，未点赞则插入记录并 like_count 加一，已点赞则删除记录并减一，整个过程放在一个事务里或用唯一索引加捕获冲突保证原子。性能上用 Redis 扛读：用 string 缓存点赞数（post_like_count:{post_id}），用 Set 缓存点赞用户集合用于快速判断是否已点，点赞请求先写 Redis 再通过 MQ 异步落库，实现写入解耦和削峰。安全上前提是登录校验，加参数校验和用户级频率限制防刷赞。异常处理要覆盖重复点赞（友好提示已点过）、目标不存在、系统繁忙等分支。数据量大时对点赞记录表按目标 ID 分库分表，并支持按时间、用户维度做统计。

## 8. 短链系统设计：如何设计一个短链系统？

> 原题 ID：`q0986`

**高频程度**：★★★★★

**考察点**：考察发号器选型、62 进制转换、冲突处理与高并发读的重定向设计。

**回答框架**：

①发号：分布式 ID（雪花/号段）保证全局唯一，避免哈希冲突。②编码：十进制 ID 不断除以 62 取余映射到 [a-zA-Z0-9]，逆序拼接。③存储与读：写少读多，映射关系放 KV 高效点查，读路径加缓存。④可用性：预生成短链池、热点缓存、301/302 选型与过期清理。

**参考回答**：

短链系统是典型的写少读多场景，读 QPS 通常是写的百倍。生成算法有两条路线：一是哈希法，对长 URL 做 MD5/SHA256 后取前 N 位，实现简单但必然存在冲突，需要唯一性检查和重试；二是分布式 ID 加进制转换，用雪花算法或号段模式生成全局唯一 ID，再把十进制 ID 不断除以 62 取余，从字符集 [a-zA-Z0-9]（先打乱顺序防止被遍历推算）取对应字符，直到商为 0，最后逆序拼接得到短串，6 位就能表示 62^6 约 570 亿条，无冲突且可水平扩展，是主流方案。存储上用 KV 型存储（如 Redis 或分库分表的 MySQL）存短码到长链的映射，读路径先用缓存挡住绝大多数请求，未命中回源并回填。写入时可以用预生成短链池的方式提前把可用短码放到 Redis 队列里，取号即用，避免实时生成的开销和冲突检查。重定向用 301（永久，利于浏览器缓存但丢失统计）或 302（临时，可做点击统计，一般选 302）。另外要处理过期清理、恶意 URL 校验、防止被爬取遍历短码。

**常见追问**：自定义短链（用户指定后缀）怎么和发号器方案结合？如何防止有人遍历短码爬取全站长链接？

## 9. 扫码登录场景设计：扫码登录场景如何设计？

> 原题 ID：`q0987`

**高频程度**：★★★★

**考察点**：考察二维码状态机与轮询/长连接驱动下的跨端授权流程。

**回答框架**：

①本质：已登录的 App 扫描未登录 Web 端二维码，触发登录凭证写入实现自动登录。②流程：生成二维码 ID、Web 轮询状态、App 扫码上报、服务端置为已扫描并返回临时 token、用户确认后置为已确认并下发授权 token。③状态机：待扫描、已扫描、已确认、已过期。④取舍：轮询 vs 长连接，二维码有效期与安全性。

**参考回答**：

扫码登录的本质是：让已经登录过的 App 去扫描未登录 Web 端展示的二维码，通过服务端做中介，把登录凭证传递给 Web 端，从而实现 Web 端自动登录。流程是这样的：Web 端打开登录页，服务端生成一个带唯一编号的二维码展示出来，浏览器开始定时轮询这个编号对应的状态；用户用 App 扫码，App 把自身 token 和二维码编号发给服务端，服务端校验后把二维码状态置为「已扫描」，并生成一个临时 token 返回给 App，此时 Web 端轮询到状态变化，页面提示「已扫码，待确认」；App 端弹出确认授权按钮，用户点确认后携带临时 token 请求服务端，服务端把状态置为「已确认」并为 Web 端生成正式的授权 token，Web 端轮询拿到 token 后完成登录。核心设计是二维码 ID 作为连接 App 与 Web 的纽带，加一个清晰的状态机（待扫描、已扫描、已确认、已过期）。工程上看，轮询实现简单但请求量大，可用长轮询或 WebSocket 降低开销；二维码要设置有效期（如 2 分钟）防止被截图复用，临时 token 要一次性且短时效，确认动作必须由用户显式触发，避免扫码即登录带来的风险。

**常见追问**：二维码被截图转发给别人，怎么防止？如果用 WebSocket 推送代替轮询，断线重连如何保证状态一致？

## 10. 单点登录系统设计：设计一个单点登录系统？

## 12. 40亿个QQ号，如何判断一个QQ号是否存在？

> 原题 ID：`q0993`

**高频程度**：★★★★

**考察点**：考察位图对海量整数存在性判断的空间优化能力。

**回答框架**：

①状态建模：存在性只有二值，用 bitmap 而非哈希表。②空间计算：QQ 号最大约 10 位即百亿级，按最大值的 1/8 估算字节数。③实现：byteIndex = num/8，bitIndex = num%8，set 用按位或，查询用按位与。④延伸：布隆过滤器用于更大范围但有误判。

**参考回答**：

判断存在性是二值状态，存在或不存在，所以最优结构是位图（bitmap）而不是哈希表。40 亿个 QQ 号如果直接用哈希表存，每个 int 占 4 字节就是 16GB 以上，而位图只需要按 QQ 号最大值来算：假设最大 10 位数（约 100 亿），所需字节数是 100 亿/8 约 1.25GB，甚至还能更低。实现上把连续的二进制位组成 byte 数组，对某个 num，byteIndex = num/8 定位到哪个字节，bitIndex = num%8 定位到字节内的第几位；set 操作是 byte[byteIndex] |= (1 << bitIndex)，查询操作是 (byte[byteIndex] & (1 << bitIndex)) != 0。这样一次内存访问就能判断存在性，时间和空间都极优。如果 QQ 号空间更大或只需要概率性判断，可以用布隆过滤器，用多个哈希函数映射到位数组，空间更省但存在误判（只会误判存在、不会误判不存在）。实际工程里还可以按号段分文件或分片存储位图，方便分布式处理。

## 13. 40亿个QQ号，如何快速找出所有不重复的QQ号？

> 原题 ID：`q0994`

**高频程度**：★★★★

**考察点**：考察用多位状态位图统计出现次数从而筛选只出现一次的整数。

**回答框架**：

①状态建模：需要三态（0 次、1 次、多次），用每数 2 位的位图。②编码：00 未出现、01 出现一次、11 出现多次，扫描后取状态为 01 的即不重复。③实现：byteIndex = num/4，两位 bitIndex 计算，按状态转移置位。④取舍：空间是普通位图的两倍，仍远小于哈希表。

**参考回答**：

这是一次扫描统计频次再筛选的问题，关键是用两位表示一个数的三态位图。因为需要区分「出现 0 次（00）、出现 1 次（01）、出现多次（11）」三种状态，所以每个数占 2 个 bit，位数组长度约为 (max_value+1)×2/8 字节，相比哈希表仍然省几个数量级。定位上 byteIndex = num/4（每个字节装 4 个数），bitIndex1 = (num%4)×2+1 表示高位，bitIndex2 = (num%4)×2 表示低位。状态转移逻辑是：如果两位都是 0（没出现过），把低位 bitIndex2 置 1，变成 01；如果低位是 1 高位是 0（出现过一次），把高位 bitIndex1 置 1，变成 11；如果高位已经是 1，说明已出现多次，直接跳过。整个数据扫描一遍后，再遍历位图，所有状态为 01 的数就是只出现过一次的 QQ 号。这个过程是 O(n) 时间和 O(max_value) 位空间，可以分片并行：按号段把数据切分到多个节点，各自建位图，最后合并结果。

**常见追问**：如果内存连两位位图都放不下，怎么分治？多次出现和一次出现的判断顺序写错会有什么后果？

## 14. 给定1000万个整数，内存限制1MB，如何对他们进行排序？

> 原题 ID：`q0995`

**高频程度**：★★★★

**考察点**：考察外部排序中分块排序加多路归并的经典方案。

**回答框架**：

①分块：按内存容量把数据切块，块内排序后写回磁盘。②多路归并：各块第一个元素建小顶堆，弹出堆顶写结果并用该块下一元素替换。③指针推进：某块读完则从其余块继续，直到全部合并完。④优化：块内用快排/归并，减少磁盘 IO，可并行。

**参考回答**：

内存放不下就用外部排序，分两步走。第一步分块排序：按 1MB 内存能容纳的数据量，把 1000 万个整数切成若干小块（比如每个块放 10 万个 int），每块读进内存用快速排序排好序，再写回磁盘文件。第二步多路归并：把所有有序小文件的第一个元素取出来建立一个小顶堆，堆顶就是当前全局最小；把堆顶元素输出到结果集，然后用它所在文件的下一个元素替换堆顶位置，并向下调整重建小顶堆；如果某个文件已经读完，就从剩下的文件里继续同样的操作；重复这个过程直到所有文件读完，最后堆里剩下的元素依次弹出就是有序结果。用堆做 k 路归并的复杂度是 O(N log k)，k 是文件数。优化上可以增大归并路数减少磁盘访问轮次、用带缓冲的顺序读写减少 IO 次数、对分块排序阶段做多线程并行，还可以用位图或计数排序在整数范围有限时进一步降复杂度。

**常见追问**：k 路归并时 k 取多大合适，为什么不是越大越好？如果整数范围很小（比如都在 0 到 1000 万），有没有更快的方案？

## 15. 给定1GB单词，内存限制1MB，如何找到出现频率最高的100个单词？

> 原题 ID：`q0996`

**高频程度**：★★★★

**考察点**：考察哈希分治、局部 TopK 与小顶堆合并的经典海量数据处理范式。

**回答框架**：

①分治：按 hash(word)%N 把 1GB 文件拆成 N 个小文件，保证相同单词落同一文件。②局部统计：逐个小文件读入内存用 HashMap 统计词频。③局部 TopK：每个文件用小顶堆维护 Top100。④全局归并：合并所有小文件的 Top100，再用小顶堆求全局 Top100。

**参考回答**：

标准解法是哈希分治加小顶堆。第一步，把 1GB 文件按 hash(word) % N 拆成 N 个小文件（N 取几百到几千，使每个文件能装进 1MB 内存），用同一个哈希函数保证相同单词一定落到同一个小文件，这样每个小文件内可以独立统计。第二步，逐个把小文件读进内存，用 HashMap 统计每个单词的出现次数。第三步，对每个小文件用一个容量为 100 的小顶堆维护它的局部 Top100：遍历词频表，堆未满直接入堆，堆满且当前词频大于堆顶就替换堆顶并调整，最终堆里就是该文件的 Top100。第四步，把所有小文件的局部 Top100 汇总（总共 N×100 个候选），同样用小顶堆求一次全局 Top100。整体复杂度近似线性，空间受控在 1MB 级别。注意点：哈希函数要稳定且分布均匀避免某个文件过大；如果某单词是超高频热词导致单文件仍然超内存，可以对热点做二次拆分或用 Count-Min Sketch 做近似统计。

**常见追问**：如果某个单词出现频率极高导致单文件仍然超内存怎么办？为什么必须保证相同单词落在同一小文件？

①分片：对两个文件用同一 hash(url)%N 规则拆成 N 个小文件，保证相同 URL 落同组。②比对：对每一组（A 的小文件 i 与 B 的小文件 i）逐个求交。③小文件求交：把较小的加载进哈希表，遍历另一个查找；或各自排序后双指针。④加速：多线程/分布式并行、布隆过滤器预筛、先文件内去重。

**回答框架**：

①写入路径：所有写先到 Primary。②oplog：Primary 把写操作记录到 oplog 这个特殊集合。③同步：Secondary 长连接拉取 oplog 并回放，实现异步复制。④延迟与选举：复制存在延迟，Primary 故障时按优先级和最新数据触发选举。

**参考回答**：

MongoDB 的数据复制通过复制集实现，底层机制是 oplog（操作日志）。工作流程是这样的：第一，所有写操作都首先在主节点 Primary 执行；第二，主节点把每一次写操作（包括插入、更新、删除）以幂等的形式记录到一个特殊集合 oplog 中，oplog 是一个固定大小的 capped collection，按时间顺序追加；第三，从节点 Secondary 与主节点保持长连接，持续拉取主节点上的新 oplog 条目并在本地按顺序回放，从而让自身数据与主节点保持一致，这个过程是异步的，所以从节点数据会略有滞后，这就是复制延迟（replication lag），可以通过 writeConcern 和 readConcern 来控制一致性强度；第四，如果主节点发生故障，复制集成员通过心跳检测发现后会自动触发选举，按节点优先级、数据新旧程度等条件选出新的主节点。通过这套机制，复制集提供了数据冗余、故障自动恢复和高可用能力。需要注意 oplog 大小要合理设置，太小会导致从节点来不及同步、需要全量重新同步。

**常见追问**：oplog 太小会有什么后果？复制延迟很大时读从节点会出现什么问题，怎么监控？

## 22. 如果从0开始做一个项目，如何设计架构（按业务怎么分）？

> 原题 ID：`q3545`

**高频程度**：★★★★★

**考察点**：考察从零做架构时按业务能力划分领域、确定数据流与演进路径的能力。

**回答框架**：

①明确业务目标与非功能需求，架构是取舍。②按业务能力而非技术分层划分领域（DDD 限界上下文）。③确定数据流与依赖方向：同步走 API/RPC，跨域状态变更走领域事件。④领域内分层、存储选型（每个领域独享数据库）、扩展性与横切关注点。⑤取舍：核心交易强一致、非核心最终一致，优先模块化单体按需拆分。

**参考回答**：

从零设计架构的核心是：先按业务能力而非技术划分领域边界，再确定数据流与依赖方向，最后为扩展性预留接口和异步事件机制，避免过度设计。步骤是：第一，明确业务目标与非功能需求，先问清核心用户是谁、核心用例是什么、QPS 与数据量、一致性与延迟要求、团队规模和交付节奏，架构是取舍，没有需求就没有架构。第二，按业务能力划分领域，用 DDD 限界上下文，不要按 controller/service/dao 这种技术分层做一级划分，而是按业务能力切，例如电商分为用户、商品、库存、订单、支付、营销、履约，每个领域高内聚低耦合、拥有自己的数据和对外接口。第三，确定数据流与依赖方向，同步调用走 API 或 RPC，跨领域的状态变更走领域事件（如 OrderCreated、PaymentSucceeded）通过 MQ 解耦，依赖方向单向、避免循环依赖。第四，领域内部再分层，接口层、应用层、领域层、基础设施层，让业务逻辑不依赖具体技术，领域层定义 Repository 接口由基础设施实现。第五，存储选型按访问模式来，交易数据用关系型，热点读用 Redis，搜索用 ES，日志事件用 Kafka，报表用 OLAP，每个领域独享数据库避免共享表导致耦合。第六，扩展性上初期用模块化单体按领域分包、接口清晰，当某领域压力大或团队拆分时再抽成独立服务，预留插件、事件订阅、配置化等扩展点。第七，横切关注点如日志、链路追踪、监控告警、配置中心、鉴权、幂等、限流熔断统一作为基础设施不侵入业务。取舍原则是核心交易强一致、非核心最终一致，强依赖同步、通知统计异步，团队小业务未稳时优先单体，非核心不重复造轮子。

**常见追问**：库存扣减到底是订单流程的一部分还是独立领域，怎么判断？Outbox 模式解决了什么问题？

## 23. 大文件上传如何优化（断点续传）？

> 原题 ID：`q4123`

**高频程度**：★★★★★

**考察点**：考察分片上传、哈希校验、秒传与断点续传的完整方案设计。

**回答框架**：

①分片：前端按固定大小（如 5MB）切片，避免单次失败重传全部。②校验：每片计算 hash，服务端记录已传分片，支持秒传与断点续传。③合并：全部片到齐后用 append 合并，校验整体 hash 保证完整性。④优化：并发上传加进度反馈，失败只重传失败分片，分片元数据用 Redis 或数据库记录。

**参考回答**：

核心是分片上传、hash 校验、秒传、合并、断点续传五步。第一，前端分片：把大文件按固定大小（如 5MB）切成多个分片，避免单次请求失败就重传整个文件。第二，计算哈希：对每个分片计算 hash（如 md5），再对整个文件计算一次整体 hash 作为文件唯一标识。第三，校验与秒传：上传前先用文件整体 hash 询问服务端是否已存在，存在则直接秒传返回，不需要真正上传；上传分片时服务端按分片 hash 校验该分片是否已传过，已传则跳过。第四，断点续传：服务端记录每个文件已上传的分片列表（可用 Redis 或数据库存 uploadId 与已传分片序号），用户重新进入上传时先拉取已传分片，只传缺失的部分。第五，合并与校验：所有分片到齐后按顺序用 append 合并成完整文件，再校验整体 hash 与声明一致，防止传输损坏。优化上可以并发上传多个分片提升速度、进度条基于已传分片数计算、失败只重传失败的分片、分片大小要在并发度与请求开销之间权衡（太小请求多、太大重传代价高），另外要考虑分片元数据的过期清理和并发上传同一文件的去重。

**常见追问**：分片大小怎么选？如果上传到一半用户换了网络或刷新页面，怎么保证续传能对上？

## 24. 如何设计一个排行榜？

> 原题 ID：`q4120`

**高频程度**：★★★★★

**考察点**：排行榜设计：ZSet 实时排序、ZINCRBY 更新分数、ZREVRANGE 取 TopN、持久化与分片扩展。

**回答框架**：

1）核心结构：Redis ZSet，member 是用户/对象，score 是分数；2）更新：ZINCRBY 原子加分，或 ZADD 直接设置；3）查询：ZREVRANGE 取 TopN，ZREVRANK 查排名，ZSCORE 查分数；4）持久化：定时落库或通过消息队列异步写 DB，保证可恢复；5）扩展：数据量极大时按维度分片（比如按榜单 ID 或时间段），或分片 ZSet 加归并；6）注意大 key 与热 key 问题；7）时间维度榜单可用 key 加日期后缀。

**参考回答**：

排行榜最适合用 Redis 的 ZSet 实现，因为它天然按 score 排序且支持排名查询。具体设计：第一，数据结构，ZSet 的 member 存用户 ID 或对象 ID，score 存分数（比如积分、票数、热度值）。第二，更新，用户分数变化用 ZINCRBY 原子加分，或者用 ZADD 直接设置新分数，这两个操作都是 O(logN) 且原子，无需加锁。第三，查询，取前 N 名用 ZREVRANGE key 0 N-1 带 WITHSCORES，查某用户排名用 ZREVRANK，查分数用 ZSCORE，取某个分数区间用 ZRANGEBYSCORE；这些操作分别是 O(logN + M) 和 O(logN)，性能很好。第四，持久化，Redis 是内存存储，榜单数据需要落库，可以定时全量落库，或者用消息队列把分数变更异步写回 MySQL/数仓，重启或故障时从库里重建 ZSet；注意如果分数是实时算出来的，也可以选择不落库，靠源数据重算。第五，扩展与治理。数据量极大时（比如千万级用户的全站排行），单个 ZSet 会变成大 key 且占用大量内存，可以考虑：按维度拆分（比如按地区、按榜单 ID 分成多个 ZSet），或者按用户 ID 分片成多个 ZSet，取 TopN 时对每个分片取前 N 再归并；时间维度的榜单（日榜、周榜）用 key 加日期后缀，并对旧 key 设置过期或归档。第六，要关注热 key 问题：如果是全站超热榜单，可以加本地缓存、多副本打散。总结起来就是"ZSet 做实时排序、异步落库保证可恢复、分片解决大 key、本地缓存解决热 key"。

**常见追问**：1）分数相同时排名怎么处理？2）分片 ZSet 怎么归并出全局 TopN？

## 25. 如何设计一个『附近的人』功能？

> 原题 ID：`q4121`

**高频程度**：★★★★

**考察点**：附近的人功能设计：地理索引（GeoHash/Redis GEO）、半径查询与距离排序、精度与性能优化、城市维度预筛。

**回答框架**：

1）核心：把用户经纬度存入地理索引（Redis GEO 基于 ZSet + GeoHash，或 MySQL 空间函数）；2）写入：GEOADD 添加位置；3）查询：GEOSEARCH/GEORADIUS 按半径搜索并返回距离、排序；4）原理：GeoHash 把二维经纬度编码成一维字符串，前缀相同的点地理上邻近，可转成 ZSet 的 score 做范围查询；5）优化：按城市或网格预筛减少候选、控制返回数量、位置更新用异步；6）权衡：精度 vs 性能、隐私与权限。

**参考回答**：

附近的人核心是要支持"给定一个坐标和半径，找出范围内的点并按距离排序"。实现上主要有两种选择。第一种是用 Redis 的 GEO 能力，这是最常用的：GEOADD 把用户的经纬度加进去，GEOSEARCH（新命令，替代 GEORADIUS）可以按半径或矩形范围查询，并支持返回距离、按距离排序、限制返回数量。它的底层原理是 GeoHash——把二维的经纬度编码成一维字符串，地理上邻近的点前缀相同，Redis 再把它转成 ZSet 的 score，就能用 ZSet 的范围查询（ZRANGEBYSCORE）快速筛出候选，然后再精确计算距离排序。第二种是数据库方案，MySQL 有 ST_Distance_Sphere 等空间函数，PostGIS 这类专业地理库能力更强，适合需要复杂空间查询和事务的场景，但性能不如 Redis。工程上要注意几点：第一，精度和性能的权衡，GeoHash 编码位数越长精度越高、但匹配越严格，Redis 用的是 52 位精度，误差在米级以内，一般够用；第二，数据量大时要减少候选集，常见做法是先按城市维度或网格预筛，只在同一城市/网格内做半径查询，避免全国范围全量扫描；第三，用户位置更新频繁（比如骑手、司机），写入量很大，可以考虑异步更新、降低更新频率、或者用专门的时空数据库；第四，返回结果要限制数量并做分页，避免一次返回过多；第五，隐私与权限要考虑，比如只对已授权用户展示位置、做位置模糊化。整体思路是"地理索引做快速筛选 + 精确距离计算做排序 + 城市/网格预筛控规模"。

**常见追问**：1）Redis GEO 和 PostGIS 该怎么选？2）位置更新特别频繁怎么优化？

5）复盘：量化收益与初期数据不一致的教训。

**参考回答**：

我用电商订单系统为例讲为什么这么设计。背景：订单创建涉及库存、支付、优惠券等多个服务，最初是单体架构，导致代码耦合严重、部署慢、扩展困难。难点有三个：一是分布式事务一致性；二是服务间通信的可靠性；三是数据一致性保障。决策上我做了四件事。第一，用 DDD 划分限界上下文，把订单、库存、支付、用户拆成独立微服务，让每个服务有自己的领域模型和数据边界，而不是按技术分层切。第二，用 Saga 模式替代两阶段提交来保证最终一致性。这里我选择事件驱动的协同式 Saga，因为 2PC 在跨服务场景下会长时间持锁、可用性差，而 Saga 通过补偿事务换取可用性。第三，引入 Kafka 做异步通信和事件溯源，保证消息可靠投递，配合本地消息表加定时补偿解决消息丢失。第四，用分布式锁和幂等设计处理并发，比如下单用唯一业务 ID 加 Redis 防重表，库存扣减用 Redis Lua 保证原子预占。复盘：上线后系统吞吐量提升了 3 倍，但初期因为补偿逻辑不完善出现过数据不一致，后来引入了定时对账和人工干预流程才稳定下来。从这个项目我得到的认知是：技术选型不是选最先进的，而是选在当前团队规模、运维能力和一致性要求下最合适的。比如 Saga 并不能完全替代 ACID，业务补偿的复杂度必须提前评估；再比如盲目拆微服务会显著增加运维成本，小团队可能反而更慢。

**常见追问**：Saga 的编排式和协同式你选哪种？为什么？

## 29. 常用组件哪些是AP，哪些是CP？

> 原题 ID：`q0952`

**高频程度**：★★★

**考察点**：考察 CAP 理论的实际落地：能否把组件归类到 CP/AP 并说明取舍依据，而不是背定义。

**回答框架**：

1) 先讲 CAP 与 P 必选；2) 按「分区时优先一致性还是可用性」给组件归类；3) 补充 ZK/etcd/Redis/MQ 的可配置情况。

**参考回答**：

CAP 说的是分布式系统里一致性 C、可用性 A、分区容错 P 三者最多同时满足两个。因为 P 在真实网络里是必选项，所以实际是在分区发生时选 C 还是选 A。典型 CP 组件：ZooKeeper、etcd、Consul（默认 CP）、HBase、MongoDB（强一致配置）、以及基于 Raft/Paxos 的配置中心；它们靠 Leader 选举和多数派写入，分区时少数派节点会拒绝服务以保证不返回旧数据。典型 AP 组件：Redis 集群（主从异步复制）、Eureka、Cassandra、DynamoDB、Kafka（可配 acks 与 ISR，默认偏可用）、Nacos（默认 AP，可切 CP）。要注意很多组件是可配置的，比如 Nacos 和 Consul 支持 CP/AP 模式切换，Kafka 用 acks=all 加 min.insync.replicas 也能变强一致，所以回答时最好说清默认偏向加可调配置，而不是一刀切。

**常见追问**：那注册中心你选 AP 还是 CP？为什么 Eureka 选 AP 更适合微服务场景？

## 30. 模块之间如何交互？

> 原题 ID：`q1481`

**高频程度**：★★★★

**考察点**：考察对「模块之间如何交互」的掌握，重点看能否讲清：模块交互指系统中不同功能单元（模块）之间如何通信与协作

**回答框架**：

同步调用（函数调用/RPC/HTTP）：调用方阻塞等待结果，简单直观，适合强一致、实时性要求高的场景；缺点是耦合调用方与被调方可用性，容易级联故障。；异步消息（MQ）：通过队列/主题解耦，生产者只负责发，消费者按能力消费，适合削峰、解耦、最终一致；代价是复杂度上升（重复消费、顺序、事务消息）。；事件驱动：模块发布领域事件，其他模块订阅，实现‘谁关心谁处理’，进一步降低耦合；但事件链难追踪，需可观测性。；共享数据/共享内存：性能高但耦合最强，容易产生隐式依赖，一般只用于同进程内高性能场景。；依赖倒置：高层模块依赖抽象接口，不依赖具体实现。；接口隔离：接口尽量小、职责单一，避免‘胖接口’导致无关模块被迫一起变。

**参考回答**：

模块交互的核心是定义清晰、稳定、低耦合的接口契约，通过同步调用、异步消息或事件驱动等方式传递数据与控制，让模块可独立开发、测试与演进。

模块交互指系统中不同功能单元（模块）之间如何通信与协作。关键不是‘怎么调’，而是‘约定什么’。 1) 交互的本质：接口契约。契约包含：输入/输出数据结构、调用语义（同步/异步、幂等性）、错误码、超时与重试策略、版本兼容规则。就像两个人合作，先约定‘我说什么、你回什么、出错怎么办’，而不是直接闯进对方房间翻东西。 2) 常见交互方式： - 同步调用（函数调用/RPC/HTTP）：调用方阻塞等待结果，简单直观，适合强一致、实时性要求高的场景；缺点是耦合调用方与被调方可用性，容易级联故障。 - 异步消息（MQ）：通过队列/主题解耦，生产者只负责发，消费者按能力消费，适合削峰、解耦、最终一致；代价是复杂度上升（重复消费、顺序、事务消息）。 - 事件驱动：模块发布领域事件，其他模块订阅，实现‘谁关心谁处理’，进一步降低耦合；但事件链难追踪，需可观测性。 - 共享数据/共享内存：性能高但耦合最强，容易产生隐式依赖，一般只用于同进程内高性能场景。 3) 设计原则： - 依赖倒置：高层模块依赖抽象接口，不依赖具体实现。 - 接口隔离：接口尽量小、职责单一，避免‘胖接口’导致无关模块被迫一起变。 - 迪米特法则：只与直接朋友通信，减少跨层调用。 - 契约版本化：接口变更要向后兼容，如加字段而非改字段，用版本号或兼容层过渡。 4) 通俗类比：模块像公司部门。同步调用像打电话，必须对方接听才能继续；异步消息像发邮件/工单，发完就走，对方有空处理；事件驱动像公司广播，谁关心谁响应。接口契约就是公司规定的公文格式和流程，格式稳定，部门才能各自独立运转。 5) 适用场景：强一致、低延迟选同步；高并发、可容忍最终一致选异步；跨团队、跨系统解耦选事件驱动；同进程高性能选共享内存但需谨慎。

**常见追问**：如何避免「1) 只答‘通过接口调用’，不区分同步/异步/事件，缺乏场景判断」？ 「2) 认为异步一定比同步好，忽略复杂度、一致性和运维成本」在真实项目中应如何规避？

## 31. 控制器，调度器，kubelet中的监听，是监听etcd吗？

> 原题 ID：`q0922`

**高频程度**：★★

**考察点**：考察 K8s 组件是否直接监听 etcd，以及 apiserver 作为唯一入口的架构原因。

**回答框架**：

1.结论：控制器、调度器、kubelet 都不直接监听 etcd；2.机制：统一通过 apiserver 的 Watch API 监听资源变化；3.原因一：安全，apiserver 提供认证、鉴权、审计；4.原因二：抽象，屏蔽底层存储，etcd 可替换；5.原因三：一致性，apiserver 负责缓存、冲突检测与准入控制。

**参考回答**：

结论是都不直接监听 etcd。在 K8s 架构里，etcd 是唯一的状态存储，但所有组件都不直接访问它，而是通过 API Server 的 Watch 接口来订阅资源变更，形成一个 apiserver 处于中心位置的星型结构。具体到各组件：Controller Manager 里的各种控制器监听 Deployment、ReplicaSet、Pod 等资源的事件，一旦有变更就对比期望状态和实际状态做调和；kube-scheduler 监听还没有被绑定节点的 Pod 以及 Node 的变化，选出合适节点后通过 apiserver 更新 Pod 的绑定信息；kubelet 则监听分配给自己的那些 Pod 及其关联的 ConfigMap、Secret、Volume 的变化，做本地的容器编排。这样设计的原因有三点。第一是安全：apiserver 提供统一的认证、鉴权、审计能力，如果每个组件都能直连 etcd，就必须各自维护一套权限体系，而且 etcd 凭据会暴露到各处，风险很大。第二是抽象：组件不需要关心底层的存储实现，以后换掉 etcd 也不影响它们。第三是一致性：apiserver 负责资源版本管理、乐观并发控制、准入控制（Admission）、以及 watch 缓存的维护，避免多个组件各自和 etcd 打交道导致状态混乱。所以 apiserver 本质上是 etcd 的唯一客户端兼所有组件的接入网关，组件之间的通信也大多是经由它读写资源对象来完成的，而不是直接互相调用。

**常见追问**：如果 apiserver 挂了，现有 Pod 会怎样？为什么说 K8s 是声明式加控制器调和的架构？

## 32. 中文检索系统为何常用 Elasticsearch？分词与倒排索引如何发挥作用？

> 原题 ID：`q3339`

**高频程度**：★★★★

**考察点**：ES 倒排索引原理、中文分词 analyzer 与 IK、BM25 相关性打分、分片水平扩展。

**回答框架**：

1）倒排索引：词→文档列表，按词定位 posting list 求交并，远快于 LIKE '%%'；2）中文分词：analyzer = char_filter + tokenizer + token_filter，IK 的 smart/max_word 与写入粗写策略；3）相关性：BM25 含词频饱和与长度归一化，支持 boost/function_score；4）分片并行：协调节点分发并行查询再归并；5）定位：搜索分析用 ES，事务用 MySQL，不拿 ES 当数据库。

**参考回答**：

ES 的核心价值是倒排索引带来的近实时全文检索能力，配合中文分词器解决切词问题，并通过分片实现水平扩展。第一，倒排索引：正排是"文档→词"，倒排是"词→文档列表"，包含词频和位置。查询时直接按词定位 posting list 再做交并，复杂度与命中词相关而非全表扫描，所以比 LIKE '%%' 快几个数量级，类比书末的索引页，按关键词直接翻页码而不是逐页翻书。第二，中文分词：英文按空格天然分词，中文没有空格必须用分词器，ES 通过 analyzer = char_filter + tokenizer + token_filter 组成分析链，中文常用 IK（ik_smart 粗粒度、ik_max_word 细粒度），工程上一般写入用细粒度建索引、查询用粗粒度提召回，也可以用 jieba、HanLP 或内置 CJK bigram，分词质量直接决定召回率。第三，相关性排序：基于 Lucene 的 BM25，是 TF-IDF 的改进，含词频饱和与文档长度归一化，支持 boost、function_score、多字段 best_fields/most_fields 等策略。第四，分片：天生分布式，协调节点把查询分发到各分片并行执行再归并，支持水平扩展和副本容灾。最后要强调定位：ES 适合海量文本的模糊和相关性搜索，不适合当强事务数据库，正确架构是 MySQL 存权威数据、ES 做检索索引、用 MQ 或 binlog 同步。

**常见追问**：1）ES 和 MySQL 数据怎么保持同步？2）ik_max_word 写入、ik_smart 查询为什么这样配？

## 33. 怎么在多台服务器同步session数据（数据库或者分布式系统）？

> 原题 ID：`q3347`

**高频程度**：★★★★

**考察点**：多机 Session 同步方案（粘性会话、集中式存储、Session 复制、JWT）、一致性与可用性权衡。

**回答框架**：

1）问题本质：Session 从进程内状态变成共享状态或让服务无状态；2）粘性会话：零改造但宕机丢会话、扩缩容重分布；3）集中式存储：Client→LB→无状态 App→Redis/DB，最常用；4）Session 复制：广播同步，节点多时网络开销大；5）JWT：签名自包含无状态，但无法主动失效、体积大。

**参考回答**：

单机 Session 存在本机内存，多台服务器时用户请求被负载均衡打到不同机器就出现登录态丢失，解决思路是把 Session 从"进程内状态"变成"进程外共享状态"，或者让服务本身无状态。常见四种方案。第一，粘性会话：LB 按 cookie 或 IP 哈希把同一用户固定到同一台机器，优点是零改造、无网络开销，缺点是机器宕机即丢会话、扩缩容导致重新分布，不满足高可用。第二，集中式 Session 存储，这是最常用的：架构是 Client→LB→无状态 App Server→Redis/DB，Redis 内存 KV 读写微秒级、支持 TTL 自动过期、可做主从/哨兵/Cluster 高可用；数据库持久化强但每请求读写 DB，QPS 高时成瓶颈，一般只做兜底或低频场景。第三，Session 复制：Tomcat 等容器支持在集群间广播同步 Session 副本，节点少时简单，但节点一多网络开销和内存冗余是 O(N²)，不推荐大集群。第四，JWT/客户端令牌：把状态签名后放在客户端，服务端完全无状态、天然适合多机和横向扩展，缺点是签发后无法主动失效，需要短过期加 refresh token 或黑名单来弥补，且 token 体积大、每次请求都携带。工程上一般选 Redis 集中式存储打底，配合合理的 Session TTL 与降级策略，对高并发无状态服务可以用 JWT。

**常见追问**：1）Redis 存 Session 挂了怎么办？2）JWT 怎么做主动登出？
