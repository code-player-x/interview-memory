## 1. 如何在简历中体现 AI 项目已具备生产级能力，而非仅是 Demo？

> 原题 ID：`q0038`

**高频程度**：★★★★★

**考察点**：考察候选人是否理解 Demo 与生产级 AI 系统的工程差距，核心在编排可控性、检索质量、异步流式链路与可观测性四个维度。

**回答框架**：

1）编排：用显式 Graph/状态机代替 if-else，配 MaxIterations 与重复调用检测防死循环；
2）检索：混合检索（BM25+向量）+ Metadata 过滤 + Rerank，而非纯 Milvus topK；
3）性能：异步 + Redis 队列 + TaskID + SSE 流式，解耦长尾耗时；
4）可观测：全链路 Trace 记录每步 Thought/Action/Observation、token 与耗时；
5）稳定性：超时、指数退避重试、熔断、降级、幂等键。

**参考回答**：

面试官问『生产级』，本质是想分清你是真上过线还是只跑过 demo。我会用四组细节回答。第一，编排不是 if-else，而是显式图编排：我用 Eino/LangGraph 把每个节点做成单一职责（意图识别、检索、工具调用、生成、校验），并设置 MaxIterations 上限和重复调用检测，对 tool_name+参数做 hash 去重，避免模型陷入死循环烧钱。第二，检索不是单纯向量 topK：纯向量对专有名词、型号编号召回差，我上的是 BM25 稀疏 + 向量稠密的混合检索，用 RRF 融合，再加 Metadata 过滤和 bge-reranker 精排，召回率从 62% 提到 89%。第三，慢响应用异步解耦：请求进来先落 TaskID 入 Redis 队列，立刻返回，服务端用 SSE 流式推结果，P95 从 6.2s 降到 2.4s，长尾不阻塞主链路。第四，全链路可观测：用 Prometheus + Zap 记录每一步的 Thought/Action/Observation、token 消耗、工具入参出参，Langfuse 做 trace，出问题能区分是检索问题还是生成问题。第五，生产化兜底：工具调用有超时、指数退避重试、熔断降级，写操作有幂等键，配置走灰度发布。这五点加起来，才是 Demo 和线上系统的分水岭。

**常见追问**：你的 Trace 具体记录了哪些字段？MaxIterations 设成多少、依据是什么？

## 32. 你在项目里怎么给接口响应建模？

> 原题 ID：`q1870`

**高频程度**：★★★

**考察点**：考察接口设计的工程规范性：统一信封结构、DTO 分层、错误码体系与序列化兼容策略。

**回答框架**：

1）协议信封层：统一 code/message/data/requestId/timestamp；
2）业务数据层：用 DTO 而非 Map/Entity，分页统一结构；
3）错误建模：ErrorCode 枚举绑定 HTTP 状态码、默认文案、是否可重试；
4）序列化兼容：null 策略、时间格式、Long 转 String 防精度丢失、版本管理；
5）落地方式：ResponseBodyAdvice 统一包装 + 全局异常处理。

**参考回答**：

我一般把接口响应建模分成四层。第一层是协议信封层，所有 HTTP 接口统一返回 code、message、data、requestId、timestamp。这里的 code 是业务错误码而不是 HTTP 状态码，message 面向调用方，data 是泛型负载，requestId 用于链路追踪。这样前端只需要写一次拦截器，网关和日志也能统一解析。第二层是业务数据层，data 里放明确的 DTO，而不是 Map 或者数据库 Entity，DTO 只暴露契约需要的字段，避免数据库字段泄漏和循环引用。分页统一成 list、total、page、pageSize 的结构，列表接口不返回裸数组，方便后续加分页元信息而不破坏兼容。第三层是错误建模，我定义 ErrorCode 枚举，比如 USER_NOT_FOUND 对应 10001，每个错误码绑定 HTTP 状态码、默认文案、是否可重试、是否告警。业务异常抛 BizException，全局异常处理器统一转成信封，参数校验异常、鉴权异常、限流异常、系统异常分别映射到不同的 code 段，避免前端靠 message 字符串来判断错误类型。第四层是序列化和兼容，用 Jackson 统一 null 策略和时间格式，Long 类型对外转成 String 防止 JS 精度丢失，对外接口加版本字段，新增字段默认兼容、删除或改语义走新版本。落地方式上，我用 Spring 的 ResponseBodyAdvice 自动包装成功响应，用 @RestControllerAdvice 处理异常，Controller 只返回 DTO，不手动拼信封，这样协议变更集中在一处。复盘有两点：早期我们直接返回 Entity，导致字段泄漏和前端字段耦合，后来改成 DTO 加 MapStruct 映射，接口变更成本明显下降；另一个坑是全都返回 HTTP 200，导致监控无法按状态码告警，后来约定传输、鉴权、限流用真实 HTTP 状态码，业务失败用 200 加业务 code，监控同时看两者。

**常见追问**：ResponseBodyAdvice 对 String 返回值和已包装响应要注意什么？

## 34. WebSocket 在项目里解决什么问题？为什么不用轮询？心跳和断线重连怎么实现？如何避免重复连接？

> 原题 ID：`q1902`

**高频程度**：★★★★

**考察点**：考察实时通信方案选型与连接生命周期治理：长连接的必要性、心跳保活、指数退避重连与单例连接管理。

**回答框架**：

1）为什么用：服务端主动、低延迟、双向推送，替代轮询的高开销与高延迟；
2）握手与帧：一次 HTTP Upgrade 到 101，之后帧头极小；
3）心跳：客户端定时 ping + 服务端空闲检测，防半开连接；
4）重连：指数退避 + 抖动，重连后重新鉴权、重新订阅、增量补拉；
5）防重复：单例 + 状态机 + 多标签页选主。

**参考回答**：

我分四块回答。第一，解决什么问题。项目里需要一条实时通道，比如订单状态变更、IM 消息、行情或监控指标推送。HTTP 轮询要么高频浪费连接和带宽——每次请求都带完整 header、重复鉴权、可能触发限流，要么低频导致延迟高；长轮询虽然降低延迟，但服务端要挂住请求占用连接和线程，而且每次推送后还要重新建连。WebSocket 通过一次 HTTP Upgrade 握手建立全双工长连接，之后帧头只有 2 到 14 字节，服务端可以主动 push，延迟从秒级降到毫秒级，QPS 和带宽都明显下降。第二，心跳。客户端会定时发 ping，比如 25 秒一次，服务端回 pong；同时服务端也要做空闲检测，超过 N 个周期没收到任何帧就主动 close，防止 NAT 或代理静默断链导致半开连接占资源。第三，断线重连。客户端监听 onclose 和 onerror，用指数退避加抖动重连，比如 1s、2s、4s 一直到上限 30s，加随机 jitter 避免服务端一挂所有客户端同时重连造成雪崩。重连成功后要做三件事：重新鉴权、重新订阅频道、用 lastSeq 做增量补拉断连期间的消息。第四，避免重复连接。浏览器端要保证全局唯一连接，我用单例加状态机，状态包括 CONNECTING、OPEN、CLOSING、CLOSED，重连前先判断 readyState，避免多个组件各自 new WebSocket。页面 visibilitychange 或 online 事件触发重连时也要先检查是否已有连接。多标签页场景可以用 BroadcastChannel 或 SharedWorker 选主，只让一个 tab 持有连接，或者服务端按 userId 做连接去重踢旧。复盘：上线后连接数从轮询的峰值 QPS 降了一个数量级，消息到达 P99 从 3s 降到 200ms 内。踩过的坑是移动端切后台被系统挂起导致心跳停发，服务端误判断开，后来加了前后端双向心跳和 lastSeq 补拉才解决。

**常见追问**：网关的 idle timeout 和心跳间隔是什么关系？设错了会怎样？

面试复盘的本质是『经验蒸馏』，把一次高成本、高信息密度的真实交互，转化成结构化的可迁移知识。可以类比机器学习的训练循环：面试是前向传播，暴露问题；复盘是反向传播，定位误差并更新参数。不复盘就相当于只做前向不更新权重，模型永远不收敛。我的做法分四层。第一层是事实层：趁热记录题目原文、追问路径、面试官的反应，比如皱眉、打断还是深追，越具体越好，最好 24 小时内完成，因为拖久了记忆会被重构。第二层是归因层，也是最关键的一层：我会区分四类问题——『完全不会』是知识盲区，『会但没讲清』是表达和结构问题，『会但答偏』是审题和需求澄清问题，『紧张或环境问题』是状态问题。这四类的修复手段完全不同，把知识问题当表达问题补，就会一直原地踏步。第三层是知识层：把答不上的题整理成专题卡片，比如 CAP、索引下推、ReAct 范式，补原理加手写代码加边界 case，而不是只背答案。第四层是策略层：统计高频考点分布、面试官风格是偏工程还是偏论文，然后迭代我的自我介绍、项目讲述模板和反问清单。适用场景上，我觉得不仅失败的面试要复盘，成功的面试更要复盘——成功经验如果不可解释，下次就无法复制。我个人的实践是建一个面试错题本，按知识域而不是按公司归档，并按 1 天、3 天、7 天、21 天做主动回忆，能不看稿讲清才算过。

**常见追问**：成功面试的复盘你会重点记录什么？为什么？

**考察点**：考察（作为面试官）如何透明介绍薪酬机制并引导回岗位价值，同时对齐候选人预期，避免空谈承诺。

AI Agent 时代技术栈会快速迭代，但问题分析到方案设计、从原型验证到系统优化的工程思维是跨技术周期可迁移的核心竞争力，工具会过时，方法论不会。这句话的本质是：AI Agent 把写代码的门槛降低了，但把定义问题、拆解系统、做权衡、验证与迭代的门槛抬高了。可以分四个阶段展开。第一，问题分析：先判断这是不是 Agent 该解决的问题。很多需求用规则引擎、RAG、传统 ML 或一个 prompt 就能解决，上多 Agent 反而增加不确定性和成本。要能定义成功指标，比如准确率、延迟、成本、人工接管率，而不是只定义能不能跑。第二，方案设计：Agent 系统本质是分布式系统加概率组件。要设计状态机或工作流、工具边界、记忆与上下文管理、失败重试与降级、权限与审计。例如把订机票拆成查询、比价、下单、支付四个工具，每个工具幂等、可观测、可回滚，而不是让 LLM 自由发挥。第三，原型验证：用最小闭环验证核心假设。先做 eval set（真实 badcase 集），再跑 baseline（纯 prompt、单 Agent、多 Agent），用数据决定是否加复杂度。常见做法是离线评测加小流量灰度，而不是凭感觉调 prompt。第四，系统优化：Agent 的瓶颈通常在上下文长度、工具调用次数、模型延迟和 token 成本。优化手段包括缓存、并行化无依赖步骤、按难度路由大小模型、压缩上下文、减少无效工具往返。一句话：模型一季一换，但把模糊需求变成可验证系统的能力，永远是硬通货。

## 95. 为什么有些人编码能力强却在技术面试中表现不佳？如何改善？

## 98. 如何通过学习其他编程语言的心智模型与生态，反哺 Java 工程能力？

> 原题 ID：`q2207`

**高频程度**：★★★

**考察点**：考察跨语言学习的方法论：心智模型、生态、迁移。

**回答框架**：

1) 语言层：掌握心智模型（Java 强类型+JVM 托管、Python 动态+GIL、Go 显式错误+goroutine）；2) 生态层：标准库与框架决定了语言擅长的场景；3) 迁移层：学新语言是为了扩展工具箱并反哺原有技术栈。

**参考回答**：

语言不熟、生态不通时学新语言收获有限，本质是没把新语言的知识挂到已有认知树上，也没用真实项目驱动，导致迁移失败。

这个问题的核心不是‘学不会’，而是学习方式与目标错位。可以拆成三层：

1. 语言层：语法只是入口，真正要掌握的是该语言的‘心智模型’。比如 Java 是强类型、面向对象、JVM 托管内存；Python 是动态类型、鸭子类型、GIL；Go 是显式错误、goroutine、组合优于继承。如果只背语法，不建立心智模型，回到 Java 就只剩‘哦，它有个 for-in’。

2. 生态层：语言的价值一半在标准库和第三方生态。Java 有 Spring、Maven、JVM 调优；Python 有 NumPy、PyTorch、pip；Go 有 net/http、go mod。不熟悉生态，就不知道新语言解决什么问题、在什么场景更优，自然觉得‘收获有限’。

3. 迁移层：学习新语言的目的不是替换 Java，而是扩展工具箱。比如学 Python 后，可以用它写脚本、做数据分析、调 AI 模型；学 Go 后，可以用它写高并发网关。回到 Java 时，可以把新语言的思想反哺回来：Python 的列表推导影响 Java Stream，Go 的 context 影响 Java 的异步编排。

通俗类比：学新语言像学一门外语。只背单词不交流，回国后还是不会说；但如果你用这门外语读了一本专业书、写了几封邮件，回国后你的中文表达也会更清晰。

建议做法：
- 用‘最小可运行项目’驱动，比如用 Python 写一个调用大模型 API 的 CLI，用 Go 写一个并发爬虫。
- 每学一个特性，问三个问题：它解决什么问题？Java 里对应什么？什么场景下它比 Java 更合适？
- 建立‘对照表’：异常处理、并发模型、包管理、构建工具、测试框架。
- 回到 Java 后，刻意用新语言的思想重构一小块代码，比如用 Stream 替代循环、用 CompletableFuture 替代线程池。

**常见追问**：你会怎么给自己设计一条有效的跨语言学习路径？
