## 1. Agentic RAG 如何把固定检索流程变成按需、多轮的检索决策？

> 原题 ID：`q0014`

**高频程度**：★★★★

**考察点**：检索控制权、查询迭代、停止条件与适用任务。

**回答框架**：

1) 固定流程基线
2) 检索工具化
3) 证据缺口驱动下一轮
4) 预算和终止条件

**参考回答**：

固定 RAG 流程通常按预设步骤检索并生成。Agentic RAG 把检索和其他数据访问能力暴露为工具，由控制器结合当前问题与已获证据，决定是否检索、访问哪个源、怎样改写查询以及是否继续。

例如回答“两个产品的保修政策有何差别”时，可以先分别查到政策，再发现某一版本日期不一致，补查对应历史版本后形成对照。下一轮查询应由具体的证据缺口驱动，不能只是重复原查询。

这种方式适合多跳问题、动态数据源和需要工具组合的任务，但增加了路由错误、循环和成本。应设置调用预算、去重、可验证的停止条件，以及缺证据时的说明或升级路径。Agentic RAG 是编排范式，不等同于 Self-RAG 这类特定训练方法；简单单跳问题可以继续采用固定流程。

**常见追问**：如果每次检索都返回相似材料，怎样判断继续检索已没有收益？

## 3. Rerank(重排序)技术是什么？在 Agent 检索链路里起什么作用？

> 原题 ID：`q0058`

**高频程度**：★★★★

**考察点**：考察重排（Rerank）原理：Cross-Encoder 与 Bi-Encoder 的区别及两阶段检索思想。

**回答框架**：

1) 定义重排；2) 召回追求高召回、重排追求高精度；3) 双塔 vs 交叉编码；4) Top-K 成本权衡。

**参考回答**：

Rerank 是在初召回（向量或 BM25 取 Top-N）之后，用更强的交叉编码模型 Cross-Encoder 对「query-文档」对精细打分重排，取 Top-K 给 LLM。作用是提升上下文相关性、过滤噪声、显著改善最终答案准确率。原理上召回阶段追求高召回，用双塔 Bi-Encoder，query 和 doc 各自编码，可以预先建索引、快但粗；重排阶段追求高精度，Cross-Encoder 让 query 和 doc 交互编码，准但慢，所以只对候选集做。这就是「召回广 + 重排精」的两阶段思想，K 要控成本，不能对全库做交叉编码。

**常见追问**：重排模型怎么选？BGE-reranker 和 Cohere Rerank 在你们场景差多少？

**考察点**：记忆是信息管理目的，RAG 是使用外部证据的机制，二者可以重叠。

**回答框架**：

1) Memory 管理交互和状态
2) RAG 检索后生成
3) 记忆可用 RAG 读取
4) 共享的治理要求

**参考回答**：

Agent Memory 通常指对交互历史、任务状态、偏好或经验的保存与再利用；RAG 指从外部信息源检索材料以辅助生成。前者描述信息的用途与生命周期，后者描述获取和使用证据的流程。

记忆可通过精确字段、文件读取或 RAG 被访问；RAG 的材料也可以是历史对话，不限于静态文档。因而不能把 RAG 固定描述为只读、静态，或认为它无需处理更新、冲突与删除。

## 8. 如何提高 RAG recall？

**回答框架**：

1) 三阶段框架：检索前/中/后；2) 检索前切块与索引；3) 检索中改写与混合；4) 检索后重排与父子块。

**参考回答**：

我会按「检索前-检索中-检索后」三阶段来做。检索前做好切块策略——按语义或标题切、加 overlap、建元数据、建混合索引；检索中用 query 改写加 Hybrid（BM25+向量）多路召回，必要时上 HyDE 或 step-back；检索后做 rerank 加回溯父块，再靠评测集看 Recall@K 哪类漏了，针对性补。召回低通常是三个根因：切块太大或太小、query 与文档表述差异大、只做向量单路。要避免两个雷区：一味加大 TopK 只会引入噪声，不评测盲调等于碰运气。

## 12. 什么是 RAG-Fusion？它和朴素 RAG 有什么区别，解决什么问题？

> 原题 ID：`q0104`

**高频程度**：★★★★

**考察点**：考察 RAG-Fusion 的多查询改写与 RRF 融合机制。

**回答框架**：

1) 定义；2) 与朴素 RAG 的差异；3) RRF 融合流程与公式；4) 收益与代价。

**参考回答**：

RAG-Fusion 是在检索前让 LLM 把用户问题改写成多个语义不同的子查询，分别检索后用 RRF 做倒数排名融合再重排，解决「单次 query 表述单一、召回不全」的问题。朴素 RAG 只用原始 query 检索一次，用户措辞和文档差异大就容易漏召。流程是：生成 N 个覆盖不同角度的改写查询→各自向量检索→RRF 融合，score = Σ 1/(k+rank)→取 TopK 送生成。收益是召回更全、对表述更鲁棒；代价是 N 倍检索加额外 LLM 改写调用，所以要控成本。效果关键在改写 query 的多样性，融合后还得 rerank。

**常见追问**：改写出多个 query，怎么保证它们不是同义重复、真的覆盖不同角度？

> 原题 ID：`q152`

**考察点**：词项匹配与语义召回的差异，以及分数校准和排序融合。

**回答框架**：

1) 两路召回
2) 分数不可直接比较
3) 加权与 RRF
4) 按查询类别评测

**参考回答**：

BM25 依赖词项匹配，适合术语、编号和专名；向量检索可召回不同措辞的相关内容，但也可能混淆只差少量关键字的对象。混合检索尝试利用二者互补，是否提高效果需要验证，不能保证总是优于单路。

## 17. RAG 召回率从 0.72 提升到 0.89，这个数据怎么算？召回率提高是否一定让最终回答更准确？

我的判断是：传统 RAG 加摘要召回的瓶颈在于检索是一次性的、被动的。三个具体原因：第一，摘要预处理是「写时」一次性压缩，它不知道未来会问什么，必然丢细节，而且检索时无法根据当前问题动态决定读哪些；第二，传统 RAG 一跳检索，遇到多文档、需要多步推理、要核对或跨源比对的场景就力不从心；第三，Agentic RAG 把检索变成「读时」的主动、多轮、带决策的过程——模型自己决定查什么、查几次、要不要精读原文、要不要验证，像人翻书、核对、再翻。所谓「读搞不定」，是长文档关键信息分散，摘要会把它糊掉；所谓「写搞不定」，是预处理时根本不知道查询会问什么，固定摘要覆盖不了所有未来问题。所以 Agentic RAG 是用运行时的按需检索和推理，去补写时静态摘要的盲区。

**常见追问**：那是不是可以不要预处理、干脆全用 Agentic 检索？成本和延迟你怎么控？

## 31. 在 Agentic RAG 里，你怎么判断「当前检索到的信息已经足以回答用户问题、可以停了」？如果判断错了（过早停或一直检索）会怎样，怎么缓解？

> 原题 ID：`q1150`

**高频程度**：★★★★

**考察点**：Agentic RAG 的停止条件设计：充分性判定与失败缓解。

**回答框架**：

1) 充分性判定器；2) 子问题 checklist 覆盖；3) 不确定性驱动续查；4) 过早停与一直检索的缓解。

**参考回答**：

这是 Agentic RAG 的核心问题——停止条件或者说充分性判定。我用四种信号组合：一是判定器，让 LLM 或一个训练好的小模型对「当前证据能否回答提问」做 yes/no 加理由，达到阈值就停；二是多证据交叉，要求关键子问题都被覆盖，做成 checklist 式判定，而不是只看单轮相关性；三是不确定性驱动，模型自评估不确定或证据之间存在冲突时继续检索；四是收敛检测，新检索结果与已有证据高度重合并不再带来增量时早停。判断错的后果也要防：过早停会导致漏答或幻觉，所以要加显式的「证据充分性」校验步和最低检索轮数下限；一直检索会成本爆炸甚至死循环，所以要设最大轮数上限、对已查 query 去重、证据收敛即早停。

## 32. 用什么小模型判断「某个章节/片段是否对回答用户问题有帮助」？这个判断能力是怎么训练出来的？

> 原题 ID：`q1151`

**高频程度**：★★★

**考察点**：考察相关性判别器的建模与训练数据构造思路。

**回答框架**：

1) 模型选型；2) 训练数据构造；3) 监督目标（帮助度而非相似度）；4) 训练方式与评测。

**参考回答**：

本质是训练一个相关性或帮助度判别器，类似 reranker 或 pointwise judger。模型选型上用小模型，比如 TinyBERT 或 BGE-reranker 量级，做轻量二分类或打分，成本低可以前置过滤。训练数据构造是「问题-章节-是否相关」三元组：先用强模型对章节打相关标签做伪标，再人工抽检校正成训练集。监督目标要定义成「帮助度」而不是表面语义相似——标签定义成「该章节是否包含答题所需事实」，甚至可以让 LLM 生成「是否必要」的标注。训练方式可以 pointwise 二分类，也可以用 pairwise 对比学习（有用大于无用），后者更贴合排序任务。评测在人工标注的验证集上看 Precision、Recall 和召回率，重点防把关键章节误杀——因为漏掉关键信息的代价比多带一点噪声大得多。

## 36. 什么是多路召回（multi-recall）？在 RAG 里具体怎么做？

> 原题 ID：`q1264`

**高频程度**：★★★

**考察点**：考察多路召回的定义与工程实现。

**回答框架**：

1) 定义；2) 四类典型通路；3) 并行取候选后 RRF/加权融合；4) 注意事项。

**参考回答**：

多路召回指同时用多种检索器——向量、BM25、标签或 metadata 过滤、图谱等——各取 top-k，再合并去重，目的是用不同召回通路互补，避免单通路漏召。典型的多路有四条：稠密向量召回负责语义；稀疏 BM25 负责关键词；按 metadata（时间、部门、权限）过滤召回；图或结构化查询召回。每一路并行取候选后，用 RRF 或归一化加权融合，再经 reranker 精排取最终 top-k。要注意两点：每路都要控制召回量，不然候选集爆炸；融合层要去重，防止同一文档多路重复出现。核心思想是「召回讲究覆盖，重排讲究精准」，两段式分工。只做单路向量检索那不能叫多路召回。

**常见追问**：不同通路要不要设不同权重？你会怎么定？

## 37. metadata 在 RAG 里是干什么的？它为什么通常不做向量化？

> 原题 ID：`q1265`

**高频程度**：★★★★

**考察点**：考察 metadata 的作用与「为什么不做向量化」的原理理解。

**回答框架**：

1) metadata 的四类用途；2) 为什么不做向量化；3) 硬过滤 vs 相似度；4) 实践中怎么做。

**参考回答**：

metadata 包括来源、时间、权限、章节、类型这些，用途有四类：权限和租户隔离，按 user 过滤可见文档；时间衰减，给新文档加权；来源可信度加权；结构化字段精确匹配，比如订单号、日期。为什么通常不做向量化：因为 metadata 大多是枚举、数值、短标签，语义连续性弱，嵌入之后反而模糊——比如「2024-03-01」和「2024-03-02」向量几乎一样，但它要表达的恰恰是精确区别；而且它更适合做硬过滤（WHERE 条件）而不是相似度匹配。实践中常见两种做法：向量召回加 metadata 后置过滤，或者向量加标签双塔。核心是分层：向量管语义，metadata 管约束。雷区是把 metadata 简单拼进文本一起向量化，既污染语义又无法精确过滤。

## 40. CRAG 和 Self-RAG 分别如何改进检索增强生成？

**高频程度**：★★★★

**考察点**：检索纠错与训练得到的反思 token 的区别。

3) 训练要求

## 57. RAG 的局限性？

> 原题 ID：`q1531`

**高频程度**：★★★★

**考察点**：考察对 RAG 局限的四层拆解能力。

**回答框架**：

1) 检索层；2) 上下文层；3) 知识层；4) 生成层。

**参考回答**：

RAG 的核心局限是它只能把外部知识「拼」进上下文，无法保证检索到、理解对、用得上，可以分四层。检索层：检索不准后面全错，向量检索依赖语义相似度，对精确匹配（编号、代码、专有名词）、多跳推理、否定和条件查询很弱；chunk 粒度也两难，太碎丢上下文，太大引入噪声，召回率和精度难同时保证。上下文层：窗口有限且中间遗忘，长上下文会导致模型对中间位置的注意力下降，token 成本也随文档量线性上升。知识层：外部库可能包含过时、矛盾或错误内容，模型缺乏权威性判断容易照单全收，知识更新需要重建索引存在延迟。生成层：模型仍可能不忠实，即使给了正确文档也会忽略、曲解或与自身参数知识冲突，产生「有据不依」的幻觉；多跳、聚合、数值推理这些任务，RAG 只是提供素材，推理仍靠模型自身能力。可以提 Lost in the Middle 论文来说明「塞更多文档不等于更好」。

## 59. 请你介绍一下向量检索和关键词检索的区别？

> 原题 ID：`q1548`

**考察点**：考察稀疏检索与稠密检索的本质差异与混合方案。

**回答框架**：

1) 关键词检索原理；2) 向量检索原理；3) 字典 vs 气味的类比；4) 场景划分与混合检索。

**参考回答**：

关键词检索像 BM25、TF-IDF，把文本切词建倒排索引，根据词频、逆文档频率和文档长度算分，本质是字面匹配——查「苹果手机」，只有包含这些词的文档才会被召回，同义词「iPhone」可能完全匹配不到。向量检索先把文本用 Embedding 编码成高维向量，检索时把 query 也编码，用余弦相似度或内积找最近邻，本质是语义匹配，能召回「iPhone」「苹果牌智能手机」甚至相关内容。类比：关键词检索像查字典，必须按字面找到词条；向量检索像找气味相近的东西，不要求名字一样只要意思接近。场景上：关键词检索适合法律条文、订单号、代码符号、专有名词等要求精确命中且需可解释的场景，成本低、更新快；向量检索适合自然语言问答、语义搜索、跨语言检索，但有算力和存储成本，且 ANN 是近似可能漏掉真正最近邻。实际系统常用混合检索：先分别召回，再用 RRF 或加权融合排序，兼顾精确与语义。

## 60. GraphRAG 和 LightRAG 详解：传统 RAG 撞墙之后的两条进阶路线，原理、对比与选型一次说清？

> 原题 ID：`q1570`

**高频程度**：★★★

**考察点**：考察 GraphRAG 与 LightRAG 的原理差异与选型判断。

**回答框架**：

1) 传统 RAG 三类硬伤；2) GraphRAG 建图 + 社区摘要 + map-reduce；3) LightRAG 双层关键词检索与增量更新；4) 选型建议。

**参考回答**：

传统 RAG 有三类硬伤：全局性问题比如「这批文档整体讲了哪些主题」，向量检索只能召回局部片段；多跳关系问题比如「A 的导师所在机构的负责人是谁」，答案分散在多个 chunk，向量相似度接不起来；以及上下文割裂，chunk 切断了实体间显式关系。GraphRAG 的思路是「先建图再分层总结」：用 LLM 对每个 chunk 做实体关系抽取，做实体消解合并成知识图谱，再用 Leiden 做社区发现切成层级社区，对每个社区生成摘要；查询时 local search 从命中实体沿边扩展，global search 用 map-reduce 遍历社区摘要汇总，所以能回答全库主题归纳这类问题。代价是索引阶段 LLM 调用量巨大、成本高、增量更新难。LightRAG 做减法：同样抽实体关系建图，但放弃昂贵的社区摘要和层级聚类，改为图结构 + 向量双索引，并提出双层检索——low-level 检索具体实体细节，high-level 检索抽象概念主题，同时支持增量插入时只更新局部图，成本低一个量级、效果接近。选型：需要全库主题归纳和跨文档关系推理且预算充足选 GraphRAG；需要多跳能力但要控成本、支持频繁更新选 LightRAG；单跳事实问答、文档量小，传统向量 RAG 就够。

## 61. 代码检索应该如何组合文本搜索、符号索引与语义检索？

> 原题 ID：`q1573`

**高频程度**：★★★★

**考察点**：考察代码检索中精确文本、符号关系和语义意图三类需求，以及组合检索而非二选一的工程方案。

**回答框架**：

1) grep/rg 适合已知字符串与正则；2) LSP/AST/代码图适合定义、引用和调用关系；3) embedding 适合自然语言描述的概念检索；4) 用结构化结果约束 LLM；5) 按查询类型路由并评测召回。

**参考回答**：

代码检索不是 grep 与 RAG 二选一，而是先判断查询类型。已知标识符、错误码、配置键或正则模式时，`rg`/grep 的字面搜索快、确定、可复现；查定义、引用、类型关系和调用链时，LSP、AST 索引或代码图比纯文本更准确；用户只描述业务意图、不知道命名时，embedding 或混合检索有助于召回语义相近的候选。

评测时按查询类型分别统计 Recall@k、定义/引用命中率、索引新鲜度和端到端定位成功率。小仓库或精确查询可能完全不需要向量库；大型异构仓库的自然语言检索才更可能从语义索引中获益。

2048 维能不能接受，取决于索引类型、数据规模、硬件和召回要求。先算账：暴力检索复杂度是 O(N·d)，2048 维、100 万条单次约 2×10⁹ 次乘加，CPU 上几十到几百毫秒，P99 更差，1 亿条基本不可用，所以「2048 维 + 大规模 + 暴力」通常不能接受。近似最近邻里：HNSW 是图索引，查询近似 O(log N)，但高维下每跳距离计算仍是 2048 维，内存占用也大（每向量 8KB，1 亿条原始就 800GB），延迟能到几毫秒到几十毫秒、召回 95%+，代价是建索引慢、内存贵；IVF-PQ 是倒排加乘积量化，把向量切成 m 段、每段用 256 个聚类中心，压缩到 m 字节，1 亿条能压到几十 GB、延迟毫秒级，但召回下降、需要调 nprobe。另外可以做降维，2048 维存在冗余，用 PCA 或随机投影降到 256~512 维，或用 Matryoshka 表示学习截断。结论是组合拳：ANN 索引 + 量化 + 降维 + 分片 + 缓存。

## 73. 如何量化生成答案与检索文档的 “事实一致性”？

> 原题 ID：`q1849`

**高频程度**：★★★★

**考察点**：考察事实一致性的量化方法（归因-判定-聚合）。

**回答框架**：

1) 拆解原子事实；2) 对齐证据；3) NLI/LLM 判定支持关系；4) 聚合指标。

**参考回答**：

核心思路是先归因、再判定、后聚合。第一步拆解，把生成答案拆成原子事实或 claims，可以句子级、三元组级或用 LLM 抽取，比如「爱因斯坦 1879 年出生于德国乌尔姆」拆成（爱因斯坦，出生年份，1879）和（爱因斯坦，出生地，德国乌尔姆）。第二步对齐检索文档，对每个 claim 从 top-k 文档中检索最相关证据片段，可以用 BM25、向量召回或 cross-encoder 重排得到 evidence set。第三步判定支持关系，二分类或三分类：用 NLI 模型判断 entailment、contradiction、neutral，或者用 LLM 裁判输出 supported、not supported、contradicted 并给出证据句；关键是指标要区分「无证据」和「有证据但矛盾」，这两类问题的修复方向完全不同。第四步聚合：Faithfulness = 被支持 claim 数 / 总 claim 数；Hallucination 率 = 被矛盾或不支持 claim 数 / 总数；引用准确率 = 引用中真正支持该 claim 的比例；引用召回率 = 应被引用的 claim 中实际有引用的比例。最后辅以人工抽样校准。

**参考回答**：

核心是解耦「索引更新」和「在线检索」，用增量索引、版本化和缓存失效策略，在保证低延迟的同时让新知识近实时可见，不能每次全量重建。做法六步：第一，变更捕获，用 CDC、消息队列或定时扫描识别新增、修改、删除的文档，生成变更事件；第二，增量切分与嵌入，只对变更文档做 chunking 和 Embedding 写入向量库，Milvus、Qdrant、Weaviate 都支持 upsert 和 delete，按 doc_id 或 chunk_id 做幂等更新；第三，索引分层与合并，新数据先写增量小索引，检索时同时查历史大索引和增量索引再合并，后台定期把小索引合并进大索引，类似 LSM-Tree 的 compaction；第四，版本与一致性，给文档和索引打版本号或时间戳，检索时过滤「生效时间小于等于当前时间」，避免读到未完成写入的数据；第五，缓存失效，高频 query 结果缓存，文档更新后按 doc_id 反向失效或设短 TTL；第六，删除要处理干净，不能只删向量，还要删元数据、倒排索引和缓存，更新采用先写新版本再标记旧版本失效，避免检索空洞。

Agentic RAG 的本质是把 RAG 从固定流水线变成由 LLM 自主决策的 Agent Loop：模型在循环中决定何时检索、检索什么、是否继续，代码骨架就是一个 while 循环加工具调用。传统 RAG 是线性流水线，检索是强制的、一次性的、与生成解耦；Agentic RAG 把检索封装成 Agent 可调用的工具，由 LLM 在推理过程中决定。循环四步：一，把用户问题、系统提示和可用工具（search、read_doc、calculator）发给 LLM；二，LLM 返回要么是最终答案、要么是一个工具调用请求；三，执行工具，把结果作为 observation 追加到消息历史；四，回到第一步，直到 LLM 输出最终答案或达到最大轮数或预算上限。伪代码就是 messages 里追加，for step in range(max_steps) 循环里调 LLM，不是 final 就执行 tool_call 追加结果。虽然代码简单，但必须有护栏：最大步数、总 Token 预算、工具调用去重、失败重试和超时，否则容易死循环烧钱。

**参考回答**：

Agentic RAG 是把 RAG 从固定流水线升级为 Agent 自主决策循环，由 LLM 动态选择检索、工具调用、推理与终止，核心是规划-执行-反思的闭环。传统 RAG 是固定流程：问题→向量检索→拼接上下文→LLM 生成。Agentic RAG 让 LLM 作为 Agent，每一步根据当前状态自主决定：是否需要检索、检索什么、用哪个工具（向量库、SQL、API、计算器）、是否改写查询、是否分解子问题、是否调用外部工具、是否已足够回答。典型实现是 ReAct 或 Plan-and-Execute 循环四步：规划，把复杂问题分解为子任务或直接进入思考-行动循环；执行，Agent 输出动作如 search(query)，系统执行并返回观察结果；反思，Agent 评估结果是否充分，决定继续检索、换工具还是生成最终答案；终止，满足条件时输出答案。代码结构上就是一个 Agent 结构体持有 LLM、工具表和 maxSteps，Run 方法里循环调用 LLM、解析 tool_call、执行工具、把观察结果追加回消息，直到得到最终答案或超出最大步数。

## 84. 语义检索 vs 关键词检索的本质区别？

> 原题 ID：`q2032`

**高频程度**：★★★★

**考察点**：考察稀疏与稠密检索的本质差异。

**回答框架**：

1) 关键词检索原理；2) 语义检索原理；3) 六条关键区别；4) 图书馆类比与场景。

**参考回答**：

关键词检索匹配字面词项，语义检索匹配向量空间中的语义意图，本质是符号匹配与分布式语义表示的差异。关键词检索比如 BM25、TF-IDF 把文档和查询看成词袋，靠词频、逆文档频率、长度归一化算相关性，本质是符号层面的精确或模糊匹配，查询里出现「苹果手机」只有包含这些词或词干的文档才得分高。语义检索用双塔 Bi-Encoder 把文本编码成稠密向量，再用余弦相似度或内积找最近邻，本质是分布式语义假设：语义相近的文本向量距离近。类比是关键词检索像图书馆按书名标签找书，标签对不上就找不到；语义检索像懂内容的图书管理员，你说想找讲水果公司发展史的书，他能给你《乔布斯传》，即使书里没有这四个字。六条关键区别：表示上是稀疏高维词项 vs 稠密低维向量；匹配上是词项重叠 vs 向量相似度；能力上关键词处理不了同义词改写和跨语言，语义检索可以；可解释性上关键词强、语义弱；成本上倒排索引轻量毫秒级，语义检索需要 GPU 编码加 ANN 索引；对精确匹配、专有名词和数字，关键词反而更稳，语义检索可能语义漂移。

## 85. 向量检索中 Flat、IVF、PQ 和 HNSW 分别解决什么问题？

> 原题 ID：`q2033`

**高频程度**：★★★★

**考察点**：区分精确检索、候选分区、向量压缩和图索引，而非给索引做绝对排名。

**回答框架**：

1) Flat 精确扫描
2) IVF 缩小候选
3) PQ 压缩表示
4) HNSW 图搜索及组合

**参考回答**：

Flat 对全部向量计算距离，可作为精确检索基线，代价随库大小增长。IVF 先把向量分到粗粒度分区，查询只访问部分分区，访问数越少通常越快但可能漏召回。

PQ 把向量分成若干子空间并编码成码本索引，主要减少存储和距离计算成本，但引入量化误差；它常与 IVF 组合成 IVF-PQ。HNSW 则建立多层近邻图，通过图遍历寻找近邻，通常需要额外的图边内存。

这些概念不完全互斥，实际系统可以组合索引与压缩。不存在同时在召回、延迟、内存、构建和更新上普遍最优的方案。比较时固定数据、距离度量和目标召回率，再测资源与延迟；HNSW 的参数和选型条件另由 HNSW 专题展开。

## 86. 在百万级向量检索中，什么时候适合选择 HNSW？如何与其他索引比较？

> 原题 ID：`q2044`

**高频程度**：★★★★

**考察点**：考察 HNSW、IVF、量化索引和精确检索的机制与选型条件，避免把某种索引说成普遍最优。

**回答框架**：

1) 先明确规模、维度、召回、延迟、内存、更新和过滤需求；2) HNSW 的分层近邻图；3) 高召回低延迟与高内存、慢构建的权衡；4) 对比 Flat、IVF/IVF-PQ 和磁盘型索引；5) 用真实数据压测参数。

**参考回答**：

HNSW 用分层可导航近邻图做近似最近邻搜索：上层稀疏图负责快速接近目标区域，底层稠密图负责精细搜索。它常能在内存充足时取得较高召回和较低查询延迟，也支持增量插入，因此是百万级向量检索的常见候选，但不是普遍意义上的“最佳方案”。

它的主要代价是图边带来的较高内存占用、索引构建成本，以及删除和大规模更新的维护复杂度。`M` 影响图连接数和内存，`efConstruction` 影响构建质量与耗时，`efSearch` 影响查询召回与延迟；这些参数没有脱离数据集的固定最优值。

选型要比较约束：数据量较小或要求精确结果时可用 Flat；内存紧张、数据规模更大时可考虑 IVF-PQ 等压缩索引；数据远超内存时可评估磁盘型 ANN；强过滤、高更新率还要单独测试索引与过滤器的协同效果。最终应在真实向量分布和过滤条件下测 Recall@k、p95/p99 延迟、内存、构建时间与更新成本，再决定是否选择 HNSW。

**常见追问**：如果内存受限，你会换成什么方案？损失什么？

RAG 不会因 Agent 而淘汰，二者是互补关系：RAG 解决「知识从哪来」，Agent 解决「任务怎么一步步做」，现代 Agent 往往把 RAG 当作一个工具来调用。先厘清概念：RAG 本质是先查资料再回答的生成范式，把外部知识库通过向量或关键词检索召回片段拼进上下文，让模型基于事实作答，缓解幻觉、知识过时、私有数据不可见；Agent 本质是自主决策加工具调用加多步执行的架构，大模型作为大脑，通过规划、调用工具、观察结果、再决策的循环完成复杂任务。类比是 RAG 像考试时允许你翻书，Agent 像一个会自己拆解任务、跑腿、查资料、写报告的实习生——实习生当然会翻书，但翻书这个动作不会因为有了实习生就消失，反而成为他的核心技能。为什么说是片面论调：层次不同，RAG 是能力组件、Agent 是编排架构，Agent 要完成任务仍需要获取外部知识；Agent 无法凭空知道私有知识，模型参数里没有你公司的内部文档和实时库存，再会规划也得靠检索拿到。

## 91. 分词器、Embedding的作用？

> 原题 ID：`q2278`

**高频程度**：★★★

**考察点**：考察分词器与 Embedding 在 LLM 输入表示中的分工。

**回答框架**：

1) 分词器解决什么；2) BPE 等算法；3) Embedding 解决什么；4) 位置 Embedding 与乐高类比。

**参考回答**：

分词器把文本切成模型可处理的 token 并映射为 ID，Embedding 把离散 token 映射为稠密向量使语义可计算，这是 LLM 输入表示的两步。分词器解决的是「文本到离散符号序列」的问题：模型只能处理数字，所以先按规则把字符串切成 token（子词、词或字），再查词表得到整数 ID；常见算法有 BPE、WordPiece、Unigram/SentencePiece，比如 BPE 从字符开始反复合并最高频相邻对，最终词表既能覆盖常见词又能把罕见词拆成子词，兼顾词表大小和 OOV 问题；分词器决定了序列长度、词表大小、多语言和数字的切分方式，直接影响训练和推理成本。Embedding 解决的是「离散 ID 到连续向量」的问题，本质是一个可学习的查找表，形状是 [词表大小, 隐藏维度]，第 i 行就是 ID 为 i 的 token 向量。它的作用有三：把离散符号变成可微可训练的稠密表示；让语义相近的 token 在向量空间中距离更近，比如猫和狗的向量相似度高于猫和汽车；作为后续注意力层的输入承载上下文信息。Transformer 里通常还会加位置 Embedding，因为自注意力本身没有顺序概念。类比是分词器把一句话拆成乐高积木块并编号，Embedding 给每块积木一个坐标。

## 93. 如何设计 RAG 的 Prompt？

**高频程度**：★★★★

**考察点**：考察 RAG Prompt 的四段式结构与幻觉抑制。

**回答框架**：

1) 四个要解决的问题；2) 四段结构；3) 为什么这样设计（条件生成）；4) 场景化调整。

**参考回答**：

RAG 的 Prompt 设计核心是把检索到的证据和用户问题用清晰的角色、边界和输出约束组织起来，让模型基于证据回答、无证据时拒答，并给出可追溯引用。它不是简单把文档拼在问题前面，而要解决四个问题：证据怎么放、模型怎么用、幻觉怎么防、结果怎么验。通用结构可以写成四段：第一段角色与任务，比如「你是基于给定资料回答问题的助手，只依据资料作答」；第二段证据区，用明确分隔符包裹检索片段，每段带编号和来源，比如 <context>[1] 来源：xxx.pdf 第 3 页 内容：… [2] …</context>；第三段用户问题，用 <question> 包裹；第四段输出约束，包括先判断资料是否足够、不足则回答「根据已有资料无法确定」不要编造、每个关键结论后用 [编号] 标注来源、按指定格式输出（JSON 或分点）。原理上 LLM 的上下文是软证据，Prompt 的作用是建立条件概率 P(answer | question, retrieved_docs)，把证据和问题分区、编号、加来源，能降低模型把参数记忆和检索内容混淆的概率。场景化调整上，事实问答和客服知识库强调只依据资料、必须引用；多跳推理要求先列证据再推理。

## 95. 所有结果都低于阈值怎么办——三种策略：降阈值重试、退化为无 RAG 直接生成、告诉用户"我找不到相关信息"？

> 原题 ID：`q3006`

**高频程度**：★★★★

**考察点**：考察低于阈值时的分级兜底路由。

**回答框架**：

1) 三种策略及其本质区别；2) 各自适用场景；3) 分级路由实现；4) 置信度校准。

**参考回答**：

低于阈值时不应只做单一动作，而应按场景在降阈值重试、无 RAG 直答、明确拒答三种策略间做分级路由与兜底。三种策略的本质区别在于对幻觉风险和可用性的权衡：降阈值重试，把阈值下调（如 0.75 到 0.6）或扩大 top-k 再检索，甚至换用 BM25 关键词混合检索，适合阈值偏保守、召回被误杀的场景，工程上要设下限且只允许有限次重试（如最多 2 次），否则等于取消阈值；退化为无 RAG 直接生成，把问题交给 LLM 自身知识回答，但必须显式标注「未引用知识库」并加免责声明，适合通用常识、闲聊、创作类问题，对强事实、合规、医疗金融场景应禁用；告诉用户找不到，直接拒答或引导澄清转人工，最安全但体验最差，适合高准确率要求的场景。工程落地建议做分级路由：先判断 query 类型（事实型、开放型、闲聊），事实型优先拒答或重试，开放型可退化直答；同时记录低分 query 用于知识库补全。置信度上建议用 rerank 分数而不是原始向量分，因为向量分受模型和归一化影响大、跨模型不可比。

## 96. 如何用 ReAct Loop 实现多跳检索？怎样利用上一跳结果构造下一跳查询？

> 原题 ID：`q3011`

**高频程度**：★★★

**考察点**：考察多跳检索与 ReAct 循环的结合方式。

**回答框架**：

1) ReAct 循环；2) 显式多跳的含义；3) 具体例子；4) 与固定 pipeline 的差异。

**参考回答**：

把多跳检索显式编入 ReAct 循环，就是让 Agent 在「思考-行动-观察」的每一步里，把上一跳检索到的内容作为下一跳检索的查询条件或上下文，逐步逼近答案。ReAct 的核心循环是 Thought（推理当前该做什么）→Action（调用工具如检索）→Observation（拿到返回结果）→再进入下一轮 Thought。显式的意思是：不把多跳检索做成黑盒的一次性 pipeline（比如先固定检索两次再回答），而是把每一跳都暴露成循环里的一次 Action，让模型自己决定要不要再查、查什么、用上一跳的什么信息去查。举个「某公司 CEO 的母校在哪个城市」的例子：第一轮 Thought 是「需要先知道这家公司的 CEO 是谁」，Action 是 Search（X 公司 CEO），Observation 返回「CEO 是张三」；第二轮 Thought 是「现在要查张三的母校」，Action 是 Search（张三 毕业院校），注意这里查询词是由上一跳 Observation 里的实体「张三」拼出来的，这就是上一跳结果作为下一跳输入；后续再搜清华大学在哪个城市，最后汇总答案。相比于固定两步 pipeline，ReAct 的优点是每一步都能根据实际结果调整，查错了可以改 query，信息够了可以提前终止。

**常见追问**：多跳检索怎么防止实体抽取错误导致后续全错？

## 99. RAG向量库，文档版本迭代更新，如何局部更新文档数据？

> 原题 ID：`q3497`

**高频程度**：★★★★

**考察点**：考察向量库增量更新与版本管理设计。

**回答框架**：

1) 稳定标识体系；2) content_hash diff 与复用；3) 逻辑删除 + 版本过滤；4) 索引合并与一致性。

**参考回答**：

文档版本迭代的局部更新，核心是给每个 chunk 打上文档 ID、版本号和内容哈希，用「逻辑删除旧版本 + 写入新版本」实现增量更新，而不是全量重建索引。为什么不能全量重建？因为整篇重新切分、重新 Embedding、整库重建代价极高——Embedding 调用贵、索引重建慢、还会造成服务抖动。做法分三步：第一，建立稳定的标识体系，每个 chunk 记录 doc_id、chunk_id、version、content_hash、更新时间，doc_id 标识逻辑文档、version 标识版本、content_hash 判断内容是否真的变了。第二，更新流程，新文档入库时先按 doc_id 查出旧版本的所有 chunk，对新文档重新切分并计算每个 chunk 的 content_hash，和旧 chunk 做 diff：hash 相同的直接复用旧向量、跳过 Embedding，hash 不同的才重新 Embedding，然后写入新版本 chunk 并把旧版本标记为 deleted。第三，查询时加过滤条件 version = latest 且 deleted = false，后台定期清理已删除数据并做索引合并。

## 103. RAG 中递归字符切分相比固定长度切分有什么优势？

> 原题 ID：`q3554`

**高频程度**：★★★

**考察点**：考察递归字符切分相对固定长度切分的优势。

**回答框架**：

1) 固定切分的缺陷；2) 递归切分的分隔符优先级；3) 三点收益；4) 书架类比。

**参考回答**：

递归字符切分通过按层级分隔符（段落→句子→词）递归切分，在控制块大小的同时尽量保持语义完整性，避免固定长度切分切断句子或段落。固定长度切分简单粗暴，按字符数硬切，容易在句子中间、单词中间甚至代码中间断开，导致语义碎片化，检索时召回不相关的块。递归字符切分定义一组分隔符优先级，比如 ['\n\n', '\n', '。', '！', '？', '，', ' ', '']，先尝试用最高优先级的分隔符（段落）切分，如果切出的块仍超过 chunk_size，就用下一级分隔符（句子）继续切分，直到块大小符合要求或分隔符用尽。这样保证三点：块边界尽量落在自然语义边界上；块大小可控；保留上下文连贯性。类比是整理书架，固定长度像按固定厚度切书、可能把一章切成两半，递归切分像先按章节分、再按小节分、最后按段落分，尽量让每部分完整。适用场景是文档问答和知识库检索，对结构清晰的文本如 Markdown、代码、论文效果更好。

## 104. 为什么普通 RAG 的一次 Top-K 检索无法解决问题？

> 原题 ID：`q3601`

**高频程度**：★★★★

**考察点**：考察单次 Top-K 检索的五类能力缺口。

**回答框架**：

1) 语义鸿沟；2) 多跳推理；3) 全局聚合；4) 召回噪声与冲突；5) 查询欠定义。

**参考回答**：

普通 RAG 的典型流程是把用户问题直接编码成向量，在向量库取相似度最高的 K 个片段拼进上下文让 LLM 回答，本质是一次性、无状态、无反馈的检索，所以有几类问题解决不了。第一，查询与文档的语义鸿沟：用户问「为什么 A 会导致 B」，文档里可能只写「A 的机制是 C，C 进而影响 B」，相似度不高，Top-K 可能召回不到关键片段；类比是你只拿一个关键词去图书馆问管理员，他只能给你最像这个关键词的书，而不是真正能回答问题的书。第二，多跳推理：问题需要先查实体 X 再根据 X 查 Y，一次检索只能拿到与原始问题最相似的片段，缺少「根据中间结果再检索」的能力，比如「某公司 CEO 的母校在哪」。第三，全局或聚合问题：像「这份报告的主要结论有哪些」「所有客户投诉的共同点」，Top-K 只取局部片段，无法覆盖全量文档。第四，召回噪声与上下文冲突：Top-K 里可能混入相似但不相关的片段，或多个片段互相矛盾，一次检索没有验证、重排、去重和交叉验证机制。第五，查询本身模糊或欠定义，缺少时间、范围、限定条件，检索方向就是错的。

**常见追问**：这五类问题里，哪一类用多轮检索也解决不了？

## 106. 为什么用 RRF，不直接用两路召回分数取平均？

> 原题 ID：`q3633`

**高频程度**：★★★★

**考察点**：考察 RRF 相对分数平均的优越性与原理。

**回答框架**：

1) 两路分数为什么不可比；2) RRF 公式；3) 评委类比；4) 四条优点与适用。

**参考回答**：

RRF 用排名而非原始分数做融合，避免不同召回通道分数尺度不可比、分布不一致的问题，是一种无参数、鲁棒的排序融合方法。两路召回的分数往往不可直接比较：向量召回常用余弦相似度（0~1 或 -1~1），BM25 是无上界的正数且分布长尾，二者量纲、分布甚至单调性都不同；直接取平均等价于假设两路分数同尺度同方差可线性叠加，这个假设通常不成立，会导致某一路（分数绝对值大或方差大）主导最终排序。RRF 的做法是对每个文档在每一路召回中的排名 r（从 1 开始）计算 1/(k+r)，再对各路求和作为最终得分，公式是 score(d) = Σ_i 1/(k + rank_i(d))，k 通常取 60。类比是两个评委，一个用百分制打分、一个用五分制打分，直接平均没意义，但如果只看「各自排第几名」再按名次给分，就能公平合并。优点有四条：只用排名天然消除量纲差异；无需调参、k 固定即可、鲁棒；对异常分数不敏感；实现简单，适合两路以上的多路融合。适用场景是混合检索、多路召回合并、不同模型或不同索引的结果融合。

**常见追问**：什么情况下加权分数融合会比 RRF 更好？

## 109. Matryoshka Embedding 怎么做到一个模型支持多种维度？

> 原题 ID：`q3797`

**高频程度**：★★★

**考察点**：考察 Matryoshka 表示学习的训练机制。

**回答框架**：

1) 普通 Embedding 截断的问题；2) MRL 训练做法；3) 推理时如何使用；4) 套娃类比与场景。

**参考回答**：

Matryoshka Embedding 通过训练时对嵌入向量做多粒度前缀截断并加权求和损失，让前 k 维就能独立表示完整语义，从而一个模型可输出任意维度。普通 Embedding 的每一维是全局耦合的，截断后信息会严重丢失。Matryoshka Representation Learning 的核心思想是让向量的前几维像俄罗斯套娃一样本身就是可用的完整表示。做法是：设完整维度为 d，训练时选取一组嵌套维度 m1 < m2 < ... < mk = d（如 8、16、32、…、1024），对同一个样本，模型输出 d 维向量后分别取前 m1、前 m2、…、前 d 维，各自接同一个分类或对比头计算损失，最后加权求和 L = Σ w_i · L_i，这样梯度会同时优化所有前缀，迫使前 m 维就承载足够语义。推理时只需取前 m 维并重新归一化（若用余弦相似度）即可直接用于检索，无需重新训练或额外投影，维度越小速度越快、存储越省，精度按需折中。类比是普通 Embedding 像把一幅画切成 1024 块、只拿前 128 块看不出画的是什么，Matryoshka 像套娃，最小的娃娃本身就是完整的娃娃只是细节少一些。适用场景是向量库需要多档存储和延迟预算、边缘设备低维、粗排用低维加精排用高维。

1) [CLS] 为什么不够；2) 各向异性现象；3) 对比学习原理与 InfoNCE；4) 工程关键设计。

**参考回答**：

直接用 BERT 的 [CLS] 或均值池化得到的句向量往往各向异性、分布坍缩，语义相似度排序差；对比学习通过拉近正例、推远负例，把表示空间重塑成各向同性且判别性强的结构，因此成为句向量训练的主流。先说 [CLS] 为什么不够：BERT 的预训练目标是 MLM 加 NSP，[CLS] 只在 NSP 里被监督去判断两句是否相邻，这个信号很弱且与「语义相似」不等价；同时 BERT 输出空间存在明显的各向异性，高频 token 和方向占据主导，随机两句的余弦相似度普遍偏高（0.7~0.9），导致相似度排序区分度差；直接拿 [CLS] 或 mean-pooling 做 STS 任务，Spearman 相关通常只有 50 多分，远低于微调后的 80 分以上。对比学习的原理是给定 anchor、正例、负例，优化 InfoNCE 损失，它等价于最大化正例对互信息的下界，同时把负例推开，本质是在超球面上做「对齐加均匀」：正例对距离小、整体表示均匀分布在球面上避免坍缩；温度 τ 控制分布的尖锐程度，τ 小则更关注难负例。工程上的关键设计包括正例构造（同句不同 dropout、NLI 蕴含对）和难负例挖掘，SimCSE 用 dropout 做正例，简单有效。

**常见追问**：难负例怎么挖？挖不好会有什么问题？

## 111. 如果检索内容正确，最终答案仍然出现幻觉，应该从哪些地方优化？

> 原题 ID：`q3996`

**高频程度**：★★★★

**考察点**：考察「有据不依」的归因与五层优化。

**回答框架**：

1) 归因：生成链路问题；2) 上下文组织；3) 提示与约束；4) 解码、后校验与模型选型。

**参考回答**：

检索内容正确但答案仍幻觉，本质是模型没有忠实使用给定证据，是 faithfulness 问题而不是召回问题，优化要按链路逐段排查。第一，上下文组织：去噪去重，检索回来的 chunk 常混有导航、广告、相似重复段落，噪声会稀释证据诱导模型脑补，做相关性重排、MMR 去冗余、按段落粒度裁剪；位置与顺序上把最相关证据放在上下文首尾（lost in the middle），并显式标注来源编号方便引用核对；长度控制上宁精勿多，超长上下文会降低对关键句的注意力。第二，提示与约束：强约束指令，明确「只依据以下资料回答，资料中没有的信息必须回答不知道」，并给出拒答示例做 few-shot；结构化输出，要求先给证据引用再给结论，强制模型对齐证据；限定回答格式如 JSON 带 citations 字段便于后续校验。第三，生成与解码：降低 temperature（如 0~0.3）减少发散。第四，后校验：做引用归因检查，用 NLI 或 LLM 判断答案中的论断是否被引用的片段支持，不支持就重生成或拒答。第五，模型选型：如果小模型指令遵循差、频繁忽略上下文，可换成指令遵循更强的模型，或做针对性微调。

**常见追问**：引用校验发现不支持的论断，是重生成还是直接删掉？
