## 1. MongoDB 使用什么数据格式存储文档？BSON 与 JSON 有何区别？

> 原题 ID：`q1028`

**高频程度**：★★★★

**考察点**：BSON 的类型系统、编码开销、遍历能力以及 Extended JSON 的用途。

**回答框架**：

1) MongoDB 驱动与服务端以 BSON 表示文档
2) BSON 保存字段类型和长度，并支持 JSON 没有的类型
3) 二进制不代表一定比 JSON 文本更小
4) Extended JSON 用可读 JSON 形式表达 BSON 特有类型

**参考回答**：

MongoDB 使用 BSON（Binary JSON）序列化文档，并用它在驱动与服务端之间传输数据。应用通常操作语言原生对象，驱动负责把它们编码为 BSON，再把查询结果解码回来。

BSON 与 JSON 都表示键值文档和数组，但 BSON 在每个值旁保存类型信息，并记录字符串、文档等内容的长度。它还原生支持 `ObjectId`、日期、二进制、32/64 位整数、`Decimal128` 和时间戳等 JSON 不具备或无法精确区分的类型。这些元数据便于数据库按字段解析、跳过和索引内容。

“binary” 不等于“必然更紧凑”。BSON 会重复保存字段名，并增加类型字节、长度和终止符；对很多小文档，它可能比紧凑 JSON 文本更大。它的主要价值是类型丰富、机器可解析和适合数据库操作，而不是无条件压缩。需要用 JSON 文本交换 BSON 特有类型时，可以使用 MongoDB Extended JSON；文档大小还受 16 MiB 上限约束。

## 4. MongoDB 支持多少级文档嵌套？复杂数据应如何决定嵌入还是引用？

> 原题 ID：`q1031`

**高频程度**：★★★★

**考察点**：明确 BSON 嵌套与文档大小上限，并按访问模式选择数据模型。

**回答框架**：

1) 对象或数组每增加一层都计入嵌套深度，最多 100 层
2) 单个 BSON 文档最大 16 MiB
3) 一起读取、规模有界、同生命周期的数据适合嵌入
4) 高基数、无界增长或独立更新的数据更适合引用

**参考回答**：

MongoDB 的 BSON 文档最多支持 100 层嵌套，每个对象或数组都会增加一层；单个 BSON 文档还受 16 MiB 大小上限约束。不过工程设计不应以接近上限为目标，关键是访问模式和数据增长方式。

经常一起读取、拥有相同生命周期、子项数量有界的数据适合嵌入，例如订单中的固定收货地址快照。这样一次读取即可得到聚合数据，并且单文档写入具有原子性。子项会无限增长、需要独立高频更新、被许多父对象共享，或经常单独查询时，更适合拆成独立集合并保存引用。

嵌入并不天然“降低数据冗余”；它经常会有意复制数据来减少联表式访问。过深结构会让更新路径、索引、多键数组和文档增长更难管理。设计时应先列出主要查询与写入，再评估文档大小、数组基数、原子性边界和一致性要求。

2. **负载均衡**：分片允许MongoDB在多个服务器之间平均分配数据和负载。每个分片都可以独立管理自己的读写操作，有效地分担了系统的负担，提高了查询性能和并发能力。

## 13. 你能简要介绍一下MongoDB吗？它与关系型数据库的主要区别是什么？

> 原题 ID：`q1027`

**高频程度**：★★★

**考察点**：考察 MongoDB 的定位（文档型 NoSQL、BSON 存储）及与关系型数据库在数据模型、Schema、查询语言上的区别。

**回答框架**：

1.定位：开源文档型 NoSQL 数据库，用 BSON 存储；2.数据模型：文档加嵌套结构与数组 vs 关系库的行列二维表；3.Schema：schemaless，无需预定义结构 vs 需预先定义表结构；4.查询语言：文档查询表达式 vs SQL；5.扩展与事务：天然横向扩展、事务能力弱于关系库。

**参考回答**：

MongoDB是一个开源、面向文档的NoSQL数据库，它采用了BSON（Binary JSON）格式存储数据。以下是MongoDB与关系型数据库的主要区别：

1. **数据模型**：

   - **MongoDB**：MongoDB是面向文档的数据库，数据以文档的形式存储，文档是一种类似于JSON的二进制表示形式（BSON）。文档可以包含嵌套的结构和数组。
   - **关系型数据库**：关系型数据库使用表格结构，数据被组织为行和列，遵循固定的表结构，需要事先定义表的结构。
2. **Schema（模式）**：

   - **MongoDB**：MongoDB是schema-less的，即不需要提前定义文档的结构，每个文档可以有不同的字段。这使得MongoDB更加灵活，适合处理半结构化或不确定结构的数据。
   - **关系型数据库**：关系型数据库需要提前定义表的结构，包括列名、数据类型等，数据必须符合预定义的模式。
3. **查询语言**：

   - **MongoDB**：MongoDB使用丰富的查询语言，支持丰富的查询表达式和嵌套文档的查询。
   - **关系型数据库**：SQL是关系型数据库的查询语言，使用表连接等方式进行查询。
4. **扩展性**：

   - **MongoDB**：MongoDB具有良好的横向扩展性，支持分片（Sharding），可以轻松地扩展存储和处理能力。
   - **关系型数据库**：通常采用垂直扩展，通过升级硬件来增加性能，这有一定的限制。
5. **事务支持**：

   - **MongoDB**：MongoDB在某些版本中引入了事务支持，但在早期版本中是不支持原子事务的。事务支持主要用于处理多文档的操作。
   - **关系型数据库**：关系型数据库通常具有原子性、一致性、隔离性和持久性（ACID）的事务支持。
6. **复杂性**：

   - **MongoDB**：MongoDB相对简单，尤其适合处理大量文档之间存在嵌套关系的场景，如JSON格式数据。
   - **关系型数据库**：关系型数据库具有强大的关联性和复杂的查询功能，适合需要复杂关系和事务的应用。

MongoDB更适用于需要灵活性、快速迭代和半结构化数据的场景，而关系型数据库更适用于具有固定模式、需要严格事务和复杂查询的场景。

## 15. 如何优化MongoDB查询性能？可以考虑索引、合理的查询语句等？

**回答框架**：

1.建索引：按查询条件与排序字段建单字段或复合索引，注意前缀顺序；2.避免集合扫描：确保查询条件字段有可用索引，用 explain 检查；3.投影：只返回需要的字段，减少数据传输；4.查询写法：避免不可索引的运算符（如不锚定的正则、ne、nin 滥用）；5.其他：数据类型一致、控制返回条数、分页与预聚合。

**参考回答**：

优化MongoDB查询性能涉及多个方面，包括索引的使用、合理的查询语句设计、适当的配置等。以下是一些优化MongoDB查询性能的建议：

1. **创建索引**：索引是提高MongoDB查询性能的关键。根据查询的字段和排序需求创建合适的索引。使用 `db.collection.createIndex()` 方法创建索引。常见的索引类型包括单字段索引、复合索引、文本索引等。

   ```JavaScript
   db.collection.createIndex({ fieldName: 1 });
   ```
2. **避免全表扫描**：尽量避免执行全表扫描，确保查询条件中的字段有索引。全表扫描对性能有很大影响，特别是在数据量较大时。
3. **合理使用投影**：在查询时使用投影操作符 `$project` ，只返回需要的字段，减少数据传输的开销。

   ```JavaScript
   db.collection.find({ /* 查询条件 */ }, { fieldName: 1, _id: 0 })
   ```
4. **使用合适的数据类型**：使用适当的数据类型能够减小数据存储的空间占用，并提高查询性能。例如，使用整数而不是字符串存储数字。
5. **分页查询**：对于大数据集的查询，使用 `limit()` 和 `skip()` 进行分页查询，而不是一次性返回所有结果。

   ```JavaScript
   db.collection.find({ /* 查询条件 */ }).skip(10).limit(10)
   ```
6. **避免使用** `$where`：避免使用 `$where` ，因为它通常会导致全表扫描，影响性能。

   ```JavaScript
   db.collection.find({ $where: "this.fieldName > 100" })
   ```
7. **使用合适的查询运算符**：根据具体查询条件选择合适的查询运算符，例如 `$eq` 、 `$gt` 、 `$lt` 等。

   ```JavaScript
   db.collection.find({ fieldName: { $gt: 100 } })
   ```
8. **利用复制集和分片**：在大规模部署中，使用复制集提高可用性，使用分片实现水平扩展。
9. **监控和调试**：使用MongoDB提供的工具和驱动程序的性能分析功能，如 `explain()` 方法，定期监控查询性能并调整索引和查询语句。

## 16. 什么是覆盖索引？为什么它对性能有影响？

> 原题 ID：`q1036`

**高频程度**：★★★★

**考察点**：考察覆盖索引的定义与性能收益：查询所需字段全在索引中，无需回表。

**回答框架**：

1.定义：索引本身包含了查询所需的全部字段，不需要回表取数据；2.收益一：减少 I/O，无需访问实际文档/数据行；3.收益二：减少网络与数据传输量；4.收益三：降低 CPU 解析与处理开销；5.实践：把查询字段纳入索引、只投影必要字段，用 explain 确认。

**参考回答**：

覆盖索引是指索引本身包含了查询所需的所有字段，而不需要通过回表（即查询主键）来获取额外的数据。当一个查询仅通过索引就能满足所有需要的字段时，就称之为覆盖索引。覆盖索引对性能有积极的影响，原因如下：

1. **减少I/O操作**：覆盖索引能够减少I/O操作，因为不需要去访问实际的数据行，索引通常存储在内存中，而实际的数据行可能需要从磁盘读取。通过只读取索引，可以减少对磁盘的I/O操作，提高查询速度。
2. **减少网络传输**：如果查询的数据可以完全由索引提供，那么在查询的过程中需要传输的数据量会减少，这对于分布式系统中的网络开销尤为重要。
3. **减少CPU开销**：数据库系统在查询时需要进行解析和处理数据，覆盖索引减少了这些处理的工作量，从而减少了CPU的开销。
4. **提高查询性能**：由于覆盖索引能够减少I/O操作、网络传输和CPU开销，整体上提高了查询性能，特别是对于频繁执行的查询，性能的提升尤为显著。

覆盖索引的效果在于最大限度地减少了从存储引擎中检索数据所需的工作，将所需的数据都存储在索引中。这使得覆盖索引成为优化查询性能的一种重要手段。在设计数据库索引时，考虑覆盖索引对于提升查询性能的影响是一个常用的优化策略。

## 20. MongoDB中的数据复制是如何工作的？

> 原题 ID：`q1039`

**高频程度**：★★★

**考察点**：考察 oplog 机制驱动的异步复制原理与选举触发。

**回答框架**：

①写入路径：所有写先到 Primary。②oplog：Primary 把写操作记录到 oplog 这个特殊集合。③同步：Secondary 长连接拉取 oplog 并回放，实现异步复制。④延迟与选举：复制存在延迟，Primary 故障时按优先级和最新数据触发选举。

**参考回答**：

MongoDB中的数据复制是通过复制集（Replica Set）来实现的。复制集是一组维护相同数据集的MongoDB服务器的集群，其中包括一个主节点（Primary）和一个或多个从节点（Secondary）。

数据复制的工作原理如下：

1. **主节点写入**：所有的写操作都首先在主节点上执行。
2. **Oplog（操作日志）**：主节点会将所有的写操作记录在一个特殊的集合中，这个集合叫做Oplog（操作日志）。Oplog保存了一份主节点上的所有写操作的记录。
3. **从节点同步**：从节点通过长时间保持与主节点的TCP连接，实时复制主节点上的Oplog。从节点不仅复制写操作，还复制删除和更新操作，以确保数据的一致性。
4. **数据复制延迟**：从节点复制Oplog的过程可能存在一定的延迟，导致从节点上的数据稍微滞后于主节点。这个延迟通常是可配置的。
5. **选举新的主节点**：如果主节点发生故障，复制集会在从节点中选择一个新的主节点。这个过程通常是自动的，复制集中的成员会根据配置中的优先级、可用性等条件选择新的主节点。

通过这种方式，MongoDB的复制集提供了数据冗余、高可用性和故障恢复的功能。当主节点发生故障时，系统可以迅速切换到一个可用的从节点，确保服务的持续可用。

1. **检测主节点不可用**：复制集中的成员（主节点和从节点）之间会保持心跳，检测彼此的可用性。如果主节点不可用，其他成员会察觉到这一情况。
2. **触发选举过程**：当其他成员检测到主节点不可用时，它们会触发选举过程，以选择新的主节点。这个过程通常是自动的，系统会自动启动选举过程。
3. **选举新的主节点**：复制集中的成员参与选举，通过相互通信进行投票，成员需要达到一定的多数派（majority）来确保选举成功。通常，具有较高优先级、可用性的从节点有更大的机会成为新的主节点。
4. **更新配置**：一旦新的主节点选举成功，其他成员将更新其配置以指向新的主节点。这个过程是自动的，不需要手动干预。
5. **系统切换到新的主节点**：客户端和其他部署在系统上的组件将开始将写操作发送到新的主节点。这样，系统在主节点故障后能够继续提供服务。

MongoDB的复制集使用了这样的机制，以确保在主节点故障时能够快速、可靠地切换到一个可用的从节点，从而保证系统的高可用性和持续可用服务。
