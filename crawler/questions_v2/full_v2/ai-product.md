## 1. 在线 AI 产品的典型架构是什么？如何兼顾延迟、成本、稳定性与可观测性？

> 原题 ID：`q2008`

**高频程度**：★★★★

**考察点**：能否把在线 AI 产品理解为『模型 + 工程化服务』，说清分层架构与延迟、成本、稳定性三条主线。

**回答框架**：

定义：把训练好的模型封装成可扩展、低延迟、可计费、可观测的在线服务，链路是接入→预处理→推理→后处理→返回。
架构分层：接入层（鉴权/限流/配额/计费）、应用层（会话/Prompt/RAG/工具调用）、模型服务层（vLLM/TGI/Triton）、数据缓存层、基础设施层。
延迟：区分 TTFT 与 TPOT，用流式输出、continuous batching、PagedAttention、投机解码优化。
成本：按 token 计费，用批处理提 GPU 利用率，用蒸馏/量化/小模型路由降单次成本。
稳定性：限流、降级、重试、熔断、多模型 fallback。
可观测与合规：请求日志、token 用量、延迟分布、A/B 测试，以及内容审核和 Prompt 注入防护。

**参考回答**：

在线AI产品本质是「模型+工程化服务」：把训练好的模型封装成可扩展、低延迟、可计费、可观测的在线API/应用，核心链路是请求接入→预处理→推理→后处理→返回，并围绕成本、延迟、稳定性做工程优化。

在线AI产品可以类比成一家餐厅：模型是后厨的厨师，推理服务是厨房流水线，网关是前台点单，缓存/批处理是提前备菜，监控是店长巡店。

1) 整体架构分层：
- 接入层：API网关/负载均衡，负责鉴权、限流、配额、计费、路由。
- 应用层：业务逻辑，如会话管理、Prompt模板、RAG检索、工具调用（Function Calling）、多轮上下文拼接。
- 模型服务层：模型推理服务，通常用Triton、vLLM、TensorRT-LLM、TGI等部署，支持动态批处理、KV Cache、量化。
- 数据与缓存层：向量库、Redis缓存、对象存储、日志。
- 基础设施层：GPU调度、弹性扩缩容、监控告警。

2) 关键工程问题：
- 延迟：首Token延迟（TTFT）和每Token延迟（TPOT）。用流式输出、连续批处理（continuous batching）、PagedAttention、投机解码优化。
- 成本：按Token计费，用批处理提高GPU利用率，用蒸馏/量化/小模型路由降低单次成本。
- 稳定性：限流、降级、重试、熔断、多模型Fallback。
- 可观测：记录请求日志、Token用量、延迟分布、错误率，做A/B测试和效果评估。
- 安全合规：内容审核、Prompt注入防护、数据脱敏、租户隔离。

3) 典型请求流程：用户请求→网关鉴权限流→应用层组装Prompt/检索上下文→推理服务排队批处理→模型生成→流式返回→后处理（审核/格式化）→计费与日志。

4) 适用场景：Chatbot、代码助手、搜索问答、图像生成、语音识别等，凡是需要把模型能力以在线服务形式提供给用户的场景。

**常见追问**：vLLM 的 PagedAttention 和 continuous batching 分别解决什么问题？TTFT 与 TPOT 的优化手段为什么不一样？

## 2. AI 编程普及后，前端与后端的核心差异还体现在哪里？

> 原题 ID：`q2190`

**高频程度**：★★★

**考察点**：能否说清 AI 编程没有消除前后端的本质差异，核心差异在信任边界、状态一致性与交付调试成本。

**回答框架**：

总观点：AI 大幅提升编码效率，但前后端在信任边界、状态持久化、交付风险上的本质区别不会消失，只是从『写代码』转移到『架构与验证』。
运行环境与信任边界：前端跑在用户可控的浏览器，必须假设一切输入不可信；后端是真正的信任边界，鉴权、价格计算、库存扣减不能放前端。
状态与一致性：前端状态是会话级、可丢失的；后端状态持久化、需事务与幂等，涉及并发扣库存只能后端设计。
调试与可观测：前端问题多在兼容/渲染/网络，后端问题多在链路/日志/慢查询/并发。
交付与演进：前端可灰度可回滚，后端涉及数据迁移、接口版本、上下游兼容，变更成本高。
结论：AI 让『写』变快，但『改错』和『兼容』的成本结构没变，定义与验证边界成为更核心的能力。

**参考回答**：

AI 编程能大幅提升编码效率，但前后端的本质差异（运行环境、状态管理、安全边界、调试与交付方式）不会因此消失，AI 只是把差异从“写代码”层面部分转移到了“架构与验证”层面。

先给一个通俗类比：前端像“在别人家里（浏览器）摆家具”，后端像“在自己家仓库里管库存和发货”。AI 可以帮你画图纸、写清单，但“谁的地盘、谁负责什么”不会变。

1) 运行环境与信任边界：前端代码运行在用户可控的浏览器/客户端，代码和接口对用户可见，必须假设一切输入不可信；后端运行在受控服务器，掌握数据库、密钥、权限，是真正的信任边界。AI 生成的前端代码再优雅，也不能把鉴权、价格计算、库存扣减放前端。

2) 状态与一致性：前端状态是“会话级、可丢失”的（刷新即没），后端状态是“持久化、需事务”的（订单、账户）。AI 很擅长写 UI 状态管理，但涉及分布式事务、幂等、并发扣库存时，仍需要后端工程师设计。

3) 调试与可观测性：前端问题多在兼容性、渲染、网络；后端问题多在链路、日志、DB 慢查询、并发。AI 能帮读日志、写单测，但线上排障依赖对系统拓扑和业务语义的理解。

4) 交付与演进：前端交付到 CDN/浏览器，可灰度、可回滚；后端涉及数据迁移、接口版本、上下游兼容，变更成本高。AI 让“写”变快，但“改错”和“兼容”的成本结构没变。

5) 适用场景：AI 对前端样板代码、组件、样式、简单 CRUD 后端收益最大；对复杂领域建模、高并发、安全合规、跨系统一致性，AI 只能辅助，不能替代判断。

结论：AI 编程降低了“编码”门槛，但没有消除前后端在信任边界、状态持久化、交付风险上的本质区别，反而让“谁能定义边界、验证正确性”成为更核心的能力。

**常见追问**：为什么说 AI 生成后端的验证成本明显高于前端？接口契约在 AI 编程时代为什么反而更重要？

## 3. 如何从产品经理视角构建一个可落地的 AI 产品？

> 原题 ID：`q2287`

**高频程度**：★★★

**考察点**：AI 产品经理视角的产品构建方法论，重点是问题定义、数据可行性、评估体系与迭代闭环。

**回答框架**：

从用户痛点出发，先判断 AI 是不是最优解（规则能解决就不必上 AI）。
把问题转化为机器学习任务（分类/回归/生成），评估数据可行性与标注成本。
设计产品原型与人机交互方式，考虑模型不确定性（置信度展示、人工兜底）。
技术方案选型：自研、调 API 还是开源微调，权衡成本、效果与迭代速度。
建立评估体系：离线指标 + 在线指标，通过 A/B 测试验证。
持续迭代：收集反馈形成数据闭环，监控模型衰减，同时关注偏见、隐私、合规等伦理风险。

**参考回答**：

构建AI产品需从用户问题出发，以数据为燃料、模型为引擎、体验为界面，通过迭代闭环持续创造价值。

AI产品经理构建人工智能产品，核心是解决‘用AI做什么’和‘怎么做’的问题。首先，定义用户痛点与价值主张，判断AI是否是最优解（例如，规则引擎能解决就不必用AI）。其次，将问题转化为机器学习任务（分类、回归、生成等），并评估数据可行性：是否有足够高质量数据？标注成本如何？然后，设计产品原型，包括人机交互方式（如推荐、对话、自动化决策），并考虑AI的不确定性（如置信度展示、人工兜底）。

接着，选择技术方案：自研模型、调用API还是开源微调？需权衡成本、效果与迭代速度。之后，建立评估体系：离线指标（准确率、召回率）与在线指标（点击率、留存率），并通过A/B测试验证。

最后，持续迭代：收集用户反馈，形成数据闭环，监控模型衰减，定期更新。

例如，智能客服产品：先分析常见问题，构建意图分类模型，设计对话流程，上线后根据未识别问题优化模型。整个过程需跨团队协作（算法、工程、设计、运营），并关注伦理与合规。

**常见追问**：数据飞轮具体怎么设计出来？冷启动阶段没有标注数据怎么办？

**回答框架**：

- 第一，有明确用户、使用频次和要解决的原流程；

- 第三，有 SLA、监控、告警、成本和容量规划；
- 第四，有离线评测、灰度、人工兜底和 badcase 闭环；

## 6. 如果公司只允许使用私有化模型，你会怎么重新选模型和设计系统？

> 原题 ID：`q3960`

**高频程度**：★★★

**考察点**：考察私有化约束下从能力优先转向可部署可微调可运维的选型与分层解耦能力。

**回答框架**：

①选型四维：许可与合规、部署成本与显存、中文与领域能力、可微调与可迭代。②系统分层：接入层、模型层（vLLM/TGI 多模型路由）、能力层（RAG/Agent 与模型解耦）、数据层、运维层。③关键原则：模型可替换，用统一 OpenAI 兼容接口或内部抽象层。④加分：量化选型、LoRA/QLoRA 微调、内部 golden set 评测、成本核算与安全审计。

**参考回答**：

私有化意味着模型权重、推理服务、数据、日志全部在公司内网或专有云，不能调用外部 API，选型核心从能力最强转为可自主部署、可微调、可运维。

选型按四个维度评估：

- 第一，许可与合规，权重是否允许商用、是否允许微调、有无输出内容责任条款，优先 Apache 2.0、MIT 等宽松许可，避开仅研究许可或带 MAU 限制的模型；
- 第二，部署成本，参数量决定显存，7B、14B、32B、72B 对应单卡到多卡，要按业务 QPS 和延迟预算反推，而不是先选最大模型；
- 第三，中文与领域能力，用公司真实业务集做小规模评测而不是只看公开榜单，私有化场景往往有强领域术语；
- 第四，可微调与可迭代，是否支持 LoRA 和 QLoRA、是否有活跃社区和工具链，决定后续能否用公司数据持续提升。系统设计上分层解耦：接入层做统一网关和鉴权；模型层用 vLLM 或 TGI 等推理框架，支持多模型路由和 A/B；能力层把 RAG、Agent、工具调用与具体模型解耦；数据层做向量库、微调数据管理和脱敏；运维层做 GPU 监控、限流、降级和灰度。关键原则是「模型可替换」，通过统一 OpenAI 兼容接口或内部抽象层，让换模型不改业务代码。加分实践：用 PagedAttention 和连续批处理提升吞吐，量化用 AWQ、GPTQ、GGUF 在精度与显存间权衡；微调优先 LoRA/QLoRA 只训练低秩矩阵，单卡即可迭代；建内部 golden set 覆盖事实性、安全性、格式遵循和拒答率防止换模型后回归；算清每百万 token 的 GPU 折旧加电费，私有化往往固定成本高、边际成本低，适合高并发稳定负载；安全上做输入输出过滤、审计日志和模型水印。

**常见追问**：LoRA 和全参微调各自适合什么场景？私有化下怎么核算推理成本？

## 7. AI 产品的收入与利润通常由哪些业务和技术因素共同决定？

## 8. 如何将 Agent 能力与复杂业务流程结合，形成可度量的产品创新？

> 原题 ID：`q2895`

**高频程度**：★★

**考察点**：考察把 Agent 与业务场景结合、推动模式创新的能力。

**回答框架**：

1) 概念与类比；2) 为什么能带来业务创新；3) 四步落地方法论；4) 人机边界与衡量。

**参考回答**：

Agent 不是把 LLM 包一层，而是用感知-规划-记忆-工具-反思的闭环去接管业务流程中原本靠人串联的环节，从而把卖软件变成卖结果、卖决策，实现业务模式创新。先讲概念：Agent 等于 LLM 大脑加规划加记忆加工具（API、数据库、RPA、代码执行）加反思。类比：传统 SaaS 是给员工一把更好的锤子，Agent 是直接雇一个会自己找锤子、还会换工具的实习生。

为什么能创新：传统软件只能覆盖确定性流程，长尾、跨系统、需要判断的环节必须靠人；Agent 恰好擅长处理非结构化输入加多步决策加跨系统操作，于是可以把过去按人头、按坐席收费的服务，改成按结果收费，比如成功一单、解决一工单，商业模式从 License 转向 Outcome-based。

落地方法论四步：

- 第一，选场景，高频、规则模糊、跨系统、人力成本高、结果可度量，例如保险理赔初审、跨境电商选品投放、供应链异常处理。
- 第二，拆能力，把业务拆成感知（读邮件工单图片）、规划（决定查哪些系统）、执行（调 ERP、CRM、支付 API）、校验（对账、合规）、反思（失败重试或转人工）。
- 第三，设计人机边界，高风险动作如付款、对外承诺必须 Human-in-the-loop 或设金额权限阈值。
- 第四，度量与迭代，定义业务指标（节省工时、转化率、差错率）而非只看模型指标，用真实 badcase 反推能力缺口。关键提醒：不要为了创新而创新，先从确定性流程加 Agent 增强混合起步，再逐步扩大自主范围。

## 9. 如何理解AI Coding中的Vibe Coding？

> 原题 ID：`q1501`

**高频程度**：★★★★

**考察点**：考察对「如何理解AI Coding中的Vibe Coding」的掌握，重点看能否讲清：Vibe Coding（氛围编程）由 Andrej Karpathy 在 2025 年 2 月提出，原话大意是：你完全沉浸在氛围里

**回答框架**：

和 Copilot 式补全不同：补全仍是人主导逐行写，Vibe Coding 是模型主导整块产出。；和 Prompt Engineering 不同：后者偏优化单次输入，Vibe Coding 是一整套‘放手+验收’的协作模式。；和传统 TDD 不同：测试从‘人先写’变成‘可让模型写、人来审’，甚至用测试作为验收闸门。

**参考回答**：

Vibe Coding 是 Karpathy 提出的‘用自然语言描述意图、让 LLM 直接生成可运行代码’的编程范式，核心是把‘写代码’降级为‘表达意图+验收结果’，人从实现者变成意图提供者与结果评审者。

Vibe Coding（氛围编程）由 Andrej Karpathy 在 2025 年 2 月提出，原话大意是：你完全沉浸在氛围里，把想做的事用自然语言告诉模型，接受它给出的代码，不再逐行深究，遇到报错就把错误贴回去让它改。

1) LLM 在大量公开代码上训练，具备从自然语言到代码的强映射能力；
2) 代码是可自动验证的产物——能编译、能跑测试、能看输出，形成‘生成-执行-反馈’闭环；
3) Agent 工具链（文件读写、终端、浏览器、测试运行）让模型能自己迭代，而不只是单轮补全。 典型工作流：描述需求 → 模型生成/修改代码 → 运行 → 把报错或截图回灌 → 模型修复 → 人验收。适合原型、脚本、Demo、个人小工具、UI 快速试错；不适合对正确性、安全性、性能、可维护性要求高的核心系统。 与相关概念的区别：

- 和 Copilot 式补全不同：补全仍是人主导逐行写，Vibe Coding 是模型主导整块产出。
- 和 Prompt Engineering 不同：后者偏优化单次输入，Vibe Coding 是一整套‘放手+验收’的协作模式。
- 和传统 TDD 不同：测试从‘人先写’变成‘可让模型写、人来审’，甚至用测试作为验收闸门。

**常见追问**：如何避免「1) 把 Vibe Coding 等同于‘AI 自动写代码’或‘Copilot 补全’，忽略‘人放弃逐行审查、只做意图与验收’这一核心特征」？ 「2) 认为它适用于所有场景，尤其在生产核心系统、金融/医疗/安全敏感代码上盲目使用」在真实项目中应如何规避？

## 12. 什么是MVP？

> 原题 ID：`q3065`

**高频程度**：★★★

目标用户：明确给谁用。；核心价值假设：用户为什么愿意用，解决什么痛点。；最小功能集：只做能跑通“价值闭环”的功能，砍掉锦上添花。；可度量反馈：能收集留存、转化、付费等数据，用于决策“坚持/转向/放弃”。

**参考回答**：

MVP（最小可行产品）是用最小成本做出能验证核心假设、可交付给真实用户并获取反馈的最简产品版本。

MVP 全称 Minimum Viable Product，最小可行产品。它的核心不是“功能最少”，而是“用最小成本验证最关键的商业/技术假设”。

通俗类比：你想开一家餐厅，不确定顾客喜不喜欢“只卖一道招牌菜”的模式。MVP 不是先租大店面、招厨师、装修，而是先摆一个小吃摊，只卖那道菜，看有没有人买、复购如何。如果没人买，你只损失一个小摊；如果有人排队，再扩大成餐厅。 关键要素：

1. 目标用户：明确给谁用。
2. 核心价值假设：用户为什么愿意用，解决什么痛点。
3. 最小功能集：只做能跑通“价值闭环”的功能，砍掉锦上添花。
4. 可度量反馈：能收集留存、转化、付费等数据，用于决策“坚持/转向/放弃”。 常见形式：落地页、众筹、人工服务（Concierge MVP）、绿野仙踪（Wizard of Oz）、单功能 App、Demo 视频等。

适用场景：创业早期、新产品线、不确定需求时。不适用于需求明确、合规要求高、或核心体验必须完整才能验证的场景。 与原型、POC 的区别：原型验证交互/设计，POC 验证技术可行性，MVP 验证市场与用户价值，必须面向真实用户并产生真实反馈。

**常见追问**：如何避免「把 MVP 等同于“半成品”或“功能少”，忽略验证假设和可度量反馈。」？ 「只做技术 Demo，不给真实用户用，无法验证市场价值。」在真实项目中应如何规避？

## 13. 在你的业务场景里，哪些问题适合用 AI 解决，哪些不适合？

**回答框架**：

在业务里判断一个需求该不该用 AI，我通常用一套‘四象限 + 五问’的方法；一、先看任务本质：AI 擅长的是‘从大量历史数据中学习模糊映射’，也就是输入到输出没有明确规则、但存在统计规律的任务；典型适合：；1) 感知类：图像/语音/视频识别，如质检缺陷检测、OCR、语音转写；2) 自然语言类：文本分类、情感分析、摘要、翻译、知识问答、客服意图识别；3) 预测类：销量预测、流失预测、风控评分、推荐排序

**参考回答**：

判断标准是：任务是否有可学习的模式、容错空间、可接受的成本与延迟，以及错误代价是否可控；有明确规则/强一致性/高代价错误/数据稀缺的场景不适合。

在业务里判断一个需求该不该用 AI，我通常用一套‘四象限 + 五问’的方法。

**一、先看任务本质：**

AI 擅长的是‘从大量历史数据中学习模糊映射’，也就是输入到输出没有明确规则、但存在统计规律的任务。典型适合：

1) 感知类：图像/语音/视频识别，如质检缺陷检测、OCR、语音转写。
2) 自然语言类：文本分类、情感分析、摘要、翻译、知识问答、客服意图识别。
3) 预测类：销量预测、流失预测、风控评分、推荐排序。
4) 生成类：文案生成、代码补全、对话助手、图像生成。
5) 决策辅助：在人类兜底的前提下给出候选方案，如医疗影像初筛、投顾建议草稿。

**二、不适合的场景：**

1) 规则明确且稳定：如税率计算、订单状态流转、权限校验，用 if-else/规则引擎更准、更便宜、可解释。
2) 强一致性/事务性：转账、库存扣减，AI 的概率性输出会破坏 ACID。
3) 错误代价极高且无法兜底：如自动驾驶直接控制、无审核的医疗诊断、法律判决。
4) 数据稀缺或标注成本极高：冷启动业务没有足够样本，模型学不到东西。
5) 需要严格可解释/可审计：如监管要求逐条给出依据，黑盒模型难满足。
6) 投入产出不划算：用 AI 的成本（算力、标注、维护）远高于收益，或延迟要求毫秒级而大模型做不到。

**三、一个通俗类比：**

AI 像‘经验丰富但会犯错的实习生’。适合让他做‘看多了就会’的模糊判断，比如从一堆评论里挑出负面的；不适合让他做‘必须分毫不差’的账房先生，比如算工资。

**四、落地时还要问五个问题：**

1) 有没有足够的历史数据/标注？
2) 错误率降到多少业务能接受？
3) 错了能不能人工兜底或回滚？
4) 延迟、成本、合规是否满足？
5) 有没有更简单的规则/统计基线？先跑基线，AI 只在明显超过基线时才上。

**五、混合架构往往最优：**

规则做硬约束和兜底，AI 做模糊部分，人做最终审核。例如客服：AI 先意图识别和生成草稿，敏感操作走规则，复杂投诉转人工。

**常见追问**：如何避免「1) 认为‘AI 万能’，所有问题都想用大模型，忽略规则引擎和传统统计方法」？ 「2) 只看准确率，不看业务错误代价、延迟、成本、可解释性和合规」在真实项目中应如何规避？

**参考回答**：

先澄清用户真实目标与约束，再谈方案设计，避免解决错误问题。

这道题考察的是需求澄清与问题定义能力。用户提出的往往是‘解决方案’而非‘真实需求’，比如用户说‘帮我做一个导出Excel按钮’，真实需求可能是‘想把数据交给财务对账’，那也许直接对接API或定时邮件更合适。 原理上，这对应‘问题空间 vs 方案空间’：先停留在问题空间，问清谁用、什么场景、要达成什么结果、成功标准是什么、有哪些约束（时间、数据、合规、预算）。

常用方法：5 Whys 追根因、Jobs-to-be-Done 描述用户要完成的‘任务’、用户故事加验收标准。 类比：病人说‘给我开点止痛药’，好医生不会直接开药，而是先问哪里痛、多久了、什么性质，因为可能是阑尾炎。直接开药就是‘直接设计’。

适用场景：需求评审、产品设计、AI Agent 的意图识别、系统架构前的需求分析。做法上先复述确认：‘我理解你想要的是X，对吗？’再给出2-3个可选方案及取舍，让用户选。

**常见追问**：如何避免「常见错误：一上来就画架构、选技术栈」？ 「把用户说的方案当需求」在真实项目中应如何规避？

## 20. 你感觉低代码这个方向：怎么看啊？

> 原题 ID：`q2651`

**高频程度**：★★★

**考察点**：考察对低代码行业方向的辩证判断：价值定位、适用边界与未来趋势。

**回答框架**：

1) 本质是抽象层级提升与研发分工重构；2) 价值在稳定层标准化场景；3) 局限在长尾复杂逻辑、性能与可维护性；4) 趋势是与 AI 生成、专业开发混合开发融合。

**参考回答**：

我的看法是：低代码是把通用能力沉淀为可视化配置、把剩余复杂逻辑留给代码扩展的工程化手段，本质是抽象层级提升和研发分工重构，而不是取代程序员。它出现的原因是数字化需求增速远高于专业开发者供给，大量 CRUD、表单、审批流、报表类系统高度同质化，重复造轮子成本太高。低代码把这些模式沉淀成元数据（Schema 或 DSL），运行时由引擎解释执行，交付周期能从月级压到天级，这部分价值是真实的。

但它的边界也很清楚：

- 一是表达力天花板，真实业务里大量长尾逻辑（跨系统事务、复杂状态机、动态权限、批量计算）一遇到就要开脚本节点和自定义组件，配置里嵌代码、代码里依赖配置，维护成本反而更高；
- 二是平台本身的复杂度转移，调试、性能、版本升级、Schema 兼容性问题会变成新的负担；
- 三是它更适合标准化程度高、变化可枚举的中后台场景，不适合强交互、强实时、极致性能的 C 端页面。

趋势上我认为会往两个方向走：

- 一是和 AI 结合，用自然语言生成 Schema 或直接生成代码，让低代码的输入方式从拖拽变成对话；
- 二是混合开发模式，低代码负责骨架和标准页面，代码负责深度定制，通过出码能力在需要时弹出到源码工程。

所以这是值得投入的方向，但要清醒认识它的适用边界。

**常见追问**：那如果 AI 能直接生成代码，低代码还有存在必要吗？

## 21. 如何评估低代码平台的产品价值、工程质量与可维护性？

> 原题 ID：`q2660`

**高频程度**：★★★★

**考察点**：考察技术项目的价值评估能力：业务价值、工程效率、技术质量与生态可持续性。

**回答框架**：

1) 业务价值指标（交付周期、复用率、非技术人员参与度）；2) 工程效率（搭建耗时、自动化程度、调试回滚）；3) 技术质量（性能、产物质量、稳定性）；4) 可持续性（扩展能力、学习成本、生态）。

**参考回答**：

我会从四个维度评价。

- 第一是业务价值：是否解决目标人群的真实痛点，关键指标包括需求交付周期从多少天缩短到多少天、参与搭建的非技术人员占比、页面和应用的复用率、上线后业务方自主修改的比例。如果这些指标没变好，平台做得再漂亮也是自嗨。
- 第二是工程效率：低代码平台本身是否让开发变快，而不是把复杂度转移。看搭建一个标准页面的平均耗时、从设计到发布的自动化程度、调试与回滚能力、与现有 CI/CD 和监控体系的集成度。
- 第三是技术质量：生成产物的质量如何，包括渲染性能（首屏、交互响应）、包体积、可访问性、产物代码的可读性，以及出码后能否被专业开发接手；还有平台自身的稳定性，比如 Schema 升级的兼容性、大页面拖拽的流畅度。
- 第四是可持续性：平台能否扩展，物料接入和自定义组件的成本高不高，新同学上手要多久，有没有文档和示例，社区或内部使用者是否在增长。反过来说，评价一个低代码项目做得差，典型信号是：只能做 demo 做不了真实业务、复杂场景全靠写脚本、Schema 一升级历史页面就崩、以及业务方仍然要拉开发帮忙改配置。

所以我的结论是，好低代码的判据是在目标场景里真正降低了交付成本，同时没有牺牲可维护性和扩展性。

**常见追问**：那如果业务指标变好了但技术债很重，你会怎么权衡？

## 22. 低代码平台的典型用户有哪些？各自需要哪些能力？

> 原题 ID：`q2734`

**高频程度**：★★★

**考察点**：考察对低代码用户分层与平台定位的理解。

**回答框架**：

1) 业务人员（公民开发者）是核心目标用户；2) 专业开发者做深度扩展与混合开发；3) IT 管理员负责治理、权限与合规；4) 外部伙伴与客户形成生态；5) 判断用户的方法与需求差异。

**参考回答**：

低代码平台的用户通常分四类。

- 第一，业务人员，也叫公民开发者，比如运营、HR、财务、销售，他们最懂业务痛点但不会写代码，低代码让他们用拖拽、表单、流程设计器快速搭建审批、报表、数据收集类应用，类比就像用 PPT 做演示不用学编程，这是低代码最核心的目标人群。
- 第二，专业开发者，他们用低代码做快速原型、内部工具，或者把低代码和代码混合开发，把精力集中在复杂逻辑和系统集成上，对他们来说平台的价值是提效而不是取代。
- 第三，IT 管理员和运维，负责平台治理、权限模型、安全合规、系统集成和监控，他们决定平台能不能在企业里规模化落地，所以平台必须提供租户隔离、审计日志、权限审批、环境和发布管理这些能力。
- 第四，外部伙伴和客户，通过低代码定制或扩展 SaaS 产品，形成生态和二次开发生态，这类用户通常要求开放的插件机制、API 和物料市场。判断用户的方法上，我会看两个维度：一个是技术能力（不会代码、会一点公式、会脚本、会代码），一个是业务所有权（自己就是需求方还是承接别人的需求）。不同人群的产品设计重点完全不同：业务人员需要极简的建模体验和丰富的模板，专业开发者需要代码级扩展和调试能力，管理员需要治理和可观测，忽略了任何一类都会导致平台用得起来但推不开。

**常见追问**：那你会优先服务专业开发者还是业务人员？为什么？
