## 1. 本地缓存与 Redis 组成多级缓存时，如何保持数据同步与最终一致？

> 原题 ID：`q0080`

**高频程度**：★★★★★

**考察点**：本地缓存与 Redis 多级缓存的同步策略、Cache-Aside、延时双删、MQ 广播失效。

**回答框架**：

1）写路径：更新 DB → 删 Redis → 广播失效消息 → 各节点删本地缓存；2）读路径：本地 → Redis → DB，逐级回填；3）防脏读：延时双删应对并发写，或订阅 binlog/CDC 统一失效；4）一致性等级：按业务选最终一致；5）反模式：写时同时双写本地+Redis 而不失效。

**参考回答**：

多级缓存里本地缓存（Caffeine）最快但各实例孤立，和 Redis 的同步我一般这样做。写路径：先更新数据库，再删除 Redis 缓存，然后通过消息队列广播失效消息，各应用节点收到后删除自己的本地缓存；读路径：本地缓存 → Redis → 数据库，逐级回填，回填时给本地缓存设较短 TTL 作为兜底。这里有两个关键点：一是为什么是"删缓存"而不是"更新缓存"，因为并发更新时双写顺序无法保证，容易出现旧值覆盖新值，删除更安全，下次读自然回源；二是怎么防止并发下的脏读，可以用延时双删——写库删缓存后，隔几百毫秒再删一次，把这段时间内被并发读回填的旧值清掉；更彻底的做法是订阅 binlog 或 CDC，由数据变更事件统一驱动各层失效，避免业务代码漏删。一致性等级上，多级缓存一般不追求强一致，按业务接受最终一致即可，关键是失效要快、要全覆盖。最容易踩的坑是写的时候同时更新本地和 Redis 而不失效，一旦其中一台机器更新失败或者广播丢失，脏数据会一直留着。

**常见追问**：1）延时双删的延时怎么定，能彻底解决吗？2）MQ 广播消息丢了怎么办？

## 2. Redis 大 Key 和热 Key 分别怎么处理？

> 原题 ID：`q0087`

**高频程度**：★★★★★

**考察点**：大 Key 与热 Key 的根因区分（体积 vs 频率）、危害与处理手段。

**回答框架**：

1）大 Key：value 过大或集合元素过多，危害是阻塞单线程、过期/删除卡顿、网络包大、迁移慢；处理：结构拆分（大 hash 分桶、大 list 分片）、压缩、异步 unlink、hscan 分批删；2）热 Key：访问集中，危害是单节点打满、读放大；处理：本地缓存短 TTL、key 加随机后缀复制多副本打散、请求合并、限流；3）根因不同处理不同。

**参考回答**：

大 Key 和热 Key 是两类问题，根因不同，一个是体积、一个是频率。大 Key 指 value 过大或集合元素过多，比如一个 100 万字段的 Hash、一个超长的 List。危害有三：Redis 单线程处理时序列化、网络传输会阻塞其他请求；过期和删除时释放内存卡顿；主从同步和集群迁移时会形成大包、迁移慢甚至超时。处理方式是结构拆分，比如把 100 万字段的 Hash 拆成 100 个 1 万字段的子 Hash 用 key 后缀分桶；大 List 分片成多个 key；能压缩就压缩；删除时用 unlink 异步删除，或者用 hscan 渐进式分批删除，避免一次 DEL 卡住。热 Key 指单个 key 的访问量极大，比如秒杀商品、明星微博。危害是压力集中到一个节点，单节点 CPU 或网卡打满，集群里其他节点却很闲。处理方式：客户端加本地缓存并设短 TTL 和随机过期时间，减少回源；把热 key 复制成 N 个副本、key 加随机后缀，把读请求打散到不同节点；入口做请求合并和限流；也可以在 Redis 代理层做统一的多级缓存。所以一句话总结：大 Key 治"拆"，热 Key 治"散"。

**常见追问**：1）怎么发现线上有大 Key 和热 Key？2）集群模式下热 key 打散后怎么写数据？

## 3. Redis所有数据类型的底层实现了解吗？

> 原题 ID：`q0369`

**高频程度**：★★★★

**考察点**：Redis 五大类型在不同规模下的编码（encoding）与底层数据结构。

**回答框架**：

1）String：int / embstr / raw（SDS）；2）List：3.2 前 ziplist+linkedlist，3.2 后 quicklist，7.0 用 listpack；3）Hash：ziplist/listpack 或 hashtable；4）Set：intset 或 hashtable；5）ZSet：ziplist/listpack 或 skiplist+字典；6）编码随数据规模自动转换，目的是省内存或提性能。

**参考回答**：

Redis 每种数据类型都会根据数据规模或特性选择不同的底层编码，可以在内存和性能之间做平衡。String 有三种编码：存整数时用 int；短字符串（44 字节以内）用 embstr，内存连续分配减少碎片；长字符串用 raw，底层是 SDS，能 O(1) 取长度且二进制安全。List 的演进最有代表性：3.2 之前是元素少用 ziplist、元素多用 linkedlist；3.2 到 6.2 统一用 quicklist，即双向链表加 ziplist，兼顾内存和操作效率；7.0 之后把 ziplist 换成了更省内存的 listpack。Hash 在小数据量时用 ziplist/listpack，超过阈值转 hashtable。Set 在元素全是整数且数量少时用 intset，否则用 hashtable。ZSet 元素少且成员短时用 ziplist/listpack，否则用 skiplist 加字典的组合。核心理解是：小规模用紧凑的连续内存结构省内存，规模变大后为了性能切换到哈希表或跳表，切换阈值由配置决定，比如 hash-max-listpack-entries、zset-max-listpack-entries。

**常见追问**：1）ziplist 和 listpack 的区别是什么？2）编码转换是单向的吗，会转回来吗？

## 4. 什么是Redis？

> 原题 ID：`q0370`

**高频程度**：★★

**考察点**：Redis 的定义（Remote Dictionary Server）、支持的数据结构与功能特性。

**回答框架**：

1）全称 Remote Dictionary Server，基于内存的 KV 存储；2）数据结构：String/List/Hash/Set/ZSet，扩展 Bitmap/HyperLogLog/GEO/Stream；3）定位：可作数据库、缓存、消息中间件；4）内置能力：复制、Lua 脚本、LRU 淘汰、事务、持久化；5）高可用：哨兵与 Cluster。

**参考回答**：

Redis 全称是 Remote Dictionary Server，也就是远程字典服务。它是一个基于内存、支持多种数据结构的存储系统，可以当数据库、缓存，也可以当消息中间件用。核心数据结构有五类：字符串 String、哈希 Hash、列表 List、集合 Set、有序集合 ZSet；此外还支持 Bitmap 位图、HyperLogLog 基数统计、GEO 地理空间索引和 Stream 消息流。功能上内置了复制 Replication、Lua 脚本、LRU 驱动的内存淘汰、事务 Transactions 和不同级别的磁盘持久化 RDB/AOF；高可用方面通过哨兵 Sentinel 和集群 Cluster 保证。它的定位可以理解成"把常用数据放在内存里的瑞士军刀"：单线程处理命令所以命令天然原子、延迟低，但内存贵、容量有限，所以典型用法是 MySQL 存权威数据、Redis 扛热点读和计数、锁、排行榜这类场景。

## 5. 为什么用Redis作为MySQL的缓存？

> 原题 ID：`q0372`

**高频程度**：★★★★

**考察点**：用 Redis 做 MySQL 缓存的原因、内存 vs 磁盘 IO、QPS 提升与一致性问题。

**回答框架**：

1）MySQL 数据在磁盘，查询要走磁盘 IO，复杂查询代价高；2）Redis 数据在内存，微秒级返回，避免磁盘 IO；3）缓存热点数据能显著提升 QPS、降低 DB 压力；4）代价与风险：一致性、缓存穿透击穿雪崩、内存成本；5）典型架构：Cache-Aside，读多写少场景收益最大。

**参考回答**：

用 Redis 做 MySQL 缓存的核心原因是访问介质不同：MySQL 是数据库系统，数据落盘，一次查询要走磁盘 IO，还涉及解析、优化、加锁、事务等开销，复杂查询可能几十毫秒；Redis 数据在内存，一次读取是微秒级，直接跳过磁盘 IO，所以把热点数据放到 Redis 能显著提升响应速度和系统 QPS，同时把大量读请求从数据库挡掉，减轻 MySQL 压力，给数据库留出处理写入的能力。典型的读写路径是 Cache-Aside：读请求先查 Redis，命中直接返回，未命中回源 MySQL 再回填并设 TTL；写请求先更新 MySQL 再删除 Redis 缓存。这套组合特别适合读多写少、能容忍短暂不一致的业务，比如商品详情、用户资料。但也要讲清代价和风险：会引入缓存与数据库的一致性问题，需要处理缓存穿透、击穿、雪崩，内存成本比磁盘高，还增加了一层需要运维的组件。所以适用边界是"热点、可容忍最终一致、读远多于写"的数据，强一致的核心资产仍然以 MySQL 为准。

**常见追问**：1）为什么是删除缓存而不是更新缓存？2）什么样的数据不适合放缓存？

## 6. Redis 常用的业务场景有哪些？

**回答框架**：

1）热点数据缓存；2）限时业务：expire 做验证码、优惠活动；3）分布式锁：SET NX EX、Lua 释放；4）计数器：INCR/INCRBY 原子递增，用于秒杀、限流、序列号；5）排行榜：ZSet；6）消息队列：List 的 push/pop 或 Stream；7）会话与去重：Set、Bitmap、HyperLogLog。

## 7. Redis如何保证访问安全？

> 原题 ID：`q0374`

**高频程度**：★★

**考察点**：Redis 访问安全措施：密码认证、绑定 IP、TLS、防火墙、ACL、保护模式与危险命令禁用。

**回答框架**：

1）requirepass 设置密码认证，客户端 AUTH；2）bind 绑定内网 IP，不暴露公网；3）TLS 加密通信；4）防火墙/安全组限制来源；5）Redis 6+ ACL 做细粒度用户与命令权限；6）禁 rename 危险命令（FLUSHALL、KEYS、CONFIG）、开启 protected-mode。

**参考回答**：

Redis 的访问安全我会从网络、认证、权限、加密四层来做。第一，网络层：用 bind 绑定内网地址，绝不把 6379 暴露到公网，再用防火墙或安全组只放通应用服务器的来源 IP，这是最重要的，历史上大量 Redis 被入侵都是因为公网裸奔。第二，认证：在 redis.conf 里设置 requirepass 开启密码认证，客户端连接后用 AUTH 提供密码；注意密码在配置文件里是明文，要控制文件权限。第三，权限：Redis 6 之前只有单一密码，6 之后有 ACL，可以为不同应用创建用户，限制可执行的命令和可访问的 key 前缀，做到最小权限；同时用 rename-command 禁用或改名 FLUSHALL、FLUSHDB、KEYS、CONFIG 等危险命令。第四，加密：跨网络或跨机房访问时启用 TLS。另外建议开启 protected-mode，配合监控审计和定期漏洞修复。原则上是"不暴露、强认证、最小权限、可审计"。

**常见追问**：1）为什么说 bind 和防火墙比密码更重要？2）ACL 怎么限制一个用户只能读某些前缀的 key？

## 8. Redis 的数据类型有哪些？

## 9. Set一个已有的数据会发生什么？

> 原题 ID：`q0377`

**高频程度**：★★★

**考察点**：SET 命令覆盖已有 key 的三种效果：覆盖值、擦除过期时间、可以覆盖不同类型。

**回答框架**：

1）覆盖原有值，旧值直接丢弃；2）擦除原有 TTL，key 变回永久；3）可以跨类型覆盖（List 被 String 覆盖），等价于隐式 DEL 再 SET；4）例外：不带 KEEPTTL 时过期时间清空，SET ... KEEPTTL 可保留；5）实践：改值想保留 TTL 要用 SET KEEPTTL 或 SETEX。

**参考回答**：

对一个已存在的 key 执行 SET，会发生三件事。第一，覆盖原有值，旧的内容直接丢弃，不管原来是什么内容。第二，擦除过期时间，原来设置的 TTL 会被清掉，key 变成永久有效；这一点经常踩坑，比如本来给缓存设了 60 秒过期，代码里用 SET 更新值后 TTL 没了，导致数据永不失效。Redis 6.0 之后可以用 SET key value KEEPTTL 来保留原有过期时间，或者直接用 SETEX/带 EX 参数重新设置。第三，可以跨类型覆盖，比如原来 mylist 是个列表，直接 SET mylist abc 会把列表干掉变成字符串，语义上等价于先隐式删除（DEL 或 unlink）再 SET，因为 Redis 的 key 是统一的命名空间，类型只体现在 value 上。所以实践建议是：更新缓存值时要显式带上过期时间，或者用 KEEPTTL，避免意外产生永久 key。

**常见追问**：1）KEEPTTL 和 SETEX 该用哪个？2）不同类型覆盖会有性能问题吗？

## 10. 浮点型在String是用什么表示？

**高频程度**：★★

**考察点**：浮点数在 String 中的存储方式：转字符串后按长度选 embstr 或 raw。

**回答框架**：

1）浮点数先转成字符串，再作为 SDS 存储；2）编码取决于转换后的字符串长度：≤44 字节用 embstr，>44 字节用 raw；3）44 字节阈值来自 jemalloc 64 字节分配档与 redisObject 开销；4）所以浮点不是原生存储，INCR 会报错，要用 INCRBYFLOAT。

**参考回答**：

Redis 的 String 保存的是二进制安全字节序列；当内容可解析为整数时，内部可能使用整数编码，其他数值通常仍以字符串表示。`INCRBYFLOAT` 由 Redis 按其数值语义解析和格式化，客户端不应把它等同于某一种固定的 IEEE 754 内存布局。

涉及金额、精确计数或跨系统对账时，应明确小数精度和舍入规则，常见做法是使用最小货币单位的整数或固定精度 decimal 方案，而不是依赖浮点字符串的显示结果。

**常见追问**：为什么金额累计通常更适合以分为单位的整数保存？

## 11. Redis String 的内存占用为何与版本、位宽和分配器有关？如何正确评估？

> 原题 ID：`q0380`

**高频程度**：★★★

**考察点**：String 的三种编码 INT / EMBSTR / RAW 及其转换条件。

**回答框架**：

1）INT：能用 long 表示的整数，直接存数值；2）EMBSTR：字符串长度 ≤44 字节，一次内存分配、只读；3）RAW：长度 >44 字节，两次分配，修改会原地更新；4）转换：EMBSTR 修改后变 RAW，append 超阈值也转 RAW；5）目的：省内存、减少碎片。

**参考回答**：

Redis String 的实际内存占用取决于 Redis 版本、对象编码、64/32 位构建、jemalloc 等分配器、键名长度和过期元数据。网上常见的“44 字节”只是在特定旧版本、64 位和特定分配器下的示例，不能当作所有实例的固定结论。

容量规划应在目标版本和真实 key/value 分布上测量，例如采样使用 `MEMORY USAGE key`、`MEMORY STATS`、RDB/AOF 大小和业务指标；同时考虑小对象分配粒度、哈希表负载、复制缓冲和碎片率。

**常见追问**：为什么仅按 value 的字节长度估算 Redis 内存，往往会低估实际占用？

## 12. SDS有什么用？

> 原题 ID：`q0383`

**高频程度**：★★★★

**考察点**：SDS 相对 C 字符串的三大优势：O(1) 取长度、预留空间减少重分配、二进制安全。

**回答框架**：

1）O(1) 长度：SDS 有 len 字段，C 字符串要 O(n) 遍历；2）空间预分配与惰性释放：扩容时多分配、缩容时不立即回收，减少内存重分配；3）二进制安全：以 len 判断结束而非 \0，可存任意二进制；4）避免缓冲区溢出：扩容前检查容量；5）兼容 C 字符串函数。

**参考回答**：

SDS 是简单动态字符串，是 Redis 自己实现的字符串结构，相比 C 原生字符串有三大优势。第一，O(1) 获取长度：SDS 结构里有 len 字段记录已使用长度，取长度直接读字段；C 字符串要靠 strlen 遍历到 \0，是 O(n)，而 Redis 里取长度是很高频的操作。第二，有预留空间，减少内存重分配：扩容时 SDS 会按策略多分配一些（比如小于 1MB 时翻倍），缩容时不立即释放多余空间而是保留下来复用；C 字符串每次修改都要重新分配，代价大。第三，二进制安全：SDS 用 len 字段判断字符串结束，而不是以 \0 作为终止符，所以可以安全存储包含 \0 的二进制数据，比如图片、序列化后的对象、protobuf 字节流；C 字符串遇到 \0 就截断了。此外 SDS 在拼接前会检查剩余容量，避免 C 字符串那种缓冲区溢出问题，同时它仍然以 \0 结尾，可以直接复用一部分 C 字符串函数。这几条让它既有性能又有安全性。

**常见追问**：1）SDS 扩容的预分配策略具体是什么？2）为什么说 C 字符串不二进制安全？

## 13. List是完全先进先出吗？

> 原题 ID：`q0384`

**高频程度**：★★★

**考察点**：List 是双端操作结构，支持 FIFO 也支持 LIFO。

**回答框架**：

1）List 是双端结构，头尾都能 O(1) 插入删除；2）LPUSH+RPOP 是先进先出（队列）；3）LPUSH+LPOP 是后进先出（栈）；4）LPUSH+LRANGE 取最新 N 条；5）不是严格 FIFO，取决于用哪两端。

**参考回答**：

List 不是完全先进先出的结构，因为它是双端操作对象，头尾两端都支持 O(1) 的插入和删除，所以既能做先进先出也能做后进先出，取决于你用哪两端配合。具体来说：LPUSH 加 RPOP 就是标准队列，先进先出，适合消息队列、任务分发；LPUSH 加 LPOP 就是栈，后进先出，适合撤销、最近浏览这类场景；LPUSH 加 LRANGE 0 N-1 可以取最新插入的 N 条，适合动态列表、最新消息；如果用 RPUSH 加 LRANGE 则是按插入顺序取最早 N 条。时间上头部和尾部操作都是 O(1)，但通过下标访问中间元素是 O(n)，因为之前是 ziplist/quicklist 这类结构，现在是 quicklist，只能遍历。所以回答这题的关键是：List 的语义由"用哪端的命令"决定，它本身是双端结构而不是天生 FIFO。

## 14. List对象底层编码方式是什么？

> 原题 ID：`q0385`

**高频程度**：★★★★

**考察点**：List 编码演进：3.2 前 ziplist/linkedlist，3.2+ quicklist（内部 listpack）。

**回答框架**：

1）3.2 之前：元素少且短用 ziplist，否则 linkedlist；2）3.2 之后统一 quicklist = 双向链表 + ziplist；3）7.0 起 ziplist 被 listpack 取代（quicklist 内部为 listpack）；4）quicklist 兼顾内存紧凑与操作效率，可配置每个节点的大小；5）意义：避免 ziplist 连锁更新和大链表内存碎片。

**参考回答**：

List 的底层编码经历了一次重要演进。Redis 3.2 之前有两种编码：ziplist 用于元素数量较少且每个元素都较短的情况，省内存且内存连续；元素多或元素长时用 linkedlist，即普通双向链表，操作灵活但每个节点都有前后指针、内存碎片多。这两种编码的切换由 list-max-ziplist-size 之类的阈值控制。3.2 之后，List 的编码统一由 quicklist 实现，它本质是一个双向链表，但链表的每个节点是一个 ziplist 而不是单个元素，相当于把"大链表"切成一块块紧凑内存，兼具 ziplist 的省内存和 linkedlist 的快速增删，还能避免单个 ziplist 过大导致的连锁更新问题。到了 Redis 7.0，ziplist 因为存在连锁更新、内存利用率不够好的问题被 listpack 取代，所以现在 List 是 quicklist 加 listpack。这个演进过程的考点是：要能说出"为什么不用纯链表"（内存碎片和指针开销）和"为什么不用单个大 ziplist"（连锁更新、扩容拷贝代价大）。

## 15. ZIPLIST是怎么压缩数据的？

> 原题 ID：`q0386`

**高频程度**：★★★

**考察点**：ziplist 的压缩原理：连续内存、双端链表语义、变长编码。

**回答框架**：

1）一块连续内存，元素紧挨存储，无指针开销；2）语义上是双端链表，可实现前后遍历；3）每个 entry 用变长编码（prevlen/encoding/内容），按数据大小选择最短表示；4）对比普通链表：省指针、省碎片、缓存友好；5）缺点：插入删除可能触发内存移动和连锁更新。

**参考回答**：

ziplist 压缩列表是一块连续的内存空间，所有元素紧挨着存储，其中可以包含多个节点 entry，逻辑上是一个双端链表，但物理上是一整块内存。它省内存的关键在于两点：一是没有指针开销，普通双向链表每个节点都要存前后指针，还分散在不同内存块里造成碎片；ziplist 通过记录上一个节点的长度来实现反向遍历，不需要指针。二是变长编码，每个 entry 由前一个节点的长度、编码字段和实际内容组成，编码字段会根据内容是整数还是字符串、长度是多少，选择最短的表示方式，比如小整数可以直接编码进编码字段，不额外占空间。缺点是插入和删除元素时要移动后面的内存，如果某个 entry 的长度变化跨过了 254 字节的边界，还可能引起后续节点 prevlen 字段扩张，形成连锁更新，这是它后来被 listpack 取代的原因。理解 ziplist 的价值在于：它体现了 Redis"小数据用紧凑结构省内存"的设计哲学，是理解 Hash、List、ZSet 小规模编码的基础。

**常见追问**：1）listpack 怎么解决连锁更新？2）ziplist 适合存多长的元素？

## 16. ZIPLIST下List可以从后往前遍历吗？

> 原题 ID：`q0387`

**高频程度**：★★

**考察点**：ziplist 反向遍历的实现：靠每个节点的 prevlen 字段回退。

**回答框架**：

1）可以反向遍历，因为 List 是双端结构；2）ziplist 每个节点保存了前一个节点的长度（prevlen）；3）用当前节点地址减去 prevlen 得到上一个节点的起始位置；4）因此不需要额外指针；5）代价：prevlen 变化可能触发连锁更新。

**参考回答**：

可以，List 是双端数据结构，无论底层是哪种编码，都必须支持从后往前遍历，否则 LPOP/RPOP 就无法实现。ziplist 的实现方式是利用每个节点保存的 prevlen 字段——它记录了前一个节点的总长度。已知当前节点的起始地址，减去 prevlen 就能算出上一个节点的起始地址，从而一步步往前回退，这样既实现了双端遍历，又不需要像普通链表那样为每个节点存前后指针，省下了内存。表头里还有一个 zltail 字段记录最后一个节点的偏移，所以从尾部开始遍历也可以 O(1) 定位。代价是 prevlen 是变长的：当前一个节点长度小于 254 字节时用 1 字节存，否则用 5 字节，所以一旦某个节点长度增长跨过这个边界，它后面所有节点的 prevlen 都要扩写，这就是连锁更新问题的来源。回答时可以顺带点出这个权衡，体现理解深度。

**常见追问**：1）为什么不用固定长度存 prevlen？2）zltail 字段有什么用？

1）先用哈希函数（SipHash 等）计算 key 的哈希值；2）与哈希掩码 sizemask（表大小 - 1）按位与得到索引；3）要求表大小是 2 的幂，这样取模可以用按位与加速；4）解决冲突用链地址法，新节点插入链表头；5）扩容时表大小为 2 的幂同样保证该计算成立。

**参考回答**：

一个数据在 hashtable 中的存储位置是这样算的：首先通过哈希函数计算 key 的哈希值，Redis 用 SipHash 之类的算法保证分布均匀且抗碰撞；然后把这个哈希值与哈希掩码 sizemask 做按位与运算，得到的结果就是该 key 在桶数组中的索引。这里的 sizemask 等于表大小减一，前提是表大小必须是 2 的幂，这样"哈希值对表大小取模"就等价于"与 sizemask 按位与"，按位与比取模快很多，这是 Redis 优化性能的一个经典技巧，也是为什么扩容时新表大小要取成 2 的幂。如果发生哈希冲突，也就是两个 key 算到同一个索引，Redis 用链地址法解决：多个 entry 挂在同一个桶的链表上，新插入的节点放在链表头部，因为新数据被访问的概率更高（类似 LRU 思想）。查找时要沿链表逐个比较 key。理解这个流程有助于解释为什么哈希表扩容要成倍扩、以及为什么冲突严重时性能会退化。

## 24. HashTable怎么扩容？

> 原题 ID：`q0397`

**高频程度**：★★★★

**考察点**：hashtable 扩容流程：分配 1 号表、渐进式 rehash（rehashidx 推进）、完成后表切换。

**回答框架**：

1）为 1 号表分配空间，大小是第一个大于等于 0 号表大小 × 2 的 2 的幂；2）进入 rehash 状态，rehashidx 从 0 开始；3）每次增删改查都顺带迁移 rehashidx 位置的数据，然后 rehashidx 加 1；4）全部迁移完后把 1 号表设为 0 号表，再新建空白 1 号表；5）渐进式避免一次性迁移阻塞。

**参考回答**：

哈希表的扩容流程是这样的。第一步，程序为 1 号表分配空间，空间大小是第一个大于等于 0 号表大小乘 2 的 2 的幂，也就是翻倍并向上取到 2 的幂，这样保证掩码运算仍然有效。第二步，进入 rehash 进行中状态，标记位 rehashidx 从 0 开始。第三步是渐进式 rehash：不是一次性把所有键值对搬过去，而是在每次对字典执行增删改查操作时，顺带把 rehashidx 位置上的所有数据迁移到 1 号表，然后把 rehashidx 加一；随着字典操作不断执行，最终 0 号表的所有键值对都会被迁移到 1 号表。第四步，迁移完成后，1 号表被设置为 0 号表，然后在 1 号表的位置创建一个新的空白表，rehashidx 置为 -1 表示未在 rehash。为什么要渐进式？因为如果字典很大，一次性迁移会长时间阻塞 Redis 的单线程，导致所有请求卡住，渐进式把开销分摊到每次操作上，保证响应延迟平稳。在 rehash 期间，查找会先查 0 号表再查 1 号表，新增数据则直接写入 1 号表，保证不丢数据。

**常见追问**：1）rehash 期间删除操作怎么处理？2）如果长时间没有操作，rehash 会一直不完成吗？

## 25. HashTable怎么缩容？

> 原题 ID：`q0398`

**高频程度**：★★★

**考察点**：hashtable 缩容流程：1 号表大小为第一个大于等于 used 的 2 的幂，同样渐进式 rehash。

**回答框架**：

1）为 1 号表分配空间，大小是第一个大于等于原表 used 的 2 的幂；2）标记 rehashidx，进入渐进式 rehash；3）每次字典操作迁移 rehashidx 位置的数据并递增；4）迁移完成后 1 号表变 0 号表，再建空白表；5）触发条件：负载因子小于 0.1。

**参考回答**：

哈希表的缩容和扩容流程基本一致，区别在于新表大小的计算方式。第一步，程序为 1 号表分配空间，新表大小是第一个大于等于原表 used（已存储键值对数量）的 2 的幂。比如原来表大小是 1024，删除大量元素后 used 只剩 100，那新表就分配到 128。第二步，进入 rehash 进行中状态，rehashidx 从 0 开始。第三步是渐进式 rehash：每次对字典执行增删改查操作时，顺带把 rehashidx 位置的数据迁移到 1 号表，然后把 rehashidx 加一，随着操作不断执行，最终 0 号表全部迁移完。第四步，1 号表被设置成 0 号表，然后在 1 号表位置新建一个空白表。触发缩容的条件是哈希表的负载因子小于 0.1，也就是 used 除以表大小小于 0.1，说明绝大部分桶都是空的、内存浪费严重。和扩容一样用渐进式 rehash，是为了避免大字典一次性迁移阻塞单线程。这里也体现了一个设计原则：扩容看"挤不挤"，缩容看"空不空"，阈值不对称——扩容在负载因子 1 或 5 时触发，缩容要等到 0.1，避免频繁抖动。

## 26. 什么时候扩容，什么时候缩容？

1）扩容条件一：没有执行 BGSAVE/BGREWRITEAOF 且负载因子 ≥ 1；2）扩容条件二：正在执行 BGSAVE/BGREWRITEAOF 且负载因子 ≥ 5；3）缩容条件：负载因子 < 0.1；4）为什么后台持久化时阈值更高：利用写时复制，减少内存页分裂与额外内存占用；5）负载因子 = used / size。

**回答框架**：

1）ZSet 有两类核心操作：按 member 查 score，按 score 范围/排名查询；2）字典：member→score 映射，单点 O(1)；3）跳表：按 score 有序，支持 ZRANGE/ZRANK/ZRANGEBYSCORE，O(logN)；4）两者共享 member/score 对象，只多指针开销；5）单一结构无法兼顾两类操作。

**参考回答**：

**考察点**：AOF 混合持久化：重写时前半部分写 RDB 格式全量，后续增量仍写 AOF 格式。

**回答框架**：

1）重写时用 RDB 方式把内存数据写入新 AOF 文件开头，格式是 RDB；2）重写期间的增量写命令继续以 AOF 格式追加到新文件；3）最终文件 = RDB 格式全量 + AOF 格式增量；4）收益：恢复速度接近 RDB，数据丢失仍按 AOF 策略；5）配置：aof-use-rdb-preamble，Redis 4.0+ 支持。

**参考回答**：

AOF 混合持久化是在 AOF 重写时把两种格式结合起来。具体流程是：触发 AOF 重写后，Redis 用类似 RDB 的方式把当前内存里的全量数据以 RDB 二进制格式写入新的 AOF 文件的开头部分；而在重写进行期间新到达的写命令，仍然以 AOF 的文本命令格式追加到同一个新文件里。所以重写完成后的新 AOF 文件，就是一个"前半部分是 RDB 格式的全量快照、后半部分是 AOF 格式的增量命令"的混合文件。这样设计的好处有两个：一是恢复速度接近 RDB，因为全量数据是直接按二进制格式加载的，不需要逐条重放命令；二是安全性仍是 AOF 级别，因为增量部分还是按 appendfsync 策略刷盘，最多只丢一个刷盘周期的数据。对比纯 AOF，它解决了恢复慢的问题；对比纯 RDB，它解决了丢失多的问题。配置项是 aof-use-rdb-preamble，Redis 4.0 之后支持并默认开启，是现在推荐的持久化方案。

## 35. 简单描述AOF重写流程？

> 原题 ID：`q0421`

**高频程度**：★★★★

**考察点**：AOF 重写流程：fork 子进程、子进程读内存生成新文件、主进程写重写缓冲区、完成后合并。

**回答框架**：

1）触发重写时主进程 fork 出子进程；2）子进程读取当前 Redis 内存数据，以命令格式写入新 AOF 文件；3）重写期间主进程把新增写命令追加到 AOF 重写缓冲区；4）子进程写完后，主进程通过管道把重写缓冲区数据发给子进程；5）子进程追加到新文件，保证完整性，最后原子替换旧文件。

**参考回答**：

AOF 重写流程是：当重写被触发的那一刻，主进程会 fork 出一个子进程，然后这个子进程读取当前 Redis 数据库里的数据，把每条数据以对应的写命令格式（比如 SET、RPUSH）写入一个新的 AOF 文件。这里的关键点是重写不是重放历史命令，而是根据当前内存数据"反推"出最小命令集，比如对一个 key 反复修改过 100 次，重写后只会生成一条最终值的 SET，这就是文件体积能大幅变小的原因。在子进程工作期间，Redis 仍然继续接收新的写命令，主进程会把这些增量数据同时写入 AOF 重写缓冲区（aof_rewrite_buf）。等子进程把全量数据都写完后，主进程会通过管道把重写缓冲区里的数据发送给子进程，子进程再把这份增量追加到新 AOF 文件末尾。这样新文件就同时包含了重写开始时的全量数据和重写期间的增量数据，是完整的。最后主进程用新文件原子替换旧的 AOF 文件，重写结束。整个过程中只有 fork 那一下和最后的替换是阻塞的，其余都是后台进行，所以对主流程影响可控。

**常见追问**：1）为什么重写不直接重放旧 AOF？2）重写期间如果子进程失败会怎样？

## 36. AOF重写你觉得有什么不足之处么？

> 原题 ID：`q0422`

**高频程度**：★★★

**考察点**：AOF 重写的三类额外开销（CPU、内存、磁盘）与 Redis 7.0 的优化（Multi Part AOF）。

**回答框架**：

1）CPU 开销：主进程写重写缓冲、管道传输、子进程写新文件；2）内存开销：AOF 缓冲与重写缓冲内容重复，浪费一份；3）磁盘开销：重写期间旧 AOF 和新 AOF 同时写，磁盘多占一份；4）Redis 7.0 用 multi-part AOF 优化，重写不再需要额外缓冲区；5）权衡：重写是必要代价，靠控制频率与实例大小缓解。

**参考回答**：

AOF 重写主要有三点不足。第一，额外的 CPU 开销：重写期间主进程要把新的写命令额外写入 AOF 重写缓冲区，还要通过管道把这份数据发送给子进程，子进程还要把这些数据写入新 AOF 日志，这些动作相比正常运行时都是额外的计算和数据搬运。第二，额外的内存开销：重写期间 AOF 缓冲区（写到旧 AOF 的）和 AOF 重写缓冲区（要发给子进程的）里的数据基本是一样的，等于同一份增量数据在内存里存了两份，写入量大时内存占用可观。第三，额外的磁盘开销：重写时 AOF 缓冲要刷入旧的 AOF 日志，AOF 重写缓冲也要刷入新的 AOF 日志，所以磁盘上同一份数据会被写入两次，磁盘带宽和空间都被多占一份。这三点都是重写机制"主进程和子进程并行"这个设计带来的固有代价。Redis 7.0 做了优化，引入了 multi-part AOF，把 AOF 拆成基础文件（base）和多个增量文件（incr），重写期间新产生的增量只写一份、不再需要额外的重写缓冲区和双份磁盘写，从机制上消掉了后两项开销。回答时可以按 CPU、内存、磁盘三个维度组织，最后补充 7.0 的优化，层次很清晰。

**常见追问**：1）multi-part AOF 的文件结构是怎样的？2）重写频率怎么定？

## 37. 介绍下Redis LRU回收算法？

> 原题 ID：`q0427`

**高频程度**：★★★

**考察点**：LRU 的定义与 Redis 的近似 LRU 实现思路。

**回答框架**：

1）LRU = Least Recently Used，最近最少使用，淘汰最久未访问的数据；2）标准 LRU 用哈希表+双向链表，访问时把节点移到表头，淘汰时删表尾；3）Redis 不维护完整链表，而是在 redisObject 里存 24 位 lru 访问时间戳；4）淘汰时随机采样若干 key，挑最久未访问的淘汰；5）3.0 后加淘汰池优化。

**参考回答**：

LRU 是 Least Recently Used 的缩写，也就是最近最少使用，核心思路是记录每个 key 最近一次被访问的时间，淘汰时优先淘汰最久没有被访问到的数据。理论基础是"时间局部性"——刚刚被访问过的数据，接下来很可能还会被访问，而很久没被访问的数据，将来被访问的概率较低。标准的 LRU 实现是哈希表加双向链表：哈希表保证 O(1) 找到节点，双向链表维护访问顺序，每次访问就把节点移到链表头部，淘汰时删除链表尾部。但 Redis 并不是标准的 LRU，因为标准 LRU 需要给每个 key 额外维护链表指针，内存成本大，而且每次访问都要移动节点、还要处理并发。Redis 的做法是近似 LRU：在 redisObject 里用一个 24 位的 lru 字段记录该 key 最后一次被访问的时间戳（实际上是一个全局的 LRU 时钟值），淘汰的时候不遍历所有 key，而是随机采样一批 key，比较它们的 lru 时间戳，挑最旧的淘汰掉；如果淘汰后内存还不够，就继续采样淘汰。3.0 之后还引入了淘汰池，把多次采样中比较旧的候选保留在池子里，进一步提升淘汰的准确性，让近似 LRU 的效果更接近真实 LRU。

**常见追问**：1）为什么不用标准 LRU？2）近似 LRU 的采样数配置是多少？

## 38. Redis LRU算法是标准的吗？为什么不用标准的？

> 原题 ID：`q0428`

**高频程度**：★★★★

**考察点**：近似 LRU 的原因与实现：随机采样 n（默认 5）+ 时间戳比较 + 淘汰池优化。

**回答框架**：

1）标准 LRU 要维护双向链表，内存成本巨大（每个 key 加两个指针）；2）近似做法：随机采样 n 个 key，n 默认 5，淘汰其中最旧的；3）内存不足则继续采样淘汰，反复进行；4）3.0 后加入淘汰池：候选池按空闲时间排序，新采样 key 只有更旧才入池，池满则淘汰最旧；5）效果接近真实 LRU，成本极低。

**参考回答**：

Redis 的 LRU 不是标准 LRU。标准 LRU 需要维护一个全局的双向链表，每个 key 都要额外存前后指针，还要在每次访问时把节点移动到链表头，内存成本和时间开销都很大，对 Redis 这种内存敏感、单线程执行的系统不划算。所以 Redis 采用近似 LRU：淘汰时不做全量排序，而是随机采样 n 个 key，这个采样个数默认是 5，由 maxmemory-samples 配置；然后根据 redisObject 里记录的 lru 时间戳，淘汰掉其中最旧的那一个；如果淘汰后内存还是不足，就继续随机采样、继续淘汰，直到内存降到阈值以下。采样数越大越接近真实 LRU，但 CPU 开销也越大，5 是一个经验上效果不错的平衡点。3.0 之后 Redis 又做了淘汰池优化：维护一个候选池，池里的数据按空闲时间排序。第一次采样的 key 都会放进去，淘汰掉最久未访问的；后续每次随机采样的 key，只有它的空闲时间大于池中空闲时间最小的那个 key 时才会入池，池子满了就淘汰池中空闲时间最大的（也就是最旧的）。这样相当于用很小的内存保留了一批"更值得淘汰"的候选，让近似 LRU 的效果更接近真实 LRU，尤其在内存压力大时表现明显更好。

**常见追问**：1）采样数调大有什么影响？2）淘汰池的大小是多少？

## 39. 什么是LFU算法，为什么Redis要引入LFU算法？

> 原题 ID：`q0429`

**高频程度**：★★★★

**考察点**：LFU 的定义、与 LRU 的差异（频率 vs 时间）、以及引入原因与计数衰减机制。

**回答框架**：

1）LFU = Least Frequently Used，最不经常使用；2）同时记录访问计数和上一次访问时间；3）计数增长受访问频率影响，且会随时间衰减（对数递增 + 定期衰减）；4）解决 LRU 的痛点：偶发批量访问把热点数据挤出去；5）适用：热点集中、访问分布长尾的场景。

**参考回答**：

LFU 是 Least Frequently Used，也就是最不经常使用，它在淘汰判断里把"访问频率"作为主要因素。具体实现上，LFU 同时记录了上一次访问时间和访问计数：lru 字段被拆成两部分，高 16 位存上次访问时间、低 8 位存访问次数，所以计数最大是 255。访问计数不是简单加一，而是概率性递增——计数越小越容易加，越大越难加，这样能避免老热点长期霸榜；同时计数还会随时间衰减，每隔一段时间（默认 1 分钟）按配置的衰减因子减少，让"曾经热但现在不热"的数据有机会被淘汰。为什么要引入 LFU？因为 LRU 只看"最近有没有被访问"，存在一个典型问题：一次偶发的批量操作或全表扫描式访问，会把大量冷数据标记成"刚访问过"，从而把真正的热点数据挤出内存，后续热点请求全部回源，造成雪崩式压力。LFU 因为看的是访问频率，偶发的一次访问不会显著提升计数，所以更稳。LFU 特别适合热点集中、访问分布是长尾的场景，比如只有少数几个商品被反复访问；如果访问分布本身均匀，LRU 和 LFU 差别不大。使用 LFU 要求 maxmemory-policy 配成 allkeys-lfu 或 volatile-lfu。

**常见追问**：1）LFU 计数为什么设计成 8 位、上限 255？2）衰减机制具体是怎么做的？

## 41. Redis缓存是如何应用的？

> 原题 ID：`q0431`

**高频程度**：★★★

**考察点**：旁路缓存（Cache-Aside）的读路径：先查缓存，未命中查库并回填。

**回答框架**：

1）读：先查 Redis，命中返回；2）未命中回源 MySQL 查询；3）查到结果写回 Redis 并设置 TTL；4）查不到时可写空值或短 TTL 防穿透；5）写：更新 DB 后删除缓存（而非更新缓存）。

**参考回答**：

我们的缓存用的是旁路缓存模式（Cache-Aside），在订单项目里的读路径是：请求进来先查 Redis，如果命中就直接返回，不再访问数据库；如果没查到，就去查 MySQL，把查到的数据写回 Redis 并设置一个过期时间，下次同样的请求就能命中缓存。这里有几个细节：第一，写回缓存时一定要设 TTL，作为一致性和内存的兜底，防止缓存永远不更新或者冷数据长期占用内存。第二，如果数据库也查不到，通常有两种处理，要么直接返回空不写缓存（可能被反复穿透），要么写一个带短 TTL 的空值占位，防止缓存穿透，具体看业务对一致性的要求。第三，写路径不是"更新缓存"而是"删除缓存"，也就是先更新数据库、再删掉 Redis 里的 key，让下次读自然回源重建；之所以是删除而不是更新，是因为并发下双写的顺序没法保证，容易旧值覆盖新值，删除更安全。整体上旁路缓存的优点是实现简单、只缓存实际被访问的数据、对强一致要求不高时性能收益很大；代价是要自己处理一致性和缓存异常。

**常见追问**：1）为什么不在写的时候直接更新缓存？2）缓存和数据库都没查到该怎么处理？

## 42. Redis做秒杀场景可以吗？讲讲思路？

> 原题 ID：`q0434`

**高频程度**：★★★

**考察点**：Redis 做秒杀的思路：库存预热到 Redis、原子扣减、异步落库、可靠性与限流。

**回答框架**：

1）库存预热：活动前把库存写入 Redis；2）扣减：用 Lua 脚本或 DECR 保证原子性，库存不足直接返回；3）结果异步落库：扣减成功后发 MQ 异步创建订单，削峰；4）防超卖：Lua 里判断库存再扣，单线程保证原子；5）限流与防刷：网关限流、一人一单、令牌桶；6）高可用：主从+哨兵或 Cluster，多节点分摊。

**参考回答**：

可以用 Redis 做秒杀的核心链路，思路是"Redis 扛并发扣减、数据库只做异步落地"。第一步，活动开始前把商品库存预热到 Redis，比如一个 key 存剩余库存。第二步，请求到达时用 Lua 脚本做原子扣减：脚本里先判断库存是否大于 0，大于才执行 DECR 并返回成功，否则直接返回售罄，脚本在 Redis 里是原子执行的，所以不会超卖，这是最关键的一步。也可以用 DECR，但 DECR 返回负数时还要再回补，不如 Lua 一次判断干净。第三步，扣减成功的请求不直接写数据库，而是发一条消息到 MQ 异步创建订单和扣减数据库库存，这样把数据库从瞬时高并发中解放出来，实现削峰。第四步，做防刷和限流：网关上做接口限流，业务上做一人一单（用 Set 或 Hash 记录用户是否已购买），防止脚本刷单。第五步是容量和高可用：单节点 Redis 处理六万左右 QPS 问题不大，百万级流量按比例需要多节点分摊，每个节点都要做主从和哨兵或者用集群，避免单点故障。另外要注意，如果对库存准确性要求极高，还需要处理 Redis 扣减成功但 MQ 或落库失败的情况，一般通过本地消息表或事务消息加对账补偿来兜底，保证最终一致。

**常见追问**：1）Redis 扣减成功但订单创建失败怎么办？2）为什么不在 Lua 里直接写数据库？

> 原题 ID：`q0438`

**高频程度**：★★★★

**考察点**：分布式锁 owner（唯一标识）的作用：保证锁的对称性，防止释放别人的锁。

**回答框架**：

1）锁要保证对称性：谁加锁谁释放；2）反例：A 加锁后因业务耗时长或 GC 卡顿导致锁过期，B 拿到锁，A 执行完释放了 B 的锁；3）后果：连锁误删，锁失效，业务互斥被破坏；4）做法：value 存唯一标识（UUID/请求ID），释放时用 Lua 比对再删；5）进阶：看门狗自动续期。

**参考回答**：

引入 owner 也就是唯一标识，是为了保证分布式锁的对称性——谁加的锁只能由谁来释放。假设没有这个机制，会出现这样的问题：服务 A 成功获取到了锁，但由于业务流程比较长，或者发生网络延迟、GC 长时间停顿等原因，锁的 TTL 到期自动释放了，而 A 的业务还在继续执行；这时候服务 B 拿到了同一把锁开始执行临界区，之后 A 执行完业务了，去"释放锁"，实际上删掉的却是 B 持有的锁，于是 B 的锁失效了，其他服务 C 又可以进来，互斥就被彻底破坏了。这就是所谓的连锁误删。所以加锁时需要在 value 里写入一个全局唯一标识，比如 UUID 或者请求 ID，释放时先用 Lua 脚本读取当前锁的 value，判断是不是自己写的，是才删除，不是就什么都不做。因为判断加删除必须是原子的，所以要用 Lua，不能分两条命令做。进一步说，即便用 owner 解决了误删，锁过期和业务未完成的矛盾依然存在，所以生产上常用 Redisson 的看门狗机制，在业务还没执行完时自动给锁续期，避免锁提前失效，同时业务侧也要做好幂等，防止极端情况下重复执行。

**常见追问**：1）锁自动续期有什么风险？2）为什么释放锁必须用 Lua 而不能用 del？

## 44. Redis Lua 脚本能保证何种原子性？边界和风险是什么？

> 原题 ID：`q0439`

**高频程度**：★★★★

**考察点**：Lua 脚本"原子性"的真正来源是 Redis 单线程串行执行，而非 Lua 语言本身。

**回答框架**：

1）Lua 本身不具备原子性；2）Redis 单线程执行命令，脚本整段执行期间不会被打断；3）因此脚本内的多个命令对外表现为一个原子操作；4）注意：脚本内没有回滚，出错也不会撤销已执行的写；5）脚本要避免耗时操作，会阻塞整个实例。

**参考回答**：

严格来说 Lua 本身不具备原子性，Lua 语言层面并没有事务回滚或者隔离保证。我们说用 Lua 保证原子性，是因为 Redis 处理命令是单线程的，一段 Lua 脚本提交给 Redis 后会被当作一个整体执行，执行过程中不会插入其他客户端的请求，所以在别的客户端看来，脚本内的多条命令要么都执行完了、要么还没开始，不会看到中间状态，这就是"原子性"的来源——它其实来自 Redis 的单线程串行执行模型，而不是 Lua 语言的语义。举个我们实际用的例子：释放分布式锁时，需要先 GET 判断 value 是不是自己的，再 DEL 删除，这两步如果分开做，中间可能被其他请求插入；打包进 Lua 后就是原子的。不过有两点必须注意：第一，Lua 脚本没有失败回滚，如果脚本执行到一半报错，前面已经执行的写操作不会撤销，所以脚本逻辑要自己保证正确性，别依赖"出错自动回滚"。第二，脚本执行期间整个 Redis 实例是被独占的，所以脚本里不能有耗时操作（比如大 key 遍历、复杂计算），否则会阻塞所有请求；Redis 也有 lua-time-limit 限制，超过后只会打日志和允许 SCRIPT KILL 中断只读脚本，不会自动终止，所以设计上要保证脚本短小。

**常见追问**：1）Lua 脚本执行中超时会怎样？2）想实现回滚语义该怎么办？

## 45. 布隆过滤器是怎么工作的？

> 原题 ID：`q0443`

**高频程度**：★★★★

**考察点**：布隆过滤器的结构（位图 + N 个哈希函数）、写入与查询流程、特点（误判、不可删除）。

**回答框架**：

1）结构：一个初始全 0 的位图数组加 N 个哈希函数；2）写入：数据经 N 个哈希函数得到 N 个哈希值，对数组长度取模定位，把对应位置置 1；3）查询：同样算出 N 个位置，全为 1 则可能存在，有一个为 0 则一定不存在；4）特点：空间效率极高但存在误判，不支持删除；5）用途：缓存穿透前置拦截、去重。

**参考回答**：

布隆过滤器由两部分组成：一个初始值全为 0 的位图数组，和 N 个相互独立的哈希函数。写入数据时，比如数据库里新增了数据 x，就用 N 个哈希函数分别对 x 做哈希计算得到 N 个哈希值，再把这 N 个哈希值对位图数组的长度取模，得到 N 个下标位置，把这些位置的值都设为 1。举个例子：位图长度 8、3 个哈希函数，数据 x 算出的位置是 1、4、6，就把第 1、4、6 位置为 1。查询数据时，同样用这 N 个哈希函数算出 N 个位置，然后看位图上这些位置是否全为 1：如果有一个位置是 0，说明这个数据一定没有被写入过，也就是一定不存在；如果全部是 1，则说明可能存在——注意是"可能"，因为不同数据算出来的位置可能有重叠，别的数据把这些位置置 1 了，就会出现误判。所以布隆过滤器的两个重要特性是：第一，空间效率极高，用几个 bit 就能表示一个元素，适合海量数据的去重和存在性判断；第二，存在误判但不漏判，不支持删除（把某一位清零会影响其他元素的判断）。针对删除需求，业界有计数布隆过滤器（每个位用计数器实现）等变体。在缓存穿透场景里，它作为前置拦截非常有效：数据库里不存在的 key 直接被布隆过滤器挡掉，不会打到缓存和数据库。

**常见追问**：1）怎么降低布隆过滤器的误判率？2）数据删除后布隆过滤器怎么办？

## 46. Redis 的主从复制模式有什么优缺点？

> 原题 ID：`q0448`

**高频程度**：★★★

**考察点**：主从复制模式的优点（读写分离、读扩展、数据冗余）与缺点（写单点、内存受限、异步丢数据）。

**回答框架**：

1）优点：读写分离提升读吞吐与响应速度；2）数据冗余，从节点可做备份、可分担读；3）缺点：写只能主节点，写能力与内存容量受单机限制；4）主节点单点风险，故障需人工或依赖哨兵；5）异步复制，故障切换可能丢数据；6）扩展性有限，容量瓶颈靠 Cluster 解决。

**参考回答**：

主从复制相对单节点的好处主要有三点。第一，读写分离提升了系统的读吞吐：写操作只在主节点执行，读请求可以分散到多个从节点，读能力随从节点数量线性扩展，网站数据的读取速度和承载能力都明显提高。第二，数据冗余与高可用基础：数据在多个节点上都有副本，从节点可以用于备份、做离线分析，主节点故障时也有数据基础进行恢复和切换。第三，为后续的哨兵和集群模式打基础，是从节点扩容、故障转移的前提。它的缺点也很明确。第一，写能力和内存容量仍然受限于主节点这一个单机，因为所有写都必须在主节点完成，主节点内存满了也没法通过加从节点来解决，写入规模遇到瓶颈。第二，主节点存在单点风险，如果没有哨兵，主节点宕机就意味着写服务不可用，需要人工介入切换。第三，主从之间是异步复制，主节点写完就返回客户端，不等从节点确认，所以主节点故障时，还没有同步到从节点的数据就丢了，这在没有开启 min-replicas-to-write 等参数时是真实存在的风险。第四，从节点太多时主节点的复制压力（网络带宽、CPU）也会增大，一般会有级联复制或限制从节点数量。所以主从复制解决的是"读扩展和冗余"，没解决"写扩展和容量"，后者要交给 Cluster 分片集群。

**常见追问**：1）怎么降低异步复制丢数据的风险？2）主从延迟很大时读从节点会有什么问题？

## 47. 哨兵机制的工作原理？

> 原题 ID：`q0450`

**高频程度**：★★★★

**考察点**：哨兵机制工作原理四步：判活（主观/客观下线）、选 leader、选新主、通知客户端。

**回答框架**：

1）判活：哨兵周期性 PING 主节点，超时先标记主观下线，再询问其他哨兵，达到 quorum 票数标记客观下线；2）选 leader：候选者拉票，每个哨兵一票，过半且超过阈值当选；3）选新主：从从节点中按优先级、复制偏移量、runid 排序选出最优者；4）通知客户端：通过发布订阅推送新主地址，客户端切换；5）此后旧主恢复后降为从节点。

**参考回答**：

哨兵机制的工作原理可以用"判活、投票选 leader、选新主、通知客户端"四步来记。第一步判活：每个哨兵会周期性地给主节点和其他哨兵发送 PING 命令来判断存活——注意 Redis 的心跳用的是 PING 命令而不是传统 TCP 心跳，更贴合自身协议。如果 PING 响应超时，哨兵先把该节点标记为主观下线（主观是因为只是自己认为）；然后它会向其他哨兵询问，如果达到配置的 quorum 数量的哨兵都认为这个主节点下线了，就标记为客观下线，这才算真正认定故障。第二步，投票选 leader：因为哨兵集群里多个哨兵都可能发现故障，需要选一个 leader 来主导故障转移。判断主节点客观下线的哨兵可以成为候选者，候选者向其他哨兵发送命令请求投票，每个哨兵只有一票，可以投给自己或别人，但只有候选者能投给自己；候选者拿到半数以上的赞成票且票数达到配置阈值，就成为 leader。第三步，选新主节点：leader 从剩余的从节点里挑选一个作为新主节点，选择依据一般优先看从节点优先级（replica-priority），优先级相同则比较复制偏移量（offset 越大说明数据越新），再相同就比较 runid 大小，同时会排除网络状态不好、与旧主断开时间过长的节点。第四步，通知客户端：选出新主后，哨兵通过发布订阅机制把新主节点的地址推送给客户端，客户端感知后切换连接；同时把旧主节点降级为从节点，等它恢复后自动作为从节点加入。这个过程实现了无人值守的自动故障转移，是高可用的核心。

**常见追问**：1）quorum 和 majority 有什么区别？2）为什么心跳用 PING 不用 TCP？

## 48. Redis sentinel（哨兵）模式优缺点有哪些？

**高频程度**：★★★

**考察点**：哨兵模式的优点（自动故障转移、高可用）与缺点（主节点单点、切换期不可用、可能丢数据）。

**回答框架**：

1）优点：自动监控与故障转移，无需人工介入，实现高可用；2）客户端可通过哨兵自动感知新主；3）缺点：本质仍是主从，主节点单点写入，容量和写能力受限；4）切换期间有短暂不可用，客户端可能报错重连；5）异步复制导致切换可能丢少量数据；6）哨兵本身需多数派存活，部署建议奇数个。

**参考回答**：

哨兵模式的优点主要是实现了高可用和自动化。它能在主节点故障时自动完成检测、选举和故障转移，不用人工介入，显著缩短故障恢复时间；客户端通过哨兵感知主节点地址变化，也能自动切换，配合起来系统可用性比裸主从高很多；同时哨兵本身是集群部署、多数派决策，避免了单点判断失误。缺点方面：第一，它本质上还是主从模式，数据只有一份主副本，主节点依然是单点写入，写能力和内存容量都受限于单机，哨兵只解决"挂了怎么办"，不解决"装不下怎么办"。第二，主从切换过程存在一段不可用窗口，从发现下线、选举 leader 到选新主、通知客户端，客户端在这期间可能报错或连接失败，需要客户端有重试和容错逻辑。第三，因为主从复制是异步的，切换时还没有同步到从节点的那部分写数据会丢失，对一致性要求高的业务要评估这个风险，也可以用 min-replicas-to-write 参数牺牲一点可用性来降低丢数据概率。第四，哨兵自身需要多数派存活才能完成选举，所以部署上一般用奇数个（3 个或 5 个）并分布在不同故障域，如果哨兵多数派都挂了，故障转移就无法进行。

## 49. 说说 Redis 哈希槽的概念？

> 原题 ID：`q0452`

**高频程度**：★★★★

**考察点**：Redis Cluster 的哈希槽概念：16384 个槽、CRC16 取模定位、节点负责部分槽。

**回答框架**：

1）Cluster 不用一致性哈希，用哈希槽；2）总共 16384（2^14）个槽；3）key 通过 CRC16 校验后对 16384 取模得到槽号；4）每个主节点负责一部分槽，槽可以迁移；5）客户端根据槽路由到对应节点，MOVED/ASK 重定向。

**参考回答**：

Redis Cluster 没有使用一致性哈希，而是引入了哈希槽的概念。整个集群一共有 16384 个哈希槽，也就是 2 的 14 次方。定位一个 key 属于哪个节点的方式是：先对 key 做 CRC16 校验计算出一个 16 位的值，然后用这个值对 16384 取模，得到的结果就是该 key 所属的槽号；集群中每个主节点负责一部分连续的或不连续的槽，比如三个节点就平均分，每个负责 5461 个左右。客户端连接任意一个节点发起请求时，节点会计算 key 的槽号，如果这个槽归自己管就直接处理，不归自己管就返回 MOVED 重定向告诉客户端应该去哪个节点；槽正在迁移过程中则可能返回 ASK。这样做的好处是：第一，分片粒度是槽而不是 key，节点的增删只需要迁移对应的槽，运维更简单；第二，槽和节点的映射关系是全局元数据，集群可以很容易地做再平衡；第三，槽数量远大于节点数量，便于均匀分配和按需倾斜。另外还有一个知识点：如果业务希望某些 key 落在同一个槽，可以用 hash tag，也就是在 key 里用花括号包住的部分来计算 CRC16，比如 user:{1001}:name 和 user:{1001}:age 会被分到同一个槽，这样多 key 操作和事务就能正常执行。

**常见追问**：1）为什么不用一致性哈希？2）hash tag 有什么使用风险？

## 50. Redis Cluster 的 16384 槽位如何工作？它与集群规模有什么关系？

> 原题 ID：`q0453`

**高频程度**：★★★★

**考察点**：哈希槽数 16384 的原因：心跳包大小（位图 2KB vs 8KB）、节点数上限、集群规模与网络开销的权衡。

**回答框架**：

1）心跳携带槽位图，16384 位 = 2KB，若用 65536 则是 8KB；2）槽位图在心跳里频繁传输，2KB 网络开销可接受；3）16384 个节点规模对集群已足够（官方建议不超过 1000 节点）；4）槽位数远大于节点数，便于均匀分配；5）奇数 vs 2 的幂的历史权衡，实际是 2^14 的位图大小与扩容需求平衡的结果。

**参考回答**：

哈希槽是 16384 个，主要有两个考虑。第一，是心跳消息的大小问题。Cluster 节点之间要定期发送心跳包，心跳包里需要带上自己的槽位图，表示"我负责哪些槽"。如果用位图表示，16384 个槽需要 16384 个 bit，也就是 2KB；如果槽数是 65536，位图就变成 8KB。这些心跳消息是周期性、全节点互相发送的，节点数一多，网络开销和内存开销会被放大好几倍，2KB 是作者认为可接受的平衡点。第二，是集群规模的现实考虑。Redis Cluster 官方建议的节点规模上限在 1000 个左右，16384 个槽分配到这些节点上，平均每个节点还有十几个槽，足够做均匀分配和细粒度再平衡；而如果只有几百个节点，65536 个槽完全是浪费，每个槽都要维护元数据、参与迁移计算。另外还有一个历史点和容量判断：哈希槽数量远大于节点数是为了让槽可以作为"最细粒度的迁移单位"，扩容时只需搬一部分槽，而不需要重新分配整个 key 空间。所以结论是 16384 是在"心跳包大小"和"集群可扩展规模"之间权衡出来的经验值，不是理论上唯一正确，而是工程上够用且开销合理。

**常见追问**：1）为什么槽数是 2 的幂？2）超过 1000 个节点会有什么问题？

## 51. Redis SCAN 的遍历保证、重复与新增/删除边界是什么？

> 原题 ID：`q0454`

**高频程度**：★★★★★

**考察点**：KEYS 命令的性能与阻塞问题、生产禁用原因、SCAN 游标替代方案。

**回答框架**：

1）性能问题：KEYS 遍历整个键空间，key 多时非常耗时；2）阻塞问题：单线程执行，期间阻塞所有其他客户端请求；3）生产环境一般直接禁用；4）替代方案 SCAN：游标分批遍历，非阻塞；5）SCAN 参数：MATCH 模式、COUNT 提示、游标 0 开始到 0 结束；6）注意 SCAN 不保证不重复、只保证在遍历期间存在的元素都被返回。

**参考回答**：

KEYS 命令的问题主要有两个。第一是性能问题：KEYS 需要遍历整个 Redis 的键空间，如果 key 数量非常庞大（几十万上百万），遍历过程非常耗时，CPU 时间被大量占用。第二也是更致命的，是阻塞问题：Redis 是单线程处理命令的，KEYS 执行期间会阻塞所有其他客户端对数据库的访问，直到它执行结束，也就是说这期间整个 Redis 几乎停止响应其他请求，会导致服务不可用或响应极慢，所以生产环境一般是禁止使用 KEYS 的，很多公司会在配置里直接用 rename-command 禁掉它。替代方案是 SCAN 命令，它通过游标（cursor）的方式分批遍历 key 空间，每次只返回一小部分，不会长时间阻塞 Redis。用法是 SCAN cursor [MATCH pattern] [COUNT count]，其中 cursor 初始值为 0，每次调用返回一个新游标，直到返回 0 表示遍历完成；MATCH 用模式匹配过滤 key；COUNT 是每次遍历的提示数量，默认 10，调大能加快遍历但会增加单次阻塞时间。使用 SCAN 有个重要特点要注意：它只保证在遍历期间一直存在的元素会被返回，但不能保证不重复返回，也不保证返回严格完整——因为遍历过程中如果发生了 rehash 或数据变更，可能有元素被返回多次或漏掉，所以业务上要容忍重复并做幂等。除了 SCAN，还有 HSCAN、SSCAN、ZSCAN 分别用于遍历 Hash、Set、ZSet 的元素。

**常见追问**：1）SCAN 的 COUNT 调大会有什么影响？2）SCAN 为什么可能返回重复元素？

> 原题 ID：`q0458`

## 56. 什么是延迟双删，用于解决什么问题？

> 原题 ID：`q0459`

**高频程度**：★★★★★

**考察点**：延迟双删的流程、解决的问题（并发回填脏数据、主从延迟回填）、适用场景与局限。

**回答框架**：

1）流程：删除缓存 → 更新数据库 → 延迟一段时间 → 再删缓存；2）解决的问题一：更新前读请求读到旧值并回填缓存导致脏数据长期存在；3）解决的问题二：读写分离下从库延迟，读到旧数据回填缓存；4）延迟时长的选择；5）局限：不能保证强一致，仍需 TTL 兜底，延迟时间难精确。

**参考回答**：

延迟双删是一种解决缓存与数据库一致性问题的策略，专门针对写操作后缓存可能残留脏数据的场景。它的流程是四步：第一步，先删除缓存，让旧数据快速失效，防止在更新过程中被读到；第二步，更新数据库，保证数据持久化；第三步，延迟一段时间，比如几百毫秒，这个延迟是为了等并发读请求的旧值回填完成、或者等主从同步完成；第四步，再删除一次缓存，把这段时间内可能被回填的旧数据清掉。它解决的是两类具体问题。第一类是并发读写导致的脏数据：更新数据库之前，如果有个读请求发现缓存未命中，去数据库读到了旧值，然后回填到缓存；等写操作把数据库更新完之后，缓存里其实还是旧值，而且如果不删就会被长期读到，第二次删除就是清掉它。第二类是主从延迟：读写分离架构下，写走主库、读走从库，主库更新后从库还没同步，此时读请求从从库读到旧数据并回填缓存，第二次删除同样能清掉这个脏值。要注意它的局限：第一，它降低不一致窗口但不能保证强一致，最终还是要靠 TTL 兜底；第二，延迟时间是经验值，太短盖不住并发回填，太长又拖慢一致性，需要结合业务压测确定；第三，第二次删除如果失败，还得靠消息重试或 TTL。所以它适合对一致性有一定要求但能接受短暂不一致的业务，比如订单、支付状态的缓存。

**常见追问**：1）延迟时间怎么确定，有没有更精确的方案？2）双删失败怎么办？

## 57. 如果硬件内存特别大，MySQL 缓存能否替代 redis？

> 原题 ID：`q0486`

**高频程度**：★★★

**考察点**：MySQL 面向磁盘设计 vs Redis 面向内存设计，无法靠加大内存互相替代。

**回答框架**：

1）设计目标不同：MySQL 各模块（buffer pool、日志、事务并发）首要目标是降低 IO 代价，不是降低内存访问代价；2）访问路径：MySQL 查数据要查页、走 B+ 树 O(logN)，Redis 用 Hash 可 O(1)；3）更新开销：MySQL 为保证隔离性要加锁、为持久性要刷 redo/binlog，Redis 更新不加锁、可不持久化；4）结论：内存再大也改变不了架构定位；5）正确姿势：两者协同而非替代。

**参考回答**：

我认为不能替代，关键原因是两者的设计目标根本不同。MySQL 的所有模块，包括 buffer pool、日志技术、事务并发控制，都是面向磁盘页设计的，它的首要目标是降低 IO 代价，而不是降低内存访问代价，所以代码里充满了页管理、刷脏、日志和锁的逻辑；而 Redis 是从头到尾面向内存设计的数据库。具体差异有三点：第一，访问路径不同。MySQL 即使数据都在 buffer pool 里，查询也要先查页、走 B+ 树的搜索过程，时间复杂度是 O(logdN)，还有 SQL 解析、优化器、执行器层层开销；而 Redis 提供多种数据结构，比如 Hash 对象可以 O(1) 直接定位。第二，更新开销不同。MySQL 为了保证事务隔离性必须加锁，为了持久性要刷 redo log 和 binlog，一次更新涉及多个模块；Redis 的更新不需要加锁（单线程天然串行），而且可以选择不持久化，写路径短得多。第三，语义能力不同。Redis 的数据结构和原子命令能直接表达计数、排行、去重、队列等模型，MySQL 要靠 SQL 组合实现且性能差。所以即使 buffer pool 无限大、磁盘 IO 都被缓存掉，MySQL 的架构开销（锁、日志、解析、事务）依然存在，它优化的方向就不是为超高 QPS 的 KV 访问服务的。正确的做法是让两者协同：MySQL 做权威存储和复杂查询，Redis 做热点缓存和高速原子操作。

**常见追问**：1）MySQL 8 的查询缓存和 Redis 缓存有什么区别？2）如果只是简单 KV 场景，能只用 MySQL 吗？

## 58. MySQL事务和Redis事务有什么区别？

> 原题 ID：`q0535`

**高频程度**：★★★★

**考察点**：Redis 事务与 MySQL 事务的区别：原子性（无回滚）、持久性、隔离性、使用方式。

**回答框架**：

1）MySQL 支持完整 ACID；2）Redis 事务不保证原子性：命令执行中途出错不停止不回滚，继续执行剩余命令，可能半成功；3）不保证持久性：RDB/AOF 都不能确保不丢数据；4）隔离性：靠单线程串行执行，而非锁/MVCC；5）命令：MULTI/EXEC/DISCARD/WATCH；6）本质：Redis 事务是"命令打包顺序执行"而非真正的事务。

**参考回答**：

Redis 的 `MULTI`/`EXEC` 会先把命令入队，再在执行阶段连续串行执行，执行期间不会被其他客户端命令穿插。因此它提供了命令序列的隔离执行，但并不等于关系数据库的完整事务。

它没有自动回滚：入队阶段的语法/命令错误会导致 EXEC 失败；执行阶段某条命令的运行时错误会单独返回错误，已经成功的命令不会撤销。需要乐观并发控制时可配合 `WATCH`，需要复杂原子逻辑时可用 Lua/Functions，并仍要设计幂等和错误处理。

**常见追问**：为什么 Redis 事务中一条运行时命令失败后，前面成功命令不会自动回滚？

1）性能提升：MySQL 走磁盘 IO，QPS 几千，Redis 内存单机十万级、亚毫秒，缓存挡住大部分读流量；2）高并发与削峰：秒杀场景做计数器、限流、队列缓冲；3）丰富数据结构：String/Hash/List/Set/ZSet/Bitmap/HLL/GEO/Stream 直接支撑业务模型；4）分布式支撑：会话共享、分布式锁、分布式 ID、消息队列；5）代价：内存成本与一致性复杂度。

**参考回答**：

引入 Redis 主要是为了解决传统数据库在性能、并发和分布式场景下的瓶颈，可以从四个层面讲。第一，性能提升也就是缓存：MySQL 这类关系型数据库数据在磁盘上，一次查询要经过 SQL 解析、优化、磁盘 IO、锁竞争，QPS 通常在几千量级，还容易在热点数据上出现锁和 IO 瓶颈；Redis 数据放内存，单机 QPS 可达十万级、延迟亚毫秒。把热点数据放 Redis，请求先查 Redis，未命中再查库并回写，能挡住 90% 以上的读流量，很好地保护数据库。第二，高并发与削峰：秒杀、抢购这类场景瞬时流量极大，直接打数据库会被压垮，Redis 可以做计数器扣库存、做接口限流、做请求缓冲队列，把瞬时洪峰接住再慢慢消费。第三，丰富的数据结构：String、Hash、List、Set、ZSet、Bitmap、HyperLogLog、GEO、Stream 等，能直接实现排行榜、点赞、去重、签到、附近的人、消息队列这些功能，不用自己造轮子，而且这些操作都是服务端原子的，省掉了应用层的并发控制。第四，分布式场景支撑：分布式系统里多台机器需要共享状态，Redis 可以做 Session 共享、分布式锁、分布式 ID 生成、幂等标记、以及基于 Stream 的异步任务队列。当然引入它也有代价：内存比磁盘贵、容量有限，而且多了一层缓存就带来一致性问题，要考虑穿透、击穿、雪崩和高可用。所以正确的做法是让它承担它擅长的部分——热点、高速、原子的场景，把权威数据留在 MySQL。

**常见追问**：1）什么数据不该放 Redis？2）引入 Redis 后系统复杂度体现在哪？

## 60. 基于 Redis Stream 实现简历分析、知识库向量化等场景的异步（还能解耦，分析和向量化可以使用其他编程语言来做）？

> 原题 ID：`q1973`

**高频程度**：★★★★

**考察点**：Redis Stream 的异步任务架构：XADD 投递、消费者组、XACK 确认、XAUTOCLAIM 重投、多语言消费者解耦。

**回答框架**：

1）原理：Stream 是 5.0 引入的追加式日志，消息有唯一 ID，支持消费者组；2）生产者：落库后 XADD 投递任务并立即返回任务 ID；3）消费者组：XGROUP CREATE 建组，XREADGROUP 消费，XACK 确认，PENDING 列表看未确认；4）容错：消费者宕机用 XAUTOCLAIM/XCLAIM 重投；5）优势：解耦、削峰、消费者可用任意语言实现；6）对比 List：支持多消费组、消息确认与重投，不像 Pub/Sub 会丢离线消息。

**参考回答**：

用 Redis Stream 做简历分析、知识库向量化这类异步任务，核心是把耗时操作从请求链路里剥离出来。原理上，Stream 是 Redis 5.0 引入的追加式日志结构，每条消息有唯一 ID（默认是时间戳加序号），支持消费者组、消息确认和未确认消息重投，比 List 的 LPUSH/BRPOP 更适合做消息队列——因为它支持多个消费者分组消费、支持 XACK 确认和 pending 列表查看、还支持消息重投，而且不像 Pub/Sub 那样消费者离线就丢消息。典型架构是：第一，生产者（比如 Web 后端）收到简历上传或文档后，先落库或存对象存储，然后用 XADD stream * task_type analyze_resume payload '{...}' 投递任务，立刻返回任务 ID，前端通过轮询或 WebSocket 获知进度，请求链路非常短。第二，消费者端用 XGROUP CREATE 创建消费者组，多个消费者用 XREADGROUP 并行消费，处理完用 XACK 确认；因为是消费者组，同一条消息只会被组内一个消费者处理，可以水平扩容消费者。第三，容错处理：用 XPENDING 查看未确认消息，如果某个消费者宕机，它的 pending 消息可以用 XAUTOCLAIM（Redis 6.2+）或 XCLAIM 转移给其他消费者重投，避免任务丢失；业务上还要保证幂等，因为重投可能重复执行。第四，因为消息格式是通用的，消费者可以用任何语言实现——比如用 Python 做向量化、用 Java 做简历解析，天然实现了服务解耦和技术栈解耦。相比专业的 Kafka，Redis Stream 的优势是部署简单、延迟低、和已有的 Redis 复用运维；不足是持久化和堆积能力不如 Kafka，适合中等吞吐、实时性要求高的任务场景。

**常见追问**：1）消费者处理失败后怎么不丢消息？2）Stream 堆积太多内存怎么办？

## 61. Redis 这类缓存和 Caffeine 的区别？

> 原题 ID：`q3395`

**高频程度**：★★★★

**考察点**：Redis（分布式远程缓存）与 Caffeine（进程内本地缓存）在延迟、容量、一致性、可用性、淘汰策略上的对比与多级组合。

**回答框架**：

1）部署形态：Caffeine 进程内、堆内存、纳秒到微秒；Redis 独立服务、走网络、0.1-1ms；2）容量成本：Caffeine 受单机堆限制且加重 GC，Redis 可扩到 TB 级；3）一致性：Caffeine 每 JVM 一份、天然不一致，靠广播失效；Redis 共享存储、多实例读同一份；4）淘汰与结构：Caffeine 用 W-TinyLFU、支持异步刷新；Redis 支持丰富数据结构、持久化、分布式能力；5）实践：多级缓存，Caffeine 挡热读、Redis 做共享层。

**参考回答**：

这两个缓存可以从几个维度对比。第一，部署形态和访问路径：Caffeine 是进程内缓存，直接操作 JVM 堆内存，一次 get 通常是纳秒到微秒级，完全没有网络开销；Redis 是独立的远程服务，客户端通过 TCP 访问，一次 RTT 大约 0.1 到 1 毫秒，跨机房更高。所以延迟上本地缓存比 Redis 快一到三个数量级。第二，容量和成本：Caffeine 受限于单机堆内存，容量有限，而且大量对象常驻堆会加重 GC 压力，尤其大对象、高 QPS 场景容易触发 Full GC 导致长停顿；Redis 容量可以独立扩展，能存 TB 级数据，但需要网络和运维成本。第三，一致性：这是最关键的差异。Caffeine 每个 JVM 一份副本，多实例之间天然不一致，更新只能靠本地失效或广播通知（Redis Pub/Sub、MQ），存在不一致窗口；Redis 是共享存储，多个实例读的是同一份数据，在单 key 维度天然一致。第四，功能和淘汰策略：Caffeine 用 W-TinyLFU 算法，命中率优于朴素 LRU，还支持异步刷新、过期策略丰富；Redis 提供丰富的数据结构、持久化、分布式锁、消息队列等能力，淘汰策略有 LRU/LFU/RANDOM 等。第五，可用性：Caffeine 随应用进程存活，进程挂了缓存就没了，但也不会成为故障点；Redis 是独立组件，需要考虑高可用（主从/哨兵/Cluster），一旦故障可能影响全部实例。所以工程上常见的做法是多级缓存：Caffeine 作为一级挡在前面承接超热数据，Redis 作为二级共享层保证多实例一致和容量扩展，数据库作为最终真相源；写的时候按"更新 DB → 删 Redis → 广播失效本地"来同步，用 TTL 兜底。

**常见追问**：1）多级缓存怎么保证本地缓存及时失效？2）本地缓存放超大对象会有什么问题？

## 62. MySQL 和 Redis 怎么保持数据一致？

> 原题 ID：`q3396`

**高频程度**：★★★★★

**考察点**：MySQL 与 Redis 的一致性方案：Cache-Aside、先更 DB 再删缓存、延迟双删、binlog 订阅、强一致代价。

**回答框架**：

1）前提：MySQL 是真相源，Redis 是缓存副本，一致性指缓存值尽量等于库值；2）为什么难：两个操作无法原子，有失败、并发、延迟；3）方案一：先更新 DB 再删缓存（最常用），删而非更新避免并发覆盖；4）方案二：先删缓存再更新 DB，需延迟双删兜底；5）方案三：Canal 订阅 binlog 异步失效，一致性好但组件多；6）强一致需加锁串行化，代价是并发；7）兜底：TTL。

**参考回答**：

先明确前提：MySQL 和 Redis 通常不是双主写入，而是 MySQL 存全量数据作真相源、Redis 做缓存副本，所谓一致性是指缓存里的值尽量等于 MySQL 的值。为什么难？因为更新 MySQL 和更新 Redis 是两个独立操作，中间可能失败、可能并发、可能延迟，无法像单机事务那样保证原子。常见方案有四类。第一，先更新数据库再删除缓存，也就是 Cache-Aside，这是最常用的做法。读的时候先查缓存，没有就查库并回填；写的时候更新库然后删缓存。为什么删而不是更新缓存？因为并发下两个线程的写顺序无法保证，可能出现旧值后写覆盖新值，而删除只是置为未命中，下次读回源拿的必然是最新值，出错窗口更小。可以用类比理解：MySQL 是账本，Redis 是贴在墙上的便签，改完账本就把便签撕掉，别人要看时重新抄一遍。第二，先删缓存再更新数据库，这种做法的问题是：删完缓存、数据库还没更新时，有读请求进来把旧值回填了缓存，导致脏数据长期存在；所以需要配合延迟双删——更新库后再延迟几百毫秒删一次，清掉并发回填的旧值。第三，订阅 binlog 异步失效，用 Canal 监听 MySQL 变更，通过消息队列广播给各节点删除缓存。这个方案一致性和覆盖面都更好，业务代码也干净，但额外引入 Canal、MQ 和消费服务，运维和排查成本明显上升。第四，如果确实要强一致，只能对读写路径加分布式锁串行化，那并发性能就没了，实际很少这么用。所以我的结论是：一致性不是免费的，要按业务容忍度选等级。绝大多数读多写少的场景（商品、用户资料）用"先更库再删缓存 + TTL 兜底"就够了；对一致性要求高的才上 binlog 订阅；强一致基本不用缓存。另外一定要记得，最终兜底永远是 TTL，它保证即使某次失效失败也能自愈。

**常见追问**：1）为什么"先删缓存再更新 DB"更容易出问题？2）Canal 方案本身有延迟，怎么避免读到旧数据？

## 63. redis的RDB和AOF两种持久化机制的原理，以及他们的适用场景是什么？

> 原题 ID：`q3491`

**高频程度**：★★★★★

**考察点**：RDB/AOF 的原理（快照 vs 追加日志）、fork+写时复制、刷盘策略、优缺点与适用场景、混合持久化。

**回答框架**：

1）RDB：某时刻全量数据二进制快照；触发方式 SAVE/BGSAVE 与 save 配置；核心是 fork+写时复制；优点是恢复快体积小，缺点是两次快照间数据会丢、fork 有开销；2）AOF：追加写命令日志，命令先入 aof_buf 再按 appendfsync 刷盘；优点是最多丢 1 秒（everysec），缺点是文件大恢复慢；3）混合持久化：AOF 文件含 RDB 头，兼顾两者；4）选型：备份与快速重启用 RDB，数据安全用 AOF，生产两者结合。

**参考回答**：

先讲 RDB。RDB 是把某一时刻 Redis 内存中的全部数据以二进制压缩形式写入磁盘，生成 dump.rdb 文件。触发方式有两种：手动命令 SAVE（阻塞主线程，不推荐）和 BGSAVE（fork 子进程写盘，主线程继续服务）；也有配置自动触发，比如 save 900 1 表示 900 秒内至少 1 个 key 变化就触发 BGSAVE。核心原理是 fork 加写时复制（COW）：fork 出的子进程与父进程共享内存页，父进程继续处理写请求时，被修改的页才复制一份，子进程看到的是 fork 那一瞬间的一致快照，因此能相对不阻塞地生成全量快照。优点是文件紧凑、恢复速度快、适合做备份和主从全量同步；缺点是两次快照之间的数据会丢失（可能丢几分钟），而且内存大时 fork 本身会短暂阻塞、写时复制还会带来额外内存占用。 再讲 AOF。AOF 以追加方式记录每一条写命令（RESP 协议的文本），重启时重放这些命令来恢复数据。流程是：写命令先追加到 aof_buf 缓冲区，然后按 appendfsync 策略刷盘——always 每条都 fsync 最安全但最慢，everysec 每秒一次最多丢 1 秒是默认策略，no 交给操作系统。AOF 文件会不断膨胀，所以需要重写：fork 子进程根据当前内存数据反推出最小命令集生成新文件，重写期间的增量写入重写缓冲区，最后合并替换。优点是数据更安全、丢失窗口小、可读性好（文本命令便于排查）；缺点是文件大、恢复慢、刷盘有开销。 适用场景上：RDB 适合做周期性备份、灾难恢复、快速重启、主从全量复制；AOF 适合对数据安全要求高的场景，作为主要恢复手段。生产中通常是两者结合：AOF 保证数据尽量不丢，RDB 用于备份和快速重启。Redis 4.0 之后还有混合持久化，把 AOF 重写后的文件前半部分写成 RDB 格式、后半部分是增量 AOF，兼顾恢复速度和数据安全，是现在比较推荐的方案。

**常见追问**：1）写时复制为什么能保证快照一致性？2）appendfsync everysec 会丢多少数据？

## 64. Jedis、Lettuce、Redisson、Spring Data Redis 的定位与选择是什么？

> 原题 ID：`q3504`

**高频程度**：★★★

**考察点**：Redis 客户端/接口的层次差异：原生命令、客户端封装（Jedis/Lettuce/Redisson/Spring Data Redis）、高级抽象，及连接模型、序列化、阻塞语义。

**回答框架**：

1）三类接口：原生命令接口、客户端封装接口、高级抽象接口（分布式对象）；2）连接模型：Jedis 同步阻塞+连接池；Lettuce 基于 Netty 支持同步/异步/响应式、连接可共享；Redisson 基于 Netty 偏分布式对象；3）序列化：默认 JDK 序列化易乱码体积大，一般换 String/JSON/Protobuf；4）语义差异：阻塞命令、批量 pipeline、事务与 Lua；5）选型：缓存用 Lettuce/Spring Data，分布式锁用 Redisson。

**参考回答**：

Redis 相关接口通常分三层。第一层是原生命令接口，比如 SET、GET、HSET，直接对应 Redis 协议，语义最清晰，但它只有单命令语义，不含连接管理、序列化和重试。第二层是客户端封装接口，比如 Jedis、Lettuce、Redisson、Spring Data Redis，它们在命令之上加了连接池、线程安全、序列化、重试、集群路由等能力。第三层是高级抽象接口，比如 Redisson 的 RLock、RMap、RTopic，把 Redis 能力映射成 Java 并发对象或消息组件，使用体验像本地对象。它们的区别主要体现在几点：一是连接模型，Jedis 是同步阻塞式，每个连接一个线程、通常要配连接池，连接不可共享；Lettuce 基于 Netty，支持同步、异步和响应式调用，连接是线程安全的可以共享，适合高并发；Redisson 也基于 Netty，但更偏分布式对象封装。二是序列化，Spring Data Redis 默认用 JdkSerializationRedisSerializer，容易产生乱码、体积大、还有反序列化安全问题，生产上一般换成 StringRedisSerializer 或 Jackson/Protobuf。三是功能语义，Pipeline 用于批量命令减少 RTT，事务用 MULTI/EXEC，需要原子逻辑用 Lua 脚本，分布式锁用 Redisson 的 RLock；这些在不同客户端里的支持程度和 API 差别很大。四是阻塞和超时语义，BRPOP 这类阻塞命令在不同客户端里的超时处理和连接占用方式不同。选型上，普通缓存读写用 Lettuce 或 Spring Data Redis 就够；需要分布式锁、限流器、延迟队列、布隆过滤器这些高级能力用 Redisson；老项目历史包袱可能还在用 Jedis，但要配好连接池和超时。

**常见追问**：1）Jedis 的连接池配小了会有什么现象？2）Redisson 的锁是怎么实现的？

## 65. Redis 出现热点 Key 时通常有哪些解决方案？

> 原题 ID：`q3555`

**高频程度**：★★★★★

**考察点**：热 Key 的本质（单分片承载超高 QPS）与三层解决方案：本地缓存、读写分离/多副本、key 拆分打散，外加限流与治理。

**回答框架**：

1）本质：Cluster 按 key 分片，同一 key 永远落同一 slot/节点，热 key 把单节点单线程打满，其他节点空闲；2）方案一：应用层本地缓存（Caffeine，短 TTL 1-5 秒）削掉大部分 QPS；3）方案二：读写分离加多副本，读请求分散到从节点（readFrom 策略）；4）方案三：把热 key 拆成多个 key（加随机后缀）分散到不同节点，读时随机取一个；5）方案四：入口限流、请求合并；6）配套：发现手段与监控。

**参考回答**：

先明确问题本质：Redis Cluster 按 key 做 CRC16 分片，同一个 key 永远落在同一个 slot、同一个节点上。所以当某个 key（比如秒杀商品、明星微博、大促爆款）QPS 达到几十万时，压力全部压在单个节点的单线程上，表现为该节点 CPU 打满、其他节点却很闲、延迟飙升，严重时拖垮整个集群。解决方案按成本从低到高有几层。第一，应用层本地缓存：用 Caffeine 或 Guava 在 JVM 里缓存热点数据，设置很短的过期时间，比如 1 到 5 秒，请求先查本地，未命中再查 Redis，这样 Redis 的 QPS 能被削掉 90% 以上。类比是把最常看的书放在自己桌上，而不是每次都去图书馆借。缺点是多实例之间有一致性延迟，适合商品详情、榜单这类对一致性要求不高的场景。第二，读写分离加多副本：主节点负责写，挂多个从节点，客户端通过 Lettuce 或 Jedis 的 readFrom 策略把读请求分发到从节点，把单节点的读压力分散到多台机器上。第三，把热 key 拆成多个 key：在业务上复制 N 份数据，key 加随机后缀（比如 hot:item:1001:0 到 hot:item:1001:9），读的时候随机选一个，这样同一个逻辑热 key 就分散到不同 slot 和节点上，单节点压力降到 1/N；写的时候要按同样规则写入所有副本，或者用定时任务统一刷新。第四，入口治理：在网关或服务层做限流、请求合并（同一时刻相同请求合并成一次查询）、以及对非核心请求降级，从源头减少对热 key 的访问。第五，配套要有发现能力：客户端埋点统计 key 访问频率，或者用 redis-cli --hotkeys 做低峰巡检，做到"能提前发现、而不是打挂之后才知道"。整体思路就是削峰（本地缓存）、分散（多副本和 key 拆分）、保护（限流降级）。

**常见追问**：1）热 key 拆成多副本后写入怎么保证各副本一致？2）本地缓存短 TTL 定多长合适？

## 66. Redis 支持哪些数据结构？各自典型场景？

> 原题 ID：`q4057`

**高频程度**：★★★★★

**考察点**：Redis 各数据结构与典型业务场景的一一对应。

**回答框架**：

1）String：缓存、计数、分布式锁；2）Hash：对象属性、部分字段更新；3）List：队列、最新列表、栈；4）Set：去重、交并差、抽奖；5）ZSet：排行榜、延迟队列、范围排名；6）Bitmap：签到、活跃统计；7）HyperLogLog：UV 基数估算；8）GEO：附近的人；9）Stream：消息流、消费组。

**参考回答**：

Redis 支持的数据结构及其典型场景可以一一对应。String 是最常用的，用于缓存值、计数器（INCR）、分布式锁（SET NX EX）、限流；Hash 是 field-value 结构，适合存对象属性，比如用户资料、商品信息，好处是可以只更新某个字段而不重写整个对象；List 是有序可重复的双端结构，适合做队列、栈、最新 N 条消息；Set 是无序不重复集合，适合去重、共同好友、抽奖、标签集合运算（交并差）；ZSet 是有序集合，每个成员带 score，适合排行榜、延迟队列（score 存时间戳）、按分数范围查询和排名；Bitmap 位图用于签到、活跃用户统计，极度省内存；HyperLogLog 用于 UV 基数估算，用极小的内存（12KB）估算海量去重计数，误差约 0.81%；GEO 用于附近的人、距离计算；Stream 是 Redis 5.0 引入的消息流结构，支持消费者组、消息确认、消息回溯，适合做轻量消息队列。总结成一句话的选型逻辑：要缓存和计数用 String，要存对象用 Hash，要队列和最新列表用 List，要去重和集合运算用 Set，要排序和排名用 ZSet，要位统计用 Bitmap，要估算基数用 HyperLogLog，要位置服务用 GEO，要可靠消息流用 Stream。

**常见追问**：1）HyperLogLog 为什么能省这么多内存？2）什么时候该用 Stream 而不是 List？

## 67. RDB 和 AOF 两种持久化区别？如何选型？

> 原题 ID：`q4058`

**高频程度**：★★★★★

**考察点**：RDB 快照与 AOF 命令日志的区别、刷盘策略与选型、混合持久化。

**回答框架**：

1）RDB：定时快照，文件小、恢复快，但可能丢最后一次快照后的数据；2）AOF：追加写命令，数据更安全，可设 everysec 刷盘，文件大、恢复慢；3）对比维度：数据安全、恢复速度、文件体积、对主流程影响；4）生产实践：AOF 保数据 + RDB 做备份/快速重启，或直接用混合持久化；5）Redis 7 支持 multi-part AOF。

**参考回答**：

RDB 是定时快照持久化，把某一时刻的全量内存数据以二进制写入磁盘。它的优点是文件紧凑、恢复速度快、对主流程影响相对可控（BGSAVE 用 fork 子进程），适合备份和快速重启；缺点是两次快照之间的数据会丢失，可能丢几分钟，而且实例内存大时 fork 本身会短暂阻塞、写时复制会带来额外内存开销。AOF 是追加日志持久化，记录每一条写命令，重启时重放来恢复数据。它的优点是数据更安全，用 appendfsync everysec 时最多丢 1 秒，always 时几乎不丢；缺点是文件比 RDB 大得多、恢复时要逐条重放所以慢，而且长期运行需要 AOF 重写来控制文件体积。从几个维度对比：数据安全性上 AOF 更好；恢复速度上 RDB 更快；文件体积上 RDB 更小；对主流程的影响上，RDB 主要是 fork 阻塞和 COW 内存开销，AOF 主要是刷盘开销（always 影响最大，everysec 可能有偶发阻塞）。选型上，生产环境通常两者结合：用 AOF 保证数据尽量不丢作为主要恢复手段，同时保留 RDB 用于周期性备份、灾难恢复和主从全量同步。如果不折腾两套，直接用混合持久化（aof-use-rdb-preamble，Redis 4.0+ 默认开启），AOF 文件前半部分是 RDB 格式的全量快照、后半部分是增量命令，兼顾恢复速度和低丢失率；Redis 7.0 还引入了 multi-part AOF，把基础文件和增量文件分离，优化了重写时的内存和磁盘开销。最后补一句判断依据：如果 Redis 只是纯缓存、数据能回源重建，持久化要求可以放低；如果把它当存储用，必须开 AOF 或混合持久化。

**常见追问**：1）为什么 AOF 恢复比 RDB 慢？2）multi-part AOF 解决什么问题？

## 68. 缓存穿透、击穿、雪崩分别是什么？如何解决？

> 原题 ID：`q4059`

**高频程度**：★★★★★

**考察点**：缓存穿透/击穿/雪崩的定义、触发条件与对应的解决方案。

**回答框架**：

1）穿透=数据不存在（缓存和库都没有）；解决：布隆过滤器、缓存空值、参数校验限流；2）击穿=单个热点 key 过期瞬间并发回源；解决：互斥锁重建、逻辑过期（不真删）、热点不过期；3）雪崩=大量 key 同时过期或 Redis 宕机；解决：过期时间加随机、多级缓存、高可用集群、熔断降级；4）一句话区分三者；5）治理要组合使用并有监控。

**参考回答**：

这三个概念要能一句话区分，再分别讲方案。缓存穿透是"数据不存在"：请求的数据在缓存和数据库里都没有，每次请求都绕过缓存直接打到数据库，典型是恶意用不存在的 ID 刷接口。解决方案：第一，缓存空值，查不到就写一个占位符并设较短 TTL，下次直接返回空，不再查库；第二，布隆过滤器在入口拦截，它说"不存在"就一定不存在，能挡掉绝大多数非法 key，注意有误判率且标准版不支持删除；第三，参数校验和限流，在网关层做格式和范围校验，对异常来源限流。缓存击穿是"单个热点 key 过期时的并发"：某个高并发热点 key 在过期瞬间，大量请求同时未命中，全部去查库并回写，形成瞬时冲击。解决方案：第一，用互斥锁或分布式锁，只让一个线程回源重建，其他线程等待或返回旧值；第二，逻辑过期，物理上不设 TTL，value 里带逻辑过期时间，发现过期后异步重建，其他请求先返回旧数据，没有空窗期；第三，对超热点数据干脆不设过期，靠后台任务定时刷新。缓存雪崩是"大量 key 同时失效或缓存整体不可用"：比如一批商品统一设了两小时过期同时失效，或者 Redis 节点/集群宕机，导致请求全压到数据库甚至把库打挂。解决方案：第一，过期时间加随机值，把失效时间打散；第二，多级缓存（本地缓存 + Redis）减少对 Redis 的依赖；第三，架构上做主从加哨兵或 Cluster 保证高可用；第四，必须有熔断降级和限流，数据库压力大时快速失败返回兜底内容，保护数据库。最后强调一点：这三者往往需要组合治理，并且要通过监控（缓存命中率、DB QPS、慢查询）来及时发现问题，而不是等出事再处理。

**常见追问**：1）三者的根本区别用一句话怎么概括？2）逻辑过期方案的核心思想是什么？

## 69. 主从复制、哨兵、集群分别解决什么？

> 原题 ID：`q4064`

**高频程度**：★★★★★

**考察点**：主从复制（读写分离）、哨兵（自动故障转移）、Cluster（分片水平扩展）各自解决的问题与 16384 槽。

**回答框架**：

1）主从复制：一主多从，读写分离、数据备份，但故障需人工切换、写能力和容量受限于主节点；2）哨兵：监控主从、自动判活选举、故障转移、通知客户端，解决高可用；3）Cluster：16384 个槽分片、多主多从、水平扩展，解决单机写入能力和容量上限；4）演进关系与组合方式；5）各自适用场景。

**参考回答**：

这三种模式分别解决不同层面的问题。主从复制解决的是"读扩展和数据冗余"：一主多从，写操作只在主节点执行，读请求分到从节点，实现读写分离提升读吞吐，同时从节点作为数据备份。它的局限是主节点仍是单点，故障需要人工切换，而且写能力和内存容量都受限于单机，主从复制还是异步的，切换时可能丢数据。哨兵解决的是"高可用"：在主从基础上增加一组哨兵进程，它们周期性 PING 监控节点存活，先标主观下线、达到 quorum 后标客观下线，然后选举 leader、从从节点中挑出新的主节点、通过发布订阅通知客户端切换，实现自动故障转移。它不解决容量和写扩展问题，本质还是主从，切换期间有短暂不可用，配置上哨兵建议部署奇数个以形成多数派。Cluster 解决的是"水平扩展"：把数据按 16384 个哈希槽分片到多个主节点，每个 key 通过 CRC16 取模定位槽，槽归属某个节点；每个主节点再挂从节点保证分片高可用。这样内存总量和写能力都能横向扩展，突破了单机的容量和写入瓶颈。代价是跨槽的多 key 操作受限（需要用 hash tag 把相关 key 放到同一槽）、客户端要支持集群协议、运维复杂度更高。演进关系上：单机 → 主从复制（解决读和冗余）→ 哨兵（解决高可用）→ Cluster（解决容量和写扩展）。实践中选型看需求：只读压力大就用主从；要求自动故障转移就用哨兵；数据量和写入量超过单机上限就必须用 Cluster。

**常见追问**：1）Cluster 模式下客户端怎么路由？2）哨兵和 Cluster 能不能一起用？

## 70. ZSet 底层如何实现？为什么能排序？

> 原题 ID：`q4066`

**高频程度**：★★★★★

**考察点**：ZSet 的双结构实现（跳表 + 哈希表）、各自负责的操作与复杂度、元素共享机制。

**回答框架**：

## 71. Pipeline 和事务（MULTI/EXEC）的区别？

> 原题 ID：`q4068`

**高频程度**：★★★★

**考察点**：Pipeline 与事务（MULTI/EXEC）的区别：网络往返优化 vs 原子性，以及各自是否支持回滚。

**回答框架**：

1）Pipeline：把多条命令批量发送、一次性收结果，减少 RTT，提升吞吐；服务端仍逐条执行，不保证原子性，中间可能插入其他客户端命令；2）事务 MULTI/EXEC：命令先入队，EXEC 时一次性按序执行，期间不会被打断（原子性）；3）共同点：都不支持回滚，运行时错误只影响该条命令；4）事务还有 WATCH 做乐观锁、DISCARD 放弃；5）选型：追求吞吐用 Pipeline，追求原子用事务或 Lua。

**参考回答**：

Pipeline 和事务是两个不同层面的东西。Pipeline 解决的是网络往返问题：正常情况下客户端发一条命令要等 Redis 回复，一次 RTT 就浪费了；Pipeline 的做法是把多条命令一次性打包发给服务端，服务端逐条执行后把结果一起返回，这样一条连接的 RTT 只花一次，吞吐能提升很多倍。要注意 Pipeline 不保证原子性，服务端仍然是逐条执行命令的，执行过程中完全可能插入其他客户端的命令，所以它只优化性能，不提供隔离或原子保证。事务 MULTI/EXEC 解决的是原子性问题：MULTI 之后命令不立即执行而是入队，直到 EXEC 才一次性按顺序执行，执行期间不会被其他客户端命令插入，形成了"打包原子执行"的效果；还有 DISCARD 放弃事务、WATCH 监视 key 做乐观锁（如果被其他客户端改动，EXEC 会失败）。两者的共同点是都不支持回滚：Redis 事务里如果某条命令在运行时出错（比如类型不匹配），只有那条命令失败，后面的命令照常执行，已经执行的也不会回滚；只有入队阶段就发现的错误（命令不存在、语法错）会让 EXEC 整体拒绝。所以严格说 Redis 事务不满足 ACID 的原子性。选型上：如果只是要减少网络开销、批量读写，用 Pipeline；如果需要命令之间不被打断，用 MULTI/EXEC；如果需要"判断加操作"这种真正需要原子的复合逻辑，最好的方式是把逻辑写进 Lua 脚本，它既能保证中间不被打断，又比事务更灵活。实践中 Pipeline 和事务也可以组合使用。

**常见追问**：1）为什么 Pipeline 不保证原子性？2）WATCH 失败后怎么处理？

## 73. Redis 从节点如何通过 replication ID 和 offset 判断与主节点的同步状态？

> 原题 ID：`q1416`

**高频程度**：★★★★

**考察点**：考察 Redis replication ID、offset 和 replication backlog 如何共同决定部分重同步或全量同步。

**回答框架**：

1) 说明主节点复制流的 ID 和递增 offset；2) 从节点保存已处理的 ID/offset；3) 重连时通过 PSYNC 发送已知位置；4) 主节点判断 ID 与 backlog 覆盖范围；5) 解释切主后的第二 ID 和全量同步兜底。

**参考回答**：

Redis 主节点为复制流维护 replication ID 和递增 offset；从节点记录自己已处理到的 replication ID/offset。连接中断后，从节点通过 PSYNC 告诉主节点自己最后看到的 ID 与 offset，主节点据此判断它是否仍能从 replication backlog 中补发缺失命令。

当 ID 匹配且 offset 仍落在 backlog 可覆盖的范围内，可进行部分重同步；ID 不匹配、backlog 已覆盖不到该位置或其他条件不满足时，需要全量同步。发生故障转移时，旧主复制流与新主的历史衔接需要额外处理，Redis 会维护第二 replication ID 等信息帮助判断可延续的历史。

具体诊断应查看 `INFO replication` 中的角色、ID、offset、backlog 和连接状态，并结合版本和故障转移时序；不要只比较一个 offset 数字就断定数据一定一致。

**常见追问**：为什么 backlog 太小会提高网络短暂抖动后触发全量同步的概率？

## 74. Redis 为什么快？

> 原题 ID：`q4063`

**高频程度**：★★★★★

**考察点**：考察 Redis 性能来自内存、事件驱动、数据结构和命令复杂度的组合，而不是“单线程”这一句口号。

**回答框架**：

1) 先看数据是否驻留内存及网络路径；2) 区分命令执行与 I/O 线程；3) 说明事件循环和非阻塞 I/O；4) 结合具体数据结构/命令复杂度；5) 用慢命令、延迟和资源指标定位瓶颈。

**参考回答**：

Redis 许多常用操作快，首先因为工作集通常在内存中，避免了磁盘随机 I/O；其事件驱动、非阻塞网络 I/O 和较简单的 RESP 协议也降低了连接处理开销。核心命令执行路径长期以单线程串行化为主，这减少了共享数据结构上的锁竞争，但并不意味着所有 Redis 工作都只有一个线程：不同版本可使用 I/O 线程，持久化、删除等也可能由后台线程处理。

性能还取决于命令和数据结构。小而受控的 String/Hash/Set 操作与一次遍历百万成员、超大 value、复杂 Lua 或阻塞命令的成本完全不同；持久化、复制、网络带宽、CPU、内存碎片和客户端输出缓冲也会成为瓶颈。

排障应看命令延迟、slowlog、`LATENCY` 事件、CPU、网络、复制和内存指标，并按具体 workload 选择拆分、限流、批量或架构调整。

**常见追问**：为什么一个 O(N) 命令即使只执行一次，也可能影响同实例上的其他客户端？

## 75. Redis 的发布订阅（pub/sub）和 Stream 区别？

> 原题 ID：`q4067`

**高频程度**：★★★

**考察点**：Pub/Sub 广播无持久化 vs Stream 持久化可靠队列

**回答框架**：

1. Pub/Sub：广播、无持久化、离线丢失、无 ACK；2. Stream：持久化、消费组、ACK、阻塞读、回溯重放、pending；3. 场景选择

**参考回答**：

核心差异：① Pub/Sub 是广播模型，消息不持久化，消费者离线就丢，没有 ACK 与重投；② Stream 是持久化消息流（类似 Kafka），支持消费组、ACK、阻塞读取（XREAD BLOCK）、按 ID 回溯与重放、pending 消息管理。所以 Pub/Sub 适合实时通知、在线推送等允许丢消息的场景；Stream 适合需要可靠投递、可重放的消息队列场景。

**常见追问**：Stream 的 pending 列表是干什么的？怎么处理一直没 ACK 的消息？
