## 1. Agent 的推理成本怎么优化？模型路由/缓存/Token 预算怎么做？

> 原题 ID：`q0026`

**高频程度**：★★★★

**考察点**：Agent 推理成本优化的三大手段：模型路由、缓存、Token 预算与压缩。

**回答框架**：

1）模型分层路由：按任务难度选模型，简单走小模型/本地模型，复杂才上大模型；2）缓存：精确匹配缓存 + 语义相似缓存，命中即不调 LLM；3）Prompt 压缩：去冗余指令、历史摘要、少样本裁剪；4）批处理提升 GPU 利用率；5）预算与监控：Token 上限、实时成本监控、异常流量限流。

**参考回答**：

Agent 推理成本优化我一般从四个方向做。第一是模型分层路由：先对请求做难度分类，简单任务（分类、抽取、格式转换）走小模型或本地部署模型，复杂推理才上大模型，路由可以用规则、小分类器或便宜模型做裁判，成本能降一大截。第二是缓存：精确匹配缓存用于完全相同的 query，语义相似缓存用 embedding 检索相似问题，命中即返回不调 LLM，工程上语义缓存通常能省 60% 左右的调用。第三是 Prompt 压缩：去掉冗余的指令和历史，对多轮对话做历史摘要，裁剪没用的少样本示例，一般能省 30% 的 token。第四是批处理，把并发请求合并提升 GPU 利用率，降低单请求成本。最后一定要加成本可观测和预算控制：按用户/会话设 token 上限，实时监控单请求成本和总花费，异常流量自动限流，目标是把单请求成本控制在一个可预期的量级。常见的坑是所有请求都走最贵的大模型，或者没有缓存导致重复问题反复烧钱。

**常见追问**：1）语义缓存怎么判断"相似到可以复用"？2）路由判断错了导致效果下降怎么兜底？

## 2. 尤其是本地缓存和 Redis 之间怎么同步

> 原题 ID：`q0080`

**高频程度**：★★★★★

**考察点**：本地缓存与 Redis 多级缓存的同步策略、Cache-Aside、延时双删、MQ 广播失效。

**回答框架**：

1）写路径：更新 DB → 删 Redis → 广播失效消息 → 各节点删本地缓存；2）读路径：本地 → Redis → DB，逐级回填；3）防脏读：延时双删应对并发写，或订阅 binlog/CDC 统一失效；4）一致性等级：按业务选最终一致；5）反模式：写时同时双写本地+Redis 而不失效。

**参考回答**：

多级缓存里本地缓存（Caffeine）最快但各实例孤立，和 Redis 的同步我一般这样做。写路径：先更新数据库，再删除 Redis 缓存，然后通过消息队列广播失效消息，各应用节点收到后删除自己的本地缓存；读路径：本地缓存 → Redis → 数据库，逐级回填，回填时给本地缓存设较短 TTL 作为兜底。这里有两个关键点：一是为什么是"删缓存"而不是"更新缓存"，因为并发更新时双写顺序无法保证，容易出现旧值覆盖新值，删除更安全，下次读自然回源；二是怎么防止并发下的脏读，可以用延时双删——写库删缓存后，隔几百毫秒再删一次，把这段时间内被并发读回填的旧值清掉；更彻底的做法是订阅 binlog 或 CDC，由数据变更事件统一驱动各层失效，避免业务代码漏删。一致性等级上，多级缓存一般不追求强一致，按业务接受最终一致即可，关键是失效要快、要全覆盖。最容易踩的坑是写的时候同时更新本地和 Redis 而不失效，一旦其中一台机器更新失败或者广播丢失，脏数据会一直留着。

**常见追问**：1）延时双删的延时怎么定，能彻底解决吗？2）MQ 广播消息丢了怎么办？

## 3. Redis 大 Key 和热 Key 分别怎么处理

> 原题 ID：`q0087`

**高频程度**：★★★★★

**考察点**：大 Key 与热 Key 的根因区分（体积 vs 频率）、危害与处理手段。

**回答框架**：

1）大 Key：value 过大或集合元素过多，危害是阻塞单线程、过期/删除卡顿、网络包大、迁移慢；处理：结构拆分（大 hash 分桶、大 list 分片）、压缩、异步 unlink、hscan 分批删；2）热 Key：访问集中，危害是单节点打满、读放大；处理：本地缓存短 TTL、key 加随机后缀复制多副本打散、请求合并、限流；3）根因不同处理不同。

**参考回答**：

大 Key 和热 Key 是两类问题，根因不同，一个是体积、一个是频率。大 Key 指 value 过大或集合元素过多，比如一个 100 万字段的 Hash、一个超长的 List。危害有三：Redis 单线程处理时序列化、网络传输会阻塞其他请求；过期和删除时释放内存卡顿；主从同步和集群迁移时会形成大包、迁移慢甚至超时。处理方式是结构拆分，比如把 100 万字段的 Hash 拆成 100 个 1 万字段的子 Hash 用 key 后缀分桶；大 List 分片成多个 key；能压缩就压缩；删除时用 unlink 异步删除，或者用 hscan 渐进式分批删除，避免一次 DEL 卡住。热 Key 指单个 key 的访问量极大，比如秒杀商品、明星微博。危害是压力集中到一个节点，单节点 CPU 或网卡打满，集群里其他节点却很闲。处理方式：客户端加本地缓存并设短 TTL 和随机过期时间，减少回源；把热 key 复制成 N 个副本、key 加随机后缀，把读请求打散到不同节点；入口做请求合并和限流；也可以在 Redis 代理层做统一的多级缓存。所以一句话总结：大 Key 治"拆"，热 Key 治"散"。

**常见追问**：1）怎么发现线上有大 Key 和热 Key？2）集群模式下热 key 打散后怎么写数据？

## 4. RAG 如何处理动态更新的知识库？增量索引与缓存策略怎么设计

> 原题 ID：`q0111`

**高频程度**：★★★★

**考察点**：RAG 知识库动态更新：增量索引、软删除与版本标记、缓存失效绑定知识版本。

**回答框架**：

1）增量建索引取代全量重建，只处理新增/变更 chunk；2）doc 带 version/update_time，向量库 upsert 或删旧插新；3）软删除 + 元数据过滤只检索生效中版本；4）缓存 key 带知识版本号，源更新主动失效；5）定期 compaction 防碎片，embedding 模型版本固定，换模型需重建。

**参考回答**：

RAG 处理动态知识库的关键是"增量建索引"而不是全量重建，因为每天新增几百篇文档时全量重建又慢又贵。具体设计：第一，每条文档带 version 和 update_time 字段，入库时只处理增量，通过比对时间戳或变更日志识别新增和修改。第二，向量库要支持 upsert 和 delete，按 doc_id 定位旧向量，先删后插或直接覆盖，保证一个 chunk 不会留两个版本。第三，删除用软删除加元数据过滤，标记失效而不是物理删除，检索时通过 metadata 过滤只召回"生效中"的版本，这样既能保证可回滚，也避免删除操作影响索引结构。第四，缓存策略要和知识版本绑定，缓存 key 设计成 query 加知识版本号，源数据更新后主动失效相关 key，否则会返回旧知识。第五，定期做索引 compaction 合并碎片，保证检索性能。还有一个容易被忽略的点：embedding 模型版本必须固定，如果换了 embedding 模型，向量空间变了，必须全量重建索引，不能混用。总体原则是"变更最小化、失效及时、检索只看到生效版本"。

**常见追问**：1）知识版本号怎么设计比较好？2）软删除的旧向量怎么清理？

## 5. Redis所有数据类型的底层实现了解吗

> 原题 ID：`q0369`

**高频程度**：★★★★

**考察点**：Redis 五大类型在不同规模下的编码（encoding）与底层数据结构。

**回答框架**：

1）String：int / embstr / raw（SDS）；2）List：3.2 前 ziplist+linkedlist，3.2 后 quicklist，7.0 用 listpack；3）Hash：ziplist/listpack 或 hashtable；4）Set：intset 或 hashtable；5）ZSet：ziplist/listpack 或 skiplist+字典；6）编码随数据规模自动转换，目的是省内存或提性能。

**参考回答**：

Redis 每种数据类型都会根据数据规模或特性选择不同的底层编码，可以在内存和性能之间做平衡。String 有三种编码：存整数时用 int；短字符串（44 字节以内）用 embstr，内存连续分配减少碎片；长字符串用 raw，底层是 SDS，能 O(1) 取长度且二进制安全。List 的演进最有代表性：3.2 之前是元素少用 ziplist、元素多用 linkedlist；3.2 到 6.2 统一用 quicklist，即双向链表加 ziplist，兼顾内存和操作效率；7.0 之后把 ziplist 换成了更省内存的 listpack。Hash 在小数据量时用 ziplist/listpack，超过阈值转 hashtable。Set 在元素全是整数且数量少时用 intset，否则用 hashtable。ZSet 元素少且成员短时用 ziplist/listpack，否则用 skiplist 加字典的组合。核心理解是：小规模用紧凑的连续内存结构省内存，规模变大后为了性能切换到哈希表或跳表，切换阈值由配置决定，比如 hash-max-listpack-entries、zset-max-listpack-entries。

**常见追问**：1）ziplist 和 listpack 的区别是什么？2）编码转换是单向的吗，会转回来吗？

## 8. 为什么用Redis作为MySQL的缓存

> 原题 ID：`q0372`

**高频程度**：★★★★

**考察点**：用 Redis 做 MySQL 缓存的原因、内存 vs 磁盘 IO、QPS 提升与一致性问题。

**回答框架**：

1）MySQL 数据在磁盘，查询要走磁盘 IO，复杂查询代价高；2）Redis 数据在内存，微秒级返回，避免磁盘 IO；3）缓存热点数据能显著提升 QPS、降低 DB 压力；4）代价与风险：一致性、缓存穿透击穿雪崩、内存成本；5）典型架构：Cache-Aside，读多写少场景收益最大。

**参考回答**：

用 Redis 做 MySQL 缓存的核心原因是访问介质不同：MySQL 是数据库系统，数据落盘，一次查询要走磁盘 IO，还涉及解析、优化、加锁、事务等开销，复杂查询可能几十毫秒；Redis 数据在内存，一次读取是微秒级，直接跳过磁盘 IO，所以把热点数据放到 Redis 能显著提升响应速度和系统 QPS，同时把大量读请求从数据库挡掉，减轻 MySQL 压力，给数据库留出处理写入的能力。典型的读写路径是 Cache-Aside：读请求先查 Redis，命中直接返回，未命中回源 MySQL 再回填并设 TTL；写请求先更新 MySQL 再删除 Redis 缓存。这套组合特别适合读多写少、能容忍短暂不一致的业务，比如商品详情、用户资料。但也要讲清代价和风险：会引入缓存与数据库的一致性问题，需要处理缓存穿透、击穿、雪崩，内存成本比磁盘高，还增加了一层需要运维的组件。所以适用边界是"热点、可容忍最终一致、读远多于写"的数据，强一致的核心资产仍然以 MySQL 为准。

**常见追问**：1）为什么是删除缓存而不是更新缓存？2）什么样的数据不适合放缓存？

**回答框架**：

1）热点数据缓存；2）限时业务：expire 做验证码、优惠活动；3）分布式锁：SET NX EX、Lua 释放；4）计数器：INCR/INCRBY 原子递增，用于秒杀、限流、序列号；5）排行榜：ZSet；6）消息队列：List 的 push/pop 或 Stream；7）会话与去重：Set、Bitmap、HyperLogLog。

## 10. Redis如何保证访问安全

> 原题 ID：`q0374`

**高频程度**：★★

**考察点**：Redis 访问安全措施：密码认证、绑定 IP、TLS、防火墙、ACL、保护模式与危险命令禁用。

**回答框架**：

1）requirepass 设置密码认证，客户端 AUTH；2）bind 绑定内网 IP，不暴露公网；3）TLS 加密通信；4）防火墙/安全组限制来源；5）Redis 6+ ACL 做细粒度用户与命令权限；6）禁 rename 危险命令（FLUSHALL、KEYS、CONFIG）、开启 protected-mode。

**参考回答**：

Redis 的访问安全我会从网络、认证、权限、加密四层来做。第一，网络层：用 bind 绑定内网地址，绝不把 6379 暴露到公网，再用防火墙或安全组只放通应用服务器的来源 IP，这是最重要的，历史上大量 Redis 被入侵都是因为公网裸奔。第二，认证：在 redis.conf 里设置 requirepass 开启密码认证，客户端连接后用 AUTH 提供密码；注意密码在配置文件里是明文，要控制文件权限。第三，权限：Redis 6 之前只有单一密码，6 之后有 ACL，可以为不同应用创建用户，限制可执行的命令和可访问的 key 前缀，做到最小权限；同时用 rename-command 禁用或改名 FLUSHALL、FLUSHDB、KEYS、CONFIG 等危险命令。第四，加密：跨网络或跨机房访问时启用 TLS。另外建议开启 protected-mode，配合监控审计和定期漏洞修复。原则上是"不暴露、强认证、最小权限、可审计"。

**常见追问**：1）为什么说 bind 和防火墙比密码更重要？2）ACL 怎么限制一个用户只能读某些前缀的 key？

## 11. Redis 的数据类型有哪些

## 13. Set一个已有的数据会发生什么

> 原题 ID：`q0377`

**高频程度**：★★★

**考察点**：SET 命令覆盖已有 key 的三种效果：覆盖值、擦除过期时间、可以覆盖不同类型。

**回答框架**：

1）覆盖原有值，旧值直接丢弃；2）擦除原有 TTL，key 变回永久；3）可以跨类型覆盖（List 被 String 覆盖），等价于隐式 DEL 再 SET；4）例外：不带 KEEPTTL 时过期时间清空，SET ... KEEPTTL 可保留；5）实践：改值想保留 TTL 要用 SET KEEPTTL 或 SETEX。

**参考回答**：

对一个已存在的 key 执行 SET，会发生三件事。第一，覆盖原有值，旧的内容直接丢弃，不管原来是什么内容。第二，擦除过期时间，原来设置的 TTL 会被清掉，key 变成永久有效；这一点经常踩坑，比如本来给缓存设了 60 秒过期，代码里用 SET 更新值后 TTL 没了，导致数据永不失效。Redis 6.0 之后可以用 SET key value KEEPTTL 来保留原有过期时间，或者直接用 SETEX/带 EX 参数重新设置。第三，可以跨类型覆盖，比如原来 mylist 是个列表，直接 SET mylist abc 会把列表干掉变成字符串，语义上等价于先隐式删除（DEL 或 unlink）再 SET，因为 Redis 的 key 是统一的命名空间，类型只体现在 value 上。所以实践建议是：更新缓存值时要显式带上过期时间，或者用 KEEPTTL，避免意外产生永久 key。

## 16. Redis字符串是怎么实现的

> 原题 ID：`q0380`

**高频程度**：★★★

**考察点**：String 的三种编码 INT / EMBSTR / RAW 及其转换条件。

**回答框架**：

1）INT：能用 long 表示的整数，直接存数值；2）EMBSTR：字符串长度 ≤44 字节，一次内存分配、只读；3）RAW：长度 >44 字节，两次分配，修改会原地更新；4）转换：EMBSTR 修改后变 RAW，append 超阈值也转 RAW；5）目的：省内存、减少碎片。

**参考回答**：

Redis 字符串对象底层有三种编码。第一是 INT，如果要存的是整数且能用 long 表示，Redis 直接把数值存在 redisObject 的指针位置，不额外分配内存，这也是为什么计数场景特别省内存；这时用 INCR 也是在整数上直接算。第二是 EMBSTR，字符串长度不超过 44 字节时使用，它把 redisObject 和 SDS 一次性分配在连续内存里，好处是内存分配次数少、碎片少、读取时一次缓存行命中；缺点是只读，任何修改都会触发重新分配，转成 RAW。第三是 RAW，长度超过 44 字节时使用，redisObject 和 SDS 分开分配，支持原地修改和扩容。我用的是 5.0 版本，阈值就是 44。除了 APPEND 或 SETRANGE 导致长度超过阈值会从 EMBSTR 转 RAW，INT 在值变成非整数或超出 long 范围时也会转成字符串编码。理解这三种编码的价值在于：知道计数为什么省内存、知道短字符串为什么快、知道修改短字符串会触发内存重分配，对性能优化和面试都很有用。

## 17. 为什么EMBSTR的阈值是44？（几乎不考）

> 原题 ID：`q0381`

**高频程度**：★★

**考察点**：EMBSTR 阈值 44 的推导：jemalloc 64 字节档、redisObject 16 字节、sdshdr 头部与 \0。

**回答框架**：

1）jemalloc 以 64 字节为分配档区分大小字符串；2）redisObject 16 字节；3）sdshdr 的 len/alloc/flags 三字段加 \0 共 4 字节；4）64 - (16+4) = 44；5）超 44 转 RAW 需两次分配。

**参考回答**：

EMBSTR 的 44 字节阈值来自内存分配器的档位。Redis 使用 jemalloc 内存分配器，它以 64 字节为阈值区分大小内存块，一次分配 64 字节以下的内存是最高效的。而一个字符串对象的内存由两部分组成：redisObject 占 16 字节，sdshdr 头部里的已分配长度、已申请长度、标记三个字段固定占 3 字节，再加上 C 字符串结尾的 \0 占 1 字节，合计 20 字节。64 减去 20 正好是 44，也就是能放下的数据最大长度。所以长度不超过 44 字节的字符串可以用 embstr 一次分配、内存连续；超过就转成 raw，redisObject 和 SDS 要分开分配两次。这题虽然冷门，但能体现对底层内存布局的理解——回答时不要只背 44，要讲清"64 字节分配档减 20 字节开销"这个推导过程。

## 18. SDS有什么用

> 原题 ID：`q0383`

**高频程度**：★★★★

**考察点**：SDS 相对 C 字符串的三大优势：O(1) 取长度、预留空间减少重分配、二进制安全。

**回答框架**：

1）O(1) 长度：SDS 有 len 字段，C 字符串要 O(n) 遍历；2）空间预分配与惰性释放：扩容时多分配、缩容时不立即回收，减少内存重分配；3）二进制安全：以 len 判断结束而非 \0，可存任意二进制；4）避免缓冲区溢出：扩容前检查容量；5）兼容 C 字符串函数。

**参考回答**：

SDS 是简单动态字符串，是 Redis 自己实现的字符串结构，相比 C 原生字符串有三大优势。第一，O(1) 获取长度：SDS 结构里有 len 字段记录已使用长度，取长度直接读字段；C 字符串要靠 strlen 遍历到 \0，是 O(n)，而 Redis 里取长度是很高频的操作。第二，有预留空间，减少内存重分配：扩容时 SDS 会按策略多分配一些（比如小于 1MB 时翻倍），缩容时不立即释放多余空间而是保留下来复用；C 字符串每次修改都要重新分配，代价大。第三，二进制安全：SDS 用 len 字段判断字符串结束，而不是以 \0 作为终止符，所以可以安全存储包含 \0 的二进制数据，比如图片、序列化后的对象、protobuf 字节流；C 字符串遇到 \0 就截断了。此外 SDS 在拼接前会检查剩余容量，避免 C 字符串那种缓冲区溢出问题，同时它仍然以 \0 结尾，可以直接复用一部分 C 字符串函数。这几条让它既有性能又有安全性。

**常见追问**：1）SDS 扩容的预分配策略具体是什么？2）为什么说 C 字符串不二进制安全？

## 19. List是完全先进先出吗

> 原题 ID：`q0384`

**高频程度**：★★★

**考察点**：List 是双端操作结构，支持 FIFO 也支持 LIFO。

**回答框架**：

1）List 是双端结构，头尾都能 O(1) 插入删除；2）LPUSH+RPOP 是先进先出（队列）；3）LPUSH+LPOP 是后进先出（栈）；4）LPUSH+LRANGE 取最新 N 条；5）不是严格 FIFO，取决于用哪两端。

**参考回答**：

List 不是完全先进先出的结构，因为它是双端操作对象，头尾两端都支持 O(1) 的插入和删除，所以既能做先进先出也能做后进先出，取决于你用哪两端配合。具体来说：LPUSH 加 RPOP 就是标准队列，先进先出，适合消息队列、任务分发；LPUSH 加 LPOP 就是栈，后进先出，适合撤销、最近浏览这类场景；LPUSH 加 LRANGE 0 N-1 可以取最新插入的 N 条，适合动态列表、最新消息；如果用 RPUSH 加 LRANGE 则是按插入顺序取最早 N 条。时间上头部和尾部操作都是 O(1)，但通过下标访问中间元素是 O(n)，因为之前是 ziplist/quicklist 这类结构，现在是 quicklist，只能遍历。所以回答这题的关键是：List 的语义由"用哪端的命令"决定，它本身是双端结构而不是天生 FIFO。

## 20. List对象底层编码方式是什么

> 原题 ID：`q0385`

**高频程度**：★★★★

**考察点**：List 编码演进：3.2 前 ziplist/linkedlist，3.2+ quicklist（内部 listpack）。

**回答框架**：

1）3.2 之前：元素少且短用 ziplist，否则 linkedlist；2）3.2 之后统一 quicklist = 双向链表 + ziplist；3）7.0 起 ziplist 被 listpack 取代（quicklist 内部为 listpack）；4）quicklist 兼顾内存紧凑与操作效率，可配置每个节点的大小；5）意义：避免 ziplist 连锁更新和大链表内存碎片。

**参考回答**：

List 的底层编码经历了一次重要演进。Redis 3.2 之前有两种编码：ziplist 用于元素数量较少且每个元素都较短的情况，省内存且内存连续；元素多或元素长时用 linkedlist，即普通双向链表，操作灵活但每个节点都有前后指针、内存碎片多。这两种编码的切换由 list-max-ziplist-size 之类的阈值控制。3.2 之后，List 的编码统一由 quicklist 实现，它本质是一个双向链表，但链表的每个节点是一个 ziplist 而不是单个元素，相当于把"大链表"切成一块块紧凑内存，兼具 ziplist 的省内存和 linkedlist 的快速增删，还能避免单个 ziplist 过大导致的连锁更新问题。到了 Redis 7.0，ziplist 因为存在连锁更新、内存利用率不够好的问题被 listpack 取代，所以现在 List 是 quicklist 加 listpack。这个演进过程的考点是：要能说出"为什么不用纯链表"（内存碎片和指针开销）和"为什么不用单个大 ziplist"（连锁更新、扩容拷贝代价大）。

**常见追问**：1）ziplist 的连锁更新是什么问题？2）quicklist 每个节点的容量怎么调？

## 21. ZIPLIST是怎么压缩数据的

> 原题 ID：`q0386`

**高频程度**：★★★

**考察点**：ziplist 的压缩原理：连续内存、双端链表语义、变长编码。

**回答框架**：

1）一块连续内存，元素紧挨存储，无指针开销；2）语义上是双端链表，可实现前后遍历；3）每个 entry 用变长编码（prevlen/encoding/内容），按数据大小选择最短表示；4）对比普通链表：省指针、省碎片、缓存友好；5）缺点：插入删除可能触发内存移动和连锁更新。

**参考回答**：

ziplist 压缩列表是一块连续的内存空间，所有元素紧挨着存储，其中可以包含多个节点 entry，逻辑上是一个双端链表，但物理上是一整块内存。它省内存的关键在于两点：一是没有指针开销，普通双向链表每个节点都要存前后指针，还分散在不同内存块里造成碎片；ziplist 通过记录上一个节点的长度来实现反向遍历，不需要指针。二是变长编码，每个 entry 由前一个节点的长度、编码字段和实际内容组成，编码字段会根据内容是整数还是字符串、长度是多少，选择最短的表示方式，比如小整数可以直接编码进编码字段，不额外占空间。缺点是插入和删除元素时要移动后面的内存，如果某个 entry 的长度变化跨过了 254 字节的边界，还可能引起后续节点 prevlen 字段扩张，形成连锁更新，这是它后来被 listpack 取代的原因。理解 ziplist 的价值在于：它体现了 Redis"小数据用紧凑结构省内存"的设计哲学，是理解 Hash、List、ZSet 小规模编码的基础。

**常见追问**：1）listpack 怎么解决连锁更新？2）ziplist 适合存多长的元素？

## 22. ZIPLIST下List可以从后往前遍历吗

> 原题 ID：`q0387`

**高频程度**：★★

**考察点**：ziplist 反向遍历的实现：靠每个节点的 prevlen 字段回退。

**回答框架**：

1）可以反向遍历，因为 List 是双端结构；2）ziplist 每个节点保存了前一个节点的长度（prevlen）；3）用当前节点地址减去 prevlen 得到上一个节点的起始位置；4）因此不需要额外指针；5）代价：prevlen 变化可能触发连锁更新。

**参考回答**：

可以，List 是双端数据结构，无论底层是哪种编码，都必须支持从后往前遍历，否则 LPOP/RPOP 就无法实现。ziplist 的实现方式是利用每个节点保存的 prevlen 字段——它记录了前一个节点的总长度。已知当前节点的起始地址，减去 prevlen 就能算出上一个节点的起始地址，从而一步步往前回退，这样既实现了双端遍历，又不需要像普通链表那样为每个节点存前后指针，省下了内存。表头里还有一个 zltail 字段记录最后一个节点的偏移，所以从尾部开始遍历也可以 O(1) 定位。代价是 prevlen 是变长的：当前一个节点长度小于 254 字节时用 1 字节存，否则用 5 字节，所以一旦某个节点长度增长跨过这个边界，它后面所有节点的 prevlen 都要扩写，这就是连锁更新问题的来源。回答时可以顺带点出这个权衡，体现理解深度。

**考察点**：hashtable 的索引计算：hash 函数求哈希值，与 sizemask 做按位与得到索引。

1）先用哈希函数（SipHash 等）计算 key 的哈希值；2）与哈希掩码 sizemask（表大小 - 1）按位与得到索引；3）要求表大小是 2 的幂，这样取模可以用按位与加速；4）解决冲突用链地址法，新节点插入链表头；5）扩容时表大小为 2 的幂同样保证该计算成立。

## 31. HashTable怎么扩容

> 原题 ID：`q0397`

**高频程度**：★★★★

**考察点**：hashtable 扩容流程：分配 1 号表、渐进式 rehash（rehashidx 推进）、完成后表切换。

**回答框架**：

1）为 1 号表分配空间，大小是第一个大于等于 0 号表大小 × 2 的 2 的幂；2）进入 rehash 状态，rehashidx 从 0 开始；3）每次增删改查都顺带迁移 rehashidx 位置的数据，然后 rehashidx 加 1；4）全部迁移完后把 1 号表设为 0 号表，再新建空白 1 号表；5）渐进式避免一次性迁移阻塞。

**参考回答**：

哈希表的扩容流程是这样的。第一步，程序为 1 号表分配空间，空间大小是第一个大于等于 0 号表大小乘 2 的 2 的幂，也就是翻倍并向上取到 2 的幂，这样保证掩码运算仍然有效。第二步，进入 rehash 进行中状态，标记位 rehashidx 从 0 开始。第三步是渐进式 rehash：不是一次性把所有键值对搬过去，而是在每次对字典执行增删改查操作时，顺带把 rehashidx 位置上的所有数据迁移到 1 号表，然后把 rehashidx 加一；随着字典操作不断执行，最终 0 号表的所有键值对都会被迁移到 1 号表。第四步，迁移完成后，1 号表被设置为 0 号表，然后在 1 号表的位置创建一个新的空白表，rehashidx 置为 -1 表示未在 rehash。为什么要渐进式？因为如果字典很大，一次性迁移会长时间阻塞 Redis 的单线程，导致所有请求卡住，渐进式把开销分摊到每次操作上，保证响应延迟平稳。在 rehash 期间，查找会先查 0 号表再查 1 号表，新增数据则直接写入 1 号表，保证不丢数据。

**常见追问**：1）rehash 期间删除操作怎么处理？2）如果长时间没有操作，rehash 会一直不完成吗？

## 32. HashTable怎么缩容

> 原题 ID：`q0398`

**高频程度**：★★★

**考察点**：hashtable 缩容流程：1 号表大小为第一个大于等于 used 的 2 的幂，同样渐进式 rehash。

**回答框架**：

1）为 1 号表分配空间，大小是第一个大于等于原表 used 的 2 的幂；2）标记 rehashidx，进入渐进式 rehash；3）每次字典操作迁移 rehashidx 位置的数据并递增；4）迁移完成后 1 号表变 0 号表，再建空白表；5）触发条件：负载因子小于 0.1。

1）扩容条件一：没有执行 BGSAVE/BGREWRITEAOF 且负载因子 ≥ 1；2）扩容条件二：正在执行 BGSAVE/BGREWRITEAOF 且负载因子 ≥ 5；3）缩容条件：负载因子 < 0.1；4）为什么后台持久化时阈值更高：利用写时复制，减少内存页分裂与额外内存占用；5）负载因子 = used / size。

**参考回答**：

哈希表什么时候扩容、什么时候缩容由负载因子决定，负载因子等于已存键值对数量 used 除以哈希表大小 size。扩容有两个条件，满足任意一个就触发：第一，服务器目前没有执行 BGSAVE 或 BGREWRITEAOF，并且负载因子大于等于 1；第二，服务器正在执行 BGSAVE 或 BGREWRITEAOF，并且负载因子大于等于 5。为什么后台持久化的时候阈值要提高？因为 Redis 做 RDB 或 AOF 重写时会 fork 子进程，父子进程共享内存页，用的是写时复制机制；如果在此时扩容，会触发大量内存页分裂和拷贝，额外占用大量内存，还可能拖慢持久化，所以在持久化期间尽量不扩容，除非哈希表已经非常拥挤、负载因子到 5 才不得不扩。缩容则由负载因子小于 0.1 触发，说明大部分桶都空着，内存浪费严重。设计上扩容和缩容阈值不对称，是为了避免在边界附近反复扩缩容产生抖动。

**常见追问**：1）写时复制在这里是怎么影响决策的？2）负载因子怎么计算和观测？

**考察点**：ZSet 的两种编码（ziplist/listpack 与 skiplist+字典）及切换阈值。

**回答框架**：

1）小规模用 ziplist/listpack，按 score 有序存储 member-score 对；2）大规模用 skiplist + 字典：跳表按 score 排序支持范围查询，字典按 member 查 score；3）阈值：元素数 < 128 且每个成员长度 < 64 字节用紧凑编码，否则切换；4）转换单向；5）两种结构各管一类查询。

**参考回答**：

ZSet 有序集合有两种底层编码。小规模时用 ziplist（Redis 7.0 后是 listpack），把 member 和 score 成对依次放在连续内存里，并按 score 从小到大排序，查找和范围操作靠遍历或二分，优点是内存非常省。当 ZSet 中所有元素同时满足两个条件——元素数量小于 128，且每个成员的长度都小于 64 字节——就用紧凑编码；否则切换到 skiplist 加字典的组合。为什么是两种结构配合？因为 ZSet 要同时满足两类查询：按 member 查 score，以及按 score 排序做范围查询（ZRANGE、ZRANK、ZRANGEBYSCORE）。跳表按 score 有序，支持 O(logN) 的插入、删除和范围遍历；字典按 member 映射到 score，让单点查询是 O(1)。只用一个结构必然有一类操作慢，所以用"跳表管有序范围 + 字典管单点查找"，两者共享同一份 member 和 score，不重复存储实际数据，只多存指针。阈值由 zset-max-ziplist-entries 和 zset-max-ziplist-value 控制，默认 128 和 64，而且和 Hash 一样，转换是单向不可逆的。

## 36. 跳表插入一条数据的平均时间复杂度是多少

> 原题 ID：`q0402`

**高频程度**：★★★

**考察点**：跳表插入的平均时间复杂度 O(logN)：先查找定位再重建索引。

**回答框架**：

1）跳表是多级索引结构，查询效率接近二分查找；2）插入先自顶向下查找插入位置，平均 O(logN)；3）随机决定新节点层高，然后逐层修改前驱的后继指针；4）整体平均 O(logN)，最坏 O(N)；5）对比平衡树：实现简单、范围查询方便、无需旋转。

**参考回答**：

跳表是一种支持多级索引的结构，查询效率可以媲美二分查找，平均查询复杂度是 O(logN)。插入一条数据的流程是：先从最高层开始，自顶向下逐层查找，定位到插入位置，这一步平均是 O(logN)；找到位置后，为新节点计算一个随机层高，然后从底层到该层逐层修改前驱节点的后继指针，把新节点链进去，同时更新 span（每层指针跨越的节点数）和 backward 指针。整体平均时间复杂度是 O(logN)，最坏情况在层高分布极不合理时是 O(N)，但概率极低，因为层高是随机的。相比平衡树，跳表的优势在于实现简单，不需要旋转和复杂的再平衡逻辑，插入删除只需改指针；而且范围查询非常自然，底层链表本身就是有序的，找到起点后顺序往后取就行，这也是 ZSet 用跳表而不是红黑树的原因。当然代价是平均空间复杂度是 O(N)，因为每层都要存指针。

## 37. 为什么跳表和HashTable要配合使用

> 原题 ID：`q0403`

**高频程度**：★★★★

**考察点**：跳表与字典配合的原因：字典管 member→score 单点查询 O(1)，跳表管按 score 的范围查询与排名。

**回答框架**：

1）ZSet 有两类核心操作：按 member 查 score，按 score 范围/排名查询；2）字典：member→score 映射，单点 O(1)；3）跳表：按 score 有序，支持 ZRANGE/ZRANK/ZRANGEBYSCORE，O(logN)；4）两者共享 member/score 对象，只多指针开销；5）单一结构无法兼顾两类操作。

**参考回答**：

跳表和字典配合使用是为了结合两种数据结构各自的优势。ZSet 实际上面临两类核心查询：一类是按成员查分值，比如 ZSCORE member 或者判断成员是否存在，这类操作字典最擅长，member 作为 key 映射到 score，时间复杂度 O(1)；另一类是按分值做范围或排名操作，比如 ZRANGE、ZRANK、ZRANGEBYSCORE、ZREVRANGE，这类操作需要数据按 score 有序，跳表天然支持，找到起点后沿底层链表顺序遍历即可，排名靠 span 字段累加实现，复杂度 O(logN)。如果只用跳表，单点查 member 要 O(logN)；如果只用字典，范围查询就得把所有元素取出来排序，代价不可接受。所以 Redis 用两个结构同时维护同一个集合：字典负责"点查"，跳表负责"有序范围"，而且两者共享同一份 member 和 score 对象，不重复存储数据本身，只多了一层指针和索引开销。这也是典型的"空间换时间、组合换全能"设计。

## 38. 跳表中一个节点的层高是怎么决定的

**回答框架**：

1）插入前随机计算层高；2）新节点初始 1 层；3）每增加一层的概率是 25%，期望层高约 1.33；4）最高 32 层，限制空间与防止退化；5）随机而非固定，让跳表整体近似平衡。

**考察点**：跳表 vs 平衡树：实现简单、区间查询高效、内存与索引策略灵活可调。

**回答框架**：

1）实现简单：平衡树插入删除要旋转和再平衡，跳表只改指针；2）区间查询高效：跳表 O(logN) 定位起点后沿底层链表顺序遍历，平衡树中序遍历不连续；3）内存与效率可调：改变层高概率即可调节索引密度；4）并发友好：无全局旋转；5）结论：代码简单、易读、不易出错，Redis 选跳表。

**参考回答**：

ZSet 用跳表而不是平衡树，主要有三个原因。第一，实现简单。平衡树（红黑树、AVL）插入和删除都会触发旋转和再平衡逻辑，代码复杂、边界情况多、容易出错；跳表的插入只是在普通链表插入的基础上多改几层指针，代码量小、逻辑清晰、也更便于调试和维护。第二，区间查询效率更高。ZSet 的核心场景是范围查询，比如 ZRANGEBYSCORE、ZRANGE，跳表可以 O(logN) 定位到区间起点，然后沿底层有序链表顺序往后遍历即可，非常高效；平衡树虽然也能定位起点，但要做中序遍历来取连续区间，指针跳转不连续、缓存不友好，实现上也麻烦。第三，内存和效率可灵活调节。跳表通过改变层高概率（Redis 是 25%）就能调整索引密度，在内存和查询速度之间做权衡；平衡树的结构是刚性的，不好调。综合来看，跳表用更简单的代码达到了和平衡树同量级的 O(logN) 查询复杂度，还在范围查询上更优，所以 Redis 选它。这也体现一个工程原则：性能达标的前提下，简单可靠比理论最优更重要。

**回答框架**：

1）数据结构：每天一个 bitmap，key 形如 sign:yyyy-MM-dd，用户 ID 作为 bit 偏移；2）签到：SETBIT sign:date uid 1；3）连续十天：BITOP AND dest 十个 key，得到十天的交集位图；4）统计人数：BITCOUNT dest，返回 1 的个数；5）注意：用户 ID 需映射为数字偏移，偏移过大会浪费内存，可做 ID 压缩映射并设过期。

## 41. RDB和AOF本质区别是什么

> 原题 ID：`q0415`

**高频程度**：★★★★

**考察点**：RDB 快照持久化 vs AOF 日志持久化的本质区别及派生的差异（恢复速度、安全性、开销）。

**回答框架**：

1）本质区别：RDB 保存内存数据的二进制快照，AOF 追加写命令日志；2）恢复速度：RDB 直接加载快照快，AOF 要重放命令慢；3）安全性：AOF 每秒刷盘丢数据少，RDB 可能丢几分钟；4）文件体积：RDB 紧凑，AOF 通常更大；5）开销：RDB fork 子进程写盘，AOF 有持续写入与重写开销；6）默认行为：RDB 默认开、AOF 默认关。

**参考回答**：

RDB 和 AOF 的本质区别是持久化的对象不同：RDB 是把某个时间点的内存数据整体生成一个二进制快照文件，属于"存结果"；AOF 是追加记录所有写命令，属于"存过程"，恢复时把命令重放一遍。因为本质不同，派生出一系列差异。第一，恢复速度：RDB 是紧凑二进制，加载时直接按格式读入内存，速度快；AOF 要逐条重放命令，文件还通常更大，恢复慢得多。第二，数据安全性：AOF 有 appendfsync 策略，everysec 时最多丢 1 秒数据，always 时几乎不丢；RDB 是按配置周期或手动触发，宕机可能丢几分钟数据。第三，文件体积与写开销：RDB 是压缩后的紧凑格式，体积小、适合备份和传输；AOF 是追加写，长期运行文件会膨胀，需要重写，且有持续的刷盘开销。第四，对主流程的影响：RDB 用 fork 子进程写盘，主要影响是 fork 时的短暂阻塞和写时复制的内存开销；AOF 的 always 策略会显著拖慢写性能。Redis 默认开启 RDB、关闭 AOF，官方推荐两者配合，4.0 之后还有混合持久化把 RDB 和 AOF 结合。所以回答的落点是"本质不同在于快照 vs 日志，其余差异都是这个本质的推论"。

**常见追问**：1）为什么 AOF 恢复比 RDB 慢？2）RDB 的 fork 会阻塞多久？

## 44. AOF刷盘的触发时机（几乎不考）

> 原题 ID：`q0418`

**高频程度**：★★

**考察点**：AOF 刷盘触发时机：关闭时、beforeSleep 事件循环钩子、servercron 定时任务，以及不同 appendfsync 策略。

**回答框架**：

1）Redis 关闭时；2）每次事件循环的 beforeSleep 钩子，处理待写缓冲；3）servercron 定时任务里；4）appendfsync 决定落盘时机：always 每次写后 fsync，everysec 每秒一次，no 交给 OS；5）本质：写入缓冲区 + 按策略 fsync。

**参考回答**：

AOF 的刷盘触发主要有三个入口。第一，Redis 关闭的时候会做一次收尾刷盘。第二，每一次事件循环的 beforeSleep 钩子函数里，会把命令先 write 到 AOF 缓冲区、再按 appendfsync 策略决定是否 fsync 落盘，这是最主要的路径，因为写命令是先进 aof_buf 缓冲区的。第三，在 servercron 这个定时任务回调里也会有相应的处理，用来兜底和推进一些后台工作。真正决定"什么时候落盘"的是 appendfsync 策略：always 表示每次写命令后都立即 fsync，最安全但性能最差；everysec 表示每秒 fsync 一次，最多丢 1 秒数据，是默认的平衡策略；no 表示只 write 不主动 fsync，由操作系统决定刷盘时机，性能最好但宕机可能丢较多数据。所以整体流程可以理解成"命令先追加到内存缓冲区，再由策略决定何时同步到磁盘"，这里要注意 write 和 fsync 是两个不同动作，write 只是写进内核页缓存，fsync 才真正落盘。

## 45. RDB对主流程有什么影响？（几乎不考）

> 原题 ID：`q0419`

**高频程度**：★★

**考察点**：持久化对主流程的影响：AOF always 写压力、everysec 的 fsync 阻塞 write、AOF 重写 fork 耗时。

**回答框架**：

1）always 策略下写日志压力大会拖慢主进程处理其他请求；2）everysec 下若后台线程上一轮 fsync 未完成，主线程 write 会被阻塞直到 fsync 完成；3）AOF 重写时数据量大导致 fork 耗时，阻塞主进程；4）RDB 同理有 fork 阻塞和写时复制内存开销；5）缓解：控制实例大小、合理配置、避免大实例 fork。

**参考回答**：

持久化对主流程的影响主要有三种情况。第一，当 appendfsync 使用 always 策略时，每条写命令都要同步 fsync 落盘，如果 AOF 写入压力很大，磁盘成为瓶颈，主进程就会在刷盘上花费大量时间，导致处理其他请求很慢，所以 always 一般只用在数据极度重要的场景。第二，当使用 everysec 策略时，正常情况下是后台线程每秒 fsync 一次，主线程只负责 write 到缓冲区，性能好；但如果后台线程上一轮的 fsync 还没有完成（比如磁盘抖动或慢盘），主线程本轮执行 write 就可能会被阻塞，直到 fsync 完成，这就是 everysec 下可能的延迟毛刺来源，Redis 会有相应保护机制但无法彻底消除。第三，AOF 重写发生时，需要 fork 子进程，如果实例内存很大、页表很大，fork 本身就要复制页表，耗时会比较明显，期间主进程被阻塞；RDB 的 BGSAVE 也有同样问题，而且 fork 之后还有写时复制带来的额外内存占用，极端情况下可能导致内存翻倍甚至触发 OOM。所以工程上的结论是：单个实例不要做得太大（通常建议控制在几个 GB 到十几 GB），合理设置刷盘策略，把持久化和业务部署在同一台机器时注意磁盘 IO 隔离。

**常见追问**：1）fork 阻塞时间跟什么有关？2）怎么缓解写时复制的内存开销？

## 46. AOF混合持久化方案是什么

> 原题 ID：`q0420`

**高频程度**：★★★

**考察点**：AOF 混合持久化：重写时前半部分写 RDB 格式全量，后续增量仍写 AOF 格式。

**回答框架**：

1）重写时用 RDB 方式把内存数据写入新 AOF 文件开头，格式是 RDB；2）重写期间的增量写命令继续以 AOF 格式追加到新文件；3）最终文件 = RDB 格式全量 + AOF 格式增量；4）收益：恢复速度接近 RDB，数据丢失仍按 AOF 策略；5）配置：aof-use-rdb-preamble，Redis 4.0+ 支持。

**参考回答**：

AOF 混合持久化是在 AOF 重写时把两种格式结合起来。具体流程是：触发 AOF 重写后，Redis 用类似 RDB 的方式把当前内存里的全量数据以 RDB 二进制格式写入新的 AOF 文件的开头部分；而在重写进行期间新到达的写命令，仍然以 AOF 的文本命令格式追加到同一个新文件里。所以重写完成后的新 AOF 文件，就是一个"前半部分是 RDB 格式的全量快照、后半部分是 AOF 格式的增量命令"的混合文件。这样设计的好处有两个：一是恢复速度接近 RDB，因为全量数据是直接按二进制格式加载的，不需要逐条重放命令；二是安全性仍是 AOF 级别，因为增量部分还是按 appendfsync 策略刷盘，最多只丢一个刷盘周期的数据。对比纯 AOF，它解决了恢复慢的问题；对比纯 RDB，它解决了丢失多的问题。配置项是 aof-use-rdb-preamble，Redis 4.0 之后支持并默认开启，是现在推荐的持久化方案。

## 47. 简单描述AOF重写流程

> 原题 ID：`q0421`

**高频程度**：★★★★

**考察点**：AOF 重写流程：fork 子进程、子进程读内存生成新文件、主进程写重写缓冲区、完成后合并。

**回答框架**：

1）触发重写时主进程 fork 出子进程；2）子进程读取当前 Redis 内存数据，以命令格式写入新 AOF 文件；3）重写期间主进程把新增写命令追加到 AOF 重写缓冲区；4）子进程写完后，主进程通过管道把重写缓冲区数据发给子进程；5）子进程追加到新文件，保证完整性，最后原子替换旧文件。

**参考回答**：

AOF 重写流程是：当重写被触发的那一刻，主进程会 fork 出一个子进程，然后这个子进程读取当前 Redis 数据库里的数据，把每条数据以对应的写命令格式（比如 SET、RPUSH）写入一个新的 AOF 文件。这里的关键点是重写不是重放历史命令，而是根据当前内存数据"反推"出最小命令集，比如对一个 key 反复修改过 100 次，重写后只会生成一条最终值的 SET，这就是文件体积能大幅变小的原因。在子进程工作期间，Redis 仍然继续接收新的写命令，主进程会把这些增量数据同时写入 AOF 重写缓冲区（aof_rewrite_buf）。等子进程把全量数据都写完后，主进程会通过管道把重写缓冲区里的数据发送给子进程，子进程再把这份增量追加到新 AOF 文件末尾。这样新文件就同时包含了重写开始时的全量数据和重写期间的增量数据，是完整的。最后主进程用新文件原子替换旧的 AOF 文件，重写结束。整个过程中只有 fork 那一下和最后的替换是阻塞的，其余都是后台进行，所以对主流程影响可控。

**常见追问**：1）为什么重写不直接重放旧 AOF？2）重写期间如果子进程失败会怎样？

## 48. AOF重写你觉得有什么不足之处么

> 原题 ID：`q0422`

**高频程度**：★★★

**考察点**：AOF 重写的三类额外开销（CPU、内存、磁盘）与 Redis 7.0 的优化（Multi Part AOF）。

**回答框架**：

1）CPU 开销：主进程写重写缓冲、管道传输、子进程写新文件；2）内存开销：AOF 缓冲与重写缓冲内容重复，浪费一份；3）磁盘开销：重写期间旧 AOF 和新 AOF 同时写，磁盘多占一份；4）Redis 7.0 用 multi-part AOF 优化，重写不再需要额外缓冲区；5）权衡：重写是必要代价，靠控制频率与实例大小缓解。

**参考回答**：

AOF 重写主要有三点不足。第一，额外的 CPU 开销：重写期间主进程要把新的写命令额外写入 AOF 重写缓冲区，还要通过管道把这份数据发送给子进程，子进程还要把这些数据写入新 AOF 日志，这些动作相比正常运行时都是额外的计算和数据搬运。第二，额外的内存开销：重写期间 AOF 缓冲区（写到旧 AOF 的）和 AOF 重写缓冲区（要发给子进程的）里的数据基本是一样的，等于同一份增量数据在内存里存了两份，写入量大时内存占用可观。第三，额外的磁盘开销：重写时 AOF 缓冲要刷入旧的 AOF 日志，AOF 重写缓冲也要刷入新的 AOF 日志，所以磁盘上同一份数据会被写入两次，磁盘带宽和空间都被多占一份。这三点都是重写机制"主进程和子进程并行"这个设计带来的固有代价。Redis 7.0 做了优化，引入了 multi-part AOF，把 AOF 拆成基础文件（base）和多个增量文件（incr），重写期间新产生的增量只写一份、不再需要额外的重写缓冲区和双份磁盘写，从机制上消掉了后两项开销。回答时可以按 CPU、内存、磁盘三个维度组织，最后补充 7.0 的优化，层次很清晰。

**常见追问**：1）multi-part AOF 的文件结构是怎样的？2）重写频率怎么定？

## 49. Redis 是怎么删除过期 key 的

> 原题 ID：`q0424`

**高频程度**：★★★★

**考察点**：过期 key 的删除策略：惰性删除 + 定期删除，及各自的优缺点。

**回答框架**：

1）惰性删除：每次访问 key 时检查是否过期，过期则删除并返回空；优点是省 CPU，缺点是长期不访问的 key 不释放、内存泄漏；2）定期删除：每 100ms 随机抽取部分设置了过期时间的 key 检查删除；优点是不依赖访问，缺点是 CPU 与内存之间要平衡；3）两者结合互补；4）过期 key 的物理删除分同步和异步（unlink）；5）与内存淘汰策略的区别。

**参考回答**：

Redis 删除过期 key 用的是惰性删除加定期删除的组合策略。惰性删除是每次从数据库取 key 的时候检查它是否过期，过期就删除并返回 null，没过期就直接返回数据；它的好处是完全不消耗额外 CPU，只在访问时判断，缺点是如果一个 key 设置了过期时间但之后再也没被访问，它就永远占着内存，属于内存泄漏。定期删除是为了弥补这个缺陷：Redis 每隔一段时间（默认每秒 10 次，即每 100ms）执行一次过期扫描，但不是一次性遍历所有过期 key——那样会阻塞，而是随机抽取一部分设置了过期时间的 key 检查并删除，同时限制单次扫描的时间上限，避免长时间占用 CPU；如果一轮里过期 key 比例很高，会继续抽，否则提前结束。两者结合的效果是：热点或常访问的过期 key 靠惰性删除很快清掉，冷门 key 靠定期删除兜底。另外要注意两个延伸点：一是物理删除大 key 时可以用 UNLINK 异步删除，避免阻塞；二是过期删除策略和内存淘汰策略不是一回事——前者针对设置了 TTL 的 key，后者是内存达到 maxmemory 时的兜底机制。

**常见追问**：1）定期删除为什么是随机抽样而不是全量？2）设置过期时间但从不访问的 key 会一直占内存吗？

## 50. Redis有几种内存回收策略

> 原题 ID：`q0425`

**高频程度**：★★★★

**考察点**：Redis 内存回收（淘汰）策略的八种配置，分"不淘汰""有过期时间的 key""所有 key"三类。

**回答框架**：

1）不淘汰：noeviction，内存满则写失败报错；2）只淘汰设置过期时间的 key：volatile-lru、volatile-lfu、volatile-random、volatile-ttl；3）淘汰所有 key：allkeys-lru、allkeys-lfu、allkeys-random；4）LRU 看最近访问、LFU 看访问频率、TTL 看剩余生存时间；5）实践：缓存场景常用 allkeys-lru 或 allkeys-lfu。

**参考回答**：

Redis 的内存回收策略分两大类。第一类是 noeviction，也就是不开启淘汰，当内存达到 maxmemory 上限后，写操作直接报错，但不淘汰已有数据，读操作仍可用；这适合把 Redis 当存储用、数据不能丢的场景。第二类是开启淘汰，细分为两个方向。一个是只在设置了过期时间的 key 里淘汰，有四种算法：volatile-lru（最近最少使用）、volatile-lfu（最不经常使用）、volatile-random（随机）、volatile-ttl（优先淘汰剩余生存时间最短的）。另一个是在所有 key 里淘汰，有三种算法：allkeys-lru、allkeys-lfu、allkeys-random。LRU 关注"最近有没有被访问"，把最久没访问的淘汰掉；LFU 关注"访问频率"，把访问次数最少的淘汰掉，能避免偶发的批量扫描把热点数据挤掉；random 不看任何特征，随机淘汰，实现最简单；ttl 只对有过期时间的 key 有效，优先清掉快过期的。实际选型上，纯缓存场景通常用 allkeys-lru 或 allkeys-lfu，如果希望热点数据长期保留、其余可淘汰，用 allkeys-lfu 更稳；如果业务里既有需要长期保留的数据又有缓存数据，把持久数据不设 TTL、缓存数据设 TTL，用 volatile-lru 更安全。

**常见追问**：1）LRU 和 LFU 在什么场景下表现差异明显？2）maxmemory 该怎么设置？

## 51. 内存回收是什么时候发起

> 原题 ID：`q0426`

**高频程度**：★★

**考察点**：内存回收的发起时机：每次读写命令处理前检查内存是否超过 maxmemory。

**回答框架**：

1）每次执行读写命令时都会检查内存使用是否超限；2）超过 maxmemory 则按策略触发淘汰；3）淘汰在命令执行前的 processCommand 阶段；4）所以是"随访问触发"而非定时任务；5）读命令在超限且 noeviction 时仍可执行。

**参考回答**：

内存回收的发起时机是：每次进行读写操作（更准确说，每条命令处理的入口阶段）都会去检查当前内存使用是否超过了 maxmemory 配置的上限，如果超过了就按配置的淘汰策略释放内存，然后再执行这条命令。所以它不是靠一个独立的定时任务来跑的，而是"随命令触发"的——只要 Redis 在处理请求，就会持续检查。这样设计的考虑是：不额外引入定时扫描的 CPU 开销，且内存压力本身就伴随写操作产生，在命令入口做检查最及时。有几个延伸细节：第一，如果策略是 noeviction 且内存已满，写命令会直接返回 OOM 错误拒绝执行，但读命令（比如 GET、DEL）通常仍可正常执行，因为读不增加内存、删除还能释放内存。第二，淘汰是按配置策略挑 victim key，LRU/LFU 用的是近似采样而不是精确全局排序。第三，如果所有 key 都不符合淘汰条件（比如用的是 volatile-lru 但一个设置了过期时间的 key 都没有），那么淘汰失败，内存继续超限时会退化成拒绝写入。

## 52. 介绍下Redis LRU回收算法

> 原题 ID：`q0427`

**高频程度**：★★★

**考察点**：LRU 的定义与 Redis 的近似 LRU 实现思路。

**回答框架**：

1）LRU = Least Recently Used，最近最少使用，淘汰最久未访问的数据；2）标准 LRU 用哈希表+双向链表，访问时把节点移到表头，淘汰时删表尾；3）Redis 不维护完整链表，而是在 redisObject 里存 24 位 lru 访问时间戳；4）淘汰时随机采样若干 key，挑最久未访问的淘汰；5）3.0 后加淘汰池优化。

**参考回答**：

LRU 是 Least Recently Used 的缩写，也就是最近最少使用，核心思路是记录每个 key 最近一次被访问的时间，淘汰时优先淘汰最久没有被访问到的数据。理论基础是"时间局部性"——刚刚被访问过的数据，接下来很可能还会被访问，而很久没被访问的数据，将来被访问的概率较低。标准的 LRU 实现是哈希表加双向链表：哈希表保证 O(1) 找到节点，双向链表维护访问顺序，每次访问就把节点移到链表头部，淘汰时删除链表尾部。但 Redis 并不是标准的 LRU，因为标准 LRU 需要给每个 key 额外维护链表指针，内存成本大，而且每次访问都要移动节点、还要处理并发。Redis 的做法是近似 LRU：在 redisObject 里用一个 24 位的 lru 字段记录该 key 最后一次被访问的时间戳（实际上是一个全局的 LRU 时钟值），淘汰的时候不遍历所有 key，而是随机采样一批 key，比较它们的 lru 时间戳，挑最旧的淘汰掉；如果淘汰后内存还不够，就继续采样淘汰。3.0 之后还引入了淘汰池，把多次采样中比较旧的候选保留在池子里，进一步提升淘汰的准确性，让近似 LRU 的效果更接近真实 LRU。

**常见追问**：1）为什么不用标准 LRU？2）近似 LRU 的采样数配置是多少？

## 53. Redis LRU算法是标准的吗？为什么不用标准的

> 原题 ID：`q0428`

**高频程度**：★★★★

**考察点**：近似 LRU 的原因与实现：随机采样 n（默认 5）+ 时间戳比较 + 淘汰池优化。

**回答框架**：

1）标准 LRU 要维护双向链表，内存成本巨大（每个 key 加两个指针）；2）近似做法：随机采样 n 个 key，n 默认 5，淘汰其中最旧的；3）内存不足则继续采样淘汰，反复进行；4）3.0 后加入淘汰池：候选池按空闲时间排序，新采样 key 只有更旧才入池，池满则淘汰最旧；5）效果接近真实 LRU，成本极低。

**参考回答**：

Redis 的 LRU 不是标准 LRU。标准 LRU 需要维护一个全局的双向链表，每个 key 都要额外存前后指针，还要在每次访问时把节点移动到链表头，内存成本和时间开销都很大，对 Redis 这种内存敏感、单线程执行的系统不划算。所以 Redis 采用近似 LRU：淘汰时不做全量排序，而是随机采样 n 个 key，这个采样个数默认是 5，由 maxmemory-samples 配置；然后根据 redisObject 里记录的 lru 时间戳，淘汰掉其中最旧的那一个；如果淘汰后内存还是不足，就继续随机采样、继续淘汰，直到内存降到阈值以下。采样数越大越接近真实 LRU，但 CPU 开销也越大，5 是一个经验上效果不错的平衡点。3.0 之后 Redis 又做了淘汰池优化：维护一个候选池，池里的数据按空闲时间排序。第一次采样的 key 都会放进去，淘汰掉最久未访问的；后续每次随机采样的 key，只有它的空闲时间大于池中空闲时间最小的那个 key 时才会入池，池子满了就淘汰池中空闲时间最大的（也就是最旧的）。这样相当于用很小的内存保留了一批"更值得淘汰"的候选，让近似 LRU 的效果更接近真实 LRU，尤其在内存压力大时表现明显更好。

**常见追问**：1）采样数调大有什么影响？2）淘汰池的大小是多少？

## 54. 什么是LFU算法，为什么Redis要引入LFU算法

> 原题 ID：`q0429`

**高频程度**：★★★★

**考察点**：LFU 的定义、与 LRU 的差异（频率 vs 时间）、以及引入原因与计数衰减机制。

**回答框架**：

1）LFU = Least Frequently Used，最不经常使用；2）同时记录访问计数和上一次访问时间；3）计数增长受访问频率影响，且会随时间衰减（对数递增 + 定期衰减）；4）解决 LRU 的痛点：偶发批量访问把热点数据挤出去；5）适用：热点集中、访问分布长尾的场景。

**参考回答**：

LFU 是 Least Frequently Used，也就是最不经常使用，它在淘汰判断里把"访问频率"作为主要因素。具体实现上，LFU 同时记录了上一次访问时间和访问计数：lru 字段被拆成两部分，高 16 位存上次访问时间、低 8 位存访问次数，所以计数最大是 255。访问计数不是简单加一，而是概率性递增——计数越小越容易加，越大越难加，这样能避免老热点长期霸榜；同时计数还会随时间衰减，每隔一段时间（默认 1 分钟）按配置的衰减因子减少，让"曾经热但现在不热"的数据有机会被淘汰。为什么要引入 LFU？因为 LRU 只看"最近有没有被访问"，存在一个典型问题：一次偶发的批量操作或全表扫描式访问，会把大量冷数据标记成"刚访问过"，从而把真正的热点数据挤出内存，后续热点请求全部回源，造成雪崩式压力。LFU 因为看的是访问频率，偶发的一次访问不会显著提升计数，所以更稳。LFU 特别适合热点集中、访问分布是长尾的场景，比如只有少数几个商品被反复访问；如果访问分布本身均匀，LRU 和 LFU 差别不大。使用 LFU 要求 maxmemory-policy 配成 allkeys-lfu 或 volatile-lfu。

**常见追问**：1）LFU 计数为什么设计成 8 位、上限 255？2）衰减机制具体是怎么做的？

## 56. Redis缓存是如何应用的

> 原题 ID：`q0431`

**高频程度**：★★★

**考察点**：旁路缓存（Cache-Aside）的读路径：先查缓存，未命中查库并回填。

**回答框架**：

1）读：先查 Redis，命中返回；2）未命中回源 MySQL 查询；3）查到结果写回 Redis 并设置 TTL；4）查不到时可写空值或短 TTL 防穿透；5）写：更新 DB 后删除缓存（而非更新缓存）。

**参考回答**：

我们的缓存用的是旁路缓存模式（Cache-Aside），在订单项目里的读路径是：请求进来先查 Redis，如果命中就直接返回，不再访问数据库；如果没查到，就去查 MySQL，把查到的数据写回 Redis 并设置一个过期时间，下次同样的请求就能命中缓存。这里有几个细节：第一，写回缓存时一定要设 TTL，作为一致性和内存的兜底，防止缓存永远不更新或者冷数据长期占用内存。第二，如果数据库也查不到，通常有两种处理，要么直接返回空不写缓存（可能被反复穿透），要么写一个带短 TTL 的空值占位，防止缓存穿透，具体看业务对一致性的要求。第三，写路径不是"更新缓存"而是"删除缓存"，也就是先更新数据库、再删掉 Redis 里的 key，让下次读自然回源重建；之所以是删除而不是更新，是因为并发下双写的顺序没法保证，容易旧值覆盖新值，删除更安全。整体上旁路缓存的优点是实现简单、只缓存实际被访问的数据、对强一致要求不高时性能收益很大；代价是要自己处理一致性和缓存异常。

**常见追问**：1）为什么不在写的时候直接更新缓存？2）缓存和数据库都没查到该怎么处理？

## 57. Redis做旁路缓存，如果MySQL更新了，此时何去何从

> 原题 ID：`q0432`

**高频程度**：★★★★

**考察点**：旁路缓存下更新数据库后缓存的处理策略：先更新 DB 再删缓存 + TTL 兜底 + binlog 订阅的取舍。

**回答框架**：

1）策略：更新 DB 后删除缓存（Cache-Aside 标准做法）；2）TTL 兜底，容忍短暂不一致；3）延时双删应对并发；4）binlog/Canal 订阅方案一致性更好但成本高；5）权衡：多数业务最终一致足够，不必强一致；6）不要用锁换强一致，会牺牲并发。

**参考回答**：

旁路缓存下数据库更新了，缓存怎么处理，我用的是"先更新 DB，再删除缓存"，同时用过期时间兜底。之所以删除而不是更新缓存：并发场景下如果写数据库和写缓存是两次独立操作，顺序无法保证，可能出现旧值后写覆盖新值，删除则让下一次读自然回源重建，窗口更小也更安全。TTL 作为最后一道兜底，即使某次删除失败或者有并发脏读，最多也就脏一个 TTL 周期，对大多数业务来说可接受。如果对一致性要求更高，可以叠加延时双删：更新 DB、删缓存之后，隔几百毫秒再删一次，清掉这段时间被并发读回填的旧值。我也评估过订阅 binlog 的方案，用 Canal 监听 MySQL 变更、通过 MQ 通知各节点失效缓存，这种方案一致性最好、覆盖面最全，但额外引入了 Canal、消息队列和消费服务，运维和排查成本明显上升。考虑到我们业务对缓存不一致的容忍度较高（商品、订单列表这类读多写少的场景，短暂脏读影响有限），投入产出不成正比，所以最终选择了先更新 DB 再删缓存加 TTL 的方案。据我了解比如腾讯云、字节飞书的一些团队在大部分场景也是类似选择，甚至有些场景连主动删除都不做，完全靠 TTL。核心判断是：缓存一致性本质是权衡，不是越强越好。

## 58. 缓存一致性如何保证

> 原题 ID：`q0433`

**高频程度**：★★★★★

**考察点**：缓存与数据库一致性方案：Cache-Aside 先写库再删缓存、延时双删、binlog 订阅、分布式锁强一致的取舍。

**回答框架**：

1）原则：不主动更新缓存，并发下更新缓存会出错；2）Cache-Aside：先写库再删缓存，可叠加延时双删；3）更强一致：Canal 订阅 binlog 异步失效；4）强一致：分布式锁串行化读写，但并发性能差；5）结论：按业务容忍度选最终一致即可，TTL 兜底。

**参考回答**：

缓存一致性我的回答分三层。第一层是原则：不要主动更新缓存，而应该删除缓存。因为"更新缓存"在并发下会出问题——两个线程分别更新数据库和缓存，操作顺序交错时会出现旧值后写、覆盖新值，而删除操作只是把状态置为"未命中"，下次读回源拿到的一定是最新库里的值，出错窗口更小。第二层是常用方案，也就是旁路缓存（Cache-Aside）：先更新数据库，再删除缓存；为了应对"删除后又被并发读回填旧值"的极端情况，可以叠加延时双删——写后间隔几百毫秒再删一次；再加 TTL 作为最终兜底，保证即使出问题也能自愈。第三层是更强一致的方案及代价：可以用 Canal 订阅 MySQL binlog，把变更事件通过 MQ 广播给各节点失效缓存，覆盖面和一致性都更好，但引入了额外组件和运维成本；理论上要做到强一致可以用分布式锁把读写串行化，但那样并发性能就没了，实际上基本不会这么用。所以我的结论是：一致性不是免费的，是按业务容忍度选等级。读多写少、能容忍秒级不一致的业务，先写库再删缓存加 TTL 就够了；对一致性要求高的场景才上 binlog 订阅。回答时把"为什么不能更新缓存""为什么不追求强一致"这两个点讲透，比罗列方案更加分。

## 59. Redis做秒杀场景可以吗？讲讲思路

> 原题 ID：`q0434`

**高频程度**：★★★

**考察点**：Redis 做秒杀的思路：库存预热到 Redis、原子扣减、异步落库、可靠性与限流。

**回答框架**：

1）库存预热：活动前把库存写入 Redis；2）扣减：用 Lua 脚本或 DECR 保证原子性，库存不足直接返回；3）结果异步落库：扣减成功后发 MQ 异步创建订单，削峰；4）防超卖：Lua 里判断库存再扣，单线程保证原子；5）限流与防刷：网关限流、一人一单、令牌桶；6）高可用：主从+哨兵或 Cluster，多节点分摊。

**参考回答**：

可以用 Redis 做秒杀的核心链路，思路是"Redis 扛并发扣减、数据库只做异步落地"。第一步，活动开始前把商品库存预热到 Redis，比如一个 key 存剩余库存。第二步，请求到达时用 Lua 脚本做原子扣减：脚本里先判断库存是否大于 0，大于才执行 DECR 并返回成功，否则直接返回售罄，脚本在 Redis 里是原子执行的，所以不会超卖，这是最关键的一步。也可以用 DECR，但 DECR 返回负数时还要再回补，不如 Lua 一次判断干净。第三步，扣减成功的请求不直接写数据库，而是发一条消息到 MQ 异步创建订单和扣减数据库库存，这样把数据库从瞬时高并发中解放出来，实现削峰。第四步，做防刷和限流：网关上做接口限流，业务上做一人一单（用 Set 或 Hash 记录用户是否已购买），防止脚本刷单。第五步是容量和高可用：单节点 Redis 处理六万左右 QPS 问题不大，百万级流量按比例需要多节点分摊，每个节点都要做主从和哨兵或者用集群，避免单点故障。另外要注意，如果对库存准确性要求极高，还需要处理 Redis 扣减成功但 MQ 或落库失败的情况，一般通过本地消息表或事务消息加对账补偿来兜底，保证最终一致。

## 60. 为什么需要引入owner的概念呢

> 原题 ID：`q0438`

**高频程度**：★★★★

**考察点**：分布式锁 owner（唯一标识）的作用：保证锁的对称性，防止释放别人的锁。

**回答框架**：

1）锁要保证对称性：谁加锁谁释放；2）反例：A 加锁后因业务耗时长或 GC 卡顿导致锁过期，B 拿到锁，A 执行完释放了 B 的锁；3）后果：连锁误删，锁失效，业务互斥被破坏；4）做法：value 存唯一标识（UUID/请求ID），释放时用 Lua 比对再删；5）进阶：看门狗自动续期。

**参考回答**：

引入 owner 也就是唯一标识，是为了保证分布式锁的对称性——谁加的锁只能由谁来释放。假设没有这个机制，会出现这样的问题：服务 A 成功获取到了锁，但由于业务流程比较长，或者发生网络延迟、GC 长时间停顿等原因，锁的 TTL 到期自动释放了，而 A 的业务还在继续执行；这时候服务 B 拿到了同一把锁开始执行临界区，之后 A 执行完业务了，去"释放锁"，实际上删掉的却是 B 持有的锁，于是 B 的锁失效了，其他服务 C 又可以进来，互斥就被彻底破坏了。这就是所谓的连锁误删。所以加锁时需要在 value 里写入一个全局唯一标识，比如 UUID 或者请求 ID，释放时先用 Lua 脚本读取当前锁的 value，判断是不是自己写的，是才删除，不是就什么都不做。因为判断加删除必须是原子的，所以要用 Lua，不能分两条命令做。进一步说，即便用 owner 解决了误删，锁过期和业务未完成的矛盾依然存在，所以生产上常用 Redisson 的看门狗机制，在业务还没执行完时自动给锁续期，避免锁提前失效，同时业务侧也要做好幂等，防止极端情况下重复执行。

**常见追问**：1）锁自动续期有什么风险？2）为什么释放锁必须用 Lua 而不能用 del？

## 61. 你提到了lua，用lua一定能保证原子性

> 原题 ID：`q0439`

**高频程度**：★★★★

**考察点**：Lua 脚本"原子性"的真正来源是 Redis 单线程串行执行，而非 Lua 语言本身。

**回答框架**：

1）Lua 本身不具备原子性；2）Redis 单线程执行命令，脚本整段执行期间不会被打断；3）因此脚本内的多个命令对外表现为一个原子操作；4）注意：脚本内没有回滚，出错也不会撤销已执行的写；5）脚本要避免耗时操作，会阻塞整个实例。

**参考回答**：

严格来说 Lua 本身不具备原子性，Lua 语言层面并没有事务回滚或者隔离保证。我们说用 Lua 保证原子性，是因为 Redis 处理命令是单线程的，一段 Lua 脚本提交给 Redis 后会被当作一个整体执行，执行过程中不会插入其他客户端的请求，所以在别的客户端看来，脚本内的多条命令要么都执行完了、要么还没开始，不会看到中间状态，这就是"原子性"的来源——它其实来自 Redis 的单线程串行执行模型，而不是 Lua 语言的语义。举个我们实际用的例子：释放分布式锁时，需要先 GET 判断 value 是不是自己的，再 DEL 删除，这两步如果分开做，中间可能被其他请求插入；打包进 Lua 后就是原子的。不过有两点必须注意：第一，Lua 脚本没有失败回滚，如果脚本执行到一半报错，前面已经执行的写操作不会撤销，所以脚本逻辑要自己保证正确性，别依赖"出错自动回滚"。第二，脚本执行期间整个 Redis 实例是被独占的，所以脚本里不能有耗时操作（比如大 key 遍历、复杂计算），否则会阻塞所有请求；Redis 也有 lua-time-limit 限制，超过后只会打日志和允许 SCRIPT KILL 中断只读脚本，不会自动终止，所以设计上要保证脚本短小。

**常见追问**：1）Lua 脚本执行中超时会怎样？2）想实现回滚语义该怎么办？

## 62. 缓存穿透是什么？怎么解决

> 原题 ID：`q0442`

**高频程度**：★★★★★

**考察点**：缓存穿透的定义、成因（查不存在的数据）、解决方案（缓存空值、布隆过滤器、参数校验、限流）。

**回答框架**：

1）定义：请求的数据缓存和数据库都没有，每次请求都打到数据库；2）成因：恶意攻击伪造大量不存在的 key，或业务参数异常；3）方案一：缓存空值或特殊标记并设短 TTL；4）方案二：布隆过滤器前置拦截，数据库写了才标记；5）方案三：参数校验与非法请求过滤、接口限流；6）权衡：空值方案内存风险，布隆有误判且删除麻烦。

**参考回答**：

缓存穿透是指用户请求的数据在缓存里没有，在数据库里也没有，所以既没法命中缓存，也没法构建缓存来服务后续请求，导致每次这样的请求都会穿透到数据库；当有大量这类请求时，数据库压力骤增。最常见的场景是攻击者伪造了大量不存在的 key，比如用随机 ID 去查用户或商品，造成两个后果：缓存没有对应数据所以落到数据库，数据库也没有数据所以无法回写缓存，下一次同样的请求还会继续落库。解决方案有几类：第一，缓存空值或特殊标记，在缓存未命中且数据库也查不到时，往缓存里写一个特殊值并设置较短的过期时间，下次请求看到这个标记就直接返回空，不再查库；缺点是如果攻击者每次都用不同的、不存在的 key，空值会撑爆内存，所以要配合短 TTL 和限流。第二，布隆过滤器，把数据库里存在的 key 预先哈希到位图里，请求进来先问布隆过滤器，如果它说不存在就直接返回，直接从入口拦掉；优点是内存极省、效率高，缺点是有误判率（说存在可能实际不存在，但说不存在一定不存在），而且标准布隆过滤器不支持删除，数据变更时要谨慎处理，可以用计数布隆或定期重建。第三，在业务层和网关层做参数校验、格式检查和接口限流，把明显非法的请求挡在外面。实际项目里一般是组合使用：布隆过滤器挡大部分 + 空值缓存兜底 + 限流保护，这样既能防攻击，又不会带来太大的内存压力。

**常见追问**：1）布隆过滤器误判会导致什么问题？2）缓存空值的 TTL 设多长合适？

## 63. 布隆过滤器是怎么工作的

> 原题 ID：`q0443`

**高频程度**：★★★★

**考察点**：布隆过滤器的结构（位图 + N 个哈希函数）、写入与查询流程、特点（误判、不可删除）。

**回答框架**：

1）结构：一个初始全 0 的位图数组加 N 个哈希函数；2）写入：数据经 N 个哈希函数得到 N 个哈希值，对数组长度取模定位，把对应位置置 1；3）查询：同样算出 N 个位置，全为 1 则可能存在，有一个为 0 则一定不存在；4）特点：空间效率极高但存在误判，不支持删除；5）用途：缓存穿透前置拦截、去重。

**参考回答**：

布隆过滤器由两部分组成：一个初始值全为 0 的位图数组，和 N 个相互独立的哈希函数。写入数据时，比如数据库里新增了数据 x，就用 N 个哈希函数分别对 x 做哈希计算得到 N 个哈希值，再把这 N 个哈希值对位图数组的长度取模，得到 N 个下标位置，把这些位置的值都设为 1。举个例子：位图长度 8、3 个哈希函数，数据 x 算出的位置是 1、4、6，就把第 1、4、6 位置为 1。查询数据时，同样用这 N 个哈希函数算出 N 个位置，然后看位图上这些位置是否全为 1：如果有一个位置是 0，说明这个数据一定没有被写入过，也就是一定不存在；如果全部是 1，则说明可能存在——注意是"可能"，因为不同数据算出来的位置可能有重叠，别的数据把这些位置置 1 了，就会出现误判。所以布隆过滤器的两个重要特性是：第一，空间效率极高，用几个 bit 就能表示一个元素，适合海量数据的去重和存在性判断；第二，存在误判但不漏判，不支持删除（把某一位清零会影响其他元素的判断）。针对删除需求，业界有计数布隆过滤器（每个位用计数器实现）等变体。在缓存穿透场景里，它作为前置拦截非常有效：数据库里不存在的 key 直接被布隆过滤器挡掉，不会打到缓存和数据库。

**常见追问**：1）怎么降低布隆过滤器的误判率？2）数据删除后布隆过滤器怎么办？

## 64. 缓存雪崩是什么？怎么解决

> 原题 ID：`q0445`

**高频程度**：★★★★★

**考察点**：缓存雪崩的定义、两个典型场景（大量同时过期、Redis 宕机）与对应解决方案。

**回答框架**：

1）定义：大量缓存同时失效或缓存整体不可用，请求全打到数据库造成压力骤增；2）场景一：大量 key 同一时间过期 → 随机 TTL、后台更新、多级缓存、加锁/限流；3）场景二：Redis 宕机或集群故障 → 主从哨兵、集群分片、熔断降级、本地缓存兜底、限流；4）共同点：给数据库加保护和熔断；5）口诀：后台更新、随机、分散、熔断降级。

**参考回答**：

缓存雪崩是指大量缓存数据在同一时间失效，或者 Redis 整体故障，导致本该由缓存承接的流量全部直接打到数据库，数据库压力骤增甚至被打挂，进而引发整个系统崩溃，形成连锁反应。它有两个典型场景。场景一，缓存集中失效：比如为了大促把一批商品放进缓存并统一设置两小时过期，到点后这批 key 同时失效，对这些商品的访问瞬间全落到数据库，形成压力波峰。应对手段是"后台更新、随机、分散、熔断降级"：给缓存过期时间加上随机值，让不同 key 的过期时间分散开，避免同一时刻集体失效；对热点数据用后台定时任务主动更新，不依赖自然过期；对超热点数据做本地多级缓存；对回源加分布式锁或信号量，保证同一 key 只有一个请求去查库，其余等待；再加接口限流保护数据库。场景二，Redis 节点或集群故障：这是更严重的雪崩，流量高峰时一个缓存节点故障甚至整个集群不可用，全部读请求压到数据库。应对手段是架构层面的高可用——主从加哨兵自动故障转移，或者用 Cluster 分片避免单点；同时必须有熔断降级机制，比如 Hystrix/Sentinel 在检测到数据库压力大或调用失败率高时快速失败，返回默认值或缓存兜底；本地缓存作为最后一道防线能挡住一部分读；还可以对非核心业务做降级，比如读旧数据或者直接返回兜底页面。总结一下，雪崩的本质是"流量和缓存容量/可用性错配"，解决思路就是分散失效时间、提升缓存可用性、并且给数据库加保护和熔断。

**常见追问**：1）雪崩和击穿的区别是什么？2）熔断降级具体怎么配置阈值？

## 65. Redis集群架构模式有哪几种

> 原题 ID：`q0446`

**高频程度**：★★★★

**考察点**：Redis 三种集群模式：主从复制、哨兵、切片集群（Cluster），及读写分离特性。

**回答框架**：

1）主从复制：一主多从，写主读从，读写分离提升读能力，但主节点单点、切换要人工；2）哨兵：在主从基础上自动判活、选举、故障转移，解决高可用；3）切片集群 Cluster：16384 个槽分片，多主多从，解决容量和写扩展；4）复制是异步的，有丢数据风险；5）演进关系：主从 → 哨兵 → Cluster。

**参考回答**：

Redis 有三种集群架构模式，是按能力演进的。第一，主从复制：一台主节点加多台从节点，主节点可读写、从节点一般只读，所有写操作在主节点执行后异步同步给从节点，读请求可以分摊到从节点，实现读写分离，提升整体读吞吐。它的优点是简单、基础，缺点是主节点是单点，故障后需要人工切换，而且写能力和内存容量都受限于主节点。第二，哨兵模式：在主从的基础上增加一组哨兵进程，它们不存数据，专门负责监控、判断主节点存活、选举 leader、执行故障转移，把原来的从节点提升为新主节点并通知客户端。它解决了主从模式不能自动故障转移的问题，实现了高可用，但本质还是主从复制，主节点单点写入的容量瓶颈依然存在，而且切换过程中会有短暂不可用和可能的数据丢失。第三，切片集群 Cluster：把数据按 16384 个哈希槽分片到多个主节点，每个主节点再挂从节点，实现多主多从。它同时解决了容量和写扩展的问题——数据分片让内存总量和写能力可以横向扩展，主从复制保证每个分片的高可用。代价是跨槽操作受限、客户端要支持集群协议、运维更复杂。需要注意的重要特性是主从复制是异步的，主节点写完就返回，不等从节点确认，所以故障切换时可能丢失少量数据；对数据安全要求极高的场景可以配置 min-replicas-to-write 等参数降低风险。

**常见追问**：1）主从复制为什么是异步的？2）Cluster 里跨槽的多 key 操作怎么办？

## 66. Redis主从复制过程是怎样的

> 原题 ID：`q0447`

**高频程度**：★★★★

**考察点**：主从复制的全量同步与增量同步流程、replication backlog 与 psync。

**回答框架**：

1）建立连接后从节点发送 PSYNC，主节点判断能否增量：能则只发缺失部分，不能则全量；2）全量同步：主节点 BGSAVE 生成 RDB，同时把期间写命令缓存，发送 RDB 给从节点加载，再补发缓冲区命令；3）增量同步：主节点把写命令写入 replication backlog 环形缓冲区和从节点输出缓冲区，从节点按 offset 追赶；4）断线重连：用 runid + offset 判断可否续传；5）backlog 太小则退化为全量。

**参考回答**：

Redis 主从复制分全量同步和增量同步两种，由从节点发起。从节点连接上主节点后发送 PSYNC 命令，带上自己记录的 runid 和 offset，主节点判断：如果这个从节点之前同步过、且它要的那部分增量还在主节点的复制积压缓冲区（replication backlog）里，就只发缺失的部分，这叫增量同步；否则执行全量同步。全量同步的流程是：主节点在后台执行 BGSAVE 生成 RDB 快照文件，同时把快照生成期间新收到的写命令缓存到缓冲区里；RDB 生成完成后把文件发给从节点；从节点清空自己的数据、加载这个 RDB；加载完之后，主节点再把缓冲区里累积的写命令发送给从节点重放，让从节点跟上主节点的最新状态，至此全量同步完成。之后的正常阶段就是命令传播，主节点每收到一条写命令，就异步地发给所有从节点，同时自己也写入 replication backlog 这个固定大小的环形缓冲区，并把每个从节点的复制偏移量记录下来。如果从节点断线重连，它会带上自己最后的 offset，主节点检查这个 offset 之后的数据是否还在 backlog 里，在就做部分重同步，只补发缺失命令；不在就只能再做一次全量同步。所以 backlog 的大小很关键，配置太小会导致频繁退化成全量同步，一般建议按"平均写入速率 × 预计断线时长"来估算。

**常见追问**：1）backlog 设多大合适？2）全量同步时主节点会阻塞吗？

## 67. Redis 的主从复制模式有什么优缺点

> 原题 ID：`q0448`

**高频程度**：★★★

**考察点**：主从复制模式的优点（读写分离、读扩展、数据冗余）与缺点（写单点、内存受限、异步丢数据）。

**回答框架**：

1）优点：读写分离提升读吞吐与响应速度；2）数据冗余，从节点可做备份、可分担读；3）缺点：写只能主节点，写能力与内存容量受单机限制；4）主节点单点风险，故障需人工或依赖哨兵；5）异步复制，故障切换可能丢数据；6）扩展性有限，容量瓶颈靠 Cluster 解决。

**参考回答**：

主从复制相对单节点的好处主要有三点。第一，读写分离提升了系统的读吞吐：写操作只在主节点执行，读请求可以分散到多个从节点，读能力随从节点数量线性扩展，网站数据的读取速度和承载能力都明显提高。第二，数据冗余与高可用基础：数据在多个节点上都有副本，从节点可以用于备份、做离线分析，主节点故障时也有数据基础进行恢复和切换。第三，为后续的哨兵和集群模式打基础，是从节点扩容、故障转移的前提。它的缺点也很明确。第一，写能力和内存容量仍然受限于主节点这一个单机，因为所有写都必须在主节点完成，主节点内存满了也没法通过加从节点来解决，写入规模遇到瓶颈。第二，主节点存在单点风险，如果没有哨兵，主节点宕机就意味着写服务不可用，需要人工介入切换。第三，主从之间是异步复制，主节点写完就返回客户端，不等从节点确认，所以主节点故障时，还没有同步到从节点的数据就丢了，这在没有开启 min-replicas-to-write 等参数时是真实存在的风险。第四，从节点太多时主节点的复制压力（网络带宽、CPU）也会增大，一般会有级联复制或限制从节点数量。所以主从复制解决的是"读扩展和冗余"，没解决"写扩展和容量"，后者要交给 Cluster 分片集群。

**常见追问**：1）怎么降低异步复制丢数据的风险？2）主从延迟很大时读从节点会有什么问题？

## 68. 哨兵机制的工作原理

> 原题 ID：`q0450`

**高频程度**：★★★★

**考察点**：哨兵机制工作原理四步：判活（主观/客观下线）、选 leader、选新主、通知客户端。

**回答框架**：

1）判活：哨兵周期性 PING 主节点，超时先标记主观下线，再询问其他哨兵，达到 quorum 票数标记客观下线；2）选 leader：候选者拉票，每个哨兵一票，过半且超过阈值当选；3）选新主：从从节点中按优先级、复制偏移量、runid 排序选出最优者；4）通知客户端：通过发布订阅推送新主地址，客户端切换；5）此后旧主恢复后降为从节点。

**参考回答**：

哨兵机制的工作原理可以用"判活、投票选 leader、选新主、通知客户端"四步来记。第一步判活：每个哨兵会周期性地给主节点和其他哨兵发送 PING 命令来判断存活——注意 Redis 的心跳用的是 PING 命令而不是传统 TCP 心跳，更贴合自身协议。如果 PING 响应超时，哨兵先把该节点标记为主观下线（主观是因为只是自己认为）；然后它会向其他哨兵询问，如果达到配置的 quorum 数量的哨兵都认为这个主节点下线了，就标记为客观下线，这才算真正认定故障。第二步，投票选 leader：因为哨兵集群里多个哨兵都可能发现故障，需要选一个 leader 来主导故障转移。判断主节点客观下线的哨兵可以成为候选者，候选者向其他哨兵发送命令请求投票，每个哨兵只有一票，可以投给自己或别人，但只有候选者能投给自己；候选者拿到半数以上的赞成票且票数达到配置阈值，就成为 leader。第三步，选新主节点：leader 从剩余的从节点里挑选一个作为新主节点，选择依据一般优先看从节点优先级（replica-priority），优先级相同则比较复制偏移量（offset 越大说明数据越新），再相同就比较 runid 大小，同时会排除网络状态不好、与旧主断开时间过长的节点。第四步，通知客户端：选出新主后，哨兵通过发布订阅机制把新主节点的地址推送给客户端，客户端感知后切换连接；同时把旧主节点降级为从节点，等它恢复后自动作为从节点加入。这个过程实现了无人值守的自动故障转移，是高可用的核心。

**常见追问**：1）quorum 和 majority 有什么区别？2）为什么心跳用 PING 不用 TCP？

## 69. Redis sentinel（哨兵）模式优缺点有哪些

> 原题 ID：`q0451`

**高频程度**：★★★

**考察点**：哨兵模式的优点（自动故障转移、高可用）与缺点（主节点单点、切换期不可用、可能丢数据）。

**回答框架**：

1）优点：自动监控与故障转移，无需人工介入，实现高可用；2）客户端可通过哨兵自动感知新主；3）缺点：本质仍是主从，主节点单点写入，容量和写能力受限；4）切换期间有短暂不可用，客户端可能报错重连；5）异步复制导致切换可能丢少量数据；6）哨兵本身需多数派存活，部署建议奇数个。

**参考回答**：

哨兵模式的优点主要是实现了高可用和自动化。它能在主节点故障时自动完成检测、选举和故障转移，不用人工介入，显著缩短故障恢复时间；客户端通过哨兵感知主节点地址变化，也能自动切换，配合起来系统可用性比裸主从高很多；同时哨兵本身是集群部署、多数派决策，避免了单点判断失误。缺点方面：第一，它本质上还是主从模式，数据只有一份主副本，主节点依然是单点写入，写能力和内存容量都受限于单机，哨兵只解决"挂了怎么办"，不解决"装不下怎么办"。第二，主从切换过程存在一段不可用窗口，从发现下线、选举 leader 到选新主、通知客户端，客户端在这期间可能报错或连接失败，需要客户端有重试和容错逻辑。第三，因为主从复制是异步的，切换时还没有同步到从节点的那部分写数据会丢失，对一致性要求高的业务要评估这个风险，也可以用 min-replicas-to-write 参数牺牲一点可用性来降低丢数据概率。第四，哨兵自身需要多数派存活才能完成选举，所以部署上一般用奇数个（3 个或 5 个）并分布在不同故障域，如果哨兵多数派都挂了，故障转移就无法进行。

**常见追问**：1）min-replicas-to-write 怎么用？2）哨兵和 Cluster 该选哪个？

## 70. 说说 Redis 哈希槽的概念

> 原题 ID：`q0452`

**高频程度**：★★★★

**考察点**：Redis Cluster 的哈希槽概念：16384 个槽、CRC16 取模定位、节点负责部分槽。

**回答框架**：

1）Cluster 不用一致性哈希，用哈希槽；2）总共 16384（2^14）个槽；3）key 通过 CRC16 校验后对 16384 取模得到槽号；4）每个主节点负责一部分槽，槽可以迁移；5）客户端根据槽路由到对应节点，MOVED/ASK 重定向。

**参考回答**：

Redis Cluster 没有使用一致性哈希，而是引入了哈希槽的概念。整个集群一共有 16384 个哈希槽，也就是 2 的 14 次方。定位一个 key 属于哪个节点的方式是：先对 key 做 CRC16 校验计算出一个 16 位的值，然后用这个值对 16384 取模，得到的结果就是该 key 所属的槽号；集群中每个主节点负责一部分连续的或不连续的槽，比如三个节点就平均分，每个负责 5461 个左右。客户端连接任意一个节点发起请求时，节点会计算 key 的槽号，如果这个槽归自己管就直接处理，不归自己管就返回 MOVED 重定向告诉客户端应该去哪个节点；槽正在迁移过程中则可能返回 ASK。这样做的好处是：第一，分片粒度是槽而不是 key，节点的增删只需要迁移对应的槽，运维更简单；第二，槽和节点的映射关系是全局元数据，集群可以很容易地做再平衡；第三，槽数量远大于节点数量，便于均匀分配和按需倾斜。另外还有一个知识点：如果业务希望某些 key 落在同一个槽，可以用 hash tag，也就是在 key 里用花括号包住的部分来计算 CRC16，比如 user:{1001}:name 和 user:{1001}:age 会被分到同一个槽，这样多 key 操作和事务就能正常执行。

**常见追问**：1）为什么不用一致性哈希？2）hash tag 有什么使用风险？

## 71. 为什么Redis的哈希槽是16384个

> 原题 ID：`q0453`

**高频程度**：★★★★

**考察点**：哈希槽数 16384 的原因：心跳包大小（位图 2KB vs 8KB）、节点数上限、集群规模与网络开销的权衡。

**回答框架**：

1）心跳携带槽位图，16384 位 = 2KB，若用 65536 则是 8KB；2）槽位图在心跳里频繁传输，2KB 网络开销可接受；3）16384 个节点规模对集群已足够（官方建议不超过 1000 节点）；4）槽位数远大于节点数，便于均匀分配；5）奇数 vs 2 的幂的历史权衡，实际是 2^14 的位图大小与扩容需求平衡的结果。

**参考回答**：

哈希槽是 16384 个，主要有两个考虑。第一，是心跳消息的大小问题。Cluster 节点之间要定期发送心跳包，心跳包里需要带上自己的槽位图，表示"我负责哪些槽"。如果用位图表示，16384 个槽需要 16384 个 bit，也就是 2KB；如果槽数是 65536，位图就变成 8KB。这些心跳消息是周期性、全节点互相发送的，节点数一多，网络开销和内存开销会被放大好几倍，2KB 是作者认为可接受的平衡点。第二，是集群规模的现实考虑。Redis Cluster 官方建议的节点规模上限在 1000 个左右，16384 个槽分配到这些节点上，平均每个节点还有十几个槽，足够做均匀分配和细粒度再平衡；而如果只有几百个节点，65536 个槽完全是浪费，每个槽都要维护元数据、参与迁移计算。另外还有一个历史点和容量判断：哈希槽数量远大于节点数是为了让槽可以作为"最细粒度的迁移单位"，扩容时只需搬一部分槽，而不需要重新分配整个 key 空间。所以结论是 16384 是在"心跳包大小"和"集群可扩展规模"之间权衡出来的经验值，不是理论上唯一正确，而是工程上够用且开销合理。

**常见追问**：1）为什么槽数是 2 的幂？2）超过 1000 个节点会有什么问题？

## 72. Redis的keys命令有什么问题

> 原题 ID：`q0454`

**高频程度**：★★★★★

**考察点**：KEYS 命令的性能与阻塞问题、生产禁用原因、SCAN 游标替代方案。

**回答框架**：

1）性能问题：KEYS 遍历整个键空间，key 多时非常耗时；2）阻塞问题：单线程执行，期间阻塞所有其他客户端请求；3）生产环境一般直接禁用；4）替代方案 SCAN：游标分批遍历，非阻塞；5）SCAN 参数：MATCH 模式、COUNT 提示、游标 0 开始到 0 结束；6）注意 SCAN 不保证不重复、只保证在遍历期间存在的元素都被返回。

**参考回答**：

KEYS 命令的问题主要有两个。第一是性能问题：KEYS 需要遍历整个 Redis 的键空间，如果 key 数量非常庞大（几十万上百万），遍历过程非常耗时，CPU 时间被大量占用。第二也是更致命的，是阻塞问题：Redis 是单线程处理命令的，KEYS 执行期间会阻塞所有其他客户端对数据库的访问，直到它执行结束，也就是说这期间整个 Redis 几乎停止响应其他请求，会导致服务不可用或响应极慢，所以生产环境一般是禁止使用 KEYS 的，很多公司会在配置里直接用 rename-command 禁掉它。替代方案是 SCAN 命令，它通过游标（cursor）的方式分批遍历 key 空间，每次只返回一小部分，不会长时间阻塞 Redis。用法是 SCAN cursor [MATCH pattern] [COUNT count]，其中 cursor 初始值为 0，每次调用返回一个新游标，直到返回 0 表示遍历完成；MATCH 用模式匹配过滤 key；COUNT 是每次遍历的提示数量，默认 10，调大能加快遍历但会增加单次阻塞时间。使用 SCAN 有个重要特点要注意：它只保证在遍历期间一直存在的元素会被返回，但不能保证不重复返回，也不保证返回严格完整——因为遍历过程中如果发生了 rehash 或数据变更，可能有元素被返回多次或漏掉，所以业务上要容忍重复并做幂等。除了 SCAN，还有 HSCAN、SSCAN、ZSCAN 分别用于遍历 Hash、Set、ZSet 的元素。

**常见追问**：1）SCAN 的 COUNT 调大会有什么影响？2）SCAN 为什么可能返回重复元素？

## 75. Redis中的大key怎么处理

> 原题 ID：`q0457`

**高频程度**：★★★★

**考察点**：大 Key 的问题（内存、网络、持久化、阻塞）与处理手段（拆分、集群、压缩、渐进删除、业务优化）。

**回答框架**：

1）问题：占用大量内存、读写网络传输延迟、持久化耗时占空间、删除/过期阻塞；2）拆分：按业务规则把大 key 拆成多个小 key（大 Set 拆多个、大 Hash 分桶）；3）集群分片：靠 Cluster 把 key 分散到不同节点降低单节点压力；4）压缩 value 减少体积；5）渐进删除：hscan+del 分批清或 unlink 异步删；6）从业务上重新评估是否真需要存这么大。

**参考回答**：

Redis 大 key 是指某个 key 对应的 value 数据量很大，比如一个几 MB 的 String、一个上百万成员的 Hash 或 Set。它带来的问题主要有四个：第一，内存占用大，单个 key 吃掉大量内存，可能导致实例内存紧张、触发淘汰甚至 OOM；第二，网络传输延迟，读写大 key 时单个请求要传输的数据包很大，不仅这个请求慢，还会占用带宽影响其他请求；第三，持久化开销，RDB 生成和 AOF 重写时大 key 会拖慢速度、占用更多磁盘空间；第四，删除和过期时阻塞，单线程删除大 key 释放内存可能卡住几百毫秒甚至更久。处理方法有几种：第一，拆分，这也是最根本的，按业务规则把大 key 拆成多个小 key，比如一个百万成员的 Set 按 ID 哈希拆成若干个几千成员的 Set，大 Hash 用分桶方式拆成 user:info:{id%100} 这样的小 Hash；第二，用 Cluster 集群分片，把 key 分散到不同节点的槽上，降低单节点的存储和访问压力；第三，对 value 做压缩，减少存储占用和网络传输量；第四，对已经存在的大 key 做渐进式清理，用 HSCAN 加 HDEL 分批删，或者直接用 UNLINK 异步删除，避免一次 DEL 阻塞主线程；第五，从业务层面重新审视，很多时候大 key 是设计问题，比如把本该分页查的数据整个塞进一个 key，应该改成按需查询或分片存储。整体思路是"预防为主、发现要早、处理要渐进"。

**常见追问**：1）UNLINK 和 DEL 的区别是什么？2）拆大 key 后怎么做数据迁移？

> 原题 ID：`q0458`

**考察点**：热 Key 的五种发现方式：hotkeys 指令、MONITOR 统计、客户端埋点、代理层统计、离线数据分析。

**参考回答**：

发现高并发系统里的热点数据（热 key）有五种常用方式。第一是 redis-cli --hotkeys 指令，Redis 4.0 起在 redis-cli 中提供，原理是向 Redis-server 发送 scan 加 OBJECT FREQ 命令遍历分析实例中所有 key，返回热 key 信息。它有几个问题：前提条件是把淘汰策略 maxmemory-policy 设为 LFU（volatile-lfu 或 allkeys-lfu）；实时性差，需要扫描整个 keyspace，扫描时间和 key 数量正相关，key 多时耗时非常长；信息不够丰富，记录的访问频率是与访问次数对数成比例的近似值，不能直观看出真实频次，也不返回 key 类型和热点出现时间。第二是用 MONITOR 命令统计，短时抓取命令流后在客户端聚合分析热点 key，它的优点是直观、能拿到真实命令，缺点是 MONITOR 本身开销大，只能短时间用，不适合长期监控。第三是客户端埋点，在 SDK 或业务代码里统计每个 key 的访问次数，定期上报汇总，这是最实时、最安全的方式，不占用 Redis 资源，缺点是要求客户端统一接入。第四是代理层统计，如果架构里有 Redis 代理（比如 Codis、Twemproxy 或自研代理），可以在代理层做统计，对业务透明。第五是离线分析，基于 RDB 或命令日志做离线统计，不影响线上但实时性差。实践中最推荐的是"客户端埋点做实时监控 + 代理层做全局统计"，因为热 key 的应对需要秒级发现，而 --hotkeys 这类扫描方案更适合低峰期做定期巡检。

## 77. 什么是延迟双删，用于解决什么问题

> 原题 ID：`q0459`

**高频程度**：★★★★★

**考察点**：延迟双删的流程、解决的问题（并发回填脏数据、主从延迟回填）、适用场景与局限。

**回答框架**：

1）流程：删除缓存 → 更新数据库 → 延迟一段时间 → 再删缓存；2）解决的问题一：更新前读请求读到旧值并回填缓存导致脏数据长期存在；3）解决的问题二：读写分离下从库延迟，读到旧数据回填缓存；4）延迟时长的选择；5）局限：不能保证强一致，仍需 TTL 兜底，延迟时间难精确。

**参考回答**：

延迟双删是一种解决缓存与数据库一致性问题的策略，专门针对写操作后缓存可能残留脏数据的场景。它的流程是四步：第一步，先删除缓存，让旧数据快速失效，防止在更新过程中被读到；第二步，更新数据库，保证数据持久化；第三步，延迟一段时间，比如几百毫秒，这个延迟是为了等并发读请求的旧值回填完成、或者等主从同步完成；第四步，再删除一次缓存，把这段时间内可能被回填的旧数据清掉。它解决的是两类具体问题。第一类是并发读写导致的脏数据：更新数据库之前，如果有个读请求发现缓存未命中，去数据库读到了旧值，然后回填到缓存；等写操作把数据库更新完之后，缓存里其实还是旧值，而且如果不删就会被长期读到，第二次删除就是清掉它。第二类是主从延迟：读写分离架构下，写走主库、读走从库，主库更新后从库还没同步，此时读请求从从库读到旧数据并回填缓存，第二次删除同样能清掉这个脏值。要注意它的局限：第一，它降低不一致窗口但不能保证强一致，最终还是要靠 TTL 兜底；第二，延迟时间是经验值，太短盖不住并发回填，太长又拖慢一致性，需要结合业务压测确定；第三，第二次删除如果失败，还得靠消息重试或 TTL。所以它适合对一致性有一定要求但能接受短暂不一致的业务，比如订单、支付状态的缓存。

**常见追问**：1）延迟时间怎么确定，有没有更精确的方案？2）双删失败怎么办？

## 78. 如果硬件内存特别大，MySQL 缓存能否替代 redis

> 原题 ID：`q0486`

**高频程度**：★★★

**考察点**：MySQL 面向磁盘设计 vs Redis 面向内存设计，无法靠加大内存互相替代。

**回答框架**：

1）设计目标不同：MySQL 各模块（buffer pool、日志、事务并发）首要目标是降低 IO 代价，不是降低内存访问代价；2）访问路径：MySQL 查数据要查页、走 B+ 树 O(logN)，Redis 用 Hash 可 O(1)；3）更新开销：MySQL 为保证隔离性要加锁、为持久性要刷 redo/binlog，Redis 更新不加锁、可不持久化；4）结论：内存再大也改变不了架构定位；5）正确姿势：两者协同而非替代。

**参考回答**：

我认为不能替代，关键原因是两者的设计目标根本不同。MySQL 的所有模块，包括 buffer pool、日志技术、事务并发控制，都是面向磁盘页设计的，它的首要目标是降低 IO 代价，而不是降低内存访问代价，所以代码里充满了页管理、刷脏、日志和锁的逻辑；而 Redis 是从头到尾面向内存设计的数据库。具体差异有三点：第一，访问路径不同。MySQL 即使数据都在 buffer pool 里，查询也要先查页、走 B+ 树的搜索过程，时间复杂度是 O(logdN)，还有 SQL 解析、优化器、执行器层层开销；而 Redis 提供多种数据结构，比如 Hash 对象可以 O(1) 直接定位。第二，更新开销不同。MySQL 为了保证事务隔离性必须加锁，为了持久性要刷 redo log 和 binlog，一次更新涉及多个模块；Redis 的更新不需要加锁（单线程天然串行），而且可以选择不持久化，写路径短得多。第三，语义能力不同。Redis 的数据结构和原子命令能直接表达计数、排行、去重、队列等模型，MySQL 要靠 SQL 组合实现且性能差。所以即使 buffer pool 无限大、磁盘 IO 都被缓存掉，MySQL 的架构开销（锁、日志、解析、事务）依然存在，它优化的方向就不是为超高 QPS 的 KV 访问服务的。正确的做法是让两者协同：MySQL 做权威存储和复杂查询，Redis 做热点缓存和高速原子操作。

**常见追问**：1）MySQL 8 的查询缓存和 Redis 缓存有什么区别？2）如果只是简单 KV 场景，能只用 MySQL 吗？

## 79. MySQL事务和Redis事务有什么区别

> 原题 ID：`q0535`

**高频程度**：★★★★

**考察点**：Redis 事务与 MySQL 事务的区别：原子性（无回滚）、持久性、隔离性、使用方式。

**回答框架**：

1）MySQL 支持完整 ACID；2）Redis 事务不保证原子性：命令执行中途出错不停止不回滚，继续执行剩余命令，可能半成功；3）不保证持久性：RDB/AOF 都不能确保不丢数据；4）隔离性：靠单线程串行执行，而非锁/MVCC；5）命令：MULTI/EXEC/DISCARD/WATCH；6）本质：Redis 事务是"命令打包顺序执行"而非真正的事务。

**参考回答**：

MySQL 事务和 Redis 事务有本质区别：MySQL 事务实现了完整的 ACID 四大特性，而 Redis 事务不保证原子性和持久性。先看原子性：Redis 事务没有回滚功能，做不到像 MySQL 那样"要么全成功要么全失败"。Redis 事务分两个阶段，MULTI 开启事务后命令先入队，EXEC 时一次性按顺序执行，如果中途某条命令执行出错，它不会停止也不会回滚已经执行的部分，而是继续执行后面的命令，所以可能出现半成功的状态。需要区分两类错误：一类是入队时就发现的错误（比如命令不存在、语法错），EXEC 会整体拒绝执行；另一类是运行时错误（比如对 String 执行 LPUSH、类型不匹配），只有那条命令失败，其他命令照常执行且不会回滚。再看持久性：Redis 无论用 AOF 还是 RDB，都不能保证数据绝对不丢——RDB 有快照间隔，AOF everysec 也可能丢 1 秒，所以不具备持久性保证。隔离性方面，Redis 靠的是单线程串行执行命令，天然不会被其他请求打断，而不是像 MySQL 那样靠锁和 MVCC。相关命令是 MULTI 开启事务、EXEC 执行、DISCARD 放弃、WATCH 监视 key（如果被其他客户端修改则事务失败，这是一种乐观锁）。所以更准确地说，Redis 事务是"命令打包顺序执行"的批处理机制，而不是带 ACID 的事务；如果需要真正的事务语义，应该用 Lua 脚本（能保证中间不被插入，但同样没有回滚）。

**常见追问**：1）RUNTIME 错误和入队错误怎么区分处理？2）WATCH 能替代锁吗？

## 80. CPU 缓存对程序性能的影响都体现在哪些方面

> 原题 ID：`q0604`

**高频程度**：★★★

**考察点**：局部性原理（时间/空间）、CPU Cache 的加载策略与命中、对程序性能的影响。

**回答框架**：

1）局部性原理：时间局部性（刚访问的数据可能再访问）、空间局部性（相邻数据可能被访问）；2）Cache 按缓存行加载，一次读一整块而非单个数据；3）命中则无需访问内存，速度快几个数量级；4）性能体现：数组顺序遍历远快于链表随机访问、多维数组按行遍历更快、伪共享问题；5）实践：提高数据局部性、减少随机内存访问。

**参考回答**：

CPU 缓存对程序性能的影响基于程序的局部性原理。局部性分两种：时间局部性指一个数据刚被访问过，那么它很可能马上还会被访问；空间局部性指一个数据被访问时，它附近地址的数据很可能也会被访问到。CPU Cache 就是利用局部性原理设计的：访问数据时，如果目标不在 Cache 中，它不会只从内存读这一个数据，而是把相邻的一整块数据（一个缓存行，通常 64 字节）连续加载进 Cache，这样相邻数据后续访问就能直接在缓存中命中，无需访问内存。这带来几方面性能影响：第一，顺序访问和随机访问差距巨大，数组顺序遍历能充分利用缓存行，性能可以是链表/树随机访问的好几倍，因为后者的指针跳转破坏了空间局部性，每次都可能 Cache 未命中；第二，多维数组的遍历顺序影响很大，按行遍历（内存连续）比按列遍历快得多；第三，多核场景下存在伪共享问题，两个线程分别修改同一缓存行里的不同变量，会互相使对方的缓存行失效，导致性能下降，解决办法是做字段填充或对齐到缓存行；第四，缓存分层（L1/L2/L3）和容量有限，热点数据集越小越容易留在缓存里，所以数据结构设计要考虑"工作集"大小。实践结论就是：写代码时尽量提高数据和指令的局部性，减少随机内存访问和缓存行跳转，这也是为什么 Java 里数组比 LinkedList 快、Redis 用紧凑的 ziplist/listpack 省内存又快的底层原因。

**常见追问**：1）什么是伪共享，怎么解决？2）缓存行大小为什么是 64 字节？

## 82. 如何设计一个本地缓存？需要考虑哪些方面

> 原题 ID：`q0990`

**高频程度**：★★★★

**考察点**：本地缓存设计要点：数据结构、容量上限、淘汰策略、过期时间、线程安全、接口设计、持久化。

**回答框架**：

1）数据结构：哈希表做查找，链表/跳表做淘汰顺序；2）容量上限：设定最大条目数或内存上限；3）淘汰策略：LRU/LFU/FIFO/W-TinyLFU，Caffeine 用 W-TinyLFU 兼顾命中率；4）过期时间：TTL 加惰性/定时清理，与淘汰策略形成双重保障；5）线程安全：多线程访问，用分段锁/CAS 保证，不对使用者暴露；6）接口：get/put/remove/clear/size；7）可选：持久化、统计指标、防缓存击穿的回源合并。

**参考回答**：

设计一个本地缓存，我会从这几个方面考虑。第一，数据结构：底层一般用哈希表保证 O(1) 查找，同时要维护淘汰顺序，LRU 用双向链表（哈希表加链表），LFU 用频率桶或最小堆。第二，容量上限：本地缓存受 JVM 堆内存限制，必须设上限，可以按条目数（比如 1024）或者按内存占用估算，超过上限就触发淘汰。第三，淘汰策略：常见有 LRU、FIFO、LFU，现代方案还有 W-TinyLFU，它用窗口加频率草图，能同时缓解 LRU 偶发批量访问污染和 LFU 老热点霸榜的问题，命中率通常更好，Caffeine 用的就是它。第四，过期时间：除了容量淘汰，还给每个条目设 TTL，做惰性删除（访问时判断）加定期清理，形成"容量淘汰 + 时间过期"双重保障，避免脏数据长期存在。第五，线程安全：本地缓存会被多线程并发访问，线程安全不应该抛给使用者，要在内部保证，实现上可用分段锁、ConcurrentHashMap 加 CAS、或者类似 Caffeine 的 ring buffer 异步维护顺序来降低锁竞争。第六，接口设计：提供 get、put、remove、clear、size 这些常用操作即可，保持简洁；还可以加 getIfAbsent/load 这种回源方法，以及统计命中率、淘汰数等指标，便于监控。第七，可选的进阶点：是否需要持久化（重启恢复）、是否要做请求合并防止缓存击穿、是否要暴露失效通知以便多实例一致。落到实践，多数场景直接用 Caffeine 就好，自研要权衡复杂度，尤其是高并发下的锁竞争和 GC 压力是最大的坑（大对象常驻堆容易触发 Full GC）。

**常见追问**：1）W-TinyLFU 相比 LRU 的优势在哪？2）本地缓存对象太多导致 GC 压力大怎么办？

1）LLM 路由优点：语义理解强、能处理长尾和模糊请求、泛化好、可动态选最合适 Agent；缺点：有延迟和成本、可能不稳定或选错、难调试难审计；2）规则路由优点：确定性、快、零额外调用、易审计、成本低；缺点：僵化、难覆盖长尾、维护成本高、无法应对未见意图；3）混合方案：规则粗筛 + LLM 终判；4）工程增强：路由结果缓存、置信度阈值 + 兜底降级、日志与评测。

**参考回答**：

这两种路由各有优劣。LLM 路由的优点是语义理解能力强，能处理模糊、口语化、长尾的请求，可以综合上下文动态判断该交给哪个 Agent，泛化能力好，新增 Agent 时只要改提示词和描述，不用改代码逻辑；缺点是每次路由都要花一次 LLM 调用的延迟和成本，输出不稳定可能选错，而且路由决策是黑盒，出了问题难以调试和审计。规则路由的优点是确定性强、响应快、零额外模型调用、成本几乎为零、结果可解释可审计，出问题容易定位；缺点是僵化，靠关键词和正则很难覆盖表达多样的长尾请求，业务一变化就要改规则、维护成本持续上升，遇到没预设过的意图基本失效。所以实践上最好做混合路由：先用规则或轻量分类器做粗筛，把明显属于某一类的请求快速分流，剩余的模糊请求再交给 LLM 做终判；同时给 LLM 路由加缓存，相同或相似请求直接复用历史决策，降低成本和延迟；再设置信度阈值，LLM 判断不确定时走兜底策略（比如交给通用 Agent 或追问澄清）；最后把路由决策和结果打日志、定期做离线评测，保证路由质量可观测。这样做的好处是既拿到了规则的快和稳，又用 LLM 兜住了长尾。

**常见追问**：1）LLM 路由怎么评估准确率？2）路由错了导致任务失败怎么补偿？

## 84. 知识库特别大（章节巨多、内容巨长）时，Agentic RAG 的成本和时延怎么压下来？

> 原题 ID：`q1152`

**高频程度**：★★★★

**考察点**：大规模知识库下 Agentic RAG 的成本与延迟压缩：两级索引、元数据预过滤、缓存、模型分级、并行与截断、流式。

**回答框架**：

1）两级索引：目录/摘要粗排（小模型快速筛候选章节）+ 命中章节精读原文；2）元数据预过滤：按时间/类目/来源/权限先砍掉无关大块；3）结果缓存：高频问题与公共知识的检索结果复用；4）模型分级：路由和判定用小模型，只在最终综合用大模型；5）并行与截断：候选检索并行、上下文按相关性截断到预算内；6）异步流式：检索与生成流水线化掩盖时延。

**参考回答**：

知识库特别大时，成本和时延主要来自"把太多内容塞进上下文"和"反复调用大模型"，所以核心思路是粗排前置、按需精读、资源分级。具体做法：第一，建两级索引——先做一个轻量的目录或摘要索引，比如章节标题加一句话摘要，检索时先用小模型在这层快速筛出候选章节，再只对命中的少数章节加载并精读原文，避免把全量文档都塞进上下文，这一步通常能砍掉绝大部分 token。第二，元数据预过滤——用时间、类目、来源、权限这些标量条件先过滤，把明显无关的大块数据排除在检索范围外，既提精度也降成本。第三，缓存——对高频问题和公共知识，把检索结果甚至最终答案缓存起来复用，特别是知识更新不频繁的场景收益很大。第四，模型分级——查询改写、相关性判定、粗排这些小任务用小模型或本地模型，只在最后的答案综合和复杂推理环节用大模型。第五，并行与截断——多路检索并行执行降低总延迟，召回的上下文按相关性打分排序后截断到 token 预算内，只保留最有价值的片段。第六，异步和流式——把检索和生成做成流水线，边检索边生成，用流式输出掩盖首 token 之前的等待时间，用户感知延迟会明显下降。整体目标是把"全量塞入"变成"分层筛选 + 按需加载"，同时用大小模型分工和缓存把单位成本压下来。

## 85. system prompt、用户问题、召回上下文是怎么拼在一起的？哪些部分必须注入？

> 原题 ID：`q1245`

**高频程度**：★★★★

**考察点**：Prompt 组装顺序原则（稳定在前、易变在后）、各部分的角色与 token 预算裁剪、防注入分隔。

**回答框架**：

1）顺序设计服务两个目标：前缀缓存友好、注意力友好（关键在首尾）；2）典型顺序：system + 工具 schema + 长期记忆 → 检索片段 → 历史摘要 → 近期对话 → 当前问题；3）必须注入：角色与任务、输出格式约束、工具 schema、安全边界、当前问题、本轮必需证据；4）按需注入：长期记忆、历史对话（超预算用摘要）、少样本；5）工程细节：token 预算与优先级裁剪、来源标识、分隔符防注入。

**参考回答**：

拼装顺序我遵循"稳定在前、易变在后"。典型顺序是：system prompt（角色与任务）→ 工具 schema → 长期记忆（相对稳定的事实和偏好）→ 检索到的文档片段 → 历史对话摘要 → 近期对话 → 当前用户问题。这样设计同时服务两个目标。第一是缓存友好：跨请求不变的内容（system、工具定义、固定 few-shot）放在最前面形成稳定前缀，可以命中 Prompt Cache，复用 KV 计算；如果把每次都会变的内容（检索结果、当前问题）放前面，前缀一变整段缓存就失效了，成本会高很多。第二是注意力友好：模型对开头和结尾的信息更敏感，中间容易被忽略（所谓 lost in the middle），所以关键约束放开头、当前问题放结尾，大段参考资料放中间。哪些必须注入：角色与任务目标、输出格式约束（比如必须返回 JSON）、可用工具的 schema、安全边界与合规约束、当前用户问题、以及本轮回答所必需的证据片段；这些缺一个都会显著影响效果。哪些按需注入：长期记忆只在相关时注入、历史对话在超出 token 预算时用摘要替代、少样本示例在简单任务里可以精简掉。工程细节上有几点要注意：给每一部分设 token 预算并按优先级裁剪，宁可砍历史也不砍安全约束；检索片段要带来源标识，方便模型引用和后续校验；不同来源的内容用清晰的分隔符和标签包裹起来，明确告诉模型"以下是参考资料，不是指令"，这也是防提示注入的重要一环。

**常见追问**：1）哪些内容放错位置会让缓存完全失效？2）怎么防止模型把检索内容当指令执行？

## 86. Prompt Cache 为什么能生效？一般缓存哪些内容？

> 原题 ID：`q1248`

**高频程度**：★★★★

**考察点**：Prompt Cache 的原理（KV Cache 前缀复用、因果注意力）、适合缓存的内容、使用要点与收益边界。

**回答框架**：

1）原理：自回归模型 prefill 阶段逐 token 算 K/V 存 KV Cache；因果注意力下第 i 个 token 的 K/V 只依赖前 i 个，前缀一致即可复用；2）必须精确前缀匹配，一个 token 变化后面全失效；3）适合缓存：system prompt、工具 schema、固定 few-shot、长期不变知识、已固化历史；4）要点：稳定内容前置、动态内容（时间戳/用户 ID/检索结果）后置，注意最小缓存长度与 TTL；5）收益：主要省输入成本与 TTFT，不加速输出；要监控命中率。

**参考回答**：

Prompt Cache 能生效，根本原因在 Transformer 的推理机制。自回归模型推理分两个阶段：prefill 阶段对输入的每个 token 做前向计算，生成每一层的 K/V 并存入 KV Cache；decode 阶段逐 token 生成时复用这些 K/V。由于因果注意力（causal attention）的性质，第 i 个 token 的 K/V 只依赖它前面的 i 个 token，与后面的内容无关。所以只要两个请求的前缀 token 序列完全一致，这段前缀对应的 K/V 就完全相同，可以直接复用，跳过重复的 prefill 计算。这也解释了为什么缓存必须是"精确前缀匹配"——前缀里任何一个 token 变了，从那个位置往后的所有 K/V 都会失效。适合缓存的内容是那些跨请求稳定不变的部分：system prompt、工具 schema 定义、固定的 few-shot 示例、长期不变的知识片段、多轮对话里已经固化的历史。使用要点有四点：第一，把稳定内容严格前置，动态内容一律后置，一个放在开头的时间戳或用户 ID 能让缓存全年不命中，这是最常见的坑；第二，注意各家的最小缓存长度门槛和 TTL（通常几分钟），请求稀疏或者前缀太短可能命中不了；第三，命中收益主要体现在输入 token 成本和首 token 延迟（TTFT）上，对输出生成速度没有帮助，所以输出占比高的任务收益有限；第四，一定要监控命中率，命中率低说明前缀设计有问题，或者动态内容混进了前缀。工程上通常配合"稳定前缀 + 增量尾巴"的结构，让多轮对话在若干轮内持续命中。

**常见追问**：1）为什么缓存不能对输出阶段生效？2）多轮对话怎么设计才能持续命中？

## 87. 长上下文场景下，如何保留关键信息、优化 Prompt 缓存策略？

> 原题 ID：`q1250`

**高频程度**：★★★★

**考察点**：长上下文下保信息（分层记忆、滚动摘要、外部化、位置策略）与保缓存（严格分区、批量压缩、增量追加）的配合。

**回答框架**：

1）保信息：分层——system 与任务约束常驻，关键结论/偏好/事实写入结构化事实卡；滚动摘要——超阈值把最早 N 轮压缩，保留数字、实体、决策、未完成事项；外部化——长文档存外部只留句柄与摘要；位置——关键约束放首尾对抗 lost-in-the-middle；2）保缓存：严格分区，前缀区只增不改；摘要更新会打断缓存，采用累积到阈值再压缩一次的批量策略；新增内容追加在尾部；3）矛盾与权衡：压缩频率决定缓存命中与上下文占用。

**参考回答**：

长上下文场景下，保留关键信息和优化 Prompt 缓存这两个目标要配合设计。先说保留关键信息，有四个手段：第一，分层记忆，system prompt 和任务约束常驻上下文；把关键结论、用户偏好、已确认的事实抽成结构化的"事实卡"常驻；过程性的细节可以丢弃。第二，滚动摘要，当对话超过阈值时，把最早的若干轮压缩成摘要，压缩时保留数字、实体、决策和未完成事项，丢弃寒暄和重复内容，摘要要有固定的 schema，避免每次风格漂移导致信息丢失。第三，外部化，长文档和大体积工具结果不放进上下文，只存一个句柄和摘要，需要时按需取回。第四，位置策略，关键约束放在开头和结尾，因为模型对中间内容注意力弱。再说保缓存：第一，严格分区，前缀区（system、工具定义、固定示例）只增不改，任何修改都会让整段缓存失效；第二，摘要更新会打断缓存，所以不要每轮都重写摘要，采用"累积到阈值再压缩一次"的批量策略，让缓存在若干轮内保持有效；第三，每轮新增内容追加在尾部，形成"稳定前缀 + 增量尾巴"的结构，这样前面的 KV 一直能命中；第四，给不同会话类型设计不同的前缀模板，提升跨会话的缓存命中。这两者的矛盾点在于：压缩必然改写前缀，压得太勤缓存频繁失效，压得太少上下文又会爆。所以工程上一般先定 token 预算，按预算反推压缩阈值和压缩粒度，比如超过 70% 才压一次，并且尽量把摘要放在尾部而不是插在中间。整体原则是"稳定内容不动、变化内容后置、压缩批量进行"。

**常见追问**：1）事实卡应该包含哪些字段？2）压缩阈值和缓存 TTL 怎么配合？

## 88. 为什么引入 Redis

> 原题 ID：`q1453`

**高频程度**：★★★★

**考察点**：引入 Redis 的四个层面原因：性能（缓存）、高并发削峰、丰富数据结构、分布式场景支撑。

**回答框架**：

1）性能提升：MySQL 走磁盘 IO，QPS 几千，Redis 内存单机十万级、亚毫秒，缓存挡住大部分读流量；2）高并发与削峰：秒杀场景做计数器、限流、队列缓冲；3）丰富数据结构：String/Hash/List/Set/ZSet/Bitmap/HLL/GEO/Stream 直接支撑业务模型；4）分布式支撑：会话共享、分布式锁、分布式 ID、消息队列；5）代价：内存成本与一致性复杂度。

**参考回答**：

引入 Redis 主要是为了解决传统数据库在性能、并发和分布式场景下的瓶颈，可以从四个层面讲。第一，性能提升也就是缓存：MySQL 这类关系型数据库数据在磁盘上，一次查询要经过 SQL 解析、优化、磁盘 IO、锁竞争，QPS 通常在几千量级，还容易在热点数据上出现锁和 IO 瓶颈；Redis 数据放内存，单机 QPS 可达十万级、延迟亚毫秒。把热点数据放 Redis，请求先查 Redis，未命中再查库并回写，能挡住 90% 以上的读流量，很好地保护数据库。第二，高并发与削峰：秒杀、抢购这类场景瞬时流量极大，直接打数据库会被压垮，Redis 可以做计数器扣库存、做接口限流、做请求缓冲队列，把瞬时洪峰接住再慢慢消费。第三，丰富的数据结构：String、Hash、List、Set、ZSet、Bitmap、HyperLogLog、GEO、Stream 等，能直接实现排行榜、点赞、去重、签到、附近的人、消息队列这些功能，不用自己造轮子，而且这些操作都是服务端原子的，省掉了应用层的并发控制。第四，分布式场景支撑：分布式系统里多台机器需要共享状态，Redis 可以做 Session 共享、分布式锁、分布式 ID 生成、幂等标记、以及基于 Stream 的异步任务队列。当然引入它也有代价：内存比磁盘贵、容量有限，而且多了一层缓存就带来一致性问题，要考虑穿透、击穿、雪崩和高可用。所以正确的做法是让它承担它擅长的部分——热点、高速、原子的场景，把权威数据留在 MySQL。

**常见追问**：1）什么数据不该放 Redis？2）引入 Redis 后系统复杂度体现在哪？

## 89. 模型的缓存机制：前缀缓存命中和未命中的成本差，怎么组织上下文去吃这个红利

> 原题 ID：`q1482`

**高频程度**：★★★★

**考察点**：前缀缓存（Prefix Caching）原理（prefill/decode、KV 复用）、命中与未命中的成本差、上下文组织方式。

**回答框架**：

1）原理：推理分 prefill（对整段 prompt 前向生成 KV）和 decode（逐 token 复用 KV）；2）前缀一致则 KV 相同可直接复用，只需 prefill 新增 token；3）成本差：命中前缀 P 时长 L 的 prompt 只需算 L-P 个 token，TTFT 与输入成本大幅下降；4）组织方式：稳定内容（system prompt、工具定义、few-shot、长文档）放最前，易变内容（用户输入、时间戳、随机 ID）放最后；5）多轮对话增量追加，避免改写前缀；6）监控命中率。

**参考回答**：

前缀缓存（Prefix Caching）的核心是复用已计算的 KV Cache。Transformer 推理分两个阶段：prefill 阶段对整段 prompt 做前向计算，生成每层、每个 token 的 K 和 V 并写入 KV Cache；decode 阶段逐 token 生成，每步复用之前的 KV 只计算当前 token。计算量上，prefill 与序列长度的关系近似 O(L²)（注意力部分）或至少 O(L) 线性，而 decode 每步只处理一个 token。前缀缓存的原理是：如果两个请求的 token 序列前缀完全一致，那么这段前缀对应的 KV 完全相同，可以直接复用，不需要重新计算。成本差可以用公式理解：假设 prompt 总长 L，命中的前缀长度是 P，那么命中时只需 prefill 剩下的 L-P 个 token，未命中则要 prefill 全部 L 个；P 越接近 L，节省越多。以 vLLM 的 Automatic Prefix Caching 为例，命中能显著降低首 token 延迟（TTFT），在长 system prompt 场景下提升最明显；商业 API 的前缀缓存命中部分通常按更低价格（比如 0.1 倍）计费。怎么组织上下文来吃这个红利？关键原则是"稳定内容前置、易变内容后置"：把 system prompt、工具定义、少样本示例、长文档这些跨请求不变的内容放最前面，把用户输入、时间戳、随机 ID、检索结果这些每次都变的放最后。多轮对话采用增量追加的方式，历史消息不要重写，只在尾部加新内容，这样前面所有轮次的 KV 都能持续命中。最后要监控命中率，如果命中率低，通常是某个动态字段被放进了前缀，比如时间戳或者 session id。

**常见追问**：1）vLLM 的前缀缓存是怎么做块级复用的？2）命中率低怎么排查？

## 90. 有的小伙伴可能已经注意到一个问题：前面提到的大多数方法都是预定义好的 pipeline，流程是死的，不管什么问题进来，处理方式都差不多

> 原题 ID：`q1965`

**高频程度**：★★★

**考察点**：预定义 pipeline 的局限（流程固定、无法动态选择）与 Agent 式动态规划/工具调用的必要性。

**回答框架**：

1）预定义 pipeline 的本质：流程写死在代码或配置，所有问题走同一条链路；2）优点：稳定、可测试、延迟和成本可控、适合边界清晰场景；3）局限：无法按问题动态决定要不要检索、检索几次、用哪个工具、是否追问，导致过度处理或处理不足；4）Agent 的能力：意图理解 → 工具选择 → 规划 → 反思重试；5）类比：固定套餐 vs 点菜现做。

**参考回答**：

预定义 pipeline 比如 RAG 的"检索→拼接→生成"、固定 CoT、固定多步模板，本质是把流程写死在代码或配置里：无论用户问什么，都走同一条链路。它的优点是稳定、可测试、延迟可控、成本可预估，适合任务边界清晰、步骤固定的场景，比如 FAQ 问答、文档摘要、固定格式抽取。但真实问题千差万别：有的只需直接回答，有的要先查数据库再算数，有的要调多个 API 并交叉验证，有的需要多轮澄清。固定 pipeline 无法根据问题类型动态决定"要不要检索、检索几次、用哪个工具、是否继续追问"，于是要么过度处理，简单问题也走重流程、白白浪费 token 和时间；要么处理不足，复杂问题缺步骤、效果差。类比一下：预定义 pipeline 像"固定套餐"，进门就上同一套菜；Agent 像"点菜加厨师现做"，先看客人需求做意图理解，再决定买什么菜（工具选择）、做几步（规划）、尝味道决定是否加料（反思与重试）。所以需要 Agent 式的动态规划与工具调用能力：模型根据当前任务自主决定调用哪些工具、以什么顺序、拿到结果后判断是否足够、不够就继续。当然也不是所有场景都要上 Agent，如果任务链路确实固定，用 pipeline 更经济可靠，关键是根据任务复杂度和多样性选架构，很多时候是两者结合——主干用 pipeline 保证稳定，局部用 Agent 处理不确定分支。

**常见追问**：1）什么场景该用 pipeline，什么场景该用 Agent？2）Agent 动态规划怎么控制成本？

## 91. 基于 Redis Stream 实现简历分析、知识库向量化等场景的异步（还能解耦，分析和向量化可以使用其他编程语言来做）

> 原题 ID：`q1973`

**高频程度**：★★★★

**考察点**：Redis Stream 的异步任务架构：XADD 投递、消费者组、XACK 确认、XAUTOCLAIM 重投、多语言消费者解耦。

**回答框架**：

1）原理：Stream 是 5.0 引入的追加式日志，消息有唯一 ID，支持消费者组；2）生产者：落库后 XADD 投递任务并立即返回任务 ID；3）消费者组：XGROUP CREATE 建组，XREADGROUP 消费，XACK 确认，PENDING 列表看未确认；4）容错：消费者宕机用 XAUTOCLAIM/XCLAIM 重投；5）优势：解耦、削峰、消费者可用任意语言实现；6）对比 List：支持多消费组、消息确认与重投，不像 Pub/Sub 会丢离线消息。

**参考回答**：

用 Redis Stream 做简历分析、知识库向量化这类异步任务，核心是把耗时操作从请求链路里剥离出来。原理上，Stream 是 Redis 5.0 引入的追加式日志结构，每条消息有唯一 ID（默认是时间戳加序号），支持消费者组、消息确认和未确认消息重投，比 List 的 LPUSH/BRPOP 更适合做消息队列——因为它支持多个消费者分组消费、支持 XACK 确认和 pending 列表查看、还支持消息重投，而且不像 Pub/Sub 那样消费者离线就丢消息。典型架构是：第一，生产者（比如 Web 后端）收到简历上传或文档后，先落库或存对象存储，然后用 XADD stream * task_type analyze_resume payload '{...}' 投递任务，立刻返回任务 ID，前端通过轮询或 WebSocket 获知进度，请求链路非常短。第二，消费者端用 XGROUP CREATE 创建消费者组，多个消费者用 XREADGROUP 并行消费，处理完用 XACK 确认；因为是消费者组，同一条消息只会被组内一个消费者处理，可以水平扩容消费者。第三，容错处理：用 XPENDING 查看未确认消息，如果某个消费者宕机，它的 pending 消息可以用 XAUTOCLAIM（Redis 6.2+）或 XCLAIM 转移给其他消费者重投，避免任务丢失；业务上还要保证幂等，因为重投可能重复执行。第四，因为消息格式是通用的，消费者可以用任何语言实现——比如用 Python 做向量化、用 Java 做简历解析，天然实现了服务解耦和技术栈解耦。相比专业的 Kafka，Redis Stream 的优势是部署简单、延迟低、和已有的 Redis 复用运维；不足是持久化和堆积能力不如 Kafka，适合中等吞吐、实时性要求高的任务场景。

**常见追问**：1）消费者处理失败后怎么不丢消息？2）Stream 堆积太多内存怎么办？

## 92. http缓存和CDN原理讲一下

> 原题 ID：`q2833`

**高频程度**：★★★★

**考察点**：HTTP 缓存（强缓存/协商缓存、关键头）与 CDN 原理（边缘节点、回源、调度、刷新与命中率）。

**回答框架**：

1）HTTP 缓存两类：强缓存（不发请求，Cache-Control max-age/immutable、Expires）与协商缓存（发请求校验，ETag/If-None-Match、Last-Modified/If-Modified-Since，命中返 304）；2）关键头：no-cache、no-store、private/public、s-maxage、stale-while-revalidate/stale-if-error；3）CDN：边缘节点缓存 + 回源 + DNS/Anycast 调度，把内容推到离用户最近处；4）核心权衡：缓存键、TTL、一致性刷新、命中率；5）实践：静态资源内容哈希 + 长缓存，HTML 短缓存或用协商缓存。

**参考回答**：

先讲 HTTP 缓存，它分两类。第一类是强缓存，命中时浏览器不发请求，直接用本地副本：靠响应头 Cache-Control 的 max-age 控制新鲜期，加上 immutable 表示在此期间不再校验；老规范还有 Expires 绝对时间，受客户端时钟影响，基本已被 Cache-Control 取代。第二类是协商缓存，浏览器会发请求带上校验信息，由服务端判断内容是否变化：响应头用 ETag 或 Last-Modified，请求头用 If-None-Match 或 If-Modified-Since，没变就返回 304 Not Modified（不带 body），变了就返回 200 和新内容。ETag 的优先级高于 Last-Modified，因为它基于内容指纹更精确，还分强 ETag 和弱 ETag（W/ 前缀）。其他关键头还有：no-cache 表示可以缓存但每次必须再验证；no-store 表示完全不缓存；private 和 public 控制是否允许共享缓存（CDN）缓存；s-maxage 是专门给共享缓存的，优先级高于 max-age；stale-while-revalidate 允许过期后先返回旧内容、后台异步刷新；stale-if-error 在源站出错时用旧内容兜底。再说 CDN：它的原理是把静态内容提前缓存到遍布各地的边缘节点，用户请求时通过 DNS 调度或 Anycast 路由到最近的边缘节点，命中就直接返回，未命中或内容是动态的就回源站获取，同时缓存下来服务后续请求。CDN 的核心价值是缩短物理距离、降低延迟和源站压力。工程上要注意几个权衡：缓存键怎么设计（是否带查询参数、是否区分设备）、TTL 设多长、内容更新时怎么刷新（主动 purge 还是靠 TTL 自然过期）、以及命中率监控——命中率低说明缓存键设计或调度有问题。实践中最常见的组合是：静态资源（JS/CSS/图片）用内容哈希命名 + 一年强缓存 + immutable，改了文件名就变，天然不冲突；HTML 入口文件用短 TTL 或协商缓存，保证能及时发版。

**常见追问**：1）为什么静态资源建议用内容哈希而不是查询参数做版本？2）CDN 刷新和预热怎么做？

## 93. 成本与延迟控制：一个任务可能会需要调用 10-30 次 LLM，怎么做缓存、模型路由、并行优化

> 原题 ID：`q2864`

**高频程度**：★★★★

**考察点**：多步 LLM 任务的成本延迟优化：多层缓存（精确/前缀/语义）、模型路由降级、并行化与预算熔断。

**回答框架**：

1）缓存三层：精确缓存（key 含 model/prompt/temperature/tools/seed）、前缀缓存（稳定内容前置，命中按低倍计费、TTFT 大降）、语义缓存（相似问题复用）；2）模型路由：按子任务难度分级，简单步骤用小模型，只在关键推理用大模型；3）并行优化：无依赖步骤并行执行、批处理合并；4）预算熔断：设 token 与调用次数上限，超限降级或失败；5）取舍：一级（温度）和工具参数必须纳入缓存 key，否则串味。

**参考回答**：

一个任务要调 10 到 30 次 LLM，成本和延迟基本是线性叠加的，所以要从三个维度同时下手。第一是缓存，分三层：精确缓存，对 model、prompt、temperature、tools、seed 组合做 key 存到 Redis 或 KV 里，temperature 等于 0 时命中率最高，注意这些参数都要纳入 key，否则会串味；前缀缓存，把固定的 system prompt、工具定义、长文档放在 prompt 前缀，利用 vLLM 的 Automatic Prefix Caching 或商业 API 的 prompt caching，命中的部分按更低价格计费、首 token 延迟大幅下降，工程上就是"稳定内容前置、动态内容后置"；语义缓存，对意思相近但措辞不同的问题，用 embedding 相似度匹配历史问答结果复用，适合客服类高频重复问题。第二是模型路由降级：把任务拆成子步骤后，按每步的难度分级——格式整理、信息抽取、简单分类这些用小模型甚至本地模型，只在关键推理和最终综合环节用大模型；还可以加"先便宜后昂贵"的策略，小模型结果置信度低时才升级到大模型。第三是并行优化：把没有依赖关系的步骤并行发起，比如多路检索、多个文档独立摘要同时跑，而不是串行等待；能合并的请求做批处理提升吞吐。第四一定要有预算熔断：给每个任务设 token 上限和最大调用次数，达到阈值就降级返回部分结果或直接失败，避免因为 Agent 陷入循环而无限烧钱，这是多步任务最容易失控的地方。整体思路是"能缓存就不调用、能小模型就不大模型、能并行就不串行、兜底要有预算上限"。

**常见追问**：1）语义缓存的相似度阈值怎么定？2）并行调用如何避免超过速率限制？

## 94. 可是真到了那个场景下，脑子就像蓝屏了一样，就像是缓存里没命中的数据——明明存在，却怎么都取不出来

> 原题 ID：`q3178`

**高频程度**：★★

**考察点**：面试卡壳的工程类比：知识未形成可检索索引、工作记忆被占用、输入式学习 vs 输出式复习。

**回答框架**：

1）存储层：知识是否以结构化可检索的方式存储（问题→原理→例子→权衡）；2）读取层：面试是限时高压串行查询，紧张占用工作记忆导致"超时"；缓解方式是预编译高频题形成肌肉记忆；3）一致性：懂（最终一致）和讲清楚（强一致）是两套模型，需要输出式复习；4）方法：结构化卡片、主动回忆、费曼技巧、白板讲题。

**参考回答**：

这道题表面在聊面试紧张，实际可以类比成缓存和检索的问题。把大脑当缓存看，卡壳通常不是数据不存在，而是索引缺失或者读取路径被阻塞。工程上对应三个层面：第一，存储层，知识有没有以"可检索结构"存储。零散地看博客、刷视频，相当于往堆内存里乱塞数据、没有建索引，面试时无法按 key 命中；正确的做法是把知识整理成"问题→原理→例子→权衡"的结构化卡片，相当于给缓存建 B+ 树索引，检索时才快。第二，读取层，也就是检索路径。面试是限时、高压、串行的查询场景，紧张会占用工作记忆，相当于线程池被占满、资源被挤占，导致原本 O(1) 的回忆变成超时失败。缓解办法是"预编译"：把高频题目练到脱口而出，形成肌肉记忆，绕过慢思考路径，就像把热点数据预热到本地缓存。第三，一致性层面，"平时懂"和"面试能讲清楚"是两套一致性模型——懂是最终一致（有个印象就行），讲清楚要求强一致（必须当场完整复现推理链）。所以要主动做输出式复习，用费曼技巧讲给别人听、白板手写推理过程、给自己录音复盘，而不是反复输入式阅读，因为输入会带来"我懂了"的错觉，输出才能暴露真实的缺口。落到可执行的方法：结构化整理知识卡片、定期主动回忆（合上资料复述）、模拟面试限时作答、建立错题和卡壳点的复盘清单。本质上就是把学习从"无索引写入"变成"建索引 + 加内存 + 预热"。

## 95. http通信如何设置缓存 √

> 原题 ID：`q3314`

**高频程度**：★★★★

**考察点**：HTTP 缓存设置：强缓存与协商缓存的头字段、请求响应头配合、按资源类型设置策略。

**回答框架**：

1）强缓存：Cache-Control max-age/immutable，Expires（已过时），命中直接读本地 200 from cache；2）协商缓存：ETag/If-None-Match、Last-Modified/If-Modified-Since，未变返 304；3）指令细节：no-cache、no-store、private/public、s-maxage、stale-while-revalidate；4）ETag 与 Last-Modified 优先级与选择；5）实践：静态资源内容哈希+长缓存，HTML 短缓存，接口按需协商缓存。

**参考回答**：

设置 HTTP 缓存就是在响应头上做配置，分强缓存和协商缓存两类。设置强缓存用响应头 Cache-Control 的 max-age 指定新鲜期秒数，HTTP/1.1 里优先级最高，还可以加 immutable 告诉浏览器在此期间不用再校验；老规范用 Expires 指定绝对时间，但受客户端时钟影响，基本已被取代。命中强缓存时浏览器直接返回 200（from disk/memory cache），完全不发网络请求。设置协商缓存则要成对配置：服务端在响应头返回 ETag（内容指纹）和 Last-Modified（最后修改时间），浏览器下次请求时自动带上 If-None-Match 和 If-Modified-Since，服务端比对后如果没变就返回 304 Not Modified（没有 body），变了才返回 200 和新内容。ETag 优先级高于 Last-Modified，因为它基于内容计算更精确，能避免"文件内容没变但修改时间变了"的误判；ETag 还分强 ETag 和弱 ETag（W/ 前缀）。其他常用指令：no-cache 表示可以缓存但每次使用前必须向服务端验证；no-store 表示完全不允许缓存，一般用于敏感数据；private 表示只允许浏览器缓存、不允许 CDN 等共享缓存；public 允许共享缓存；s-maxage 只对共享缓存生效且优先级高于 max-age；stale-while-revalidate 允许过期后先返回旧内容并在后台异步刷新。工程实践上按资源类型分别设置：带内容哈希的静态资源（app.abc123.js）设一年 max-age 加 immutable，因为文件名变了就是新资源；HTML 入口文件设很短的 max-age 或者 no-cache 走协商缓存，保证发版能及时生效；接口数据一般不用强缓存，需要缓存的加短 TTL 或用 ETag 做协商缓存；用户相关或敏感数据用 no-store 或 private，避免被 CDN 缓存造成越权。

**常见追问**：1）ETag 比 Last-Modified 好在哪，有什么缺点？2）no-cache 和 no-store 的区别？

## 96. Redis 这类缓存和 Caffeine 的区别

> 原题 ID：`q3395`

**高频程度**：★★★★

**考察点**：Redis（分布式远程缓存）与 Caffeine（进程内本地缓存）在延迟、容量、一致性、可用性、淘汰策略上的对比与多级组合。

**回答框架**：

1）部署形态：Caffeine 进程内、堆内存、纳秒到微秒；Redis 独立服务、走网络、0.1-1ms；2）容量成本：Caffeine 受单机堆限制且加重 GC，Redis 可扩到 TB 级；3）一致性：Caffeine 每 JVM 一份、天然不一致，靠广播失效；Redis 共享存储、多实例读同一份；4）淘汰与结构：Caffeine 用 W-TinyLFU、支持异步刷新；Redis 支持丰富数据结构、持久化、分布式能力；5）实践：多级缓存，Caffeine 挡热读、Redis 做共享层。

**参考回答**：

这两个缓存可以从几个维度对比。第一，部署形态和访问路径：Caffeine 是进程内缓存，直接操作 JVM 堆内存，一次 get 通常是纳秒到微秒级，完全没有网络开销；Redis 是独立的远程服务，客户端通过 TCP 访问，一次 RTT 大约 0.1 到 1 毫秒，跨机房更高。所以延迟上本地缓存比 Redis 快一到三个数量级。第二，容量和成本：Caffeine 受限于单机堆内存，容量有限，而且大量对象常驻堆会加重 GC 压力，尤其大对象、高 QPS 场景容易触发 Full GC 导致长停顿；Redis 容量可以独立扩展，能存 TB 级数据，但需要网络和运维成本。第三，一致性：这是最关键的差异。Caffeine 每个 JVM 一份副本，多实例之间天然不一致，更新只能靠本地失效或广播通知（Redis Pub/Sub、MQ），存在不一致窗口；Redis 是共享存储，多个实例读的是同一份数据，在单 key 维度天然一致。第四，功能和淘汰策略：Caffeine 用 W-TinyLFU 算法，命中率优于朴素 LRU，还支持异步刷新、过期策略丰富；Redis 提供丰富的数据结构、持久化、分布式锁、消息队列等能力，淘汰策略有 LRU/LFU/RANDOM 等。第五，可用性：Caffeine 随应用进程存活，进程挂了缓存就没了，但也不会成为故障点；Redis 是独立组件，需要考虑高可用（主从/哨兵/Cluster），一旦故障可能影响全部实例。所以工程上常见的做法是多级缓存：Caffeine 作为一级挡在前面承接超热数据，Redis 作为二级共享层保证多实例一致和容量扩展，数据库作为最终真相源；写的时候按"更新 DB → 删 Redis → 广播失效本地"来同步，用 TTL 兜底。

**常见追问**：1）多级缓存怎么保证本地缓存及时失效？2）本地缓存放超大对象会有什么问题？

## 97. MySQL 和 Redis 怎么保持数据一致

> 原题 ID：`q3396`

**高频程度**：★★★★★

**考察点**：MySQL 与 Redis 的一致性方案：Cache-Aside、先更 DB 再删缓存、延迟双删、binlog 订阅、强一致代价。

**回答框架**：

1）前提：MySQL 是真相源，Redis 是缓存副本，一致性指缓存值尽量等于库值；2）为什么难：两个操作无法原子，有失败、并发、延迟；3）方案一：先更新 DB 再删缓存（最常用），删而非更新避免并发覆盖；4）方案二：先删缓存再更新 DB，需延迟双删兜底；5）方案三：Canal 订阅 binlog 异步失效，一致性好但组件多；6）强一致需加锁串行化，代价是并发；7）兜底：TTL。

**参考回答**：

先明确前提：MySQL 和 Redis 通常不是双主写入，而是 MySQL 存全量数据作真相源、Redis 做缓存副本，所谓一致性是指缓存里的值尽量等于 MySQL 的值。为什么难？因为更新 MySQL 和更新 Redis 是两个独立操作，中间可能失败、可能并发、可能延迟，无法像单机事务那样保证原子。常见方案有四类。第一，先更新数据库再删除缓存，也就是 Cache-Aside，这是最常用的做法。读的时候先查缓存，没有就查库并回填；写的时候更新库然后删缓存。为什么删而不是更新缓存？因为并发下两个线程的写顺序无法保证，可能出现旧值后写覆盖新值，而删除只是置为未命中，下次读回源拿的必然是最新值，出错窗口更小。可以用类比理解：MySQL 是账本，Redis 是贴在墙上的便签，改完账本就把便签撕掉，别人要看时重新抄一遍。第二，先删缓存再更新数据库，这种做法的问题是：删完缓存、数据库还没更新时，有读请求进来把旧值回填了缓存，导致脏数据长期存在；所以需要配合延迟双删——更新库后再延迟几百毫秒删一次，清掉并发回填的旧值。第三，订阅 binlog 异步失效，用 Canal 监听 MySQL 变更，通过消息队列广播给各节点删除缓存。这个方案一致性和覆盖面都更好，业务代码也干净，但额外引入 Canal、MQ 和消费服务，运维和排查成本明显上升。第四，如果确实要强一致，只能对读写路径加分布式锁串行化，那并发性能就没了，实际很少这么用。所以我的结论是：一致性不是免费的，要按业务容忍度选等级。绝大多数读多写少的场景（商品、用户资料）用"先更库再删缓存 + TTL 兜底"就够了；对一致性要求高的才上 binlog 订阅；强一致基本不用缓存。另外一定要记得，最终兜底永远是 TTL，它保证即使某次失效失败也能自愈。

**常见追问**：1）为什么"先删缓存再更新 DB"更容易出问题？2）Canal 方案本身有延迟，怎么避免读到旧数据？

## 98. redis的RDB和AOF两种持久化机制的原理，以及他们的适用场景是什么

> 原题 ID：`q3491`

**高频程度**：★★★★★

**考察点**：RDB/AOF 的原理（快照 vs 追加日志）、fork+写时复制、刷盘策略、优缺点与适用场景、混合持久化。

**回答框架**：

1）RDB：某时刻全量数据二进制快照；触发方式 SAVE/BGSAVE 与 save 配置；核心是 fork+写时复制；优点是恢复快体积小，缺点是两次快照间数据会丢、fork 有开销；2）AOF：追加写命令日志，命令先入 aof_buf 再按 appendfsync 刷盘；优点是最多丢 1 秒（everysec），缺点是文件大恢复慢；3）混合持久化：AOF 文件含 RDB 头，兼顾两者；4）选型：备份与快速重启用 RDB，数据安全用 AOF，生产两者结合。

**参考回答**：

先讲 RDB。RDB 是把某一时刻 Redis 内存中的全部数据以二进制压缩形式写入磁盘，生成 dump.rdb 文件。触发方式有两种：手动命令 SAVE（阻塞主线程，不推荐）和 BGSAVE（fork 子进程写盘，主线程继续服务）；也有配置自动触发，比如 save 900 1 表示 900 秒内至少 1 个 key 变化就触发 BGSAVE。核心原理是 fork 加写时复制（COW）：fork 出的子进程与父进程共享内存页，父进程继续处理写请求时，被修改的页才复制一份，子进程看到的是 fork 那一瞬间的一致快照，因此能相对不阻塞地生成全量快照。优点是文件紧凑、恢复速度快、适合做备份和主从全量同步；缺点是两次快照之间的数据会丢失（可能丢几分钟），而且内存大时 fork 本身会短暂阻塞、写时复制还会带来额外内存占用。 再讲 AOF。AOF 以追加方式记录每一条写命令（RESP 协议的文本），重启时重放这些命令来恢复数据。流程是：写命令先追加到 aof_buf 缓冲区，然后按 appendfsync 策略刷盘——always 每条都 fsync 最安全但最慢，everysec 每秒一次最多丢 1 秒是默认策略，no 交给操作系统。AOF 文件会不断膨胀，所以需要重写：fork 子进程根据当前内存数据反推出最小命令集生成新文件，重写期间的增量写入重写缓冲区，最后合并替换。优点是数据更安全、丢失窗口小、可读性好（文本命令便于排查）；缺点是文件大、恢复慢、刷盘有开销。 适用场景上：RDB 适合做周期性备份、灾难恢复、快速重启、主从全量复制；AOF 适合对数据安全要求高的场景，作为主要恢复手段。生产中通常是两者结合：AOF 保证数据尽量不丢，RDB 用于备份和快速重启。Redis 4.0 之后还有混合持久化，把 AOF 重写后的文件前半部分写成 RDB 格式、后半部分是增量 AOF，兼顾恢复速度和数据安全，是现在比较推荐的方案。

**常见追问**：1）写时复制为什么能保证快照一致性？2）appendfsync everysec 会丢多少数据？

## 99. Redis相关接口区别

> 原题 ID：`q3504`

**高频程度**：★★★

**考察点**：Redis 客户端/接口的层次差异：原生命令、客户端封装（Jedis/Lettuce/Redisson/Spring Data Redis）、高级抽象，及连接模型、序列化、阻塞语义。

**回答框架**：

1）三类接口：原生命令接口、客户端封装接口、高级抽象接口（分布式对象）；2）连接模型：Jedis 同步阻塞+连接池；Lettuce 基于 Netty 支持同步/异步/响应式、连接可共享；Redisson 基于 Netty 偏分布式对象；3）序列化：默认 JDK 序列化易乱码体积大，一般换 String/JSON/Protobuf；4）语义差异：阻塞命令、批量 pipeline、事务与 Lua；5）选型：缓存用 Lettuce/Spring Data，分布式锁用 Redisson。

**参考回答**：

Redis 相关接口通常分三层。第一层是原生命令接口，比如 SET、GET、HSET，直接对应 Redis 协议，语义最清晰，但它只有单命令语义，不含连接管理、序列化和重试。第二层是客户端封装接口，比如 Jedis、Lettuce、Redisson、Spring Data Redis，它们在命令之上加了连接池、线程安全、序列化、重试、集群路由等能力。第三层是高级抽象接口，比如 Redisson 的 RLock、RMap、RTopic，把 Redis 能力映射成 Java 并发对象或消息组件，使用体验像本地对象。它们的区别主要体现在几点：一是连接模型，Jedis 是同步阻塞式，每个连接一个线程、通常要配连接池，连接不可共享；Lettuce 基于 Netty，支持同步、异步和响应式调用，连接是线程安全的可以共享，适合高并发；Redisson 也基于 Netty，但更偏分布式对象封装。二是序列化，Spring Data Redis 默认用 JdkSerializationRedisSerializer，容易产生乱码、体积大、还有反序列化安全问题，生产上一般换成 StringRedisSerializer 或 Jackson/Protobuf。三是功能语义，Pipeline 用于批量命令减少 RTT，事务用 MULTI/EXEC，需要原子逻辑用 Lua 脚本，分布式锁用 Redisson 的 RLock；这些在不同客户端里的支持程度和 API 差别很大。四是阻塞和超时语义，BRPOP 这类阻塞命令在不同客户端里的超时处理和连接占用方式不同。选型上，普通缓存读写用 Lettuce 或 Spring Data Redis 就够；需要分布式锁、限流器、延迟队列、布隆过滤器这些高级能力用 Redisson；老项目历史包袱可能还在用 Jedis，但要配好连接池和超时。

**常见追问**：1）Jedis 的连接池配小了会有什么现象？2）Redisson 的锁是怎么实现的？

## 100. Redis 出现热点 Key 时通常有哪些解决方案？

> 原题 ID：`q3555`

**高频程度**：★★★★★

**考察点**：热 Key 的本质（单分片承载超高 QPS）与三层解决方案：本地缓存、读写分离/多副本、key 拆分打散，外加限流与治理。

**回答框架**：

1）本质：Cluster 按 key 分片，同一 key 永远落同一 slot/节点，热 key 把单节点单线程打满，其他节点空闲；2）方案一：应用层本地缓存（Caffeine，短 TTL 1-5 秒）削掉大部分 QPS；3）方案二：读写分离加多副本，读请求分散到从节点（readFrom 策略）；4）方案三：把热 key 拆成多个 key（加随机后缀）分散到不同节点，读时随机取一个；5）方案四：入口限流、请求合并；6）配套：发现手段与监控。

**参考回答**：

先明确问题本质：Redis Cluster 按 key 做 CRC16 分片，同一个 key 永远落在同一个 slot、同一个节点上。所以当某个 key（比如秒杀商品、明星微博、大促爆款）QPS 达到几十万时，压力全部压在单个节点的单线程上，表现为该节点 CPU 打满、其他节点却很闲、延迟飙升，严重时拖垮整个集群。解决方案按成本从低到高有几层。第一，应用层本地缓存：用 Caffeine 或 Guava 在 JVM 里缓存热点数据，设置很短的过期时间，比如 1 到 5 秒，请求先查本地，未命中再查 Redis，这样 Redis 的 QPS 能被削掉 90% 以上。类比是把最常看的书放在自己桌上，而不是每次都去图书馆借。缺点是多实例之间有一致性延迟，适合商品详情、榜单这类对一致性要求不高的场景。第二，读写分离加多副本：主节点负责写，挂多个从节点，客户端通过 Lettuce 或 Jedis 的 readFrom 策略把读请求分发到从节点，把单节点的读压力分散到多台机器上。第三，把热 key 拆成多个 key：在业务上复制 N 份数据，key 加随机后缀（比如 hot:item:1001:0 到 hot:item:1001:9），读的时候随机选一个，这样同一个逻辑热 key 就分散到不同 slot 和节点上，单节点压力降到 1/N；写的时候要按同样规则写入所有副本，或者用定时任务统一刷新。第四，入口治理：在网关或服务层做限流、请求合并（同一时刻相同请求合并成一次查询）、以及对非核心请求降级，从源头减少对热 key 的访问。第五，配套要有发现能力：客户端埋点统计 key 访问频率，或者用 redis-cli --hotkeys 做低峰巡检，做到"能提前发现、而不是打挂之后才知道"。整体思路就是削峰（本地缓存）、分散（多副本和 key 拆分）、保护（限流降级）。

**常见追问**：1）热 key 拆成多副本后写入怎么保证各副本一致？2）本地缓存短 TTL 定多长合适？

## 101. Redis 中缓存穿透、缓存击穿、缓存雪崩分别是什么？

> 原题 ID：`q3578`

**高频程度**：★★★★★

**考察点**：缓存穿透、击穿、雪崩的定义差异、成因与治理手段对比。

**回答框架**：

1）穿透：数据在缓存和 DB 都不存在，每次绕过缓存打 DB；治理：缓存空值（短 TTL）、布隆过滤器、参数校验与限流；2）击穿：单个热点 key 过期瞬间大量并发同时回源；治理：互斥锁只让一个线程回源、逻辑过期异步重建、热点 key 不过期；3）雪崩：大量 key 同时过期或 Redis 宕机导致 DB 被打垮；治理：过期时间加随机、多级缓存、高可用集群、熔断降级、限流；4）对比：穿透是数据不存在，击穿是单 key 并发，雪崩是批量失效或整体故障。

**参考回答**：

这三个问题都源于缓存未命中后流量落到数据库，但触发条件和治理手段不同。第一，缓存穿透：请求的数据在缓存和数据库里都不存在，比如攻击者用大量不存在的 userId 查询，每次都会穿透到 DB，DB 压力随攻击量线性增长。治理手段：一是缓存空值，查不到时写入一个 null 或占位符并设置较短 TTL（比如 30 到 60 秒），注意要区分业务上的"不存在"和系统异常，别把故障也缓存成空值；二是布隆过滤器在入口拦截，把库里的 key 预先哈希到位图里，说不存在就一定不存在，缺点是存在误判率、标准版不支持删除，可以用计数布隆或定期重建；三是参数校验和限流，在网关层做 ID 格式与范围校验，对异常 IP 限流。第二，缓存击穿：某个热点 key 在过期的那一瞬间，大量并发请求同时未命中，全部去查 DB 并回写，造成瞬时冲击。治理手段：一是互斥锁或分布式锁（SET NX PX 或 Redisson），只让一个线程去回源重建，其余线程等待或直接返回旧值；二是逻辑过期，value 里存一个逻辑过期时间但物理上不设 TTL，发现逻辑过期后由一个线程异步重建，其他请求先返回旧数据，这样完全没有空窗期；三是把超热数据设为不过期，靠后台任务定期更新。第三，缓存雪崩：大量 key 在同一时间过期，或者 Redis 整体故障宕机，导致本该由缓存承接的流量全部压到数据库。治理手段：一是给过期时间加随机值，把失效时间打散；二是用多级缓存（本地 + Redis）减少对 Redis 的依赖；三是架构上做主从加哨兵或 Cluster 保证高可用；四是必须有熔断降级和限流，DB 压力大时快速失败返回兜底内容，保护数据库不被打垮。一句话总结对比：穿透是"数据根本不存在"，击穿是"单个热点 key 过期时的并发"，雪崩是"大量 key 同时失效或缓存整体不可用"。

**常见追问**：1）逻辑过期方案怎么处理重建失败？2）布隆过滤器的误判会导致什么问题？

## 102. 【Q5】为什么说键值缓存（Key-Value Cache）是LLM推理，尤其是在长上下文场景下的主要瓶颈

> 原题 ID：`q3909`

**高频程度**：★★★★

**考察点**：KV Cache 的显存占用公式与增长规律、decode 阶段的 memory-bound 特性、长上下文下带宽成为瓶颈及优化方向。

**回答框架**：

1）什么是 KV Cache：缓存历史 token 的 K/V 避免重复计算；2）显存占用 ≈ 2 × batch × layers × heads × head_dim × seq_len × dtype_bytes，随上下文长度线性增长；3）举例：LLaMA-70B 每 token 约 320KB，32K 上下文单序列约 10GB；4）瓶颈本质：decode 阶段每步只算 1 个 token，算术强度极低、是 memory-bound，GPU 大部分时间在搬 KV Cache，算力利用率常低于 10%；5）优化：GQA/MQA 减少 KV 头、量化 KV、PagedAttention、前缀缓存复用、滑动窗口与稀疏注意力。

**参考回答**：

要理解为什么 KV Cache 是长上下文推理的主要瓶颈，先看它的规模。LLM 自回归解码时，每生成一个 token 都要对之前所有 token 的 K、V 做注意力计算；为了不重复计算，工程上把历史 token 的 Key/Value 张量缓存下来，这就是 KV Cache。它的显存占用大约是 2 × batch × layers × heads × head_dim × seq_len × dtype_bytes，其中 2 是因为要存 K 和 V 两份。以 LLaMA-70B 为例，80 层、GQA 8 个 KV head、head_dim 128、fp16，每个 token 约 2×80×8×128×2 = 320KB，32K 上下文单条序列就约 10GB，batch 一开就爆显存。关键点在于它的增长是随 seq_len 线性的，上下文越长占用越大，而 attention 的算力需求增长更快，但显存是硬约束。更本质的瓶颈在于：decode 阶段每步只计算 1 个 token，算术强度（每字节访存对应的计算量）极低，属于 memory-bound，GPU 大部分时间在把 KV Cache 从 HBM 搬到 SM，带宽成为瓶颈，算力利用率常常低于 10%。长上下文下这个问题被放大：一方面 KV Cache 大到装不下只能换出、重算或分块；另一方面每次 decode 都要读一遍完整的 KV，带宽消耗与上下文长度成正比，导致吞吐和 TTFT 都严重恶化。优化方向包括：用 GQA/MQA 减少 KV head 数量（从架构上直接降低 KV 体积）、KV 量化（int8/int4）压缩带宽、PagedAttention 做细粒度显存管理和共享、前缀缓存复用相同前缀的 KV、以及滑动窗口注意力、稀疏注意力、StreamingLLM 等减少有效 KV 长度的方案。所以结论是：长上下文的瓶颈主要不是算力，而是 KV Cache 带来的显存容量和访存带宽压力。

**常见追问**：1）GQA 是怎么减少 KV Cache 的？2）PagedAttention 解决的是什么问题？

## 103. Redis 里保存的是原始对话、摘要，还是 Agent 运行状态？

> 原题 ID：`q3975`

**高频程度**：★★★★

**考察点**：Agent 场景下 Redis 存什么：三层数据区分（原始对话、摘要、运行时状态）与 Redis 的定位。

**回答框架**：

1）原始对话：token 量大、需长期可追溯，通常落库，Redis 只做热缓存；2）摘要：派生数据，可放 Redis 加速读取，但要有持久化兜底；3）运行时状态：Redis 的核心用途——当前会话 messages 数组、system prompt 版本、工具调用结果、plan/scratchpad、当前 step、重试次数、超时、分布式锁、幂等 key、限流计数、SSE/WebSocket 连接映射；4）为什么用 Redis：多轮有状态、跨进程跨实例、低延迟；5）注意：关键状态要有持久化兜底，不能只靠 Redis。

**参考回答**：

回答这个问题要区分三层数据。第一层是原始对话，也就是用户与模型的完整消息列表。它的特点是 token 量大、需要长期可追溯和审计，所以通常落在 MySQL、Postgres 或对象存储里，Redis 只作为热缓存存在，用来加速最近几轮对话的读取，而且要有 TTL 和回源逻辑。第二层是摘要，也就是对历史对话的压缩结果，用于控制上下文窗口。它属于派生数据，可以放 Redis 加速读取，但同样要有持久化兜底，因为它也影响后续推理，丢了就相当于记忆中断。第三层是 Agent 运行时状态，这也是 Redis 最核心的用途，包括：当前会话的 messages 数组、system prompt 版本、工具调用的中间结果、plan 和 scratchpad、当前执行到第几步、重试次数、超时时间、以及分布式锁、幂等 key、限流计数、SSE 或 WebSocket 的连接映射等等。为什么这些放 Redis？因为 Agent 是多轮、有状态、而且可能跨进程跨实例的：每轮推理都要读上下文，需要低延迟；服务可能多副本部署，状态必须共享；还需要 TTL、原子操作和发布订阅这些能力，Redis 天然适配。同时也要说清边界：Redis 是内存存储，虽然可持久化但并非绝对不丢，所以关键状态（比如已确认的用户事实、订单相关中间态）必须有落库或重建机制，不能完全依赖 Redis；实践中常见做法是"Redis 存运行时热状态、数据库存权威数据"，Redis 挂了可以从库恢复会话上下文，代价是多花一点重建时间。

## 104. Redis 支持哪些数据结构？各自典型场景？

**考察点**：Redis 各数据结构与典型业务场景的一一对应。

**回答框架**：

1）String：缓存、计数、分布式锁；2）Hash：对象属性、部分字段更新；3）List：队列、最新列表、栈；4）Set：去重、交并差、抽奖；5）ZSet：排行榜、延迟队列、范围排名；6）Bitmap：签到、活跃统计；7）HyperLogLog：UV 基数估算；8）GEO：附近的人；9）Stream：消息流、消费组。

**参考回答**：

Redis 支持的数据结构及其典型场景可以一一对应。String 是最常用的，用于缓存值、计数器（INCR）、分布式锁（SET NX EX）、限流；Hash 是 field-value 结构，适合存对象属性，比如用户资料、商品信息，好处是可以只更新某个字段而不重写整个对象；List 是有序可重复的双端结构，适合做队列、栈、最新 N 条消息；Set 是无序不重复集合，适合去重、共同好友、抽奖、标签集合运算（交并差）；ZSet 是有序集合，每个成员带 score，适合排行榜、延迟队列（score 存时间戳）、按分数范围查询和排名；Bitmap 位图用于签到、活跃用户统计，极度省内存；HyperLogLog 用于 UV 基数估算，用极小的内存（12KB）估算海量去重计数，误差约 0.81%；GEO 用于附近的人、距离计算；Stream 是 Redis 5.0 引入的消息流结构，支持消费者组、消息确认、消息回溯，适合做轻量消息队列。总结成一句话的选型逻辑：要缓存和计数用 String，要存对象用 Hash，要队列和最新列表用 List，要去重和集合运算用 Set，要排序和排名用 ZSet，要位统计用 Bitmap，要估算基数用 HyperLogLog，要位置服务用 GEO，要可靠消息流用 Stream。

## 105. RDB 和 AOF 两种持久化区别？如何选型？

> 原题 ID：`q4058`

**高频程度**：★★★★★

**考察点**：RDB 快照与 AOF 命令日志的区别、刷盘策略与选型、混合持久化。

**回答框架**：

1）RDB：定时快照，文件小、恢复快，但可能丢最后一次快照后的数据；2）AOF：追加写命令，数据更安全，可设 everysec 刷盘，文件大、恢复慢；3）对比维度：数据安全、恢复速度、文件体积、对主流程影响；4）生产实践：AOF 保数据 + RDB 做备份/快速重启，或直接用混合持久化；5）Redis 7 支持 multi-part AOF。

**参考回答**：

RDB 是定时快照持久化，把某一时刻的全量内存数据以二进制写入磁盘。它的优点是文件紧凑、恢复速度快、对主流程影响相对可控（BGSAVE 用 fork 子进程），适合备份和快速重启；缺点是两次快照之间的数据会丢失，可能丢几分钟，而且实例内存大时 fork 本身会短暂阻塞、写时复制会带来额外内存开销。AOF 是追加日志持久化，记录每一条写命令，重启时重放来恢复数据。它的优点是数据更安全，用 appendfsync everysec 时最多丢 1 秒，always 时几乎不丢；缺点是文件比 RDB 大得多、恢复时要逐条重放所以慢，而且长期运行需要 AOF 重写来控制文件体积。从几个维度对比：数据安全性上 AOF 更好；恢复速度上 RDB 更快；文件体积上 RDB 更小；对主流程的影响上，RDB 主要是 fork 阻塞和 COW 内存开销，AOF 主要是刷盘开销（always 影响最大，everysec 可能有偶发阻塞）。选型上，生产环境通常两者结合：用 AOF 保证数据尽量不丢作为主要恢复手段，同时保留 RDB 用于周期性备份、灾难恢复和主从全量同步。如果不折腾两套，直接用混合持久化（aof-use-rdb-preamble，Redis 4.0+ 默认开启），AOF 文件前半部分是 RDB 格式的全量快照、后半部分是增量命令，兼顾恢复速度和低丢失率；Redis 7.0 还引入了 multi-part AOF，把基础文件和增量文件分离，优化了重写时的内存和磁盘开销。最后补一句判断依据：如果 Redis 只是纯缓存、数据能回源重建，持久化要求可以放低；如果把它当存储用，必须开 AOF 或混合持久化。

**常见追问**：1）为什么 AOF 恢复比 RDB 慢？2）multi-part AOF 解决什么问题？

## 106. 缓存穿透、击穿、雪崩分别是什么？如何解决？

> 原题 ID：`q4059`

**高频程度**：★★★★★

**考察点**：缓存穿透/击穿/雪崩的定义、触发条件与对应的解决方案。

**回答框架**：

1）穿透=数据不存在（缓存和库都没有）；解决：布隆过滤器、缓存空值、参数校验限流；2）击穿=单个热点 key 过期瞬间并发回源；解决：互斥锁重建、逻辑过期（不真删）、热点不过期；3）雪崩=大量 key 同时过期或 Redis 宕机；解决：过期时间加随机、多级缓存、高可用集群、熔断降级；4）一句话区分三者；5）治理要组合使用并有监控。

**参考回答**：

这三个概念要能一句话区分，再分别讲方案。缓存穿透是"数据不存在"：请求的数据在缓存和数据库里都没有，每次请求都绕过缓存直接打到数据库，典型是恶意用不存在的 ID 刷接口。解决方案：第一，缓存空值，查不到就写一个占位符并设较短 TTL，下次直接返回空，不再查库；第二，布隆过滤器在入口拦截，它说"不存在"就一定不存在，能挡掉绝大多数非法 key，注意有误判率且标准版不支持删除；第三，参数校验和限流，在网关层做格式和范围校验，对异常来源限流。缓存击穿是"单个热点 key 过期时的并发"：某个高并发热点 key 在过期瞬间，大量请求同时未命中，全部去查库并回写，形成瞬时冲击。解决方案：第一，用互斥锁或分布式锁，只让一个线程回源重建，其他线程等待或返回旧值；第二，逻辑过期，物理上不设 TTL，value 里带逻辑过期时间，发现过期后异步重建，其他请求先返回旧数据，没有空窗期；第三，对超热点数据干脆不设过期，靠后台任务定时刷新。缓存雪崩是"大量 key 同时失效或缓存整体不可用"：比如一批商品统一设了两小时过期同时失效，或者 Redis 节点/集群宕机，导致请求全压到数据库甚至把库打挂。解决方案：第一，过期时间加随机值，把失效时间打散；第二，多级缓存（本地缓存 + Redis）减少对 Redis 的依赖；第三，架构上做主从加哨兵或 Cluster 保证高可用；第四，必须有熔断降级和限流，数据库压力大时快速失败返回兜底内容，保护数据库。最后强调一点：这三者往往需要组合治理，并且要通过监控（缓存命中率、DB QPS、慢查询）来及时发现问题，而不是等出事再处理。

**常见追问**：1）三者的根本区别用一句话怎么概括？2）逻辑过期方案的核心思想是什么？

## 107. 主从复制、哨兵、集群分别解决什么？

> 原题 ID：`q4064`

**高频程度**：★★★★★

**考察点**：主从复制（读写分离）、哨兵（自动故障转移）、Cluster（分片水平扩展）各自解决的问题与 16384 槽。

**回答框架**：

1）主从复制：一主多从，读写分离、数据备份，但故障需人工切换、写能力和容量受限于主节点；2）哨兵：监控主从、自动判活选举、故障转移、通知客户端，解决高可用；3）Cluster：16384 个槽分片、多主多从、水平扩展，解决单机写入能力和容量上限；4）演进关系与组合方式；5）各自适用场景。

**参考回答**：

这三种模式分别解决不同层面的问题。主从复制解决的是"读扩展和数据冗余"：一主多从，写操作只在主节点执行，读请求分到从节点，实现读写分离提升读吞吐，同时从节点作为数据备份。它的局限是主节点仍是单点，故障需要人工切换，而且写能力和内存容量都受限于单机，主从复制还是异步的，切换时可能丢数据。哨兵解决的是"高可用"：在主从基础上增加一组哨兵进程，它们周期性 PING 监控节点存活，先标主观下线、达到 quorum 后标客观下线，然后选举 leader、从从节点中挑出新的主节点、通过发布订阅通知客户端切换，实现自动故障转移。它不解决容量和写扩展问题，本质还是主从，切换期间有短暂不可用，配置上哨兵建议部署奇数个以形成多数派。Cluster 解决的是"水平扩展"：把数据按 16384 个哈希槽分片到多个主节点，每个 key 通过 CRC16 取模定位槽，槽归属某个节点；每个主节点再挂从节点保证分片高可用。这样内存总量和写能力都能横向扩展，突破了单机的容量和写入瓶颈。代价是跨槽的多 key 操作受限（需要用 hash tag 把相关 key 放到同一槽）、客户端要支持集群协议、运维复杂度更高。演进关系上：单机 → 主从复制（解决读和冗余）→ 哨兵（解决高可用）→ Cluster（解决容量和写扩展）。实践中选型看需求：只读压力大就用主从；要求自动故障转移就用哨兵；数据量和写入量超过单机上限就必须用 Cluster。

**常见追问**：1）Cluster 模式下客户端怎么路由？2）哨兵和 Cluster 能不能一起用？

## 108. ZSet 底层如何实现？为什么能排序？

> 原题 ID：`q4066`

**高频程度**：★★★★★

**考察点**：ZSet 的双结构实现（跳表 + 哈希表）、各自负责的操作与复杂度、元素共享机制。

**回答框架**：

1）需求：既要按 score 排序做范围查询和排名，又要按 member 做单点查找；2）跳表：按 score 有序，支持范围查询 O(logN)、排名靠 span；3）哈希表：member→score 映射，单点查找 O(1)；4）两者共享同一份 member/score 元素，只多存指针和索引，不重复存数据；5）跳表层数随机（25% 晋升、最高 32 层），空间换时间；6）小规模时用 ziplist/listpack 编码。

**参考回答**：

ZSet 底层同时使用跳表和哈希表，目的是同时满足两类操作。ZSet 的核心需求有两个：一是按 score 排序做范围查询和排名，比如 ZRANGE、ZRANGEBYSCORE、ZRANK、ZREVRANGE；二是按 member 做单点操作，比如 ZSCORE 查分数、判断成员是否存在、ZINCRBY 加分。跳表按 score 有序组织数据，范围查询能找到起点后沿底层链表顺序遍历，复杂度 O(logN)，排名通过 span 字段（每层指针跨越的节点数）累加得到；哈希表存 member 到 score 的映射，单点查找和更新是 O(1)。如果只用跳表，单点查 member 要 O(logN)；如果只用哈希表，范围查询就得把所有元素取出排序，完全不可接受。关键实现细节是：这两个结构共享同一份 member 和 score 元素（通过指针指向同一个对象），并不会把数据存两遍，只多了一层索引和指针的开销，属于用空间换时间。另外跳表的层高是随机决定的——每个节点初始 1 层，每增加一层的概率是 25%，最高 32 层，这样平均查询复杂度能保持 O(logN) 且不需要像平衡树那样旋转再平衡。小规模时（元素少于 128 个且每个成员短于 64 字节）ZSet 会用 ziplist/listpack 紧凑编码省内存，超过阈值才切换到跳表加哈希表，这个转换是单向的。

**常见追问**：1）为什么说跳表和字典共享元素？2）ZRANK 怎么用 span 算出排名？

## 109. Pipeline 和事务（MULTI/EXEC）的区别？

> 原题 ID：`q4068`

**高频程度**：★★★★

**考察点**：Pipeline 与事务（MULTI/EXEC）的区别：网络往返优化 vs 原子性，以及各自是否支持回滚。

**回答框架**：

1）Pipeline：把多条命令批量发送、一次性收结果，减少 RTT，提升吞吐；服务端仍逐条执行，不保证原子性，中间可能插入其他客户端命令；2）事务 MULTI/EXEC：命令先入队，EXEC 时一次性按序执行，期间不会被打断（原子性）；3）共同点：都不支持回滚，运行时错误只影响该条命令；4）事务还有 WATCH 做乐观锁、DISCARD 放弃；5）选型：追求吞吐用 Pipeline，追求原子用事务或 Lua。

**参考回答**：

Pipeline 和事务是两个不同层面的东西。Pipeline 解决的是网络往返问题：正常情况下客户端发一条命令要等 Redis 回复，一次 RTT 就浪费了；Pipeline 的做法是把多条命令一次性打包发给服务端，服务端逐条执行后把结果一起返回，这样一条连接的 RTT 只花一次，吞吐能提升很多倍。要注意 Pipeline 不保证原子性，服务端仍然是逐条执行命令的，执行过程中完全可能插入其他客户端的命令，所以它只优化性能，不提供隔离或原子保证。事务 MULTI/EXEC 解决的是原子性问题：MULTI 之后命令不立即执行而是入队，直到 EXEC 才一次性按顺序执行，执行期间不会被其他客户端命令插入，形成了"打包原子执行"的效果；还有 DISCARD 放弃事务、WATCH 监视 key 做乐观锁（如果被其他客户端改动，EXEC 会失败）。两者的共同点是都不支持回滚：Redis 事务里如果某条命令在运行时出错（比如类型不匹配），只有那条命令失败，后面的命令照常执行，已经执行的也不会回滚；只有入队阶段就发现的错误（命令不存在、语法错）会让 EXEC 整体拒绝。所以严格说 Redis 事务不满足 ACID 的原子性。选型上：如果只是要减少网络开销、批量读写，用 Pipeline；如果需要命令之间不被打断，用 MULTI/EXEC；如果需要"判断加操作"这种真正需要原子的复合逻辑，最好的方式是把逻辑写进 Lua 脚本，它既能保证中间不被打断，又比事务更灵活。实践中 Pipeline 和事务也可以组合使用。

**常见追问**：1）为什么 Pipeline 不保证原子性？2）WATCH 失败后怎么处理？

## 110. 如何设计一个短链接系统（如 dwz.cn/abc）？

> 原题 ID：`q4116`

**高频程度**：★★★★★

**考察点**：短链接系统设计：发号与 62 进制编码、映射存储、302 跳转、缓存与布隆过滤、点击统计。

**回答框架**：

1）发号：分布式 ID（号段/Snowflake）或哈希，再转 62 进制压缩成长度短的码；2）存储：短码→长 URL 映射，Redis 缓存热点 + DB 持久化；3）跳转：302 临时重定向（便于统计，301 会被浏览器长期缓存）；4）高并发：缓存命中率是关键，布隆过滤器挡非法短码，限流防刷与防遍历；5）统计：点击计数异步落库；6）注意短码唯一性与防猜测（加随机盐或自增+混淆）。

**参考回答**：

设计短链接系统我会从四个环节讲。第一，短码生成，也就是发号。常见做法是用分布式 ID 生成器（号段模式或 Snowflake）产生唯一数字 ID，再转成 62 进制（0-9、a-z、A-Z）得到长度很短的字符串，比如 6 位 62 进制能表示约 568 亿个链接，足够用；也可以用哈希（MD5 取前几位）加冲突检测，但哈希方案有碰撞需要重试，自增 ID 加进制转换更可控。要注意防遍历和防猜测，自增 ID 直接转进制容易被顺序扫出来，可以加混淆（比如位运算打乱）或加随机盐。第二，存储。核心是短码到长 URL 的映射，用 MySQL 持久化保证不丢，Redis 做缓存承接热点读，因为跳转是极高频的读操作。第三，跳转。用户访问短链接时服务端查映射，然后返回 HTTP 302 重定向到原始长 URL。这里为什么用 302 而不是 301？因为 301 是永久重定向，浏览器和 CDN 会长期缓存，后续请求不再经过我们的服务器，就没法做点击统计和链接失效控制；302 是临时的，每次都会请求服务端，便于统计和灵活控制。如果对性能极致要求且不需要统计，也可以用 301，这是权衡。第四，高并发保障。跳转链路要尽可能快，重点在缓存命中率：可以把映射全部放 Redis，甚至在网关层直接查缓存并返回 302，DB 只做持久化和回源；用布隆过滤器快速挡掉不存在的短码，防穿透；入口做限流防刷、防恶意遍历；还要考虑缓存穿透、热 key 等问题。最后是统计，点击量这类数据一般不直接同步更新数据库，而是先在 Redis 里计数、通过消息队列异步落库，避免影响跳转性能。整体上这个题的重点是"短码唯一、跳转低延迟、防遍历、可统计"。

**常见追问**：1）为什么短链接一般用 302 而不是 301？2）短码怎么防止被顺序猜测？

## 111. 如何设计一个排行榜？

> 原题 ID：`q4120`

**高频程度**：★★★★★

**考察点**：排行榜设计：ZSet 实时排序、ZINCRBY 更新分数、ZREVRANGE 取 TopN、持久化与分片扩展。

**回答框架**：

1）核心结构：Redis ZSet，member 是用户/对象，score 是分数；2）更新：ZINCRBY 原子加分，或 ZADD 直接设置；3）查询：ZREVRANGE 取 TopN，ZREVRANK 查排名，ZSCORE 查分数；4）持久化：定时落库或通过消息队列异步写 DB，保证可恢复；5）扩展：数据量极大时按维度分片（比如按榜单 ID 或时间段），或分片 ZSet 加归并；6）注意大 key 与热 key 问题；7）时间维度榜单可用 key 加日期后缀。

**参考回答**：

排行榜最适合用 Redis 的 ZSet 实现，因为它天然按 score 排序且支持排名查询。具体设计：第一，数据结构，ZSet 的 member 存用户 ID 或对象 ID，score 存分数（比如积分、票数、热度值）。第二，更新，用户分数变化用 ZINCRBY 原子加分，或者用 ZADD 直接设置新分数，这两个操作都是 O(logN) 且原子，无需加锁。第三，查询，取前 N 名用 ZREVRANGE key 0 N-1 带 WITHSCORES，查某用户排名用 ZREVRANK，查分数用 ZSCORE，取某个分数区间用 ZRANGEBYSCORE；这些操作分别是 O(logN + M) 和 O(logN)，性能很好。第四，持久化，Redis 是内存存储，榜单数据需要落库，可以定时全量落库，或者用消息队列把分数变更异步写回 MySQL/数仓，重启或故障时从库里重建 ZSet；注意如果分数是实时算出来的，也可以选择不落库，靠源数据重算。第五，扩展与治理。数据量极大时（比如千万级用户的全站排行），单个 ZSet 会变成大 key 且占用大量内存，可以考虑：按维度拆分（比如按地区、按榜单 ID 分成多个 ZSet），或者按用户 ID 分片成多个 ZSet，取 TopN 时对每个分片取前 N 再归并；时间维度的榜单（日榜、周榜）用 key 加日期后缀，并对旧 key 设置过期或归档。第六，要关注热 key 问题：如果是全站超热榜单，可以加本地缓存、多副本打散。总结起来就是"ZSet 做实时排序、异步落库保证可恢复、分片解决大 key、本地缓存解决热 key"。

**常见追问**：1）分数相同时排名怎么处理？2）分片 ZSet 怎么归并出全局 TopN？

## 112. 如何设计一个『附近的人』功能？

> 原题 ID：`q4121`

**高频程度**：★★★★

**考察点**：附近的人功能设计：地理索引（GeoHash/Redis GEO）、半径查询与距离排序、精度与性能优化、城市维度预筛。

**回答框架**：

1）核心：把用户经纬度存入地理索引（Redis GEO 基于 ZSet + GeoHash，或 MySQL 空间函数）；2）写入：GEOADD 添加位置；3）查询：GEOSEARCH/GEORADIUS 按半径搜索并返回距离、排序；4）原理：GeoHash 把二维经纬度编码成一维字符串，前缀相同的点地理上邻近，可转成 ZSet 的 score 做范围查询；5）优化：按城市或网格预筛减少候选、控制返回数量、位置更新用异步；6）权衡：精度 vs 性能、隐私与权限。

**参考回答**：

附近的人核心是要支持"给定一个坐标和半径，找出范围内的点并按距离排序"。实现上主要有两种选择。第一种是用 Redis 的 GEO 能力，这是最常用的：GEOADD 把用户的经纬度加进去，GEOSEARCH（新命令，替代 GEORADIUS）可以按半径或矩形范围查询，并支持返回距离、按距离排序、限制返回数量。它的底层原理是 GeoHash——把二维的经纬度编码成一维字符串，地理上邻近的点前缀相同，Redis 再把它转成 ZSet 的 score，就能用 ZSet 的范围查询（ZRANGEBYSCORE）快速筛出候选，然后再精确计算距离排序。第二种是数据库方案，MySQL 有 ST_Distance_Sphere 等空间函数，PostGIS 这类专业地理库能力更强，适合需要复杂空间查询和事务的场景，但性能不如 Redis。工程上要注意几点：第一，精度和性能的权衡，GeoHash 编码位数越长精度越高、但匹配越严格，Redis 用的是 52 位精度，误差在米级以内，一般够用；第二，数据量大时要减少候选集，常见做法是先按城市维度或网格预筛，只在同一城市/网格内做半径查询，避免全国范围全量扫描；第三，用户位置更新频繁（比如骑手、司机），写入量很大，可以考虑异步更新、降低更新频率、或者用专门的时空数据库；第四，返回结果要限制数量并做分页，避免一次返回过多；第五，隐私与权限要考虑，比如只对已授权用户展示位置、做位置模糊化。整体思路是"地理索引做快速筛选 + 精确距离计算做排序 + 城市/网格预筛控规模"。

**常见追问**：1）Redis GEO 和 PostGIS 该怎么选？2）位置更新特别频繁怎么优化？

## 113. 如何设计一个短链接的高并发跳转？

> 原题 ID：`q4125`

**高频程度**：★★★★

**考察点**：短链接高并发跳转设计：Redis 映射、302 重定向、布隆过滤、62 进制压缩、命中率与延迟指标。

**回答框架**：

1）数据分层：短码→长 URL 映射全量放 Redis，DB 只做持久化与回源；2）链路极简：网关/Nginx 层直接查缓存并返回 302，避免多次应用跳转；3）拦截：布隆过滤器挡非法短码，防穿透与遍历；4）短码压缩：62 进制编码减少长度；5）高可用：Redis 主从/Cluster，热点短链本地缓存；6）指标：压测重点看缓存命中率与重定向延迟，异步做点击统计。

**参考回答**：

短链接高并发跳转的设计核心是"把跳转链路做到极短、把数据放到离请求最近的地方"。第一，数据分层：短码到长 URL 的映射优先全量放 Redis，因为跳转是纯读、量极大且 KV 简单，Redis 内存完全放得下千万到亿级的映射；MySQL 只做持久化和缓存未命中时的回源。第二，链路极简：把查询和重定向尽量前置，比如在 Nginx/OpenResty 或网关上直接查 Redis 并返回 302，不必再经过多层应用服务和 RPC 调用，减少网络跳数和序列化开销；如果热点短链特别集中，还可以再加一层应用本地缓存（Caffeine）或 Nginx 层缓存。第三，拦截非法请求：用布隆过滤器判断短码是否存在，不存在的直接返回 404，避免大量不存在的短码穿透到 Redis 和 DB，同时也防止被遍历探测。第四，短码压缩：短码用 62 进制（数字+大小写字母）编码，同样的 ID 空间下长度更短，能减少存储和传输开销。第五，高可用：Redis 用主从加哨兵或 Cluster 保证不成为单点，热点短链可以做多副本打散防热 key，缓存穿透和击穿也要按常规方案防。第六，统计别挡路：点击量这类写操作不同步更新数据库，先在 Redis 计数并用消息队列异步落库，保证跳转路径只有读操作。压测和监控的重点指标是缓存命中率和重定向延迟（P99），因为命中率直接决定 DB 压力和整体吞吐；同时要监控 302 的响应时间、Redis 的 QPS 和延迟，以及短码生成侧的唯一性和冲突率。整体目标就是：跳转路径只有"查缓存 + 返回 302"两步，其他动作全部异步化。

**常见追问**：1）跳转在网关层做会有什么限制？2）短链热 key 怎么处理？
